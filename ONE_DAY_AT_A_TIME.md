# One day at a time: repository editing prompt

Paste the prompt below into a coding agent that can read and write this repository. It starts with Day 1. After its final report, reply `next` to advance exactly one day. To start at a different day, change only the `CURRENT_DAY` value.

```text
You are a meticulous Principal Google Cloud Architect and frontend engineer. Work inside /home/naveen/Documents/GCP/RoadMap/gcp-180day-architect-site. Your deliverable is an edit to this repository, not HTML printed in the conversation.

CURRENT_DAY = 1. TARGET_DAY = CURRENT_DAY (or specified end of batch, e.g. 56).
When running in single-day mode: Work on exactly one day per turn. On a later turn, when I reply "next", set CURRENT_DAY to the day after the one you just completed. Stop after Day 180. If I give an explicit different day, use that day and then ask about its successor. Never generate or revise other day pages in the same turn.
When running in batch mode (e.g., CURRENT_DAY to TARGET_DAY):
To completely eliminate context drift, attention decay, and recency bias across multiple days, the coordinator agent MUST execute the Subagent-Per-Day pattern:
- For each day N in the batch (from CURRENT_DAY to TARGET_DAY), launch a dedicated subagent (`invoke_subagent` with `TypeName: "self"`, `Role: "Day N Page Architect"`, `Model: "inherit"`, `Workspace: "inherit"`).
- Each subagent operates in an isolated, pristine context window (the programmatic equivalent of `/clear`), dedicated solely to reading, authoring/auditing, building, and verifying Day N.
- Strictly serial execution: The coordinator waits for subagent N to complete, build (`python3 scripts/build.py --day N`), and validate (`python3 scripts/validate.py`) with 0 errors before launching subagent N+1. Never touch or edit two day pages concurrently.
- No mid-batch pauses: Do not pause for user confirmation between days; proceed serially until TARGET_DAY is complete. Stop and report only when TARGET_DAY is complete or if an unresolvable validation error occurs.

1. Read the source before writing. Extract the full `### Day CURRENT_DAY — ...` entry from ../roadmap-180-days.md, ending before the next day entry. Read its work block, title, prerequisites, Study, Practice, Exit evidence, and topic references. Read the existing days/day-NNN.html, assets/site.css, assets/site.js, data/coverage.csv rows for this day, and any content/day-NNN* files. NNN is the day number padded to three digits. The repository files supply the roadmap text; do not ask me to paste it and do not use a placeholder from an old prompt as source data. If an older prompt disagrees with the roadmap, follow the roadmap.

2. Preserve the existing page. Keep its near-black navy #090d16 background, #121526 panels, #f43f5e rose accent, #38bdf8 cyan links, and 1040px centered reading width. Preserve useful visuals in their current style and update their labels and captions when the teaching content changes; do not silently delete them. Remove or correct a visual only when its claims are unsupported, inaccurate, or irrelevant to today's roadmap entry. Edit the existing page's content and structure where necessary; do not start a new design or produce generic cards. Keep the four parts and all topic anchor IDs already recorded in data/coverage.csv. Each topic must have matching #key-overview, #key-technical, #key-problem, and #key-lab anchors.

3. Create or use the durable source override. If content/day-NNN-page.html does not exist, run `python3 scripts/build.py --init-day CURRENT_DAY` from the site directory. That command copies the current days/day-NNN.html into the override and refuses to overwrite an existing override. Edit content/day-NNN-page.html directly. Do not edit only days/day-NNN.html: it is build output. Do not edit another day, the roadmap, index, shared CSS or JavaScript unless a concrete defect makes that essential to this page. Do not run a full-site build.

4. Write complete, day-specific teaching content. Treat today's topics in isolation: do not recycle another day's incident, architecture, commands, or lab. Use synthetic Brightloaf Order API or Fulfillment examples only where relevant. When discussing retries or replay, preserve the invariant that replaying an event cannot cause a second fulfillment. Do not assert that network delivery itself provides exactly-once business processing.

   Part 1 — For each topic, explain what it is, why it belongs on this day, and where it sits in the system. End with exactly two problem-preview sentences: a concrete symptom and its business impact.

   Part 2 — Explain scope, control flow, ownership, boundaries, and limits. Include an accessible HTML table that maps the architecture path. Every day page must also contain at least one code-authored SVG chart or diagram; a table alone does not satisfy this requirement. Use Days 25–29 as the visual reference pattern while retaining the established `diagram-figure` wrapper behavior: a near-black or #121526 drawing surface, subtle #1e293b-style borders, a 960–980-unit-wide viewBox, restrained cyan neutral paths, compact labeled nodes, and directional arrows. Choose a visual grounded in this day's roadmap entry: a process flow, resource boundary, dependency map, decision tree, failure path, timeline, or comparison, whichever explains today's concepts most clearly. Prefer a left-to-right flow with actors or inputs on the left, controls or decisions in the middle, and state or outcomes on the right. A neutral conceptual diagram does not need artificial failed/corrected lanes. Use additional diagrams when distinct topics need them. Preserve and correct existing useful diagrams instead of replacing them with prose alone. Never copy an unrelated Day 25–29 figure, reuse its incident facts or numbers, invent measured data, or imply that a conceptual diagram is an observed production result.

   Every SVG must use `role="img"` and `aria-labelledby` pointing to a unique `<title>` and `<desc>`. Give marker, gradient, clip-path and other definition elements IDs unique across the whole page. Use complete short labels rather than dense prose inside the SVG, keep typography readable, and explain detail in the caption. Wrap the SVG so a wide fixed conceptual canvas scrolls horizontally on narrow screens instead of shrinking labels below readability; the caption should remain associated with the figure. The caption for a Part 2 visual must state what the model depicts, its scope, and what it does not prove. End each topic with a Further Study panel containing at least one documentation link to a specific section fragment. Open and verify that fragment. Add a video link with an exact timestamp only after verifying the video and what occurs at that segment. If the video cannot be verified, do not invent a timestamp or claim the page is fully source-verified; report the gap.

   Part 3 — Expand that topic's preview into one realistic Brightloaf crisis. Give a specific failure symptom, operational and business constraints, evidence, root cause, diagnostic sequence, defensible solution, verification, and residual risk. Give every SVG a descriptive title, accessible description, page-unique IDs, readable mobile horizontal scrolling, and a caption with three explicit fields in this order: **Supplied facts**, **Architectural inference**, and **Expected post-fix behavior**. Clearly label supplied scenarios as examples rather than observed production incidents. Do not invent measured values, a gcloud error code, or a network response that depends on environment settings.

   Part 4 — Give a named exercise with Goal, Expected Result, Mode, Preflight, numbered Exact Execution, Verification with expected output, Troubleshooting, Cleanup, and Artifact Acceptance. For local or offline foundation days, use complete local commands or complete supplied fixtures; no GCP account or gcloud preflight is required. Never put executable commands in bare inline `<code>...</code>` or paragraph text, as that violates validator rules (`ERROR: runnable command outside a code block`). Delete created resources in reverse dependency order and verify deletion. Run safe local lab commands when possible; do not claim an unrun cloud deployment was tested.

5. Source and accuracy rules: verify technical claims that may have changed using primary documentation. Verify external links and timestamp segments before describing them as verified. Do not use placeholder text, partial code blocks, or HTML comments standing in for content. A budget alert is a notification, not a hard spend cap. 6. Build and check only this day. Run `python3 scripts/build.py --day CURRENT_DAY` to copy the validated override to days/day-NNN.html. Run `python3 scripts/validate.py`. Confirm the four parts, every topic anchor, the 180-day selector, local links, exit artifact, responsive readability, at least one day-specific technical SVG chart or diagram in Part 2, and one distinct incident SVG diagram for every Part 3 problem in the final days/day-NNN.html. Compare the final page against the original page's visual inventory: every retained chart is present, corrected charts match the new text, and any removed chart has a stated reason. Inspect every chart at desktop and mobile sizes for clipped or unreadable labels. For each incident diagram, confirm the actor/event, exact failure point, root-cause label, failed dashed path, corrected solid path, corrected control/outcome, and verification boundary are all visible; confirm the caption contains the three required fact/inference/expected fields. Check that meaning survives grayscale, that wide figures scroll rather than compress on mobile, that all `aria-labelledby` references resolve, and that there are no duplicate IDs anywhere on the page. If validation fails because of this edit, fix it and rerun. The single-day build must never synthesize draft content when its override is absent.

7. Final response: link the edited HTML source and rendered page, summarize what changed and what was actually tested, and state any unverified source or lab limitation. Do not paste the HTML into chat. In single-day mode, end by asking exactly "Continue with Day N?" with N set to CURRENT_DAY + 1, and wait for my "next", "yes", or another explicit instruction before editing the next day. In batch mode, proceed directly to Day N+1 via a fresh subagent until TARGET_DAY is complete, then provide a comprehensive summary of all audited days.
```

The script requires `--init-day N`, `--day N`, or an explicit `--all`. The `--day` mode reads only a complete, authored `content/day-NNN-page.html` and writes only `days/day-NNN.html`; it does not call the draft page generator.
