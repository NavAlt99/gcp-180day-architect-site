<!-- topic-01:overview -->
A hypervisor runs virtual machines (VMs) by presenting virtual hardware to each guest. A VM has its own guest operating-system kernel and userspace. A Type 1 hypervisor runs directly on host hardware; a Type 2 hypervisor runs as software on a host operating system.

<!-- topic-01:technical -->
Virtualization lets several guest systems share physical CPU, memory, storage and networking while maintaining separate OS environments. The hypervisor schedules virtual CPUs and maps guest memory and devices to host resources. A guest can run a different kernel from its neighbor; a kernel crash in one guest does not ordinarily mean every other guest's kernel crashed. Isolation still depends on the hypervisor, host configuration and shared physical resources. A VM can also be overcommitted or starved for CPU and storage even when its guest reports a healthy process.

Cloud VMs add an API and service layer for image selection, machine size, disks, network interfaces and lifecycle. The customer commonly controls the guest OS, patching and application, while the provider manages the underlying host infrastructure. A container differs because its processes share the host kernel. Choosing a VM can be appropriate for stronger kernel separation or OS customization, but it does not remove the need for guest hardening, backups and observability.

**Further study:** [Docker's container and VM discussion](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/) and [Compute Engine instances](https://docs.cloud.google.com/compute/docs/instances#introduction).

<!-- topic-01:problem -->
**Failure:** An architect puts a legacy workload requiring a custom kernel module inside a standard Linux container and expects it to load independently of the host.

**Cause:** The container shares the host kernel. A container image packages userspace files, not an independent guest kernel. The kernel-module requirement crosses the container isolation boundary.

**Fix:** Reassess the workload requirement. Use an appropriately managed VM or redesign the dependency so the host provides the needed capability under an approved policy. Document the guest patch and security owner. Giving the container broad host privileges can make the module appear to work but weakens isolation and does not create a guest kernel.

<!-- topic-02:overview -->
Linux containers isolate processes through kernel mechanisms. Namespaces give processes separate views of resources such as PIDs, networks, mounts, IPC, hostnames and user IDs. Cgroups account for and limit resource use. Seccomp filters system calls, while capabilities divide privileged operations into narrower units.

<!-- topic-02:technical -->
Namespaces answer “what can this process see?” A PID namespace changes the visible process IDs; a network namespace has its own interfaces and routing view; mount, IPC, UTS and user namespaces isolate other kernel names and identities. Cgroups answer “how much resource can this group consume?” Cgroup v2 exposes controls such as CPU and memory limits. Reaching a memory limit can kill a process inside a container even while the host has free RAM. Seccomp can restrict system-call use, and capabilities can grant or withhold specific privileged operations. None of these mechanisms alone is a complete security boundary; the runtime configuration and host kernel still matter.

A container is therefore a host-kernel process with configured isolation, not a small VM. Container root may map to a different host user when user namespaces are configured, but being root inside a container does not automatically mean unrestricted host control. Conversely, privileged mode and broad mounts can give a container dangerous access. Architects should inspect the effective namespace, cgroup and privilege configuration rather than relying on the word “container.”

**Further study:** [Linux namespaces manual](https://man7.org/linux/man-pages/man7/namespaces.7.html#DESCRIPTION), [Linux cgroup v2 guide](https://docs.kernel.org/admin-guide/cgroup-v2.html), [Linux seccomp filter guide](https://docs.kernel.org/userspace-api/seccomp_filter.html#introduction), and [Linux capabilities manual](https://man7.org/linux/man-pages/man7/capabilities.7.html#DESCRIPTION).

<!-- topic-02:problem -->
**Failure:** A containerized worker restarts repeatedly even though the VM's free-memory graph looks comfortable.

**Cause:** The worker's cgroup memory limit is smaller than host RAM, and its usage reaches that limit. Host free memory does not override the cgroup boundary. A broad seccomp error would produce a different failure signature.

**Fix:** Inspect the worker's cgroup path, configured memory limit and memory events at the restart time. Reduce its working set or set a justified limit, then rerun with a bounded synthetic workload. Keep the security profile narrow; disabling seccomp or adding broad capabilities would not fix a memory-limit event.

<!-- topic-02:lab -->
**Goal:** Inspect your current Linux process's isolation facts and, if a disposable local container runtime exists, compare them with a container. **Mode:** read-only terminal. No cloud resources.

### Step 1 — Observe the current process

Open a Linux terminal and run:

```sh
printf 'PID=%s\n' "$$"
readlink /proc/self/ns/pid /proc/self/ns/net /proc/self/ns/mnt /proc/self/ns/user
cat /proc/self/cgroup
grep -E '^(CapEff|Seccomp):' /proc/self/status
```

Expected: namespace identifiers, a cgroup membership line and effective-capability/seccomp fields. Exact values vary by host. `/proc/self` in separate commands refers to each command process; for comparing the same process over time, use the captured shell PID in your note. Do not infer that a seccomp field alone proves a complete sandbox.

### Step 2 — Compare with a local container if available

If you already have an approved disposable Docker installation and a local image, run a container that reads only its own `/proc` view. Replace `IMAGE_NAME` with a known local image name; do not pull an unfamiliar image merely for this step.

```sh
docker image ls
docker run --rm --read-only --network none IMAGE_NAME sh -c 'readlink /proc/self/ns/pid /proc/self/ns/net; cat /proc/self/cgroup; grep -E "^(CapEff|Seccomp):" /proc/self/status'
```

Expected: values may differ from the host, depending on the runtime configuration. If Docker or a suitable image is unavailable, mark this comparison “not observed” and use the host output plus the source reading. Never label an assumed namespace difference as observed.

### Step 3 — Explain two boundaries

In your worksheet, identify one namespace view and one cgroup resource-control fact, then explain why neither is a separate guest kernel. **Verification:** the worksheet distinguishes visibility, resource enforcement and privilege filtering. **Cleanup:** the optional container exits with `--rm`; confirm no container remains. No image is pulled by this lab and no cloud resource exists.
