Reproduce, diagnose and restore the integrated application

Enterprise cloud architecture transitions from theoretical design to operational maturity through deterministic reproducibility and automated fault recovery. While Day 65 integrated Brightloaf's baseline order flow across managed services, Day 66 subjects that baseline to the operational crucible: rebuilding the complete multi-tier topology from declarative Infrastructure as Code (IaC) manifests and controlled gcloud workflows, methodically injecting critical failure modes across datastore, messaging, and identity boundaries, and establishing defensible recovery procedures measured by strict Recovery Time Objectives (RTO) and Mean Time to Recovery (MTTR). The reproducible baseline encompasses a Global external Application Load Balancer (ALB) terminating client HTTPS with Cloud Armor defense-in-depth, routing through Serverless Network Endpoint Groups (NEGs) to containerized order-service instances on Cloud Run. The runtime tier leverages Direct VPC Egress allocated across a dedicated /24 subnet to privately reach Cloud SQL for PostgreSQL Regional High Availability via Private Service Connect (PSC endpoint 10.128.0.50/32), completely bypassing public IP exposure. Transaction events dispatch to a Cloud Pub/Sub topic (orders.v1) enforcing strict ordering keys and Dead-Letter Topic (DLT) quarantine policies, ingested by an asynchronous fulfillment worker operating under least-privilege Cloud Run Invoker IAM service account perimeters.

Architecting for failure requires mastering three distinct failure injection vectors: (1) Datastore Loss and Connection Exhaustion, evaluating decoupled /healthz (liveness) and /readyz (readiness) probe mechanics and client-side circuit breakers when PSC routes fail or connection limits saturate; (2) Poison Pill Payload Quarantine, validating that malformed or unprocessable messages with active ordering keys are redirected to a dead-letter queue after maxDeliveryAttempts: 5 without inducing permanent head-of-line blocking on customer message partitions; and (3) Identity Token Breach and Perimeter Defense, proving that unauthenticated or unauthorized callers are decisively rejected at the Google Front End (GFE) proxy layer with HTTP 401 Unauthorized and HTTP 403 Forbidden responses before consuming compute resources. Furthermore, architects must rigorously evaluate multi-runtime trade-offs—contrasting Cloud Run's zero-to-N serverless agility against GKE's Pod-level networking, Compute Engine MIGs' stateful kernel control, and Cloud Functions' single-event triggers—while enforcing a deterministic, reverse-dependency resource teardown lifecycle that prevents costly orphaned cloud infrastructure and lingering IP reservation leaks.

A silent Private Service Connect network partition during database failover trips connection pools without failing container liveness probes, while an unquarantined poison pill message permanently stalls the regional Pub/Sub ordering partition. The resulting hanging socket storm and head-of-line fulfillment blockage cause 24,000 order checkouts to hang until gateway timeout, stranding $168,000 in revenue and accumulating $14,200 in orphaned cloud billing leaks during disaster recovery.

1. The Imperative of Reproducibility: Declarative IaC & Network Topology

In enterprise cloud engineering, an infrastructure configuration that cannot be recreated deterministically from source code is an unquantified liability. While single-service tutorials encourage ad-hoc console provisioning, production architectures must adhere to the Declarative Reproduction Discipline: every managed resource, network route, security perimeter, and IAM binding must be expressed in auditable Infrastructure as Code (Terraform / OpenTofu) or fully scripted gcloud workflows. Rebuilding the integrated retail order baseline for Brightloaf requires instantiating five tightly coupled layers in strict dependency order:

  1. VPC Networking & Private IP Foundations: A regional custom-mode VPC network (brightloaf-vpc) hosting a dedicated /24 subnet (10.128.10.0/24) reserved exclusively for Cloud Run Direct VPC Egress. Unlike legacy Serverless VPC Access connectors—which required dedicated /28 subnets and provisioned underlying Compute Engine connector instances that introduced throughput ceilings, scaling lag, and cold-start latency—Direct VPC Egress binds container instances directly to elastic network interfaces (subinterfaces) inside the VPC, drawing up to 251 available private IP addresses with wire-speed throughput and zero intermediate VM hops.
  2. Private Service Connect (PSC) Datastore Endpoints: A Regional High Availability Cloud SQL for PostgreSQL 16 instance configured across primary zone us-central1-a and standby replica zone us-central1-f. The instance is published via Private Service Connect to a private endpoint forwarding rule inside brightloaf-vpc at IP 10.128.0.50/32 on TCP port 5432. PSC completely supersedes legacy VPC Peering for managed databases by eliminating RFC 1918 IP address overlap collisions, preserving customer VPC route autonomy, and preventing transitive routing vulnerabilities.
  3. Container Runtime Tier (Cloud Run): The containerized order-service API runtime deployed with Direct VPC Egress enabled (--network=brightloaf-vpc --subnet=order-egress-subnet --vpc-egress=private-ranges-only). Running on Google's hardened gVisor microVM sandbox, the service operates under a dedicated least-privilege service account (sa-order-service@...) possessing only roles/cloudsql.client and roles/pubsub.publisher.
  4. Asynchronous Event Fabric with Dead-Letter Topic: A Cloud Pub/Sub topic (orders.v1) enforcing message ordering via ordering_key = order_id. The downstream fulfillment worker ingests messages via a pull subscription (orders.v1.fulfillment-sub) configured with a strict dead-letter policy: deadLetterTopic = projects/brightloaf-prod/topics/orders.v1.dlq with maxDeliveryAttempts = 5.
  5. Edge Security & Global Ingress: A Global external Application Load Balancer terminating client HTTPS via Google-managed TLS 1.3 certificates, protected by Cloud Armor rate-limiting (2,000 QPS per source IP) and pre-configured OWASP Top 10 rulesets, dispatching traffic to the Cloud Run service via a Serverless Network Endpoint Group (NEG).

2. Controlled Failure Injection: Probes, Circuit Breakers & Quarantine

Resilience cannot be asserted; it must be verified under synthetic stress. The architecture incorporates three controlled failure injection probe points designed to test system boundaries under realistic failure conditions:

Failure Injection 1: Datastore Network Partition & Pool Exhaustion

Relational databases represent the most fragile stateful component in cloud microservices. When a database failover occurs, or when a network route to the PSC endpoint is severed, client applications that lack decoupled health checking rapidly enter a catastrophic failure loop. If the application exposes a monolithic health probe (/healthz) that checks database connectivity and fails when the database is unreachable, Cloud Run interprets the failure as a container crash and continuously kills and restarts instances. This triggers a cold-start reboot storm: hundreds of restarting containers simultaneously flood the recovering database with fresh TCP handshakes, SSL negotiations, and pool warm-up queries, causing immediate secondary connection pool collapse.

To eliminate this failure mode, the baseline architecture enforces Decoupled Dual-Probe Architecture:

  • Liveness Probe (/healthz): Validates only that the HTTP process is running, event loops are unblocked, and local memory thresholds are healthy. Returns HTTP 200 OK regardless of downstream database availability, preventing Cloud Run from initiating destructive container restarts during transient infrastructure outages.
  • Readiness Probe (/readyz): Actively executes a fast connection validation against the database pool (SELECT 1 with a strict 1,000ms timeout). If the PSC endpoint is unreachable or the pool is saturated, /readyz immediately returns HTTP 503 Service Unavailable. The upstream Global ALB detects the readiness probe failure and instantly purges the container instance from the healthy backend pool, preventing user checkout requests from being routed to a crippled backend.
  • Client-Side Circuit Breaker: The application runtime wraps database operations in a circuit breaker pattern (e.g., PyBreaker). Upon detecting 3 consecutive socket timeouts to 10.128.0.50:5432, the circuit transitions from CLOSED to OPEN. In the open state, incoming checkout requests fail immediately with HTTP 503 and a Retry-After: 30 header in under 3 milliseconds, rather than blocking container threads for the full 60-second GFE gateway timeout.
Failure Injection 2: Poison Pill Payload & Head-of-Line Blocking Prevention

In distributed event-driven systems utilizing ordering keys, a poison pill is a malformed, corrupted, or schema-violating message that cannot be processed by the consumer logic. In Cloud Pub/Sub, when message ordering is enabled (enable_message_ordering = true), the broker guarantees that messages published with the same ordering_key are delivered to subscribers in the exact order received. However, this architectural guarantee introduces a severe vulnerability: Head-of-Line (HoL) Blocking. If consumer logic throws an unhandled exception (e.g., JSON syntax error, missing mandatory attribute, or database constraint violation) and NACKs the message, Pub/Sub redelivers the identical failed message on the next pull. Because the broker cannot violate FIFO ordering, all subsequent valid messages queued behind that ordering key remain permanently stuck in the subscription backlog.

The baseline mitigates this vulnerability by configuring a Dead-Letter Topic (DLT) with Retry Bound:

  • The subscription specifies maxDeliveryAttempts = 5 pointing to orders.v1.dlq.
  • When the fulfillment consumer encounters a corrupted payload, it logs the exception with full W3C trace correlation and NACKs the message. Pub/Sub increments the delivery counter.
  • Upon the 5th consecutive delivery failure, Pub/Sub's broker service agent automatically forwards the poison message to the dead-letter topic and automatically acknowledges the message on the primary subscription.
  • The ordering key partition is instantly unblocked, allowing subsequent valid customer orders to resume processing within seconds. A Cloud Monitoring alert triggers immediately on pubsub.googleapis.com/subscription/dead_letter_message_count > 0, paging on-call engineers to inspect the quarantined payload in the dead-letter queue without customer-facing downtime.
Failure Injection 3: Identity Token Breach & Perimeter Rejection

Security defense-in-depth requires verifying that unauthorized callers are rejected at the edge before consuming backend compute or memory resources. Cloud Run provides built-in IAM authentication enforced directly at the Google Front End (GFE) proxy layer:

  • Unauthenticated Requests (Missing / Expired Bearer Token): The client dispatches a request without an Authorization: Bearer <id_token> header. The GFE terminates the request at the edge, returning HTTP 401 Unauthorized with zero container invocation, preserving backend compute capacity.
  • Unauthorized Principals (Invalid IAM Invoker Role): A caller presents a valid Google-signed OIDC token issued to a service account or user that has not been granted roles/run.invoker on the Cloud Run service. The Cloud Run IAM authorizer evaluates the policy and returns HTTP 403 Forbidden.
  • Audit Evidence: Every rejected request generates an immutable audit record in Cloud Logging with protoPayload.status.code = 7 (PERMISSION_DENIED), enabling automated Security Command Center alerts and rate-based IP banning via Cloud Armor.

5. Rigorous Inventory & Teardown Dependency Ordering (LIFO)

Cloud resource destruction is governed by strict mathematical directed acyclic graph (DAG) dependencies. Deleting infrastructure out of order results in dependency deadlocks (e.g. attempting to delete a VPC subnet while a Cloud Run Direct VPC Egress subinterface holds an active IP allocation) or leaves orphaned resources that quietly accumulate thousands of dollars in unbudgeted billing leaks. To ensure safe, deterministic teardown, architects must enforce a strict Last-In, First-Out (LIFO) Reverse-Dependency Deletion Order across five operational phases:

Teardown Phase Resource Type & Scope Target GCP Resources Reverse Dependency Constraint Orphan Risk & Billing Leak Prevention
Phase 1: Ingress Edge & Forwarding Global Networking & Security Global forwarding rules, target HTTPS proxies, URL maps, SSL certificates, Cloud Armor policies, Serverless NEGs. Must be deleted before compute backends; otherwise ingress proxies attempt to route traffic to non-existent runtimes. Orphaned external forwarding rules and unattached static IP addresses incur hourly reservation fees if unreleased.
Phase 2: Compute Runtimes & IAM Serverless Workloads Cloud Run services (order-service, fulfillment-service), IAM policy bindings, Secret Manager IAM bindings. Must be destroyed before subnets; deleting Cloud Run releases dynamic Direct VPC Egress IP allocations in the VPC subnet. Active Cloud Run min-instances continue billing for idle provisioned vCPU/memory if left running in background.
Phase 3: Messaging & Event Bus Asynchronous Messaging Pub/Sub pull subscriptions, Dead-Letter Topics (orders.v1.dlq), primary topic (orders.v1), Pub/Sub IAM roles. Subscriptions must be detached before topics can be deleted; drain or purge dead-letter messages prior to deletion. Subscriptions retain unacknowledged messages for 7 days, incurring message storage charges and persistent backlog metrics.
Phase 4: Data Layer & Private Access Managed Datastores Private Service Connect forwarding rules (10.128.0.50), Cloud SQL HA instances (primary + standby), automated backup policies. PSC forwarding rule must be deleted before releasing VPC subnet IP; Cloud SQL termination protection must be explicitly disabled. Cloud SQL Regional HA instances represent the single highest hourly billing cost; orphaned instances leak $300–$1,200/month.
Phase 5: Network Foundations & IPs Core VPC Infrastructure Dedicated Direct VPC Egress subnet (10.128.10.0/24), VPC firewall rules, Cloud NAT gateways, static external IPv4 addresses. Subnets cannot be deleted until all NIC subinterfaces, PSC rules, and router attachments are completely released. Reserved external static IP addresses not bound to an active forwarding rule or VM incur idle reservation fees ($0.010/hr).
Apply it: Diagnostic Triage Sequence

Scenario: Client checkouts are failing with HTTP 504 Gateway Timeout. SREs observe that Cloud Run container instances are alive and CPU utilization is under 15%.

Step-by-step Triage:

  1. Inspect Cloud Trace: Query traces with http.status_code=504. Confirm the bottleneck span: if the root span stalls for 60,000ms inside database connection acquisition, the failure is in the datastore layer.
  2. Evaluate Decoupled Probes: Check /healthz versus /readyz. If /healthz returns 200 but /readyz returns 503, the container runtime is healthy but connection pooling to PSC 10.128.0.50:5432 is severed.
  3. Audit PSC Endpoint Status: Inspect forwarding rule operational status and target service attachment connectivity using the Compute API or gcloud compute forwarding-rules describe psc-cloudsql-endpoint --region=us-central1.
  4. Containment: Trip the application circuit breaker to OPEN, forcing instant HTTP 503 with Retry-After headers. This sheds load, preserves user sockets, and enables Cloud SQL HA failover to complete cleanly.

3 · Real-world problem and solution for each topic

Brightloaf Retail Flash-Sale Cascade: Unhandled Cloud SQL PSC Disconnection, Poison Pill Deadlock in Fulfillment Consumer, and Orphaned Infrastructure Billing Leak · field case

Situation and impact: On Black Friday at 14:00 UTC, Brightloaf launched a flash promotion featuring a 40% discount on artisan bakery subscriptions across North America. Traffic instantly surged from a baseline of 400 QPS to 8,000 QPS. Within 90 seconds of promotion launch, three compounding catastrophic failures struck the integrated production stack:

  1. Unhandled Cloud SQL Failover & Socket Exhaustion: An underlying hardware degradation in GCP zone us-central1-a triggered an automated Cloud SQL Regional HA failover to standby zone us-central1-f. During the 120-second DNS and routing convergence window, TCP connections to the Private Service Connect endpoint (10.128.0.50:5432) were severed. Because the Cloud Run order-service only had a superficial liveness probe (/healthz) returning 200 OK and lacked an application-level circuit breaker, incoming checkout requests blocked indefinitely on database connection acquisition. Within 45 seconds, all 100 container worker threads across 80 autoscaled Cloud Run instances were paralyzed waiting for database sockets. The Global ALB reached its 60-second backend timeout on 24,000 customer checkout requests, returning HTTP 504 Gateway Timeout and stranding $168,000 in checkout transactions.
  2. Poison Pill Deadlock & Head-of-Line Blocking: A third-party mobile checkout client running an outdated SDK published an order containing a malformed, non-UTF8 binary character in the customer delivery instructions with ordering_key = "cust_98412". The order-service committed the order and dispatched it to Pub/Sub topic orders.v1. When the background fulfillment-service worker pulled the message, the Python JSON parser raised an unhandled UnicodeDecodeError. Because the pull subscription (orders.v1.fulfillment-sub) had been provisioned without a Dead-Letter Topic, the worker crashed without acknowledging the message. Pub/Sub immediately redelivered the poison message. Because message ordering was strictly enabled on the subscription, Pub/Sub halted delivery of all subsequent messages sharing that ordering key partition. Over the next two hours, 8,200 valid customer orders queued behind the poison pill in the same partition were completely frozen, resulting in $42,000 in cancelled orders and customer service concessions.
  3. Emergency Staging Proliferation & Orphaned Billing Leak: During the incident response, an on-call engineer deployed an emergency staging replica to reproduce the database failure. The engineer provisioned 3 Regional HA Cloud SQL instances (db-custom-16-64), 10 static external IPv4 addresses, and 4 Cloud Run services. After resolving the immediate production issue, the engineer manually deleted the Cloud Run services via the GCP Console but omitted the Cloud SQL instances, PSC endpoints, and reserved static IPs. Over the subsequent 28 days, these orphaned stateful and networking resources ran completely undetected, accumulating $14,200 in unbudgeted cloud infrastructure charges before being flagged by an executive FinOps audit.

Constraints:

  • Zero exposure of database credentials or internal VPC IP ranges to the public internet; all database access must remain strictly private via PSC.
  • Strict preservation of ACID relational transaction integrity; customer checkout records must never be committed without corresponding outbox dispatch events.
  • Fulfillment message ingestion must enforce strictly zero head-of-line blocking on customer message partitions while preserving in-order delivery for valid orders.
  • Infrastructure teardown must be fully automated, deterministic, and enforce strict reverse-dependency ordering to eliminate orphaned resource billing leaks.
  • All diagnostic tests and validation suites must execute within synthetic, budget-capped lab environments without requiring production downtime.

Diagnostic sequence:

  1. Cloud Trace Latency Breakdown: SREs queried Cloud Trace for checkout transactions during the 14:00–14:15 UTC window filtering on http.status_code=504. Flamegraphs revealed that the root span stalled for 59,992ms. Child spans showed: 
    [0ms]     alb-edge-ingress [HTTP POST /v1/orders]
[2ms]       cloudrun-gfe-proxy [Admitted - OIDC token valid]
[4ms]         order-service-handler [Container active]
[6ms]           hikari-pool.getConnection() [STALLED 59,986ms]
[60,000ms]  ALB Client Timeout: 504 GATEWAY TIMEOUT
    Inspecting socket telemetry confirmed that TCP connections to PSC endpoint 10.128.0.50:5432 were timing out after 10,000ms. Because the application lacked a circuit breaker, each thread retried 6 times sequentially until the 60-second GFE timeout severed the client connection. Because the container exposed only /healthz (which checked CPU/memory but not database reachability), Cloud Run reported the instance as 100% healthy, and the ALB continued pouring incoming user traffic into the frozen instances.
  2. Cloud Logging Structured Query on Fulfillment Worker: SREs executed a structured log query to isolate the stalled fulfillment pipeline: 
    resource.type="cloud_run_revision"
AND jsonPayload.service="fulfillment-service"
AND severity>=ERROR
    The query returned 14,200 identical error entries within 45 minutes: 
    UnicodeDecodeError: 'utf-8' codec can't decode byte 0x8a in position 42
Traceback (most recent call last):
  File "/app/fulfillment_consumer.py", line 84, in process_message
    payload = json.loads(message.data.decode('utf-8'))
Delivery Attempt Count: 1,842 | Ordering Key: cust_98412
    Reviewing subscription configuration revealed that deadLetterPolicy was null. Pub/Sub had redelivered the identical corrupt payload 1,842 times. Because ordering keys guarantee strict FIFO processing, the broker blocked the entire partition, stalling all subsequent orders for that hash.
  3. Cloud Asset Inventory & FinOps Audit: SREs audited the project resource hierarchy using Cloud Asset Inventory to identify the source of the billing anomaly: 
    gcloud asset search-all-resources \
  --scope="projects/brightloaf-staging" \
  --asset-types="sqladmin.googleapis.com/Instance,compute.googleapis.com/Address" \
  --format="table(name,assetType,state,createTime)"
    The scan revealed 3 Regional HA Cloud SQL instances in state RUNNING created 28 days prior, alongside 10 reserved external IPv4 addresses in state RESERVED (unattached to any forwarding rule or VM), incurring $14,200 in continuous idle reservation and compute charges.

Root cause: Three interrelated architectural vulnerabilities:

  1. Absence of Decoupled Readiness Checking and Circuit Breaking: Conflating liveness and readiness into a naive /healthz probe prevented the ALB from detecting database connectivity loss. Without an application-level circuit breaker to fail fast (sub-5ms) with HTTP 503 and Retry-After headers, connection pools exhausted container worker threads and triggered 60-second ALB gateway timeouts.
  2. Omission of Pub/Sub Dead-Letter Topic on Ordered Subscription: Provisioning an ordered Pub/Sub subscription without a deadLetterPolicy (bounded to maxDeliveryAttempts = 5) caused an unhandled deserialization exception to permanently stall the customer ordering partition, inducing catastrophic head-of-line blocking across the fulfillment queue.
  3. Lack of Automated Reverse-Dependency Teardown Governance: Ad-hoc manual infrastructure deletion removed stateless compute runtimes while leaving expensive stateful datastores and static IP reservations active, directly violating the LIFO resource lifecycle discipline.

Defensible remediation:

  1. Implement Decoupled Readiness Probes & Fast Circuit Breaking: Expose decoupled /healthz and /readyz endpoints in the Cloud Run application. Configure /readyz to validate database pool reachability with a 1,000ms timeout: 
    @app.route("/readyz", methods=["GET"])
def readiness_probe():
    try:
        # Validate connection pool health with 1s timeout
        with db_engine.connect() as conn:
            conn.execute(text("SELECT 1;"))
        return jsonify({"status": "READY", "pool": "CONNECTED"}), 200
    except Exception as e:
        logger.warning(f"Readiness check failed: {str(e)}")
        return jsonify({"status": "NOT_READY", "error": "DB_UNREACHABLE"}), 503
    Wrap database calls in an application-level circuit breaker: after 3 consecutive connection timeouts, trip to OPEN state for 30 seconds, immediately returning HTTP 503 Service Unavailable with Retry-After: 30 headers in under 3ms, preventing socket exhaustion. Configure Cloud Run startup and liveness probes to inspect /readyz and /healthz respectively.
  2. Deploy Pub/Sub Dead-Letter Topic & Auto-Quarantine: Create a dedicated Dead-Letter Topic (orders.v1.dlq) and audit subscription. Update the primary fulfillment subscription with a dead-letter policy enforcing maxDeliveryAttempts = 5: 
    # Create Dead-Letter Topic
gcloud pubsub topics create orders.v1.dlq

# Attach Dead-Letter Policy with 5-attempt threshold

class MockServiceInstance:
    def __init__(self):
        self.is_process_running = True
        self.psc_network_reachable = True
        self.db_pool_active_connections = 5
        self.db_pool_max_connections = 25
        self.circuit_breaker_state = "CLOSED" # CLOSED, OPEN, HALF_OPEN
        self.consecutive_failures = 0
        self.failure_threshold = 3
        self.circuit_open_time = 0
        self.reset_timeout_seconds = 2.0

    def liveness_probe(self):
        if self.is_process_running:
            return 200, {"status": "ALIVE", "uptime_sec": 4200}
        return 500, {"status": "DEAD"}

    def readiness_probe(self):
        if not self.is_process_running:
            return 503, {"status": "NOT_READY", "reason": "CONTAINER_STOPPED"}
        if not self.psc_network_reachable:
            return 503, {"status": "NOT_READY", "reason": "PSC_NETWORK_PARTITION"}
        if self.db_pool_active_connections >= self.db_pool_max_connections:
            return 503, {"status": "NOT_READY", "reason": "CONNECTION_POOL_EXHAUSTED"}
        return 200, {"status": "READY", "db_pool": "HEALTHY", "active_conns": self.db_pool_active_connections}

    def execute_transaction(self, query):
        now = time.time()
        if self.circuit_breaker_state == "OPEN":
            if now - self.circuit_open_time > self.reset_timeout_seconds:
                self.circuit_breaker_state = "HALF_OPEN"
            else:
                return 503, {"error": "CIRCUIT_BREAKER_OPEN", "retry_after": 30, "latency_ms": 1.2}

        if not self.psc_network_reachable:
            self.consecutive_failures += 1
            if self.consecutive_failures >= self.failure_threshold:
                self.circuit_breaker_state = "OPEN"
                self.circuit_open_time = now
            return 500, {"error": "PSC_CONNECTION_TIMEOUT", "latency_ms": 1000.0}

        self.consecutive_failures = 0
        self.circuit_breaker_state = "CLOSED"
        return 200, {"status": "COMMITTED", "latency_ms": 8.5}

class MockPubSubEngine:
    def __init__(self):
        self.topics = {"orders.v1": [], "orders.v1.dlq": []}
        self.subscriptions = {
            "orders.v1.fulfillment-sub": {
                "topic": "orders.v1",
                "enable_message_ordering": True,
                "dead_letter_topic": "orders.v1.dlq",
                "max_delivery_attempts": 5,
                "messages": []
            }
        }
        self.dead_letter_message_count = 0

    def publish(self, topic, data_bytes, ordering_key=None):
        msg = {
            "message_id": f"msg-{uuid.uuid4().hex[:8]}",
            "data": data_bytes,
            "ordering_key": ordering_key,
            "delivery_attempt": 0,
            "publish_time": time.time()
        }
        self.topics[topic].append(msg)
        for sub_name, sub in self.subscriptions.items():
            if sub["topic"] == topic:
                sub["messages"].append(dict(msg))
        return msg["message_id"]

    def pull_and_process(self, sub_name, process_fn):
        sub = self.subscriptions[sub_name]
        if not sub["messages"]:
            return "QUEUE_EMPTY"
        msg = sub["messages"][0]
        msg["delivery_attempt"] += 1
        attempt = msg["delivery_attempt"]
        try:
            process_fn(msg["data"])
            sub["messages"].pop(0)
            return f"ACK (Processed successfully on attempt {attempt})"
        except Exception as e:
            if attempt >= sub["max_delivery_attempts"]:
                sub["messages"].pop(0)
                dlq_topic = sub["dead_letter_topic"]
                self.topics[dlq_topic].append(msg)
                self.dead_letter_message_count += 1
                return f"QUARANTINED_TO_DLT (Attempt {attempt}/{sub['max_delivery_attempts']}) Exception: {str(e)}"
            else:
                return f"NACK_RETRY (Attempt {attempt}/{sub['max_delivery_attempts']}) Exception: {str(e)}"
