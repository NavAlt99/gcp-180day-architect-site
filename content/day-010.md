<!-- topic-01:overview -->
Docker builds a container image from a Dockerfile and runs it as a container. An image is a layered, read-only template; the running container adds a writable layer. Mounts and volumes store data outside that disposable layer. A registry distributes images. An inode records filesystem metadata, while flush and fsync operations affect when buffered writes are requested to reach durable storage.

<!-- topic-01:technical -->
A Dockerfile records build steps such as selecting a base image, copying application files and setting the startup command. The resulting image has layers that can be reused across builds and pulled from a registry. A running container has a writable layer, but deleting that container removes its layer; a named volume can outlive it. A bind mount instead exposes a chosen host path. This distinction matters for stateful services: an application that writes only into a disposable container layer can appear healthy until replacement loses its data. A volume provides persistence across container replacement but is not automatically a backup, replica or multi-zone storage system.

Within a filesystem, an inode identifies a file's metadata and data blocks independently of its pathname. Application writes may first sit in language/runtime and kernel buffers. Flushing a language stream moves its data toward the OS; fsync asks the OS to synchronize that file's data and metadata with storage. Even a successful file fsync does not necessarily synchronize the containing directory entry, and cloud storage durability depends on the actual filesystem and backing service. Architects must define the required durability guarantee rather than infer it from one successful print statement.

**Further study:** [Docker images and layers](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/), [Docker volumes](https://docs.docker.com/engine/storage/volumes/), [Dockerfile overview](https://docs.docker.com/build/concepts/dockerfile/), and [Linux fsync manual](https://man7.org/linux/man-pages/man2/fsync.2.html#DESCRIPTION).

<!-- topic-01:problem -->
**Failure:** An order API writes a recovery marker inside its container. The deployment replaces the container, and the marker disappears even though the write had returned successfully.

**Cause:** The marker lived in the old container's writable layer. Container replacement removed that layer; a successful write or fsync there did not make it survive deletion of the container. No persistent volume or external data store held the marker.

**Fix:** Put state in an appropriate persistent store or explicitly mounted volume, define backup and recovery requirements, then test container replacement. Keep images immutable and separate data lifecycle from container lifecycle. Verify that the new container sees the marker and that cleanup does not delete required data. A named volume alone still needs a backup and failure-domain plan for production.

### Step 1 — Create the image source

Open a Linux terminal in the Day 1 repository. Create a dedicated directory and two files:

```sh
mkdir -p ~/gcp-architect-learning/day-010-image
cd ~/gcp-architect-learning/day-010-image
cat > Dockerfile <<'EOF'
FROM python:3.12-alpine
WORKDIR /app
COPY app.py /app/app.py
RUN mkdir /data
ENTRYPOINT ["python", "/app/app.py"]
EOF
cat > app.py <<'PY'
from pathlib import Path
import os
import sys

path = Path('/data/order.txt')
action = sys.argv[1]
if action == 'write':
    with path.open('w', encoding='utf-8') as stream:
        stream.write('demo-order\n')
        stream.flush()
        os.fsync(stream.fileno())
    print('wrote and fsynced demo-order')
elif action == 'read':
    print(path.read_text(encoding='utf-8').strip() if path.exists() else 'missing')
else:
    raise SystemExit('use write or read')
PY
```

The sample contains no credential or customer data. The file fsync demonstrates the API call; it cannot simulate a real power failure or prove directory-entry durability.

### Step 2 — Build and test the disposable layer

```sh

docker run --rm --network none gcp-day10:lab write
docker run --rm --network none gcp-day10:lab read
```

Expected: the first container prints `wrote and fsynced demo-order`; the second prints `missing`, because it is a new container and the first container's writable layer was removed. <!-- topic-02:overview -->
Container orchestration manages many containers across machines from a declared desired state. Kubernetes exists to schedule workloads, replace failed instances, roll out changes and provide service discovery when direct manual container commands no longer scale.

<!-- topic-02:technical -->
Running one container on one host leaves the operator responsible for placement, restart, network endpoint changes and updates. An orchestrator accepts a desired state, observes actual state and repeatedly tries to reconcile the difference. Kubernetes has a control plane that stores API objects and runs controllers and a scheduler; worker nodes run Pods. A Deployment can request a number of interchangeable Pods, and the controller replaces missing Pods. A Service provides a stable way to find a changing set of Pod endpoints. Reconciliation is eventual: a declared replica count does not guarantee that capacity, image availability or healthy nodes exist to satisfy it.

Orchestration adds operational complexity. The control plane, cluster networking, node resources, image registry and workload policies become dependencies. Architects should distinguish a container process restart from a Pod replacement and a node failure, then define readiness, resource requests and rollout checks. “Kubernetes will heal it” is incomplete if all replacements use a broken image or cannot be scheduled.

**Further study:** [Kubernetes components](https://kubernetes.io/docs/concepts/overview/components/#core-components) and [Kubernetes workloads](https://kubernetes.io/docs/concepts/workloads/).

<!-- topic-02:problem -->
**Failure:** A Deployment requests three order API replicas, but only one becomes ready after an update. The team keeps restarting that Pod and assumes the scheduler is broken.

**Cause:** The updated image exceeds available node memory, so two Pods remain unschedulable. The desired state is valid, but the cluster lacks capacity for it. A broken image pull or readiness probe would have different evidence.

**Fix:** Inspect desired versus ready replicas, Pod scheduling events, node allocatable resources and resource requests. Add appropriate capacity or right-size the request, then observe the controller create and ready the missing Pods. Recheck customer traffic through the Service. Repeated manual restarts do not create memory capacity.

<!-- topic-03:overview -->
Kubernetes core objects divide responsibilities. A Pod hosts one or more closely coupled containers; a Deployment maintains a desired set of Pods; a Service selects Pods for a stable network endpoint; an Ingress describes HTTP(S) routing when an Ingress controller exists. ConfigMaps hold non-secret configuration, while Secrets hold sensitive values as Kubernetes API objects requiring careful access control.

<!-- topic-03:technical -->
A Deployment owns a Pod template and a desired replica count. The template's labels must match its selector. A Service independently selects Pods using labels; a mismatch can leave a healthy Deployment with no Service endpoints. An Ingress routes to a Service, not directly to an arbitrary Pod, and does nothing without a controller implementing it. The Kubernetes project now recommends Gateway for new feature development while Ingress remains a stable, frozen API. ConfigMaps and Secrets let configuration be supplied separately from the image, but a Secret's API representation is not a substitute for RBAC, encryption policy and safe delivery into a container.

These objects are declarative: the API stores a desired state and controllers work toward it. Architects need to trace owner relationships and selectors before debugging a packet path. A ready Pod behind a Service with the wrong selector remains unreachable through that Service even though the process itself works.

**Further study:** [Pods](https://kubernetes.io/docs/concepts/workloads/pods/#what-is-a-pod), [Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/), [Services](https://kubernetes.io/docs/concepts/services-networking/service/), [Ingress](https://kubernetes.io/docs/concepts/services-networking/ingress/), [ConfigMaps](https://kubernetes.io/docs/concepts/configuration/configmap/), and [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/).

<!-- topic-03:problem -->
**Failure:** The order API's two Pods are ready, but traffic through its Service has no backend endpoints.

**Cause:** The Pod template has label `app: orders`, while the Service selector asks for `app: order`. Kubernetes does not infer that these are equivalent. The Ingress can route to the Service name but cannot manufacture matching endpoints.

**Fix:** Compare Deployment template labels, Service selector and EndpointSlice membership. Correct the selector to the intended label, observe endpoints appear, then test the Service and external route separately. Avoid restarting healthy Pods to solve a label mismatch.

### Step 1 — Read the manifest fixture

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
spec:
  replicas: 2
  selector:
    matchLabels: {app: orders}
  template:
    metadata:

    spec:
      containers:
        - name: api
          image: example.invalid/orders:demo

kind: Service
metadata:
  name: orders
spec:
  selector: {app: order}
  ports:
    - port: 80
      targetPort: 8080
```
