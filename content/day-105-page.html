1 · Topics of the day

Day 105 focuses on cryptographic transport security, enterprise identity attestation, and hybrid boundary isolation across Google Cloud. Architects evaluate TLS termination patterns and bidirectional cryptographic authentication (mTLS) backed by private Certificate Authority Service (CAS), secure hybrid link-layer and network-layer encryption via MACsec and HA VPN IPsec, zero-public-IP administrative access using IAP TCP forwarding over legacy bastion jumphosts, and authoritative DNS integrity using DNSSEC and query audit logging.

Exit evidence: Engineers design and verify an enterprise certificate rotation trace, mTLS service mesh attestation pipeline, hybrid link-layer MACsec versus IPsec encapsulation model, IAP tunneling security policy, and DNSSEC chain-of-trust ownership matrix meeting all Day 105 Exit evidence criteria.

1. TLS everywhere: managed certificates, mTLS, Certificate Authority Service

Enterprise workloads require pervasive cryptographic transport security across public ingress, internal microservices, and third-party integrations. Google Cloud Certificate Manager provides scalable, automated TLS provisioning with DNS-authorization and wildcard support at the edge. Within the private VPC, Mutual TLS (mTLS) enforces cryptographic client identity verification using ephemeral X.509 certificates issued by Google Cloud Certificate Authority Service (CAS), eliminating shared secret anti-patterns.

Problem preview: An external payment webhook rejects incoming orders because the application load balancer certificate lacks an intermediate trust bundle; mTLS ensures both server and client validate cryptographic identity.

2. Secure hybrid connectivity: MACsec for Interconnect, HA VPN encryption

Connecting on-premises infrastructure to Google Cloud requires defense-in-depth transport cryptography. Cloud Interconnect provides dedicated, high-bandwidth private circuits, but physical cables traverse third-party facilities; MACsec (IEEE 802.1AE) provides line-rate hardware encryption at Layer 2. For internet-routed connections, Cloud HA VPN provides 99.99% SLA-backed Layer 3 IPsec encapsulation (IKEv2, AES-GCM).

Problem preview: An enterprise border router renegotiates an IPsec security association causing a 200ms packet stall; combining MACsec on Dedicated Interconnect with HA VPN delivers wire-speed encryption with automated cryptographic failover.

3. Bastion patterns vs IAP TCP forwarding

Traditional infrastructure architectures relied on public-facing bastion jump hosts (jumphosts) placed in public subnets to administer private VMs. This model created significant attack surfaces: persistent public IP scanning, SSH brute-forcing, bastion patching overhead, and shared SSH key management risks. Identity-Aware Proxy (IAP) TCP Forwarding eliminates the need for public IPs and jump hosts entirely, encapsulating administrative protocols within TLS WebSockets authorized dynamically by Google IAM and Context-Aware Access.

Problem preview: An internet scanner attempts automated brute-force attacks against SSH port 22; IAP TCP forwarding eliminates public IP exposure entirely and enforces multi-factor IAM checks before tunneling bytes.

4. DNS security (DNSSEC, DNS logging)

Domain Name System (DNS) is the critical control plane of all network communication, yet plain DNS queries are unauthenticated and susceptible to cache poisoning, man-in-the-middle spoofing, and covert data exfiltration. Domain Name System Security Extensions (DNSSEC) provides cryptographic integrity and authenticity using digital signatures. In parallel, Cloud DNS query logging and Cloud DNS firewall policies provide enterprise visibility and threat prevention against malicious domain lookups and DNS tunneling.

Problem preview: A malicious internal script queries a covert DNS exfiltration endpoint; DNS query logging captures the base64-encoded tunneling subdomain and triggers automated incident response.

1. TLS everywhere: managed certificates, mTLS, Certificate Authority Service: technical mechanics

1. Edge TLS vs. Internal Mutual TLS (mTLS)

  • Public Ingress TLS: External Application Load Balancers terminate client TLS sessions at the GFE edge. Google-managed certificates automate 90-day renewals using ACME DNS or HTTP challenges. Certificate Manager allows attaching up to 1,000,000 certificates per load balancer via Certificate Maps.
  • Mutual TLS (mTLS): In zero-trust networks, server authentication is insufficient. The server requests and validates a client X.509 certificate during the TLS handshake. Certificate Authority Service (CAS) acts as the highly available, managed PKI root/subordinate tier, issuing short-lived workload certificates integrated with Cloud Service Mesh and SPIFFE IDs.

2. Certificate Authority Service (CAS) Architecture

  • CA Pools: Group certificate authorities with common IAM policies, issuance modes, and certificate revocation lists (CRLs).
  • Tiers: DevOps Tier (optimized for high-volume, short-lived container certificates, 30-day CRLs) vs. Enterprise Tier (FIPS 140-2 Level 3 HSM-backed keys, strict auditing, comprehensive compliance certifications).
  • Rotation Mechanics: Subordinate CAs must be renewed before expiration; workload sidecars utilize Automated Certificate Management protocols to refresh leaf certs every 24 hours.

Architectural evaluation questions

  • Why should microservice-to-microservice traffic utilize mTLS with Private CAS rather than public Google-managed certificates?
  • What is the architectural difference between the DevOps Tier and Enterprise Tier in Google Cloud CAS?
  • How does Certificate Manager use Certificate Maps to overcome traditional SSL certificate limits on Cloud Load Balancing?

Further study: Google Cloud Certificate Authority Service: Architecture and CA pool management.

2. Secure hybrid connectivity: MACsec for Interconnect, HA VPN encryption: technical mechanics

1. MACsec on Cloud Interconnect (Layer 2)

  • Standard: IEEE 802.1AE encrypts all Ethernet frames at the physical link layer between customer on-prem edge routers and Google Cloud colocation points of presence (PoPs).
  • Line-Rate Performance: Encrypts at 10 Gbps and 100 Gbps speeds with zero CPU overhead or packet fragmentation.
  • Key Agreement (MKA): Uses Connectivity Association Keys (CAKs) and Connectivity Key Names (CKNs) stored securely in Google Cloud Secret Manager and synchronized with the on-premise hardware.

2. Cloud HA VPN (Layer 3 IPsec)

  • SLA & Architecture: Cloud HA VPN guarantees 99.99% availability by enforcing two active tunnels per gateway across independent Google Cloud failure domains.
  • Encapsulation: Uses IPsec Encapsulating Security Payload (ESP) in tunnel mode, paired with IKEv2 and dynamic BGP routing.
  • Crypto Suites: Recommends AES-GCM-256 with Diffie-Hellman Group 19/20 for Perfect Forward Secrecy (PFS).

Architectural evaluation questions

  • Why does MACsec provide superior throughput and lower latency compared to IPsec for hybrid interconnects?
  • Under what circumstances would an architect run HA VPN IPsec over Cloud Interconnect (VPN over Interconnect)?
  • What is the operational impact on BGP sessions when a MACsec pre-shared key (CAK) expires?

Further study: Google Cloud Interconnect: MACsec encryption architecture and key management.

3. Bastion patterns vs IAP TCP forwarding: technical mechanics

1. Architectural Comparison: Bastion vs. IAP TCP Forwarding

  • Bastion Jump Host Anti-Pattern: Requires public IP on bastion VM; ingress firewall rule 0.0.0.0/0:22; requires maintaining OS patch cycles, SSH keys, bastion user accounts, and monitoring for host compromise. If the bastion is compromised, the attacker has a pivot point into the entire private VPC.
  • IAP TCP Forwarding Architecture: Private VMs have zero public IP addresses. The administrative client uses gcloud compute ssh --tunnel-through-iap. The Google Cloud CLI initiates an authenticated TLS WebSocket connection to the Google IAP proxy endpoint. IAP evaluates IAM permissions (roles/iap.tunnelResourceAccessor) and Context-Aware Access policies (device status, IP, MFA) before forwarding TCP packets directly into the VPC via Google internal forwarding range 35.235.240.0/20.

2. Firewall Invariant for IAP

  • The VPC firewall only needs a single ingress rule allowing TCP port 22 (SSH) and port 3389 (RDP) from source IP range 35.235.240.0/20.
  • All traffic originating from outside this range is rejected at the network perimeter.

Architectural evaluation questions

  • Why does IAP TCP forwarding eliminate the operational overhead and security risk of traditional bastion hosts?
  • What exact Google-owned CIDR block must be whitelisted in VPC firewall rules to allow IAP TCP tunneling?
  • How can Context-Aware Access policies be layered on top of IAP to prevent administrative access from unmanaged personal devices?

Further study: Google Cloud IAP: TCP forwarding concepts and administrative access control.

4. DNS security (DNSSEC, DNS logging): technical mechanics

1. Cloud DNSSEC Cryptographic Trust Chain

  • Zone Signing Key (ZSK): Used by Cloud DNS to sign all Resource Record Sets (RRsets) in the zone, producing RRSIG records. Typically uses elliptic curve algorithms (ECDSAP256SHA256) and rotates automatically.
  • Key Signing Key (KSK): Signs the ZSK record set (DNSKEY). The hash of the KSK is submitted to the parent registrar as a Delegation Signer (DS) record, establishing an unbroken chain of cryptographic trust to the DNS root.
  • Authenticated Denial of Existence: Uses NSEC3 records to prevent zone-walking attacks while proving non-existence of subdomains.

2. Cloud DNS Query Logging & DNS Firewall

  • Query Logging: Captures all DNS queries originating from inside the VPC, logging client IP, requested FQDN, record type, response code, and latency to Cloud Logging.
  • DNS Firewall Policies: Applies threat intelligence domain blocklists at the VPC resolver level. Blocks known malware C2 domains and DNS exfiltration endpoints before IP resolution can take place.

Architectural evaluation questions

  • How does DNSSEC protect client resolvers against DNS cache poisoning and spoofed record injection?
  • What is the operational consequence if a domain registrar DS record does not match the active Cloud DNS KSK?
  • How does Cloud DNS query logging enable Security Operations teams to detect DNS data exfiltration?

Further study: Google Cloud DNS: DNSSEC concepts, algorithm selection, and DS record management.

1. TLS everywhere: managed certificates, mTLS, Certificate Authority Service · field case

Enterprise scenario: Internal payment ingestion API fails with HTTP 502 Bad Gateway and upstream TLS alert `unknown_ca` (SSL alert 48).

Constraints: Zero-trust architecture mandates all internal RPC calls must enforce mutual TLS; no unencrypted plaintext in VPC.

Evidence:

Envoy sidecar proxy log showing certificate verification failure:

{
  "response_flags": "UC",
  "upstream_transport_failure_reason": "TLS_error:|268435581:SSL_routines:OPENSSL_internal:CERTIFICATE_VERIFY_FAILED:ssl/tls_record.cc:291",
  "connection_termination_details": "peer_certificate_verification_failed: unable to get local issuer certificate",
  "downstream_remote_address": "10.128.0.45:49182",
  "upstream_host": "10.128.1.12:8443"
}

Analysis: The calling client sidecar was issued a new leaf certificate from a freshly created CAS subordinate pool, but the receiving server sidecar trust bundle had not been updated with the new subordinate CA root.

Root cause: The receiving service trust bundle only contained the root CA certificate and omitted the intermediate subordinate CA certificate that signed the client leaf.

Diagnostic sequence:

  1. Inspect Envoy sidecar logs on both caller and receiver pods for SSL handshake termination details.
  2. Extract the active server trust store bundle using `openssl s_client -connect 10.128.1.12:8443 -showcerts`.
  3. Query Certificate Authority Service for the issuing subordinate CA certificate chain.
  4. Confirm whether the server trust anchor includes the full subject key identifier (SKI) of the new issuing CA.

Defensible remediation: Update the trust config map across the service mesh to distribute the complete CAS CA pool bundle containing root and intermediate signing certificates.

Verification: Initiate mutual TLS curl probe passing client certificate and verifying full chain validation without errors.

Residual risk: Workloads must reload trust bundles dynamically without requiring full container restart to prevent downtime during CA rotations.

2. Secure hybrid connectivity: MACsec for Interconnect, HA VPN encryption · field case

Enterprise scenario: Dedicated Interconnect interface drops all traffic during scheduled CKN key rotation, causing multi-region failover.

Constraints: Financial compliance requires uninterrupted L2 encryption on all physical transoceanic circuits.

Evidence:

Cisco IOS-XE syslog showing MKA key rollover failure:

%MKA-3-KEY_MISMATCH: MKA session failed on HundredGigE0/1/0: CKN 0123456789ABCDEF CAK mismatch with peer
%LINK-3-UPDOWN: Interface HundredGigE0/1/0, changed state to down
%BGP-5-ADJCHANGE: neighbor 169.254.0.1 Down Interface down

Analysis: Google Cloud Interconnect MACsec config was updated with a new primary CKN, but the on-premise router had not pre-configured the fallback key chain, triggering link tear-down.

Root cause: The on-premise edge router did not have hitless MKA key rollover configured, causing an immediate link drop when Google activated the new CKN.

Diagnostic sequence:

  1. Check Google Cloud Console Interconnect status for MACsec operational state (`OPERATIONAL` vs `NOT_ESTABLISHED`).
  2. Inspect router MKA session status: `show mka sessions interface HundredGigE0/1/0`.
  3. Validate active CKN and CAK strings stored in Cloud Secret Manager against on-premise key chain definitions.
  4. Verify MACsec key rotation was executed using the hitless graceful rollover procedure.

Defensible remediation: Configure dual-key MKA key chains on the edge router with overlapping validity windows before initiating MACsec key rotation in Google Cloud.

Verification: Simulate key rollover in staging; verify `show mka session` transitions keys with zero dropped packets and stable BGP.

Residual risk: Hardware vendor MKA implementation differences require standardized lab testing before global production key rotations.

3. Bastion patterns vs IAP TCP forwarding · field case

Enterprise scenario: Security team detects 45,000 failed SSH login attempts per hour on public bastion host `/var/log/auth.log`.

Constraints: DevOps engineers must maintain 24/7 emergency SSH access to production VMs while eliminating external port scanning.

Evidence:

Audit log snippet from compromised legacy bastion VM:

Sep 29 03:14:02 bastion-01 sshd[19842]: Failed password for invalid user admin from 198.51.100.42 port 54122 ssh2
Sep 29 03:14:04 bastion-01 sshd[19845]: Failed password for root from 198.51.100.42 port 54124 ssh2
Sep 29 03:14:06 bastion-01 sshd[19848]: Failed password for invalid user deploy from 198.51.100.42 port 54126 ssh2

Analysis: Legacy bastion VM had public IP 34.120.45.10 with open port 22 to 0.0.0.0/0, subjecting it to continuous dictionary attacks.

Root cause: Public bastion host exposed SSH directly to the internet; absence of IAP configuration forced reliance on vulnerable static key authentication.

Diagnostic sequence:

  1. Review VPC firewall rules to identify ingress rules allowing port 22 from `0.0.0.0/0`.
  2. Inspect Compute Engine instance inventory to locate all VMs configured with external public IP addresses.
  3. Check IAM role bindings for `roles/iap.tunnelResourceAccessor` on the target project.
  4. Verify existence of the required Google IAP forwarding firewall rule for `35.235.240.0/20`.

Defensible remediation: Deprovision the bastion VM, author a VPC firewall rule allowing `35.235.240.0/20` on port 22, and enforce <kbd>gcloud compute ssh --tunnel-through-iap</kbd>.

Residual risk: Local workstation must have Google Cloud SDK installed and user must maintain valid OAuth credentials.

4. DNS security (DNSSEC, DNS logging) · field case

Enterprise scenario: All external internet clients experience SERVFAIL when attempting to resolve corporate website following registrar migration.

Constraints: DNSSEC must remain active to satisfy federal cyber compliance mandates; cannot permanently disable validation.

dig +dnssec output showing broken chain of trust: ```text ;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL, id: 41209 ;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1 ;; OPT PSEUDOSECTION: ; EDNS: version: 0, flags: do; udp: 4096 ;; QUESTION SECTION: ;api.brightloaf.com. IN A ``` Analysis: The registrar retained an obsolete DS record pointing to a decommissioned on-premise BIND KSK, while Google Cloud DNS was signing records with a newly generated ECDSAP256SHA256 KSK.

Root cause: Cryptographic trust chain divergence: Registrar DS record did not match the Cloud DNS Key Signing Key (KSK).

Diagnostic sequence:

  1. Query authoritative DNSKEY records using <kbd>dig @ns-cloud-a1.googledomains.com api.brightloaf.com DNSKEY +multiline</kbd>.
  2. Query parent registrar DS records using <kbd>dig DS brightloaf.com +trace</kbd>.
  3. Compute the cryptographic hash (SHA-256) of the Google Cloud DNS KSK and compare against parent DS record digest.
  4. Check Google Cloud DNSSEC state via <kbd>gcloud dns managed-zones describe brightloaf-zone</kbd>.

Defensible remediation: Extract active KSK DS record details from Cloud DNS and update the parent domain registrar records immediately.

Verification: Run <kbd>dig +dnssec api.brightloaf.com</kbd> against public validating resolvers (`8.8.8.8`) and verify `NOERROR` with valid `RRSIG`.

Residual risk: Registrar DNS propagation and parent zone TTLs (typically 24 hours) may prolong SERVFAIL caching during misconfigurations.

  2. Root Certificate Authority (CA) Generation

    Generate an RSA 4096-bit private key and self-signed root certificate simulating Enterprise CAS Root:

    cat <<'EOF' > generate_pki.sh
#!/usr/bin/env bash
set -euo pipefail
# 1. Root CA
openssl genrsa -out root_ca.key 4096
openssl req -x509 -new -nodes -key root_ca.key -sha256 -days 365 \
  -subj "/C=US/ST=California/O=Brightloaf/OU=Security/CN=Brightloaf-Root-CA" \
  -out root_ca.crt

# 2. Subordinate Intermediate CA
openssl genrsa -out sub_ca.key 2048
openssl req -new -key sub_ca.key -out sub_ca.csr \
  -subj "/C=US/ST=California/O=Brightloaf/OU=Mesh/CN=Brightloaf-Sub-CA"

cat <<'EXT' > sub_ca.ext
basicConstraints=critical,CA:TRUE,pathlen:0
keyUsage=critical,digitalSignature,keyCertSign,cRLSign
EXT

openssl x509 -req -in sub_ca.csr -CA root_ca.crt -CAkey root_ca.key \
  -CAcreateserial -out sub_ca.crt -days 180 -sha256 -extfile sub_ca.ext

# 3. Concatenate CA Chain Bundle
cat sub_ca.crt root_ca.crt > ca_chain.crt
echo "[PASS] Root and Subordinate CAs generated successfully."
EOF
bash generate_pki.sh

  4. Mutual TLS Validation Engine

    Execute Python verification server and client enforcing bidirectional TLS certificate exchange:

    cat <<'EOF' > test_mtls.py
import socket
import ssl
import threading
import time

def run_server():
    context = ssl.create_default_context(ssl.Purpose.CLIENT_AUTH)
    context.verify_mode = ssl.CERT_REQUIRED
    context.load_verify_locations(cafile="ca_chain.crt")
    context.load_cert_chain(certfile="server.crt", keyfile="server.key")

    bind_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    bind_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    bind_socket.bind(("127.0.0.1", 18443))
    bind_socket.listen(5)

    conn, addr = bind_socket.accept()
    with context.wrap_socket(conn, server_side=True) as sconn:
        peer_cert = sconn.getpeercert()
        subject = dict(x[0] for x in peer_cert['subject'])
        print(f"[SERVER] Handshake Success! Authenticated Client CN: {subject.get('commonName')}")
        sconn.sendall(b"HTTP/1.1 200 OK\r\nContent-Length: 17\r\n\r\nMTLS-AUTH-SUCCESS")
    bind_socket.close()

server_thread = threading.Thread(target=run_server)
server_thread.daemon = True
server_thread.start()
time.sleep(1)

client_context = ssl.create_default_context(ssl.Purpose.SERVER_AUTH, cafile="ca_chain.crt")
client_context.load_cert_chain(certfile="client.crt", keyfile="client.key")

raw_sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
with client_context.wrap_socket(raw_sock, server_hostname="localhost") as csock:
    csock.connect(("127.0.0.1", 18443))
    server_cert = csock.getpeercert()
    srv_sub = dict(x[0] for x in server_cert['subject'])
    print(f"[CLIENT] Handshake Success! Authenticated Server CN: {srv_sub.get('commonName')}")
    csock.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\n\r\n")
    data = csock.recv(1024)
    print(f"[CLIENT] Received: {data.decode().splitlines()[0]}")
EOF
python3 test_mtls.py

import math
import re

def calculate_shannon_entropy(data: str) -> float:
    if not data:
        return 0.0
    prob = [float(data.count(c)) / len(data) for c in dict.fromkeys(list(data))]
    return - sum([p * math.log(p) / math.log(2.0) for p in prob])

sample_dns_logs = [
    {"client_ip": "10.128.0.5", "query": "api.brightloaf.internal", "type": "A"},
    {"client_ip": "10.128.0.5", "query": "database-primary.brightloaf.internal", "type": "A"},

]

    print(f"[{status:26s}] Client: {log['client_ip']:12s} Entropy: {entropy:.2f} Len: {length:2d} -> {log['query']}")
