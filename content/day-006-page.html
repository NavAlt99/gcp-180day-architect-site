1 · Topics of the day

Kernel, user space, files and permissions

The Linux kernel manages processes, memory, devices and filesystem access; user-space programs request those services through system calls. Paths locate files and directories. Ownership and permission bits determine which users and groups may read, write or traverse them.

Why today and where it sits: Day 6 moves from network paths to the operating-system boundary that hosts an application. Brightloaf's Order API process runs in user space, while the kernel resolves its file paths and applies credentials and permission checks.

Problem preview: After deployment, the Order API reports PermissionError: [Errno 13] Permission denied: '/srv/brightloaf/order-api/config.json' while an administrator can read the file. Checkout requests cannot be processed because the service identity cannot traverse or read its configuration path.

Processes, streams, signals and services

A process is a running program with an identity, environment, open file descriptors and exit status. Standard input, output and error are file descriptors 0, 1 and 2. Pipes and redirection connect those streams. A service manager such as systemd starts, stops and monitors long-lived processes; signals request or force process state changes.

Why today and where it sits: Long-running Order API and Fulfillment workers need observable startup, shutdown and restart behavior before they can be operated safely on a VM. The shell launches diagnostic commands, the kernel owns process state and signals, and a service manager owns the declared unit lifecycle.

Problem preview: A deployment sends SIGKILL to a Fulfillment worker before it records completion, and the broker later replays the same event. Without a durable idempotency decision, Brightloaf ships the order twice and incurs inventory and refund costs.

2 · Technical discussion of each topic

Kernel, user space, files and permissions

A shell command is a user-space process. When it opens a file, the kernel resolves the path and checks permissions using the process's identity and the file or directory metadata. A directory's execute bit permits traversal; its read bit permits listing names. A file's read, write and execute bits have different meanings. Permissions are grouped for owner, group and others. For example, mode 600 grants read and write to the owner only; mode 700 on a directory grants the owner list, create and traverse rights while excluding others under the ordinary mode-bit model. Access-control lists and other security mechanisms can add rules beyond those basic bits.

The file owner and group are separate from the current shell user. A user can usually change modes on a file they own, but changing ownership to another user typically requires privilege. This matters in cloud VMs because a service running under its own account may fail to read a secret even though an interactive administrator can. Granting broad permissions hides the owner mismatch and increases exposure; first inspect the identity, path components and intended service account.

Processes, streams, signals and services

When a shell launches a program, the kernel gives the process an ID and resources. The shell can redirect output into a file or pipe it to another process. A successful shell exit code only reports how a command terminated; it does not prove the service met a customer request. SIGTERM asks a process to terminate and can be handled for cleanup; SIGKILL cannot be caught or ignored and prevents application cleanup. A forced stop may leave in-flight work unfinished, so the architect should favor graceful shutdown with a bounded deadline before escalation.

At boot, a service manager activates configured units according to dependencies and target state. A unit describes how to start the service, its restart policy and other operating constraints. Systemd reports unit state while the kernel reports process state; a unit can fail after its process exits. Standard output/error may be captured in the journal for a managed service, while other applications write separate files under /var/log or elsewhere. Diagnostic evidence should include timestamp, unit, PID, exit status and relevant log lines. A journal entry proves what was logged, not that every request was served.

3 · Real-world problem and solution for each topic

Case 1 · Administrator can read; service user receives EACCES

Failure: An order API service cannot read its configuration file after deployment, although an administrator can open it in a shell.

Cause: The service runs as a separate user. The file is owned by the administrator with owner-only read permission, or a parent directory lacks traverse permission for the service identity.

Fix: Inspect the service's effective user/group, file owner/mode and every parent directory. Put the file under the intended service account or an appropriately restricted group and grant only the needed read/traverse access. Restart the service and verify a read under its identity. Changing the file to world-readable would mask the root cause and expose configuration.

Constraints: the configuration may contain sensitive values, the service must remain unprivileged, and the repair must not grant access to unrelated users. Preserve the original owner, group and modes in the change record so the change can be reversed.

Diagnostic sequence: capture the unit's configured user and effective process credentials; run namei -l or inspect each parent directory; inspect file owner, group, mode and ACL; then reproduce the read as the service identity in a controlled environment. This separates blocked directory traversal from a final-file read failure.

Verification and residual risk: verify a successful read as the configured service user, a clean unit start, and a rejected read from an unrelated ordinary identity. The application can still fail on malformed content, ACLs, read-only mounts or host security policy, so a successful permission check is not full readiness proof.

Case 2 · Forced worker stop exposes a duplicate-fulfillment defect

Failure: An order worker disappears during deployment. The service manager restarts it, but an order processed just before the stop is replayed and fulfilled twice.

Cause: The worker was killed before it could finish or record its work, and the application lacked an idempotency check. “Service active again” does not establish that in-flight orders were safe.

Fix: Inspect the previous unit state, PID, termination signal, exit status and timestamped logs. Give the worker a bounded graceful-stop path and ensure replay is idempotent using an order key or equivalent durable state. Test a stop during a synthetic order, then verify one fulfillment after restart. A forced kill remains a recovery tool when graceful stop exceeds its deadline, not the normal success criterion.

Constraints: deployment must finish within a bounded drain window, an unresponsive process must still be stoppable, and an acknowledged event may be delivered again. Brightloaf cannot use a longer shutdown timeout as its only duplicate-prevention control.

Diagnostic sequence: correlate unit stop and restart timestamps with the old and new PIDs, signal or wait status, broker delivery identifier, fulfillment key and durable commit record. Determine whether the first worker performed the external action before recording completion and whether the second worker checked the same stable key.

Verification and residual risk: inject the same synthetic event key before and after a graceful restart and confirm one committed fulfillment plus a replay result that references the original decision. Retrying an external carrier call may still need the same idempotency key at that boundary; process supervision alone cannot provide exactly-once business behavior.

Exercise 1 · Inspect a private configuration path

Goal: Observe identity and file-mode behavior without elevated privileges. Mode: local Linux terminal in the Day 1 repository.

Expected Result: identify the current process credentials, create a private directory and file, observe owner-only modes, read the file as its owner, and remove only the disposable fixture.

Preflight: use an ordinary non-root Linux shell. Confirm the required local commands before creating the fixture:

command -v id pwd mkdir printf chmod stat cat rm rmdir
test "$(id -u)" -ne 0 && printf 'preflight: ordinary user\n'

Expected: each command prints a path or shell builtin name, followed by preflight: ordinary user. No Google Cloud account, credential or billable resource is involved.

Step 1 — Identify the current user

Open a terminal and run: 

id
pwd

Expected: your user ID, primary/supplementary groups and current directory. Record the values; they vary by machine. The command is read-only.

Step 2 — Create a private sample 

mkdir -p ~/gcp-architect-learning/day-006-permissions
printf 'synthetic-config=true\n' > ~/gcp-architect-learning/day-006-permissions/sample.txt
chmod 700 ~/gcp-architect-learning/day-006-permissions
chmod 600 ~/gcp-architect-learning/day-006-permissions/sample.txt
stat -c '%A %U %G %n' ~/gcp-architect-learning/day-006-permissions/sample.txt

Expected: the file's symbolic mode begins with -rw------- , followed by your user and group. The directory mode is private as well. In your note, explain why another ordinary user should not be able to read this file through these mode bits. Do not place a real credential in the sample.

Step 3 — Compare read and write permission 

chmod 400 ~/gcp-architect-learning/day-006-permissions/sample.txt
stat -c '%A %n' ~/gcp-architect-learning/day-006-permissions/sample.txt
cat ~/gcp-architect-learning/day-006-permissions/sample.txt

Expected mode -r-------- and the synthetic line printed. The owner can read but lacks ordinary write permission. Do not test this as root, because privileged access changes the result. Restore the safe private mode: 

chmod 600 ~/gcp-architect-learning/day-006-permissions/sample.txt

Verification: save the id result and before/after modes in the Day 6 note. Cleanup: keep the synthetic sample if it supports your evidence; otherwise, after confirming the exact path, remove the file and directory: 

rm ~/gcp-architect-learning/day-006-permissions/sample.txt
rmdir ~/gcp-architect-learning/day-006-permissions

No cloud resource or billable service exists.

Troubleshooting: if stat lacks GNU -c support, record the full output of stat sample.txt instead. If the read behaves differently, confirm that the shell is not privileged and inspect ACLs with getfacl when that command is available.

Artifact Acceptance: the Day 6 note contains the actual UID and groups, the -rw------- and -r-------- modes, the synthetic line, the cleanup result, and an explanation of directory search versus file read permission.

Exercise 2 · Compare graceful and forced worker termination

Goal: Compare graceful termination with forced termination and inspect service evidence. Mode: local Linux terminal; the optional journal step needs a working user systemd manager. No sudo or cloud account is needed.

Expected Result: SIGTERM produces a timestamped cleanup line and exit status 0; SIGKILL produces no cleanup line and normally yields Bash wait status 137. The evidence must use only the PID captured from the disposable worker.

Preflight: open an ordinary Bash shell in ~/gcp-architect-learning and verify the local tools:

cd ~/gcp-architect-learning
command -v bash python3 ps kill
python3 --version

Expected: command paths plus a Python 3 version. The systemd journal step is optional and must be skipped when the per-user service manager is unavailable.

Step 1 — Create a disposable worker

Open a terminal in the Day 1 repository and create the script: 

cd ~/gcp-architect-learning
cat > day-006-worker.py <<'PY'
from datetime import datetime, timezone
import os
import signal
import time

def stamp(message):
    now = datetime.now(timezone.utc).isoformat()
    print(f'{now} {message}', flush=True)

def stop(signum, frame):
    stamp(f'graceful stop pid={os.getpid()} signal={signum}')
    raise SystemExit(0)

signal.signal(signal.SIGTERM, stop)
stamp(f'started pid={os.getpid()}')
while True:
    time.sleep(1)
PY

The file contains synthetic process behavior only. The handler writes an observable line when SIGTERM arrives.

Step 2 — Start and gracefully stop it

Keep the same terminal open and run: 

python3 -u day-006-worker.py > day-006-graceful.log 2>&1 &
worker_pid=$!
sleep 1
ps -p "$worker_pid" -o pid,stat,comm
kill -TERM "$worker_pid"
wait "$worker_pid"
graceful_status=$?
printf 'graceful exit=%s\n' "$graceful_status"
cat day-006-graceful.log

Expected: ps lists the Python process, the log has started and graceful stop , and the exit status is 0. PID and timestamps vary. Record the actual PID and result.

Step 3 — Compare a forced stop 

python3 -u day-006-worker.py > day-006-forced.log 2>&1 &
worker_pid=$!
sleep 1
kill -KILL "$worker_pid"
wait "$worker_pid"
forced_status=$?
printf 'forced exit=%s\n' "$forced_status"
cat day-006-forced.log

Expected: the log has started but no graceful stop . In Bash, the forced exit is commonly 137 (128 plus signal 9); record the observed value. The shell may also print a “Killed” message. Do not send a kill signal to any PID other than the one captured from this disposable process.

Step 4 — Inspect the journal when available

If your Linux VM has a user systemd manager, run the following in the same repository. Skip and record “user manager unavailable” if the first command cannot connect; do not install or enable a system service just for this lesson. 

systemctl --user status --no-pager
python_path="$(command -v python3)"
systemd-run --user --unit=gcp-day6-lab --collect "$python_path" "$PWD/day-006-worker.py"
systemctl --user status gcp-day6-lab --no-pager
journalctl --user -u gcp-day6-lab --since '5 minutes ago' --no-pager
systemctl --user stop gcp-day6-lab
journalctl --user -u gcp-day6-lab --since '5 minutes ago' --no-pager

Expected: the unit shows a running PID, then the journal shows start and graceful-stop messages with timestamps. Journal access and exact formatting depend on the VM's configuration. Verification: save commands, PID, exit codes and log or journal timestamps; explain which stop allowed cleanup. Cleanup: confirm the user unit is stopped and the captured PIDs no longer appear. Keep the script and logs as evidence or delete them after recording; no cloud resource exists.

Step 5 — Clean up in reverse dependency order

systemctl --user stop gcp-day6-lab 2>/dev/null || true
rm -f ~/gcp-architect-learning/day-006-graceful.log
rm -f ~/gcp-architect-learning/day-006-forced.log
rm -f ~/gcp-architect-learning/day-006-worker.py
test ! -e ~/gcp-architect-learning/day-006-worker.py && printf 'cleanup: complete\n'

Expected final line: cleanup: complete. Stop the optional unit before deleting the executable it references.

Troubleshooting: if wait reports a different nonzero forced status, record the shell and observed status rather than changing it to 137. If the graceful log is empty, confirm Python was started with -u and that the captured PID belongs to the disposable worker.

Artifact Acceptance: the note includes both PIDs, UTC log timestamps, the observed graceful and forced exit statuses, the presence or absence of the cleanup line, optional journal evidence or an explicit skip reason, and a statement that replay safety comes from durable idempotency rather than the service manager.
