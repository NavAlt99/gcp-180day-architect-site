1 · Concepts and problem previews

Google Cloud accounts and the Free Trial

What it is. A Google Cloud Account binds a corporate or personal Google identity to cloud resources through an associated Cloud Billing Account. Google Cloud offers a Free Trial providing $300 in promotional credit valid for 90 days across Compute Engine, Cloud Storage, BigQuery, and managed services. Claiming the Free Trial requires a verified credit card or bank account for identity authentication, but Google Cloud guarantees that accounts are never automatically billed upon trial expiration unless an administrator explicitly upgrades to a paid account. Cloud Billing Accounts exist as standalone administrative objects linked across one or more projects to fund operational workloads.

Why today. Day 18 marks the entrance into Block 2 (Cloud environment and identity, Days 18–35). Before provisioning cloud infrastructure, an architect must establish secure billing boundaries, understand credit consumption lifecycles, and implement governance controls to prevent billing accidents in sandbox environments.

System location. Cloud Billing Accounts sit at the administrative root of the Google Cloud commercial relationship, connected to projects via the Cloud Resource Manager API.

Problem preview. An expired corporate payment method on an unmonitored billing account triggers automated suspension across training sandbox projects, instantly terminating running compute instances. Without redundant payment routing and billing preflight verification, sudden cloud account lockouts disrupt engineering onboarding and delay critical project timelines.

Google Cloud Free Tier and monthly limits

What it is. Distinct from the 90-day Free Trial credit, the Google Cloud Free Tier provides non-expiring monthly usage allowances ("Always Free") across core infrastructure services. Eligible resources include one e2-micro virtual machine instance per month in qualifying US regions (us-central1, us-east1, us-west1) with 30 GB standard persistent disk, 5 GB-months of regional Cloud Storage, 2 million Cloud Run requests, and 1 TB of monthly BigQuery analysis. Crucially, a budget alert is merely a notification mechanism—it does not programmatically halt running compute instances or cap billable API invocations.

Why today. Architects must distinguish between promotional credits, Always Free limits, and billable compute usage. Assuming that budget notifications enforce hard spending limits is among the most frequent and costly operational misconceptions made by cloud practitioners.

System location. The Google Cloud billing meter and Cloud Monitoring quota subsystem continuously evaluate API consumption against published service limits.

Problem preview. A training pipeline exceeds its monthly Always Free Compute Engine quota by running an oversized VM in a non-qualifying region, incurring unexpected daily billing charges. Misinterpreting passive budget alert emails as automated hard spend caps leads to budget exhaustion and unexpected corporate credit card overages.

Google Cloud Console navigation and project selection

What it is. The Google Cloud Console provides a centralized web interface and integrated Cloud Shell terminal for administering cloud resources. Navigation is structured around the resource hierarchy (Organization → Folders → Projects). Projects serve as the foundational isolation boundary, characterized by three distinct identifiers: (1) a human-friendly, mutable Project Name; (2) an immutable, globally unique Project ID; and (3) an immutable, system-assigned numeric Project Number. Navigating the console requires pinned service shortcuts, search filters, and active project context management.

Why today. All cloud operations—whether executed via web console, gcloud CLI, or Terraform—operate within an active project context. Conflating mutable project names with immutable project IDs or operating in the wrong ambient project context creates critical security and operational risks.

System location. The Google Cloud Console, Cloud Resource Manager, and Cloud Shell execution environment mediating operator access to cloud APIs.

Problem preview. An engineer executing a resource cleanup command from Cloud Shell targets the production project instead of the training sandbox due to ambient project context drift. Conflating project display names with immutable project IDs risks accidental deletion of production microservice endpoints, creating immediate customer checkout outages.

2 · Architecture, control flow, boundaries, and limits

Google Cloud account structure, billing accounts, and project linkages

Scope, control flow, and ownership. Managing Google Cloud infrastructure requires a clear separation between identity, resource management, and commercial billing:

  • Identity Layer: User accounts (Google Accounts, Google Workspace, or Cloud Identity) authenticate through OAuth 2.0 to access Google Cloud APIs.
  • Resource Hierarchy: Projects organize compute, storage, and networking resources into isolated security and administrative domains. A project cannot exist without a parent organization or folder in enterprise deployments.
  • Cloud Billing Account: An administrative construct that defines how Google is paid (credit card, bank account, or invoiced corporate billing). A single billing account can fund multiple projects, but each project can be linked to at most one billing account at any given time.

Free Trial versus Paid Account transitions. The $300 Free Trial credit applies to all billable Google Cloud services over 90 days. While the trial is active, accounts are constrained by lower default quotas (e.g. GPU allocations and Windows Server licenses are restricted to prevent fraud). When promotional credits expire or 90 days elapse, all active workloads are suspended unless an administrator explicitly upgrades to a paid account. Upgrading activates standard service quotas while retaining access to the ongoing Always Free tier allowances.

Always Free tier boundaries and the budget alert misconception

Always Free service boundaries and regional rules. Google Cloud provides recurring monthly usage allowances across key products without charging the linked billing account, provided usage strictly complies with published regional and SKU parameters:

  • Compute Engine: 1 non-preemptible e2-micro virtual machine instance per month (approximately 744 hours), limited to us-central1 (Iowa), us-east1 (South Carolina), or us-west1 (Oregon). Includes 30 GB-months of standard persistent disk storage and 1 GB per month of outbound internet egress. Provisioning an e2-micro in Europe or Asia immediately incurs standard compute billing.
  • Cloud Storage: 5 GB-months of Standard Storage, restricted to regional buckets in us-central1, us-east1, or us-west1. Includes 5,000 Class A (mutation) operations and 50,000 Class B (read) operations per month. Dual-region or multi-region buckets do not qualify.
  • Cloud Run & Functions: 2 million requests per month, 360,000 GB-seconds of memory, and 180,000 vCPU-seconds. Idle services scaled to zero instances incur zero charges.
  • BigQuery: 1 TB of query data scanning per month and 10 GB of active storage.
  • Cloud Logging: 50 GB of log ingestion per project per month free of charge.

The Budget Alert Misconception: Notifications versus Hard Spend Caps. One of the most critical operational lessons for a cloud architect is understanding that a Cloud Billing budget alert is an advisory notification, not a programmatic spend cap:

  • When actual or forecasted spending crosses configured thresholds (e.g. 50%, 90%, 100% of $50), Google Cloud dispatches notification emails to billing administrators and optionally publishes a JSON event to a Google Cloud Pub/Sub topic.
  • Crucially, Google Cloud will NOT automatically shut down running virtual machines, delete storage buckets, or throttle API traffic when a budget alert fires. Resources continue running, and financial charges continue to accrue uninhibited until an operator intervenes.
  • To enforce an absolute, programmatic spend cap, an architect must build an automated kill-switch: configure the budget to publish to a Pub/Sub topic, subscribe a serverless Cloud Function, and write code that invokes the Cloud Billing API (projects.billingInfo.update) to programmatically unlink the billing account or stop Compute Engine instances.

Because Cloud Shell caches active CLI configuration in ~/.config/gcloud, engineers working across multiple projects must guard against ambient project drift—accidentally issuing commands against an unintended environment because the default project was left pointing to another project.

3 · Real-world field problems and incident handling

Incident exercise · Billing account disconnection suspends active workloads

Illustrative scenario—not an observed production incident. During an ongoing engineering study cohort at Brightloaf, team members arriving for morning lab work reported that all experimental Cloud Run microservices and Compute Engine instances in the brightloaf-sandbox-18 project were unreachable. Developers attempting to deploy code via Cloud Shell received the error: ERROR: (gcloud.run.deploy) PERMISSION_DENIED: The billing account for project [brightloaf-sandbox-18] is disabled in state [CLOSED]. Billing must be enabled to activate services. When the platform lead logged into the Google Cloud Console, they discovered that the corporate purchasing credit card linked to the primary Cloud Billing Account had expired on the first of the month. Because no secondary payment method was configured and billing notification emails were sent to a legacy distribution alias, Google Cloud suspended the billing account after a grace period, disabling APIs and stopping all compute resources across six associated projects.

Constraints: Rely on synthetic Brightloaf test fixtures, observe zero budget spend, and preserve the duplicate fulfillment invariant.

Root cause analysis: The organization lacked billing account redundancy and automated preflight verification: (1) no backup payment method was linked to the Cloud Billing Account; (2) billing alerts were routed to an unmonitored mailbox; and (3) CI/CD deployment pipelines did not include a billing health verification preflight step, allowing infrastructure to run blind until payment failure caused catastrophic service suspension.

5-step diagnostic sequence:

  1. Execute the billing project inspection command: the billing project describe command to check the billingEnabled boolean and retrieve the linked billingAccountName.
  2. Query the billing account status using the Cloud Billing API or console to verify whether the account state is OPEN or CLOSED.
  3. Audit Cloud Audit Logs to identify the exact timestamp of billing suspension and review the list of halted compute and serverless instances.
  4. Update the Cloud Billing Account with an active primary payment method and configure a verified secondary backup credit card or bank account.
  5. Re-link the project to the active billing account (the billing project link command) and verify that API operations resume with zero orphaned resources.

Defensible solution: Establish robust billing governance and automated pipeline preflight checks: First, configure a secondary payment method in the Google Cloud Billing Console to guarantee automated failover if primary card processing fails. Second, update the Cloud Billing Account notification contacts to include active engineering leads and financial operations channels. Third, implement an automated preflight script in all deployment pipelines asserting billingEnabled == true before initiating resource provisioning. Fourth, confirm that restored microservices uphold the duplicate fulfillment invariant (≤ 1 physical fulfillment per unique order ID) when processing re-submitted transactions.

Verification and residual risk: Execute a simulated billing verification script asserting that billingEnabled is True and that the linked billing account is Open; verify that Cloud Run services process synthetic order requests and return HTTP 201; confirm that duplicate order submissions are rejected by relational constraints. Residual risk: When billing is re-enabled following suspension, ephemeral external IP addresses previously assigned to Compute Engine VMs may have been released and reassigned by Google Cloud; mitigate by reserving static external IP addresses or relying on Cloud DNS hostnames for inter-service communication.

Incident exercise · Budget alert misconception leads to cloud spend overrun

Illustrative scenario—not an observed production incident. A development squad at Brightloaf configured a $50 monthly budget alert on their sandbox project to conduct performance benchmarking on order intake models. Believing that Google Cloud would automatically cut off compute instances when spending reached $50, the engineers initiated an unconstrained load test on Friday afternoon spinning up four a2-highgpu-1g GPU-accelerated virtual machine instances ($3.67/hr each) to benchmark receipt parsing. At 11:30 PM Friday, total project spend crossed $50, and Google Cloud dutifully dispatched an alert email to the billing administrator. However, because the email arrived outside business hours, nobody reviewed the notification. The GPU instances continued computing throughout the weekend. By Monday morning, the project had accumulated 68 hours of continuous multi-GPU execution, racking up an unexpected charge of over $1,400 against the corporate credit card, exceeding the intended budget by 2,800%.

Constraints: Rely on synthetic Brightloaf test fixtures, observe zero budget spend, and preserve prior audit evidence.

Root cause analysis: The engineering team conflated passive budget notifications with programmatic spending caps. Standard Cloud Billing budget alerts send emails and publish Pub/Sub messages, but they deliberately do not interrupt running resources or cancel billable API operations.

5-step diagnostic sequence:

  1. Inspect active billing account budgets using the budget list command with the billing account parameter to verify configured threshold percentages (e.g. 50%, 90%, 100%) and notification channels.
  2. Review billing export data in BigQuery or the Cloud Console Cost Table report to pinpoint the exact SKU (e.g. Compute Engine GPU running in us-central1) responsible for the cost surge.
  3. Inspect running virtual machines using the compute instance list command to identify orphaned, unmonitored benchmark instances.
  4. Immediately terminate all rogue GPU instances (the compute instance deletion command) to stop financial hemorrhaging.
  5. Construct an automated Pub/Sub programmatic billing kill-switch architecture that subscribes a Cloud Function to budget alert topics and programmatically unlinks billing or stops instances when spend exceeds 100%.

Defensible solution: Implement programmatic cost controls, Compute Engine resource quotas, and automated instance self-termination: First, establish hard project-level Compute Engine quotas requesting 0 GPU allocations in sandbox projects, preventing engineers from accidentally launching high-cost instances. Second, for specialized workloads, embed automated self-termination timers into startup scripts (e.g. shutdown -h +120 to halt the VM after 2 hours). Third, deploy a programmatic billing cap using Cloud Functions subscribed to the budget Pub/Sub topic; when received spend exceeds the target budget, the function calls the Cloud Billing API to disable project billing or halt compute instances. Fourth, emphasize the Cloud Digital Leader business principle: automated financial governance protects corporate operating margins from runaway development loops.

Verification and residual risk: Execute a synthetic cost monitoring script simulating budget notifications at 50%, 90%, and 100%; verify that reaching 100% triggers automated instance termination; confirm that the core order fulfillment service maintains the duplicate fulfillment invariant (≤ 1 shipment) across recovery cycles. Residual risk: Programmatically unlinking billing as a hard spend cap shuts down all resources indiscriminately, including persistent database instances; mitigate in production environments by implementing targeted instance shutdown (halting compute VMs while preserving databases) rather than complete billing disconnection.

Incident exercise · Project context drift deploys resources to wrong environment

Illustrative scenario—not an observed production incident. A site reliability engineer at Brightloaf was assigned to clean up an outdated testing service named order-api-v1 in the development sandbox project. Opening Cloud Shell in the Google Cloud Console, the engineer executed a cleanup command: a service deletion command targeting order-api-v1. Unbeknownst to the engineer, a colleague had previously used the shared workstation terminal to troubleshoot an incident in the production project, executing setting the active project to brightloaf-prod-us without resetting the default. Because the deletion command did not specify an explicit --project parameter, the gcloud CLI executed against the ambient production project, instantly terminating Brightloaf's live production Order API. Real-time customer checkout immediately failed with HTTP 404 Not Found errors across all retail channels, triggering an emergency P1 outage that lasted 22 minutes until the service could be redeployed from the CI/CD artifact repository.

Constraints: Rely on synthetic Brightloaf test fixtures, observe zero budget spend, and preserve the duplicate fulfillment invariant.

Root cause analysis: The operational failure stemmed from relying on implicit ambient project state in the CLI across multi-tenant environments. Without visual project indicators in shell prompts or mandatory --project flags in operational runbooks, human error caused a destructive command to cross project isolation boundaries.

5-step diagnostic sequence:

  1. Query active gcloud CLI configuration using the active project lookup command to determine the current ambient project context.
  2. Inspect Cloud Audit Logs in the production project filtering on resource.type="cloud_run_revision" and methodName="google.cloud.run.v1.Services.DeleteService" to identify the caller and deletion timestamp.
  3. Correlate the caller's identity with Cloud Shell access logs to confirm project context drift as the root cause.
  4. Immediately restore production availability by triggering the automated CI/CD pipeline to redeploy the latest immutable container image from Artifact Registry.
  5. Enforce operational controls: reconfigure terminal shell prompts (PS1) to dynamically display the active project ID, and enforce mandatory --project flags in all script runbooks.

Defensible solution: Eliminate ambient project ambiguity through prompt configuration, CLI configurations, and IAM privilege separation: First, customize the shell prompt (PS1) in Cloud Shell and local developer environments to dynamically display the active gcloud project in bold colors, providing immediate visual feedback of the target environment. Second, utilize named gcloud configurations (creating a configuration profile for prod and a profile for sandbox) to switch between fully isolated profile contexts. Third, mandate that all operational runbooks, automation scripts, and destruction commands explicitly specify --project="${TARGET_PROJECT_ID}" rather than relying on default state. Fourth, enforce strict IAM privilege boundaries: revoke administrative write/delete permissions for regular developers in production projects, requiring break-glass privileged access workflows to prevent accidental cross-project destruction.

Verification and residual risk: Execute a test script verifying that the shell prompt dynamically reflects project changes; assert that issuing destructive commands without an explicit --project flag is blocked by policy wrappers; verify that production order endpoints maintain continuous availability and uphold the duplicate fulfillment invariant (≤ 1 shipment). Residual risk: Complex shell prompt hooks that invoke the active project lookup command on every command execution can introduce latency in terminal rendering; mitigate by caching the active project in an environment variable updated only during project switching.

import sys

# Google Cloud Always Free Monthly Quotas
FREE_TIER_LIMITS = {
    "compute_hours_per_month": 744,       # 1 e2-micro instance 24/7
    "compute_allowed_regions": {"us-central1", "us-east1", "us-west1"},
    "storage_gb_months": 5.0,             # 5 GB Standard Storage
    "storage_allowed_regions": {"us-central1", "us-east1", "us-west1"},
    "cloud_run_requests": 2_000_000,      # 2 million requests
    "bigquery_query_tb": 1.0              # 1 TB scanned
}

# Standard On-Demand Rates for Overages
RATES = {
    "e2_micro_hourly": 0.0084,            # ~$6.25/mo
    "storage_gb_monthly": 0.020,          # $0.02/GB
    "cloud_run_per_million": 0.40,        # $0.40 per million requests
    "bigquery_per_tb": 6.25               # $6.25 per TB scanned
}

def calculate_monthly_bill(workload):
    name = workload["name"]
    region = workload["region"]
    vm_hours = workload.get("vm_hours", 0)
    storage_gb = workload.get("storage_gb", 0.0)
    run_reqs = workload.get("cloud_run_requests", 0)
    bq_tb = workload.get("bigquery_tb_scanned", 0.0)

    billable_charges = {}

    # 1. Compute Engine Calculation
    if region not in FREE_TIER_LIMITS["compute_allowed_regions"]:
        # Regional disqualification: 100% of compute hours are billable
        billable_hours = vm_hours
        print(f"  [!] Compute in non-free region '{region}': Free tier does not apply.")
    else:
        billable_hours = max(0, vm_hours - FREE_TIER_LIMITS["compute_hours_per_month"])

    if billable_hours > 0:
        billable_charges["Compute Engine"] = billable_hours * RATES["e2_micro_hourly"]

    # 2. Cloud Storage Calculation
    if region not in FREE_TIER_LIMITS["storage_allowed_regions"]:
        billable_storage = storage_gb
    else:
        billable_storage = max(0.0, storage_gb - FREE_TIER_LIMITS["storage_gb_months"])

    if billable_storage > 0:

import re
import sys

def validate_project_id(project_id):
    """
    Google Cloud Project ID rules:
    - 6 to 30 characters in length
    - Starts with a lowercase letter
    - Contains only lowercase letters, digits, and hyphens
    - Cannot end with a hyphen
    - Cannot contain uppercase letters or underscores
    """
    pattern = r'^[a-z][a-z0-9-]{4,28}[a-z0-9]$'
    is_valid = bool(re.match(pattern, project_id))
    return is_valid

def execute_safe_operation(active_context_project, target_project, command_type):
    """
    Guards against ambient project context drift.
    Requires explicit target project matching active context and blocks production deletions.
    """
    print(f"\nEvaluating command: '{command_type}'")
    print(f"  Active CLI Context: '{active_context_project}'")
    print(f"  Target Flag Project: '{target_project}'")

    if not validate_project_id(target_project):
        raise ValueError(f"Invalid Project ID format: '{target_project}'")

    if active_context_project != target_project:
        print("  [ERROR] Project context mismatch! Active context does not match target flag.")
        print("  Aborting execution to prevent accidental cross-project modification.")
        return False

    if "prod" in target_project and command_type in ("DELETE", "DESTROY", "TEARDOWN"):
        print("  [BLOCKED] Destructive operation on PRODUCTION project rejected by safety guard.")
        print("  Requires explicit break-glass bypass token.")
        return False

    print(f"  ✓ Operation '{command_type}' authorized on project '{target_project}'.")
    return True
