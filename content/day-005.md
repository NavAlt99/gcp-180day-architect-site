<!-- topic-01:overview -->
A virtual private network (VPN) connects private networks across an untrusted transport by authenticating peers and protecting traffic in a tunnel. A site-to-site VPN joins network gateways; a client VPN connects an individual device. The tunnel, routes and firewall permissions are separate parts of a working connection.

<!-- topic-01:technical -->
An IPsec site-to-site VPN encapsulates private traffic between gateways and protects it in transit. The inner packet still has source and destination addresses that must be routed on both sides. Tunnel establishment proves the peers can negotiate protection; it does not prove that the desired subnet prefixes are advertised or that firewalls permit the application. Overlapping private ranges complicate routing even when encryption is healthy. Tunnel overhead also reduces the effective path MTU, so a small packet may succeed while a larger one stalls. In Google Cloud, Cloud VPN extends a peer network to a VPC over IPsec; it is for private-network connectivity, not a general public-internet egress gateway.

An architect should document the peer endpoints, protected prefixes, route exchange, allowed ports, availability design and owner of each gateway. Verification needs both directions of a representative application flow, not just a tunnel-up indicator.

**Further study:** [RFC 4301 §3.3, IPsec tunnel mode](https://www.rfc-editor.org/rfc/rfc4301#section-3.3) and [Google Cloud VPN overview](https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview).

<!-- topic-01:problem -->
**Failure:** A VPN dashboard shows the tunnel up, but Brightloaf's cloud order service cannot reach an on-premises inventory database.

**Cause:** The on-premises side has no route back to the cloud source prefix. The encrypted tunnel is healthy, but the return packet cannot find the tunnel. A blocked database port or overlapping prefixes would be different causes that require their own evidence.

**Fix:** Check the exact source/destination prefixes, forward route, return route and firewall rules. Add the missing approved route advertisement and test a database connection in both directions. Keep tunnel health and application reachability as separate checks. If large responses still hang, investigate tunnel MTU after the route is corrected.

<!-- topic-02:overview -->
A load balancer presents a frontend address or service and distributes connections or requests among backends. Network load balancing makes decisions from transport and network information; application load balancing can use HTTP details such as host and path. Health checks determine which backends are eligible for new traffic.

<!-- topic-02:technical -->
Load balancing separates the client-facing endpoint from the set of serving instances. A network load balancer can handle transport flows without understanding HTTP paths; an application load balancer can route different URLs or hostnames to different backend services. Proxy and passthrough products also differ in whether they terminate a connection or preserve its packet properties. Internal versus external exposure is a separate choice about who can reach the frontend. In Google Cloud, the product family includes Application Load Balancers and Network Load Balancers with different scopes and protocol support.

Health probes test a configured condition, not every customer request. A backend may pass a shallow TCP or HTTP health check while its order-processing dependency is broken. Conversely, a wrong probe path or blocked probe source can mark a healthy application unavailable. The architect must define a useful health condition, backend capacity assumptions, session behavior and a way to inspect frontend, backend and probe results during failure.

**Further study:** [Google Cloud Load Balancing overview — types](https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview#types-of-cloud-load-balancers) and [Health checks overview — health state](https://docs.cloud.google.com/load-balancing/docs/health-check-concepts#health_state).

<!-- topic-02:problem -->
**Failure:** Customers reach the load balancer but receive a service error. Both order backends are reported unhealthy, although each process is running.

**Cause:** The configured health probe asks for `/ready`, but the backends only serve `/health`; the probe receives a non-success response. A running process is not equivalent to passing the configured probe.

**Fix:** Compare the probe protocol, port and path with what the backend actually serves. Correct the probe or application route, then wait for the configured healthy threshold and verify a customer request. If the probe itself cannot reach the backend, inspect firewall and routing for probe traffic. Do not send all traffic to unhealthy backends just to clear the alert.

**Goal:** Choose the right load-balancing layer and repair a failed probe in a supplied design. **Mode:** local worksheet.

### Step 1 — Classify the traffic

```text
Requirement A: route HTTPS /orders and /reports to different backend services
Requirement B: forward a non-HTTP UDP stream to a backend pool
Backend 1: GET /health -> 200; GET /ready -> 404

```

Mark A as an application-layer routing need and B as a network/transport need. In Google Cloud, use the product comparison link above to identify compatible families; do not assert that one load balancer type handles both requirements.

### Step 2 — Diagnose the probe

Record the observed 404 for `/ready` and predict that the backend fails this configured probe. Choose one repair: implement a meaningful `/ready` endpoint or change the probe to a suitable existing endpoint after checking that it reflects readiness. Explain why `/health` returning 200 does not automatically satisfy a probe sent to `/ready`. **Verification:** the worksheet identifies the wrong path and specifies a post-repair customer request. **Cleanup:** no load balancer or backend was deployed.

<!-- topic-03:overview -->
A firewall evaluates traffic against rules that match properties such as direction, source, destination, protocol, port and target. An allow decision permits a matching flow at that boundary; a deny decision blocks it. A firewall rule does not create a missing route or make an application listen on a port.

<!-- topic-03:technical -->
Ingress rules concern traffic entering a target; egress rules concern traffic leaving it. In Google Cloud VPC firewall rules, the applicable rule with the lowest numeric priority value takes precedence, and a deny wins when otherwise matching allow and deny rules have equal priority. Target selection matters as much as a source range or port: a rule for one VM group does not protect every VM. Connection tracking can allow return packets for established permitted flows, while a new reverse-direction flow is a different case. Higher-level firewall policies can also affect evaluation, so a real diagnosis must inspect the effective policy, not just one visible VPC rule.

Cloud architects use firewall rules to express narrowly allowed paths between tiers. Broad “allow all” rules can hide a route or service defect and enlarge exposure. During an incident, compare the packet tuple and target with the rule's direction, priority and logging; then check whether the packet reached a listening service. A matching allow is evidence of policy permission, not end-to-end success.

**Further study:** [Google Cloud VPC firewall rules — components and priority](https://docs.cloud.google.com/firewall/docs/firewalls#firewall_rule_components).

<!-- topic-03:problem -->
**Failure:** An order API VM should accept HTTPS from the load balancer, but direct connections from the public internet also succeed.

**Cause:** A broad ingress allow rule for TCP 443 targets the VM at a higher priority than the intended narrow rule. The narrow rule does not restrict traffic already allowed by the broader match.

**Fix:** Inspect effective policies and matching rule priorities for the actual VM target and packet source. Remove or narrow the broad rule, preserve the load-balancer source path, and verify both a permitted probe and a denied direct attempt. Keep logs for the transition. Do not rely on the application's login page as the only network boundary.

<!-- topic-03:lab -->
**Goal:** Evaluate a supplied ingress rule set and propose a least-privilege repair. **Mode:** local worksheet; no firewall is modified.

### Step 1 — Evaluate rules in priority order

```text
Target: order-api VM; packet: source 198.51.100.25 -> TCP 443
Priority 100: allow ingress TCP 443 from 0.0.0.0/0 to order-api
Priority 200: allow ingress TCP 443 from 203.0.113.0/24 to order-api
Priority 300: deny ingress TCP 443 from 0.0.0.0/0 to order-api
```

The packet matches the priority-100 allow, so it is permitted despite the later deny. The addresses are documentation fixtures. Write this result and the rule that won in your note.

### Step 2 — Repair and test the policy

Remove or narrow the broad priority-100 allow in your *proposed* rule set. Keep the intended load-balancer source range allowed and direct sources denied. Evaluate two packets: one from 203.0.113.25 and one from 198.51.100.25. Expected: the first is allowed and the second denied, assuming no higher-level policy changes the result. **Cleanup and cost:** no cloud project or firewall rule was touched; save the before/after rule table.
