1. SLSA levels, software supply chain concepts, SBOMs

The Supply-chain Levels for Software Artifacts (SLSA) framework provides a comprehensive specification for software supply chain integrity. As modern attacks shift from exploiting production vulnerabilities to poisoning upstream dependencies and build systems, organizations must establish verifiable provenance for every container artifact. Google Cloud Build supports SLSA Level 3 compliance out of the box, generating signed in-toto provenance metadata detailing the source repository, commit hash, builder identity, and compilation parameters.

Problem preview: A rogue dependency update injects malicious code during build time; because build provenance is absent, security teams cannot determine which production container digests contain the poisoned commit.

2. Secrets in CI/CD (never in code or images)

Securing sensitive credentials, private keys, and API tokens across the Continuous Integration and Continuous Deployment lifecycle requires eliminating static secrets from source code, Dockerfiles, and intermediate container filesystem layers. Google Cloud provides integrated secrets governance through Secret Manager, Cloud Build native secret bindings, and Docker BuildKit secret mounts, ensuring credentials exist strictly in ephemeral memory during execution and never persist into published container images.

3. Container hardening (distroless images, non-root users, read-only filesystems)

Container runtime hardening establishes defense-in-depth within Kubernetes pods, ensuring that even if an attacker achieves remote code execution through an application-level vulnerability, they are trapped in a restricted, unprivileged sandbox. Enterprise container hardening rests on three fundamental pillars: Google Distroless base images (eliminating shells and package managers), enforcing non-root user execution (preventing root privilege escalation), and locking the container filesystem in read-only mode with dedicated temporary memory scratch spaces.

1. SLSA levels, software supply chain concepts, SBOMs: technical mechanics

Securing the software supply chain requires cryptographic traceability across code, dependencies, build systems, and deployment engines.

SLSA Framework Levels & Invariants

  1. SLSA Build Level 1 (Build Script & Provenance):
  2. The build process is automated via a build script (e.g. cloudbuild.yaml).
  3. Provenance is generated, describing how the artifact was produced and listing top-level inputs.
  4. SLSA Build Level 2 (Hosted Build Service & Signed Provenance):
  5. The build runs on a dedicated hosted service (Cloud Build) rather than an individual developer workstation.
  6. Provenance is generated and digitally signed directly by the build platform using a platform-managed key.
  7. SLSA Build Level 3 (Hardened & Hermetic Isolation):
  8. The build executes in an ephemeral, isolated environment (Cloud Build isolated worker pool) preventing cross-build contamination.
  9. Hermetic builds ensure all inputs, compilers, and dependencies are explicitly declared and resolved before execution.
  10. Provenance is verifiable independently: users can verify the cryptographic signature using tools like slsa-verifier against Google’s public certificate authority.

Software Bill of Materials (SBOM)

  • Standardized Formats: SPDX (Software Package Data Exchange) and CycloneDX.
  • Granular Inventory: Documents every OS package (dpkg, rpm, apk) and language runtime library (npm, PyPI, Maven, Go modules) embedded in the container.
  • Vulnerability Correlation: When a new zero-day (such as CVE-2026-X) is disclosed, security teams query the SBOM database in Artifact Analysis to identify every affected image digest in seconds, without needing to perform slow filesystem scans across running pods.

Architectural evaluation questions

  • What specific threats does SLSA Level 3 build provenance mitigate that traditional unit testing and SAST scanning miss?
  • How does an in-toto signed provenance statement allow admission controllers to verify that an image was compiled strictly from an authorized GitHub commit?
  • What is the operational advantage of storing SPDX SBOM metadata alongside container image digests in Artifact Registry?

Further study: Supply-chain Levels for Software Artifacts (SLSA) Specification.

2. Secrets in CI/CD (never in code or images): technical mechanics

Container image layers are immutable tar archives. Merely deleting a file in a subsequent Dockerfile instruction does not remove it from the image—the file remains permanently embedded in the earlier intermediate layer history.

Anti-Patterns vs Secure Ingestion Patterns

  1. Anti-Pattern 1: Dockerfile ENV or ARG Secrets:
  2. Using ARG NPM_TOKEN or ENV DB_PASSWORD=xyz persists the variable directly into image manifest metadata and filesystem layer diffs.
  3. Anyone with read access to the image can execute docker history --no-trunc [IMAGE] or inspect layer tarballs to recover the secret in cleartext.
  4. Anti-Pattern 2: COPYing Secret Files then rming Them:
  5. Executing COPY id_rsa /root/.ssh/id_rsa && npm install && rm /root/.ssh/id_rsa creates a persistent image layer containing the private SSH key.
  6. Secure Pattern 1: Cloud Build Native Secret Manager Integration:
  7. In cloudbuild.yaml, declare availableSecrets referencing Secret Manager resource URIs.
  8. Map secrets directly to environment variables or secret volumes attached exclusively to designated build steps: ```yaml availableSecrets: secretManager:
    • versionName: projects/$PROJECT_ID/secrets/npm-token/versions/latest env: 'NPM_TOKEN' ```
  9. Secure Pattern 2: BuildKit Build-Time Secret Mounts:
  10. Use Docker BuildKit syntax # syntax=docker/dockerfile:1.4 and mount secrets at compile time: RUN --mount=type=secret,id=npm_token npm install.
  11. The secret file is mounted in memory strictly for the duration of the command and is never committed to any layer.
  12. Secure Pattern 3: Runtime Workload Identity & CSI Secret Store:
  13. In production GKE, avoid baking secrets into container environments altogether. Inject secrets dynamically at runtime using the Secret Manager CSI Driver mounting secrets as volatile in-memory tmpfs volumes.

Architectural evaluation questions

  • Why does executing `RUN rm /secret.key` in a Dockerfile fail to eliminate the secret from the published container image?
  • How does Docker BuildKit `--mount=type=secret` guarantee that temporary credentials are never stored in intermediate layer tarballs?
  • What is the operational function of the Secret Manager CSI Driver in eliminating static Kubernetes secret objects from etcd?

Further study: Google Cloud Secret Manager and Cloud Build Integration Guide.

3. Container hardening (distroless images, non-root users, read-only filesystems): technical mechanics

Container hardening dramatically reduces the attack surface and renders common post-exploitation tactics ineffective.

The Three Pillars of Container Hardening

  1. Google Distroless Container Images:
  2. Standard base images (Ubuntu, Debian, Alpine) contain hundreds of unnecessary utilities: package managers (apt, apk), interactive shells (/bin/sh, /bin/bash), network tools (curl, wget, nc), and system libraries.
  3. Google Distroless images (gcr.io/distroless/static-debian12, distroless/python3, distroless/java17-debian12) contain only the application binary, its runtime dependencies, and minimal root certificates.
  4. Without a shell or package manager, attackers cannot execute shell injection payloads, download second-stage malware, or spawn reverse shells.
  5. Non-Root User Execution:
  6. By default, containers run as UID 0 (root). If a container escapes or mounts host paths, root in the container can compromise the host kernel.
  7. In the Dockerfile: Specify a high-numbered non-root UID (e.g. USER 65532:65532 in Distroless, or USER 10001:10001).
  8. In the Kubernetes Manifest: Enforce securityContext.runAsNonRoot: true and securityContext.runAsUser: 65532. Policy Controller admission webhooks reject any manifest omitting these fields.
  9. Read-Only Root Filesystem with tmpfs Scratch:
  10. Enforcing securityContext.readOnlyRootFilesystem: true locks the container filesystem in read-only mode.
  11. Attackers cannot write binaries to /tmp, modify configuration files in /etc, or overwrite web assets in /var/www.
  12. Applications requiring writable scratch space (for temporary buffers or PID files) mount ephemeral emptyDir volumes backed by RAM (medium: "Memory").

Architectural evaluation questions

  • How does eliminating shells (`/bin/sh`, `/bin/bash`) in Distroless base images prevent command injection exploitation?
  • Why is running as non-root critical even when containers operate inside isolated Linux namespaces?
  • What is the operational pattern for supporting applications that require temporary scratch files while enforcing a read-only root filesystem?

Further study: Google Cloud Container Workload Hardening and Distroless Guide.

1. SLSA levels, software supply chain concepts, SBOMs · field case

Enterprise scenario: Production cluster runs an unauthorized container build containing code that never existed in the official Git repository.

Failure symptoms and impact: Backdoor embedded in API server; attacker exfiltrates database records via hidden HTTP endpoint; origin of build unknown.

Constraints: All production workloads must prove SLSA Level 3 provenance originating from the main branch before admission.

Evidence:

Container Admission Verification failure:

ERROR: Verification failed for us-central1-docker.pkg.dev/prod/api@sha256:d82bf1
slsa-verifier: no in-toto provenance attestation found.
Builder Identity: UNKNOWN (Built locally on developer workstation)
Source Commit: UNVERIFIABLE

Analysis: An engineer built and pushed a container image directly from their local laptop using personal credentials, bypassing Cloud Build and injecting unreviewed testing code into production.

Root cause: Artifact Registry allowed direct image pushes from developer user accounts, allowing untracked local builds to bypass Cloud Build SLSA provenance generation.

Diagnostic sequence:

  1. Extract the container image digest from the running Kubernetes pod manifest.
  2. Execute <kbd>gcloud artifacts docker images describe [DIGEST] --show-provenance</kbd> to inspect provenance metadata.
  3. Check Artifact Registry IAM policies to identify which identities have `roles/artifactregistry.writer` permissions.
  4. Verify that Binary Authorization policies enforce `slsa-provenance` attestations.

Defensible remediation: Revoke human write access to production Artifact Registry repositories, restrict image pushing strictly to the Cloud Build service account, and enforce SLSA Level 3 verification in Binary Authorization.

Residual risk: Compromised developer credentials with git push access could still commit malicious code directly to source control.

2. Secrets in CI/CD (never in code or images) · field case

Enterprise scenario: Security audit discovers production database master passwords exposed in public container registry layers.

Failure symptoms and impact: Third-party auditors discover active database credentials using <kbd>docker history</kbd>; immediate emergency database password rotation mandated.

Constraints: CI/CD pipeline must fail immediately if any `ARG` or `ENV` instruction contains sensitive keywords.

Evidence:

Docker history inspection output:

IMAGE          CREATED        CREATED BY                                      SIZE
8a72b91c89f1   2 hours ago    ARG DB_PASS=super_secret_pg_pass_99201           0B
3e41c098a72b   2 hours ago    ENV DATABASE_URL=postgresql://admin:$DB_PASS@... 0B

Analysis: The build script passed credentials via Docker build-args, permanently baking the secret into the image metadata.

Root cause: Developers used `ARG` and `ENV` instructions in Dockerfiles to configure database connections, permanently exposing credentials in container layer metadata.

Diagnostic sequence:

  1. Execute <kbd>docker history --no-trunc [IMAGE_NAME]</kbd> to inspect the full compilation command history.
  2. Review the Dockerfile source code for `ARG` and `ENV` statements matching credential patterns.
  3. Check Secret Manager to verify if an existing managed secret was bypassed.
  4. Audit Cloud Build step logs to see how variables were passed to the <kbd>docker build</kbd> command.

Defensible remediation: Refactor the Dockerfile to eliminate `ARG`/`ENV` secrets, configure Cloud Build `availableSecrets` with Secret Manager, and inject credentials dynamically at runtime via Secret Manager CSI.

Residual risk: Application logs emitted during runtime startup must be audited to ensure credentials are not dumped to stdout.

3. Container hardening (distroless images, non-root users, read-only filesystems) · field case

Enterprise scenario: Web pod compromised via command injection; attacker downloads malware binary to /tmp and runs it as root.

Failure symptoms and impact: Attacker modifies cluster node configuration and pivots laterally; incident detection delayed due to standard shell usage.

Constraints: All production pods must run as non-root with read-only root filesystems and zero installed shell binaries.

Evidence:

Runtime Container Threat Detection finding:

{
  "category": "EXECUTION_ADDED_BINARY",
  "resource": "k8s_pod/checkout-api-882bf",
  "details": {
    "binary_path": "/tmp/xmrig_miner",
    "user": "root (UID 0)",
    "parent_process": "/bin/sh"
  }
}

Analysis: The container inherited from debian:latest, ran as root, and had a writable root filesystem, allowing the attacker to download and execute arbitrary binaries.

Root cause: The application used a full Debian base image running as root with a writable filesystem, allowing an attacker to drop and execute binaries.

Diagnostic sequence:

  1. Review the application Dockerfile to inspect the base image and user declarations.
  2. Inspect the Kubernetes Deployment manifest for `securityContext` settings (`runAsNonRoot`, `readOnlyRootFilesystem`).
  3. Test whether `/bin/sh` or `/bin/bash` can be executed inside the pod via <kbd>kubectl exec</kbd>.
  4. Verify filesystem mount permissions on `/tmp` and `/app`.

Defensible remediation: Migrate the Dockerfile to Google Distroless, declare `USER 65532:65532`, and enforce `readOnlyRootFilesystem: true` with an in-memory tmpfs mount in the Kubernetes deployment manifest.

Residual risk: In-memory buffer overflows targeting application memory structures must be mitigated by memory-safe programming languages or compiler protections.

  2. Implement the SLSA Provenance Verification Tool

    Write a Python tool that evaluates the provenance document against enterprise supply chain policies (builder ID, git repository URI, and hermetic invariants):

    cat <<'EOF' > verify_slsa.py
import json
import sys

TRUSTED_BUILDER = "https://cloudbuild.googleapis.com/GoogleHostedWorker"
TRUSTED_REPO_PREFIX = "git+https://github.com/fintech-enterprise/"

def verify_provenance():
    with open("slsa_provenance.json", "r") as f:
        statement = json.load(f)

    print("=== Verifying SLSA Level 3 Build Provenance ===\n")
    pred = statement.get("predicate", {})
    builder_id = pred.get("builder", {}).get("id")
    repo_uri = pred.get("invocation", {}).get("configSource", {}).get("uri", "")
    commit = pred.get("invocation", {}).get("configSource", {}).get("digest", {}).get("sha1", "")
    slsa_level = pred.get("buildConfig", {}).get("slsaLevel", 0)
    hermetic = pred.get("buildConfig", {}).get("hermetic", False)

    violations = []
    if builder_id != TRUSTED_BUILDER:
        violations.append(f"UNTRUSTED BUILDER: {builder_id} (Expected {TRUSTED_BUILDER})")
    if not repo_uri.startswith(TRUSTED_REPO_PREFIX):
        violations.append(f"UNTRUSTED REPO: {repo_uri}")
    if slsa_level < 3:
        violations.append(f"INSUFFICIENT SLSA LEVEL: Level {slsa_level} (Requires Level 3)")
    if not hermetic:
        violations.append("NON-HERMETIC BUILD: Dependencies not isolated")

    print(f"Artifact Subject: {statement['subject'][0]['name']}")
    print(f"Digest: {statement['subject'][0]['digest']['sha256']}")
    print(f"Builder ID: {builder_id}")
    print(f"Source Git Commit: {commit}")
    print(f"Evaluated SLSA Level: {slsa_level} (Hermetic: {hermetic})\n")

    if violations:
        print("VERDICT: PROVENANCE VERIFICATION FAILED [!]")
        for v in violations:
            print(f"  - {v}")
        verdict = "REJECT"
    else:
        print("VERDICT: PROVENANCE VERIFIED (SLSA L3 Compliant) [OK]")
        verdict = "ACCEPT"

    report = {
        "verdict": verdict,
        "builder": builder_id,
        "source_commit": commit,
        "slsa_level": slsa_level,
        "violations": violations
    }
    with open("slsa_verification_report.json", "w") as out:
        json.dump(report, out, indent=2)
    print("\nWrote slsa_verification_report.json.")

if __name__ == "__main__":
    verify_provenance()
EOF

import json
import re
import sys

SECRET_REGEXES = [
    (re.compile(r"GITHUB_TOKEN=[a-zA-Z0-9_-]+"), "Exposed GitHub Personal Access Token"),
    (re.compile(r"DB_PASSWORD=[a-zA-Z0-9_-]+"), "Exposed Database Password in ENV"),
    (re.compile(r"ghp_[a-zA-Z0-9]{36}"), "GitHub Token Pattern")
]

def inspect_layers():
    with open("image_history.json", "r") as f:
        layers = json.load(f)

    print("=== Container Image Layer History Secret Audit ===\n")
    findings = []

    for idx, layer in enumerate(layers, 1):
        cmd = layer.get("created_by", "")
        lid = layer.get("layer_id", "")
        for pattern, desc in SECRET_REGEXES:
            match = pattern.search(cmd)
            if match:
                findings.append({
                    "layer_index": idx,
                    "layer_id": lid,
                    "finding": desc,
                    "snippet": match.group(0)[:30] + "..."
                })

    print(f"Total Layers Analyzed: {len(layers)}")
    print(f"Secret Exposures Discovered: {len(findings)}\n")
    for f in findings:
        print(f"[CRITICAL] Layer #{f['layer_index']} ({f['layer_id']}):")
        print(f"  Type: {f['finding']}")
        print(f"  Snippet: {f['snippet']}\n")

    verdict = "REJECT" if findings else "PASS"
    report = {
        "verdict": verdict,
        "findings_count": len(findings),
        "findings": findings
    }
    with open("layer_audit_report.json", "w") as out:
        json.dump(report, out, indent=2)
    print(f"Audit completed with verdict: {verdict}. Wrote layer_audit_report.json.")

if __name__ == "__main__":
    inspect_layers()
EOF
