<!-- topic-01:overview -->
CPU scheduling shares processor time among runnable tasks; waiting and context switches affect how much work completes. Virtual memory maps process addresses to physical pages. Page faults, page cache, swap, out-of-memory (OOM) events and pressure-stall information (PSI) describe different aspects of memory and resource pressure.

<!-- topic-01:technical -->
A process can be slow because it is running on a saturated CPU, waiting for CPU time, blocked on storage, or stalled while memory pages are reclaimed. High CPU utilization alone does not distinguish these cases. A context switch changes which task runs; it has a cost, but seeing many switches is not automatically the root cause. A page fault means a virtual address needed mapping work; a minor fault can be resolved without disk I/O, while a major fault may need data from storage. The page cache uses RAM to avoid repeated file reads and is often reclaimable, so low “free” RAM is not by itself an OOM diagnosis. Swap can relieve pressure at a performance cost, but it is not a replacement for enough memory.

OOM is an exceptional response when memory demands cannot be satisfied under the applicable limits. PSI reports time tasks were stalled by CPU, memory or I/O contention, and its “some” and “full” lines describe different scopes of stall. In cloud VMs and containers, check both host and cgroup limits: a workload can hit its container memory limit while the host still has available memory. Architects compare latency, resource limits, PSI, OOM events and application logs before resizing or tuning anything.

**Further study:** [Linux kernel memory concepts — page cache and reclaim](https://docs.kernel.org/admin-guide/mm/concepts.html#page-cache), [Linux PSI interface](https://docs.kernel.org/accounting/psi.html#pressure-interface), and [proc meminfo fields](https://man7.org/linux/man-pages/man5/proc_meminfo.5.html#DESCRIPTION).

<!-- topic-01:problem -->
**Failure:** A worker becomes slow and then restarts. A dashboard shows low free RAM, so the team increases the VM size, but restarts continue.

**Cause:** The worker is constrained by a smaller cgroup memory limit and is killed when it exceeds that limit. Page cache occupied much of the host's otherwise reclaimable RAM; the host-wide free-memory graph was not the relevant boundary.

**Fix:** Correlate the worker restart time with container/cgroup memory events, OOM logs, process working set and memory PSI. Adjust the workload limit or memory usage after identifying the first violated boundary. Separately inspect CPU pressure if latency remains. Avoid triggering an OOM deliberately in a shared lab VM.

<!-- topic-01:lab -->
**Goal:** Record a safe local CPU and memory baseline, then classify supplied pressure evidence. **Mode:** Linux terminal with Python 3; the CPU task stops after about half a second and allocates no large buffer.

### Step 1 — Run a bounded CPU task

Open a terminal and run:

```sh
python3 - <<'PY'
import resource
import time
start_wall = time.perf_counter()
start_cpu = time.process_time()
deadline = start_wall + 0.5
work = 0
while time.perf_counter() < deadline:
    work += 1
used_wall = time.perf_counter() - start_wall
used_cpu = time.process_time() - start_cpu
print(f'wall_seconds={used_wall:.2f} cpu_seconds={used_cpu:.2f} work_iterations={work}')
print('minor_faults=', resource.getrusage(resource.RUSAGE_SELF).ru_minflt)
print('major_faults=', resource.getrusage(resource.RUSAGE_SELF).ru_majflt)
PY
```

Expected: wall time near 0.5 seconds, nonzero CPU time and a machine-dependent iteration count. Fault counts vary. The difference between wall and CPU time can include scheduling and other delays; one short sample is not a performance benchmark.

### Step 2 — Read memory and pressure indicators

```sh
grep -E '^(MemTotal|MemAvailable|Cached|SwapTotal|SwapFree):' /proc/meminfo
cat /proc/pressure/cpu
cat /proc/pressure/memory
```

Expected: memory fields in kB and, on a kernel with PSI enabled, “some” and possibly “full” lines with averages and totals. If `/proc/pressure` is absent, record that the kernel does not expose PSI here. Do not use the numbers to claim that this tiny CPU task caused host-wide pressure.

### Step 3 — Classify a supplied incident

```text
Case A: high CPU some-PSI; no OOM event; requests queue before execution
Case B: cgroup memory.events oom_kill increases; worker PID changes after restart
```

Expected: A suggests CPU waiting or throttling needs investigation; B shows a memory-limit/OOM boundary. In your note, identify one next observation for each. **Cleanup:** the bounded process has exited; no cloud or persistent service resource was created. Keep only your baseline note.

<!-- topic-02:overview -->
Diagnostic command-line tools answer different questions. Grep, sed and awk filter or transform text; jq selects fields from JSON. Curl tests an HTTP exchange; dig asks DNS questions; ss inspects sockets; tcpdump captures packets at a network interface. A tool's output is evidence only for the boundary it observes.

<!-- topic-02:technical -->
Text-processing tools are useful for logs when the format is known. Grep finds matching lines, sed performs stream edits, and awk selects or computes from fields. JSON should be parsed structurally with jq or a proper JSON parser rather than with a fragile text pattern. Curl can show HTTP response details but a successful curl to one URL does not prove other paths or users work. Dig can compare A and AAAA answers from chosen resolvers without proving transport reachability. Ss shows local socket state, not whether a remote firewall permits traffic. Tcpdump can show packets seen at an interface, but capture permissions and location determine visibility; it may include sensitive payloads, so use a synthetic or approved environment.

The diagnostic sequence follows the suspected boundary. For a failed order request, first record the name and address, then socket establishment, TLS if used, HTTP status and application logs. Choose the smallest tool and data set that can confirm or falsify the current hypothesis. A single green command exit must not be promoted to an end-to-end claim.

**Further study:** [GNU grep manual](https://www.gnu.org/software/grep/manual/grep.html), [GNU sed manual](https://www.gnu.org/software/sed/manual/sed.html), [GNU awk manual](https://www.gnu.org/software/gawk/manual/gawk.html), [jq manual](https://jqlang.org/manual/), [curl manual](https://curl.se/docs/manpage.html), and [ss manual](https://man7.org/linux/man-pages/man8/ss.8.html).

<!-- topic-02:problem -->
**Failure:** An operator greps a JSON log for “error” and reports zero failed orders, but customers still see failures.

**Cause:** The log uses a structured numeric status field, and the failed entries do not contain the literal word “error.” A text search answered a different question than “how many orders returned a 5xx status.”

**Fix:** Inspect the log schema, parse its status field with a JSON-aware tool, count the relevant records and compare their timestamps with request metrics. Use curl, DNS and socket tools only to test the matching live boundary. Do not claim zero failures from an unmatched text pattern.

<!-- topic-02:lab -->
**Goal:** Compare text search with structured parsing on synthetic logs. **Mode:** local Linux terminal; no network or packet capture.

### Step 1 — Create a small fixture

Open a terminal in the Day 1 repository and run:

```sh
cd ~/gcp-architect-learning
cat > day-008-orders.jsonl <<'EOF'
{"order_id":"demo-1","status":200,"latency_ms":40}
{"order_id":"demo-2","status":503,"latency_ms":900}
{"order_id":"demo-3","status":200,"latency_ms":55}
EOF
grep 'error' day-008-orders.jsonl || true
grep '503' day-008-orders.jsonl
```

Expected: the first search prints nothing, while the second finds the demo-2 line. Neither search understands JSON field meaning; a quoted string elsewhere could make the second search misleading.

### Step 2 — Parse the status field

If jq is installed, run:

```sh
jq -r 'select(.status >= 500) | .order_id' day-008-orders.jsonl
```

Expected output is `demo-2`. If jq is unavailable, use Python 3:

```sh
python3 - <<'PY'
import json
with open('day-008-orders.jsonl', encoding='utf-8') as stream:
    for line in stream:
        event = json.loads(line)
        if event['status'] >= 500:
            print(event['order_id'])
PY
```

Expected output is also `demo-2`. In your note, explain why structured parsing supports the claim and the first grep did not.

### Step 3 — Map the remaining tools to boundaries

Record one question each for curl (HTTP), dig (DNS), ss (local sockets) and tcpdump (packets at an interface). If available, this read-only local command shows socket state without sending traffic:

```sh
ss -tan
```

Its rows vary by host; an empty or short list is valid. If the tool reports that socket inspection is unavailable in a restricted container, record that limitation rather than inventing a socket state. Do not run a packet capture on a shared machine. **Verification:** the note contains the one failed order and four tool-to-boundary mappings. **Cleanup:** keep the synthetic log as evidence or delete only that file; no cloud resource exists.
