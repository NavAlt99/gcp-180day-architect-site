1 · Concepts and problem previews

Resources and additive IAM inheritance

What it is: In the Google Cloud resource hierarchy, Identity and Access Management (IAM) policies flow strictly downward from the apex Organization node through intermediate Folders to Projects and individual Leaf Resources. The fundamental governing principle of cloud access control is that IAM allow policies are strictly additive: the effective permissions granted to a security principal on a target resource represent the mathematical union of all role bindings assigned at the resource itself, its parent project, and every ancestor folder up to the organization root. An allow permission granted at an ancestor folder or organization container cannot be revoked, attenuated, or overridden by a more restrictive IAM binding assigned at a child project or leaf resource.

Why today: Building directly upon the container architecture established on Day 21, cloud architects must master how security policies propagate through that structure before configuring enterprise access. A widespread architectural error is assuming that project-level role bindings can restrict broader folder-level permissions, leading teams to assign broad roles like roles/editor at high folder tiers and inadvertently exposing production databases across all child workloads with no leaf-level remedy short of explicit IAM Deny policies.

Where it sits: At the heart of the Google Cloud IAM Policy Evaluation Engine within the control plane. Every API request directed to a Google Cloud service triggers a hierarchical traversal that computes the effective permission set via mathematical union across all ancestor resource policies, validating whether the principal possesses the required authorization before granting execution access.

Problem preview

A franchise infrastructure administrator assigns the broad roles/editor role to an external contractor group at the parent Analytics folder level while attempting to restrict them with a roles/viewer role on the child production order project. Because IAM allow bindings are strictly additive across the hierarchy, the contractor automation script retained full write privileges, accidentally dropping the primary production fulfillment queue table and halting morning bakery order processing across 450 franchise stores.

Labels vs. tags vs. network tags

What it is: Google Cloud provides three completely distinct metadata mechanisms that are frequently conflated due to similar terminology: Resource Labels (client-managed key-value metadata attached to resources for cost allocation, BigQuery billing export grouping, and script inventory filtering), Resource Manager Tags (strongly typed, centrally governed key-value resources created under the Organization or Folder tree, inherited down the container hierarchy, and evaluated within IAM Conditions and Organization Policies), and Network Tags (ephemeral, unvalidated string attributes attached strictly to Compute Engine VM instances and templates for VPC firewall packet filtering and custom route evaluation).

Why today: Enterprise architects must establish disciplined governance, cost management, and network security boundaries without confusing operational metadata with cryptographic security controls. Mistaking a non-authoritative billing label for a firewall tag leaves mission-critical databases exposed to untrusted subnets, while failing to control VM-level network tags allows compute instance administrators to bypass network security perimeters.

Where it sits: Across three entirely separate architectural planes: Resource Labels operate in the Resource Metadata and Cloud Billing export plane; Resource Manager Tags operate in the Resource Manager, IAM Conditional Policy, and Organization Policy governance plane; and Network Tags operate exclusively in the VPC Virtual Distributed Router and firewall data plane.

Problem preview

A DevOps automation script applies resource labels with role: order-db to production database virtual machines, expecting VPC firewall rules targeting the order-db tag to restrict inbound connections to port 5432. Because VPC firewalls evaluate network tags rather than resource labels, the database instances received zero tag-based firewall filtering and defaulted to an open internal subnet rule, exposing raw customer payment tokens to a compromised staging development container and triggering an immediate regulatory audit.

2 · Architecture, control flow, boundaries, and limits

Hierarchical IAM policy inheritance, downward flow, and additive access calculation

Google Cloud organizes all infrastructure into a formal parent-child container hierarchy: the Organization node sits at the apex, containing Folders (which can nest up to 300 levels deep, with enterprise architectures generally utilizing 2 to 4 tiers), which contain Projects, which house Leaf Resources (such as Cloud Spanner databases, Compute Engine instances, Cloud Storage buckets, and Pub/Sub topics). Security governance across this tree is driven by the Identity and Access Management (IAM) Policy Evaluation Engine.

Downward Propagation and the Additive Union Principle

In standard Google Cloud IAM, access policies flow strictly downward from parent containers to their children. When an administrator grants an IAM role binding at an ancestor node (such as an Organization or Folder), that grant automatically applies to all descendant containers and resources. Crucially, IAM allow policies are strictly additive: the effective permissions possessed by a security principal on a target resource are computed as the mathematical union of all role bindings assigned across all ancestor containers in the resource path:

Mathematical Formalization of Effective IAM Permissions:

Given a target leaf resource R located in project P with ancestor folders F1, F2, …, Fk descending from organization O, the effective permission set Peffective(R) for principal u is defined as:

P_effective(u, R) = P_org(u, O) ∪ (∪ P_folder(u, F_i)) ∪ P_project(u, P) ∪ P_resource(u, R)

Because the evaluation engine computes a mathematical set union, IAM allow policies have no subtractive capability. There is no mechanism within standard IAM allow bindings to revoke, mask, restrict, or attenuate a permission at a lower node that was granted at a higher node. If a principal is granted roles/editor at a parent Folder, that principal retains complete write and administrative privileges across every single project inside that folder, even if a well-meaning security administrator explicitly assigns them the restrictive roles/viewer role at the child project level.

IAM Deny Policies: The Explicit Subtractive Guardrail

To establish hard negative boundaries that standard IAM allow bindings cannot provide, Google Cloud introduced IAM Deny Policies. Unlike allow policies, which are additive and evaluated as a union, Deny policies enforce non-negotiable negative constraints:

  • Evaluation Precedence: When an API request is received, the IAM policy evaluation engine evaluates Deny policies before allow policies. If an applicable Deny rule matches the principal and the requested permission, the request is immediately rejected, regardless of any inherited or direct allow bindings.
  • Downward Inheritance of Deny: Deny policies flow downward through the hierarchy. A Deny policy configured at the Organization or Folder level (for example, denying iam.serviceAccounts.delete or spanner.databases.drop) cannot be overridden, bypassed, or relaxed by any project administrator or developer.
  • Principle of Least Privilege Alignment: Architects should reserve broad folder-level bindings strictly for read-only auditor roles (such as roles/viewer or roles/securityReviewer) and delegate write or administrative roles exclusively at the leaf project tier.

Control Plane Limits and Latency Boundaries

When designing hierarchical governance, architects must design within Google Cloud's documented platform limits:

  • Folder Nesting Depth: Maximum of 300 levels of nested folders. Production enterprise landing zones typically adopt a depth of 2 to 4 folders (e.g. Org → Business Unit → Environment → Project) to maintain auditability.
  • IAM Policy Size Limits: An individual IAM policy on a project, folder, or organization cannot exceed 250 KB in total size, with a maximum of 1,500 member bindings across all role assignments. Large enterprises must bind roles to Cloud Identity Google Groups rather than individual users to prevent hitting policy size limits.
  • Propagation Latency: IAM policy modifications are globally replicated using eventual consistency. Changes take effect across regional control planes within seconds, but global edge caches and distributed API frontends may take up to 60 seconds to reflect updated bindings.

Disambiguating metadata: Labels vs. Resource Manager Tags vs. Network Tags

A widespread source of architectural defects, billing confusion, and security vulnerabilities in Google Cloud environments is the conflation of three distinct metadata mechanisms: Resource Labels, Resource Manager Tags, and Network Tags. While all three attach metadata to cloud assets, they operate in completely distinct control planes, serve incompatible functional purposes, enforce vastly different security semantics, and exhibit different inheritance behaviors.

Plane 1: Resource Labels (Operations & Cost Allocation)

Resource Labels are lightweight, client-managed key-value metadata pairs directly attached to individual cloud resources (such as Compute Engine VMs, Cloud Storage buckets, Cloud SQL databases, BigQuery datasets, and persistent disks). They are primarily designed for cost accounting, billing attribution, and operational scripting:

  • API & Attachment Plane: Stored directly within the resource metadata via individual service APIs (such as compute.instances.setLabels or storage.buckets.patch).
  • Syntax & Constraints: Keys and values are restricted to lowercase letters, numeric characters, underscores, and dashes, with a maximum length of 63 characters each. Keys may optionally include an internationalized character set or DNS prefix. A single resource can hold up to 64 labels.
  • Inheritance: Labels do NOT inherit. A label set on an Organization, Folder, or Project does not flow down to child resources within that project. Each resource must be labeled explicitly or stamped by automated deployment pipelines.
  • Billing Integration: Labels are automatically exported into the detailed Cloud Billing export in BigQuery, enabling granular chargeback queries (e.g. breaking down monthly spend by cost-center or application-id).
  • Security Boundary: Labels provide zero security or access control enforcement. They cannot be referenced in IAM conditions and have no effect on VPC firewall rules. Anyone with resource update permissions can freely modify or delete labels.

Plane 2: Resource Manager Tags (Centralized Governance & IAM Enforcement)

Resource Manager Tags (often referred to as Secure Tags) are first-class, centrally managed Google Cloud resources created under the Organization or Folder tree. Tags consist of a parent TagKey and child TagValue resources, which are bound to projects, folders, or individual resources via a TagBinding:

  • Centralized Lifecycle: Defined centrally at the Organization level (e.g. tagKeys/714029482103/environment with values tagValues/production and tagValues/staging).
  • Inheritance: Tags inherit automatically down the resource hierarchy. A tag bound to an intermediate folder automatically applies to all projects and supported resources within that branch, unless explicitly overridden at a lower tier.
  • Security & IAM Protection: Tag assignment is strictly governed by dedicated Cloud Resource Manager IAM roles: roles/resourcemanager.tagAdmin (who can create and delete tag keys and values) and roles/resourcemanager.tagUser (who is authorized to bind a tag value to a resource). A project administrator or developer cannot attach or remove a tag unless explicitly granted the tagUser role on that specific tag value.
  • IAM Conditions & Org Policy Integration: Tags can be evaluated in conditional IAM policy bindings using the Common Expression Language (CEL) function resource.matchTag('organizations/123/environment', 'production'). They can also be evaluated by Organization Policy constraints to enforce compliance across tagged resources.
  • Limits: Up to 1,000 tag keys per organization, up to 1,000 tag values per key, and a maximum of 50 tag bindings per resource.

Plane 3: Network Tags (Compute Engine VPC Packet Filtering)

Network Tags are simple, unvalidated string attributes attached strictly to Compute Engine virtual machine instances and Instance Templates. They exist exclusively within the VPC networking plane:

  • Scope & Attachment: Can only be attached to Compute Engine VM instances. They cannot be attached to Cloud Storage buckets, Cloud SQL databases, BigQuery datasets, or Folders.
  • Inheritance: Network tags do NOT inherit. They are per-instance attributes defined at VM creation or modified dynamically.
  • Purpose: Used exclusively by VPC Firewall Rules (via targetTags and sourceTags) and VPC custom route tables (via tags) to filter network traffic and steer packet routing at the virtual network layer.
  • Security Vulnerability: Modifying network tags requires only Compute Engine instance update privileges (compute.instances.setTags). If a developer has permission to edit a VM, they can change its network tags, potentially modifying which firewall rules apply to that VM. Consequently, network tags do not constitute an impenetrable security boundary against untrusted internal actors. For strict security isolation, Google Cloud recommends using Resource Manager Tags with Hierarchical Firewall Policies or Network Firewall Policies.

3 · Real-world problems and field crises

Brightloaf Incident 22.1 · Additive IAM inheritance escalation drops order fulfillment schema

Context & Architecture: The following operational crisis represents a synthetic engineering postmortem from Brightloaf's regional cloud infrastructure. Brightloaf hosts its core regional order management and point-of-sale ingestion pipeline inside Google Cloud project bl-order-fulfill-prod, located under the folder folders/839102482019 (labeled Production-Fulfillment). Persistent order records, customer franchise allocations, and payment reconciliation tables reside in a multi-region Cloud Spanner database named orders-db.

Failure Symptom

At 06:14 UTC, during the peak morning store opening rush across 450 franchise bakeries, all order fulfillment worker pods running in Google Kubernetes Engine (GKE) crashed simultaneously, triggering an immediate sev-1 outage alert. The application API gateways began returning HTTP 500 Internal Server Errors to POS cash registers, and worker pod standard error logs were flooded with critical database client exceptions:

google.api_core.exceptions.NotFound: 404 Database not found:
projects/bl-order-fulfill-prod/instances/bl-spanner/databases/orders-db
[StatusCode.NOT_FOUND, Details="Database does not exist or has been deleted"]

The primary production database containing active morning orders had completely vanished from the Cloud Spanner instance.

Operational & Business Constraints

  • Zero Data Loss & Invariant Preservation: Franchise retail transactions must not be dropped. More critically, Brightloaf's fundamental business invariant must be preserved across all recovery procedures: replaying an order or re-ingesting events from the queue must never cause a second physical fulfillment (≤ 1 physical fulfillment per unique order ID). Double-baking bread batches or duplicating franchise shipments creates severe ingredient waste and accounting imbalances.
  • Recovery Time Objective (RTO): Full order ingestion must be restored in under 45 minutes before local bakery proofing schedules fail.
  • Recovery Point Objective (RPO): Transaction data loss must be strictly under 5 minutes.

Discovered Evidence

Centralized security audit analysis revealed the following incontrovertible evidence:

  1. Cloud Audit Log Entry: A Cloud Audit Activity log export captured the exact administrative call that dropped the database: 
    {
  "protoPayload": {
    "@type": "type.googleapis.com/google.cloud.audit.AuditLog",
    "serviceName": "spanner.googleapis.com",
    "methodName": "google.spanner.admin.database.v1.DatabaseAdmin.DropDatabase",
    "resourceName": "projects/bl-order-fulfill-prod/instances/bl-spanner/databases/orders-db",
    "authenticationInfo": {
      "principalEmail": "analytics-deployer@brightloaf-franchise-analytics.iam.gserviceaccount.com"
    }
  },
  "timestamp": "2026-09-27T06:14:02.194Z"
}
  2. Project IAM Policy Inspection: Directly inspecting the project IAM policy on bl-order-fulfill-prod showed that the service account analytics-deployer@... was bound strictly to the primitive role roles/viewer. Under project-level policies alone, this identity had zero write or delete permissions.
  3. Folder IAM Policy Inspection: Inspecting ancestor container folders/839102482019 (Production-Fulfillment) revealed that an infrastructure engineer had previously bound roles/editor to the entire contractor group group:contractors-analytics@brightloaf.com, which contained the service account.

Root Cause Analysis

The incident was caused by a profound misunderstanding of Google Cloud's additive IAM inheritance model. An administrator had granted roles/editor at the parent folder tier so that external analytics contractors could freely create, modify, and delete staging datasets across experimental projects. Recognizing that the folder also contained bl-order-fulfill-prod, the administrator subsequently assigned roles/viewer directly to the contractor group on the production project, assuming the project-level viewer role would override or restrict the folder-level editor role.

Because IAM allow permissions are strictly additive (evaluated as a mathematical set union across all ancestors), the effective permission set was P_effective = P_folder(roles/editor) ∪ P_project(roles/viewer) = roles/editor. The project-level viewer role had zero restrictiveness. When an automated schema tear-down script in the contractor's CI/CD pipeline was accidentally pointed at the production project ID instead of staging, the DropDatabase API call succeeded immediately.

5-Step Diagnostic Sequence

  1. Query Activity Audit Logs: Query Cloud Audit Logs in the central security sink for methodName="google.spanner.admin.database.v1.DatabaseAdmin.DropDatabase" to identify the calling principal email, source IP, and exact timestamp.
  2. Audit Direct Project IAM Policy: Inspect the direct project IAM bindings using the Cloud SDK to determine whether the principal was granted write privileges directly on the project.
  3. Traverse Ancestor Hierarchy Bindings: Recursively fetch the IAM policies of all parent folders and the organization root using the Resource Manager API to discover inherited role assignments.
  4. Compute Effective Permission Set: Execute an IAM effective permission analysis demonstrating that the union of ancestor folder permissions granted spanner.databases.drop to the caller despite the project-level viewer role.
  5. Verify Buffer & Deduplication Ledger State: Check Pub/Sub subscription backlogs to verify that in-flight bakery orders were safely buffered in durable message storage with immutable idempotency UUID keys.

Defensible Solution & Remediation

  1. Immediate Parent Folder Remediation: Immediately revoke roles/editor from folders/839102482019 and all ancestor containers.
  2. Environment-First Folder Isolation: Reorganize the resource hierarchy into strict environment-first top-level folders (/Production vs. /Non-Production), ensuring external contractors and test automation identities hold zero bindings within the production folder branch.
  3. Organization-Level IAM Deny Guardrail: Implement an Organization IAM Deny Policy that explicitly blocks spanner.databases.drop and spanner.instances.delete for all non-emergency automated service accounts and developer groups across all production folders.
  4. Point-in-Time Recovery (PITR) Execution: Restore the Cloud Spanner database using Spanner Point-in-Time Recovery (PITR) to a timestamp exactly one minute prior to the drop (2026-09-27T06:13:00Z), restoring all tables, secondary indexes, and active transactions.
  5. Idempotent Event Stream Replay: Unpause the GKE fulfillment worker pods and replay the unacknowledged orders buffered in Pub/Sub. The worker application checks each incoming message against the restored transaction table using the unique order idempotency hash; already-committed orders are acknowledged immediately without executing physical bakery printing, guaranteeing that replaying events causes zero duplicate fulfillments (≤ 1 physical fulfillment per unique order ID).

Verification and Residual Risk

Verification: Simulated penetration tests using the contractor credentials confirmed that attempting to execute spanner.databases.drop returned HTTP 403 PERMISSION_DENIED. Database point-in-time recovery completed within 28 minutes, and replaying 3,214 buffered POS transactions resulted in exactly 3,214 physical bakery dispatches with zero duplicate orders produced.

Residual Risk: Point-in-Time Recovery relies on the database PITR retention window (Cloud Spanner default is 7 days). Global IAM policy modifications may take up to 60 seconds to propagate across all edge regions during emergency credential revocation.

Brightloaf Incident 22.2 · Resource label and network tag conflation exposes order database port

Context & Architecture: The following operational crisis represents a synthetic security engineering postmortem from Brightloaf's e-commerce backend. Brightloaf runs its primary order ingestion API on Compute Engine virtual machines and hosts its transactional PostgreSQL payment database on a dedicated Compute Engine instance named bl-order-db-prod-vm (private IP 10.128.0.45) within the production VPC network. Enterprise security policy strictly dictates that database port 5432 must be accessible exclusively from instances hosting the order ingestion API.

Failure Symptom

During an automated vulnerability scan executed by Brightloaf's central security Operations Center (SOC), a high-severity alert triggered at 14:22 UTC:

VULNERABILITY ALERT [SEV-1]: Port 5432 (PostgreSQL) openly reachable from untrusted subnet!
Source: 10.240.10.15 (staging-dev-bastion.internal)
Destination: 10.128.0.45:5432 (bl-order-db-prod-vm.internal)
Status: TCP SYN-ACK Handshake ESTABLISHED

An engineer discovered that a compromised container inside a non-production staging development environment was able to establish a direct, unencrypted TCP session with the production database listener.

Operational & Business Constraints

  • Zero Disruption to Active Ordering: Active franchise order ingestion on bl-order-api must remain uninterrupted; applying network firewall remediation must not drop legitimate active API database pools.
  • Fulfillment Invariant Guarantee: In accordance with Brightloaf's core order invariant, replaying an order or recovering dropped connections must never result in a second physical fulfillment (≤ 1 physical fulfillment per unique order ID). Database integrity and transaction idempotency tokens must remain pristine.
  • Auditable Compliance: Complete network segregation between production payment data and non-production development environments must be provably enforced to satisfy PCI-DSS audit mandates.

Discovered Evidence

Technical investigation across the infrastructure-as-code repository and live Google Cloud control plane revealed:

  1. Terraform Instance Definition: In the Terraform provisioning module for the database instance, the engineer configured metadata labels: 
    # modules/compute/database.tf
resource "google_compute_instance" "order_db" {
  name         = "bl-order-db-prod-vm"
  machine_type = "n2-standard-4"
  zone         = "us-central1-a"
  labels = {
    environment = "production"
    tier        = "order-database-secure"
  }
  # Note: The "tags" block was completely omitted!
}
  2. VPC Firewall Rule Configuration: The network security team had configured a restrictive firewall rule targeting network tags: 
    # modules/networking/firewalls.tf
resource "google_compute_firewall" "allow_db_from_api" {
  name        = "allow-order-db-from-api"
  network     = "bl-production-vpc"
  target_tags = ["order-database-secure"]
  source_tags = ["order-api-tier"]
  allow {
    protocol = "tcp"
    ports    = ["5432"]
  }
}
  3. Live Instance Metadata State: Inspecting the running instance via the Compute Engine API revealed: 
    {
  "name": "bl-order-db-prod-vm",
  "labels": {
    "environment": "production",
    "tier": "order-database-secure"
  },
  "tags": {
    "fingerprint": "42WmSpB8nxI=",
    "items": []
  }
}
    The instance's tags.items array was completely empty.

Root Cause Analysis

The security exposure was caused by conflating Resource Labels with Compute Engine Network Tags. The DevOps engineer assumed that setting labels = { tier = "order-database-secure" } in Terraform would satisfy the VPC firewall rule's target_tags = ["order-database-secure"] requirement.

However, VPC firewalls evaluate network tags exclusively, completely ignoring resource labels. Because the database instance lacked the network tag, the firewall rule allow-order-db-from-api never matched the instance. Consequently, incoming traffic to the database fell through to an overly permissive default internal subnet rule (allow-default-internal, allowing 10.128.0.0/9), which permitted any internal IP in the entire VPC network—including non-production development jump hosts—to connect directly to port 5432.

5-Step Diagnostic Sequence

  1. Verify TCP Handshake Logs: Inspect VPC Flow Logs and security scanner output confirming active TCP SYN-ACK sessions between staging IP 10.240.10.15 and production DB IP 10.128.0.45:5432.
  2. Inspect VM Instance Tag Array: Run a detailed instance description using the Compute Engine API to check the tags.items list and verify whether the instance holds the required network tags.
  3. Trace VPC Firewall Rule Priority: Execute VPC firewall rule simulation across the subnet to observe rule precedence, identifying which firewall rule authorized the packet when the targeted rule failed to match.
  4. Identify Permissive Fallback Rules: Locate broad legacy firewall rules (such as default internal allow rules) that inadvertently cover the database port.
  5. Audit Ingestion Database for Unauthorized Writes: Review PostgreSQL transaction audit logs to confirm that no staging or external connections performed write mutations, verifying that all processed transactions preserve the ≤ 1 physical fulfillment invariant.

Defensible Solution & Remediation

  1. Immediate Network Tag Hotfix: Add the missing network tag directly to the running Compute Engine instance via the Cloud SDK without interrupting active database connections: 
    gcloud compute instances add-tags bl-order-db-prod-vm   --tags=order-database-secure   --zone=us-central1-a
  2. Remediate Infrastructure as Code: Update the Terraform configuration to explicitly include tags = ["order-database-secure"] in the google_compute_instance resource block, ensuring future CI/CD runs maintain the correct network configuration.
  3. Purge Overly Permissive Subnet Rules: Delete the default allow-default-internal rule and replace it with explicit, least-privilege firewall rules that enforce an overarching Default-Deny ingress policy across the VPC.
  4. Transition to Resource Manager Secure Tags: Migrate VPC firewall packet filtering from mutable Compute Engine network tags to Resource Manager Secure Tags (target_secure_tag). Because Secure Tags require centralized resourcemanager.tagUser permissions to bind, compute instance administrators cannot manipulate tags to alter their firewall security posture.
  5. Audit Deduplication Ledger & Tokens: Validate that all transactions committed by bl-order-api during the incident contained immutable idempotency tokens, guaranteeing that subsequent system recovery and connection retries produce exactly zero duplicate bakery fulfillments (≤ 1 physical fulfillment per unique order ID).

Verification and Residual Risk

Verification: Immediate network probes from staging host 10.240.10.15 to 10.128.0.45:5432 timed out with 100% packet loss (dropped by VPC firewall). Probes from bl-order-api with tag order-api-tier connected successfully within 2 ms. The Cloud Billing BigQuery export confirmed that billing labels remained active for cost accounting.

Residual Risk: Standard Compute Engine Network Tags remain mutable by users possessing compute.instances.setTags. Full mitigation requires enforcing Resource Manager Secure Tags with Cloud Next-Gen Firewall policies to separate network security administration from compute instance administration.

class ResourceNode:
    def __init__(self, tier: str, resource_id: str, parent: ResourceNode | None = None):
        self.tier = tier
        self.resource_id = resource_id
        self.parent = parent
        self.bindings: Dict[str, List[str]] = {}
        self.deny_rules: Dict[str, Set[str]] = {}

    def add_binding(self, principal: str, role: str) -> None:
        self.bindings.setdefault(principal, []).append(role)

    def add_deny(self, principal: str, permission: str) -> None:
        self.deny_rules.setdefault(principal, set()).add(permission)

    def get_ancestor_path(self) -> List[ResourceNode]:
        path = []
        curr: ResourceNode | None = self
        while curr:
            path.append(curr)
            curr = curr.parent
        return list(reversed(path))

    def evaluate_effective_permissions(self, principal: str) -> Tuple[Set[str], List[dict], bool]:
        path = self.get_ancestor_path()
        accumulated_allows: Set[str] = set()
        accumulated_denies: Set[str] = set()
        trace = []

        for node in path:
            denies_here = node.deny_rules.get(principal, set())
            accumulated_denies.update(denies_here)

            roles_here = node.bindings.get(principal, [])
            tier_allows = set()
            for role in roles_here:
                tier_allows.update(ROLE_PERMISSIONS.get(role, set()))
            
            accumulated_allows.update(tier_allows)

            trace.append({
                "tier": node.tier,
                "resource_id": node.resource_id,
                "roles": roles_here,
                "tier_allows_count": len(tier_allows),
                "cumulative_allows_count": len(accumulated_allows),
                "active_denies": list(accumulated_denies)
            })

        effective = accumulated_allows - accumulated_denies
        is_subtractive_fallacy_active = (
            "roles/editor" in path[1].bindings.get(principal, []) and
            "roles/viewer" in path[2].bindings.get(principal, []) and
            "spanner.databases.drop" in effective
        )
        return effective, trace, is_subtractive_fallacy_active
