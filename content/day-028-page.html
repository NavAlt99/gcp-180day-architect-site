Topic 01

Programmatic budget notifications via Pub/Sub

What it is: Google Cloud Budgets can link directly to Cloud Pub/Sub topics to publish real-time JSON event notifications whenever actual or forecasted spend crosses specified threshold percentages (e.g., 50%, 90%, 100%), as well as periodically throughout the billing period as new resource usage is processed. These programmatic notifications enable automated event-driven architectures to ingest spend signals, trigger alerts in chat systems, update FinOps dashboards, or initiate automated cost-containment workflows (such as reducing development VM sizing or halting non-essential staging pipelines).

Why today: Standard email alerts require human triage, introducing hours of lag during rapid cloud spend spikes. Programmatic notifications provide machine-readable event streams that empower automated systems to respond within seconds of spend threshold crossings. However, because Pub/Sub guarantees at-least-once delivery, consumers must be explicitly designed for idempotency to avoid catastrophic over-remediation.

Where it sits: Cloud Budgets operate within the Cloud Billing control plane, pushing standardized JSON event envelopes across project boundaries into a designated Pub/Sub topic, which in turn distributes them to push or pull subscribers such as Cloud Functions, Cloud Run, or Eventarc handlers.

Duplicate Pub/Sub budget messages received by an unmemoized remediation Cloud Function triggered an aggressive secondary quota strip on production Cloud Run. The false duplicate execution dropped customer bakery orders mid-flight, costing Brightloaf $42,000 in lost morning sales.

Topic 02

Labels for cost attribution

What it is: Resource labels in Google Cloud are key-value string pairs attached directly to supported infrastructure resources—including Compute Engine instances, Persistent Disks, Cloud Storage buckets, BigQuery datasets, and GKE clusters. Unlike Resource Manager tags (which govern hierarchical IAM policies) or network tags (which control VPC firewall routes), resource labels are specifically ingested into Google Cloud's detailed and standard BigQuery billing export. This allows FinOps teams to group, filter, and allocate dollar-for-dollar costs along business dimensions such as cost-center, environment, team, and service.

Why today: Cloud projects often house multi-tenant applications or shared services where a single project invoice obscures which business unit generated which cost. Without rigorous resource labeling enforced at provisioning time, finance cannot assign chargebacks, identify runaway development experiments, or calculate unit economics for customer transactions.

Where it sits: Labels reside directly in the metadata of individual cloud resources, propagate automatically into Cloud Billing records, and appear as repeated STRUCT fields (labels.key and labels.value) in BigQuery billing export tables for SQL analysis and Looker Studio dashboards.

Untagged and unlabeled analytical BigQuery datasets prevented finance from attributing an unexpected $35,000 compute invoice to specific regional bakery divisions. The inability to allocate costs caused a dispute between marketing and operations, stalling production infrastructure funding for three weeks.

Topic 01 · Programmatic budget notifications via Pub/Sub

While standard email notifications alert human administrators to budget threshold crossings, modern cloud operating models demand event-driven automation. Google Cloud Budgets can link directly to a Cloud Pub/Sub topic, emitting structured JSON envelopes whenever actual or forecasted spend crosses defined threshold rules (e.g., 50%, 90%, 100%), as well as periodically throughout the billing period as new resource consumption metrics are processed.

Pub/Sub Event Delivery Semantics & Frequency

Architects integrating programmatic budget notifications must account for the specific operational characteristics of Google Cloud Billing's notification engine:

  • At-Least-Once Delivery: Cloud Pub/Sub guarantees that every published message is delivered to attached subscriptions at least once. If an automated consumer (such as a Cloud Function or Cloud Run service) processes a message but experiences a network glitch, slow logging response, or exceeds its acknowledgment deadline, Pub/Sub will redeliver the message. Consumers must therefore be strictly idempotent.
  • Periodic Status Notifications: Budgets do not publish events solely at the exact instant a threshold is crossed. Cloud Billing also publishes periodic status updates—often multiple times per day—whenever usage data is aggregated and spend is recalculated. Even if no new threshold has been breached, messages containing the current costAmount and the highest alertThresholdExceeded will be emitted.
  • Out-of-Order Delivery: Because Pub/Sub distributes messages across distributed messaging brokers, sequential delivery is not guaranteed unless message ordering keys are explicitly configured. A consumer might receive an update with a higher cost amount followed seconds later by an in-flight earlier update.

Notification Message Payload Schema

The message payload published to Pub/Sub is base64-encoded UTF-8 JSON. Downstream consumers parse this envelope to evaluate current spend and determine whether programmatic remediation is warranted.

Idempotency & State Machine Design

Because duplicate deliveries and periodic updates arrive over the same Pub/Sub topic, an automated remediation consumer must maintain an external or transactional state store (such as Google Cloud Memorystore for Redis, Cloud Firestore, or Cloud SQL) to prevent destructive re-execution.

A resilient idempotent consumer constructs a deterministic composite key from the event envelope:

dedup_key = f"{budgetDisplayName}:{costIntervalStart}:{alertThresholdExceeded}"

Before executing any operational action (such as dispatching a Slack webhook, scaling down non-production Compute Engine Managed Instance Groups, or temporarily disabling exploratory BigQuery query slots), the consumer queries the state store:

  1. Check Existence: If dedup_key already exists in the state store with status COMPLETED, the consumer logs an informational message (DUPLICATE_EVENT_DROPPED) and immediately acknowledges (ACK) the Pub/Sub message.
  2. Atomic Lock & Record: If dedup_key is absent, the consumer atomically writes the key with a processing state and a time-to-live (TTL) corresponding to the end of the billing interval.
  3. Execute Gated Action: The consumer executes the bounded remediation action. Crucially, automated remediation logic must enforce safety guardrails: production order ingestion, transaction databases, and fulfillment services must be hard-coded as non-terminable, preserving Brightloaf's duplicate fulfillment invariant (≤ 1 physical fulfillment per unique order ID).
  4. Acknowledge: Once the workflow completes, the consumer marks the state record as COMPLETED and returns an HTTP 200 / Pub/Sub ACK.

Topic 02 · Labels for cost attribution

In enterprise cloud deployments, infrastructure resources from multiple teams, environments, and business lines frequently reside within the same project or consume shared billing accounts. While project-level billing identifies gross project spend, it cannot answer granular questions such as: How much did the recommendation model cost compared to the checkout API last month? or Which engineering department is responsible for this unattached 50TB Persistent Disk?

Resource Labels: Technical Constraints & Mechanics

Google Cloud resource labels are lightweight key-value pairs attached directly to supported resources (such as Compute Engine instances, disks, GKE clusters, Cloud Storage buckets, and BigQuery datasets). Labels serve primarily as operational metadata and cost attribution tags.

Resource labels conform to strict structural rules enforced by Google Cloud APIs:

  • Capacity Limits: Each individual resource can hold a maximum of 64 labels.
  • Character Set & Case: Both keys and values must conform to RFC 1035 format. Keys and values can contain only lowercase letters, numeric characters, underscores (_), and dashes (-). International Unicode characters are supported in label values. Uppercase letters and whitespace are strictly prohibited.
  • Length Restrictions: Label keys must start with a lowercase letter, cannot be empty, and have a maximum length of 63 characters. Label values can be empty and have a maximum length of 63 characters.
  • Billing Propagation Delay: When labels are attached or modified on a running resource, telemetry updates propagate into Cloud Billing within one to four hours. Billing records reflect labels applied at the time of resource usage; retroactively modifying a label does not alter past historical billing export records.

Architectural Distinction: Labels vs. Tags vs. Network Tags

A frequent anti-pattern among cloud architects is confusing Resource Labels, Resource Manager Tags, and Compute Network Tags. Each fulfills an entirely distinct architectural domain:

BigQuery Detailed Billing Export Integration & SQL Unnesting

Google Cloud delivers billing telemetry into BigQuery through Standard Export (project, service, SKU, and daily costs) and Detailed Export (which includes individual resource IDs and attached labels). In BigQuery, labels are stored as a repeated record: ARRAY<STRUCT<key STRING, value STRING>>.

Because labels are stored as an array of structs, standard SQL aggregation requires unnesting the array to filter or group by business dimensions:

-- Querying cost attribution by cost-center from BigQuery Detailed Billing Export
SELECT
  project.id AS project_id,
  (SELECT value FROM UNNEST(labels) WHERE key = 'cost-center') AS cost_center,
  (SELECT value FROM UNNEST(labels) WHERE key = 'env') AS environment,
  service.description AS service_name,
  ROUND(SUM(cost), 2) AS total_cost_usd
FROM
  `brightloaf-billing.billing_export.gcp_billing_export_resource_v1_01A2B3_4C5D6E_7F8G9H`
WHERE
  _PARTITIONDATE = CURRENT_DATE() - 1
GROUP BY
  project_id, cost_center, environment, service_name
ORDER BY
  total_cost_usd DESC;

FinOps Best Practices: Mandatory Taxonomy & Governance

To eliminate "unallocated spend" blindspots, enterprise platform engineering teams establish a mandatory labeling taxonomy enforced at build and deploy time:

  • cost-center: Identifies the financial general ledger code or department (e.g., cc-bakery-ops, cc-ecommerce).
  • environment: Categorizes deployment tier (e.g., production, staging, development).
  • service: Specifies the microservice or business capability (e.g., order-ingestion, dispatch-optimizer).
  • owner: Contact email or squad alias responsible for resource lifecycle and billable hygiene.

Compliance is enforced using Terraform CI/CD validation rules (such as tflint or HashiCorp Sentinel) and Google Cloud Organization Policies with Tag binding, denying resource creation if mandatory cost attribution keys are missing.

Part 3 · Real-world problems

Analyzing severe production failures at Brightloaf: an unmemoized budget remediation consumer that throttled order intake upon duplicate Pub/Sub redelivery, and an unlabeled data pipeline that distorted eCommerce cost ledgers.

Crisis 28.1

Non-Idempotent Budget Consumer Triggers Duplicate Automated Quota Throttling on Production Ingestion

Symptom

At 08:14 UTC during the peak morning customer ordering window, Brightloaf's regional retail storefront and wholesale bakery partner APIs began returning widespread HTTP 429 Too Many Requests and HTTP 503 Service Unavailable errors. Over 8,400 bakery store replenishment orders failed mid-flight, shopping carts timed out, and automated physical dispatch at four central distribution facilities stalled.

Constraints

  • Messaging Protocol: Cloud Billing budgets publish event envelopes to Cloud Pub/Sub under an at-least-once delivery guarantee.
  • Automated Cost Remediation: A serverless Cloud Function was provisioned to listen for 100% budget threshold events and enforce emergency capacity limits to stop runaway spend.
  • Invariant: Brightloaf's physical duplicate fulfillment invariant (≤ 1 physical fulfillment per unique order ID) must never be compromised; order ingestion must never drop transactions or trigger untracked retry duplicates.

Evidence

Telemetry extracted from Cloud Logging and Cloud Audit Logs (cloudaudit.googleapis.com) revealed a catastrophic cascade:

  1. At 08:14:02 UTC, Cloud Billing published a 100% threshold notification (costAmount: 5120.40, budgetAmount: 5000.00, alertThresholdExceeded: 1.0) with message ID msg-882194 to topic projects/brightloaf-billing/topics/billing-alerts.
  2. The subscriber Cloud Function instance budget-remediator-01 received msg-882194. While processing, it experienced a 12-second latency spike attempting to push an audit record to an external monitoring dashboard. Because the Pub/Sub subscription acknowledgment deadline was configured to the default 10 seconds, Pub/Sub marked the message as unacknowledged and redelivered it.
  3. At 08:14:14 UTC, a second Cloud Function instance budget-remediator-02 pulled the redelivered msg-882194.
  4. Instance 01 completed its first execution, lowering Cloud Run maximum instances for order-ingestion-api from 100 to 20.
  5. Crucially, the remediation script lacked idempotency state tracking. Instance 02 executed the script a second time against the already-throttled service. Finding the current limit at 20, its stepped fallback logic aggressively dropped maximum instances from 20 down to 2! Concurrency collapsed from 8,000 requests/second to barely 160 requests/second.

Root Cause

The automated budget remediation consumer was designed without idempotency guards, naively assuming exactly-once delivery from Cloud Pub/Sub. Furthermore, the remediation script violated infrastructure boundary isolation by targeting production order ingestion services instead of being strictly confined to non-production development and staging tiers.

5-Step Diagnostic Sequence

  1. Inspect Pub/Sub Subscription Metrics: Query Cloud Monitoring for subscription/oldest_unacked_message_age and subscription/redelivered_message_count on billing-alerts-sub to confirm message retransmissions.
  2. Analyze Remediation Consumer Execution Logs: In Cloud Logging, filter by resource.type="cloud_function" AND textPayload=~"msg-882194" to identify overlapping executions and elapsed processing times exceeding the 10-second ACK deadline.
  3. Audit Resource Mutation Events: Search Cloud Audit Logs for methodName="google.cloud.run.v1.Services.ReplaceService" to verify that the reduction of maxScale from 100 to 20 and then 20 to 2 was executed by the budget remediation service account.
  4. Review Consumer Source Code for Idempotency Memoization: Inspect the Cloud Function handler to confirm whether it performs any deduplication lookup against a persistent state store (e.g., Firestore or Redis) prior to executing mutations.
  5. Validate Environment Scope Filtering: Check whether the remediation query filtered on resource labels (e.g., env="dev") or indiscriminately modified services across the entire project.

Defensible Solution

To permanently resolve the vulnerability while safeguarding production operations:

  1. Immediate Operational Recovery: Restore Cloud Run maxScale for order-ingestion-api back to 100 instances immediately via gcloud, and increase the Pub/Sub subscription ACK deadline from 10 seconds to 300 seconds.
  2. Deploy Persistent Atomic Deduplication Lock: Implement an idempotency check in the consumer handler using Cloud Firestore or Memorystore. The consumer derives a deterministic key: 
    dedup_key = f"{msg['budgetDisplayName']}#{msg['costIntervalStart']}#{msg['alertThresholdExceeded']}"
    If the key exists with status COMPLETED, the consumer logs DUPLICATE_EVENT_DROPPED and immediately returns an ACK without executing remediation.
  3. Enforce Production Immunity Guardrails: Hard-code environment segregation in the remediation engine. Automated quota or scaling reductions are strictly restricted to resources labeled env="development" or env="sandbox". Production order pipelines are classified as non-terminable, ensuring Brightloaf's duplicate fulfillment invariant (≤ 1 physical fulfillment per unique order ID) is unconditionally preserved.

Verification

In a controlled staging rehearsal, publish two identical Pub/Sub budget notification messages to the topic within a 500ms window. Verify that the consumer executes the targeted development teardown once, acquires the Firestore state lock, and logs [IDEMPOTENT_FILTER] Message msg-test-duplicate ignored (already completed) on the second arrival while acknowledging the message.

Residual Risk

If the external state store experiences a complete regional outage, the consumer might fail open and allow duplicate execution or fail closed and drop remediation. Mitigate by implementing a local in-memory LRU cache fallback within container memory holding recently seen message IDs.

Crisis 28.2

Unlabeled Workload Blindspot Inadvertently Attributes Shared Analytics Cluster to eCommerce Operations

Symptom

Following the monthly close, Brightloaf's finance department issued an internal cloud cost chargeback report attributing $54,700 to the eCommerce business unit—a 240% spike over its approved $16,200 baseline. Facing an unexpected deficit, the eCommerce business sponsor disputed the charge and placed an emergency spending freeze on cloud infrastructure, halting feature releases and planned checkout scalability enhancements.

Constraints

  • Billing Ingestion: BigQuery Detailed Billing Export is active and serves as the single source of truth for corporate chargeback calculations.
  • Shared Tenancy: Exploratory analytics and retail applications share a consolidated GCP billing account.
  • Dispute Resolution Policy: Any line-item charge disputed by a department head requires cryptographic or audit-log verified proof of resource ownership before charges can be cleared.

Evidence

FinOps investigation into BigQuery billing export records revealed the mechanism of contamination:

  1. The standard finance attribution SQL query was written with a naive fallback logic: 
    COALESCE((SELECT value FROM UNNEST(labels) WHERE key = 'cost-center'), project.name) AS cost_center
  2. A data science squad had deployed an ad-hoc GKE batch processing cluster and run multi-terabyte BigQuery geospatial queries to forecast holiday bakery demand. Because they provisioned these resources manually via scripts without attaching labels, the labels array in the billing export was empty.
  3. Because the GKE cluster was spun up inside the shared brightloaf-ecommerce-prod host project, the COALESCE function defaulted the attribution string to brightloaf-ecommerce-prod, automatically mapping $38,500 of exploratory data science compute into the eCommerce operations general ledger.

Root Cause

A systemic lack of resource labeling enforcement in the deployment pipeline allowed unlabeled shared compute to be provisioned. This was compounded by flawed FinOps attribution queries that collapsed unlabeled orphan spend into host project ownership rather than isolating it into a transparent unallocated variance bucket.

5-Step Diagnostic Sequence

  1. Quantify Unlabeled Spend in BigQuery Export: Execute an unnesting query on gcp_billing_export_resource_v1_* filtering for records where labels IS NULL or ARRAY_LENGTH(labels) = 0 to calculate total unattributed dollar volume.
  2. Isolate High-Variance SKUs: Group unlabeled records by sku.description and resource.name to identify which specific services (Compute Engine N2 instances and BigQuery Analysis) generated the $38,500 surge.
  3. Correlate Resource Identifiers with Audit Logs: Cross-reference the identified GKE node pool instance names against Cloud Audit Logs (cloudaudit.googleapis.com) to extract the principal email who invoked compute.instances.insert.
  4. Inspect CI/CD and Infrastructure as Code: Review the Terraform repository to verify whether the root module enforces default labels on Google Cloud provider blocks.
  5. Review FinOps Reporting Logic: Audit SQL views feeding Looker Studio dashboards to identify improper COALESCE expressions that disguise unallocated spend as operational application costs.

Defensible Solution

To restore financial accountability and prevent recurring attribution disputes:

  1. Financial Ledger Reallocation: Reassign the $38,500 invoice line item from cc-ecommerce to the Central Data Science R&D cost center (cc-analytics-rd), unfreezing eCommerce infrastructure funding.
  2. Fix FinOps Attribution SQL: Refactor the BigQuery chargeback views to route all records lacking a valid cost-center label to an explicit UNALLOCATED_SHARED_DEBT category: 
    CASE
  WHEN (SELECT value FROM UNNEST(labels) WHERE key = 'cost-center') IS NOT NULL
  THEN (SELECT value FROM UNNEST(labels) WHERE key = 'cost-center')
  ELSE 'UNALLOCATED_SHARED_DEBT'
END AS cost_center
  3. Enforce Mandatory Labeling via Policy: Implement mandatory labeling across all deployment pipelines. Update Terraform root provider configurations to inject default_labels (cost-center, env, service, owner) on all resources. Furthermore, deploy Google Cloud Policy Controller (OPA Gatekeeper) admission rules in GKE and Organization Policies to block the creation of any Compute Engine, Cloud Storage, or BigQuery resource lacking mandatory cost attribution keys.

Verification

Run the refactored FinOps SQL script against the billing dataset. Confirm that the $38,500 is cleanly segregated and that cc-ecommerce displays exactly $16,200.00. Then run a preflight Terraform deployment of an unlabeled VM and confirm that the CI pipeline halts with an explicit error: Missing required label: cost-center.

Residual Risk

Legacy resources provisioned before policy enforcement will continue to emit unlabeled billing telemetry. Mitigate by running scheduled inventory audit scripts that scan for unlabeled resources and automatically alert the project owner or apply default fallback labels.

Expected Result: Unique threshold events trigger bounded actions on non-production workloads; redelivered messages are identified via composite key lookup, logged as DUPLICATE_EVENT_DROPPED, and acknowledged immediately without re-executing mutations.

#!/usr/bin/env python3
"""
Lab 28.1: Idempotent Pub/Sub Budget Notification Consumer & Deduplication Engine
Demonstrates at-least-once message handling, composite state deduplication,
and safe remediation guardrails preserving Brightloaf's duplicate fulfillment invariant.
"""

import json
import os
import sys
from datetime import datetime, timezone

class IdempotentBudgetConsumer:
    def __init__(self):
        # Simulated persistent state store (e.g., Firestore / Memorystore Redis)
        self.state_store = {}
        self.remediation_history = []
        self.log_entries = []

    def log(self, level: str, message: str):
        timestamp = datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M:%S UTC")
        formatted = f"[{timestamp}] [{level.upper()}] {message}"
        print(formatted)
        self.log_entries.append(formatted)

    def derive_dedup_key(self, payload: dict) -> str:
        """Derive deterministic composite key from billing event envelope."""
        budget_name = payload.get("budgetDisplayName", "unknown")
        interval_start = payload.get("costIntervalStart", "unknown")
        threshold = payload.get("alertThresholdExceeded", 0.0)
        return f"{budget_name}#{interval_start}#{threshold:.2f}"

    def process_notification(self, raw_message: dict) -> dict:
        msg_id = raw_message.get("message_id")
        payload = raw_message.get("data", {})
        
        budget_name = payload.get("budgetDisplayName")
        cost = payload.get("costAmount", 0.0)
        budget = payload.get("budgetAmount", 0.0)
        threshold = payload.get("alertThresholdExceeded", 0.0)
        currency = payload.get("currencyCode", "USD")

        self.log("INFO", f"Received message {msg_id}: budget '{budget_name}', spend ${cost:,.2f}/{budget:,.2f} {currency} ({threshold*100:.0f}% threshold)")

        dedup_key = self.derive_dedup_key(payload)

        # Step 1: Check idempotency state store
        if dedup_key in self.state_store:
            prior = self.state_store[dedup_key]
            self.log("WARN", f"[IDEMPOTENT_DROP] Duplicate event detected for key '{dedup_key}'. First processed at {prior['timestamp']}. ACK returned without action.")
            return {
                "message_id": msg_id,
                "status": "DUPLICATE_DROPPED",
                "dedup_key": dedup_key,
                "action": "NONE"
            }

        # Step 2: Atomic State Registration
        self.state_store[dedup_key] = {
            "timestamp": datetime.now(timezone.utc).isoformat(),
            "cost_at_trigger": cost,
            "threshold": threshold,
            "status": "PROCESSING"
        }

        # Step 3: Execute Gated Remediation Workflow
        action_summary = "NOTIFY_ONLY"
        if threshold >= 1.0:
            self.log("CRITICAL", f"100% Budget exceeded! Evaluating automated remediation guardrails...")
            
            # Guardrail check: Production workloads are strictly immune!
            self.log("GUARDRAIL", "Evaluating target: 'order-ingestion-api' (env: 'production')")
            self.log("GUARDRAIL", "IMMUNITY TRIGGERED: Production order intake is shielded from automated scaling.")
            self.log("GUARDRAIL", "Duplicate fulfillment invariant preserved: <= 1 physical fulfillment per unique order ID.")
            
            # Non-destructive action on non-production workloads only
            self.log("ACTION", "Targeting non-production: Scaling down dev batch workers ('analytics-dev-workers') from 10 to 2 instances.")
            action_summary = "SCALE_DOWN_DEV_WORKERS"
            self.remediation_history.append({
                "target": "analytics-dev-workers",
                "env": "development",
                "action": "scale_down",
                "from_instances": 10,
                "to_instances": 2
            })
        elif threshold >= 0.9:
            self.log("ALERT", f"90% Budget warning ($ {cost:,.2f}). Dispatching PagerDuty/Slack notification to FinOps channel.")
            action_summary = "PAGERDUTY_FINOPS_ALERT"
        elif threshold >= 0.5:
            self.log("NOTICE", f"50% Budget checkpoint ($ {cost:,.2f}). Dispatching informational digest to engineering leads.")
            action_summary = "CADENCE_EMAIL_DIGEST"

        # Step 4: Finalize State & Return ACK
        self.state_store[dedup_key]["status"] = "COMPLETED"
        self.state_store[dedup_key]["action_taken"] = action_summary
        self.log("SUCCESS", f"Workflow '{action_summary}' finished. State '{dedup_key}' locked. Message ACKed.")

        return {
            "message_id": msg_id,
            "status": "PROCESSED",
            "dedup_key": dedup_key,
            "action": action_summary
        }

def analyze_attribution(records):
    """Processes records, unrolls labels, and calculates attribution buckets."""
    total_spend = sum(r["cost_usd"] for r in records)
    
    attribution_by_cost_center = {}
    detailed_rows = []
    unlabeled_spend = 0.0

    for r in records:
        labels_dict = {item["key"]: item["value"] for item in r.get("labels", [])}
        cost_center = labels_dict.get("cost-center")
        env = labels_dict.get("env", "unspecified")
        service_name = labels_dict.get("service", r["service"])
        
        is_labeled = bool(cost_center)
        if not is_labeled:
            cost_center = "UNALLOCATED_SHARED_DEBT"
            unlabeled_spend += r["cost_usd"]

        if cost_center not in attribution_by_cost_center:
            attribution_by_cost_center[cost_center] = 0.0
        attribution_by_cost_center[cost_center] += r["cost_usd"]

        detailed_rows.append({
            "resource_id": r["resource_id"],
            "project_id": r["project_id"],
            "service": r["service"],
            "cost_center": cost_center,
            "env": env,
            "service_tag": service_name,
            "cost_usd": r["cost_usd"],
            "labeled": is_labeled
        })

    labeled_spend = total_spend - unlabeled_spend
    compliance_rate = (labeled_spend / total_spend) * 100 if total_spend > 0 else 0

    return {
        "total_spend": total_spend,
        "labeled_spend": labeled_spend,
        "unlabeled_spend": unlabeled_spend,
        "compliance_rate": compliance_rate,
        "by_cost_center": attribution_by_cost_center,
        "rows": detailed_rows
    }
