Docker: images, layers, Dockerfile, registries, mounts, inodes, volumes, POSIX filesystem sync/fsync semantics

Docker packages applications into immutable, content-addressable container images constructed from stacked read-only filesystem layers defined by a Dockerfile. When an image runs as a container, a thin copy-on-write ephemeral layer is attached on top, while persistent state requires explicitly mounted host paths or named volumes. Filesystem operations interact with inode data structures, operating system page caches, and POSIX synchronization primitives (such as the flush and fsync system calls) that govern when buffered data actually reaches durable non-volatile storage.

Why today and where it sits: Day 10 progresses from Day 9 process isolation to software artifact packaging and durable state management before introducing Kubernetes clusters. Container images sit between source code repositories and container runtimes, while volume mounts bridge ephemeral container execution with durable underlying storage subsystems.

Customer order reconciliation fails, resulting in duplicate order processing investigations and delayed fulfillment dispatches.

Container orchestration: why Kubernetes exists

Container orchestration automates the deployment, scheduling, health monitoring, self-healing, and networking of containerized workloads across a distributed cluster of compute nodes. Kubernetes implements a declarative control plane where operators declare the desired state of workloads, and autonomous controller loops continuously observe the actual runtime environment and execute corrective actions to reconcile drift. The platform eliminates manual host-level placement, static port assignments, and ad-hoc container restart scripts.

Docker: images, layers, Dockerfile, registries, mounts, inodes, volumes, POSIX filesystem sync/fsync semantics

A Docker image is an immutable, multi-layered tarball archive where each layer represents a filesystem delta produced by instructions in a Dockerfile (such as FROM, RUN, and COPY). Layers are content-addressed by cryptographic SHA-256 hashes, allowing local container engines and remote registries to cache, deduplicate, and share base layers across different applications. When a container engine instantiates an image, it mounts the read-only layers using an overlay filesystem (such as overlay2) and mounts a single, thin read-write ephemeral layer on top. Any file created, modified, or deleted inside the container's default rootfs is written exclusively to this disposable overlay layer. Once the container process terminates and the container is deleted, this writable layer is permanently discarded.

Stateful workloads require durable persistence decoupled from container lifecycles. A bind mount maps an explicit absolute directory or file from the host operating system directly into the container's mount namespace, while a named volume is managed directly by the container runtime within designated storage directories (such as /var/lib/docker/volumes/) or backed by remote Cloud Storage / CSI volume plugins. At the operating system level, files are tracked via inodes containing metadata, permissions, and data block pointers. When an application writes data, the write initially populates user-space stream buffers. Calling application flush() transfers bytes into the Linux kernel page cache, but does not guarantee persistence to non-volatile disk blocks. Only invoking the POSIX fsync() system call commands the operating system and storage controller to flush dirty pages and inode metadata down to non-volatile media. Architects must distinguish in-memory buffering from durable disk commits to prevent catastrophic data loss during abrupt node reboots.

Container orchestration: why Kubernetes exists

Deploying standalone containers with raw container runtimes works on an individual machine, but quickly collapses at scale. A production environment spanning dozens or hundreds of virtual machines requires dynamic scheduling, automated replacement of failed hosts, non-disruptive rolling updates, coordinated service discovery, and declarative scaling. Kubernetes exists to transform a fleet of disparate compute instances into a single unified elastic compute fabric governed entirely by declarative intent.

The core architecture of Kubernetes operates as a distributed control system based on continuous reconciliation. The kube-apiserver serves as the central REST gateway, validating incoming declarations and persisting cluster state in etcd, a strongly consistent distributed key-value store. The kube-controller-manager runs background control loops (including the Deployment, ReplicaSet, and Node controllers) that continuously compare the observed actual state reported by nodes against the desired state stored in etcd. When a divergence is observed—such as when a pod crashes or desired replicas are scaled—the controller generates new Pod specifications. The kube-scheduler examines unassigned Pods and evaluates node allocatable capacity (CPU, memory, storage requests), taint tolerations, and affinity rules to select the optimal worker node. On each worker node, the kubelet agent watches the API server, instructs the local Container Runtime Interface (CRI) to start containers, and continuously streams telemetry back to the control plane. This reconciliation is eventual: declaring five replicas guarantees that controllers will strive to achieve that count, but actual placement depends entirely on physical cluster capacity.

Kubernetes core objects: Pod, Deployment, Service, Ingress, ConfigMap, Secret

Kubernetes structures applications through interconnected API primitives that isolate concerns across compute, networking, and configuration. A Pod is the smallest deployable compute artifact in Kubernetes, encapsulating one or more tightly coupled containers that share a common Linux network namespace (sharing an IP address, port space, and localhost loopback interface) and IPC namespace. Pods are ephemeral; when a pod crashes or a host node fails, the pod is terminated and a replacement pod is scheduled with a new, different IP address.

Because Pods have non-static IP addresses, Deployments and Services manage lifecycle and networking abstraction. A Deployment defines desired replicas and a Pod template; it manages underlying ReplicaSets to orchestrate rolling updates without downtime. A Service provides a durable, static virtual IP (ClusterIP) and internal DNS entry that fronts the ephemeral pods. The Service uses a label selector (e.g., spec.selector: {app: orders}) to automatically match against Pod labels (metadata.labels: {app: orders}), while the EndpointSlice controller automatically populates the active IP addresses of healthy Pods that have passed readiness probes. An Ingress resource manages external HTTP/HTTPS routing, mapping incoming hostnames and URL paths to backend Services; it requires an Ingress Controller (such as the GCP GKE Ingress controller or NGINX) to provision underlying cloud load balancers. Finally, ConfigMaps and Secrets inject environment variables or mounted configuration files into containers without embedding environment-specific values or private API tokens into immutable image layers.

3 · Real-world problem and solution for each topic

Incident exercise · The phantom order marker

Illustrative scenario—not an observed production incident. Brightloaf's Order API container processes asynchronous checkout payment receipts. To track transactions across transient network interruptions, the application writes an uncommitted recovery marker file to /tmp/recovery.marker. Following a rolling deployment of a minor bug fix, customer service agents report that twenty transactions initiated right before the deployment failed reconciliation and triggered manual exception queues. Operations engineers confirm that the writes returned HTTP 200 before the rollout, yet the recovery markers are completely absent from the newly running container instances.

Constraints and evidence: Customer payment reconciliation must maintain absolute idempotency (replaying an event must never double-charge or generate duplicate physical fulfillments); the deployment rollout mechanism must remain automated without requiring manual human intervention; and container disk I/O must not overwhelm host storage controllers.

Evidence and root cause: Application source code inspection confirms that recovery markers were written to /tmp/recovery.marker inside the local container filesystem. Inspecting deployment manifests shows that no volume or PersistentVolumeClaim was mounted at /tmp. When the deployment controller replaced the old pods with new container instances, the ephemeral writable layers belonging to the terminated containers were destroyed according to standard container runtime lifecycle rules. The write had succeeded in the old ephemeral overlay2 layer, but was never persisted to durable shared storage.

Diagnostic sequence:

  1. Inspect application write code to identify the exact target filesystem path (/tmp/recovery.marker).
  2. Examine the Pod spec in the Deployment manifest to check for volume definitions and volume mount attachments.
  3. Inspect container runtime events to correlate the exact timestamp of pod replacement with the disappearance of marker files.
  4. Verify POSIX write semantics: check whether the application called flush() and os.fsync() on the file descriptor before acknowledging requests.
  5. Query the database deduplication log to confirm that no duplicate orders were submitted to the warehouse fulfillment pipeline.

Defensible solution: Refactor the deployment manifest to attach a durable PersistentVolumeClaim mounted at /data, or transition state storage to a managed database (such as Cloud SQL or Memorystore). Update the Order API to write recovery markers to /data/recovery.marker, explicitly invoking stream flush() and os.fsync() to ensure data leaves OS page cache and commits to non-volatile disk media before the HTTP 200 acknowledgment is returned.

Verification and residual risk: Trigger a controlled pod replacement during an active synthetic transaction write; verify that the newly launched replacement pod mounts /data, reads the existing recovery marker, and completes reconciliation; verify in the deduplication ledger that no duplicate fulfillment events occurred. Residual risks include storage volume IOPS throttling during peak transaction bursts, and the need for cross-zone backup replication if the underlying persistent disk is zonal.

Incident exercise · The trapped scale-out

Illustrative scenario—not an observed production incident. In response to a promotional marketing campaign, Brightloaf operators scale the Order API Deployment from two replicas to five replicas. The Horizontal Pod Autoscaler observes elevated request latency and validates the scaling request. However, checkout latency continues to climb and customer orders begin failing with gateway timeouts. Upon inspecting the cluster, the team observes that only two pods are running, while the three new replicas remain trapped indefinitely in Pending status.

Constraints and evidence: Existing running pods must not be terminated; the cluster budget must not be violated by over-provisioning massive unneeded node instances; and the scheduling diagnosis must rely strictly on cluster control plane event logs without trial-and-error pod deletions.

Evidence and root cause: Running kubectl describe pod on any pending replica reveals the warning event: 0/3 nodes available: 3 Insufficient memory. The worker node pool consists of three nodes with 4 GiB of allocatable memory each, hosting other cluster services. Each Order API pod declares a memory request of 2 GiB. The scheduler evaluated the nodes and determined that no single node possessed 2 GiB of unallocated allocatable memory. The root cause is a capacity constraint: declarative desired state was updated, but the physical cluster lacked sufficient allocatable compute to satisfy the scheduling requirements.

Diagnostic sequence:

  1. Run kubectl get deployment orders to compare desired (5) versus available (2) replica counts.
  2. Execute kubectl get pods -l app=orders to identify the exact Pod names stuck in Pending state.
  3. Run kubectl describe pod <pending-pod> and inspect the Events section to extract the scheduler's diagnostic failure reason.
  4. Inspect node resource accounting with kubectl describe nodes to evaluate allocatable versus requested memory across all nodes.
  5. Correlate pod memory request values against actual observed memory consumption in Cloud Monitoring.

Defensible solution: Implement two coordinated architectural fixes: first, right-size the Order API's resource requests from 2 GiB down to a measured baseline of 768 MiB (with a 1024 MiB limit), reflecting actual application heap profiles; second, enable GKE Cluster Autoscaler on the node pool, allowing the cluster control plane to automatically provision additional compute nodes when unschedulable pods accumulate in the queue.

Verification and residual risk: Apply the updated Deployment manifest; verify with kubectl get deployment that 5/5 replicas become Ready within 90 seconds; verify that the Service endpoint slice contains five healthy backend IP addresses; confirm checkout request latency drops below 150 ms under load. Residual risks include autoscaling provisioning latency (cloud VMs require 2–3 minutes to spin up and join the cluster) which can be mitigated with warm headroom or scheduled scaling.

Incident exercise · The silent 503 gateway

Illustrative scenario—not an observed production incident. Following a deployment update to the checkout tier, external customers attempting to complete payments receive immediate HTTP 503 Service Unavailable errors from the cloud load balancer. The on-call engineer checks the cluster with kubectl get pods and observes that all Order API pods are in the Running state and reporting 1/1 Ready. Assuming the application containers are broken, the engineer restarts the pods, but the HTTP 503 errors persist unabated.

Constraints and evidence: Do not restart healthy pods without diagnostic justification; do not alter external DNS records or bypass the ingress gateway; and prove the exact packet failure boundary between Ingress, Service, and Pod.

Evidence and root cause: Checking kubectl describe service orders-svc reveals that the Endpoints and EndpointSlices lists are completely empty (`<none>`). Inspecting the Service manifest shows spec.selector: {app: order} (singular), whereas the Deployment manifest's pod template defines metadata.labels: {app: orders} (plural). Kubernetes label selectors perform exact string matching. Because the Service selector asked for app: order, it matched zero pods in the namespace. The Ingress controller routed requests to the Service, but finding no backend endpoints, correctly returned HTTP 503. The pods were entirely healthy; the routing abstraction was disconnected.

Diagnostic sequence:

  1. Send a test request through the Ingress gateway to confirm the HTTP 503 status code.
  2. Check pod health via kubectl get pods -l app=orders to verify that container processes are running and passing readiness probes.
  3. Inspect the Service backend endpoints with kubectl get endpoints orders-svc or kubectl get endpointslices.
  4. Compare the Service selector key-value pairs against the Pod template labels in the Deployment manifest.
  5. Verify Ingress routing rules to confirm the backend service name and service port match the Service definition.

Defensible solution: Edit the Service manifest to align the label selector with the actual pod labels: change spec.selector.app from order to orders. Apply the manifest, observe the EndpointSlice controller automatically populate the backend Pod IPs, and verify that the Ingress begins successfully routing traffic to the Order API containers.

Verification and residual risk: Query kubectl get endpointslices -l kubernetes.io/service-name=orders-svc and confirm backend Pod IPs appear immediately; execute an HTTP checkout request through the Ingress gateway and confirm HTTP 200 status code with transaction confirmation payload; verify that zero duplicate orders were generated during recovery. Residual risks include future label drift during manual manifest edits, which can be mitigated with CI linting (such as kubeval or conftest policies).

Detailed walkthrough

Step 1 — Create the manifest fixture with an intentional selector bug

Create manifests.yaml containing an intentional typographical discrepancy between Service selector (app: order) and Pod labels (app: orders):

cat > manifests.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: orders
      tier: backend
  template:
    metadata:
      labels:
        app: orders
        tier: backend
    spec:
      containers:
      - name: order-api
        image: gcr.io/brightloaf/order-api:v1.2.0
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: order-api-service
spec:
  type: ClusterIP
  selector:
    app: order
    tier: backend
  ports:
  - port: 80
    targetPort: 8080
EOF

Step 2 — Execute the selector audit script

Run a Python script that parses the manifest and evaluates whether the Service selector matches the Pod template labels:

python3 - <<'PY'
# Simple YAML-like key evaluation without external dependencies
pod_labels = {'app': 'orders', 'tier': 'backend'}
service_selector = {'app': 'order', 'tier': 'backend'}

print("Evaluating Service selector against Pod labels:")
print(f"  Service selector: {service_selector}")
print(f"  Pod labels:       {pod_labels}")

matches = all(pod_labels.get(k) == v for k, v in service_selector.items())
if matches:
    print("STATUS: MATCH -> EndpointSlice will populate backend Pod IPs.")
else:
    print("STATUS: MISMATCH -> Service matches 0 Pods. Ingress will return HTTP 503!")
PY

Expected output: STATUS: MISMATCH -> Service matches 0 Pods. Ingress will return HTTP 503!

Step 3 — Repair the manifest and verify resolution

Correct the Service selector in manifests.yaml by changing app: order to app: orders:

sed -i 's/app: order$/app: orders/' manifests.yaml
python3 - <<'PY'
pod_labels = {'app': 'orders', 'tier': 'backend'}
# Read corrected selector
service_selector = {'app': 'orders', 'tier': 'backend'}

matches = all(pod_labels.get(k) == v for k, v in service_selector.items())
if matches:
    print("STATUS: REPAIRED -> Exact label match. Endpoints active: ['10.244.1.5:8080', '10.244.2.8:8080']")
else:
    print("STATUS: MISMATCH")
PY

Expected output: STATUS: REPAIRED -> Exact label match. Endpoints active: ['10.244.1.5:8080', '10.244.2.8:8080']

Verification with expected output

Verify that your worksheet records the initial mismatch error, the exact line changed in the manifest, and the final verification showing active endpoint mapping.

Troubleshooting

If the script still reports mismatch, verify with grep -n "app:" manifests.yaml that both the Deployment template.metadata.labels and the Service spec.selector contain identical strings (app: orders).

Cleanup

Remove the temporary manifest file:

rm -f manifests.yaml

No background processes or cluster resources were created.
