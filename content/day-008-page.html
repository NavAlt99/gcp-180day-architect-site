CPU scheduling and waiting, context switching, virtual memory, page faults, RAM/page…

Operating system resource telemetry reveals the fundamental hardware bottlenecks governing compute workloads: CPU scheduling queues, voluntary and involuntary context switches, virtual memory translation, page cache dynamics, and kernel Out-Of-Memory (OOM) invocations. Pressure Stall Information (PSI) introduces kernel-level accounting that quantifies exact microsecond starvation across CPU, memory, and storage subsystems independently of naive utilization metrics.

Why today: Cloud architects must distinguish whether workload latency stems from CPU quota starvation, active memory reclaim, or storage I/O stalls before committing to expensive and ineffective machine resizing.

Where it sits: Builds directly on Day 7 process inspection and forms the kernel telemetry baseline used to predict Day 9 container cgroup constraints.

Problem preview: A production batch worker exhibits sudden latency spikes and intermittent crashes, prompting operators to double the host VM instance memory based on low free RAM graphs. The service restarts persist because the application exceeded a strict container cgroup memory quota rather than host-wide physical memory capacity.

CPU scheduling algorithms, run queues, and CFS context switching

  • What it is in general: The Linux kernel allocates processor cores among runnable threads using the Completely Fair Scheduler (CFS, evolved into EEVDF in newer kernels). CFS models an "ideal multi-tasking CPU" on hardware by assigning each thread a virtual runtime (vruntime) metric representing the scaled processor execution time it has consumed. The classic CFS model orders runnable entities by virtual runtime; EEVDF additionally uses eligibility and virtual deadlines. The active policy depends on the running kernel. When the kernel interrupts a running thread to dispatch another, it executes a Context Switch: flushing CPU hardware registers, swapping kernel stack pointers, updating CPU program counters, and changing address-space state as required; TLB invalidation is architecture- and address-space-dependent, not mandatory for every switch. Context switches divide into Voluntary Switches (where a thread blocks waiting for I/O, locks, or timers) and Involuntary Switches (where a thread exhausts its allocated scheduling time slice or is preempted by a higher-priority task).
  • Relevance to a cloud architect: Saturated host CPUs manifest as high run queue depths (runnable demand exceeding available CPU capacity; load average also includes uninterruptible tasks) and elevated involuntary context switching rates. High context switching rates degrade performance because competing working sets can displace cache lines; a context switch does not inherently flush every hardware cache. Architects must separate compute saturation (tasks actively executing instruction pipelines) from scheduling starvation (tasks queued and waiting for access to physical cores).
  • Relevance to GCP: Compute Engine shared-core machine types (such as e2-micro, e2-small, and e2-medium) rely on CPU hypervisor time-sharing and burst allowances. E2 shared-core VMs have documented sustained CPU shares and limited bursting. Compare observed CPU demand, quota and scheduling signals with those documented allowances; do not infer a specific KVM mechanism or universal severe stall from one counter. In contrast, non-shared-core machine families provide documented vCPU resources, but dedicated tenancy and NUMA placement are separate properties that must not be assumed. Primary documentation: sched(7) Linux CPU scheduling overview description (accessed 2026-10-04).
  • Further study: sched(7) completely fair scheduling and priority policies (accessed 2026-10-04); vmstat(8) system activity and context switch reporting (accessed 2026-10-04). cgroup v2 memory interfaces (accessed 2026-10-16); EEVDF Scheduler (accessed 2026-10-16); E2 shared-core machine types (accessed 2026-10-16).
  • Process scheduling foundations and execution state machine: CPU Scheduling is the core operating system subsystem (governed by the short-term dispatcher) that continuously evaluates the ready queue to decide which runnable process is dispatched onto an available physical processor core. The kernel coordinates execution across three fundamental lifecycle states:
  • Running State: The process currently occupies a CPU core, actively executing instructions in user space (Ring 3) or kernel space (Ring 0).
  • Ready State: The process is fully prepared to execute and resides queued in the scheduler runqueue awaiting core dispatch.
  • Waiting State (Blocked): The process cannot make forward progress because it is awaiting high-latency Input/Output (I/O) from a disk or network socket, or sleeping on a synchronization lock or timer.
  • Context switching mechanics and PCB preservation: Rapid time-sharing is achieved through a Context Switch. To switch between active threads, the operating system saves the execution context—including CPU general-purpose registers, floating-point units, stack pointer, program counter, and Process Control Block (PCB) metadata—of the running process and restores the previously preserved register state and PCB of the incoming process. While context switches create the illusion of smooth parallel execution (multitasking), excessive switching consumes non-trivial kernel CPU cycles and can incur cache-working-set interference rather than inherently flushing all L1/L2 caches.
  • Scheduling metrics and quantitative FCFS versus SJF analysis: When selecting processes from the ready queue, scheduling algorithms evaluate two core performance metrics: Waiting Time (the total duration a process spends queued in the ready state awaiting processor allocation) and Turnaround Time (the total elapsed wall-clock duration from initial process submission to final completion, equal to Waiting Time + CPU Burst Time only in the no-I/O, zero-overhead example below).

Consider a classic First-Come, First-Served (FCFS) scheduling scenario with three processes arriving simultaneously at time t = 0:

  • Process 1 (P1): Requires 24 ms of CPU burst time.
  • Process 2 (P2): Requires 3 ms of CPU burst time.
  • Process 3 (P3): Requires 3 ms of CPU burst time.

Under FCFS execution order (P1 → P2 → P3), the Gantt chart execution timeline runs P1 from 0 to 24 ms, P2 from 24 to 27 ms, and P3 from 27 to 30 ms.

  • Waiting Time: P1 = 0 ms, P2 = 24 ms, P3 = 27 ms. Average Waiting Time = (0 + 24 + 27) / 3 = 17 ms.
  • Turnaround Time: P1 = 0 + 24 = 24 ms, P2 = 24 + 3 = 27 ms, P3 = 27 + 3 = 30 ms. Average Turnaround Time = (24 + 27 + 30) / 3 = 27 ms.

In contrast, if the operating system applies Shortest Job First (SJF) scheduling, the shortest tasks execute first (P2 → P3 → P1): P2 runs from 0 to 3 ms, P3 runs from 3 to 6 ms, and P1 runs from 6 to 30 ms. The waiting times become P2 = 0 ms, P3 = 3 ms, and P1 = 6 ms, plunging the Average Waiting Time to (0 + 3 + 6) / 3 = 3 ms! This simplified simultaneous-arrival example illustrates head-of-line waiting; it does not demonstrate that Linux or a cloud hypervisor uses SJF or establish a production latency result. Treat algorithm comparison as optional background, not a tuning instruction.

CPU time states and load average

  • What it is in general: Top-style us/sy/ni/id/wa/hi/si/st distinguish ordinary user, kernel, niced user, idle, I/O-wait accounting, hardware interrupts, softirq work and steal time. Tool labels differ; avoid double-counting guest time. Load average counts runnable and uninterruptible tasks, not utilization percent.
  • Relevance to a cloud architect: Compare demand with effective CPU capacity, including affinity and quota. High load with idle time is not proof of compute saturation. iowait is idle-time accounting with outstanding I/O, not a per-process timer or a unique disk diagnosis.
  • Relevance to GCP: On Compute Engine, compare guest observations with documented machine-series CPU allowances. Steal time does not identify a particular hypervisor mechanism; zero steal does not rule out every scheduling delay.
  • Concrete example: For an owned PID, sample mpstat -P ALL 1 3, pidstat -u -w -p "$PID" 1 3 and iostat -y -xz 1 3. Compare the same interval: CPU imbalance, process CPU/switches and device latency answer different questions.
  • Evidence limit: Tool availability and sample scope must be established before a conclusion.
  • Further study: mpstat OPTIONS (accessed 2026-10-16); pidstat OPTIONS (accessed 2026-10-16); iostat REPORTS (accessed 2026-10-16)

Process states and scheduling controls

  • What it is in general: R means running or runnable; S interruptible sleep, D uninterruptible sleep, Z a zombie process and T a stopped process. A zombie retains exit bookkeeping until reaped; it is not a runnable CPU-consuming worker.
  • Relevance to a cloud architect: Nice changes ordinary fair-scheduling preference, not a reserved CPU share. SCHED_FIFO is real-time policy that can starve other tasks; it is described without changing policy. Affinity limits eligible CPUs without reserving them.
  • Relevance to GCP: Inside a VM/container, interpret taskset output with guest topology, cpusets and quotas. High interrupt or softirq time suggests kernel work to investigate, not an automatic CPU limit change.
  • Concrete example: Read ps -o pid,ppid,stat,ni,comm -p "$PID" and taskset -pc "$PID" for an owned PID. For Z, inspect the parent/reaper; for persistent R, compare CPU-time growth with capacity.
  • Evidence limit: One snapshot misses short transitions. No real-time scheduling, affinity or interrupt setting is changed, and observed state alone does not establish latency causality.
  • Further study: ps PROCESS STATE CODES (accessed 2026-10-16); sched DESCRIPTION (accessed 2026-10-16); taskset DESCRIPTION (accessed 2026-10-16)

cgroup v2 CPU controller

  • What it is in general: cpu.max sets bandwidth quota/period; cpu.weight controls relative allocation under contention within the hierarchy. cpu.stat includes cumulative throttling fields such as nr_throttled: inspect interval deltas, not just lifetime totals.
  • Relevance to a cloud architect: A quota 50000 100000 represents half a CPU of average bandwidth, not a fixed half-core or latency guarantee. Weight does not reserve idle capacity or override ancestor limits.
  • Relevance to GCP: Kubernetes CPU requests inform scheduling and relative allocation; CPU limits can enforce bandwidth. QoS also depends on memory and request/limit configuration. Inspect effective cgroup settings rather than assuming a label describes active limits.
  • Concrete example: Compare two timestamped reads of cpu.max, cpu.weight and cpu.stat for the same supplied cgroup. Growing nr_throttled supports a quota-throttling hypothesis during that interval; correlate demand and request latency.
  • Evidence limit: Counters alone do not identify a slow request or every host scheduling delay. Read supplied/existing values only; no controller writes are proposed.
  • Further study: cgroup v2 CPU Interface Files (accessed 2026-10-16); Kubernetes resource-limit enforcement (accessed 2026-10-16)

Virtual memory architecture, MMU page tables, and page fault dynamics

  • What it is in general: Linux user-space processes do not interact directly with physical RAM. Instead, each process operates inside an isolated virtual address space governed by the CPU's Memory Management Unit (MMU). The kernel organizes virtual memory into fixed-size units known as Memory Pages (architecture- and configuration-dependent base page sizes and supported huge-page sizes, for example 4 KiB, 2 MiB or 1 GiB on common x86 configurations). Virtual addresses map to physical memory frames via hierarchical page tables. When a thread accesses a virtual page that has not yet been mapped to a physical frame, the MMU triggers a synchronous CPU exception called a Page Fault. Page faults divide into two critical operational classes:
    1. Minor Page Faults: The requested memory page is already resident in physical RAM (for example, shared library text segments or freshly allocated anonymous memory claimed via malloc) and the kernel satisfies the fault without backing-storage reads; allocation, zero-fill or copy-on-write work can still be required.
    2. Major Page Faults: The requested page is absent from physical RAM and must be read synchronously from backing storage (such as disk swap space or an executable binary on a persistent filesystem), causing the requesting thread to block until storage I/O completes.
  • Relevance to a cloud architect: A spike in minor page faults indicates high process allocation churn or fork-exec activity, typically consuming modest CPU overhead. In contrast, an elevated rate of major page faults can reflect normal cold file access or memory pressure and must be correlated with the workload: the working set of the workload exceeds available physical RAM, forcing the kernel to fetch swapped or unmapped memory from disk, inducing catastrophic latency tail events.
  • Relevance to GCP: Compute Engine Persistent Disks (standard PD, balanced PD, SSD PD) have bounded IOPS and read throughput ratings governed by disk type, provisioned size and applicable VM and performance limits. A workload that incurs continuous major page faults on a Compute Engine instance with standard HDD storage quickly exhausts disk IOPS quotas, potentially increasing affected workload latency as faulting threads wait in uninterruptible sleep (D state) awaiting page reads. Primary documentation: Linux kernel memory concepts — virtual memory and page cache (accessed 2026-10-04).
  • Further study: Linux kernel memory concepts — address spaces and page allocation (accessed 2026-10-04); proc_meminfo(5) kernel memory counters description (accessed 2026-10-04).
  • Virtual memory architecture, pages, and physical frames: Virtual Memory decouples software addressing from physical hardware, granting each application the illusion of an expansive, contiguous memory space while transparently leveraging secondary storage (such as SSD swap partitions or swap files) as an extension to physical RAM. Physical memory (RAM) is partitioned into fixed-size hardware blocks designated as Frames. A process's logical address space is segmented into identically sized contiguous blocks designated as Pages (typically 4 KB in x86/ARM architectures, or 2 MB / 1 GB HugePages). The hardware Memory Management Unit (MMU) consults hierarchical Page Tables to translate logical virtual addresses into physical RAM frame addresses.
  • Four-stage page fault handling lifecycle and thrashing dynamics: When an executing thread references an address on a virtual page that is not currently mapped to an active physical RAM frame, the CPU hardware generates an interrupt trap called a Page Fault. The kernel handles this through a four-stage storage-backed major-fault example; minor faults and protection violations take different paths:
  1. Hardware Trap: The hardware MMU halts execution and triggers an interrupt trap, transferring CPU control from Ring 3 user space to the Ring 0 kernel page fault handler (vector 14 on x86; exception encoding and privilege levels differ on other architectures).
  2. Context Switch to Waiting Queue: The operating system saves the executing process's register state and PCB, transitioning the thread from the running state to the waiting (blocked) queue so processor cycles can be allocated to other runnable tasks.
  3. Secondary Storage Read: The kernel I/O subsystem reads the missing page data from secondary storage (swap space or executable filesystem blocks) and loads it into an available physical RAM frame.
  4. Page Table Update and Resume: The kernel updates the page table entry with the physical frame address, sets the page "present" bit, and moves the process back into the ready queue to resume execution at the instruction that caused the fault.

Sustained reclaim and repeated storage-backed faults can lead to Thrashing—an operational pathology where the operating system spends substantial time reclaiming memory or waiting for page I/O, reducing useful throughput without requiring a literal zero-throughput state.

  • Page replacement algorithms and Belady's Anomaly: When a page fault occurs and all physical RAM frames are occupied, the operating system may need to reclaim a page; a clean file-backed page can be discarded and reread without a swap write to free up a frame for the incoming page:
  • First-In, First-Out (FIFO): Evicts the page that has resided in physical memory the longest. While straightforward to manage using a simple queue, FIFO suffers from Belady's Anomaly, an architectural anomaly where allocating more physical RAM frames can paradoxically increase the total number of page faults for certain memory reference patterns.
  • Least Recently Used (LRU): Evicts the page that has not been referenced for the longest period of time. By analyzing past access patterns to approximate future locality, LRU exploits locality but is not universally superior for every reference sequence but incurs higher computational tracking overhead (requiring hardware timestamping or page stack manipulations).
  • Optimal Page Replacement (OPT / MIN): Evicts the page that will not be referenced for the longest period of time in the future. Because an operating system kernel cannot predict future execution branches, OPT is purely theoretical and serves as the benchmark standard against which practical heuristics (such as LRU or clock algorithms) are evaluated.

Process memory accounting

  • What it is in general: VSS describes virtual address mappings, RSS resident pages, and PSS the proportional share of resident shared pages. Summed process RSS can count shared pages repeatedly. smaps provides mapping accounting; pmap summarizes mappings, not a cgroup memory bill.
  • Relevance to a cloud architect: mmap can reserve/map address space without making every page resident. Copy-on-write permits physical sharing until writes require private copies; private residency can grow without a comparable new virtual mapping.
  • Relevance to GCP: Compare process accounting with host MemAvailable and cgroup memory.current separately on Compute Engine. These scopes include different charges and cannot be substituted for one another.
  • Concrete example: For an owned readable process, inspect /proc/$PID/smaps Rss/Pss/Shared/Private fields and pmap -x "$PID". Supplied RSS=100 MiB and PSS=60 MiB supports sharing, not 40 MiB of immediately reclaimable memory.
  • Evidence limit: Permissions, concurrent mapping changes and sharing attribution affect snapshots. PSS is not a precise marginal allocation cost or a substitute for cgroup-limit evidence.
  • Further study: proc_pid_smaps DESCRIPTION (accessed 2026-10-16)

Memory hierarchy: active/inactive RAM, page cache, dirty writeback, and swap space

  • What it is in general: The Linux memory subsystem classifies physical RAM into active/inactive anonymous allocations and file-backed memory. Unused physical memory is automatically utilized by the kernel as Page Cache, storing recently read and written filesystem blocks in RAM to avoid expensive persistent disk transactions. When applications write to files, modifications remain buffered in RAM as Dirty Pages until writeback workers; kswapd primarily performs background memory reclaim and can interact with writeback asynchronously flush them to persistent storage. Consequently, examining raw free memory (MemFree in /proc/meminfo) frequently reveals low single-digit gigabytes on healthy production nodes. The crucial metric is MemAvailable, which estimates the total memory available for starting new applications without swapping, taking into account reclaimable page cache and dentries. Swap Space provides disk-backed overflow storage for anonymous memory pages, allowing the kernel to evict cold process heap allocations to preserve page cache for hot I/O paths.
  • Relevance to a cloud architect: Naive monitoring rules that trigger alerts when "Free RAM" drops below 10% produce widespread false positives because the Linux kernel deliberately fills idle RAM with reclaimable page cache. Conversely, systems without swap have fewer anonymous-page eviction options, but reclaim, allocation failures, pressure and OOM behavior depend on workload and limits rather than a universal crash pattern. Architects rely on MemAvailable and kernel reclaim rates rather than raw MemFree to evaluate true host memory headroom.
  • Relevance to GCP: Inspect the actual VM image and swapon --show output rather than assuming one swap policy for all public images; swap can affect latency and its suitability is workload-specific. In high-throughput streaming and database workloads (e.g. Kafka or PostgreSQL on Compute Engine), architects first observe writeback and storage latency; optional advanced tuning can review kernel dirty page ratios (vm.dirty_ratio and vm.dirty_background_ratio) to ensure dirty memory writeback occurs smoothly without choking Persistent Disk write queues. Primary documentation: proc_meminfo(5) memory distribution and page cache metrics (accessed 2026-10-04).
  • Further study: proc_meminfo(5) MemAvailable and page cache fields (accessed 2026-10-04); vmstat(8) memory and swap transfer reporting (accessed 2026-10-04).

Memory tuning knobs (optional)

  • What it is in general: vm.swappiness influences reclaim preference; zero does not universally disable swapping. vm.overcommit_memory selects allocation-accounting policy, not an RSS limit. min_free_kbytes affects allocator reserves. Slab cache includes reclaimable and unreclaimable allocations.
  • Relevance to a cloud architect: Transparent huge pages can reduce translation overhead but incur allocation/compaction tradeoffs. NUMA policy affects memory locality; CPU and memory placement differ. None is a universal fix for a low free-memory graph.
  • Relevance to GCP: VM size, guest configuration and workload determine relevance. Observe existing policy and pressure first; no universal Google Cloud sysctl values are recommended.
  • Concrete example: Read existing /proc/sys/vm/swappiness, /proc/sys/vm/overcommit_memory, /proc/sys/vm/min_free_kbytes and Slab/SReclaimable/SUnreclaim fields. Record them alongside PSI without sysctl writes or dropping caches.
  • Evidence limit: Optional interpretation only. Configuration changes require workload evidence and rollback planning; readings do not certify improvement.

Out-Of-Memory (OOM) killer mechanics, badness heuristics, and cgroup memory boundaries

  • What it is in general: When physical memory and swap exhaustion prevents the kernel from fulfilling an urgent memory allocation request, the kernel invokes the Out-Of-Memory (OOM) Killer to prevent a complete system deadlock. The kernel scans all running processes and computes an internal "badness" heuristic score (exposed via /proc/[pid]/oom_score), considering eligible tasks and accounted memory with oom_score_adj; low privilege or runtime is not a general current scoring rule. System administrators can influence this choice by writing to /proc/[pid]/oom_score_adj (-1000 immunizes a critical process like sshd or systemd, while +1000 targets sacrificial workers). Crucially, in modern containerized operating systems, memory enforcement operates at both the host VM level and the Control Group (cgroup v1/v2) boundary. In cgroups v2, the kernel enforces limits such as memory.high (throttling and direct reclaim pressure without invoking the OOM killer solely for memory.high) and memory.max (hard ceiling triggering a cgroup-level OOM killer). When a process inside a cgroup exceeds its memory.max, reclaim failure can invoke OOM selection within the affected cgroup even if the underlying host VM has hundreds of gigabytes of unallocated physical RAM.
  • Relevance to a cloud architect: Containerized applications running on Kubernetes (GKE) or container runtimes frequently crash with exit status 137 (a shell convention consistent with SIGKILL, which is signal 9; OOM requires corroboration). Blindly upsizing host VMs does not resolve container OOM terminations if the pod specification or container manifest specifies an inadequate container memory limit. Architects must inspect cgroup memory.events and kernel dmesg logs to distinguish container-level quota violations from host-wide physical exhaustion.
  • Relevance to GCP: Google Kubernetes Engine (GKE) nodes utilize cgroup v2 on modern Container-Optimized OS (COS) images. When a pod exceeds its configured container memory limit, the Linux kernel terminates the offending process and GKE records an OOMKilled status event. If the host VM itself runs low on memory, kubelet can perform node-pressure eviction, but rapid allocation can reach kernel OOM first; eviction ordering considers requests, priority and usage rather than an unconditional QoS-only ordering. Primary documentation: proc(5) process oom_score and oom_score_adj description (accessed 2026-10-04).
  • Further study: proc(5) oom_score heuristics and adjustments (accessed 2026-10-04); Linux kernel memory concepts — OOM handling (accessed 2026-10-04).

Userspace OOM handling (optional)

  • What it is in general: systemd-oomd uses configured cgroup/PSI policy to select eligible groups on supported systems. earlyoom uses a separate memory/swap-availability policy. A userspace kill can also yield SIGKILL; exit 137 does not identify its actor.
  • Relevance to a cloud architect: Distinguish memory.high direct-reclaim pressure, memory.max failure and daemon policy. zram is compressed RAM-backed block storage that can provide swap; it consumes RAM/CPU rather than creating unlimited physical capacity.
  • Relevance to GCP: Do not assume a VM image enables either daemon or zram. Establish service state, configuration, scope and timestamps before attributing a restart to an image default or kernel limit.
  • Concrete example: On a system already using it, read systemctl status systemd-oomd --no-pager and journalctl -u systemd-oomd --since "10 minutes ago" --no-pager. Compare with kernel OOM and cgroup records; no service is enabled or reconfigured.
  • Evidence limit: Features depend on installed versions/configuration. Missing records do not rule out another killer. No OOM, swap exhaustion or zram setup is induced.
  • Further study: systemd-oomd DESCRIPTION (accessed 2026-10-16); earlyoom What does it do (accessed 2026-10-16); zram documentation (accessed 2026-10-16)

Pressure Stall Information (PSI): quantifying CPU, memory, and I/O starvation

  • What it is in general: Traditional utilization metrics (such as CPU percentage or free memory) describe current resource usage but fail to indicate whether workloads are actually delayed or impaired by resource shortages. Pressure Stall Information (PSI) is a Linux kernel accounting facility that directly tracks the percentage of wall-clock time that tasks spend stalled while waiting for congested CPU, memory, or block I/O resources. Exposed through pseudo-files in /proc/pressure/{cpu,memory,io} and inside cgroup directories, PSI reports two distinct starvation levels:
    1. some: The percentage of time in which at least one non-idle task was stalled waiting for the contended resource (indicating micro-contention and beginning latency degradation).
    2. full: The percentage of time in which all non-idle tasks were simultaneously stalled waiting for the resource (indicating complete workload paralysis, such as during synchronous memory reclaim or storage thrashing). PSI provides rolling moving averages over 10-second, 60-second, and 300-second windows alongside cumulative total stall time in microseconds.
  • Relevance to a cloud architect: PSI allows architects to establish automated, proactive health checks and auto-scaling triggers. Rather than waiting for a fatal OOM kill or severe API timeout, monitoring agents trigger proactive traffic draining or horizontal pod autoscaling when memory:some or cpu:some pressure exceeds defined operational thresholds (such as 10% over a 60-second window).
  • Relevance to GCP: Verify metric availability in the current Ops Agent metric catalog before claiming default PSI collection; a separate collection/export path may be required. Compute Engine autoscalers and GKE custom metric horizontal pod autoscalers (HPAs) can query PSI stall rates to scale application clusters dynamically based on real hardware contention rather than inaccurate CPU utilization averages. Primary documentation: Linux kernel documentation — Pressure Stall Information interface (accessed 2026-10-04).
  • Further study: Linux PSI interface and cgroup monitoring (accessed 2026-10-04); proc(5) pressure accounting pseudo-filesystem (accessed 2026-10-04).

Stream text filtering with grep and sed: patterns, word boundaries, and limits

  • What it is in general: Text stream inspection tools process unstructured log streams line-by-line using regular expressions. The grep utility evaluates input streams against Basic Regular Expressions (BRE) or Extended Regular Expressions (ERE with -E), returning matching records based on the selected regular expression; use -F for literal fixed-string matching, character classes, or word boundaries (). Options such as -i (case-insensitivity), -v (inverting matches), -c (counting matching lines), and -C (emitting surrounding context lines) allow operators to quickly narrow down unstructured syslogs. The sed (stream editor) utility performs non-interactive text transformations, deletions, and substitutions on piped streams using programmable addressing scripts (e.g. s/regex/replacement/g). Crucially, stream text tools evaluate records as flat string sequences: they lack schema awareness, syntactic data validation, and multiline field boundary understanding.
  • Relevance to a cloud architect: Relying on naive text grepping across semi-structured or JSON application logs introduces severe false-negative and false-positive diagnostic errors: searching for the substring "error" misses structured numeric failure codes (such as HTTP 500 or gRPC status 14), while returning false positives for informational logs stating "error_count=0" or a field value containing the literal substring "error". Architects mandate structured logging schemas and establish standardized log parsing rules for observability pipelines.
  • Relevance to GCP: While Google Cloud CLI commands support local piping to grep (e.g. gcloud compute instances list | grep RUNNING), enterprise cloud operations utilize Cloud Logging log filters (written in Cloud Logging Query Language) on the backend to filter structured JSON payload fields server-side before egressing data over networks. Primary documentation: grep(1) pattern search utility description (accessed 2026-10-04).
  • Further study: grep(1) regular expression syntax and matching modes (accessed 2026-10-04); sed(1) stream editor command language (accessed 2026-10-04). jq manual (accessed 2026-10-16); VPC Flow Logs collection (accessed 2026-10-16).

Field processing with awk: columnar aggregation, record splitting, and reporting

  • What it is in general: When log streams or system command outputs follow tabular, columnar formatting (such as space-delimited Web server access logs, vmstat, or ps outputs), the awk pattern scanning and processing language provides powerful field-based extraction and statistical computation. The tool automatically splits each incoming line into positional field variables ($1, $2, ... $NF) based on a configurable field separator (-F). In addition to printing specific columns, awk supports associative arrays, arithmetic aggregations, conditional branching, and pattern action blocks (BEGIN, pattern matching, END). This allows operators to compute average latency, calculate response code percentiles, or identify top talker IP addresses from access log streams in a single one-line command without writing full Python or shell scripts.
  • Relevance to a cloud architect: Field extraction tools allow operators to extract actionable quantitative metrics from legacy flat log files during real-time incident triage without requiring external log aggregation databases to be functional. However, column-positional parsing breaks immediately if upstream log formats introduce unquoted spaces within fields or alter column ordering.
  • Relevance to GCP: Compute Engine serial console logs, Linux startup script logs (/var/log/messages), and Google Cloud Ops Agent local configuration files frequently require column-based extraction during bare-metal instance debugging. Architects standardize log formats on structured JSON to replace brittle positional awk scripts with schema-validated parsers. Primary documentation: gawk(1) pattern scanning and processing language description (accessed 2026-10-04).
  • Further study: gawk(1) field splitting, patterns, and actions (accessed 2026-10-04); grep(1) matching options and context control (accessed 2026-10-04).

Text pipeline helpers for bounded log analysis

  • What it is in general: sort orders extracted records; uniq -c counts adjacent equal lines, so sort first unless input is already grouped. cut/tr handle text delimiters/characters, not JSON grammar. head/tail bound displayed samples without validating omitted records.
  • Relevance to a cloud architect: Parse and validate the structured field first, then aggregate it. A top-N count describes a selected sample, not a production error rate without a denominator and time window.
  • Relevance to GCP: Exported Cloud Logging records require the same separation. No live export or backend query is executed in this mechanism.
  • Concrete example: For the already validated five-row fixture: jq -r ".status" orders.jsonl | LC_ALL=C sort -n | uniq -c | sort -nr | head -n 5. Expect two 200 values and one each of 404, 500 and 503; tie ordering has no causal meaning.
  • Evidence limit: The fixture is bounded. On larger streams head can close a pipe early and cause SIGPIPE under pipefail; never hide unrelated pipeline failures.
  • Further study: sort DESCRIPTION (accessed 2026-10-16); jq manual (accessed 2026-10-16)

Structured data parsing with jq: JSON filters, nested traversal, and numeric selections

  • What it is in general: Modern cloud telemetry, API payloads, and container runtime logs are formatted as JavaScript Object Notation (JSON). The jq command-line processor provides a complete, type-aware query language for slicing, filtering, mapping, and transforming structured JSON documents. Unlike text stream filters, jq parses JSON values for structured evaluation; it is not a browser DOM, validating syntax and supporting hierarchical path traversals (e.g. .user.credentials[0].id). It supports exact type comparisons, boolean filtering (e.g. select(.http.status_code >= 500)), array projections, field restructuring, and raw text output (-r). If an input stream contains corrupted or non-JSON text, jq fails explicitly with a syntax parse error rather than silently returning erroneous empty output.
  • Relevance to a cloud architect: JSON-aware parsing is mandatory for automated continuous deployment gates, incident triage scripts, and cloud telemetry evaluation. Parsing JSON with grep or sed is a severe anti-pattern that leads to false conclusions during production outages: key ordering in JSON objects is non-deterministic, whitespace is arbitrary, and reliable numeric-field comparisons require parsing the JSON field rather than matching unrelated digits.
  • Relevance to GCP: The Google Cloud CLI (gcloud) returns structured JSON for supported resource commands via the global flag --format=json. Cloud architects pair gcloud JSON output with jq to extract project IDs, VPC subnet allocations, firewall rule configurations, and instance status fields reliably across automated deployment pipelines. Primary documentation: grep(1) pattern search utility description (accessed 2026-10-04).

Network endpoint diagnostics: curl and dig for DNS and application layer probing

  • What it is in general: Probing service availability across network boundaries requires tools that isolate name resolution from application protocol transactions. The dig (domain information groper) utility performs flexible DNS lookups directly against designated nameservers (@nameserver), querying specific record types (A, AAAA, CNAME, SRV), tracing delegation hierarchies from root servers (+trace), and displaying authoritative DNS flags, return codes (NOERROR, NXDOMAIN, SERVFAIL), and Time-To-Live (TTL) expiration counters. The curl command-line tool transfers data across network protocols (HTTP, HTTPS, FTP), allowing operators to inspect raw HTTP status headers (-I), view TLS handshakes and cipher negotiation (-v), override DNS resolution locally without changing /etc/hosts (--resolve), and extract detailed network timing breakdowns using write-out format variables (-w "%{time_namelookup} %{time_connect} %{time_appconnect} %{time_total} ").
  • Relevance to a cloud architect: Testing network connectivity requires isolating the failure boundary: an API call failure can originate from DNS misconfiguration, firewall blockages, TLS certificate expiration, or backend service application crashes. Probing with dig isolates whether the domain name maps to the correct IP address; probing with curl isolates whether TCP transport, TLS negotiation, and HTTP routing succeed independently.
  • Relevance to GCP: Cloud architects utilize dig to verify Google Cloud DNS private zones, Split-Horizon DNS configurations, and DNS forwarding rules. They utilize curl to probe Google Cloud Internal Application Load Balancers, Cloud Run endpoints, and Cloud Storage signed URLs, verifying IAM authentication headers and inspecting latency metrics along the Google Cloud network path. Primary documentation: curl(1) command-line URL transfer tool description (accessed 2026-10-04).

Path and TLS probing with the named tools

Kernel socket and packet analysis: ss socket states and tcpdump packet captures

  • What it is in general: When higher-level HTTP or application diagnostic tools report connectivity failures, operators drop to the transport and network layers to observe kernel socket tables and interface packet streams. The ss (socket statistics) utility dumps live kernel socket tables directly from the Linux inet_diag netlink subsystem, replacing the legacy netstat command. It displays active listening ports (-l), established TCP connections (-t), UDP sockets (-u), associated process PIDs (-p), and socket buffer queue depths (Recv-Q and Send-Q). Interpret Recv-Q by socket state: on established TCP sockets it represents unread queued data, while listening sockets report queued connections. One snapshot alone does not prove application failure. The tcpdump utility captures raw network packets directly from the network interface using the libpcap library and kernel Berkeley Packet Filters (BPF). Filtering packets by protocol, IP address, port, and TCP flags (e.g. SYN, ACK, RST), tcpdump can show packets visible at the selected capture point; absent packets can also reflect the wrong interface/filter, capture loss or timing and do not locate an upstream drop by themselves.
  • Relevance to a cloud architect: Transport-level tools provide ground truth during perimeter connectivity failures: a capture can establish visibility at the selected interface; attribution to an upstream firewall requires corroborating policy and logging evidence. Socket queue inspection with ss separates application deadlocks (zero socket reads) from external network routing failures.
  • Relevance to GCP: Compute Engine virtual interfaces (virtio-net or gVNIC) process traffic encapsulated within Andromeda virtual networking. Running tcpdump inside a Compute Engine VM captures traffic only after it has traversed VPC firewall evaluation. To observe packets blocked by VPC firewalls before reaching the instance, use applicable Firewall Rules Logging and connectivity/policy evidence. VPC Flow Logs ingress sampling occurs after ingress firewall evaluation, so denied ingress is absent there; Packet Mirroring also has documented visibility limits. Primary documentation: ss(8) socket statistics utility description (accessed 2026-10-04).
  • Further study: ss(8) TCP connection states and socket memory (accessed 2026-10-04); tcpdump(8) network traffic capture and filter syntax (accessed 2026-10-04).

TCP state diagnosis

  • What it is in general: TIME_WAIT is normal after active close, not automatically a leak. CLOSE_WAIT means peer close was received while local closure remains outstanding. SYN-SENT means an active opener is awaiting establishment.
  • Relevance to a cloud architect: Persistent growing CLOSE_WAIT supports an application-closure hypothesis, not proof from one snapshot. Retransmission can accompany loss, congestion, reordering or other conditions; compare the same connection over time.
  • Relevance to GCP: Guest ss output describes the local network namespace, not Google Cloud VPC policy, backend health or a specific upstream loss point.
  • Concrete example: Compare ss -tan state close-wait, ss -tan state time-wait and ss -ti at two recorded times. Keep connection identity and sample interval with any retransmission observation.
  • Evidence limit: Permissions, namespaces and tool/kernel versions affect visibility. A high TIME_WAIT count does not authorize TCP tuning or process termination.
  • Further study: ss OPTIONS (accessed 2026-10-16)

Firewall and connection-tracking questions: evidence limits

  • What it is in general: A socket, packet capture and firewall decision are distinct observations. Seeing a SYN establishes visibility at that capture point; missing packets do not uniquely locate a drop.
  • Relevance to a cloud architect: Check interface, namespace, filter and time window first. Guest firewall processing differs from Google Cloud VPC enforcement; ss does not enumerate either policy.
  • Relevance to GCP: VPC Flow Logs ingress sampling follows ingress firewall evaluation, so denied ingress is absent. Applicable Firewall Rules Logging and reviewed policy can corroborate denial; mirroring is not a universal view of dropped packets.
  • Concrete example: If curl times out and ss shows SYN-SENT, establishment is incomplete. A permitted tcpdump capture can add evidence of retries; correlate policy/logging before naming a responsible rule.
  • Evidence limit: An empty capture or connection-table snapshot does not prove a specific firewall dropped the request. The investigation may remain inconclusive.
