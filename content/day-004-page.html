1 · Topics of the day

HTTP/HTTPS, status codes and HTTP versions

HTTP defines requests and responses; HTTPS protects HTTP with an authenticated encrypted connection. HTTP/1.1, HTTP/2 and HTTP/3 share core request and status semantics but use different framing and transport arrangements.

Why today and where it sits: Day 4 extends Day 3's established-connection evidence to TLS and application response. A Brightloaf checkout request can connect successfully yet receive an HTTP error from the Order API or its proxy.

Problem preview: Port 443 accepts a connection while GET /orders returns HTTP 503. Shoppers cannot complete checkout even though the transport probe is green.

Technical discussion · Real-world problem · Exercise

TLS 1.3 handshake and certificate identity

TLS 1.3 negotiates protected communication. For certificate-authenticated server connections, the client checks a certificate path under its trust policy and compares the intended service name with the certificate identity.

Why today and where it sits: TLS sits between an established transport path and trusted HTTPS application exchange. The edge certificate presented for Brightloaf's Order API must match the hostname customers requested.

Problem preview: The edge serves a trusted, current certificate for admin.example.test when a shopper requests orders.example.test. Browsers reject the service identity before a trusted HTTP response can be used.

Technical discussion · Real-world problem · Exercise

MTU and MSS clamping

MTU limits the IP packet size a path can carry; path MTU is constrained by its smallest relevant hop. TCP MSS describes the largest TCP payload a peer advertises for reception, and a tunnel can reduce the safe inner packet size.

Why today and where it sits: Day 4's failure worksheet must distinguish a size-dependent packet-path fault from TLS or HTTP behavior. The relevant boundary lies between the Order API's transport endpoint and the tunnel carrying its packets.

Problem preview: Small Order API requests succeed after a VPN change, but larger responses stall. Customers see intermittent checkout failures as payload size grows.

SNAT and DNAT at a network boundary

NAT rewrites addresses and sometimes ports. Outbound SNAT can replace a private source with a routable egress address; DNAT changes a destination for a mapped inbound target, and state ties a reply to the original flow.

Why today and where it sits: The Day 4 route worksheet needs the pre-translation and post-translation tuple to explain a private host's return traffic. For Brightloaf's Order API, the NAT boundary sits on an outbound dependency path, not inside the application.

Problem preview: A private Order API host sends an update request through an egress gateway without the expected SNAT mapping. The remote endpoint has no usable return path to that private source, delaying maintenance.

Static routes, dynamic routes and BGP

Routing selects a next hop for a destination prefix. Static routes are configured explicitly, while dynamic protocols exchange reachability; BGP exchanges prefixes and path information between peers.

Why today and where it sits: A tunnel, NAT device and healthy application still require separate forward and return route decisions. Brightloaf's cloud-to-fulfillment path provides a concrete place to label selected prefixes.

Problem preview: The VPN and BGP session report up, but the fulfillment site lacks a route back to the Order API source prefix. Requests leave the cloud while replies do not return, holding orders at the integration boundary.

2 · Technical discussion of each topic

HTTP/HTTPS, status codes, HTTP/1.1 vs HTTP/2 vs HTTP/3

An HTTP request names a method, target and fields; the response contains a status and possibly a representation. A 2xx status means the request succeeded, 3xx requests further action, 4xx indicates a client-side request problem, and 5xx indicates the server failed to fulfill an apparently valid request. These are application outcomes. No status code exists if the client cannot establish the needed transport or TLS session. HTTPS also requires certificate and service-identity checks before an HTTP response should be trusted.

HTTP/1.1 uses a textual message syntax and normally processes requests over a TCP connection. HTTP/2 uses binary framing and multiplexes streams over a connection, commonly over TLS/TCP. HTTP/3 carries HTTP semantics over QUIC, which runs over UDP and integrates TLS 1.3. A version change does not turn an HTTP 503 into a routing error. In cloud designs, version support affects proxies, load balancers, observability and firewall rules, but method and status semantics still guide application diagnosis.

TLS 1.3 handshake and certificate validation chains

During a TLS 1.3 handshake, peers negotiate cryptographic parameters and establish keys before sending protected application data. The server presents certificate evidence and proves possession of the corresponding private key. The client must validate the chain according to its trust policy and compare the service name it intended to contact with the certificate's permitted identifiers. A certificate can be within its validity period and signed by a trusted authority yet still be wrong for the requested host. Conversely, a name match alone does not repair an untrusted or expired chain.

In cloud architectures, TLS may terminate at a load balancer and a separate connection may run to the backend. An architect must know which hop is authenticated and encrypted. A green backend health check cannot substitute for the public hostname check. Error evidence should name whether the failure is chain trust, validity, name matching, protocol negotiation or later HTTP behavior; these require different fixes.

MTU and MSS clamping

Encapsulation by a tunnel adds headers, reducing the space available for the inner packet. A path that carries small handshake packets can fail when larger application data packets exceed a tunnel or link MTU. Path MTU discovery lets a sender adapt to a lower path limit when it receives the relevant too-big signal. If that signal is blocked, a connection can appear to establish and then stall during data transfer. MSS clamping at a tunnel boundary can reduce the advertised TCP segment size, but it is a targeted workaround that must reflect the real encapsulation overhead and does not fix every UDP or routing problem.

For a simple IPv4/TCP example without IP or TCP options, a 1500-byte IP MTU leaves 1460 bytes for TCP payload after 20-byte IPv4 and 20-byte TCP headers. If a tunnel leaves an inner IP MTU of 1400, the corresponding simple payload bound is 1360. Actual headers and policies can differ; observe the path rather than treating these arithmetic examples as a universal configuration value.

NAT (SNAT/DNAT) for private outbound

An outbound flow from a private host cannot simply present its RFC 1918 source address to the public Internet and expect a globally routable reply. A NAT device can replace the source with a public address and often a translated source port, storing a mapping so return traffic reaches the original private endpoint. The reverse packet must match that state. DNAT instead changes the destination, such as mapping a published endpoint to an internal server. These changes affect the address tuple seen on each side; packet captures and firewall logs must be interpreted at the correct boundary.

NAT is not itself an access policy. A translation entry may exist while a firewall blocks the flow, or an allowed flow may fail because no route to the NAT device exists. In cloud designs, architects need to know whether a NAT product handles outbound connections only and whether it provides any inbound mapping. For troubleshooting, record pre-translation and post-translation source/destination and the return path.

Routing basics

A router generally selects the most specific matching destination prefix before applying route preferences among candidates for the same prefix. The forward path and return path are separate decisions, and both must exist for a request/reply exchange. A default route is used only when no more-specific route matches. A static route is straightforward for a stable small design but must be maintained when topology changes. Dynamic protocols distribute changing reachability, with policy and convergence behavior that require careful review.

BGP advertises network prefixes and attributes such as AS path between peers. It is not a substitute for local firewall policy or an application health check. Cloud VPN or dedicated connectivity may use BGP to exchange routes, but a BGP session being up does not prove the desired prefix is advertised, selected or reachable in both directions. For incidents, record the exact destination, selected prefix, next hop, advertisement and reverse route.

3 · Real-world problem and solution for each topic

Case 1 · A healthy listener with HTTP 503

Illustrative symptom and impact: Brightloaf's port-443 health probe is green, but customer requests to GET /orders receive HTTP/2 503 for ten minutes. Checkout stalls and operations may misread a working TCP connection as proof the Order API is healthy.

Constraints, evidence and root cause: The supplied scenario has an accepted TLS session and an HTTP response. The proxy has no healthy Order API backend for the customer path, while the port probe only tests its listener. Confirm the negotiated version, request host and path, proxy logs and backend health before assigning that root cause; an HTTP 503 can arise elsewhere.

Response and verification: Freeze unrelated changes, correlate a synthetic request ID through edge and backend logs, and restore a healthy backend or roll back the faulty release. Verify the customer path returns its expected status and an order record is created once. Keep Fulfillment's durable replay check in place so retries cannot produce duplicate shipment. Add an application-level path probe alongside the transport probe. A healthy probe on one path remains limited evidence for other methods and routes.

Case 2 · Certificate chain passes but name fails

Illustrative symptom and impact: Customers request orders.example.test and receive a hostname-mismatch warning even though the edge certificate is current and chains to a trusted CA. Checkout is blocked before a trusted HTTP response is available.

Constraints, evidence and root cause: The supplied certificate contains admin.example.test as its DNS identity. Date and path validation can succeed while the requested service name fails to match. The edge may select a certificate by listener or server name, so record the requested hostname, selected TLS endpoint and actual leaf identity before modifying anything.

Response and verification: Select or issue a certificate covering the intended Order API hostname, attach it to the correct edge listener, and repeat chain, validity and name checks with normal client verification enabled. Then test /orders separately for HTTP status and order behavior. Do not disable hostname checks or treat the green backend probe as certificate evidence. If TLS terminates at the edge, separately review how the backend hop is protected.

Case 3 · Large responses stall across a tunnel

Illustrative symptom and impact: After a VPN change, Brightloaf's small Order API response succeeds but a larger response stalls after TCP establishes. Checkout requests with larger payloads time out, while ordinary listener probes stay green.

Constraints, evidence and root cause: In the supplied IPv4/TCP arithmetic fixture, a 1380-byte TCP payload fits a simple 1500-byte physical IP MTU but exceeds a 1400-byte inner-tunnel IP MTU after 20-byte IP and TCP headers. The failure hypothesis is a path-MTU black hole when needed too-big feedback is blocked or ignored. Header options, encapsulation and real packet sizes can differ, so captures and path feedback must confirm the diagnosis.

Response and verification: Compare working and failing sizes in both directions, inspect tunnel overhead and ICMP too-big feedback, and correct the path-MTU behavior. If a targeted TCP MSS clamp is needed, calculate it from the verified inner path rather than copying the fixture number. Retest small and large payloads, TLS and the actual HTTP path. A successful handshake alone cannot close this incident, and UDP traffic needs separate evaluation.

Case 4 · Missing outbound source translation

Illustrative symptom and impact: Brightloaf's private Order API host reaches an internal subnet but cannot download an update through its egress gateway. The remote service does not return useful traffic to the private source, delaying a planned maintenance window.

Constraints, evidence and root cause: In the supplied tuple, 10.2.0.5:53000 should become 203.0.113.8:41001 before reaching 198.51.100.20:443. A route may exist while the NAT mapping is missing, the flow bypasses the NAT device, or return traffic misses the same stateful boundary. The addresses are documentation fixtures; a firewall change alone cannot make an RFC 1918 source globally routable.

Response and verification: Record routes and tuples on both sides of the egress boundary, check mapping creation, and confirm reply association with the private socket. Correct the route or SNAT rule supported by those observations, then test a permitted destination and the return path. Keep least-privilege egress policy and avoid adding DNAT as an outbound fix. A successful translated connection does not prove that the application update is valid.

Case 5 · BGP up, return prefix absent

Illustrative symptom and impact: Brightloaf's cloud Order API sends a request to fulfillment address 10.50.4.8 through a VPN, but no reply returns. The tunnel and BGP peering both report up, yet order handoff is delayed.

Constraints, evidence and root cause: The supplied forward table selects 10.50.4.0/24, but the remote side has no route to the actual source prefix 10.20.0.0/16. Session state proves a routing peer relationship, not that this prefix was advertised, accepted, selected or permitted by policy. Inspect the selected routes for the exact source and destination before blaming the application.

Response and verification: Correct the missing return advertisement or route policy, then confirm the selected forward and reverse next hops and relevant firewall decisions. Test a synthetic order handoff and record a single fulfillment decision. Keep the event key stable for any retry; the Fulfillment store must suppress duplicate business action. Recheck route selection after convergence, because an apparently healthy session can later lose or replace a needed prefix.

Exercise 5 · Check forward and return prefixes

Goal: Choose a next hop and diagnose a missing return prefix. Mode: local Python 3 plus a supplied route table.

Preflight: Bring the Day 3 exit diagram and open a Day 4 worksheet. Confirm Python 3 in a local terminal; this lab does not use gcloud, a tunnel or a cloud project.

Step 1 — Select the most specific route

Open a Linux terminal and run:

python3 - <<'PY'
from ipaddress import ip_address, ip_network
destination = ip_address('10.50.4.8')
routes = [('0.0.0.0/0', 'internet'), ('10.50.0.0/16', 'vpn'),
          ('10.50.4.0/24', 'private-link')]
matches = [(ip_network(prefix).prefixlen, prefix, hop)

print('selected:', prefix, 'via', hop)
PY
