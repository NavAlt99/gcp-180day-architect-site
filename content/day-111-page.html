Day 111 addresses the comprehensive systems architecture, network boundary isolation, and third-party supply chain governance required for regulated enterprise workloads on Google Cloud. Architects evaluate Cardholder Data Environment (CDE) scoping under PCI-DSS v4.0 (minimizing audit scope through iframe payment gateways and Cloud DLP tokenization), healthcare cloud architecture under HIPAA/HITECH (Business Associate Agreement execution, electronic Protected Health Information handling, and clinical audit sinks), and third-party vendor risk management (SaaS integration boundaries, reciprocal SOC 2 audits, and zero-trust Private Service Connect endpoints).

1. PCI-DSS design

Designing architectures for PCI-DSS v4.0 requires minimizing the Cardholder Data Environment (CDE) scope to the smallest possible footprint. Scope reduction is achieved by utilizing hosted fields, iFrames, and third-party tokenization gateways so that raw Primary Account Numbers (PANs) never touch merchant servers, qualifying the workload for SAQ A. For components that must process payments, architects enforce strict network segmentation via VPC Service Controls, zero transitive routing to corporate networks, Cloud NGFW Layer 7 inspection, and end-to-end CMEK encryption.

Problem preview: A developer connects a test analytics pipeline directly into the payment processing database; the entire analytics cluster is immediately brought into PCI audit scope until strict VPC-SC perimeter isolation is restored.

2. HIPAA design

Designing healthcare workloads under HIPAA (Health Insurance Portability and Accountability Act) and HITECH mandates requires strict adherence to the Security and Privacy Rules. In Google Cloud, architects must execute a formal Business Associate Agreement (BAA) covering all projects handling electronic Protected Health Information (ePHI). Key architectural requirements include restricting deployments exclusively to HIPAA-included services, enforcing CMEK encryption at rest, mandating TLS 1.3 in transit, enabling full Data Access audit logging, and implementing emergency break-glass procedures with immediate forensic auditing.

3. Vendor and third-party risk basics

Modern enterprise cloud architectures rely heavily on third-party SaaS integrations, external APIs, and managed service providers, creating substantial supply chain risk. Vendor and third-party risk management (TPRM) requires establishing formal governance boundaries: conducting vendor security assessments (VSRAs), reviewing reciprocal SOC 2 Type II and ISO 27001 reports, enforcing data processing addenda (DPAs) with strict audit clauses, and implementing zero-trust network integration patterns such as Private Service Connect (PSC) to prevent vendor lateral movement into corporate VPCs.

Problem preview: A third-party marketing SaaS is breached by ransomware; Private Service Connect isolation ensures the attacker cannot pivot across the integration endpoint into the enterprise production network.

1. PCI-DSS design: technical mechanics

1. PCI Scope Reduction Architectures

  • SAQ A Architecture: Customer browser enters credit card data directly into a third-party tokenization iframe (e.g. Stripe Elements, Adyen). The merchant's GCP backend receives only an opaque surrogate token. Merchant servers never store, process, or transmit cardholder data, reducing audit scope by 95%.
  • SAQ A-EP Architecture: Merchant serves the payment page but uses client-side JavaScript to send data directly to payment processor. Requires rigorous web application firewall (Cloud Armor) inspection and script integrity monitoring.

2. CDE Network Segmentation & Hardening (PCI v4.0 Req 1 & 3)

  • Isolated VPC: CDE workloads must reside in a dedicated Google Cloud project with a standalone VPC. Default networks and external IP addresses are strictly prohibited.
  • Egress Filtering: All outbound traffic must pass through a Cloud Secure Web Proxy with FQDN whitelisting restricted exclusively to authorized payment processor endpoints.
  • CMEK Encryption: Persistent disks and Cloud Storage buckets storing encrypted cardholder tokens must use dedicated Cloud KMS keys backed by Cloud HSM (FIPS 140-2 Level 3).

Architectural evaluation questions

  • How does utilizing hosted payment iframes reduce an enterprise's PCI-DSS compliance scope from SAQ D to SAQ A?
  • What network controls must be implemented to prove that a non-CDE subnet cannot communicate with the CDE under PCI v4.0?
  • Why does PCI-DSS v4.0 mandate multi-factor authentication (MFA) for all administrative access to the CDE?

2. HIPAA design: technical mechanics

1. HIPAA Administrative & Technical Safeguards

  • Business Associate Agreement (BAA): A legally binding contract between Google Cloud and the customer. Google agrees to implement required administrative, physical, and technical safeguards. Customers must execute the BAA in Google Cloud Console before uploading any ePHI.
  • HIPAA-Included Services: Only services certified under Google Cloud's HIPAA assessment may store or process ePHI. Standard services (Compute Engine, GCS, BigQuery, Cloud SQL, Cloud Run) are included; experimental preview features are excluded.

2. Clinical ePHI Access Controls & Audit Trails

  • 45 CFR § 164.312(b) Audit Controls: Organizations must record and examine activity in systems that contain or use ePHI. Data Access audit logs (DATA_READ, DATA_WRITE) must be enabled and exported to locked storage.
  • Minimum Necessary Standard: Workforce members must only access the minimum ePHI necessary to accomplish their clinical or business function, enforced via Dataplex column-level policy tags and row-level access filters.

Architectural evaluation questions

  • What is the legal consequence of storing Protected Health Information in a Google Cloud project before executing a BAA?
  • How does an architect verify whether a newly announced Google Cloud service is approved for HIPAA workloads?
  • How does the HIPAA "minimum necessary" standard translate into technical IAM and BigQuery access controls?

Further study: Google Cloud HIPAA Compliance: Implementation guide, BAA terms, and included services.

3. Vendor and third-party risk basics: technical mechanics

1. Zero-Trust Vendor Network Integration

  • The Anti-Pattern (VPC Peering): Peering directly with a third-party vendor's VPC creates bidirectional IP routing, extending the enterprise blast radius into the vendor's infrastructure.
  • The Secure Pattern (Private Service Connect): Consumes vendor-managed services privately using a local forwarder IP (e.g. 10.128.50.4). PSC provides unidirectional Layer 4 TCP connection proxying with zero IP routing between VPCs. The vendor cannot initiate connections into the consumer network.

2. Vendor Security Risk Assessment (VSRA) Framework

  • Assessment Criteria: Data classification shared with vendor, SOC 2 Type II report scope and unqualified opinion, encryption at rest and in transit standards, incident notification SLAs (e.g. 24–72 hours), and employee background screening.
  • Continuous Monitoring: Annual reassessment of vendor posture and monitoring of vendor breach disclosures.

Architectural evaluation questions

  • Why is Private Service Connect (PSC) vastly superior to VPC Peering for integrating third-party vendor SaaS solutions?
  • What are the mandatory legal clauses that must be included in a third-party vendor Data Processing Addendum (DPA)?
  • How does an enterprise architect evaluate an external vendor's SOC 2 Type II report to identify material control deficiencies?

Further study: Google Cloud Private Service Connect: Secure third-party service integration and publishing.

1. PCI-DSS design · field case

Enterprise scenario: External QSA assessment identifies unauthorized VPC peering between the corporate data warehouse and the Cardholder Data Environment, expanding audit scope to 300 non-compliant VMs.

Constraints: Financial transactions must process uninterrupted; corporate analytics must receive sanitized transaction metrics without entering CDE scope.

Evidence:

Network routing table audit log snippet:

Peering Connection: cde-to-analytics-peering
Network A: cde-production-vpc (10.200.0.0/16)
Network B: corporate-analytics-vpc (10.100.0.0/16)
State: ACTIVE (Transitive IP routing enabled)
QSA Audit Violation: Requirement 1.2.3 - Direct connection between CDE and non-CDE corporate networks.
Impact: Entire 300-VM corporate analytics cluster pulled into full PCI-DSS Level 1 assessment scope.

Analysis: Data engineers peered the VPCs to allow direct JDBC database queries, violating strict PCI network isolation rules.

Root cause: VPC peering violated network segmentation mandates, allowing bidirectional IP routability between CDE and corporate networks.

Diagnostic sequence:

  1. Inspect VPC peering connections using <kbd>gcloud compute networks peerings list</kbd>.
  2. Trace active routes between CDE subnets and corporate analytical networks.
  3. Check for direct IP communication using VPC Flow Logs.
  4. Evaluate Private Service Connect (PSC) or Cloud Pub/Sub as compliant decoupled alternatives.

Defensible remediation: Tear down VPC peering immediately; deploy Private Service Connect with strict proxy boundaries to export only tokenized data.

Verification: Confirm zero routes exist between corporate network and CDE; verify QSA re-assessment acknowledges scope reduction.

Residual risk: Analytical teams requiring transaction metrics must ingest asynchronously via unidirectional tokenized message queues.

2. HIPAA design · field case

Enterprise scenario: Hospital internal compliance auditor flags 14,000 unencrypted patient clinical diagnostic notes stored in a public-read Google Cloud Storage bucket.

Constraints: Clinical staff require mobile access to patient updates, but HIPAA mandates zero public exposure and strict encryption at rest.

Evidence:

Cloud Storage bucket permission audit result:

{
  "bucket_name": "hospital-clinical-notes-prod",
  "iam_policy": {
    "bindings": [
      {
        "role": "roles/storage.objectViewer",
        "members": ["allUsers"]
      }
    ]
  },
  "hipaa_violation": "45 CFR § 164.312(a)(1) - Failure to control access to ePHI",
  "potential_penalty": "Tier 4 Willful Neglect ($50,000 per violation up to annual maximum)"
}

Analysis: A misconfigured Terraform module granted public read access to a clinical notes bucket, exposing patient records.

Root cause: Public read IAM binding was applied to an ePHI bucket; absence of Organization Policy public access prevention allowed public exposure.

Diagnostic sequence:

  1. Immediately remediate public access using <kbd>gcloud storage buckets set-iam-policy</kbd>.
  2. Enable Organization Policy constraint `constraints/storage.publicAccessPrevention` on the folder.
  3. Query Cloud Audit logs to determine if unauthorized IP addresses accessed patient notes.
  4. Initiate mandatory 60-day HIPAA breach assessment and notification protocol.

Defensible remediation: Enforce `publicAccessPrevention = "enforced"` on the bucket and parent organization; enforce CMEK encryption with Cloud HSM.

Verification: Attempt unauthenticated curl to bucket object (fails with HTTP 401/403); verify access is restricted exclusively to authorized clinical IAM identities.

Residual risk: All downloaded access logs must be retained for 6 years in an immutable WORM bucket to satisfy HIPAA documentation retention rules.

3. Vendor and third-party risk basics · field case

Enterprise scenario: Security Operations Center detects suspicious outbound API calls streaming customer demographic profiles to an unvetted third-party analytics provider.

Constraints: Enterprise TPRM policy mandates that all third-party data transfers must be authorized by the Vendor Risk Committee and covered by a formal DPA.

Evidence:

Cloud NGFW egress log capturing unauthorized vendor traffic:

{
  "connection": {
    "src_ip": "10.128.0.42",
    "dest_ip": "198.51.100.89",
    "dest_port": 443,
    "protocol": 6
  },
  "fqdn": "telemetry-collector.unvetted-saas-vendor.io",
  "bytes_sent": 48210920,
  "tprm_status": "UNAPPROVED_VENDOR_TRANSFER"
}

Analysis: A marketing engineering team integrated a free analytics software development kit (SDK) into the frontend, which silently streamed user data to an external SaaS vendor without security review.

Root cause: Engineering integrated an unvetted third-party SDK, bypassing the Vendor Security Risk Assessment and legal DPA process.

Diagnostic sequence:

  1. Review Cloud Secure Web Proxy logs to identify all outbound connections to `unvetted-saas-vendor.io`.
  2. Search corporate vendor registry to confirm absence of executed DPA or SOC 2 review.
  3. Inspect application source code and dependencies for unapproved third-party SDKs.
  4. Block vendor domain immediately via Cloud Secure Web Proxy and Cloud DNS Firewall policies.

Defensible remediation: Block outbound traffic to the vendor domain, remove the SDK from application code, and submit the vendor to formal TPRM evaluation.

Verification: Verify SWP logs confirm zero traffic reaching the vendor domain; confirm application builds pass automated software bill of materials (SBOM) scanning.

Residual risk: Historical data sent to the unvetted vendor must be formally requested for deletion under applicable privacy statutes.

  2. CDE Segmentation Validator

    Author and run Python script verifying network isolation and blocking unauthorized cross-boundary routes:

    cat <<'EOF' > test_cde_segmentation.py
import ipaddress

CDE_SUBNET = ipaddress.ip_network("10.240.0.0/24")
CORPORATE_SUBNET = ipaddress.ip_network("10.100.0.0/16")

simulated_routes = [
    {"src": "10.240.0.5", "dst": "199.36.153.4", "desc": "Restricted Google API VIP", "allowed": True},
    {"src": "10.240.0.5", "dst": "10.100.4.12", "desc": "Corporate Data Warehouse", "allowed": False}, # VIOLATION
    {"src": "10.100.4.12", "dst": "10.240.0.5", "desc": "Corporate Ingress into CDE", "allowed": False}, # VIOLATION
    {"src": "35.235.240.10", "dst": "10.240.0.5", "desc": "IAP Admin Bastion Tunnel", "allowed": True}
]

print("================================================================")
print("PCI-DSS v4.0 CDE NETWORK SEGMENTATION AUDITOR")
print("================================================================")

for r in simulated_routes:
    src_ip = ipaddress.ip_address(r["src"])
    dst_ip = ipaddress.ip_address(r["dst"])

    # Evaluate segmentation rule: No route between CDE and Corporate subnets
    is_peered_violation = (
        (src_ip in CDE_SUBNET and dst_ip in CORPORATE_SUBNET) or
        (src_ip in CORPORATE_SUBNET and dst_ip in CDE_SUBNET)
    )

    status = "BLOCKED (PCI Compliant)" if is_peered_violation else "PERMITTED"
    print(f"[{status:24s}] Route: {r['src']:15s} -> {r['dst']:15s} ({r['desc']})")
    if is_peered_violation:
        assert not r["allowed"], "Segmentation test failed: unauthorized cross-boundary route allowed!"

print("================================================================")
EOF

  2. Clinical ePHI Redaction & De-Identification Engine

    Author and run Python script simulating Safe Harbor de-identification of clinical patient records:

    cat <<'EOF' > test_hipaa_redaction.py
import hashlib
import re

SALT = b"Hospital-Clinical-DeId-Salt-2026"

clinical_records = [
    {
        "patient_name": "Eleanor Vance",
        "mrn": "MRN-849201",
        "dob": "1984-06-12",
        "diagnosis": "Type 2 Diabetes Mellitus",
        "notes": "Patient prescribed Metformin 500mg daily."
    },
    {
        "patient_name": "Thomas Dudley",
        "mrn": "MRN-109284",
        "dob": "1972-11-28",
        "diagnosis": "Essential Hypertension",
        "notes": "Follow-up blood pressure check scheduled in 4 weeks."
    }
]

def deidentify_hipaa_record(record: dict) -> dict:
    # HIPAA Safe Harbor: Remove Name, MRN, exact DOB -> replace with age range and pseudonym
    pseudo_id = "PATIENT-" + hashlib.sha256(record["mrn"].encode() + SALT).hexdigest()[:12].upper()
    birth_year = record["dob"].split("-")[0]
    return {
        "patient_pseudonym": pseudo_id,
        "birth_year": birth_year,
        "diagnosis": record["diagnosis"],
        "clinical_notes": record["notes"]
    }

print("================================================================")
print("HIPAA SAFE HARBOR ePHI CLINICAL DE-IDENTIFICATION")
print("================================================================")
for raw in clinical_records:
    deid = deidentify_hipaa_record(raw)
    print(f"Original: {raw['patient_name']} (MRN: {raw['mrn']}, DOB: {raw['dob']})")
    print(f"Sanitized: {deid['patient_pseudonym']} | Year: {deid['birth_year']} | Condition: {deid['diagnosis']}")
    print("----------------------------------------------------------------")
    assert "patient_name" not in deid
    assert "mrn" not in deid
    assert raw["mrn"] not in deid["patient_pseudonym"]
print("================================================================")
EOF

  2. Vendor Security Risk Assessment (TPRM) Scoring Engine

    Author and run Python script evaluating third-party vendor risk questionnaires and SOC 2 attestations:

    cat <<'EOF' > evaluate_vendor_risk.py
vendor_profiles = [
    {
        "name": "CloudPay Global Gateway",
        "soc2_type2": True,
        "dpa_executed": True,
        "data_classification": "RESTRICTED",
        "network_pattern": "PSC_PRIVATE",
        "encryption_in_transit": "TLS_1_3"
    },
    {
        "name": "FastMetrics Free Analytics",
        "soc2_type2": False,
        "dpa_executed": False,
        "data_classification": "INTERNAL",
        "network_pattern": "PUBLIC_INTERNET",
        "encryption_in_transit": "TLS_1_2"
    }
]

def score_vendor(v: dict) -> tuple[int, list[str]]:
    score = 100
    flags = []
    if not v["soc2_type2"]:
        score -= 40
        flags.append("Missing accredited SOC 2 Type II report")
    if not v["dpa_executed"]:
        score -= 30
        flags.append("No executed Data Processing Addendum (DPA)")
    if v["network_pattern"] != "PSC_PRIVATE" and v["data_classification"] in ["CONFIDENTIAL", "RESTRICTED"]:
        score -= 20
        flags.append("Sensitive data routed over public internet instead of PSC")
    return score, flags

print("================================================================")
print("THIRD-PARTY VENDOR SECURITY RISK ASSESSMENT (TPRM)")
print("================================================================")
for v in vendor_profiles:
    score, flags = score_vendor(v)
    decision = "APPROVED (Authorized Integration)" if score >= 80 else "REJECTED (High Supply Chain Risk)"
    print(f"Vendor: {v['name']:26s} | Score: {score}/100 | Decision: {decision}")
    for f in flags:
        print(f"   -> RISK FLAG: {f}")
    print("----------------------------------------------------------------")
print("================================================================")
EOF
