VPC as a global resource: Andromeda SDN and cross-region private backbones

In Google Cloud, a Virtual Private Cloud (VPC) network is a globally scoped software-defined network (SDN) powered by Google's Andromeda virtualization stack. Unlike traditional cloud providers where virtual networks are bound to a single physical data center or geographic region, a GCP VPC spans all Google Cloud regions worldwide without requiring inter-region VPN tunnels, public internet routing, or external gateway peering. Compute instances, GKE nodes, and serverless runtimes deployed in disparate continents communicate securely across Google's private, encrypted global fiber-optic backbone using private RFC 1918 IP addresses. This global scope enables centralized network policy administration, global Application Load Balancing backends across multiple continents, and simplified disaster recovery topologies.

This capability belongs on Day 49 because Days 36–48 covered compute engines, Kubernetes clusters, and serverless runtimes; we now construct the underlying enterprise networking foundation that connects all distributed compute assets. In the complete Google Cloud architecture, the global VPC serves as the foundational data plane interconnecting all project services and hybrid enterprise links.

When an architect assumes inter-region communication requires public internet egress or complex gateway peering, they inadvertently provision unnecessary VPN tunnels that add 25ms of packet encapsulation latency and expose internal traffic to public routing risks. Production cross-region database replication stalls under peak shopping traffic, generating replica lag alerts and inconsistent customer order histories.

Subnets as regional resources: zonal spanning, MTU configurations and IP boundaries

While the VPC itself is global, subnets inside a VPC are strictly regional resources. A subnet is defined within a single Google Cloud region (e.g. us-central1) and automatically spans all availability zones within that region (e.g. us-central1-a, us-central1-b, us-central1-c, us-central1-f). VMs in distinct zones of the same region attach to the same subnet, sharing a unified IP address space and broadcast domain without requiring inter-zone routing gateways. Subnets support configurable Maximum Transmission Unit (MTU) sizes—including standard 1460 bytes (Google default), 1500 bytes (standard Ethernet), and 8896 bytes (jumbo frames for high-bandwidth analytics)—and enforce strict address allocation boundaries where Google reserves four host addresses in every primary subnet range (network, gateway, second-to-last, and broadcast).

This topic belongs on Day 49 because designing multi-zone, highly available compute architectures requires understanding that zone failures do not isolate subnets. In production networks, subnets establish the regional failure containment and IP grouping boundary for security firewalls and compute provisioning.

When a cloud team sizes a regional subnet too small under the misconception that each availability zone requires a distinct subnet, the subnet exhausts available IP addresses during a single-zone maintenance event. Automated zonal MIG scaling fails immediately with resource exhaustion errors, dropping checkout traffic during a regional hardware migration.

Auto mode vs custom mode VPCs and controlled enterprise IP planning

Google Cloud offers two network provisioning modes: Auto mode VPCs and Custom mode VPCs. Auto mode automatically creates a pre-determined /20 subnet in every Google Cloud region using a fixed global allocation within the 10.128.0.0/9 CIDR block, expanding automatically as Google introduces new global regions. While convenient for rapid prototyping and sandboxes, Auto mode is strictly prohibited in enterprise production environments because its rigid 10.128.0.0/9 range inevitably collides with on-premises corporate data center networks, partner connections, and other peered VPCs. Custom mode VPCs provide zero default subnets, granting architects total declarative control over IP address blocks, region selections, and subnet expansion, ensuring full compatibility with corporate IP allocation registries (IPAM).

This topic belongs on Day 49 because enterprise cloud adoption fails if initial cloud networks collide with existing corporate address spaces, requiring painful, multi-month re-IP migrations. In enterprise landing zones, custom mode VPCs are an absolute mandatory baseline enforced by organizational policies.

When a development team spins up a default Auto mode VPC and attempts to peer with the on-premises corporate inventory database, the peering handshake fails instantly due to overlapping 10.128.0.0/9 CIDR blocks. Engineers are forced to tear down production databases and re-provision infrastructure from scratch, delaying the planned retail platform migration by six weeks.

Subnet IP ranges, secondary ranges for GKE pods and services, and non-disruptive range expansion

Google Cloud subnets support one primary IP address range (used for Compute Engine VM network interfaces, internal load balancers, and GKE worker nodes) and multiple alias secondary IP ranges (dedicated to GKE Pod CIDRs and ClusterIP Service CIDRs). Unlike legacy networking where changing subnet boundaries requires tearing down infrastructure, Google Cloud allows expanding the primary CIDR range of an existing subnet non-disruptively, provided the new range has a shorter prefix length (e.g. expanding /24 to /22) and does not overlap with existing subnets. However, secondary ranges cannot be modified or expanded once created; expanding GKE Pod capacity requires provisioning new secondary ranges and creating multi-pod CIDR node pools.

This capability belongs on Day 49 because Day 42–45 GKE clusters rely on VPC-native IP alias routing; inadequate subnet planning leads to catastrophic IP exhaustion during cluster growth. In container platforms, secondary ranges define the ultimate scaling ceiling of containerized microservices.

When an architect allocates a narrow /20 secondary range for GKE Pods on a high-density cluster, a rolling node pool surge upgrade exhausts all available pod IP addresses mid-deployment. The GKE control plane freezes, unable to schedule new pods while draining old nodes, halting application delivery across the primary retail cluster.

Routes: system-generated, custom static, dynamic BGP routing, and route selection priority

Routing in Google Cloud is fully distributed across the Andromeda SDN, eliminating physical router bottlenecks and single points of failure. Every VPC contains system-generated default routes: a default internet gateway route (0.0.0.0/0, priority 1000) and local subnet routes (priority 0) matching each subnet's primary and secondary CIDRs. Administrators configure custom static routes (with user-defined priority 0–65535, next-hop instances, or next-hop VPNs) and dynamic routes exchanged automatically via Border Gateway Protocol (BGP) between Google Cloud Routers and on-premises routers. The Andromeda packet processing engine resolves forwarding using an exact hierarchical evaluation order: 1) Longest Prefix Match (most specific destination CIDR wins), 2) Lowest Priority Value (e.g. priority 100 beats priority 1000), and 3) Equal-Cost Multi-Path (ECMP) hashing across identical priority paths.

This topic belongs on Day 49 because hybrid cloud connectivity, security inspection firewalls, and multi-region failover depend entirely on deterministic route prioritization. In production networks, routes dictate the exact physical journey of every packet entering or leaving the cloud environment.

When a custom static route with priority 100 is left active after a maintenance drill, it silently overrides dynamic BGP failover routes advertised by the primary Cloud Router during an on-premises WAN link failure. Network traffic blackholes into an inactive gateway, cutting off all retail store point-of-sale registers from the central order processing API.

VPC as a Global Resource: Andromeda SDN Architecture and Data Plane Routing

Google Cloud VPC networks are global software-defined constructs. When a packet originates from a Compute Engine VM or GKE Pod in us-central1 destined for an internal IP in europe-west1, the packet never traverses public internet transit providers or third-party exchanges. Instead, the packet is processed by Andromeda—Google's distributed network virtualization stack:

  • Host-Level Open vSwitch / Flow Processing: Andromeda programming operates directly on the Linux host hypervisors. When a VM transmits an IP packet, Andromeda intercepts the packet at the virtual NIC (virtio-net or gVNIC), looks up the global VPC routing and firewall tables cached in host memory, and encapsulates the packet in a proprietary Google network encapsulation header.
  • Jupiter Fabric Transmission: The encapsulated packet enters Google's private global fiber network (Jupiter datacenter fabric and B4 global WAN). It travels over dedicated transatlantic/transpacific optical paths with multi-terabit bandwidth and sub-millisecond switching latency.
  • Destination Decapsulation: Upon reaching the destination host hypervisor in Europe, Andromeda verifies firewall egress/ingress state, strips the encapsulation header, and injects the raw IP packet directly into the destination VM's virtual interface.

Because the network is entirely virtualized, cross-region communication within a VPC requires zero VPN gateways, zero NAT instances, and zero peering overhead. The only distinction between intra-region and inter-region traffic is the physical speed-of-light propagation latency and standard Google Cloud inter-region data transfer egress fees ($0.01 to $0.02 per GB).

Subnets as Regional Resources: Address Reservation and Zonal Resiliency

In Google Cloud, subnets are regional constructs rather than zonal constructs. A subnet defined with primary range 10.10.0.0/24 in us-central1 automatically spans all zones in that region. When a VM is created in zone us-central1-a, it draws an IP address from that subnet (e.g. 10.10.0.4). When a second VM is created in zone us-central1-b, it draws an IP from the exact same subnet (e.g. 10.10.0.5). Both VMs communicate directly as Layer 3 neighbors without any inter-zone gateway devices.

Google Cloud Subnet Reserved IP Addresses:

Every subnet primary range reserves exactly four IP addresses for internal network infrastructure operations:

  1. Network Address (First IP, e.g. .0): Base network identifier.
  2. Default Gateway (Second IP, e.g. .1): Local subnet default gateway for outbound routing.
  3. Reserved Address (Second-to-last IP, e.g. .254 in a /24): Reserved by Google Cloud for future expansion and DHCP server bindings.
  4. Broadcast Address (Last IP, e.g. .255 in a /24): RFC standard broadcast address (though Andromeda does not flood broadcast frames).

Consequently, the usable host capacity for any subnet primary range is calculated as: $$\text{Usable Hosts} = 2^{(32 - \text{prefix})} - 4$$

Secondary Ranges & GKE IP Alias Allocation Calculations

GKE clusters running in VPC-native mode allocate IP addresses directly from the VPC subnet fabric rather than using overlay network encapsulation (e.g. Flannel or Calico IP-in-IP). This requires allocating three distinct IP address spaces per cluster:

  1. Node CIDR (Subnet Primary Range): Provides IP addresses for GKE worker VM host interfaces. Sized according to expected maximum worker node count.
  2. Pod CIDR (Subnet Secondary Range): Sized according to maximum pods. GKE allocates a contiguous /24 block (256 addresses, accommodating up to 110 pods per node) to each worker node by default. Therefore, a cluster supporting up to 256 nodes requires a /16 Pod secondary range (65,536 addresses).
  3. Service CIDR (Subnet Secondary Range): Sized according to internal Kubernetes ClusterIP Service objects. A /20 range provides 4,096 Service IPs.

Subnet Range Expansion Rules:

  • Primary subnet ranges can be expanded to a shorter prefix (e.g., 10.10.0.0/24 can expand to 10.10.0.0/22) non-disruptively without rebooting VMs.
  • Primary ranges can NEVER be shrunk, shifted, or modified to a longer prefix.
  • Secondary ranges CANNOT be modified or expanded after creation; if pod IP space is exhausted, administrators must add an additional secondary range and configure a new GKE node pool mapped to the new range.

Routes, Priority Precedence, and BGP Dynamic Routing

Every routing lookup in Google Cloud follows Andromeda's strict deterministic evaluation order:

  1. Step 1: Longest Prefix Match (LPM): The most specific destination subnet mask always wins. For example, a route destined for 10.10.1.0/24 always takes precedence over a route to 10.10.0.0/16 or 0.0.0.0/0, regardless of priority integer values.
  2. Step 2: Lowest Priority Integer (Administrative Distance): If two routes have identical destination CIDRs, Andromeda selects the route with the lowest numerical priority (0 is highest priority; 65535 is lowest priority). Default system routes have priority 0 (local subnets) and 1000 (default internet gateway).
  3. Step 3: Equal-Cost Multi-Path (ECMP): If two or more routes share the exact same destination CIDR and identical priority, Andromeda hashes traffic flows across all available next-hops using 5-tuple packet hashing (source IP, destination IP, protocol, source port, destination port).

Part 3 · Real-world problem and solution for each topic

Global VPC Cross-Region Asymmetric Routing and Hairpin Outage · field case

Situation and impact: Brightloaf established a primary production environment in us-central1 and a disaster recovery site in us-east1 within the same VPC. During an automated database snapshot replication test, cross-region bandwidth plummeted to less than 2 Mbps, and replication alerts fired continuously. Simultaneously, inter-region network egress billing showed an unexpected $4,800 surge over a 48-hour testing period.

Constraints: Must preserve low-latency database replication between regions; must route all traffic across private Google networks without public internet hops; and must stay within monthly data transfer budgets.

Diagnosis and solution: Network topology inspection via Cloud Logging and Network Intelligence Center revealed that an engineer had created a custom static route for 10.11.0.0/22 pointing to an intermediate legacy NAT virtual appliance in us-central1 (priority 500) intended for deep packet inspection. Rather than allowing Andromeda to route directly across Google's private backbone to us-east1, packets were forced into a single-threaded virtual machine appliance that became CPU-bound and dropped 82% of packets. The solution was removing the redundant custom static route, allowing Andromeda's native priority 0 local subnet route to handle forwarding directly across regions at line rate.

Alternative and residual risk: If corporate regulatory standards strictly mandate Layer 7 deep packet inspection on all inter-region traffic, the inspection appliances must be deployed behind an internal load balancer with autoscaling and multi-NIC interfaces rather than a single static next-hop VM.

Subnet Zonal Misunderstanding and Address Fragmentation Exhaustion · field case

Situation and impact: Brightloaf's operations team prepared for high-volume Thanksgiving bakery orders by provisioning a new managed instance group in us-central1. Believing that subnets were zonal constructs like Compute Engine VMs, the engineer created four separate /28 subnets (one per zone) with only 12 usable IPs each. During a zonal maintenance drain, instances in us-central1-a were terminated and rescheduled in us-central1-b, which immediately failed with ZONE_RESOURCE_POOL_EXHAUSTED: IP space exhausted in subnet. Fifty order processing workers failed to boot, dropping 3,200 online pie orders.

Constraints: Must maintain high availability across all four zones of us-central1; must support autoscaling up to 80 instances during holiday peaks; and must avoid frequent manual IP modifications.

Diagnosis and solution: The incident root cause was a fundamental misunderstanding of Google Cloud subnet boundaries. Instead of fragmenting address space across multiple narrow zonal subnets, Google Cloud subnets are regional and naturally encompass all zones. The resolution involved consolidating the fragmented /28 blocks into a single regional /22 subnet (1,020 usable hosts) in us-central1. The single subnet dynamically allocates IP addresses to worker instances in zones a, b, c, and f seamlessly, enabling unrestricted cross-zonal autoscaling.

Alternative and residual risk: Consolidating into a single regional subnet requires managing network firewall rules via network tags or service accounts rather than subnet CIDR filters, since all zones share the same primary IP range.

Auto Mode Default CIDR Overlap with On-Premises Data Center · field case

Situation and impact: Brightloaf established a dedicated Cloud Interconnect link to connect its on-premises bakery ERP database (IP range 10.128.0.0/16) with a newly provisioned Google Cloud analytics project. The cloud network was created in default Auto mode. When network engineers attempted to establish BGP peering, the Cloud Router logged fatal BGP peering errors: PEERING_ROUTE_OVERLAP: Advertised prefixes conflict with local subnet 10.128.0.0/20 in us-central1. The entire hybrid connection was blocked, halting the ERP data migration.

Constraints: Cannot re-IP the legacy on-premises ERP database; must establish hybrid connectivity over Cloud Interconnect; and must enforce organizational policy prohibiting Auto mode VPCs.

Diagnosis and solution: Auto mode VPCs automatically provision subnets across the entire 10.128.0.0/9 CIDR block. Because the on-premises corporate network occupied 10.128.0.0/16, BGP could not exchange routes due to conflicting subnet ranges. The solution required deleting the Auto mode VPC, enforcing the organization policy constraints/compute.skipDefaultNetworkCreation, and provisioning a Custom mode VPC using an allocated, non-overlapping enterprise block: 172.16.0.0/20. BGP peering established immediately, enabling sub-millisecond database queries.

Alternative and residual risk: If an organization cannot immediately migrate off Auto mode, Private NAT or Cloud NAT with customized IP mappings can translate overlapping ranges, though it introduces NAT processing latency and eliminates end-to-end IP auditability.

GKE Pod Secondary Range Exhaustion During Surge Upgrade · field case

Situation and impact: Brightloaf's primary production GKE cluster in us-central1 initiated an automated node pool surge upgrade (configured with maxSurge=1, maxUnavailable=0). The cluster contained 60 worker nodes. Mid-upgrade, the GKE cluster entered a deadlocked state: new surge nodes registered as NotReady with Kubelet error Failed to allocate Pod CIDR: out of addresses in secondary range gke-pods. The upgrade halted, node drains timed out, and checkout pods were evicted without replacements, causing intermittent 503 errors on 15% of checkout traffic.

Constraints: Must upgrade cluster nodes to patched Kubernetes versions; cannot destroy and recreate the production cluster; and must support cluster expansion up to 100 worker nodes.

Diagnosis and solution: The cluster was originally provisioned with a /18 secondary range for Pods (16,384 addresses). With GKE's default /24 allocation per node (256 addresses per node), the secondary range can only support a maximum of 64 nodes ($16384 / 256 = 64$). When the surge upgrade provisioned additional temporary surge nodes, total nodes exceeded 64, immediately exhausting the Pod CIDR. Because secondary ranges cannot be resized, the solution required adding a new secondary range (gke-pods-expansion: 10.40.0.0/16) to the VPC subnet and provisioning a new node pool mapped to the new pod range using multi-pod CIDR allocation, allowing the old node pool to be safely drained and retired.

Alternative and residual risk: For large-scale GKE clusters, architects should reduce --max-pods-per-node (e.g. from 110 to 32), which allows GKE to allocate a more compact /26 CIDR per node, quadrupling the node capacity of any given secondary IP range.

Static Route Shadowing BGP Dynamic Cloud Router Failover · field case

Situation and impact: Brightloaf operates a hybrid retail architecture where cloud-based order APIs communicate with on-premises point-of-sale inventory databases over Cloud Interconnect with Cloud VPN backup. During an unexpected fiber cut on the physical Interconnect, the Cloud Router successfully detected BGP link failure within 3 seconds and began advertising routes over the backup Cloud VPN tunnel. However, all retail store inventory queries blackholed, cutting off live stock tracking across all 250 bakeries for 45 minutes.

Constraints: Must achieve automated failover in under 10 seconds during WAN link disruptions; cannot introduce manual routing intervention; and must adhere to strict deterministic route priorities.

Diagnosis and solution: Routing table analysis revealed that during a legacy migration, an engineer had configured a custom static route: destination=192.168.10.0/24, next-hop=interconnect-gateway, priority=100. When BGP dynamically advertised 192.168.10.0/24 over the backup Cloud VPN tunnel with base priority 200, Andromeda evaluated the two identical destination prefixes and selected the custom static route because priority 100 numerically beats priority 200. Consequently, packets continued forwarding into the dead physical Interconnect interface. The resolution was deleting the static route and configuring dynamic BGP routes exclusively on both Cloud Interconnect (base priority 100) and Cloud VPN (base priority 200). Upon physical cut, BGP withdrew the priority 100 route, allowing the priority 200 VPN route to take over within 3 seconds.

Alternative and residual risk: BGP failover timing depends on BGP keepalive and hold timers (typically 20s/60s). For sub-second failover, Bidirectional Forwarding Detection (BFD) should be enabled on the BGP sessions.

Exercise 4: Route Shadowing Conflict Emulation and Priority Resolution

Goal: Model a route conflict where an overlapping static route shadows a dynamic route, and resolve it using priority tuning.

Expected Result: Mathematical proof and route table verification demonstrating that Longest Prefix Match overrides priority, and lower numerical priority resolves identical destination ties.

Mode: Python routing simulation · Prerequisite: Exercise 3.

  1. Author Routing Simulation Script. Create route-simulator.py: 
    cat <<'EOF' > route-simulator.py
import ipaddress

routes = [
    {"name": "Local Subnet", "dest": "10.10.0.0/22", "prio": 0, "next_hop": "VPC Fabric"},
    {"name": "Default Internet GW", "dest": "0.0.0.0/0", "prio": 1000, "next_hop": "Internet Gateway"},
    {"name": "Custom Static Route", "dest": "192.168.10.0/24", "prio": 100, "next_hop": "Old-Appliance-VM"},
    {"name": "BGP Dynamic Failover", "dest": "192.168.10.0/24", "prio": 200, "next_hop": "Cloud-VPN-Gateway"},
    {"name": "Specific Host Route", "dest": "192.168.10.50/32", "prio": 500, "next_hop": "Direct-PSC-Endpoint"}
]

def resolve_packet(target_ip_str):
    target = ipaddress.IPv4Address(target_ip_str)
    matching = [r for r in routes if target in ipaddress.IPv4Network(r["dest"])]
    if not matching:
        return None
    # 1. Longest Prefix Match (max prefixlen)
    max_prefix = max(ipaddress.IPv4Network(r["dest"]).prefixlen for r in matching)
    lpm_routes = [r for r in matching if ipaddress.IPv4Network(r["dest"]).prefixlen == max_prefix]
    # 2. Lowest Priority Number
    winner = min(lpm_routes, key=lambda x: x["prio"])
    return winner

test_ips = ["10.10.1.25", "192.168.10.10", "192.168.10.50", "8.8.8.8"]
print("=== ANDROMEDA ROUTE SELECTION SIMULATION ===")
for ip in test_ips:
    r = resolve_packet(ip)
    print(f"Target: {ip:<15} -> Matched: {r['name']} ({r['dest']}), Next-Hop: {r['next_hop']} (Prio: {r['prio']})")
EOF
