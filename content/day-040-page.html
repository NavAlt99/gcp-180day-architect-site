1 · Topics of the day

Preemptible/Spot workload fit and interruption handling

Spot VMs provide unused Compute Engine capacity at substantial discounts (60–91% off on-demand pricing). In exchange for lower cost, Google Cloud retains the right to reclaim the compute resources whenever regional demand spikes. When reclaimed, Compute Engine provides an advance notice of exactly 30 seconds via the metadata server before forcefully ACPI-powering down the instance.

Spot VMs are ideal for stateless batch jobs, machine learning training, and asynchronous worker queues where jobs are idempotent and checkpointed. They are dangerous for synchronous, user-facing order APIs or stateful primary databases where an unhandled 30-second termination causes dropped connections and database lock contention.

Problem preview: A cost-conscious team migrates the Brightloaf fulfillment worker pool to Spot VMs without adding preemption signal listeners. During a regional capacity reclamation event, 4 worker instances are terminated mid-transaction, leaving hundreds of unacknowledged Pub/Sub messages stranded and database transaction locks stalled.

Sole-tenant nodes and licensing (BYOL)

A Sole-Tenant Node is a dedicated physical Compute Engine server assigned exclusively to host virtual machines from a single Google Cloud customer. This physical isolation eliminates noisy-neighbor resource competition and satisfies strict regulatory standards (such as HIPAA, PCI-DSS, and governmental data sovereignty) that prohibit co-tenancy on shared hardware.

Sole-tenant nodes also enable Bring Your Own License (BYOL) strategies for enterprise software (such as Microsoft Windows Server or Microsoft SQL Server) licensed on physical core, socket, or processor counts rather than virtual CPUs.

Problem preview: A healthcare integration database storing sensitive medical dietary requirements is deployed on standard multi-tenant Compute Engine infrastructure. An annual compliance audit flags the shared physical hypervisor co-tenancy, resulting in a severe regulatory violation notice and halting an enterprise partner onboarding pipeline.

Shielded VMs and Confidential VMs

Shielded VMs provide verifiable boot and runtime integrity using UEFI firmware, Secure Boot, a virtual Trusted Platform Module (vTPM), and Integrity Monitoring. Secure Boot verifies that bootloaders and kernel drivers are digitally signed, while vTPM measures the boot sequence to detect kernel rootkits or unauthorized firmware tampering.

Confidential VMs take data protection further by encrypting data in memory (data-in-use) using hardware-level memory encryption (AMD SEV or Intel TDX). Memory is encrypted with dedicated hardware keys generated on-die by the secure processor; even the host hypervisor, Google Cloud engineers, and other host processes cannot inspect memory payloads.

Problem preview: An unhardened Linux VM boots an unverified kernel driver introduced via a compromised third-party package. Because Shielded VM Secure Boot was disabled, the unsigned rootkit successfully loads into ring 0 memory, bypassing host detection tools and compromising memory security.

OS Login and SSH key management

OS Login links Linux POSIX user accounts directly to IAM identities, integrating administrative SSH access into centralized Google Cloud identity management. This eliminates the operational risk of managing static public SSH keys manually in project-level or instance-level metadata.

With OS Login, administrative privileges (sudo) are controlled via IAM roles (roles/compute.osAdminLogin vs roles/compute.osLogin), and multi-factor authentication (2FA) is enforced at login. Organization policies can enforce compute.requireOsLogin, preventing any user from injecting backdoor SSH keys into metadata.

Problem preview: A departing external contractor's Google Workspace account is suspended, but their personal public SSH key remains saved in project-level metadata. The contractor connects directly to an internet-facing bastion host using their private key, bypassing corporate identity revocation controls.

2 · Technical discussion of each topic

Preemptible/Spot workload fit and interruption handling

The 30-second preemption notice lifecycle

When Compute Engine requires capacity back, it initiates preemption. The preemption signal is delivered via the local metadata server at the endpoint: 

curl -s -H "Metadata-Flavor: Google" \
  http://metadata.google.internal/computeMetadata/v1/instance/preempted

When preemption begins, this endpoint transitions from returning FALSE to TRUE. Compute Engine waits exactly 30 seconds before sending an ACPI power-off signal to the operating system.

Checkpoint and drain handling

A well-architected asynchronous worker must implement an active preemption listener daemon or trap the ACPI signal:

  1. Stop ingestion: Cease pulling new messages from the queue (e.g. Pub/Sub subscription).
  2. Drain or nack: If in-flight units of work can finish within 20 seconds, complete and commit them. If they exceed 20 seconds, roll back local transactions, write a checkpoint token to durable storage (Cloud Storage or Persistent Disk), and negative-acknowledge (nack) the message so another worker can claim it.
  3. Flush logs: Flush telemetry buffers to Cloud Logging before the 30-second window elapses.

Sole-tenant nodes and licensing (BYOL)

Physical isolation and node groups

Sole-tenant nodes provide dedicated physical hardware. To configure sole tenancy:

  1. Node Template: Specifies the underlying physical server type (e.g. c2-node-60-240).
  2. Node Group: Allocates one or more physical hosts in a designated zone and manages maintenance policies.
  3. Node Affinity: Labels applied to VM instance templates ensuring VMs schedule exclusively onto matching sole-tenant node groups.
Maintenance Policy Host Maintenance Behavior Typical Use Case
Default (Live Migrate in Group) VMs live-migrate to another sole-tenant host in the group High-availability enterprise systems with multiple physical hosts
Migrate within Node VMs stay on physical host while underlying firmware updates Strict licensing compliance tied to specific physical hardware IDs
Terminate & Restart VMs shut down and reboot after host maintenance completes Batch HPC workloads that can tolerate maintenance downtime

Shielded VMs and Confidential VMs

Shielded VM security controls

  • Secure Boot: Verifies signature of bootloader, kernel, and kernel modules against UEFI CA certs. Prevents rootkits at the boot level.
  • Virtual TPM (vTPM): Provides hardware cryptographic measurements (Measured Boot) and stores sealed encryption keys.
  • Integrity Monitoring: Compares early-boot measurements against an established baseline; generates Cloud Monitoring alerts upon divergence.

Confidential Computing (Data-in-Use Encryption)

Standard VMs encrypt data-at-rest (disks) and data-in-transit (TLS across network). Confidential VMs protect data-in-use by encrypting RAM with hardware keys generated on the CPU security processor. Even if an attacker compromises the underlying host KVM hypervisor, memory contents appear as encrypted ciphertext.

OS Login and SSH key management

IAM-driven POSIX access

Legacy Compute Engine SSH access relied on injecting public keys into instance or project metadata. OS Login replaces this with Cloud Identity:

  • roles/compute.osLogin: Standard user POSIX shell access without sudo privileges.
  • roles/compute.osAdminLogin: Administrative POSIX shell access with passwordless sudo rights.
  • Organization Policy constraints/compute.requireOsLogin: Globally disables metadata-based SSH key injection across the organization or folder.

3 · Real-world problems and solutions

The scenarios below are realistic production architectural failure modes involving Compute Engine Spot instances, compliance tenancy, hardware security, and access control.

Topic 1 field case — Unhandled Spot preemption causes stranded transactions and lock contention

Situation and business impact

To reduce cloud infrastructure expenditure by 70%, Brightloaf migrates its background fulfillment worker fleet to Compute Engine Spot VMs. The worker application consumes order messages from Cloud Pub/Sub, executes payment settlement verification, and reserves inventory in Cloud SQL.

During a seasonal peak, Google Cloud reclaims compute capacity in us-central1-b, initiating preemption across 4 worker instances. The fulfillment application does not listen to the metadata server preemption endpoint or handle termination signals. At second 30, Compute Engine forcefully terminates the VMs. The four workers leave 120 uncommitted distributed transactions open, holding pessimistic row locks on hot inventory tables. Inbound orders stall on database lock acquisition timeouts for 15 minutes until Cloud SQL resets the orphaned database connections.

Constraints

  • Spot VMs can be preempted at any moment with only 30 seconds of advance warning.
  • Workloads must preserve the invariant that replaying an order event never triggers duplicate fulfillment.
  • Critical database row locks must be released cleanly before instance shutdown.

Root cause

The fulfillment worker was deployed on Spot instances without preemption signal detection. The application failed to use the 30-second window to pause consumption, roll back in-flight transactions, and release database locks cleanly.

Diagnostic sequence

  1. Inspect Cloud Audit Logs: Filter by compute.instances.preempted to confirm Google Cloud initiated preemption.
  2. Review Cloud SQL active connection metrics: Correlate the preemption timestamp with a sudden spike in idle locked sessions and query wait times.
  3. Review application logs: Confirm that the worker logged no shutdown sequence or connection pool drain before abruptly disconnecting.

Defensible solution

Implement a local preemption listener daemon (or SIGTERM shutdown hook). The hook continuously polls http://metadata.google.internal/computeMetadata/v1/instance/preempted. Upon detecting TRUE:

  1. Immediately stop pulling new messages from Cloud Pub/Sub.
  2. Roll back uncommitted Cloud SQL transactions and cleanly close connection pools within 15 seconds.
  3. Negative-acknowledge (nack) pending Pub/Sub message IDs so peer workers can immediately reprocess them.

Verification

Simulate a Spot preemption in a staging environment (gcloud compute instances simulate-maintenance-event or synthetic preemption metadata injection). Verify that all open database transactions are rolled back within 10 seconds, connection pools close cleanly, and Cloud SQL reports zero lingering locks.

Residual risk

If a worker execution step takes longer than 25 seconds (e.g. slow external payment gateway call), it cannot complete before the 30-second termination limit and must rely on transactional idempotency upon message redelivery.

Topic 2 field case — Multi-tenant co-location violates BYOL licensing and data isolation

Situation and business impact

To support an enterprise B2B partner requiring strict physical hardware isolation (HIPAA / PCI-DSS compliance), Brightloaf deploys a dedicated partner inventory SQL database. The enterprise agreement stipulates that all database workloads must reside on physically dedicated hardware, and the software is licensed under Bring Your Own License (BYOL) rules requiring per-physical-core licensing.

The deployment engineer provisions standard Compute Engine virtual machines without specifying a node affinity or tenancy policy. During a routine vendor license audit, the auditor checks host hardware IDs and discovers the database VMs are running on shared, multi-tenant physical hypervisors alongside other GCP customers. The partner's security compliance office issues an immediate non-compliance breach notice, freezing partner transaction integration and threatening substantial licensing true-up penalties.

Constraints

  • Must guarantee 100% physical hardware isolation from other Google Cloud tenants.
  • Must comply with core-based enterprise software licensing audits.
  • Database availability must be maintained during Google Cloud physical host maintenance events.

Root cause

Default Compute Engine instances run on shared multi-tenant hosts. The engineer omitted creating Sole-Tenant Node Groups and binding node affinity labels to the instance deployment.

Defensible solution

Provision a Sole-Tenant Node Group in us-central1-a with a node template matching the licensed core architecture. Configure the node group maintenance policy to default (Live Migrate within Node Group). Configure the VM instance with --node-group affinity, guaranteeing physical isolation and audit-compliant BYOL licensing.

Verification

Query the instance host description (gcloud compute instances describe INSTANCE_NAME --format="yaml(status,scheduling.nodeAffinities)"). Confirm that the VM is bound to the sole-tenant node group and that physical server ID logs prove zero foreign tenant co-location.

Residual risk

Sole-tenant nodes bill for the entire physical server capacity regardless of how many vCPUs are assigned to running VMs; unallocated capacity results in higher baseline costs.

Topic 3 field case — Unsigned kernel module bypasses boot verification on non-shielded VM

Situation and business impact

A production database server at Brightloaf is built from a legacy custom image with Shielded VM Secure Boot disabled. During a routine package update from an external package repository, a compromised third-party driver package installs an unsigned custom kernel module (rootkit.ko).

Upon reboot, because Secure Boot was turned off, the Linux kernel boots without verifying digital signatures. The malicious kernel module loads into ring 0 memory, hooks system calls, and silently monitors local database disk I/O, capturing raw customer payment data before disk-level encryption occurs. The compromise goes undetected for three weeks until external payment processors detect fraudulent credit card activity originating from Brightloaf transactions.

Constraints

  • Bootloaders, kernels, and kernel drivers must have verifiable cryptographic integrity.
  • Any unauthorized modification to the operating system boot sequence must immediately prevent boot or trigger alerts.
  • Memory containing customer credentials must be safeguarded from hypervisor-level inspection.

Root cause

The VM was provisioned without Shielded VM protections (Secure Boot and vTPM integrity monitoring were disabled). The operating system accepted unsigned, untrusted kernel code during initialization.

Defensible solution

Enforce Shielded VMs with Secure Boot enabled (--shielded-secure-boot), vTPM enabled (--shielded-vtpm), and Integrity Monitoring active (--shielded-integrity-monitoring). For highly sensitive workloads handling credit card memory buffers, enable Confidential Computing (--confidential-compute) to hardware-encrypt RAM.

Verification

Inspect the Shielded VM early-boot attestation report in Cloud Logging (protoPayload.serviceName="compute.googleapis.com" AND protoPayload.methodName="compute.instances.integrityReport"). Verify that early-boot hash matches the baseline and that attempting to load an unsigned test module triggers a kernel refusal (Required key not available).

Residual risk

Legitimate custom proprietary drivers (e.g. specialized network accelerators) must be digitally signed with a customer key enrolled in the UEFI firmware database, or Secure Boot will block them from loading.

Topic 4 field case — Lingering metadata SSH key allows unauthorized bastion access after contractor departure

Situation and business impact

An external database optimization contractor was granted access to Brightloaf's staging environment. The contractor added their personal laptop public SSH key to the project-level metadata via the GCP Console.

Three months later, the contractor's contract expires. IT offboards the contractor, suspending their Google Workspace identity and deleting their Cloud IAM permissions. However, the static public SSH key remains saved in project metadata. Because the staging bastion host has an external IP address and port 22 open, the contractor's laptop can still establish an active root SSH session directly to the bastion host, completely bypassing Google Cloud IAM revocation and two-factor authentication controls.

Constraints

  • Revoking an employee or contractor's Cloud IAM account must immediately terminate all SSH capabilities.
  • Administrative access to all Compute Engine virtual machines must enforce enterprise Two-Factor Authentication (2FA).
  • Prevent developers from adding back-channel SSH keys to instance or project metadata.

Root cause

Relying on metadata-based SSH key management. Metadata keys are static text strings completely decoupled from Cloud IAM identity lifecycles and corporate access governance.

Defensible solution

  1. Purge all public keys from project and instance metadata.
  2. Enable OS Login across the project (gcloud compute project-info add-metadata --metadata=enable-oslogin=TRUE).
  3. Enforce Organization Policy constraints/compute.requireOsLogin to prevent metadata key re-introduction.
  4. Manage access strictly through IAM: grant roles/compute.osLogin for standard users and roles/compute.osAdminLogin for operators needing sudo.

Verification

Attempt to connect using a raw SSH key not tied to an active IAM user: verify the server immediately rejects the key (Permission denied (publickey)). Connect using gcloud compute ssh with an active IAM account: verify successful POSIX login with 2FA prompt and audit logging in Cloud Audit Logs.

Residual risk

Third-party automation tools (e.g. legacy Ansible playbooks) that rely on fixed SSH key pairs will break when OS Login is enforced and must be migrated to service account impersonation or Cloud IAP tunneling.

Exercise 1 — Spot VM preemption simulation and graceful shutdown handler

Goal: Author a restartable worker daemon with a preemption poller that drains work within the 30-second window.

Mode: tabletop design / cloud sandbox · Prerequisites: Day 39 exit artifact.

Preflight

Open day-040-security.md. Define workload constraints: Max batch processing duration = 10s; Checkpoint storage = Cloud Storage bucket gs://bf-worker-checkpoints/.

  1. Author the preemption listener script. Create preemption-listener.sh: 
    #!/bin/bash
while true; do
  STATUS=$(curl -s -H "Metadata-Flavor: Google" \
    http://metadata.google.internal/computeMetadata/v1/instance/preempted)
  if [ "$STATUS" = "TRUE" ]; then
    echo "PREEMPTION DETECTED! Beginning 15-second graceful shutdown..."
    # 1. Stop worker ingest
    systemctl stop fulfillment-worker
    # 2. Flush in-flight checkpoint to durable storage
    touch /tmp/worker-checkpoint.state
    # 3. Release locks and exit
    echo "Shutdown complete. Ready for termination."
    exit 0
  fi
  sleep 2
done
  2. Formulate the Spot VM launch command. 
    gcloud compute instances create bf-spot-worker \
  --project=PROJECT_ID \
  --zone=us-central1-a \
  --machine-type=e2-micro \
  --provisioning-model=SPOT \
  --instance-termination-action=STOP \
  --metadata-from-file=startup-script=preemption-listener.sh
  3. Simulate preemption. Document the simulated event command: 
    gcloud compute instances simulate-maintenance-event bf-spot-worker \
  --project=PROJECT_ID \
  --zone=us-central1-a
Expected result

A validated preemption listener script and Spot instance definition in day-040-security.md proving clean shutdown within 15 seconds.

Exercise 4 — OS Login configuration and IAM role binding

Goal: Enable project-wide OS Login, configure IAM POSIX permissions, and verify access revocation.

Mode: tabletop / sandbox · Prerequisites: Exercises 1–3.

  1. Enable OS Login project-wide. 
    gcloud compute project-info add-metadata \
  --project=PROJECT_ID \
  --metadata=enable-oslogin=TRUE
  2. Grant IAM roles. Differentiate standard user from admin:

  --member="user:lead@brightloaf.com" \
