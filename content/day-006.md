<!-- topic-01:overview -->
The Linux kernel manages processes, memory, devices and filesystem access; user-space programs request those services through system calls. Paths locate files and directories. Ownership and permission bits determine which users and groups may read, write or traverse them.

<!-- topic-01:technical -->
A shell command is a user-space process. When it opens a file, the kernel resolves the path and checks permissions using the process's identity and the file or directory metadata. A directory's execute bit permits traversal; its read bit permits listing names. A file's read, write and execute bits have different meanings. Permissions are grouped for owner, group and others. For example, mode 600 grants read and write to the owner only; mode 700 on a directory grants the owner list, create and traverse rights while excluding others under the ordinary mode-bit model. Access-control lists and other security mechanisms can add rules beyond those basic bits.

The file owner and group are separate from the current shell user. A user can usually change modes on a file they own, but changing ownership to another user typically requires privilege. This matters in cloud VMs because a service running under its own account may fail to read a secret even though an interactive administrator can. Granting broad permissions hides the owner mismatch and increases exposure; first inspect the identity, path components and intended service account.

**Further study:** [Linux chmod manual — mode bits](https://man7.org/linux/man-pages/man2/chmod.2.html#DESCRIPTION) and [Linux credentials manual](https://man7.org/linux/man-pages/man7/credentials.7.html).

<!-- topic-01:problem -->
**Failure:** An order API service cannot read its configuration file after deployment, although an administrator can open it in a shell.

**Cause:** The service runs as a separate user. The file is owned by the administrator with owner-only read permission, or a parent directory lacks traverse permission for the service identity.

**Fix:** Inspect the service's effective user/group, file owner/mode and every parent directory. Put the file under the intended service account or an appropriately restricted group and grant only the needed read/traverse access. Restart the service and verify a read under its identity. Changing the file to world-readable would mask the root cause and expose configuration.

<!-- topic-02:overview -->
A process is a running program with an identity, environment, open file descriptors and exit status. Standard input, output and error are file descriptors 0, 1 and 2. Pipes and redirection connect those streams. A service manager such as systemd starts, stops and monitors long-lived processes; signals request or force process state changes.

<!-- topic-02:technical -->
When a shell launches a program, the kernel gives the process an ID and resources. The shell can redirect output into a file or pipe it to another process. A successful shell exit code only reports how a command terminated; it does not prove the service met a customer request. SIGTERM asks a process to terminate and can be handled for cleanup; SIGKILL cannot be caught or ignored and prevents application cleanup. A forced stop may leave in-flight work unfinished, so the architect should favor graceful shutdown with a bounded deadline before escalation.

At boot, a service manager activates configured units according to dependencies and target state. A unit describes how to start the service, its restart policy and other operating constraints. Systemd reports unit state while the kernel reports process state; a unit can fail after its process exits. Standard output/error may be captured in the journal for a managed service, while other applications write separate files under `/var/log` or elsewhere. Diagnostic evidence should include timestamp, unit, PID, exit status and relevant log lines. A journal entry proves what was logged, not that every request was served.

**Further study:** [Linux signal manual](https://man7.org/linux/man-pages/man7/signal.7.html), [systemd service units](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), and [journalctl manual](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html).

<!-- topic-02:problem -->
**Failure:** An order worker disappears during deployment. The service manager restarts it, but an order processed just before the stop is replayed and fulfilled twice.

**Cause:** The worker was killed before it could finish or record its work, and the application lacked an idempotency check. “Service active again” does not establish that in-flight orders were safe.

**Fix:** Inspect the previous unit state, PID, termination signal, exit status and timestamped logs. Give the worker a bounded graceful-stop path and ensure replay is idempotent using an order key or equivalent durable state. Test a stop during a synthetic order, then verify one fulfillment after restart. A forced kill remains a recovery tool when graceful stop exceeds its deadline, not the normal success criterion.

<!-- topic-02:lab -->
**Goal:** Compare graceful termination with forced termination and inspect service evidence. **Mode:** local Linux terminal; the optional journal step needs a working user systemd manager. No sudo or cloud account is needed.

### Step 1 — Create a disposable worker

Open a terminal in the Day 1 repository and create the script:

```sh
cd ~/gcp-architect-learning
cat > day-006-worker.py <<'PY'
import os
import signal
import time

def stop(signum, frame):
    print(f'graceful stop pid={os.getpid()} signal={signum}', flush=True)
    raise SystemExit(0)

signal.signal(signal.SIGTERM, stop)
print(f'started pid={os.getpid()}', flush=True)
while True:
    time.sleep(1)
PY
```

The file contains synthetic process behavior only. The handler writes an observable line when SIGTERM arrives.

### Step 2 — Start and gracefully stop it

Keep the same terminal open and run:

```sh
python3 -u day-006-worker.py > day-006-graceful.log 2>&1 &
worker_pid=$!
sleep 1
ps -p "$worker_pid" -o pid,stat,comm
kill -TERM "$worker_pid"
wait "$worker_pid"
graceful_status=$?
printf 'graceful exit=%s\n' "$graceful_status"
cat day-006-graceful.log
```

Expected: `ps` lists the Python process, the log has `started` and `graceful stop`, and the exit status is 0. PID and timestamps vary. Record the actual PID and result.

### Step 3 — Compare a forced stop

```sh
python3 -u day-006-worker.py > day-006-forced.log 2>&1 &
worker_pid=$!
sleep 1
kill -KILL "$worker_pid"
wait "$worker_pid"
forced_status=$?
printf 'forced exit=%s\n' "$forced_status"
cat day-006-forced.log
```

Expected: the log has `started` but no `graceful stop`. In Bash, the forced exit is commonly 137 (128 plus signal 9); record the observed value. The shell may also print a “Killed” message. Do not send a kill signal to any PID other than the one captured from this disposable process.

### Step 4 — Inspect the journal when available

If your Linux VM has a user systemd manager, run the following in the same repository. Skip and record “user manager unavailable” if the first command cannot connect; do not install or enable a system service just for this lesson.

```sh
systemctl --user status --no-pager
systemd-run --user --unit=gcp-day6-lab --collect /usr/bin/python3 "$PWD/day-006-worker.py"
systemctl --user status gcp-day6-lab --no-pager
journalctl --user -u gcp-day6-lab --since '5 minutes ago' --no-pager
systemctl --user stop gcp-day6-lab
journalctl --user -u gcp-day6-lab --since '5 minutes ago' --no-pager
```

Expected: the unit shows a running PID, then the journal shows start and graceful-stop messages with timestamps. Journal access and exact formatting depend on the VM's configuration. **Verification:** save commands, PID, exit codes and log or journal timestamps; explain which stop allowed cleanup. **Cleanup:** confirm the user unit is stopped and the captured PIDs no longer appear. Keep the script and logs as evidence or delete them after recording; no cloud resource exists.
