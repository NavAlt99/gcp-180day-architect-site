<!-- topic-01:overview -->
HTTP is an application protocol for requests and responses; HTTPS carries HTTP over an authenticated encrypted transport. HTTP status codes describe an application's response class. HTTP/1.1, HTTP/2 and HTTP/3 preserve core HTTP semantics while using different message framing and transport arrangements.

<!-- topic-01:technical -->
An HTTP request names a method, target and fields; the response contains a status and possibly a representation. A 2xx status means the request succeeded, 3xx requests further action, 4xx indicates a client-side request problem, and 5xx indicates the server failed to fulfill an apparently valid request. These are application outcomes. No status code exists if the client cannot establish the needed transport or TLS session. HTTPS also requires certificate and service-identity checks before an HTTP response should be trusted.

HTTP/1.1 uses a textual message syntax and normally processes requests over a TCP connection. HTTP/2 uses binary framing and multiplexes streams over a connection, commonly over TLS/TCP. HTTP/3 carries HTTP semantics over QUIC, which runs over UDP and integrates TLS 1.3. A version change does not turn an HTTP 503 into a routing error. In cloud designs, version support affects proxies, load balancers, observability and firewall rules, but method and status semantics still guide application diagnosis.

**Further study:** [RFC 9110 §15, status codes](https://www.rfc-editor.org/rfc/rfc9110#section-15), [RFC 9113 §2, HTTP/2 overview](https://www.rfc-editor.org/rfc/rfc9113#section-2), and [RFC 9114 §2, HTTP/3 overview](https://www.rfc-editor.org/rfc/rfc9114#section-2).

<!-- topic-01:problem -->
**Failure:** A health dashboard reports “port 443 open,” but customers see HTTP 503 when requesting the order API.

**Cause:** A transport probe tested that a connection could be made. It did not exercise the route, backend selection or application behavior that produces the HTTP response.

**Fix:** Run a request for the same host and path as customers, record the negotiated protocol version and status, then inspect proxy and backend health. If the request never reaches HTTP, separate DNS, TCP or QUIC, and TLS evidence first. Do not classify a returned 503 as a failed TLS handshake.

<!-- topic-02:overview -->
TLS 1.3 is a protocol that establishes encrypted, integrity-protected communication and authenticates a server with a certificate when certificate authentication is used. A certificate chain links the presented certificate to a trusted authority, while a service-identity check compares the requested name with the certificate's valid identities.

<!-- topic-02:technical -->
During a TLS 1.3 handshake, peers negotiate cryptographic parameters and establish keys before sending protected application data. The server presents certificate evidence and proves possession of the corresponding private key. The client must validate the chain according to its trust policy and compare the service name it intended to contact with the certificate's permitted identifiers. A certificate can be within its validity period and signed by a trusted authority yet still be wrong for the requested host. Conversely, a name match alone does not repair an untrusted or expired chain.

In cloud architectures, TLS may terminate at a load balancer and a separate connection may run to the backend. An architect must know which hop is authenticated and encrypted. A green backend health check cannot substitute for the public hostname check. Error evidence should name whether the failure is chain trust, validity, name matching, protocol negotiation or later HTTP behavior; these require different fixes.

**Further study:** [RFC 8446 §4, TLS 1.3 handshake](https://www.rfc-editor.org/rfc/rfc8446#section-4) and [RFC 9525 §6.3, DNS name matching](https://www.rfc-editor.org/rfc/rfc9525#section-6.3).

<!-- topic-02:problem -->
**Failure:** Customers request `orders.example.test` over HTTPS and receive a hostname-mismatch warning, although the certificate is current and issued by a trusted CA.

**Cause:** The edge presents a certificate whose DNS identity is `admin.example.test`. Valid dates and a trusted issuer do not make it valid for another requested host.

**Fix:** Identify the TLS termination point and selected certificate, issue or select a certificate covering the intended hostname, attach it to the correct listener, and recheck the requested hostname. Never disable certificate validation to make the warning disappear. After TLS succeeds, test the actual HTTP route independently.

<!-- topic-03:overview -->
MTU is the largest IP packet a link can carry without exceeding its size limit. Path MTU is the smallest usable MTU along a route. TCP MSS is the maximum TCP payload size an endpoint advertises for received segments; it is related to, but different from, path MTU.

<!-- topic-03:technical -->
Encapsulation by a tunnel adds headers, reducing the space available for the inner packet. A path that carries small handshake packets can fail when larger application data packets exceed a tunnel or link MTU. Path MTU discovery lets a sender adapt to a lower path limit when it receives the relevant too-big signal. If that signal is blocked, a connection can appear to establish and then stall during data transfer. MSS clamping at a tunnel boundary can reduce the advertised TCP segment size, but it is a targeted workaround that must reflect the real encapsulation overhead and does not fix every UDP or routing problem.

For a simple IPv4/TCP example without IP or TCP options, a 1500-byte IP MTU leaves 1460 bytes for TCP payload after 20-byte IPv4 and 20-byte TCP headers. If a tunnel leaves an inner IP MTU of 1400, the corresponding simple payload bound is 1360. Actual headers and policies can differ; observe the path rather than treating these arithmetic examples as a universal configuration value.

**Further study:** [RFC 1191 §3.1, path MTU and TCP MSS](https://www.rfc-editor.org/rfc/rfc1191#section-3.1), [RFC 8201 §1, IPv6 path MTU failure mode](https://www.rfc-editor.org/rfc/rfc8201#section-1), and [RFC 9293 §3.7.1, effective MSS](https://www.rfc-editor.org/rfc/rfc9293#section-3.7.1).

<!-- topic-03:problem -->
**Failure:** After a VPN is added, small API requests succeed, but larger responses stall. The TCP handshake completes.

**Cause:** Tunnel overhead reduced the inner path MTU. Large packets were dropped, and the necessary too-big feedback was blocked or ignored, producing a path-MTU black hole. The handshake's small packets did not exercise the failing size.

**Fix:** Compare successful and failing packet sizes, tunnel overhead and path-MTU feedback. Permit the required ICMP feedback or correct the path-MTU behavior; use a justified MSS clamp for TCP when appropriate. Test large and small payloads in both directions. An HTTP application rewrite would not repair the packet-size boundary.

<!-- topic-04:overview -->
Network Address Translation rewrites address information at a boundary. SNAT changes a packet's source address, commonly for private outbound traffic; DNAT changes its destination address, commonly when directing traffic to an internal target. Port translation can allow several private endpoints to share one public address.

<!-- topic-04:technical -->
An outbound flow from a private host cannot simply present its RFC 1918 source address to the public Internet and expect a globally routable reply. A NAT device can replace the source with a public address and often a translated source port, storing a mapping so return traffic reaches the original private endpoint. The reverse packet must match that state. DNAT instead changes the destination, such as mapping a published endpoint to an internal server. These changes affect the address tuple seen on each side; packet captures and firewall logs must be interpreted at the correct boundary.

NAT is not itself an access policy. A translation entry may exist while a firewall blocks the flow, or an allowed flow may fail because no route to the NAT device exists. In cloud designs, architects need to know whether a NAT product handles outbound connections only and whether it provides any inbound mapping. For troubleshooting, record pre-translation and post-translation source/destination and the return path.

**Further study:** [RFC 3022 §2.2, traditional NAT and NAPT](https://www.rfc-editor.org/rfc/rfc3022#section-2.2) shows address and port translation.

<!-- topic-04:problem -->
**Failure:** A private VM can reach another private subnet but cannot download an update from the public Internet. Its route points toward an egress gateway, yet the remote site never sees a usable return address.

**Cause:** The outbound path lacks the expected SNAT mapping, or traffic bypasses the translation device. A firewall change alone cannot make a private source globally routable.

**Fix:** Check the route to the egress boundary and whether a translation entry is created for the VM's source tuple. Verify the public post-NAT source and reverse mapping, then test a permitted destination. Preserve least-privilege egress controls. Do not configure DNAT as a substitute for outbound SNAT.

<!-- topic-05:overview -->
Routing chooses a next hop for a destination prefix. Static routes are configured explicitly; dynamic routing protocols exchange reachability information. BGP is a routing protocol used to exchange prefixes and path information between autonomous systems and, in some cloud designs, between a cloud network and external networks.

<!-- topic-05:technical -->
A router generally selects the most specific matching destination prefix before applying route preferences among candidates for the same prefix. The forward path and return path are separate decisions, and both must exist for a request/reply exchange. A default route is used only when no more-specific route matches. A static route is straightforward for a stable small design but must be maintained when topology changes. Dynamic protocols distribute changing reachability, with policy and convergence behavior that require careful review.

BGP advertises network prefixes and attributes such as AS path between peers. It is not a substitute for local firewall policy or an application health check. Cloud VPN or dedicated connectivity may use BGP to exchange routes, but a BGP session being up does not prove the desired prefix is advertised, selected or reachable in both directions. For incidents, record the exact destination, selected prefix, next hop, advertisement and reverse route.

**Further study:** [RFC 1812 §5.2.4, forwarding decision](https://www.rfc-editor.org/rfc/rfc1812#section-5.2.4) and [RFC 4271 §3, BGP operation](https://www.rfc-editor.org/rfc/rfc4271#section-3).

<!-- topic-05:problem -->
**Failure:** A cloud VM sends requests to an on-premises service through a VPN, but no reply returns. The tunnel and BGP session both report up.

**Cause:** The cloud has a route to the on-premises prefix, while the on-premises router lacks a route back to the cloud source prefix. Session state alone did not establish bidirectional reachability.

**Fix:** Inspect the selected forward route and the return route for the actual source address. Correct the missing advertisement or route policy, then verify both directions and firewall permissions. If both routes are present, inspect packet filtering next. A static default route pointing elsewhere can also hide a missing specific prefix.

<!-- topic-05:lab -->
**Goal:** Choose a next hop and diagnose a missing return prefix. **Mode:** local Python 3 plus a supplied route table.

### Step 1 — Select the most specific route

Open a Linux terminal and run:

```sh
python3 - <<'PY'
from ipaddress import ip_address, ip_network
destination = ip_address('10.50.4.8')
routes = [('0.0.0.0/0', 'internet'), ('10.50.0.0/16', 'vpn'),
          ('10.50.4.0/24', 'private-link')]
matches = [(ip_network(prefix).prefixlen, prefix, hop)
           for prefix, hop in routes if destination in ip_network(prefix)]
_, prefix, hop = max(matches)
print('selected:', prefix, 'via', hop)
PY
```

Expected:

```text
selected: 10.50.4.0/24 via private-link
```

The /24 wins over the /16 and default because it is the longest matching prefix. This script models prefix choice only; real routing can also use policy and route preference.
