Part 1 · Topics of the day

Fleet/Enterprise concepts, Connect Gateway, Config Sync, Policy Controller and multi-cluster service boundaries

GKE Fleets (formerly Anthos Fleets) establish a logical multi-cluster management and governance domain spanning Google Kubernetes Engine clusters across multiple GCP projects, regions, and hybrid topologies. Fleets formalize three foundational distributed architectural axioms: namespace sameness (namespaces with identical names across fleet member clusters represent the same administrative and tenancy boundary), service sameness (services sharing names and namespaces across member clusters represent the same logical service), and identity sameness (workloads residing in identical namespaces share the same Workload Identity authority). Operating over a dedicated Fleet Host Project, enterprise platform teams leverage fleet-level team management through Scopes and Fleet Namespaces to delegate isolated cluster slices to product engineering groups without granting cluster-admin privileges. Connect Gateway provides centralized, audited administrative access through Google Cloud IAM without requiring inbound firewall openings, bastion hosts, or public Kubernetes API server endpoints. Config Sync acts as a continuous GitOps reconciliation engine mapping declarations from Git repositories or OCI registries to fleet clusters via RootSync and RepoSync primitives. Policy Controller enforces declarative guardrails via Open Policy Agent (OPA) Gatekeeper admission webhooks, preventing non-compliant configurations from reaching etcd. In parallel, Multi-Cluster Services (MCS) and Multi-Cluster Ingress (MCI) resolve cross-cluster endpoints using native VPC routing via clusterset.local. Upstream in the software supply chain, automated Artifact Analysis scanning and Binary Authorization admission controllers verify cryptographic attestations signed by Cloud KMS keys before container digests are admitted onto fleet worker nodes prior to Days 114–115.

This capability belongs on Day 46 because Days 42–45 established single-cluster workload execution, networking, and resilience; enterprise organizations cannot scale operations across multiple independent cluster silos without centralized governance and shared service boundaries. In the complete cloud architecture, Fleets sit as the overarching multi-cluster management layer binding regional production, staging, and disaster recovery clusters to enterprise identity, GitOps pipelines, and global traffic routing.

When an unverified GitOps commit propagates an invalid cluster selector across the fleet, Config Sync encounters admission rejections on secondary clusters while Connect Gateway routes diagnostic requests to an outdated cluster API endpoint. Engineers cannot reconcile cross-cluster service discovery between primary and failover regions, leaving customer checkout requests failing over to nonexistent endpoints and halting regional order processing.

Evaluate cost and operational overhead of service-mesh vs. direct communication

Cloud Service Mesh provides advanced Layer 7 traffic routing, fine-grained fault injection, telemetry extraction, and automated zero-trust mutual TLS (mTLS) with cryptographically validated SPIFFE identities. In Google Cloud, architects evaluate two control plane models: Managed Istio (Google-managed Istiod control plane with automatic canary upgrades and Envoy sidecar injection) and Traffic Director (Google Cloud's global xDS control plane supporting both Envoy sidecars and Proxyless gRPC architectures). However, running sidecar proxies across hundreds of microservices imposes heavy compute, memory, latency, and operational tax: every Pod requires an injected Envoy container consuming 50MB to 150MB of resident RAM and 0.1 to 0.25 vCPU cores, alongside a 1.5ms to 4.0ms latency tax per service hop resulting from userspace kernel context switching and iptables packet redirection. For high-throughput transactional architectures, platform architects must determine whether application requirements mandate Layer 7 proxy features or whether native GKE Dataplane V2 eBPF Network Policies, container-native NEGs, and Cloud IAM Workload Identity achieve sufficient security and traffic management at zero sidecar resource cost.

This topic belongs on Day 46 because architects must make defensible runtime design decisions rather than defaulting to complex platform add-ons that multiply cloud bills and degrade p99 transaction performance. In production infrastructure, this choice defines the boundary between the data plane network layer and container resource allocation models across all fleet worker nodes.

When an engineering team blindly enables sidecar injection across high-throughput data processing pods, aggregate memory consumption spikes by 40% and p99 latency degrades by 8ms per microservice call. The cluster exhausts available node pool memory during seasonal traffic surges, triggering cascading OutOfMemory (OOM) evictions that crash the core billing and order ingestion pipelines.

GKE Fleets, Fleet Host Projects, Team Scopes, Connect Gateway, GitOps, and Supply Chain Boundaries

A GKE Fleet establishes a unified administrative, identity, and networking domain spanning multiple Kubernetes clusters across regions and projects. Rather than treating clusters as disparate operational islands requiring distinct credentials and manual networking stitching, Fleets establish structural enterprise governance:

  • Fleet Host Project Architecture: Enterprise landing zones adopt the dedicated Fleet Host Project pattern. A centralized project (e.g. corp-fleet-host) hosts the Fleet resource and enables the gkehub.googleapis.com API. Individual clusters located in spoke workload projects (e.g. app-prod-central1, app-prod-east1) are registered as fleet members. This cleanly separates fleet-wide administrative governance and shared service controllers from project-level compute quotas and network VPC allocations.
  • Fleet-Level Team Management (Scopes & Fleet Namespaces): Fleets introduce a multi-tenancy abstraction called Scopes. Platform teams define a Scope representing an application team or business unit (e.g. checkout-team) and bind it to specific fleet member clusters. Within that Scope, platform teams declare Fleet Namespaces (e.g. order-system). GKE Enterprise automatically reconciles the namespace across all clusters bound to the scope, sets up team-scoped RBAC, and applies centralized resource quotas without requiring custom scripts on every physical cluster.
  • Namespace, Identity, and Service Sameness:
    • Namespace Sameness: Namespaces with identical names across fleet member clusters are treated as the same administrative entity. RBAC bindings, network policies, and audit scopes defined for that namespace apply identically everywhere.
    • Identity Sameness: Workload Identity pools map service account identities across fleet members uniformly. A Kubernetes Service Account named order-sa in namespace order-system assumes the same Google Cloud IAM principal set regardless of physical host cluster: principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/order-system/sa/order-sa.
    • Service Sameness: Services declared with the Multi-Cluster Services (MCS) API via ServiceExport are automatically aggregated across clusters into a unified ServiceImport reachable cluster-wide via the cluster-set internal domain: order-api.order-system.svc.clusterset.local. CoreDNS intercepts this domain and resolves it directly to available pod IPs across member clusters without intermediate reverse proxies.
  • Connect Gateway: Provides centralized, IAM-authenticated Kubernetes API access to all fleet member clusters. Instead of exposing public API endpoints, whitelisting corporate IP blocks, or maintaining fragile VPN bastions, operators and CI/CD pipelines connect to connectgateway.googleapis.com using standard Google Cloud OAuth2 tokens. The Connect Agent running inside the cluster maintains an outbound gRPC tunnel (port 443) back to Google infrastructure. Connect Gateway intercepts the request, verifies Cloud IAM permissions (e.g. roles/gkehub.gatewayAdmin or roles/gkehub.gatewayEditor), and passes the request down the reverse tunnel using Kubernetes RBAC user/group impersonation headers. All administrative actions produce immutable audit entries in Cloud Audit Logs.
  • Config Sync (Multi-Repo GitOps): Config Sync continuously synchronizes declarative infrastructure manifests from Git repositories or OCI container registries into fleet clusters. It employs a two-tier hierarchy:
    • RootSync: Managed by central platform engineering teams. Reconciles cluster-wide resources including CRDs, cluster roles, fleet namespaces, and global Policy Controller constraints.
    • RepoSync: Delegated to individual product engineering teams within their assigned Fleet Namespace or Scope. Reconciles namespace-scoped resources such as Deployments, Services, ConfigMaps, and HorizontalPodAutoscalers without risk of altering cluster-wide infrastructure.
  • Policy Controller (OPA Gatekeeper): Built on the Open Policy Agent (OPA) Gatekeeper engine, Policy Controller intercepts Kubernetes admission requests (`ValidatingWebhookConfiguration`) and audits running workloads against declarative Rego policies. Platform teams enforce CIS Kubernetes benchmarks, enforce mandatory label taxonomies, block privileged containers (`privileged: true`), and reject non-read-only root filesystems before manifests can be committed to etcd. Policies can operate in warn (audit only) or enforce mode.
  • Software Supply Chain Security (Cloud Build, Artifact Registry, Binary Authorization): GKE Fleets integrate natively with Google Cloud supply chain security tooling:
    • Cloud Build: Executes automated container image builds and generates non-falsifiable SLSA Level 3 build provenance records documenting exact source repository commit hashes, builder identities, and build steps.
    • Artifact Registry: Stores container images and executes automated Artifact Analysis vulnerability scans (CVE detection in OS packages and language runtimes) upon push.
    • Binary Authorization: Acts as an admission webhook that evaluates container image digests against defined signature policies prior to pod scheduling. Images must be cryptographically attested by authorized Cloud KMS asymmetric signing keys (e.g., verifying that the image passed automated vulnerability scanning and unit testing in CI). If an unsigned, altered, or unverified container image digest is submitted, Binary Authorization denies admission. An audited "breakglass" mechanism exists for emergencies, generating high-priority Security Command Center and Cloud Audit Log alerts.

Cost, Latency, and Operational Trade-Offs: Cloud Service Mesh vs. Direct Communication

Cloud Service Mesh provides advanced Layer 7 capabilities, but enterprise platform architects must rigorously evaluate its substantial compute tax, latency penalties, and operational overhead against simpler, native cloud alternatives:

1. Control Plane Architecture: Managed Istio vs. Traffic Director

Google Cloud offers two primary architectural patterns for service mesh control planes:

  • Managed Cloud Service Mesh (Istio-based): Google manages the lifecycle of the Istiod control plane, providing automatic minor version upgrades, zero-touch certificate authority rotation (via Google Mesh CA), and automated sidecar proxy injection. Workloads run standard Envoy sidecars. Features include full Istio Custom Resource Definitions (VirtualService, DestinationRule, Gateway, AuthorizationPolicy, Sidecar).
  • Traffic Director (xDS API-based): Uses Google Cloud's globally distributed, highly available traffic management platform as a native control plane. Rather than running an in-cluster control plane daemon, Traffic Director acts as an xDS v3 API server communicating directly with Envoy sidecars or Proxyless gRPC applications. It enables seamless integration between Kubernetes workloads, Compute Engine VMs, and serverless runtimes.

3. The Financial and Performance Reality of Service Mesh at Scale

While marketing materials emphasize zero-code security, platform architects must model the true aggregate cost across large production fleets:

  • The Memory Tax: In a production cluster running 500 pods, injecting an Envoy sidecar consuming an average of 120MB allocates 60GB of RAM purely for proxy infrastructure. In Google Cloud, this necessitates provisioning an additional 2 to 4 high-memory worker nodes (e.g. n2-standard-16 or n2-highmem-8), adding $600 to $1,800 per month per cluster in raw compute costs without processing a single additional business transaction.
  • The Microservice Latency Chain: In a modern microservices architecture, a single end-user request frequently triggers a call chain across multiple services (e.g., Ingress Gateway -> API Gateway -> Cart Service -> Inventory Service -> Payment Gateway). With Envoy sidecars at both client and server ends of every connection, each hop incurs two proxy traversals and user-space context switches. Over a 4-hop internal chain, the sidecar mesh adds 8ms to 16ms of pure proxy latency overhead to the p99 response time. For high-frequency trading, real-time gaming, or flash-sale retail, this latency penalty can violate customer SLAs.
  • Operational Fragility: Deploying sidecars tightly couples application pod initialization to the availability of the mesh mutating admission webhook. If the Istio control plane experiences an outage or temporary network partition, new application pods cannot be scheduled, turning a control plane hiccup into a critical application availability outage. Furthermore, unscoped sidecars download the complete cluster endpoint registry (CDS and EDS), causing memory consumption to spiral during rapid horizontal pod autoscaling.

4. Decision Framework for Platform Architects

  1. When to adopt Cloud Service Mesh (Envoy Sidecars):
    • Strict regulatory mandates (e.g. PCI-DSS, HIPAA, FedRAMP) requiring pervasive, cryptographically verifiable mTLS encryption with SPIFFE identities between all internal microservices on the wire.
    • Complex east-west Layer 7 traffic routing requirements: dynamic HTTP header routing, path-based canary deployments, request shadowing, and distributed fault injection across polyglot microservice stacks.
    • Enterprise cross-cloud or hybrid environments where unified telemetry and access control policies must bridge heterogeneous Kubernetes clusters and legacy virtual machines.
  2. When to adopt Proxyless gRPC:
    • High-throughput, latency-critical internal microservice topologies that are already standardized on gRPC (e.g. distributed streaming engines, internal search indices).
    • Environments requiring zero-trust mTLS and dynamic traffic shifting without sacrificing sub-millisecond wire-speed networking or allocating node memory to sidecars.
  3. When to rely on Native Direct Communication (Dataplane V2 + Gateway API):
    • High-throughput, latency-sensitive transactional workloads (e-commerce checkout, financial clearing, IoT ingest pipelines) where extra proxy hops degrade performance.
    • Cost-sensitive deployments where dedicating 15%–30% of cluster CPU and memory budgets to sidecar proxies cannot be economically justified.
    • Architectures where edge Cloud Application Load Balancers provide Layer 7 ingress routing, and native GKE Dataplane V2 eBPF Network Policies provide sufficient microsegmentation and isolation.

Part 3 · Real-world problem and solution for each topic

Fleet Multi-Cluster Service Discovery Outage · field case

Situation and impact: Brightloaf operates a primary GKE cluster in us-central1 and a disaster recovery cluster in us-east1 united under a single GKE Fleet. During a planned regional failover drill, the frontend checkout service in us-east1 is directed to consume the backend order-api hosted in us-central1 via Multi-Cluster Services (MCS) domain order-api.order-system.svc.clusterset.local. Instead of routing traffic seamlessly across regions, CoreDNS in us-east1 returns NXDOMAIN, causing instant 503 Service Unavailable errors on all cross-region checkout requests. Over $120,000 in mobile customer orders fail within 25 minutes.

Constraints: Must preserve multi-cluster namespace sameness; cannot expose internal database or API endpoints to the public internet; and must resolve cross-cluster endpoints using native VPC routing without introducing fragile public IP ingress hops.

Diagnosis and solution: Inspection of the fleet configuration reveals that while the primary cluster had exported the service via a ServiceExport manifest, the secondary cluster's Fleet membership lacked the required IAM role roles/gkehub.serviceAgent on the Google Cloud service identity. Consequently, the Fleet MCS controller was blocked from synchronizing the EndpointSlice resources into the secondary cluster's order-system namespace. CoreDNS received no local cluster-set records and rejected all queries. The resolution required granting the GKE Hub service agent the necessary IAM binding on the project, re-registering the cluster membership, and applying a verified ServiceExport manifest in the primary cluster.

Alternative and residual risk: While Multi-Cluster Services eliminates external load balancer costs for internal east-west traffic, cross-region egress bandwidth incurs standard Google Cloud inter-region data transfer fees ($0.01/GB). If a primary region experiences severe networking degradation, failover routing must be throttled or coupled with local database read replicas to avoid cross-region database lock contention.

Unscoped Envoy Proxy Memory Exhaustion and Tail Latency Degeneration · field case

Situation and impact: Brightloaf deployed Cloud Service Mesh with automatic sidecar injection across all 80 microservices in the production cluster. During morning breakfast peak traffic (14,000 orders/minute), the high-throughput BreadBaker order notification service experiences sudden p99 latency degradation from 12ms to 480ms. Within 10 minutes, dozens of notification pods terminate with exit code 137 (OOMKilled), triggering cascading TCP reset errors on customer order placement.

Constraints: Must maintain secure zero-trust identity between microservices; must not disable mTLS encryption on customer financial data paths; and must preserve container memory allocation within the existing node pool capacity.

Diagnosis and solution: Examination of the terminated pods indicates that the application container consumed only 180MiB of its 512MiB limit, but the co-located istio-proxy container breached its default 256MiB limit and was terminated by the Linux cgroup OOM reaper. Because the pod lacked a customized Istio Sidecar resource, Envoy downloaded the complete Cluster Discovery Service (CDS) and Endpoint Discovery Service (EDS) configuration for all 80 microservices in the cluster—totaling over 1,400 pod endpoints. The constant churn of dynamic endpoints caused Envoy's memory buffer to grow monotonically until kernel termination. The solution entailed deploying an Istio Sidecar resource restricting the proxy's egress visibility strictly to the three backend services it actually communicates with, dropping Envoy memory usage by 78% and stabilizing p99 latency under 15ms.

Alternative and residual risk: Scoping sidecars requires meticulous maintenance of dependency lists. If a microservice introduces a new downstream API call without updating its Sidecar manifest, Envoy drops the outbound requests with 502 Bad Gateway errors. Platform teams should automate sidecar generation via CI/CD service dependency catalogs.

# Architecture Decision Record (ADR 046): Multi-Cluster Fleet Governance & Service Runtime Selection

## Context & Problem Statement
Brightloaf is scaling its order processing architecture from a single GKE cluster to a multi-region active-passive topology across `us-central1` and `us-east1`. We must choose between deploying an enterprise Service Mesh (Cloud Service Mesh / Istio) across all workloads or standardizing on native GKE Dataplane V2 with Multi-Cluster Services (MCS) and Gateway API.

## Decision Drivers
1. **Cost & Compute Overhead:** Microservice sidecars consume substantial memory and CPU across 500+ pods ($24,356/yr baseline tax).
2. **Latency Sensitivity:** Order ingestion requires p99 round-trip latency under 20ms; intermediate proxy hops introduce 1.5ms–4ms per call.
3. **Zero-Trust Compliance:** PCI-DSS audit requires mutual authentication and cryptographic identity verification between services handling payment tokens.
4. **Operational Simplicity:** Avoid control plane version coupling and mutating webhook failure modes during rolling upgrades.

## Evaluated Alternatives
- **Alternative A: Universal Cloud Service Mesh (Sidecar Injection on all pods)**
  - *Pros:* Automatic L7 mTLS, fine-grained canary traffic shifting, uniform telemetry.
  - *Cons:* $24k/year compute tax, +8ms accumulated chain latency, OOMKilled risks during endpoint churn.
- **Alternative B: Native GKE Dataplane V2 + MCS + Selective Cloud Service Mesh (Recommended)**
  - *Pros:* Zero sidecar overhead for high-throughput streaming/order workers; eBPF host-level packet filtering; direct VPC routing via `clusterset.local`.
  - *Cons:* Requires application-level TLS or selective mesh deployment strictly on PCI-scoped payment pods.

## Decision & Implementation Boundary
We adopt **Alternative B**. All general microservices run natively on GKE Dataplane V2 with eBPF Network Policies and Fleet Multi-Cluster Services. Cloud Service Mesh sidecar injection is strictly quarantined to the `payment-system` namespace. All sidecars MUST include an explicit `Sidecar` CRD to prune egress discovery.
