1. Recovery Acceptance Criteria After Backup Restore or Replica Promotion

Declaring a database recovered requires satisfying explicit, objective acceptance criteria spanning network, security, and data layers. Too often, teams celebrate when a backup restore or replica promotion operation completes successfully in the CLI, only to direct user traffic to an instance that lacks necessary IAM service account bindings, has outdated read-only parameters, or contains corrupted foreign key indexes. An enterprise acceptance checklist enforces sequential verification gates before read-write connection pools are re-opened to client traffic.

Problem preview: A promoted read replica accepts traffic while still configured in read-only transaction mode, causing all customer checkout writes to fail. Pre-traffic recovery acceptance gates verify read-write status and connection pool reconnection before opening application ingress.

2. Verifying Data Invariants, Recovery Time (RTO), and Data Loss (RPO)

After a database restore or failover, infrastructure metrics measure duration and connection counts, but only application-level data invariants prove whether data corruption or transaction loss occurred. A business invariant is an immutable truth that must hold across all operational states: in banking, total debits must equal total credits; in e-commerce, every paid order must be fulfilled exactly once and inventory count plus items sold must equal total initial stock. Verifying these invariants against post-restore data provides empirical proof of actual Recovery Point Objective (RPO) and confirms zero customer financial harm.

Problem preview: A database restore finishes in 10 minutes, but 45 in-flight payment records lack corresponding fulfillment entries. Running post-restore invariant reconciliation scripts isolates unfulfilled transactions and measures actual data loss.

3. Executing One Representative Recovery Path and Comparing Alternatives

A resilient architecture maintains distinct recovery paths optimized for different disaster scopes. **Cloud SQL Regional High Availability** is the primary intra-regional recovery path, providing fully automated, zero-data-loss failover across zones within seconds. Conversely, **Cross-Region Read Replica Promotion** is the catastrophic recovery path invoked only when an entire geographical cloud region experiences sustained, catastrophic failure. Understanding the exact mechanical trade-offs between these two paths—and executing one representative path while documenting the operational runbook for the alternative—is an essential competency for Google Cloud Professional Architects.

1. Recovery Acceptance Criteria After Backup Restore or Replica Promotion: technical mechanics

1. The Four-Stage Recovery Acceptance Pipeline

  • Stage 1: Infrastructure Readiness Gate:
  • Verify database instance status is RUNNABLE via the instance describe API.
  • Confirm Private Service Access (PSA) VPC peering IP address is reachable from application subnets.
  • Verify SSL/TLS certificates and Cloud SQL Auth Proxy client authorization tokens.
  • Stage 2: Engine Configuration & Mode Gate:
  • In promoted replicas, assert the database engine has disabled standby mode: SHOW transaction_read_only; must return off.
  • Check max_connections, shared_buffers, and active connection headroom.
  • Stage 3: Application Health Gate:
  • Execute lightweight diagnostic query: SELECT 1;.
  • Test connection pool draining and recycling: ensure application pods re-establish live sockets without stale connection errors.
  • Stage 4: Post-Restore Binary Log & Replication Stream Gate:
  • If promoted to primary, ensure automated backups and point-in-time recovery (WAL archiving) are re-enabled immediately.
  • A newly promoted primary is un-backed-up until a fresh base snapshot completes; running without backups creates severe residual risk.

Architectural evaluation questions

  • Why must a promoted replica immediately have automated backups and WAL archiving re-enabled before opening production write traffic?
  • What hidden configuration states (such as `transaction_read_only = on`) can cause a promoted replica to reject application writes?
  • How does the Cloud SQL Auth Proxy handle automatic connection recovery when a primary instance changes IP addresses during failover?

2. Verifying Data Invariants, Recovery Time (RTO), and Data Loss (RPO): technical mechanics

1. Mathematical Definitions of RTO and RPO

  • Recovery Time Objective (RTO): The maximum tolerable elapsed time between the declaration of disaster and the full restoration of production read-write capability: $\text{RTO} = T_{\text{restored}} - T_{\text{disaster}}$.
  • Recovery Point Objective (RPO): The maximum acceptable data loss measured in time backward from the disaster event: $\text{RPO} = T_{\text{disaster}} - T_{\text{last_committed_data_preserved}}$.

2. Core Business Invariant Verification

  • Invariant 1: Conservation of Account Balances: $$\sum \text{Customer Balances} + \sum \text{Pending Escrow} = \text{Total Ledger Cash}$$
  • Invariant 2: Strict Single Fulfillment: $$\forall \text{order} \in \text{Orders}: \text{count}(\text{fulfillments}(\text{order})) = 1 \iff \text{order.status} = \text{'PAID'}$$ Every paid order must have exactly one warehouse dispatch record; zero paid orders may have duplicate or zero dispatches.
  • Invariant 3: Inventory Stock Parity: $$\text{Current Stock} + \sum \text{Shipped Quantities} = \text{Initial Stock}$$

3. Auditing Alerting Behavior During Failover

  • When a database fails over, dozens of downstream microservices experience temporary connection pool drops.
  • Alert Fatigue Prevention: SLO burn-rate alerts must distinguish between an acute 60-second failover window (which burns a minor fraction of the 30-day error budget) and an unrecovered, catastrophic total outage. If the failover completes within the contractual RTO (e.g. <120s), incident managers should receive informational updates while on-call escalation pages are held until RTO thresholds are breached.

Architectural evaluation questions

  • What is the mathematical difference between infrastructure restoration time (RTO) and transactional data loss (RPO)?
  • How does verifying application-level data invariants prove data consistency beyond low-level database page checksums?
  • Why should alert policies incorporate grace periods matching the expected database HA failover duration?

3. Executing One Representative Recovery Path and Comparing Alternatives: technical mechanics

1. Comparative Analysis of Recovery Paths

  • Path A: Cloud SQL Regional High Availability (Representative Path Executed):
  • Topology: Primary instance in Zone A, Standby instance in Zone B, sharing a synchronized Regional Persistent Disk.
  • Failover Trigger: Automated heartbeats detected by Google Cloud control plane. If the primary VM fails for >60s, the control plane attaches the regional disk to the standby VM and redirects the regional static IP.
  • RPO & RTO: RPO = 0; RTO = 60–120 seconds.
  • Failback: Completely seamless; once Zone A recovers, it automatically synchronizes as the new standby.
  • Path B: Cross-Region Replica Promotion (Alternative Path Detailed):
  • Topology: Primary in us-central1, asynchronous Read Replica in us-east1 replicating over Google's global fiber backbone.
  • Failover Trigger: Human-in-the-loop operational decision. Promoted via the Cloud SQL replica promotion API.
  • RPO & RTO: RPO = Asynchronous replication byte lag (typically 1–10 seconds); RTO = 5–15 minutes (provisioning standalone metadata, promoting instance, updating application DNS).
  • Failback Complexity: High; promoting a replica permanently severs replication. To fail back, SREs must provision a new replica in us-central1, wait for full initial data synchronization, and execute a scheduled maintenance cutover.

Architectural evaluation questions

  • Under what exact operational criteria should an organization trigger cross-region replica promotion instead of waiting for Regional HA failover?
  • Why does promoting a cross-region read replica permanently sever replication, and what steps are required to fail back?
  • How does Regional Persistent Disk synchronous replication guarantee RPO=0 during an unexpected zonal hypervisor crash?

1. Recovery Acceptance Criteria After Backup Restore or Replica Promotion · field case

Enterprise scenario: Following an emergency cross-region replica promotion during a regional outage, all Brightloaf customer checkout transactions threw HTTP 500 errors with database exception: `ERROR: cannot execute INSERT in a read-only transaction`.

Constraints: Must automate post-promotion acceptance checks so that transaction read-write mode is verified before application pods switch database endpoints.

Diagnostic sequence:

  1. Execute direct psql query against promoted instance: `SELECT pg_is_in_recovery();`.
  2. Inspect application pod datasource configuration and environment variable overrides.
  3. Review application error logs in Logs Explorer for specific database SQL state codes (`25006`).

Root cause: Unverified application datasource binding: the database had promoted correctly to primary, but the application connection pool was configured with read-only session flags, rejecting all insert operations.

Defensible remediation: Incorporate an automated pre-flight acceptance probe in the deployment script that executes a transactional insert/delete test using the application's primary datasource credentials before updating Cloud DNS or Kubernetes service selectors.

Verification: Run automated acceptance probe script; confirm it executes a canary write transaction, verifies `pg_is_in_recovery() = false`, and returns exit code 0 before traffic shifting occurs.

Residual risk: Cross-region promotion breaks the original replication link; a new replica must be provisioned in the primary region to re-establish HA.

2. Verifying Data Invariants, Recovery Time (RTO), and Data Loss (RPO) · field case

Enterprise scenario: Following an unexpected Cloud SQL zonal failover, warehouse dispatch operators reported that 28 orders placed immediately prior to the failover were dispatched twice, while 14 customer credit cards were charged without an order record being created.

Constraints: Must establish an automated invariant verification script that reconciles payment gateway ledgers against database order records immediately post-failover.

Diagnostic sequence:

  1. Query the database for orphan payment tokens lacking corresponding order IDs.
  2. Audit warehouse dispatch records grouped by `order_id` to identify duplicate entries.
  3. Reconcile payment gateway settlement reports against database ledger tables.

Root cause: Non-atomic transactional boundaries: decoupled database writes without cross-table atomic locks allowed transient failover disconnects to corrupt business state consistency.

Defensible remediation: Enclose order creation, inventory deduction, and payment capture inside an atomic database transaction. Implement post-failover invariant verification scripts that audit data integrity before opening ingress.

Verification: Trigger a simulated failover; execute the invariant reconciliation script; confirm 100% of orders satisfy the single-fulfillment invariant with zero duplicate dispatches and zero orphan charges.

Residual risk: External third-party payment gateways operate outside the local database ACID boundary; distributed two-phase commit or transactional outbox patterns are required.

# Automated Post-Restore / Post-Failover Recovery Acceptance Engine
import json
import time

class SimulatedDatabase:
    def __init__(self, is_in_recovery=False, allow_writes=True, current_connections=12):
        self._in_recovery = is_in_recovery
        self._allow_writes = allow_writes
        self._connections = current_connections
        self._max_connections = 100
        self.table_data = {}

    def query_scalar(self, sql):
        if sql == "SELECT pg_is_in_recovery();":
            return self._in_recovery
        if sql == "SHOW transaction_read_only;":
            return "on" if not self._allow_writes else "off"
        if sql == "SELECT count(*) FROM pg_stat_activity;":
            return self._connections
        return None

    def execute_canary_transaction(self, test_key, test_val):
        if not self._allow_writes or self._in_recovery:
            raise RuntimeError("ERROR: cannot execute INSERT in a read-only transaction")
        self.table_data[test_key] = test_val
        # Delete immediately to leave zero residual data
        del self.table_data[test_key]
        return True

def run_recovery_acceptance_suite(db_instance):
    results = {
        "timestamp": time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime()),
        "stages": {},
        "passed": False
    }

    # Stage 1: Engine Recovery Mode Assertion
    in_rec = db_instance.query_scalar("SELECT pg_is_in_recovery();")
    results["stages"]["1_engine_mode"] = {
        "check": "pg_is_in_recovery == False",
        "value": in_rec,
        "status": "PASS" if not in_rec else "FAIL"
    }

    # Stage 2: Transaction Read-Write Mode Assertion
    ro_status = db_instance.query_scalar("SHOW transaction_read_only;")
    results["stages"]["2_read_write_mode"] = {
        "check": "transaction_read_only == off",
        "value": ro_status,
        "status": "PASS" if ro_status == "off" else "FAIL"
    }

    # Stage 3: Connection Headroom Assertion
    active_conns = db_instance.query_scalar("SELECT count(*) FROM pg_stat_activity;")
    headroom_ok = active_conns < 80 # Must have >20% headroom
    results["stages"]["3_connection_headroom"] = {
        "active_connections": active_conns,
        "headroom_sufficient": headroom_ok,
        "status": "PASS" if headroom_ok else "FAIL"
    }

    # Stage 4: Live Canary Write/Delete Transaction
    canary_ok = False
    try:
        canary_ok = db_instance.execute_canary_transaction("__canary_probe__", "probe_val")
        results["stages"]["4_canary_transaction"] = {"status": "PASS", "error": None}
    except Exception as e:
        results["stages"]["4_canary_transaction"] = {"status": "FAIL", "error": str(e)}

    # Overall Acceptance Certificate
    all_passed = (not in_rec) and (ro_status == "off") and headroom_ok and canary_ok
    results["passed"] = all_passed
    return results

# Scenario A: Promoted Primary that is fully healthy
healthy_promoted_db = SimulatedDatabase(is_in_recovery=False, allow_writes=True, current_connections=15)
cert_healthy = run_recovery_acceptance_suite(healthy_promoted_db)
print("=== SCENARIO A: HEALTHY PROMOTED INSTANCE ===")
print(json.dumps(cert_healthy, indent=2))
assert cert_healthy["passed"], "Healthy promoted instance should pass acceptance!"

# Scenario B: Promoted instance stuck in read-only mode
unhealthy_ro_db = SimulatedDatabase(is_in_recovery=False, allow_writes=False, current_connections=15)
cert_unhealthy = run_recovery_acceptance_suite(unhealthy_ro_db)
print("
=== SCENARIO B: UNHEALTHY READ-ONLY INSTANCE ===")
print(json.dumps(cert_unhealthy, indent=2))
assert not cert_unhealthy["passed"], "Read-only instance must be rejected by acceptance suite!"

print("
PASS: Database recovery acceptance engine mathematically verified.")
EOF

# Automated Business Invariant Auditor and RTO/RPO Verification Engine
import json
import time

# Simulated Post-Failover Dataset
orders_table = [
    {"order_id": f"ord-{i:03d}", "customer": f"cust-{i:03d}", "amount": 50.0, "status": "PAID"}
    for i in range(1, 101)
]

# Simulated fulfillments: Exactly 1 per order (Normal invariant)
fulfillments_table = [
    {"fulfillment_id": f"ful-{i:03d}", "order_id": f"ord-{i:03d}", "carrier": "FedEx"}
    for i in range(1, 101)
]

def verify_single_fulfillment_invariant(orders, fulfillments):
    fulfillment_counts = {}
    for f in fulfillments:
        oid = f["order_id"]
        fulfillment_counts[oid] = fulfillment_counts.get(oid, 0) + 1

    violations = []
    for o in orders:
        oid = o["order_id"]
        count = fulfillment_counts.get(oid, 0)
        if o["status"] == "PAID" and count != 1:
            violations.append({
                "order_id": oid,
                "status": o["status"],
                "fulfillment_count": count,
                "violation": "Duplicate fulfillment" if count > 1 else "Missing fulfillment"
            })

    return (len(violations) == 0), violations

def measure_rto_rpo(disaster_time_epoch, recovery_time_epoch, last_committed_epoch):
    # RTO: Elapsed duration to restore service
    measured_rto_sec = recovery_time_epoch - disaster_time_epoch
    # RPO: Data gap between disaster and last preserved transaction
    measured_rpo_sec = max(0, disaster_time_epoch - last_committed_epoch)

    return {
        "measured_rto_seconds": measured_rto_sec,
        "measured_rpo_seconds": measured_rpo_sec,
        "rto_sla_target_seconds": 120,
        "rpo_sla_target_seconds": 0,
        "rto_compliant": measured_rto_sec <= 120,
        "rpo_compliant": measured_rpo_sec == 0
    }

# Execute Invariant Audit
invariant_passed, violations = verify_single_fulfillment_invariant(orders_table, fulfillments_table)
print("=== INVARIANT VERIFICATION: SINGLE FULFILLMENT ===")
print(f"All 100 Paid Orders Have Exactly 1 Fulfillment: {invariant_passed}")
assert invariant_passed, f"Invariant breached: {violations}"

# Measure Recovery Metrics for Regional HA Failover
t_disaster = 1700000000
t_recovered = 1700000084 # Restored in 84 seconds
t_last_data = 1700000000  # Synchronous replication preserved all data (0s loss)

recovery_metrics = measure_rto_rpo(t_disaster, t_recovered, t_last_data)
print("
=== MEASURED RTO AND RPO METRICS ===")
print(json.dumps(recovery_metrics, indent=2))

assert recovery_metrics["rto_compliant"], "RTO breached SLA target!"
assert recovery_metrics["rpo_compliant"], "RPO breached: Data loss occurred!"

print("
PASS: Invariant verification and RTO/RPO evaluation mathematically certified.")

# Day 98: Disaster Recovery Runbook: Cross-Region Replica Promotion (Alternative Path)

## 1. Operational Decision Matrix: When to Trigger Cross-Region Promotion
| Disaster Scenario | Recommended Recovery Path | Justification | Data Loss (RPO) |
