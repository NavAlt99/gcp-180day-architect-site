1 · Topics of the day

VM Manager (patching, inventory, OS config)

Google Cloud VM Manager is a suite of integrated tools designed to automate the management and compliance of large Compute Engine VM fleets. It consists of three capabilities: OS Patch Management (executing scheduled operating system updates, kernel patches, and pre/post-patch script hooks), OS Inventory Management (collecting operating system version, installed packages, kernel revisions, and Common Vulnerabilities and Exposures [CVE] status), and OS Configuration Management (declaratively enforcing installed packages, repositories, and custom guest policies).

While immutable Managed Instance Groups encourage updating golden images and performing rolling replacements, stateful VMs and enterprise batch fleets often rely on in-place patch jobs. Uncoordinated fleet-wide patching can inadvertently reboot all instances concurrently, destroying serving availability.

Problem preview: An operator initiates an ad-hoc VM Manager patch job across the Order API fleet with concurrent rollout mode and automatic reboot enabled. A patch in the upstream package repository breaks the application runtime dependencies, triggering simultaneous reboots across all production VMs and causing total checkout downtime.

Live migration and maintenance policies (migrate vs terminate)

Compute Engine infrastructure undergoes regular physical host maintenance, including hypervisor updates, security patches, hardware repairs, and power management. When Google Cloud maintains the underlying physical host, a virtual machine's maintenance policy dictates its behavior: MIGRATE (default) or TERMINATE.

Under Live Migration (MIGRATE), Compute Engine transparently shifts running VMs to another physical host within the same zone without rebooting the guest OS or interrupting in-flight memory state, with only a sub-second network blackout. However, if an instance is misconfigured to TERMINATE, maintenance events will forcefully stop the VM, destroying transient in-memory state and dropping incoming connections.

Problem preview: A high-throughput in-memory order cache VM is configured with onHostMaintenance: TERMINATE instead of MIGRATE. During a routine Google Cloud host firmware maintenance window, the cache instance is forcefully powered down, dumping all read traffic directly onto the primary Cloud SQL database and triggering severe database CPU saturation.

Sustained use discounts, committed use discounts, rightsizing recommendations

Compute Engine financial governance combines automated usage savings, term commitments, and algorithmic rightsizing. Sustained Use Discounts (SUDs) provide automatic discounts (up to 30%) on eligible machine families (such as N1, N2) when an instance runs for more than 25% of a billing month, requiring zero administrative setup.

Committed Use Discounts (CUDs) provide deep discounts (up to 57–70%) in exchange for 1-year or 3-year term commitments, available as resource-based (specific vCPU/memory in a single region) or flexible spend-based (dollar-per-hour across regions). Concurrently, Cloud Recommender analyzes rolling 8-day CPU and memory telemetry to generate rightsizing recommendations, preventing teams from locking over-provisioned machine types into multi-year commitments.

Problem preview: A procurement team purchases 3-year rigid resource-based CUDs for N1 machine types in us-east1 without consulting engineering, right before the Order API is migrated to N2D instances in us-central1. The company wastes tens of thousands of dollars on unused N1 commitments while simultaneously paying un-discounted on-demand rates in the new region.

2 · Technical discussion of each topic

VM Manager (patching, inventory, OS config)

The three pillars of VM Manager

VM Manager is an agent-based management suite installed on Compute Engine instances via the Google Cloud guest environment (google-osconfig-agent):

  • OS Patch Management: Orchestrates the rollout of OS updates across Linux and Windows instances. Key features include defining maintenance windows, pre-patch and post-patch script hooks (e.g. draining an instance from a load balancer before patching and un-draining after), package exclusion filters, and reboot policies (DEFAULT, ALWAYS, NEVER).
  • OS Inventory Management: Queries installed package versions, OS distribution details, kernel releases, and checks against the National Vulnerability Database (NVD) to generate vulnerability reports in Security Command Center.
  • OS Configuration Management: Deploys OS policies that enforce declarative desired state: ensuring specific monitoring agents or security packages are present, managing custom software repositories, and running compliance check scripts.

Patch rollout modes and blast radius

When executing a patch job, the rollout mode controls concurrency:

Rollout Mode Execution Mechanics Availability Impact
Concurrent (Default) Patches all selected VMs simultaneously High risk of complete service outage if patches trigger reboots or break runtimes
Zone-by-Zone Completes patching in one zone before starting the next Preserves multi-zone service availability if paired with regional load balancing
Rolling (Disruption Budget) Patches in fixed batches (e.g. max 10% of fleet at a time) Recommended for production; preserves serving capacity throughout rollout

Live migration and maintenance policies (migrate vs terminate)

Live migration mechanics

When Google Cloud needs to perform hardware maintenance on a physical server hosting a virtual machine, the KVM hypervisor orchestrates a Live Migration. The migration process:

  1. Identifies a healthy physical target host in the same availability zone.
  2. Copies memory pages and CPU register state incrementally across high-speed internal data center networks while the source VM continues processing requests.
  3. Pauses the source VM for a sub-second blackout window (typically <200ms) to transfer final dirty memory pages.
  4. Transfers network routing state to the new host and resumes execution seamlessly. Storage state remains intact because Persistent Disks are network-attached.

Maintenance policy configuration

VM instances configure maintenance behavior via scheduling parameters:

  • --maintenance-policy=MIGRATE: Enables transparent live migration. Supported on standard general-purpose, compute-optimized, and memory-optimized VM families.
  • --maintenance-policy=TERMINATE: Forces VM termination during host maintenance. Required for VMs with attached GPUs (unless using specific A3/G2 configurations), certain sole-tenant hardware affinity setups, or Spot VMs.
  • --restart-on-failure: Determines whether Compute Engine automatically boots the VM if it terminates due to a hardware crash or maintenance stop.

Sustained use discounts, committed use discounts, rightsizing recommendations

Comparing SUDs, CUDs, and Rightsizing

Optimizing Compute Engine economics requires selecting the right financial mechanism for each workload lifecycle:

Mechanism Commitment Term Discount Level Flexibility Workload Suitability
Sustained Use Discounts (SUD) None (Automatic) Up to 30% incremental High (automatic per region on N1/N2) Dynamic, bursty, or newly launched workloads before commitment
Resource-based CUD 1 or 3 years Up to 57% (standard) / 70% (memory) Low (locked to specific machine series and region) Predictable, stable baseline infrastructure running 24/7
Flexible Spend-based CUD 1 or 3 years Up to 28% (1-yr) / 46% (3-yr) High (applies across regions, series, and Cloud Run/GKE) Organizations undergoing active architectural migrations or cross-region growth
Recommender Rightsizing Immediate change Varies based on downsize High (stop VM, change machine type, restart) Over-provisioned VMs running at <15% average CPU over 8 days

3 · Real-world problems and solutions

The scenarios below represent realistic production engineering incidents involving VM Manager patching, host maintenance configuration, and financial commitment misalignments.

Topic 1 field case — Fleet-wide concurrent patch job triggers mass reboot failure

Situation and business impact

A security compliance auditor issues an urgent directive to patch an OpenSSL vulnerability across all Compute Engine instances at Brightloaf. The operations team configures an ad-hoc VM Manager patch job targeting label service=order-api. The patch job is configured with rollout-mode: CONCURRENT and reboot-config: DEFAULT (which allows automatic reboots when package updates require it).

An upstream OS package update included a breaking dependency modification to glibc that causes the custom compiled Order API binary to fail dynamically on startup. Because the patch job was concurrent, VM Manager applied the patch and rebooted all 8 production Order API instances simultaneously. Upon reboot, the application failed to start on all instances, causing an immediate 100% outage for customer order processing that persisted until engineers could manually roll back the package.

Constraints

  • Critical OS security patches must be applied promptly across production VM fleets.
  • Patch execution must never reduce serving availability below 75% of target capacity.
  • Automated rollback must trigger if instances fail post-patch health verification.

Root cause

Using concurrent rollout mode without a canary or zone-by-zone staging policy. The team executed an un-gated fleet-wide reboot without post-patch health verification or rollback hooks.

Diagnostic sequence

  1. Inspect VM Manager patch job status: gcloud compute os-config patch-jobs describe PATCH_JOB_ID displays COMPLETED_WITH_ERRORS with all 8 instances reporting reboot completed.
  2. Inspect system service status: SSH to an instance reveals systemd status for order-api.service in a CrashLoopBackOff state due to shared library linking errors.
  3. Correlate load balancer metrics: Backend service healthy instance count dropped from 8 to 0 at the exact moment the concurrent patch job triggered reboots.

Defensible solution

Enforce staged, zero-downtime patch policies:

  1. Configure patch jobs to execute Zone-by-Zone or with a disruption budget (max-concurrent: 1).
  2. Implement pre-patch and post-patch scripts: The pre-patch script marks the VM unhealthy to Cloud Load Balancing and waits 30 seconds for connections to drain. The post-patch script tests the local /healthz endpoint before re-enabling the instance.
  3. If the post-patch script fails, the patch job halts immediately, leaving the remaining zones intact and healthy.

Verification

Execute a test patch job with intentional bad packages in staging: verify that the patch job halts after the first instance fails post-patch health verification, leaving surviving nodes healthy and serving traffic with zero gateway errors.

Residual risk

Staged patch jobs take significantly longer to complete across large fleets (hours instead of minutes); security teams must balance patch duration against availability risk.

Topic 2 field case — Inappropriate TERMINATE maintenance policy destroys primary in-memory cache

Situation and business impact

Brightloaf operates a dedicated high-memory Redis caching instance (cache-primary-01) that caches product catalog details, pricing rules, and hot user sessions. During initial VM provisioning, the deployment script set --maintenance-policy=TERMINATE to save on perceived live migration overhead.

At 03:00 AM on Wednesday, Google Cloud initiates routine physical host maintenance on the physical server hosting cache-primary-01. Instead of performing a transparent live migration, Compute Engine forcefully shuts down the instance. All in-memory cached state is wiped. When the VM automatically restarts 4 minutes later with an empty cache, the sudden 100% cache-miss storm slams directly into the backend Cloud SQL database, pushing database CPU to 100% and causing checkout request timeouts.

Constraints

  • The in-memory cache must survive regular Google Cloud physical infrastructure maintenance without downtime.
  • Must avoid cold-cache thunderous herd storms hitting relational databases.
  • Preserve the invariant that replaying an order event never triggers a duplicate fulfillment.

Root cause

The VM maintenance policy was misconfigured to TERMINATE instead of the default MIGRATE. The application was forced to reboot on host maintenance instead of live-migrating transparently.

Defensible solution

Update the VM scheduling configuration to enable Live Migration (gcloud compute instances set-scheduling cache-primary-01 --maintenance-policy=MIGRATE). When Google performs physical host maintenance, memory state, active connections, and cache keys are preserved as the instance transfers to another physical host with only sub-second latency jitter.

Verification

Trigger a simulated host maintenance event (gcloud compute instances simulate-maintenance-event cache-primary-01). Monitor Redis client connections: verify that all in-memory keys remain intact, the VM uptime counter does not reset, and client connection latency remains under 200ms throughout the migration.

Residual risk

Certain specialized hardware configurations (such as GPUs or some sole-tenant configurations) do not support Live Migration and must implement application-level cluster replication (e.g. Redis Sentinel or Memorystore High Availability) to absorb termination events.

Topic 3 field case — Misaligned 3-year resource commitment locks in obsolete machine types

Situation and business impact

To capture an advertised 57% discount, Brightloaf's finance department purchased a 3-year Resource-based Committed Use Discount (CUD) for 200 vCPUs and 800 GB of RAM tied strictly to the N1 machine series in us-east1. Concurrently, the Cloud Recommender service had flagged that the application fleet was oversized by 60%, running at an average of 9% CPU utilization.

Two months later, the software engineering team re-architects the Order API to run on modern N2D and E2 instances in us-central1 to achieve better price-performance and proximity to fulfillment warehouses. Because resource-based CUDs are non-transferable across machine series and non-transferable across regions, the company remains contractually obligated to pay for the 200 vCPUs of N1 capacity in us-east1 every month for the next 34 months, while paying 100% on-demand rates for the active fleet in us-central1.

Constraints

  • Financial commitments must match the actual multi-year engineering roadmap.
  • Must eliminate waste from over-provisioned idle vCPUs before committing capital.
  • Discounts must allow flexibility as workloads shift across regions and compute families.

Root cause

Purchasing rigid resource-based commitments without reviewing Cloud Recommender rightsizing metrics or consulting the architectural roadmap. Committing capital to oversized, legacy machine types in the wrong geographic region.

Defensible solution

  1. Rightsizing first: Apply Cloud Recommender recommendations to downsize existing instances (e.g. from n1-standard-8 to n2d-standard-2) based on verified 8-day telemetry.
  2. Establish true baseline: Measure stable steady-state compute consumption after rightsizing.
  3. Adopt Flexible CUDs: Purchase Flexible Spend-based CUDs (e.g. committing to $50/hour of compute). Flexible CUDs apply automatically across any VM family (N1, N2, N2D, E2, C3), any region, and across Compute Engine, GKE, and Cloud Run.

Verification

Review Google Cloud Cost Management Billing Reports: Confirm that the Flexible CUD credit applies directly to active N2D instances in us-central1, achieving a ~46% overall discount while eliminating unused commitment penalties.

Residual risk

Flexible spend commitments provide slightly lower percentage discounts (~46% for 3-year) compared to rigid resource commitments (~57% for 3-year), but completely mitigate the risk of 100% unutilized waste during architectural changes.

Exercise 1 — VM Manager staged patch job specification with health gates

Goal: Formulate an automated OS patch job using VM Manager with zone-by-zone execution and pre/post-patch health check scripts.

Mode: tabletop design / cloud sandbox · Prerequisites: Day 40 exit artifact.

Preflight

Open day-041-runbook.md. Define the patch scope: Target label env=production,service=order-api; Maintenance window = Sunday 02:00–04:00 UTC; Reboot policy = REBOOT_ALWAYS.

  1. Author the pre-patch script hook. Create pre-patch.sh to drain traffic: 
    #!/bin/bash
# Signal local health check endpoint to return 503 to drain connections
touch /var/run/draining
sleep 30
exit 0
  2. Author the post-patch script hook. Create post-patch.sh to verify service readiness: 
    #!/bin/bash
rm -f /var/run/draining
systemctl restart order-api
# Test local endpoint
for i in {1..12}; do
  if curl -s http://127.0.0.1:8080/healthz | grep "OK"; then
    echo "Service verified post-patch."
    exit 0
  fi
  sleep 5
done
echo "Post-patch health verification failed!"
exit 1
  3. Formulate the declarative patch deployment. Define the gcloud execution command: 
    gcloud compute os-config patch-jobs execute \
  --project=PROJECT_ID \
  --instance-filter-group="labels=env:production,service:order-api" \
  --rollout-mode=ZONE_BY_ZONE \
  --disruption-budget-percentage=25 \
  --pre-patch-linux-executable=pre-patch.sh \
  --post-patch-linux-executable=post-patch.sh \
  --reboot-config=DEFAULT
Expected result

A validated staged patch job specification in day-041-runbook.md proving zero-downtime execution and automated failure gating.

Exercise 2 — Live migration maintenance policy configuration and simulation

Goal: Configure VM scheduling parameters for Live Migration and verify maintenance signal handling.

Mode: tabletop / sandbox · Prerequisites: Exercise 1.

  1. Inspect existing VM scheduling configuration. 
    gcloud compute instances describe INSTANCE_NAME \
  --project=PROJECT_ID \
  --zone=us-central1-a \
  --format="yaml(scheduling)"
  2. Enforce Live Migration. Update the maintenance policy: 
    gcloud compute instances set-scheduling INSTANCE_NAME \
  --project=PROJECT_ID \
  --zone=us-central1-a \
  --maintenance-policy=MIGRATE \
  --restart-on-failure
  3. Simulate host maintenance. Trigger a live migration event and record the metadata server notice behavior: 
    gcloud compute instances simulate-maintenance-event INSTANCE_NAME \
  --project=PROJECT_ID \
  --zone=us-central1-a
    Document in day-041-runbook.md how computeMetadata/v1/instance/maintenance-event signals the guest OS.
Expected result

A verified maintenance policy configuration ensuring running memory persistence across physical host maintenance.

Exercise 3 — Recommender rightsizing evaluation and commitment modeling

Goal: Analyze rolling CPU/memory telemetry, apply rightsizing recommendations, and structure a flexible CUD commitment model.

Mode: financial and telemetry analysis · Prerequisites: Day 8 CPU/memory signal metrics.

  1. Retrieve Recommender rightsizing recommendations. 
    gcloud recommender recommendations list \
  --project=PROJECT_ID \
  --location=us-central1 \
  --recommender=google.compute.instance.MachineTypeRecommender \
  --format="table(content.overview.instance,content.overview.currentMachineType,content.overview.recommendedMachineType)"
  2. Model the rightsizing transition. In day-041-runbook.md, document the downsizing workflow for an oversized VM (n2-standard-8 to n2-standard-2):
    • Graceful service drain via load balancer.
    • Stop instance: gcloud compute instances stop INSTANCE_NAME.
    • Change machine type: gcloud compute instances set-machine-type INSTANCE_NAME --machine-type=n2-standard-2.
    • Start instance and confirm memory headroom (>25% free under peak load).
  3. Formulate the commitment strategy. Calculate the steady-state hourly spend across the rightsized fleet. Structure a 70% baseline commitment using 3-Year Flexible Spend-based CUDs and document the projected 46% net savings.
Expected result / acceptance

A completed day-041-runbook.md linking guest metrics to application symptoms, patch job rollout procedures, live migration configurations, and a rightsizing cost-optimization matrix.

Cleanup and cost

No new chargeable resources are left running. If sandbox test instances were modified, ensure they are stopped or deleted:

gcloud compute instances delete bf-patch-test --zone=us-central1-a --quiet
