Kubernetes architecture: control plane, nodes, etcd, kubelet, kube-proxy

Kubernetes operates on a declarative reconciliation model governed by a split-plane architecture. The control plane consists of the stateless kube-apiserver (the front door handling authentication, authorization, and schema validation), etcd (a distributed, strongly consistent key-value store holding the single source of truth for desired and observed state), kube-scheduler (which assigns unassigned pods to optimal worker nodes based on resource requests and topology constraints), and kube-controller-manager (which executes non-terminating control loops to reconcile actual cluster state toward desired state).

On each worker node, the kubelet communicates with the API server to receive pod specifications and drives the local container runtime (e.g. containerd via CRI), while kube-proxy programs local virtual IP routing rules (via iptables or eBPF in Dataplane V2). When desired and observed state diverge, developers frequently confuse local worker node execution failures with control plane API outages.

Problem preview: After rolling out a new Order API Deployment manifest, developers observe pods stuck indefinitely in ImagePullBackOff and assume the GKE API server has crashed. In reality, the control plane successfully stored desired state in etcd and scheduled the pods, but the worker node kubelet is failing to authenticate against the private Artifact Registry due to a missing Kubernetes imagePullSecret.

Autopilot vs Standard mode (when to choose each)

Google Kubernetes Engine (GKE) offers two operational paradigms: Standard and Autopilot. In GKE Standard, the customer manages the worker node pools, chooses underlying Compute Engine machine families, configures OS images (Container-Optimized OS or Ubuntu), tunes cluster autoscaler thresholds, and pays for the full physical capacity of provisioned node VMs regardless of actual pod allocation.

In GKE Autopilot, Google manages the entire node lifecycle, node security hardening, operating system upgrades, and automated bin-packing. Customers configure only pod manifests and pay strictly for requested pod vCPU, memory, and storage per second. However, Autopilot enforces strict security guardrails—disallowing privileged containers, hostPath volume mounts, and custom kernel modules—which breaks certain legacy or specialized infrastructure tooling.

Problem preview: An operations team attempts to deploy a third-party security daemonset that requires privileged: true and host filesystem access onto a newly provisioned GKE Autopilot cluster. The GKE Autopilot admission controller rejects the pod manifest with a webhook denial, blocking compliance visibility and stalling production migration.

Zonal vs regional clusters (regional for HA control plane)

A GKE cluster's availability is governed by its control plane topology. A Zonal Cluster runs a single control plane replica located in a single availability zone. During automated master upgrades, control plane maintenance, or a zonal facility impairment, the single Kubernetes API server becomes unreachable. Although existing running pods continue to serve traffic, all control plane operations—including horizontal pod autoscaling (HPA), automated pod recreation, and deployment rollouts—completely halt.

A Regional Cluster provisions three replicated control plane masters distributed across three separate zones in the region, fronted by an internal load balancer. Regional clusters provide a 99.95% control plane SLA (compared to 99.5% for zonal) and ensure that scheduled master version upgrades occur rolling, zone-by-zone, with zero interruption to API access.

Problem preview: The production Order API is deployed on a Zonal GKE cluster in us-central1-a; during an unexpected morning traffic surge, Google initiates an automated control plane patch. The single API server goes offline for 12 minutes, preventing the Horizontal Pod Autoscaler from scaling out pods as traffic doubles, causing the surviving pods to crash from memory exhaustion and triggering widespread customer checkout failures.

2 · Technical discussion of each topic

Kubernetes architecture: control plane, nodes, etcd, kubelet, kube-proxy

The declarative reconciliation loop

Kubernetes does not execute imperative execution scripts; it continuously enforces a declarative state loop. An operator or CI/CD pipeline submits a desired state (e.g. replicas: 5) to kube-apiserver. The API server authenticates the caller, checks authorization via RBAC, validates schema against OpenAPI definitions, executes mutating and validating admission webhooks, and writes the object to etcd.

The control flow proceeds asynchronously:

  1. Controller Manager: The Deployment controller observes the new Deployment in etcd and creates a matching ReplicaSet. The ReplicaSet controller detects missing pods and writes 5 unassigned Pod manifests to etcd.
  2. Scheduler: The kube-scheduler continuously watches for Pods with spec.nodeName empty. It filters candidate nodes based on resource requests (CPU, memory), taints/tolerations, and node selectors, ranks the surviving nodes, and issues a Bind call assigning the pod to a node.
  3. Kubelet: The kubelet running on the target node watches the API server. Upon seeing a pod assigned to its node name, it calls the local container runtime (containerd) over the Container Runtime Interface (CRI) to pull container images, set up cgroups and namespaces, attach storage via CSI, configure networking via CNI, and start the application containers.
  4. Kube-proxy: Concurrently, kube-proxy configures kernel packet forwarding (iptables or eBPF maps) so cluster-internal Service virtual IPs route traffic directly to the newly allocated Pod IPs.
Component Plane Primary Function State Storage
kube-apiserver Control Plane REST API entry point; authentication, authorization, validation Stateless (queries etcd)
etcd Control Plane Distributed, consistent key-value store (Raft consensus) Persistent WAL and database
kube-scheduler Control Plane Assigns unscheduled pods to eligible worker nodes Stateless (reads/writes via API)
kube-controller-manager Control Plane Runs reconciliation loops (Deployment, Node, Endpoints) Stateless (reconciles etcd state)
kubelet Worker Node Node agent; manages container lifecycle, probes, and status Local CRI/cgroups state
kube-proxy Worker Node Programs network packet filter rules for Service VIPs Local iptables / eBPF state

Autopilot vs Standard mode (when to choose each)

Shared responsibility and operational boundary

GKE Autopilot shifts operational boundaries significantly compared to GKE Standard:

Operational Area GKE Standard GKE Autopilot
Node Provisioning & Sizing Customer chooses machine type, series, and disk sizes Google automatically provisions nodes sized to fit pods
Node Pool Management Customer defines, scales, and manages node pools No user-visible node pools; fully automated
Billing Metric Billed for provisioned Compute Engine VM core/RAM Billed strictly for pod requested vCPU, RAM, and storage
Security Hardening Customer configures Shielded GKE, COS, and policies Enforced by default: no privileged containers, read-only root FS
Node OS Upgrades Configurable surge, blue-green, or manual maintenance Fully automated rolling upgrades managed by Google Cloud
Custom Daemonsets Full host access, privileged hostPath permitted Restricted; hostPath disallowed without specific volume exceptions

Autopilot security constraints

Autopilot clusters enforce the GKE Hardening Guidelines via built-in admission webhooks:

  • Pods cannot run with securityContext.privileged: true.
  • Containers cannot add dangerous Linux capabilities (e.g. CAP_SYS_ADMIN, CAP_NET_ADMIN).
  • Host namespaces (hostNetwork, hostPID, hostIPC) are blocked.
  • Workloads requiring raw host network capture or hardware driver access must run on GKE Standard.

Zonal vs regional clusters (regional for HA control plane)

Control plane redundancy and maintenance impact

In GKE, Google manages the control plane VMs transparently. However, the geographic placement of those master VMs determines SLA and operational resilience:

  • Zonal Cluster: One control plane replica runs in a single zone. If that zone suffers an infrastructure impairment, or when Google applies Kubernetes master version updates, the API server is unavailable. Running pods on worker nodes continue executing network traffic, but all control operations halt: HPA cannot scale out, crashed pods cannot be rescheduled, and kubectl commands fail. Control plane SLA: 99.5%.
  • Regional Cluster: Three control plane replicas run in three separate zones within the region. An internal load balancer distributes API requests across all three replicas. During master upgrades, replicas are updated sequentially (one zone at a time), ensuring the API server remains continuously available with zero downtime. Control plane SLA: 99.95%.
Dimension Zonal Cluster Regional Cluster
Control Plane Replicas 1 master in 1 zone 3 masters across 3 distinct zones
Control Plane SLA 99.5% availability 99.95% availability
Control Plane Upgrade Downtime API downtime during master restarts (~10–15m) Zero API downtime (rolling master replacement)
HPA / Scaling during Outage Stalled (HPA controller unreachable) Continuous (surviving masters process metrics)
Management Fee Flat cluster fee ($0.10/hr, waived for 1 cluster) Flat cluster fee ($0.10/hr)

3 · Real-world problems and solutions

The scenarios below represent realistic production engineering failure modes involving Kubernetes reconciliation diagnostics, Autopilot security constraints, and control plane topology selection.

Topic 1 field case — Registry credential omission misdiagnosed as control plane API failure

Situation and business impact

During a major release of the Brightloaf Order API, the continuous deployment pipeline applies an updated Deployment manifest specifying image us-central1-docker.pkg.dev/brightloaf-prod/order/api:v2.4.0. Ten minutes after deployment, the on-call engineer notices that order endpoints return stale responses. Running kubectl get pods reveals all 6 new pods in an ImagePullBackOff state.

The engineer incorrectly assumes that the GKE control plane API server is corrupted or failing to schedule workloads and initiates a disruptive cluster control plane reboot. During the 15-minute reboot, API access is lost, while the underlying problem remains untouched: the GKE nodes lacked IAM permission to pull images from the newly created private Artifact Registry repository because Workload Identity was missing a required credential binding. Customer checkout is stalled for 35 minutes due to troubleshooting delays.

Constraints

  • Engineers must diagnose reconciliation failures using structured Kubernetes control loop observability.
  • Must not perform destructive control plane actions when the failure resides in node-level execution.
  • Workloads must preserve the invariant that replaying an order event never triggers duplicate fulfillment.

Root cause

The control plane successfully reconciled desired state, creating ReplicaSets and binding pods to nodes. The failure was strictly localized to the node's kubelet, which encountered an HTTP 403 Forbidden from Artifact Registry due to an unconfigured service account binding. The engineer lacked understanding of the reconciliation boundary between the control plane and the kubelet.

Diagnostic sequence

  1. Inspect pod status: kubectl describe pod POD_NAME immediately reveals under Events: the exact error: Failed to pull image: rpc error: code = Unknown desc = failed to pull and unpack image ... 403 Forbidden.
  2. Check scheduler state: Confirm spec.nodeName is populated, proving kube-scheduler executed successfully.
  3. Check API server state: Confirm API server responds cleanly to queries, proving control plane health.

Defensible solution

Grant the GKE node service account roles/artifactregistry.reader on the target repository, or configure Workload Identity with a Kubernetes service account bound to a Google service account holding registry permissions. Trigger a rollout restart (kubectl rollout restart deployment order-api) to clear the backoff delay.

Verification

Describe the newly spawned pods: verify that Events: displays Successfully pulled image followed by Started container order-api. Pods transition to Running and pass HTTP readiness probes within 30 seconds.

Residual risk

If container images are exceptionally large (>2GB), initial image pull duration may cause temporary timeouts if node disks experience severe I/O throttling.

Topic 2 field case — Privileged security agent blocked by GKE Autopilot admission webhook

Situation and business impact

To satisfy an enterprise cyber-insurance audit, Brightloaf is required to run a proprietary host-level intrusion detection daemonset across all Kubernetes clusters. The cluster was provisioned as GKE Autopilot to minimize maintenance toil for the small operations team.

When applying the daemonset manifest, the Kubernetes API server immediately rejects the submission: admission webhook "autopilot.gke.io" denied the request: securityContext.privileged: true is not allowed in Autopilot. The security team refuses to sign off on production go-live without the agent running, blocking a high-profile multi-million-dollar retail partnership launch scheduled for Monday morning.

Constraints

  • Compliance requires host-level security observability across all running container workloads.
  • Must adhere to Google Cloud Kubernetes hardening guidelines.
  • Must select the defensible cluster operational mode based on workload technical requirements.

Root cause

Architectural mismatch between workload requirements and GKE mode. GKE Autopilot enforces strict security guardrails that prohibit privileged containers, hostPath volume mounts, and custom Linux capabilities. The team selected Autopilot without evaluating legacy daemonset requirements.

Defensible solution

Evaluate the two architectural alternatives:

  1. Preferred: Replace the legacy privileged daemonset with a Google Cloud native managed solution (Security Command Center GKE Container Threat Detection) which monitors runtime events via the hypervisor without requiring privileged pods.
  2. Alternative: If the proprietary agent is legally mandated by contract, provision a GKE Standard regional cluster with a dedicated node pool, enabling privileged: true and host filesystem mounts under explicit custom RBAC controls.

Verification

If deploying native Container Threat Detection: verify event generation in Security Command Center by triggering a benign test event. If deploying GKE Standard: verify the daemonset achieves Running state across all worker nodes and reports healthy heartbeat telemetry to the compliance dashboard.

Residual risk

Operating GKE Standard reintroduces operational toil: the team becomes responsible for node pool sizing, node auto-upgrades, and OS patch management.

Topic 3 field case — Zonal cluster control plane outage stalls HPA during peak surge

Situation and business impact

Brightloaf runs its production Order API on a Zonal GKE cluster located in us-central1-a. At 08:45 AM, as morning breakfast orders surge by 300%, Google Cloud initiates an automated control plane patch on the cluster master.

Because the cluster is zonal, there is only one control plane master VM. The API server goes offline for 11 minutes. While existing worker pods continue serving, the Horizontal Pod Autoscaler (HPA) cannot query the Metrics Server or issue scale-up commands to the API server. Inbound traffic saturates the existing 6 pods; their memory utilization spikes, and the Linux kernel out-of-memory (OOM) killer terminates 4 of the 6 pods. Because the control plane is offline, Kubernetes cannot reschedule or recreate the terminated pods. The remaining 2 pods collapse, resulting in total checkout failure for 15 minutes.

Constraints

  • Cluster control plane must maintain high availability during automated Google Cloud master upgrades.
  • Horizontal Pod Autoscaling must operate continuously without interruption during peak traffic.
  • Preserve the invariant that replaying an order event never triggers a duplicate fulfillment.

Root cause

Deploying a critical production service on a Zonal GKE cluster. A single control plane replica creates a single point of failure that disables autoscaling and pod rescheduling during master maintenance.

Defensible solution

Migrate the production workload to a Regional GKE cluster spanning us-central1-a, us-central1-b, and us-central1-c. Regional clusters maintain three replicated control plane masters behind an internal load balancer with a 99.95% availability SLA. When Google performs master upgrades, the masters are updated rolling, one zone at a time, ensuring continuous API server availability and uninterrupted HPA autoscaling.

Verification

Trigger an intentional master upgrade on a regional test cluster (gcloud container clusters upgrade). Simultaneously run a synthetic load test that forces HPA scale-out: verify that HPA continuously polls metrics, scales pod replicas from 6 to 18, and maintains 100% HTTP 200 responses throughout the upgrade window.

Residual risk

Regional clusters require worker node pools to be distributed across three zones, which can incur cross-zone data transfer costs if pods communicate heavily across zones without topology-aware routing.

Exercise 1 — Tracing declarative reconciliation from manifest to running container

Goal: Step through the Kubernetes reconciliation loop and trace how an image pull failure appears in API telemetry versus node events.

Mode: local cluster (kind/minikube) or GKE sandbox · Prerequisites: Day 41 exit artifact.

Preflight

Open day-042-reconciliation.md. Prepare a minimal deployment manifest test-reconcile.yaml targeting a non-existent or restricted container image.

  1. Apply the manifest. 
    kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reconcile-test
spec:
  replicas: 2
  selector:
    matchLabels:
      app: reconcile-test
  template:
    metadata:
      labels:
        app: reconcile-test
    spec:
      containers:
      - name: test-app
        image: gcr.io/google-samples/invalid-image-tag:v999
EOF
  2. Observe control plane success. Run kubectl get deployment reconcile-test and kubectl get rs. Confirm that the API server accepted the desired state and the ReplicaSet created 2 pods.
  3. Observe node-level failure. Run kubectl describe pod -l app=reconcile-test. Inspect the Events: section. Identify the exact line: Failed to pull image ... ErrImagePull / ImagePullBackOff. Document why the control plane is healthy despite pod failure.
  4. Reconcile to healthy state. Update the image to a valid reference: 
    kubectl set image deployment/reconcile-test test-app=mirror.gcr.io/library/nginx:alpine
    Verify that the kubelet immediately downloads the valid image and pods achieve Running status.
Expected result

A step-by-step reconciliation trace recorded in day-042-reconciliation.md distinguishing control plane state storage from node-level kubelet execution.

Exercise 2 — GKE Autopilot vs Standard operational ownership and cost model comparison

Goal: Construct a comprehensive architectural decision sheet comparing operational responsibility, capability restrictions, and cost profiles between GKE Autopilot and GKE Standard.

Mode: architectural analysis · Prerequisites: Exercise 1.

  1. Map the ownership boundaries. In day-042-reconciliation.md, create a table contrasting: OS updates, node auto-repair, cluster autoscaler tuning, resource bin-packing, and security compliance.
  2. Evaluate cost modeling.
    • Scenario A (GKE Standard): 3 nodes of e2-standard-4 (12 vCPUs, 48 GB RAM). Billed for 100% of VM hours regardless of pod allocation.
    • Scenario B (GKE Autopilot): Workload requests 4 vCPUs and 16 GB RAM total. Billed strictly for 4 vCPUs and 16 GB RAM seconds.
    • Calculate the break-even utilization threshold where Standard becomes cheaper than Autopilot (typically ~65–75% steady-state cluster utilization).
  3. Document the selection policy. State the bright-line rule: "Default to GKE Autopilot for all standard web microservices; mandate GKE Standard only when workloads require privileged security daemonsets or custom kernel configurations."

Exercise 3 — Regional vs Zonal cluster control plane SLA and blast radius analysis

  1. Formulate the Regional GKE creation command.

  --project=PROJECT_ID \

  --release-channel=regular \

  2. Model the control plane maintenance sequence. In day-042-reconciliation.md, document how Google Cloud updates the three regional masters:
