Control plane, data plane, async operations, and desired vs observed state

Every GCP resource operation travels through two distinct subsystems. The control plane handles instructions — it authenticates the caller, evaluates IAM, records the desired state, and issues an operation token. The data plane is the running infrastructure that enforces that state: the hypervisor that starts the VM, the disk subsystem that attaches the volume, the network that enforces firewall rules.

Because these planes are physically and logically separate, a successful control-plane response does not guarantee that the data-plane effect has completed. GCP makes this explicit: most Compute Engine write operations return a long-running operation (LRO) with its own URL and status fields. The resource is not usable until the operation reaches DONE: true and status: RUNNING appears on the instance.

Desired state is what you declared (machine type, image, zone, tags). Observed state is what the data plane has actually established, reported back via a describe or list call. Permission propagation compounds the gap: a newly granted IAM binding can take time to propagate through GCP's authorization infrastructure, so a principal that just received a role may see transient PERMISSION_DENIED errors on the first attempt.

Problem preview: An operator grants a service account the Compute Instance Admin role and immediately issues gcloud compute instances list, receiving PERMISSION_DENIED. Because the operator assumes IAM is instantaneous, they retry with a wider role, inadvertently escalating privilege. Business impact: the service account now holds broader access than intended, violating the principle of least privilege recorded in Day 26's exit artifact.

gcloud VM lifecycle: create, inventory, and delete with error classification

The first time you touch a real cloud resource you encounter a concrete lesson in asynchronous operations: gcloud compute instances create returns immediately with an operation name, not a running VM. You must poll the operation or use --async=false (the default) to block until the resource is ready. Skipping this step means you may attempt to SSH into a VM that is still provisioning.

The error classification discipline is equally important. Before retrying any failed operation, determine whether the error is transient (quota exceeded, resource exhausted, internal error) or terminal (invalid image, wrong zone, missing permission). Retrying a terminal error wastes quota and may create orphaned operations. Check gcloud compute operations describe or look at the operation's httpErrorStatusCode and error.errors[].code fields.

After creation, inventory with gcloud compute instances describe and gcloud compute instances list --filter. After deletion, confirm with an empty list and verify the operation reached DONE. These steps together form the exit evidence required by the roadmap.

Problem preview: After a quota-exceeded error on instance creation, an operator retries without inspecting the operation state, triggering a second creation attempt. The first attempt had already succeeded (the quota check was a transient spike); now there are two VMs. Business impact: double billing and a stale VM that continues running after the lab ends, violating the sandbox budget assumptions from Day 18.

2 · Technical discussion of each topic

Control plane, data plane, async operations, and desired vs observed state

The two-plane model

In GCP, the control plane is the set of management APIs that accept, validate, and durably record resource intent. When you call gcloud compute instances create, the request reaches the Compute Engine API service. The API authenticates your identity (via OAuth 2.0 or service account token), checks IAM bindings against the requested resource and project, applies any applicable organization policy constraints (e.g., constraints/compute.restrictCloudRunRegion), and then writes the desired configuration to GCP's internal resource store. At this point the API returns an operation object — not a running VM.

The data plane is the physical and virtual infrastructure layer: hypervisors, network fabric, storage controllers. A background process watches the resource store and drives the data plane toward the desired state. When the VM is fully allocated, networked, and booted, the data plane marks the operation as complete and updates the resource's status field. Until then, the resource exists in the control plane's records (desired state) but may not be fully operable in the data plane (observed state).

Long-running operations (LROs)

Compute Engine operations are returned as zone-scoped or region-scoped resources accessible via gcloud compute operations describe OPERATION_NAME --zone=ZONE. Key fields:

  • status: PENDING, RUNNING, or DONE
  • progress: 0–100
  • error: present only on failure, contains errors[].code and errors[].message
  • httpErrorStatusCode: HTTP status of the underlying failure (4xx = client error, 5xx = transient)
  • targetLink: the resource URL that will exist when status = DONE

By default, gcloud compute instances create waits synchronously (blocks until DONE). Pass --async to get the operation name immediately and poll manually. This is useful in scripts that create many resources in parallel.

Permission propagation delay

IAM binding changes propagate through GCP's authorization infrastructure. Google's documentation notes that changes can take up to 60 seconds to propagate globally but are typically faster within a region. A principal that just received a role should be tested with a short wait before assuming the binding has not applied. The correct response to a transient PERMISSION_DENIED is to wait and retry with the same principal and scope, not to widen the role.

Desired vs observed state: the diagnostic invariant

When a resource appears healthy in the console but a workload cannot reach it, the likely explanation is a data-plane lag or a network-level constraint that is not reflected in the control-plane resource record. Conversely, when the control plane reports an error but a resource appears to be functioning, the resource may have been partially provisioned — the safest action is to describe the operation, read its error, and decide whether to delete and re-create or repair.

Architecture path: control-plane to data-plane flow

Stage Plane Actor / component Output
1. API call authenticated Control Compute Engine API + IAM Caller identity confirmed; permission checked
2. Org policy evaluated Control Organization Policy Service Constraint pass/fail; request rejected if violated
3. Desired state recorded Control Resource store (internal) Operation object with status PENDING returned to caller
4. Scheduling Control → Data Borgmaster / cluster scheduler Physical host selected; boot disk allocated
5. VM provisioned Data Hypervisor + network fabric VM kernel starts; NIC and firewall rules applied
6. Status reconciled Control Resource store updated Operation status → DONE; instance status → RUNNING
7. Inventory visible Control List/describe API Instance appears in gcloud output with current fields

gcloud VM lifecycle: create, inventory, and delete with error classification

The four-phase VM lifecycle

Every controlled VM operation follows four phases: create, observe, inventory, delete. Each phase has a distinct gcloud command set and a distinct set of failure modes.

Phase 1 — Create

# Minimal disposable VM: e2-micro in us-central1-a
gcloud compute instances create bf-lab-vm \
  --project=PROJECT_ID \
  --zone=us-central1-a \
  --machine-type=e2-micro \
  --image-family=debian-12 \
  --image-project=debian-cloud \
  --no-address \
  --scopes=cloud-platform \
  --labels=env=lab,owner=day34

# Check the returned operation
gcloud compute operations describe OPERATION_NAME \
  --zone=us-central1-a \
  --project=PROJECT_ID

The --no-address flag avoids assigning a public IP — correct for a sandbox lab with no external access requirement. --scopes=cloud-platform gives the instance's default service account access to GCP APIs (narrowed by IAM in production).

Error classification before retrying

Error code / HTTP status Category Retry? Correct action
QUOTA_EXCEEDED / 429 Transient (rate) or terminal (hard quota) Only after checking quota page gcloud compute project-info describe --project=PROJECT_ID to check quotas; request increase or use a different region
RESOURCE_EXHAUSTED / 429 Transient in practice Wait, then retry same zone or try alt zone Use --zone in a different zone; do not widen permissions
PERMISSION_DENIED / 403 Terminal (until policy changes) No — identify principal + scope first Run gcloud auth list, check IAM bindings, wait for propagation
INVALID_ARGUMENT / 400 Terminal (client error) No — fix the request Inspect the error message; correct machine type, image, or zone value
INTERNAL_ERROR / 500 Transient (server-side) Yes — after exponential back-off Describe the operation first; if DONE+error, create fresh; if RUNNING, wait

Phase 2 — Observe the operation

# Wait for the operation (if --async was used)
gcloud compute operations wait OPERATION_NAME \
  --zone=us-central1-a \
  --project=PROJECT_ID

# Describe the instance (desired → observed state)
gcloud compute instances describe bf-lab-vm \
  --zone=us-central1-a \
  --project=PROJECT_ID \
  --format="yaml(name,status,networkInterfaces,machineType)"

Phase 3 — Inventory

# List with a label filter to confirm scope
gcloud compute instances list \
  --project=PROJECT_ID \
  --filter="labels.env=lab AND labels.owner=day34" \
  --format="table(name,zone,status,machineType.machine_type())"

Phase 4 — Delete and confirm

# Delete (--quiet skips interactive prompt in scripts)
gcloud compute instances delete bf-lab-vm \
  --zone=us-central1-a \
  --project=PROJECT_ID \
  --quiet

# Confirm empty — expect zero rows
gcloud compute instances list \
  --project=PROJECT_ID \
  --filter="labels.env=lab AND labels.owner=day34"

Active-identity check (Day 26 prerequisite)

# Who is acting?
gcloud auth list
gcloud config get account

# Which project?
gcloud config get project

# What roles does the acting principal hold?
gcloud projects get-iam-policy PROJECT_ID \
  --flatten="bindings[].members" \
  --filter="bindings.members=user:YOUR_EMAIL"

3 · Real-world problems and solutions

The scenarios below are illustrative examples based on the Day 34 topics. They are not observed production incidents. Numeric values and specific error codes are illustrative; do not treat them as measured results.

Topic 1 field case — Permission propagation misread as a missing role

Situation and business impact

A Brightloaf platform engineer creates a dedicated service account (bf-deploy-sa) for the Order API staging deployment and binds it to the roles/compute.instanceAdmin.v1 role on the bf-staging project. Immediately after the binding, the engineer runs an inventory script using the service account's credentials and receives PERMISSION_DENIED. Assuming the binding was incomplete, the engineer escalates the binding to roles/compute.admin (which includes additional permissions over network and firewall objects). The staging environment now has a service account with broader network access than required by the Order API workload.

Operational and business constraints

  • Day 26 exit artifact established that all service accounts must be scoped to the minimum role required.
  • The staging project budget is monitored; the engineer must not create additional chargeable resources during diagnosis.
  • The identity of the acting principal must match the service account, not the engineer's personal credentials.

Evidence

The engineer captured the PERMISSION_DENIED response from gcloud compute instances list --project=bf-staging run as bf-deploy-sa. The Cloud Audit Log entry shows the caller as the service account with the roles/compute.instanceAdmin.v1 binding already present in the project's IAM policy at the time of the call. The log entry timestamp is within the documented propagation window.

Root cause

IAM binding changes have a documented propagation delay. The binding was recorded at the control plane but had not yet propagated to the authorization infrastructure that evaluates the actual API call. The engineer treated the transient denial as a missing role rather than a propagation lag, then widened the scope without re-testing the original binding.

Diagnostic sequence

  1. After any new IAM binding, wait at least 60 seconds before the first authoritative test.
  2. Run gcloud projects get-iam-policy bf-staging --flatten="bindings[].members" --filter="bindings.members=serviceAccount:bf-deploy-sa@..." to confirm the binding is recorded.
  3. Test the exact operation that failed (not a broader one) — gcloud compute instances list --project=bf-staging --impersonate-service-account=bf-deploy-sa@....
  4. If it still fails after 90 seconds, investigate the specific resource scope, not the role breadth.

Defensible solution

Revert bf-deploy-sa to roles/compute.instanceAdmin.v1. Implement a short programmatic wait in the deployment script after any binding change before the first permission-dependent call. Document the expected propagation window in the runbook.

Verification

After reverting: run the same gcloud compute instances list command as the service account and confirm it succeeds. Pull the Cloud Audit Log entry for the successful call and confirm the role remains roles/compute.instanceAdmin.v1. Confirm no additional bindings were added by a separate get-iam-policy call.

Residual risk

Propagation windows are probabilistic, not guaranteed. Under load or in multi-region projects, the window may extend beyond 60 seconds. The deployment script should use exponential back-off with a bounded retry count rather than a fixed wait.

Topic 2 field case — Blind retry after quota error creates a duplicate VM

Situation and business impact

A Brightloaf platform engineer runs a CI script that creates a single disposable lab VM (bf-lab-vm) in us-central1-a. The script receives a 429 QUOTA_EXCEEDED error response within a few seconds of the create call. The script's error handler unconditionally retries, issuing a second gcloud compute instances create bf-lab-vm command. The first command had already succeeded — the quota error was a rate-limiting spike that the first request passed, and the VM was provisioned. The second create call with the same name fails (the VM already exists), but an unrelated branch of the script has already sent a VM start notification using the operation name from the first call, which is now DONE. Both the first and (erroneously expected) second VMs are tracked, and the cleanup script only deletes the one whose name it records, leaving the original running.

Operational and business constraints

  • The lab VM must be deleted at the end of each run to stay within the sandbox budget from Day 18.
  • No external SSH access; the VM runs with --no-address.
  • The CI script must not create additional project-wide IAM bindings as a workaround.

Evidence

The CI log shows two gcloud compute instances create invocations with the same instance name. The second returns an ALREADY_EXISTS error. The billing report (tabletop: assumed hourly) shows a running e2-micro that was not deleted at end-of-run. An inventory check at the start of the next run reveals the orphaned instance.

Root cause

The script did not inspect the operation state before retrying. A transient 429 does not mean the operation failed — the Compute Engine API accepted the request and the operation may already be in PENDING or DONE state. The correct discipline: on any error, describe the operation (if an operation name was returned) before retrying. If the operation is DONE with no error, the resource exists; do not retry the create.

Diagnostic sequence

  1. On any non-2xx response from instances create, check whether an operation name was included in the response body (it usually is, even on errors).
  2. gcloud compute operations describe OPERATION_NAME --zone=ZONE --project=PROJECT_ID — check status and error.
  3. If status=DONE and no error block, the VM exists; do not retry create. Verify with instances describe.
  4. If status=DONE and error present, the VM does not exist; retry the create.
  5. If status=RUNNING or PENDING, wait and poll — do not retry.

Defensible solution

Rewrite the error handler to inspect the operation state before any retry. Add a post-create inventory check by label to detect any pre-existing VM of the same name. Update the cleanup script to delete by label filter rather than by stored name, so any orphan created under the same label set is caught.

Verification

Run the script with a simulated 429 injected after the first create call (using a mock or a local test harness). Confirm that the script detects the operation as DONE, skips the retry, and the inventory shows exactly one VM. After the run, confirm the label-based cleanup removes it and the inventory is empty.

Residual risk

If the operation name is not returned with the error response (network-level timeout), the script cannot distinguish a submitted-but-unconfirmed request from a rejected one. A pre-create inventory check by a unique idempotency label is a second defence.
