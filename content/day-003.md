<!-- topic-02:overview -->
DNS maps names to typed resource records. A and AAAA records carry IPv4 and IPv6 addresses; CNAME names an alias; MX directs mail; TXT carries text; NS identifies authoritative name servers; SOA describes a zone's authority; PTR maps an address to a name for reverse lookup. TTL tells a caching resolver how long an answer may be reused.

<!-- topic-02:technical -->
An application commonly asks a local resolver for a name. A recursive resolver can answer from cache or query the DNS hierarchy until it reaches an authoritative server for the relevant zone. The authoritative server holds the zone's records; the recursive resolver serves clients and caches responses. A cached answer can remain visible after an authoritative change until its TTL expires, so “the record was updated” and “every client now sees it” are different claims. Negative answers may also be cached under separate rules.

Record types answer different questions. An A or AAAA answer provides an address to try, but does not establish a route, transport connection or healthy application. A CNAME points to another name that must be resolved; MX is about mail delivery rather than web requests. NS and SOA describe delegation and zone authority. PTR is commonly used for reverse lookup; it does not prove ownership or authentication of the forward name. In cloud incidents, checking the requested type, response, TTL, resolver and authoritative zone avoids treating every reachability problem as “DNS is down.”

**Further study:** [RFC 1034 §2.4, DNS components](https://www.rfc-editor.org/rfc/rfc1034#section-2.4) distinguishes resolvers and name servers; [RFC 1035 §3.2, record types and TTL](https://www.rfc-editor.org/rfc/rfc1035#section-3.2) defines the record fields.

<!-- topic-02:problem -->
**Failure:** Brightloaf changes an order API's A record to a new address. Some customers still reach the old endpoint for several minutes, while a direct query of the authoritative server shows the new value.

**Cause:** The customers' recursive resolvers cached the old A answer within its TTL. A correct authoritative update does not invalidate every existing cache immediately. Another possibility is that the application queried AAAA and took a different address family; the requested record type must be recorded.

**Fix:** Compare answers from the affected resolver and the authoritative server, including record type and remaining TTL. Keep the old endpoint healthy during the planned transition, then verify that both A and AAAA paths reach the intended service. Lower TTL *before* a future planned change, allowing earlier cached records to expire. Do not assert that lowering TTL at cutover flushes previous caches.

<!-- topic-03:overview -->
TCP is a connection-oriented byte-stream transport with sequencing, retransmission and flow control. UDP sends datagrams without TCP's connection establishment or delivery guarantees. Ports identify transport endpoints; TCP connection states describe a connection's lifecycle, while socket buffers hold data waiting to be sent or read.

<!-- topic-03:technical -->
TCP's ordinary active open uses a three-message handshake: SYN, SYN-ACK, ACK. The peers exchange initial sequence numbers and reach ESTABLISHED before the application treats the connection as ready. A TCP connection is identified by protocol plus source and destination addresses and ports. The server can listen on one port while many clients connect using distinct source endpoints. After closing, TIME-WAIT is a normal state that helps handle delayed segments from the old connection; it is not automatically a leak or an outage.

TCP preserves ordered bytes for an application but does not preserve application message boundaries. A single send can be read in pieces, and multiple sends can be combined in one read. Socket buffers absorb short differences between producer and consumer rates; full buffers can cause backpressure or blocking, not magic unlimited capacity. UDP keeps datagram boundaries but does not itself guarantee delivery, ordering or duplicate suppression. An application choosing UDP must provide any needed reliability at another layer. A DNS answer that names an IP is separate from the transport handshake, and an established connection is separate from a successful HTTP response.

**Further study:** [RFC 9293 §3.5, TCP connection establishment](https://www.rfc-editor.org/rfc/rfc9293#section-3.5), [RFC 9293 §3.6, TCP connection closing](https://www.rfc-editor.org/rfc/rfc9293#section-3.6), and [RFC 768, UDP delivery model](https://www.rfc-editor.org/rfc/rfc768).

<!-- topic-03:problem -->
**Failure:** A client times out before receiving any HTTP response. The DNS answer is correct, and an operator sees a server process running, so they blame application response formatting.

**Cause:** The trace shows the client's SYN leaving but no SYN-ACK returning. The TCP connection never reaches ESTABLISHED; the application cannot have returned a valid HTTP response over that connection. A missing route, blocked packet or unavailable listener is a more plausible first boundary. If SYN-ACK returned but final ACK was absent, the diagnosis would differ.

**Fix:** Check the source/destination IPs and ports, route in both directions, firewall rules and listening socket. Capture both sides of the handshake if permitted. Once ESTABLISHED is observed, test TLS and then HTTP separately. Do not treat normal TIME-WAIT connections from previous requests as proof that the current request established.

The addresses are documentation examples. Draw one path for each address family. The IPv4 trace reaches ESTABLISHED after the third packet; the IPv6 trace does not prove establishment. Neither trace includes TLS or HTTP evidence.

### Step 2 — Check the state boundary

In a Linux terminal run:

```sh
python3 - <<'PY'
traces = {'IPv4': ['SYN', 'SYN,ACK', 'ACK'], 'IPv6': ['SYN']}
for family, packets in traces.items():
    established = packets[:3] == ['SYN', 'SYN,ACK', 'ACK']
    print(f'{family} handshake complete: {established}')
PY
```

Expected:

```text
IPv4 handshake complete: True
IPv6 handshake complete: False
```

The script classifies a *fixture*, not a live packet capture. Label both socket endpoints and write the next observation needed for the failing IPv6 path: whether a route exists and whether a SYN-ACK returns. State why DNS success is insufficient. **Cleanup:** keep the diagram; no socket, process or cloud resource remains.
