Passthrough Network Load Balancers (external and internal)

Passthrough Network Load Balancers (NLBs) are non-proxied Layer 4 distributed routing engines engineered on Google's Maglev packet forwarder architecture. Unlike reverse proxies that terminate TCP sockets and negotiate separate backend connections, Passthrough NLBs forward raw IP datagrams directly to backend VM network interfaces without altering client IP headers, TCP sequence numbers, or UDP payloads. Utilizing Direct Server Return (DSR), backend virtual machines reply directly to the client's public IP address via the VPC Internet Gateway, eliminating return-path bottleneck constraints and achieving line-rate multi-million packet-per-second throughput with microsecond latency. External and Internal Passthrough NLBs support stateful failover policies, active/backup backend pools, and configurable failover ratio thresholds.

When an engineer configures an External Passthrough Network Load Balancer with port forwarding on 9443 while pointing to backend services listening on 8443, all client SYN packets are rejected with TCP resets because Maglev bypasses port translation and delivers raw packets to the guest OS. In-store point-of-sale registers across 200 retail storefronts fail to synchronize transaction logs, halting $850,000 in afternoon checkout receipts and leaving customer queues stalled at retail registers.

Session affinity, connection draining, timeouts

Production reliability requires deterministic connection lifecycle management during autoscaling scale-down events, blue-green deployments, and rolling instance updates. Session affinity binds sequential requests from a single client to an identical backend instance using 2-tuple client IP hashes, 3-tuple client IP/protocol hashes, 5-tuple hashes, managed HTTP cookies (GENERATED_COOKIE), or custom request headers, balancing stateful application requirements against load distribution uniformity. Connection draining (deregistration delay) establishes a defined grace window (such as 300 seconds) during which instances marked for decommissioning stop receiving new connections while existing in-flight TCP streams and HTTP keep-alive connections terminate naturally. Synchronizing frontend client timeouts, backend service timeouts, and backend web server keep-alive timeouts prevents silent socket terminations and intermittent gateway errors.

When an automated rolling update replaces Compute Engine instances without connection draining configured, active long-running TCP streams and file upload payloads are instantly terminated with ERR_CONNECTION_RESET. Over 450 franchise store managers lose uncommitted end-of-day financial ledger uploads, corrupting batch reconciliations and requiring 16 hours of emergency database repair.

Passthrough Network Load Balancers (external and internal)

Passthrough Network Load Balancers are high-performance, non-proxied Layer 4 load balancers built upon Google's Maglev software-defined distributed packet routing architecture. Unlike Application Load Balancers or Proxy Network Load Balancers that terminate incoming client TCP connections and establish separate backend TCP sessions, Passthrough NLBs route raw IP packets directly to guest virtual machine interfaces without modifying packet payloads, source IP addresses, or source ports.

Maglev Distributed Packet Forwarder Architecture

Maglev runs as a horizontally scalable user-space packet forwarder on commodity Linux servers across Google Points of Presence (PoPs) and data center clusters. Its core design principles provide resilient high-availability and extreme packet processing throughput:

  • Consistent Hashing Lookup Table: Maglev assigns packets to backend targets using a specialized consistent hashing algorithm. Each backend instance generates a random preference list across a lookup table of prime size M (where M is significantly larger than the number of backends, typically hundreds of thousands of entries). When backends are added or removed during autoscaling, minimal disruption is guaranteed: exactly 1/N of keys are remapped, preserving existing connection state across the cluster.
  • Connectionless Packet Steering: Maglev does not maintain synchronized connection state tables across forwarders. Instead, any Maglev node receiving a packet executes the 5-tuple consistent hash (source IP, source port, destination IP, destination port, IP protocol) to deterministically steer the packet to the exact same backend instance. The packet is encapsulated in a lightweight Generic Routing Encapsulation (GRE) or Geneve tunnel and transmitted over Google's Andromeda SDN virtualization fabric directly to the host hypervisor.
  • Direct Server Return (DSR) Mechanics: In traditional proxy architectures, all ingress and egress traffic must traverse the load balancer, creating a severe egress bandwidth choke point. Under Maglev Passthrough NLB, the load balancer VIP is not rewritten to the backend VM's internal IP address; the destination IP header remains the Forwarding Rule VIP. Compute Engine automatically injects a local routing rule into the guest OS kernel (observable via the Linux local routing table), enabling the guest OS to accept packets destined for the VIP on its primary network interface. When the backend application transmits its response (e.g. TCP SYN-ACK or data stream), it sets the packet's source IP to the Forwarding Rule VIP and routes directly to the VPC default gateway. The return packet egresses directly to the client over Google's backbone, completely bypassing Maglev. This asymmetrical routing model delivers near-zero latency, multi-million packet-per-second capability, and unlimited aggregate egress bandwidth bounded only by guest VM network interfaces.

External vs Internal Passthrough NLBs

Google Cloud delivers two distinct flavors of Passthrough NLB:

  • External Passthrough Network Load Balancer: Fronted by a regional external IPv4 or IPv6 address. Terminates internet-facing TCP and UDP traffic, as well as ESP, GRE, ICMP, and ICMPv6 protocols. Backends can be configured as Managed Instance Groups (MIGs), unmanaged instance groups, or Zonal Network Endpoint Groups (NEGs) with GCE_VM_IP endpoints. Modern deployments utilize regional Backend Services rather than legacy Target Pools, unlocking advanced traffic steering, multi-protocol health checks, and stateful failover policies.
  • Internal Passthrough Network Load Balancer: Fronted by an internal RFC 1918 private IPv4 address (or internal IPv6) allocated from a VPC subnet. Provides ultra-low latency east-west load balancing for microservices, internal database clusters (PostgreSQL, MySQL read replicas), and Kubernetes NodePort forwarding. By default, Internal Passthrough NLBs are regional; however, enabling the --allow-global-access flag permits clients located in any Google Cloud region, or connected via Cloud VPN and Cloud Interconnect, to seamlessly access the internal regional VIP.

Failover Policy Mechanics

Passthrough NLBs configured with Backend Services support automated failover policies between an active (primary) backend pool and a standby (backup) backend pool within the same region:

  • Failover Ratio Threshold: Defined by --failover-ratio (a float between 0.0 and 1.0, typically set to 0.25). When the proportion of healthy backend instances in the primary backend service falls below this threshold (e.g. fewer than 25% healthy), the load balancer automatically engages the backup backend service, steering incoming traffic to standby instances.
  • Connection Draining and Drop Mechanics on Failover: The failover policy offers granular control over existing connections via the --drop-drain-connection flag:
    • --no-drop-drain-connection (Default): When failover activates, existing established TCP connections to surviving healthy instances in the primary pool are preserved and drained gracefully, while only new connections are steered to the backup pool. This minimizes user disruption for stable long-lived connections.
    • --drop-drain-connection: When failover triggers, existing connections to the failing primary backend service are immediately severed. This is critical for active-passive database failovers where surviving nodes in the primary pool may be in split-brain or read-only states and must not process further writes.

Health checks (protocols, intervals, thresholds; firewall rules needed for health check ranges)

Health checks represent the foundational reliability engine of Google Cloud load balancing. Centralized probing systems actively query backend endpoints to determine whether an instance is capable of receiving client traffic, automatically evicting degraded instances and preventing traffic black holes.

Prober Mechanisms and Protocol Capabilities

Google Cloud supports five distinct probe protocols configured through Compute Engine health check resources:

  • HTTP Health Checks: Probers transmit an HTTP/1.1 GET request to a specified request path (e.g. /healthz). The check succeeds if the backend returns an HTTP 200 OK response within the timeout window. Optional configurations include validating custom Host headers and matching exact ASCII response body strings (up to 1,024 bytes).
  • HTTPS Health Checks: Probers establish a TLS handshake before issuing the HTTP GET request. The prober does not validate whether the backend's TLS certificate is signed by a public CA, allowing self-signed backend certificates.
  • HTTP/2 Health Checks: Probers establish an HTTP/2 multiplexed stream, verifying high-efficiency gRPC and microservice endpoints natively.
  • TCP Health Checks: Probers execute a standard three-way TCP handshake (SYN, SYN-ACK, ACK) on the target port. A simple handshake constitutes success, or an optional send/receive request-response text string can be validated.
  • SSL Health Checks: Probers negotiate an SSL/TLS handshake over TCP, ensuring the backend socket can negotiate cryptographic parameters successfully.

Liveness vs Readiness Semantics

Architects must carefully delineate between liveness (/healthz) and readiness (/readyz) probe semantics:

  • /healthz (Liveness): Validates that the application runtime process is active, the event loop is responsive, and local memory is intact. This endpoint must execute in less than 5 milliseconds without blocking on downstream dependencies.
  • /readyz (Readiness): Validates that the instance has loaded required in-memory caches, established database connection pools, and is fully prepared to serve customer transactions.
  • Production Anti-Pattern: Connecting a load balancer health check directly to an endpoint that performs heavy database queries (such as SELECT 1 FROM orders) or external third-party API calls. If the central database experiences transient query latency under peak load, the health check will time out across every backend instance simultaneously, triggering a catastrophic cascading failure where the entire cluster is marked UNHEALTHY even though the web servers are functioning perfectly.

Timing Parameters and Distributed Prober Frequency

Health check behavior is governed by four core parameters:

  • check-interval: The time between probe initiations from a single prober (default: 5 seconds).
  • timeout-sec: The duration the prober waits for a response before marking that probe attempt as failed (default: 5 seconds; must be ≤ check-interval).
  • unhealthy-threshold: The number of consecutive probe failures required to transition an instance from HEALTHY to UNHEALTHY (default: 2 or 3).
  • healthy-threshold: The number of consecutive probe successes required to transition an instance back to HEALTHY (default: 2).

Calculating Distributed Prober Load: A common misconception is that a backend receives only one probe every check-interval seconds. Google Cloud deploys redundant, distributed prober fleets located across multiple zones and edge locations to eliminate prober single points of failure. In production, multiple independent probers query each backend VM concurrently. For example, if 3 to 6 distributed probers query an instance with a 5-second interval, the backend VM will receive an incoming probe every 0.8 to 1.6 seconds. Health check handler endpoints must be lightweight and non-allocating to prevent prober-induced CPU exhaustion.

Health Check Prober IP Ranges and Mandatory VPC Ingress Firewall Rules

Health check probes originate from immutable, reserved Google Cloud internal network blocks—not from the load balancer forwarding rule VIP. Backend instances located in private subnets must be reachable from these IP blocks:

Failure Cascade Analysis: If a VPC firewall rule omits any of the required prober ranges, or if a newly provisioned VM template fails to attach the specified network tag (e.g. allow-health-check), the prober SYN packets are dropped by the VPC ingress filter. Once the unhealthy-threshold consecutive timeouts elapse, the load balancer marks all backends UNHEALTHY. For Application Load Balancers, this triggers an immediate planetary HTTP 502 Bad Gateway outage across 100% of incoming user requests.

Session affinity, connection draining, timeouts

Maintaining transaction integrity and state consistency during operational lifecycle changes requires harmonious orchestration of session binding, graceful connection termination, and timeout hierarchies.

Session Affinity Modes and Operational Trade-Offs

Session affinity directs subsequent requests from a specific client to the identical backend instance, essential for stateful web applications, local memory caches, or sequential transaction handshakes:

Affinity Mode Hash Tuple / Mechanism Applicable Load Balancers Architectural Characteristic & Trade-Off
NONE 5-Tuple / Least Request All load balancers Default round-robin distribution; optimal load spreading; no state persistence.
CLIENT_IP 2-Tuple (Source IP, Dest IP) External/Internal Passthrough NLB, ALB Binds client IP to backend. Vulnerability: Corporate NAT gateways with thousands of users appear as one IP, creating severe traffic hotspots on a single VM.
CLIENT_IP_PROTO 3-Tuple (Src IP, Dest IP, Protocol) Passthrough NLB Differentiates between TCP and UDP traffic from the same client IP address.
CLIENT_IP_PORT_PROTO 5-Tuple (Src IP, Src Port, Dest IP, Dest Port, Proto) Internal Passthrough NLB High entropy; distributes independent client sockets across backends while maintaining packet affinity per stream.
GENERATED_COOKIE Injected HTTP Cookie (GCPHTTP_LOADBALANCER_COOKIE) Global & Regional external ALB, Internal ALB The load balancer sets a cryptographically signed cookie with configurable TTL (e.g. affinityCookieTtlSec=1800). Immune to client-side NAT IP consolidation.
HEADER_FIELD Specified HTTP Request Header Application Load Balancers Hashes custom HTTP headers (e.g. X-User-ID or Authorization). Ideal for authenticated API gateways and multi-tenant SaaS routing.
HTTP_COOKIE Existing Application Cookie Application Load Balancers Evaluates an application-defined session cookie name and path, binding requests without injecting additional headers.

Connection Draining (Deregistration Delay) Mechanics

When an instance is removed from a backend service—whether through autoscaler scale-down, an automated rolling instance replacement, or manual backend maintenance—abruptly terminating the instance severs in-flight TCP connections, resulting in client socket resets (ECONNRESET), corrupted multi-part file uploads, and aborted financial transactions.

  • Draining State Transition: Compute Engine transitions the target instance into the DRAINING state. The load balancer control plane immediately excludes the instance from consistent hash rings and round-robin scheduling algorithms; zero new connections are dispatched to the instance.
  • Grace Window (drainingTimeoutSec): Configurable between 0 and 3,600 seconds (default: 0 seconds for unmanaged backends; recommended production setting: 300 seconds). During this grace window, existing established TCP streams, active WebSocket connections, and long-running HTTP transactions are permitted to complete naturally.
  • Instance Deletion Lifecycle: When all active connections terminate naturally, or when the configured drainingTimeoutSec countdown expires, Compute Engine issues an ACPI shutdown signal / SIGTERM to guest processes. The guest OS is granted a standard 30-second shutdown script execution window before a final SIGKILL destroys the virtual machine.

Timeout Alignment and the Keep-Alive Race Condition

A prevalent production failure pattern in Layer 7 load balancing stems from misaligned HTTP timeout hierarchies:

  • Frontend Keep-Alive Timeout: Google Front End (GFE) proxies support client keep-alive timeouts up to 610 seconds, allowing browsers to reuse idle TCP sockets.
  • Backend Service Timeout: Configured on the Google Cloud Backend Service (default: 30 seconds). Governs the maximum duration the load balancer waits for a backend HTTP response before aborting with HTTP 504 Gateway Timeout. For long-polling endpoints, Server-Sent Events (SSE), or large analytical reporting queries, this timeout must be increased (e.g. to 300s or 600s).
  • Backend Web Server Keep-Alive Timeout (The Race Condition): Between the load balancer proxy (GFE/Envoy) and the backend web server (e.g. Nginx, Gunicorn, Apache), persistent TCP keep-alive sockets are maintained. The backend web server's keep-alive timeout MUST be configured slightly larger than the load balancer's keep-alive timeout (Google Cloud ALB maintains an idle keep-alive of 600 seconds):
    • The Failure Sequence: If Nginx has keepalive_timeout 600s; and the ALB also uses 600 seconds, a classic TCP race condition occurs. If Nginx decides to close the idle TCP socket (sending a TCP FIN) at the exact millisecond the ALB dispatches a newly arrived client request into that socket, the request collides with the FIN packet. Nginx rejects the request with a TCP RST, and the ALB returns an intermittent HTTP 502 Bad Gateway (logged in Cloud Logging as backend_connection_closed_before_data_sent_to_client).
    • The Architectural Remedy: Configure the backend web server keep-alive timeout to 650 seconds (greater than 600s). This guarantees that the load balancer proxy always initiates idle socket closures, permanently eliminating keep-alive collision 502 errors.
Apply it

Input: Brightloaf store managers upload daily 150 MB store reconciliation spreadsheets taking up to 180 seconds. During rolling MIG image updates, uploads abort with Broken pipe. In addition, users observe occasional 502 errors on idle pages. Expected: Update the backend service with --draining-timeout=300s and --timeout=300s, and configure backend Nginx instances with keepalive_timeout 650s;. Draining protects active uploads during rolling deployments, while keepalive alignment prevents TCP socket race collisions.

SSL certificates: Google-managed, self-managed, Certificate Manager, SSL policies

Securing public edge endpoints and internal service boundaries requires automated public-key infrastructure (PKI), rapid cryptographic rotation, and enforceable cipher governance.

Google-Managed Certificates vs Self-Managed Certificates

  • Self-Managed SSL Certificates: Customers generate private keys, submit Certificate Signing Requests (CSRs) to external commercial Certificate Authorities (CAs), and upload the signed PEM certificate chain and private key to Compute Engine. Architectural Risk: High operational toil and vulnerability to human error; an expired certificate instantly causes global connection rejections and browser security warnings.
  • Classic Google-Managed Certificates: Fully automated, zero-cost public certificates issued by Google Trust Services (GTS) or Let's Encrypt. Google automatically provisions the certificate and initiates background renewal 30 days prior to expiration. Architectural Limitations: Requires that the public DNS A/AAAA record points directly to the load balancer VIP for HTTP-based ACME domain validation. Does not support wildcard domain names (e.g. *.brightloaf.com), and enforces a ceiling of 100 Subject Alternative Names (SANs) per certificate.

Google Cloud Certificate Manager Architecture

Certificate Manager represents Google Cloud's modern, enterprise-scale TLS orchestration platform, decoupling certificate administration from load balancer target proxies and enabling planetary scale:

  • Certificate Maps & Certificate Map Entries: Rather than attaching individual certificates directly to a Target HTTPS Proxy, the proxy references a unified Certificate Map. The map contains multiple Certificate Map Entries matching specific Server Name Indication (SNI) hostnames or wildcard expressions to designated certificates. This permits dynamically serving tens of thousands of domains and multi-tenant customer hostnames without modifying the load balancer control plane.
  • Wildcard Certificates via DNS Authorization: Certificate Manager overcomes classic limitations by supporting wildcard certificates (e.g. *.brightloaf.com). Verification is accomplished through DNS Authorization: Certificate Manager generates a unique CNAME challenge record (e.g. _acme-challenge.brightloaf.com pointing to a Google domain verification target). Once populated in Cloud DNS, Google Trust Services validates domain control and issues the wildcard certificate before traffic is ever routed to the load balancer VIP.
  • Cloud Private CA Integration: For zero-trust internal enterprise architectures, Certificate Manager integrates directly with Google Cloud Certificate Authority Service (Private CA). Managed internal certificates are issued and rotated automatically against private enterprise root and subordinate CAs, terminating internal mTLS and TLS across Internal Application Load Balancers without exposing private keys.

SSL Policies and Cryptographic Governance

By default, Google Cloud external target proxies accept legacy TLS versions and broad cipher suites to ensure backwards compatibility with older clients. Enterprise landing zones enforce strict cryptographic posture using declarative SSL Policies:

SSL Policy Profile Minimum TLS Version Permitted Cipher Families Blocked Vulnerabilities & Deprecated Ciphers
COMPATIBLE TLS 1.0, 1.1, 1.2 Broadest compatibility; permits older CBC and RSA key exchange ciphers Permits legacy clients; vulnerable to BEAST, POODLE if TLS 1.0 enabled.
MODERN TLS 1.2 PFS (Perfect Forward Secrecy) ciphers: ECDHE-RSA-AES128-GCM, ECDHE-ECDSA-AES256-GCM, CHACHA20-POLY1305 Disables vulnerable CBC ciphers, RC4, 3DES, and static RSA key exchange. Meets PCI-DSS standards.
RESTRICTED TLS 1.2 Strict cipher subset: AES-128/256-GCM and CHACHA20-POLY1305 with ECDHE Rejects older enterprise clients and payment terminals lacking ECDHE support.

Passthrough NLB Port Mismatch & Failover Drain Flap in Point-of-Sale Fleet · field case

Situation and impact: Brightloaf's retail operations launched an in-store Point-of-Sale (POS) synchronization daemon across 200 retail storefronts nationwide, listening on TCP port 9443. The infrastructure team provisioned an External Passthrough Network Load Balancer with a forwarding rule on port 9443, but configured the backend service to target port 8443 under the false assumption that Maglev would perform Port Address Translation (PAT). Furthermore, an aggressive failover policy was attached with --drop-drain-connection enabled. All POS registers failed to connect, throwing immediate TCP connection reset errors and triggering false failovers that severed active store manager sessions, stalling $850,000 in retail transactions during peak afternoon sales.

Constraints: Must preserve low-latency Direct Server Return without proxy serialization; register firmware is hardcoded to connect to port 9443; cannot insert intermediary proxy instances due to latency budgets; backend failover must not drop surviving healthy connections.

Diagnosis and root cause: Protocol packet captures on the backend VMs revealed incoming TCP SYN packets arriving with destination port 9443 unaltered. Because Maglev is a non-proxied passthrough forwarder operating on DSR, it does not rewrite TCP ports; packets reach the guest OS virtual NIC with the exact destination port transmitted by the client. Since the guest application daemon was bound only to 0.0.0.0:8443, the Linux kernel rejected incoming SYN packets with TCP RST. Concurrently, transient probe timeouts caused the active pool health ratio to momentarily dip below 0.25; because --drop-drain-connection was set, Maglev immediately terminated all established sessions rather than draining them gracefully.

Defensible remediation: 1. Reconfigured the backend application systemd unit to bind directly to TCP port 9443. 2. Aligned the Backend Service and TCP Health Check port definitions to 9443. 3. Updated the Failover Policy on the Backend Service with --failover-ratio=0.25 and --no-drop-drain-connection, ensuring established sessions to healthy instances persist during standby failovers.

Verification and residual risk: Verified using ss -tulpn | grep 9443 on backend VMs and validating end-to-end TCP handshakes from remote POS clients. Residual risk: If a local host firewall (e.g. ufw or iptables) within the guest OS blocks port 9443, handshakes will still be dropped even though VPC firewalls are clear.

VPC Security Hardening Dropping Health Probers Triggering Global 502 Outage · field case

Situation and impact: During a scheduled infrastructure security hardening window, Brightloaf applied a strict default-deny firewall rule (priority 65000) across the production Shared VPC. Within 60 seconds, the Global external Application Load Balancer began returning HTTP 502 Bad Gateway to 100% of global user traffic. The primary e-commerce web platform and mobile API went completely dark worldwide for 42 minutes during peak hours, generating 3,800 customer support escalations and stranding $280,000 in active checkout carts.

Constraints: Must maintain zero-trust security posture; cannot grant open internet ingress to private backend subnets; backends must only accept authenticated proxy traffic and legitimate Google health probers.

Diagnosis and root cause: Cloud Logging and Cloud Monitoring revealed that all 120 healthy backend instances across us-east4-a and us-east4-b transitioned to UNHEALTHY simultaneously. The new default-deny firewall rule lacked an exception for Google's immutable health check prober CIDR blocks: 35.191.0.0/16 and 130.211.0.0/22. Because prober TCP SYN packets were dropped at the VPC boundary, the prober timeout (5s) expired across 3 consecutive cycles. When every backend instance in a backend service is marked UNHEALTHY, Google Front End proxies return an immediate 502 Bad Gateway to clients.

Defensible remediation: 1. Provisioned a high-priority (priority 1000) VPC ingress firewall rule explicitly permitting TCP traffic on port 8080 from prober ranges 35.191.0.0/16 and 130.211.0.0/22. 2. Targeted the firewall rule strictly to backend instances using the network tag allow-health-check. 3. Within two probe cycles (10 seconds), backend health status transitioned from UNHEALTHY to HEALTHY, and the global ALB immediately resumed normal traffic serving.

Verification and residual risk: Verified using the backend service health status API to confirm all instances transitioned to healthState: HEALTHY. Residual risk: Regional External and Internal ALBs also require ingress traffic from the regional proxy-only subnet CIDR; if the proxy subnet is blocked, Envoy proxies cannot forward user requests even if health checks report healthy.

Abrupt MIG Rolling Update Terminating 450 In-Flight Ledger Streams (0s Draining) & Keep-Alive Race · field case

Situation and impact: Brightloaf franchise store managers submit large daily revenue reconciliation spreadsheets (50 MB to 200 MB) through an enterprise billing portal, requiring 60 to 180 seconds to stream. During an automated CI/CD deployment that triggered a rolling update of the backend Managed Instance Group, 450 store managers experienced abrupt upload failures with ERR_CONNECTION_RESET and Broken pipe. Corrupted database ledger fragments triggered audit compliance alarms, requiring 16 hours of emergency manual reconciliation. In addition, users reported intermittent 502 Bad Gateway errors on idle web pages throughout the day.

Constraints: Must execute zero-downtime rolling updates; large file uploads cannot be fragmented across HTTP chunk boundaries; cannot pause deployments during business hours; must eliminate idle socket 502 errors.

Diagnosis and root cause: Investigation identified two compounded architectural misconfigurations: 1. Zero Connection Draining Delay: The Backend Service had connection draining configured with a default timeout of 0 seconds (disabled). When Compute Engine initiated rolling replacement of VM instances, it issued immediate ACPI shutdown signals to instances actively processing 150 MB upload streams. Sockets were killed instantly. 2. Keep-Alive Race Condition: The backend Nginx web servers were configured with keepalive_timeout 600s;, matching the ALB idle keep-alive timeout of 600s. When Nginx closed an idle keep-alive socket at the exact moment the load balancer dispatched a new HTTP request, the request was rejected with TCP RST, producing intermittent 502 errors.

Defensible remediation: 1. Configured connection draining on the Backend Service with --draining-timeout=300s (5 minutes), providing ample grace time for 180-second file uploads to conclude cleanly. 2. Reconfigured the backend Nginx keep-alive timeout to 650 seconds (exceeding the ALB 600s timeout by 50 seconds), guaranteeing that the load balancer proxy always initiates socket retirement and eliminating the TCP race condition. 3. Implemented proper SIGTERM handling in the container runtime, pausing new request intake and completing in-flight streams before process termination.

Verification and residual risk: Rehearsed in staging by generating synthetic 150 MB upload streams and triggering a rolling MIG restart; 100% of uploads returned HTTP 201 Created. Residual risk: Excessively long draining timeouts (e.g. 1 hour) can stall emergency security rollouts; draining timeouts must align with the 99th percentile request processing duration.

Expired Self-Managed SSL Certificate on Checkout Domain Halting Global Commerce · field case

Situation and impact: At midnight UTC on Sunday, Brightloaf's primary payment and checkout domain (checkout.brightloaf.com) began displaying critical browser security warnings: NET::ERR_CERT_DATE_INVALID. Automated payment webhook calls from Stripe, Adyen, and PayPal immediately aborted TLS handshakes, refusing to deliver payment authorizations. The commercial SSL certificate had expired. Because the certificate had been purchased manually from an external commercial CA and uploaded as a self-managed resource, the single security operations engineer who held CA console credentials was off-grid on personal leave. Global commerce halted for 5.5 hours, forfeiting $1.4 million in checkout revenue.

Constraints: Must eliminate manual certificate renewal tracking permanently; must support wildcard domain coverage (*.brightloaf.com); must automate certificate validation without requiring production load balancer VIP DNS downtime; must enforce modern cipher suites.

Diagnosis and root cause: The enterprise was utilizing a self-managed SSL certificate attached to the global Target HTTPS Proxy. The manual expiration tracking spreadsheet failed to flag the Sunday renewal. Furthermore, classic Google-managed certificates could not be adopted directly because the domain architecture required wildcard coverage (*.brightloaf.com), which classic managed certificates do not support.

Defensible remediation: 1. Migrated TLS lifecycle governance to Google Cloud Certificate Manager. 2. Created a DNS Authorization resource in Certificate Manager, obtaining an automated challenge CNAME record (_acme-challenge.brightloaf.com). 3. Created the CNAME record in Cloud DNS, proving domain ownership to Google Trust Services. 4. Created a Google-managed wildcard certificate targeting *.brightloaf.com referencing the DNS authorization. 5. Bound the certificate to a Certificate Map, linked a Certificate Map Entry to the target hostname, and attached the map to the Target HTTPS Proxy. 6. Applied a modern SSL Policy with --min-tls-version=1.2 and --profile=MODERN, permanently securing TLS 1.3 handshakes with autonomous 30-day pre-expiry auto-renewals.

Verification and residual risk: Validated domain issuance status using the Certificate Manager resource details showing status ACTIVE. Residual risk: DNS authorization requires persistent retention of the _acme-challenge CNAME in Cloud DNS; if the DNS record is deleted, automated background certificate renewals will fail 30 days prior to certificate expiration.

Exercise 1: Deploy an External Passthrough Network Load Balancer with Failover Policy

Goal: Deploy a Regional External Passthrough NLB operating with Direct Server Return, configure an active and backup backend service, and verify failover threshold policies.

Mode: production practice · Prerequisite: Day 53 exit artifacts.

  1. Reserve a Regional Static External IP Address: 
    gcloud compute addresses create nlb-static-ip \
  --region=us-east4
  2. Create a Regional TCP Health Check: 
    gcloud compute health-checks create tcp nlb-tcp-check \
  --region=us-east4 \
  --port=9000 \
  --check-interval=5s \
  --timeout=3s \
  --healthy-threshold=2 \
  --unhealthy-threshold=2
  3. Create Primary and Backup Regional Backend Services: 
    gcloud compute backend-services create nlb-primary-svc \
  --load-balancing-scheme=EXTERNAL \
  --protocol=TCP \
  --region=us-east4 \
  --health-checks=nlb-tcp-check \
  --health-checks-region=us-east4
    gcloud compute backend-services create nlb-backup-svc \
  --load-balancing-scheme=EXTERNAL \
  --protocol=TCP \
  --region=us-east4 \
  --health-checks=nlb-tcp-check \
  --health-checks-region=us-east4
  4. Configure Failover Policy on Primary Backend Service: Set failover ratio to 25% and preserve healthy active sessions: 
    gcloud compute backend-services update nlb-primary-svc \
  --region=us-east4 \
  --backup-service=nlb-backup-svc \
  --failover-ratio=0.25 \
  --no-drop-drain-connection
  5. Create Regional Forwarding Rule: 
    gcloud compute forwarding-rules create nlb-forwarding-rule \
  --load-balancing-scheme=EXTERNAL \
  --address=nlb-static-ip \
  --region=us-east4 \
  --backend-service=nlb-primary-svc \
  --ports=9000
  6. Verify Forwarding Rule and Failover Policy Details: 
    gcloud compute forwarding-rules describe nlb-forwarding-rule \
  --region=us-east4 \
  --format="yaml(name,IPAddress,portRange,loadBalancingScheme,backendService)"
    gcloud compute backend-services describe nlb-primary-svc \
  --region=us-east4 \
  --format="yaml(failoverPolicy)"
Expected result / acceptance

The Forwarding Rule provisions with scheme EXTERNAL on port 9000. The failover policy reports failoverRatio: 0.25 and dropDrainConnection: false. Packets steer via Maglev DSR directly to backend instances without proxy termination.

Troubleshooting

Ensure backend virtual machines run listener daemons bound to 0.0.0.0:9000; passthrough NLBs do not perform port translation (PAT).

Cleanup and cost

Delete forwarding rules, backend services, health checks, and reserved IP address when testing is complete.

Exercise 2: Create Multi-Protocol Health Checks and Ingress Prober Firewall Rules

Goal: Deploy an HTTP health check with custom request path and timing parameters, configure the mandatory Google prober firewall rule, and inspect health status.

Mode: production practice · Prerequisite: Day 53 exit artifacts.

  1. Create Advanced HTTP Health Check with Host Header and Custom Path: 
    gcloud compute health-checks create http app-health-check \
  --port=8080 \
  --request-path=/healthz \
  --host=health.brightloaf.com \
  --check-interval=5s \
  --timeout=3s \
  --healthy-threshold=2 \
  --unhealthy-threshold=3 \
  --global
  2. Create Ingress VPC Firewall Rule for Google Prober CIDR Blocks: 
    gcloud compute firewall-rules create allow-health-check-ingress \
  --network=prod-shared-vpc \
  --action=ALLOW \
  --direction=INGRESS \
  --priority=1000 \
  --source-ranges=35.191.0.0/16,130.211.0.0/22 \
  --rules=tcp:8080 \
  --target-tags=allow-health-check
  3. Verify Distributed Prober Frequency and Inspect Backend Health: 
    gcloud compute backend-services get-health web-backend-svc \
  --global \
  --format="table(status.healthStatus[].instance,status.healthStatus[].healthState)"
  4. Simulate Probe Failure and Observe Status Transition: Stop the health check listener on one VM: 
    sudo systemctl stop healthz.service

    Wait 15 seconds (3 probe cycles) and re-query health status; observe that the instance transitions to UNHEALTHY while the remaining instances continue serving traffic.

Expected result / acceptance

Firewall rule permits prober CIDR blocks 35.191.0.0/16 and 130.211.0.0/22 on port 8080. Health status confirms state HEALTHY under normal operation and transitions cleanly to UNHEALTHY upon listener failure.

Troubleshooting

If instances report UNHEALTHY, confirm that the guest application is listening on 0.0.0.0:8080 rather than localhost 127.0.0.1:8080 and that the VM instance has the allow-health-check network tag attached.

Cleanup and cost

Restart the health service and retain the firewall rule as part of the production VPC baseline.

Exercise 3: Configure Connection Draining, Session Affinity, and Keep-Alive Timeout Tuning

Goal: Update a backend service with a 300-second connection draining timeout, cookie-based session affinity, and align backend server keep-alive timeouts to 650s.

Mode: production practice · Prerequisite: Day 53 exit artifacts.

  1. Configure Connection Draining and Generated Cookie Affinity: 
    gcloud compute backend-services update web-backend-svc \
  --global \
  --draining-timeout=300s \
  --session-affinity=GENERATED_COOKIE \
  --affinity-cookie-ttl=1800
  2. Verify Backend Service Configuration: 
    gcloud compute backend-services describe web-backend-svc \
  --global \
  --format="yaml(connectionDraining.drainingTimeoutSec,sessionAffinity,affinityCookieTtlSec)"
  3. Configure Backend Nginx Keep-Alive Timeout (Prevent Race 502s): Create or update Nginx configuration to set keepalive higher than the ALB 600s idle timeout: 
    cat << 'EOF' | sudo tee /etc/nginx/conf.d/keepalive.conf
# Set keepalive timeout to 650s to exceed Google Cloud ALB 600s timeout
keepalive_timeout 650s;
keepalive_requests 10000;
EOF
sudo nginx -t && sudo systemctl reload nginx
  4. Initiate Rolling Action Restart and Monitor Draining Transition: 
    gcloud compute instance-groups managed rolling-action restart order-app-mig-east4 \
  --region=us-east4 \
  --max-unavailable=1

    Monitor instance states during the rollout, verifying that instances enter DRAINING state and allow active connections to finish before termination.

Expected result / acceptance

Backend service confirms drainingTimeoutSec: 300 and sessionAffinity: GENERATED_COOKIE. Nginx keepalive is verified at 650s. Zero in-flight connection drops or 502 race errors during rolling replacement.

Troubleshooting

Verify that client requests preserve cookies across sequential API invocations to test session affinity consistency.

Cleanup and cost

No extra GCP infrastructure charges are incurred for connection draining or session affinity.

Exercise 4: Provision Wildcard TLS with Certificate Manager and Enforce Modern SSL Policy

Goal: Deploy a modern SSL Policy enforcing TLS 1.2 minimum with the MODERN profile, create a DNS Authorization in Certificate Manager, and issue a Google-managed wildcard certificate.

Mode: production practice · Prerequisite: Day 53 exit artifacts.

  1. Create Modern SSL Policy: Enforce modern PFS cipher suites and disable insecure legacy ciphers: 
    gcloud compute ssl-policies create strict-modern-ssl-policy \
  --profile=MODERN \
  --min-tls-version=1.2 \
  --global
  2. Create DNS Authorization in Certificate Manager: 
    gcloud certificate-manager dns-authorizations create brightloaf-dns-auth \
  --domain="brightloaf.com" \
  --location=global
  3. Retrieve ACME DNS Challenge Record: 
    gcloud certificate-manager dns-authorizations describe brightloaf-dns-auth \
  --location=global \
  --format="yaml(dnsResourceRecord)"

    Populate the designated _acme-challenge CNAME in Cloud DNS.

  4. Provision Google-Managed Wildcard Certificate: 
    gcloud certificate-manager certificates create brightloaf-wildcard-cert \
  --domains="brightloaf.com,*.brightloaf.com" \
  --dns-authorizations=brightloaf-dns-auth \
  --location=global
  5. Create Certificate Map and Map Entry: 
    gcloud certificate-manager maps create brightloaf-cert-map \
  --location=global
    gcloud certificate-manager maps entries create brightloaf-wildcard-entry \
  --map=brightloaf-cert-map \
  --certificates=brightloaf-wildcard-cert \
  --hostname="*.brightloaf.com" \
  --location=global
  6. Bind Certificate Map and SSL Policy to Target HTTPS Proxy: 
    gcloud compute target-https-proxies update web-target-https-proxy \
  --certificate-map=brightloaf-cert-map \
  --ssl-policy=strict-modern-ssl-policy
  7. Verify TLS Handshake and Cipher Negotiation: 
    openssl s_client -connect api.brightloaf.com:443 -servername api.brightloaf.com -tls1_3
Expected result / acceptance

The Certificate Map binds the wildcard certificate to the proxy. The SSL Policy restricts handshakes to TLS 1.2+ with modern PFS ciphers. The certificate auto-renews 30 days prior to expiration via DNS authorization.

Troubleshooting

Ensure the _acme-challenge CNAME record in Cloud DNS resolves globally before creating the certificate; DNS propagation delays can hold certificate status in PROVISIONING.

Cleanup and cost

Delete test certificates, certificate maps, and SSL policies when no longer required.
