1 · Topics of the day

Day 101 establishes the foundational architecture for enterprise zero-trust remote access and workforce identity governance. Architects analyze the transition from legacy VPNs and static credentials to modern Workforce Identity Federation (WIF) with external identity providers (IdPs), enterprise Cloud Identity administration with Context-Aware Access (CAA), and Identity-Aware Proxy (IAP) for web application perimeter defense and secure TCP tunneling.

Exit evidence: Engineers master Workforce Identity Federation pool and provider configuration with SAML 2.0 / OIDC attribute mapping, Context-Aware Access device posture enforcement with FIDO2 security key policies, and Identity-Aware Proxy deployment with cryptographic backend JWT validation and zero-public-IP VM access.

1. Workforce Identity Federation (external IdPs for employees)

Workforce Identity Federation enables organizations to extend their external identity provider (IdP)—such as Microsoft Entra ID (Azure AD), Okta, or Ping Identity—directly into Google Cloud without synchronizing user identities or maintaining duplicate credentials in Cloud Identity. External employees, contractors, and partner personnel authenticate using their existing corporate credentials via SAML 2.0 or OpenID Connect (OIDC). Google Cloud Security Token Service (STS) validates the external identity assertions, applies attribute mappings and CEL attribute conditions, and issues short-lived federated credentials granting access to Google Cloud console, gcloud CLI, and Cloud APIs.

Problem preview: An enterprise onboards 1,200 external auditors via SAML federation; due to missing attribute conditions, an auditor belonging to an external 'SecOps' group matches an internal production role binding, inadvertently gaining full administrative access across the production VPC.

2. Cloud Identity

Cloud Identity provides enterprise identity and access management (IAM) as a service, decoupling user directory management from Google Workspace. It enables organizations to provision user accounts, enforce security policies, manage corporate devices, and configure single sign-on (SSO) with third-party identity providers. Crucially, Cloud Identity integrates natively with Access Context Manager to enforce Context-Aware Access (CAA), granting access based on contextual parameters such as IP address, device security posture (screen lock, disk encryption, minimum OS version), and geographic location.

Problem preview: An engineering director's laptop is compromised with malware; despite having valid MFA credentials, Context-Aware Access intercepts the connection because the device's disk encryption has been deactivated.

3. Identity-Aware Proxy (IAP) for zero-trust access to apps and TCP forwarding to VMs

Identity-Aware Proxy (IAP) establishes a zero-trust security perimeter around HTTP/HTTPS applications and administrative TCP ports (such as SSH on port 22 and RDP on port 3389). Instead of relying on traditional perimeter VPNs or public IP addresses, IAP intercepts incoming requests at the Google Cloud edge. For web applications behind an External Application Load Balancer, IAP validates the user's identity, group memberships, and context-aware device posture before proxying traffic, attaching a cryptographically signed JSON Web Token (`x-goog-iap-jwt-assertion`). For administrative VM access, IAP TCP forwarding creates an authenticated, encrypted WebSocket tunnel from the local client directly to private instance IP addresses via Google's dedicated forwarding netblock `35.235.240.0/20`.

Problem preview: An attacker on an internal corporate network attempts to spoof user identities to access a sensitive payroll API; because the backend verifies the cryptographic ECDSA signature on `x-goog-iap-jwt-assertion`, forged plaintext headers are immediately discarded.

1. Workforce Identity Federation (external IdPs for employees): technical mechanics

1. Workforce Identity Federation Architecture

  • Workforce Pools: Top-level Google Cloud resource (locations/global/workforcePools/[pool-id]) that manages the federation relationship.
  • OIDC & SAML 2.0 Providers: Configured within the pool with provider metadata (issuer URI, client ID, JWKS keys, or SAML metadata XML).
  • Attribute Mappings: Maps external IdP assertion claims to Google Cloud identity attributes (google.subject, google.groups, google.display_name).
  • Attribute Conditions: Common Expression Language (CEL) expressions evaluated by STS to restrict federation (e.g. assertion.tid == 'approved-azure-tenant-id').

2. Authentication & Credential Exchange Flow

  1. User initiates login via gcloud or Console: gcloud auth login --cred-file=workforce-config.json.
  2. User is redirected to external IdP, completes MFA, and receives a signed SAML Response or OIDC ID token.
  3. gcloud submits the external token to Google Cloud STS (sts.googleapis.com/v1/token).
  4. STS verifies the cryptographic signature against the IdP's JWKS endpoint.
  5. STS evaluates attribute conditions; if approved, it mints a short-lived federated token.
  6. IAM evaluates role bindings granted to principalSet://iam.googleapis.com/locations/global/workforcePools/[pool-id]/group/[group-name].

  • What is the primary architectural advantage of Workforce Identity Federation over traditional Google Cloud Directory Sync (GCDS)?

2. Cloud Identity: technical mechanics

1. Cloud Identity Directory & Single Sign-On

  • User Lifecycle: Provisioned via Google Cloud Directory Sync (GCDS) from Active Directory or automated SCIM connectors from Okta.
  • SAML 2.0 Inbound SSO: Delegated authentication to corporate IdP while Cloud Identity maintains user profile stubs.
  • 2-Step Verification (2SV): Policy controls allowing enforcement of FIDO2/WebAuthn security keys, disabling insecure SMS/voice fallbacks.

2. Context-Aware Access (CAA) Architecture

  • Access Context Manager: Central policy engine defining Access Levels across organizations.
  • Contextual Attributes: Evaluates device OS (device.os_type), encryption status (device.is_encrypted), screen lock (device.is_screen_lock_enabled), and corporate ownership.
  • Endpoint Verification: Chrome extension and lightweight native agent that reports real-time device health to Google Front End (GFE).
  • CEL Policy Expressions: Written in Common Expression Language (e.g., device.is_encrypted && device.os_version >= '14.0').

Architectural evaluation questions

  • Which combination of Cloud Identity features provides the strongest defense against adversary-in-the-middle (AiTM) phishing attacks?
  • What happens when a user attempts to access the Google Cloud Console from a corporate laptop whose full-disk encryption was disabled?
  • How does Google Cloud Directory Sync (GCDS) handle passwords when synchronizing Active Directory to Cloud Identity?

Further study: Google Cloud Identity: SSO, 2FA, and Context-Aware Access architecture.

3. Identity-Aware Proxy (IAP) for zero-trust access to apps and TCP forwarding to VMs: technical mechanics

1. IAP for Web Applications (HTTPS)

  • Traffic Flow: Client -> External ALB -> IAP Policy Engine -> Backend Service (GCE, GKE, Cloud Run).
  • Signed JWT Assertion: IAP strips any client-supplied x-goog-iap-jwt-assertion header and injects a freshly signed JWT.
  • JWT Verification Requirements: Backends must verify: (1) Token signature against Google public keys (https://www.gstatic.com/iap/verify/public_key-jwk), (2) Audience (aud) matches /projects/[project-num]/global/backendServices/[backend-id], (3) Issuer is https://cloud.google.com/iap, (4) Expiry (exp) is current.

2. IAP TCP Forwarding for Administrative Access

  • Zero Public IPs: Target VMs have only private IP addresses; no public IPv4 addresses assigned.
  • Forwarding IP Range: Google forwarder netblock 35.235.240.0/20.
  • VPC Firewall Ingress Rule: Ingress rule allowing TCP port 22/3389 strictly from source range 35.235.240.0/20.
  • Tunnel Invocation: <kbd>gcloud compute ssh [instance-name] --tunnel-through-iap --zone=[zone]</kbd>.

Architectural evaluation questions

  • Why MUST backend web services behind Identity-Aware Proxy validate the cryptographic signature on the `x-goog-iap-jwt-assertion` header?
  • What is the exact source IP CIDR range that must be permitted in VPC firewall rules for IAP TCP forwarding to reach private VMs?
  • Which IAM role must be granted to an engineer to allow them to establish an SSH session through IAP TCP forwarding?

Further study: Google Cloud IAP: Zero-trust web application proxy and TCP tunneling.

The following field cases analyze real-world production security incidents and zero-trust perimeter failures: a cross-organizational privilege leak where an enterprise onboarding 3,000 merger contractors misconfigured Workforce Identity Federation attribute mappings, allowing contractors with identical group names to assume Cloud Security Administrator privileges, an executive account takeover caused by phishing an SMS-based 2-Step Verification code because Cloud Identity had not enforced mandatory FIDO2 hardware security keys or Context-Aware Access device health gates, and a lateral movement exploit where an attacker on an internal corporate network bypassed IAP authentication by directly injecting a forged plaintext header because backend microservices failed to cryptographically verify the `x-goog-iap-jwt-assertion` signature. Each case provides verbatim logs, terminal transcripts, diagnostic sequences, root cause analysis, defensible remediations, and dual-lane failed/corrected flow diagrams.

1. Workforce Identity Federation (external IdPs for employees) · field case

Enterprise scenario: An external contractor from an acquired company assumed the `roles/resourcemanager.organizationAdmin` role upon first login via gcloud.

Constraints: M&A integration required immediate gcloud access for 3,000 contractor developers without synchronizing directories.

Evidence:

Security Token Service exchange audit log:

{
  "protoPayload": {
    "serviceName": "sts.googleapis.com",
    "methodName": "ExchangeToken",
    "authenticationInfo": {"principalSubject": "principal://iam.googleapis.com/locations/global/workforcePools/contractor-pool/subject/contractor@acquired.com"},
    "request": {"audience": "//iam.googleapis.com/locations/global/workforcePools/contractor-pool/providers/entra-provider"},
    "response": {"mappedAttributes": {"google.groups": ["admins", "developers"]}}
  }
}

Root cause: Attribute mapping was defined as "google.groups": "assertion.groups". The external IdP contained a local group named "admins" which matched the pre-existing IAM binding principalSet://.../group/admins intended exclusively for corporate IT admins.

Root cause: Unqualified group attribute mapping allowed untrusted external group names ('admins') to collide with sensitive corporate administrative IAM bindings.

Diagnostic sequence:

  1. Query the workforce pool provider configuration using gcloud iam workforce-pools providers describe.
  2. Inspect the attribute mapping rules for google.groups.
  3. Audit IAM role bindings on the organization node to identify any references to the workforce pool.
  4. Inspect the external IdP SAML/OIDC token claims presented by the contractor.

Defensible remediation: Prefix external groups with the IdP identifier using CEL mapping: `google.groups = assertion.groups.map(g, 'contractor-' + g)` and add an attribute condition restricting tenant ID.

Verification: Execute gcloud token exchange and assert that the minted credentials only contain prefixed groups (e.g. `contractor-admins`) which possess zero default permissions.

Residual risk: Group membership revocation at the external IdP takes effect only after the short-lived federated token expires (maximum 1 hour).

2. Cloud Identity · field case

Enterprise scenario: An administrator on a personal unencrypted tablet successfully logged into the Google Cloud Console from a coffee shop and altered production firewall rules.

Constraints: Corporate policy requires all console administrative actions to originate exclusively from company-owned, encrypted laptops running approved operating systems.

Evidence:

Cloud Audit Activity log showing unmanaged device login:

{
  "protoPayload": {
    "authenticationInfo": {"principalEmail": "admin@corp.com"},
    "methodName": "compute.firewalls.patch",
    "requestMetadata": {
      "callerIp": "198.51.100.42",
      "callerSuppliedUserAgent": "Mozilla/5.0 (iPad; CPU OS 15_4 like Mac OS X)"
    }
  }
}

Audit revealed Access Context Manager access levels were defined but not bound to the Google Cloud Console service in the Context-Aware Access policy configuration.

Root cause: Context-Aware Access levels were never enforced on the Google Cloud Console application, allowing unmanaged personal devices to authenticate.

Diagnostic sequence:

  1. Inspect Access Context Manager access levels using gcloud access-context-manager levels list.
  2. Verify Context-Aware Access bindings across Cloud Console and Google APIs.
  3. Inspect device inventory in Cloud Identity Admin Console to confirm device management status.
  4. Review Cloud Audit logs for caller IP, user agent, and device ID.

Defensible remediation: Create a strict Access Level requiring `device.is_encrypted && device.is_admin_approved` and bind it to the Google Cloud Console service.

Verification: Attempt login from an unmanaged iPad and verify immediate interception with Context-Aware Access 403 block screen.

Residual risk: Endpoint Verification agent on client devices requires periodic synchronization with Google Front End (typical refresh interval: 15-30 minutes).

3. Identity-Aware Proxy (IAP) for zero-trust access to apps and TCP forwarding to VMs · field case

Enterprise scenario: An internal payroll microservice behind IAP was accessed by an unauthorized attacker who extracted employee salary data.

Constraints: The microservice runs inside GKE and is exposed via an External Application Load Balancer with IAP enabled.

Evidence:

Microservice application access log:

2026-09-29T11:42:01Z [INFO] GET /api/v1/salaries HTTP/1.1
Host: payroll.internal
X-Goog-Authenticated-User-Email: accounts.google.com:ceo@corp.com
Client IP: 10.128.0.42 (Internal GKE pod in adjacent development namespace)

Analysis: The backend microservice inspected only the unauthenticated header X-Goog-Authenticated-User-Email without validating the cryptographic x-goog-iap-jwt-assertion signature. A rogue container inside the cluster spoofed the header and directly invoked the pod's ClusterIP service.

Root cause: The backend application trusted plaintext identity headers without validating the cryptographic ES256 signature and audience of the IAP JWT assertion.

Diagnostic sequence:

  1. Inspect the backend service source code to verify how client identity is extracted.
  2. Verify whether network policies or mTLS protect direct pod-to-pod traffic in the GKE cluster.
  3. Check if the application verifies the ES256 signature against Google's public key endpoint.
  4. Audit VPC firewall rules to ensure direct ingress from untrusted internal pods is blocked.

Defensible remediation: Implement a middleware library validating the `x-goog-iap-jwt-assertion` token signature against Google JWKS and verifying that the `aud` claim matches the specific backend service ID.

Verification: Send a request with a spoofed plaintext header and verify that the backend immediately responds with HTTP 401 Unauthorized.

Residual risk: If Google rotates public keys, backend caches must refresh keys from the public JWKS endpoint without incurring excessive latency.

import base64
import json
import time

class IAPJwtValidator:
    def __init__(self, expected_audience):
        self.expected_audience = expected_audience

    def validate_assertion(self, token_str):
        if not token_str:
            raise ValueError('Missing IAP JWT assertion')
        parts = token_str.split('.')
        if len(parts) != 3:
            raise ValueError('Malformed JWT token structure')

        payload_raw = base64.urlsafe_b64decode(parts[1] + '==')
        payload = json.loads(payload_raw)

        # Verify claims
        if payload.get('aud') != self.expected_audience:
            raise PermissionError(f'Audience mismatch: got {payload.get("aud")}')
        if payload.get('iss') != 'https://cloud.google.com/iap':
            raise PermissionError('Invalid token issuer')
        if payload.get('exp', 0) < time.time():
            raise PermissionError('Token has expired')

        return payload.get('email')

if __name__ == '__main__':
    aud = '/projects/108420918237/global/backendServices/91823'

        'email': 'sre@corp.com'

    user_email = validator.validate_assertion(valid_token)
