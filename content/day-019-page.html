1 · Concepts and problem previews

Cloud Shell architecture, persistent storage, and ephemeral runtime

What it is: Cloud Shell is an online bash development and administrative environment provisioned automatically from the Google Cloud Console. Backed by an ephemeral Debian Linux Compute Engine virtual machine container, it mounts a persistent 5 GB disk under the user's home directory (/home/$USER) and arrives pre-authenticated with the active Google Cloud user session. Pre-installed with major DevOps and cloud management utilities—including the Google Cloud CLI, Terraform, Docker, Git, Python, and language compilers—Cloud Shell provides an immediate command-line control plane without requiring local workstation installations or firewall exceptions.

Why today: Having established sandbox billing controls and account hierarchies on Day 18, architects need an operational interface to inspect resources, query APIs, and validate sandbox security settings. Understanding Cloud Shell is critical because its hybrid architecture—combining a temporary container runtime with persistent disk storage—establishes the fundamental boundary between ephemeral compute states and persistent data volumes in cloud design.

Where it sits: Cloud Shell resides in a Google-managed tenant project outside the customer's Virtual Private Cloud (VPC). It connects securely to the Google Cloud management API control plane (*.googleapis.com) via internal Google frontends, exposing an integrated Web Preview reverse proxy that tunnels local HTTP listeners on the container out to authenticated browser sessions.

Problem preview

An engineer customizes system-level packages in /usr/local and starts a background daemon during an urgent production debugging session, only to discover all customizations and background jobs vanished after a 20-minute idle disconnect. The incident response stalled during an active bakery dispatch outage, doubling mean time to recovery while the team scrambled to reconstruct missing diagnostics tools.

Local gcloud installation, core properties, and named configuration profiles

What it is: The Google Cloud CLI (gcloud) is the primary local command-line interface for deploying, configuring, and operating Google Cloud services. Its runtime state is governed by structured properties—including core/project, core/account, compute/region, and compute/zone—which can be organized into distinct, named configuration profiles stored in the user's local configuration directory (~/.config/gcloud/configurations/). Named configurations allow operators to switch seamlessly between development, staging, and production environments without continually passing manual parameters or re-authenticating.

Why today: Relying exclusively on Cloud Shell is insufficient for production operations requiring automated local scripts, IDE integrations, and isolated identity boundaries. Establishing disciplined local gcloud configuration management on Day 19 prevents the cross-project operational drift that causes accidental modifications across enterprise project boundaries.

Where it sits: Installed locally on engineer workstations, CI/CD runners, and bastion hosts, gcloud manages OAuth 2.0 refresh tokens, constructs signed REST and gRPC API payloads, and persists local preferences. It enforces a strict property evaluation hierarchy, resolving parameters sequentially across command-line flags, environment variables, active named configurations, and system defaults.

Problem preview

An automation engineer switches active configurations in terminal A but executes a destructive bucket cleanup script in terminal B where an inherited environment variable overrides the expected project context. Brightloaf's staging cleanup script purged production order reconciliation tables, halting payment auditing and delaying automated franchisee settlement payouts for twelve hours.

Specialized cloud tooling: gcloud storage vs gsutil, BigQuery CLI, and kubectl

What it is: Google Cloud provides specialized command-line utilities tailored to distinct resource domains: gcloud storage is the modern, high-performance CLI for Cloud Storage replacing the legacy Python-based gsutil; bq is the command-line client for BigQuery data warehousing and analytics queries; and kubectl is the upstream Kubernetes CLI, integrated with Google Kubernetes Engine (GKE) through the gke-gcloud-auth-plugin. While all three interface with Google Cloud services, they maintain separate credential resolution workflows and configuration storage backends.

Why today: Cloud enterprise architectures extend beyond basic infrastructure provisioning. Real-world solutions require uploading assets to object stores, querying analytical datasets, and managing containerized workloads. Mastering how these specialized tools authenticate and locate their target resources is essential to ensure operational commands reach the correct infrastructure endpoints.

Where it sits: These tools run alongside gcloud in local environments and Cloud Shell. While gcloud storage is fully unified into the core SDK binary and bq directly inherits active SDK credentials, kubectl relies on a separate client configuration file (~/.kube/config). Because kubectl does not automatically track active gcloud project changes, an architectural decoupling exists between the GCP project context and the Kubernetes cluster target.

Problem preview

A developer updates gcloud config to point to brightloaf-dev and issues a namespace deletion command believing the Kubernetes context automatically followed the active Google Cloud project. The command executed against the production GKE cluster referenced by the untouched kubeconfig context, tearing down Brightloaf's live delivery dispatch microservices and dropping four thousand in-flight orders.

2 · Architecture, control flow, boundaries, and limits

Cloud Shell runtime architecture, storage boundaries, and web preview proxying

Cloud Shell is fundamentally an orchestration layer that provisions an on-demand, Google-managed virtual machine container to provide engineers with an immediate operational shell into Google Cloud. Rather than maintaining a persistent Compute Engine instance with dedicated IP addresses and ongoing compute costs, Cloud Shell utilizes a decoupled container architecture where the execution runtime is strictly ephemeral while the user's workspace state is persisted onto an independent storage volume.

Runtime Container Lifecycle & Quotas

When an operator clicks the Cloud Shell icon in the Google Cloud Console or accesses Cloud Shell via web browser, the control plane allocates a Debian Linux container running on an e2-medium equivalent Compute Engine VM (1 vCPU, 4 GB RAM). This instance is provisioned in a Google-owned tenant project and operates under strict operational guardrails:

  • Inactivity Timeout: If no keyboard activity or terminal interaction occurs for 20 minutes, the session is terminated and the runtime VM is decommissioned.
  • Maximum Session Length: An individual continuous interactive session is capped at 12 hours, after which the container is recycled regardless of active typing or running processes.
  • Weekly Usage Quota: Cloud Shell enforces a rolling 50-hour weekly quota per user identity. Once exceeded, further terminal sessions cannot be launched until the rolling quota window clears.
  • Boost Mode: Operators can temporarily enable Boost Mode, which provisions an upgraded e2-standard-2 VM (2 vCPU, 8 GB RAM) for intensive build or compilation tasks. Boost Mode expires automatically after 24 hours.

The Ephemeral vs. Persistent Filesystem Boundary

The defining architectural principle of Cloud Shell is the storage boundary between /home/naveen and the rest of the filesystem. The root filesystem (/), system directories (/usr, /etc, /var), and temporary scratch paths (/tmp) are backed by an ephemeral overlay filesystem residing entirely inside the temporary container. When a session terminates—whether due to the 20-minute inactivity timer, explicit logout, or container cycling—all modifications made outside /home/naveen are permanently discarded.

In contrast, the user's home directory is backed by a 5 GB persistent disk that is automatically detached when the session ends and remounted at /home/naveen when a new session boots. This persistent volume retains dotfiles (such as .bashrc, .profile, and .gitconfig), local Git repositories, and tool caches. However, if an account does not access Cloud Shell for 120 consecutive days, Google Cloud initiates automated persistent disk purge workflows, sending notification emails before deleting the volume.

Customization Hooks & Web Preview

To bridge the gap between ephemeral operating system state and persistent user tools, Cloud Shell supports an automated initialization hook: /home/naveen/.customize_environment. When present and marked executable, the Cloud Shell provisioning daemon executes this shell script under the root context immediately after the container starts, allowing automated re-installation of system-level Debian packages, daemons, or kernel configurations without manual intervention.

For testing web applications (such as API backends or web hooks), Cloud Shell incorporates a secure Web Preview proxy. Developers can bind an HTTP listener to port 8080 (or any unprivileged port between 1024 and 65535). Cloud Shell tunnels traffic through Google frontends to an authenticated URL format (https://<port>-cs-<session-id>.cs-<region>-default.cloudshell.dev), restricting access strictly to the authenticated Google identity via secure session cookies.

Local gcloud configuration hierarchy, named profiles, and property precedence

The Google Cloud CLI (gcloud) is the core operational client for Google Cloud management. Because enterprise architects routinely interact with multiple projects across isolated lifecycle environments (such as sandboxes, staging clusters, and production organizations), gcloud organizes its operational state into structured properties and named configuration profiles.

Named Configuration Architecture

A named configuration is an isolated collection of key-value properties that define the operational context of the CLI. All configuration states are stored locally in the user's home directory under ~/.config/gcloud/configurations/ as INI-formatted text files (e.g. config_brightloaf-dev, config_brightloaf-prod). The currently active profile is tracked by a simple text pointer file: ~/.config/gcloud/active_config.

Core properties configured within a named profile include:

  • core/project: The immutable globally unique Google Cloud project ID targeted by commands.
  • core/account: The authenticated IAM principal email address (user or service account).
  • compute/region: The default geographical region for regional Compute and serverless resources (e.g. us-central1).
  • compute/zone: The default zonal data center location (e.g. us-central1-a).
  • core/disable_usage_reporting: Telemetry collection preferences.

The Four-Tier Property Precedence Ladder

When any gcloud command is invoked, the SDK resolves each required property (such as the target project ID) by evaluating a strict, four-tier precedence hierarchy from top to bottom:

  1. Tier 1 — Explicit Command-Line Flags (Highest Precedence): Passing --project, --account, --configuration, or --billing-project directly to a command unconditionally overrides all other sources.
  2. Tier 2 — Environment Variables: If no explicit flag is passed, gcloud inspects process environment variables. Key variables include CLOUDSDK_CORE_PROJECT, CLOUDSDK_CORE_ACCOUNT, and CLOUDSDK_ACTIVE_CONFIG_NAME. If set, an environment variable silently overrides the saved settings in the active profile.
  3. Tier 3 — Active Named Configuration: If no flag or environment variable is present, gcloud reads the property from the currently activated profile in ~/.config/gcloud/configurations/config_<name>.
  4. Tier 4 — SDK Installation Defaults (Fallback): If a property is not defined in any of the higher tiers, gcloud falls back to internal built-in defaults (or prompts the user interactively).
The Silent Override Trap

The existence of Tier 2 environment variables represents one of the most frequent sources of accidental cross-project outages. If an engineer runs an automated test script that exports CLOUDSDK_CORE_PROJECT=brightloaf-prod in a shell session, subsequent manual commands executed in that same shell will target production—even if the operator explicitly runs the configuration activation command to switch to a development profile!

Specialized cloud tooling: gcloud storage high-performance transfer, BigQuery bq CLI, and kubectl auth decoupling

Enterprise administration across Google Cloud incorporates specialized tools designed for specific architectural planes. While all integrate with the broader Google ecosystem, each tool exhibits distinct configuration models, performance envelopes, and authentication bindings.

gcloud storage vs. Legacy gsutil

For over a decade, gsutil served as the standard Python-based CLI for Cloud Storage. While functional, gsutil suffered from significant performance bottlenecks when processing large quantities of small files or multi-gigabyte object uploads, relying on complex .boto configuration files for multi-threading.

Google Cloud has replaced gsutil with gcloud storage, a ground-up rewrite integrated directly into the core SDK. Key architectural enhancements include:

  • High-Throughput Concurrency: Implements modern multiprocessing and multithreading in Python 3 by default, delivering up to 94x faster transfer speeds for multi-file workloads without manual threading adjustments.
  • Automatic Parallel Composite Uploads: Large objects are automatically partitioned into chunks, uploaded simultaneously across parallel TCP streams, and composed into a single object in Cloud Storage.
  • Unified Flag & Auth Model: Eliminates legacy .boto configuration files, inheriting gcloud's active named configuration, OAuth 2.0 credentials, and quota project headers natively.

BigQuery bq CLI & SQL Dialect Traps

The bq CLI provides direct command-line access to BigQuery's REST API endpoints (bigquery.googleapis.com). While bq automatically reads the active account and project from the gcloud configuration, it introduces a severe syntax trap: Legacy SQL vs. GoogleSQL.

By default, certain interactive commands in bq fallback to Legacy SQL unless the query explicitly specifies standard GoogleSQL. Legacy SQL uses non-standard bracketed table references ([project:dataset.table]), lacks ANSI compliance, and fails on modern analytical features such as common table expressions (CTEs) and array unnesting. Architects must enforce --use_legacy_sql=false in all automation scripts or permanently declare use_legacy_sql = false in the user's ~/.bigqueryrc configuration file.

kubectl Authentication & Context Decoupling

The most critical architectural boundary exists between the Google Cloud CLI and the Kubernetes command-line tool, kubectl. While Google Kubernetes Engine (GKE) clusters are hosted on Google Cloud infrastructure, kubectl is an independent, upstream open-source binary that reads its state exclusively from ~/.kube/config.

GKE bridges authentication through the gke-gcloud-auth-plugin binary. When an operator runs kubectl against a GKE cluster, the client executes the auth plugin as a child process, which queries gcloud to obtain a short-lived OAuth 2.0 access token and injects it as a Bearer token into the Kubernetes API request.

The Architectural Decoupling Trap: Switching the active gcloud project does NOT switch the kubectl current context! A developer can execute a project switch command to target brightloaf-dev, but if their ~/.kube/config current context points to gke_brightloaf-prod_us-central1_prod-cluster, subsequent kubectl commands will execute directly against the production Kubernetes cluster!

3 · Real-world field problems and incident handling

Incident exercise · Cloud Shell ephemeral disk recycling wipes uncommitted emergency patch

Symptom: During a morning peak delivery surge at 06:45 UTC, Brightloaf\'s automated bread fulfillment queue stalled due to an unhandled serialization bug in the order dispatch worker. An on-call site reliability engineer launched Cloud Shell to compile and deploy an emergency binary patch. After compiling the binary in /tmp/patch-build and installing required toolchains into /usr/local/bin, the engineer joined a 30-minute operational conference call with franchise managers. Upon returning to the browser terminal, Cloud Shell had timed out due to 20 minutes of inactivity. When the engineer reconnected, a new container booted; /tmp and /usr/local/bin were empty, all compiled artifacts and diagnostic toolchains were gone, and the recovery had to start from scratch.

Operational and business constraints: Brightloaf operates on strict morning delivery Service Level Objectives (SLOs), requiring orders received by 06:00 to be dispatched to bakery distribution trucks by 07:30. Every 15-minute delay risks franchise delivery window penalties of $25,000 across 32 regional fulfillment centers. Furthermore, any hotfix applied to the fulfillment processor must strictly preserve the architectural invariant that replaying an order event never triggers duplicate physical baking batches or double-fulfills an order.

Evidence: Inspecting the newly reincarnated Cloud Shell instance revealed that the container ID had changed and uptime was less than 60 seconds:

$ uptime
 07:22:14 up 1 min,  1 user,  load average: 0.12, 0.08, 0.02
$ ls -la /tmp/patch-build
ls: cannot access '/tmp/patch-build': No such file or directory
$ which custom-dispatch-builder
custom-dispatch-builder not found
$ df -hT /home/$USER /tmp
Filesystem     Type   Size  Used Avail Use% Mounted on
/dev/sdb       ext4   4.8G  1.2G  3.4G  27% /home/dev_brightloaf_com
tmpfs          tmpfs  2.0G     0  2.0G   0% /tmp

Root cause: The engineer treated Cloud Shell as a persistent virtual workstation rather than an ephemeral container. The root filesystem (/), system directories (/usr/local), and scratch storage (/tmp) reside on temporary container overlay and memory mounts that are discarded when the Cloud Shell session watchdog triggers the 20-minute idle termination. Only the 5 GB volume mounted at /home/$USER is persistent.

Diagnostic sequence (5 steps):

  1. Audit filesystem mount hierarchy: Execute df -hT to verify the exact device and mount point boundaries between ephemeral tmpfs overlays and the persistent disk backing /home/$USER.
  2. Check container lifecycle and uptime markers: Run uptime and examine /var/log/dmesg to determine whether a container restart occurred during the idle period.
  3. Identify uncommitted build artifacts: Compare persistent repository checkouts under /home/$USER/workspace/ against references to /tmp in local shell history.
  4. Codify container bootstrap automation: Author an initialization script at /home/$USER/.customize_environment to automate any required system packages upon container provisioning.
  5. Execute order replay invariant test: Before deploying the compiled hotfix to production, run a dry-run replay test using synthetic order payloads, verifying that the database fulfillment table with a unique order ID constraint explicitly rejects duplicate processing attempts.

Defensible solution: Re-establish the hotfix build entirely within /home/$USER/workspace/hotfix-build/. Create an automated environment customization script at /home/$USER/.customize_environment with executable permissions, ensuring that required build toolchains are automatically installed as root if the container is recycled. Finally, implement an end-to-end integration test verifying that order replays reject duplicate fulfillment records.

Verification: Terminate the Cloud Shell container explicitly using the Cloud Console menu, re-open the terminal, and verify that the build environment auto-provisions and that compiled binaries in ~/workspace remain intact:

$ ls -la /home/$USER/workspace/hotfix-build/bin/order-dispatcher
-rwxr-xr-x 1 dev_brightloaf_com dev_brightloaf_com 18452240 Sep 27 07:28 /home/$USER/workspace/hotfix-build/bin/order-dispatcher
$ python3 /home/$USER/workspace/hotfix-build/tests/test_fulfillment_dedup.py
[TEST] Replaying order payload ID: ORD-99281-REPLAY
[TEST] First delivery dispatch: 200 OK (Fulfillment recorded)
[TEST] Second delivery dispatch: 409 Conflict (Duplicate order_id rejected by DB constraint)
[PASS] Invariant verified: Fulfillment count == 1

Residual risk: While user files in /home/$USER survive session timeouts, Cloud Shell imposes a hard 50-hour weekly quota and an absolute 12-hour session cutoff. If an operator exceeds 50 hours of usage within a rolling seven-day window, Cloud Shell access will be blocked until the quota clears, requiring local workstation failover procedures.

Incident exercise · Ambient environment variable overrides gcloud named configuration

Symptom: A DevOps engineer opened a terminal window on their workstation to execute a routine staging cleanup script intended to purge ephemeral test storage buckets and reset staging database fixtures. The engineer ran the configuration activation command to switch to the brightloaf-dev named configuration and verified that the profile was marked active. However, when the cleanup script executed, it wiped the production order replay staging bucket, destroying thousands of archived payment reconciliation receipts.

Operational and business constraints: Brightloaf must maintain complete payment reconciliation logs for seven years to comply with financial auditing regulations and franchise settlement agreements. An outage that destroys production reconciliation buckets forces manual payment reconstruction, delaying weekly franchisee disbursement checks and incurring external audit penalties. Critically, during bucket restoration and re-ingestion, the order fulfillment engine must ensure that previously processed orders are not re-executed by downstream automated bakery systems.

Evidence: Running diagnostic inspections inside the active shell revealed an active configuration targeting development, but an ambient environment variable pointing directly to production:

Root cause: Earlier that morning, the engineer had executed a CI debug script in the same terminal session that contained export CLOUDSDK_CORE_PROJECT=brightloaf-prod-001. In gcloud\'s property precedence ladder, Tier 2 environment variables silently take precedence over Tier 3 active named configuration profiles. When the cleanup script ran the gcloud storage remove command without an explicit --project flag, the command resolved brightloaf-prod-001 despite the active profile indicating brightloaf-dev.

Diagnostic sequence (5 steps):

  1. Interrogate active profile vs effective property resolution: Compare the output of the configuration list command against the effective project returned by the gcloud project query command.

  4. Sanitize environment and implement safety guard: Author a shell wrapper (gcloud-safe-exec.sh) that purges ambient CLOUDSDK_* variables and enforces target project validation before executing mutating commands.
  5. Verify database fulfillment invariant during reconciliation recovery: Replay archived order records from database change-data-capture logs, verifying that the unique primary key constraint on order fulfillment IDs prevents any double-fulfillment during the data recovery window.

Defensible solution: Unset the leaked environment variable immediately using unset CLOUDSDK_CORE_PROJECT. Configure the shell prompt (PS1) to evaluate and display the effective resolved project dynamically on every command line. Refactor all administrative scripts to pass explicit Tier 1 flags (--project="$TARGET_PROJECT") or include an automated preflight assertion halting execution if the resolved project does not match the script\'s intended scope.

Verification: Test the safety guard script with an intentional environment variable injection and verify that execution is halted with an explicit error before any cloud API call is made:

Residual risk: While wrapper scripts and shell prompt indicators prevent manual mistakes, team members running unmonitored ad-hoc commands without wrappers can still introduce silent overrides. Organization policies restricting service account permissions per workstation are required for comprehensive defense-in-depth.

Incident exercise · Kubectl context decoupling routes staging deployment to production GKE cluster

Symptom: A Brightloaf release engineer prepared to test an experimental release of the bakery order fulfillment microservice featuring aggressive multi-threaded order queue consumption and a disabled Redis deduplication cache. The engineer ran the configuration activation command to set the gcloud active project to brightloaf-staging and confirmed with Compute Engine VM listing commands that the active project was indeed staging. The engineer then ran the kubectl manifest deployment command. Within minutes, production bakery dispatch alerts fired: live orders were experiencing race conditions, customer support was flooded with duplicate baking reports, and the production fulfillment service had been overwritten with the staging container image.

Operational and business constraints: Brightloaf\'s operational core invariant mandates that no order can ever result in multiple physical fulfillment dispatches, regardless of network retries, pod restarts, or concurrent consumer threads. A deployment that disables deduplication caching poses an immediate threat of over-baking and inventory destruction across regional facilities.

Evidence: Checking the Kubernetes context revealed that while gcloud was targeting staging, kubectl\'s current context remained tethered to the production cluster:

$ gcloud config get-value project
brightloaf-staging-4029

$ kubectl config current-context

Root cause: The engineer operated under the mistaken assumption that switching the active Google Cloud CLI project automatically switches the Kubernetes context. In reality, kubectl operates independently, resolving cluster endpoints and credentials exclusively from ~/.kube/config. Changing the active gcloud project does not touch the current-context field in ~/.kube/config.

Diagnostic sequence (5 steps):

  4. Verify database-level fulfillment idempotency defense: Inspect the PostgreSQL database logs to confirm that the row-level lock (SELECT ... FOR UPDATE) and primary key constraint on order_id blocked concurrent duplicate inserts despite the disabled application cache.
  5. Implement synchronized multi-CLI context switcher: Create an automated context synchronization tool (verify-cloud-context.py) that validates that the active gcloud project matches the GKE cluster project embedded in the kubectl context before allowing deployments.

Defensible solution: Immediately execute a rollback on the production Kubernetes deployment using an explicit context parameter to restore the certified image. Synchronize the local kubeconfig using the cluster credential retrieval command. Establish an automated deployment gate that requires explicit context flags or fails if kubectl\'s current context project does not match the intended deployment target.

Lab 19.1 · Cloud Shell environment probe, persistent vs ephemeral boundary test, and custom environment initialization

Goal: Probe the architectural boundary between ephemeral container root storage and the persistent 5 GB disk mount in Cloud Shell, verify Web Preview reverse proxy mechanics, and establish an automated environment initialization hook via .customize_environment.

Expected result: A verified directory audit demonstrating filesystem persistence across container reboots, an automated bootstrap script in ~/.customize_environment, and an active Web Preview response on port 8080.

#!/bin/bash

EXPECTED_PROJECT=""
while [[ $# -gt 0 ]]; do
  case "$1" in

      EXPECTED_PROJECT="$2"
      shift 2
      ;;
    --)
      shift
      break
      ;;
    *)
      break
      ;;
  esac

if [[ -z "$EXPECTED_PROJECT" ]]; then
  echo "[GUARD ERROR] Must specify --expected-project " >&2
  exit 1
fi

# Check for ambient CLOUDSDK environment variable leaks
LEAKED_VARS=$(env | grep -E '^CLOUDSDK_(CORE_PROJECT|ACTIVE_CONFIG_NAME)' || true)
if [[ -n "$LEAKED_VARS" ]]; then
  echo "[GUARD CRITICAL] Leaked CLOUDSDK environment variables detected:" >&2
  echo "$LEAKED_VARS" >&2
  echo "[ABORT] Command rejected to prevent silent precedence override." >&2
  exit 2
fi

# Interrogate effective CLI project
RESOLVED_PROJECT=$(gcloud config get-value project 2>/dev/null || true)
if [[ "$RESOLVED_PROJECT" != "$EXPECTED_PROJECT" ]]; then
  echo "[GUARD CRITICAL] Context mismatch! Resolved: '$RESOLVED_PROJECT' | Expected: '$EXPECTED_PROJECT'" >&2
  echo "[ABORT] Command rejected to prevent cross-project mutation." >&2
  exit 3
fi

echo "[GUARD PASS] Validated target project: $RESOLVED_PROJECT"
echo "[GUARD PASS] Executing: $@"
exec "$@"
EOF

#!/usr/bin/env python3
import sys, re, argparse

def parse_kube_context(kubeconfig_path):
    with open(kubeconfig_path, 'r') as f:
        content = f.read()
    match = re.search(r'^current-context:\s*(\S+)', content, re.MULTILINE)
    if not match:
        raise ValueError("Could not find current-context in kubeconfig")
    return match.group(1)

def extract_project_from_gke_context(context_name):
    # GKE context pattern: gke___
    parts = context_name.split('_')
    if len(parts) >= 4 and parts[0] == 'gke':
        return parts[1]
    return None

def main():
    parser = argparse.ArgumentParser(description="Multi-CLI Context Parity Validator")
    parser.add_argument("--gcloud-project", required=True, help="Active gcloud project ID")
    parser.add_argument("--kubeconfig", required=True, help="Path to kubeconfig")
    parser.add_argument("--require-parity", action="store_true", help="Enforce exact project match")
    args = parser.parse_args()

    kube_ctx = parse_kube_context(args.kubeconfig)
    gke_proj = extract_project_from_gke_context(kube_ctx)

    print(f"[AUDIT] Active gcloud project:  {args.gcloud_project}")
    print(f"[AUDIT] Active kubectl context: {kube_ctx}")
    print(f"[AUDIT] Embedded GKE project:   {gke_proj}")

    if args.require_parity:
        if gke_proj != args.gcloud_project:
            print(f"[CRITICAL ERROR] Target drift detected! gcloud project '{args.gcloud_project}' does not match GKE cluster project '{gke_proj}'!", file=sys.stderr)
            print("[ABORT] Halting deployment pipeline to preserve cluster isolation and fulfillment invariant.", file=sys.stderr)
            sys.exit(1)
        print("[SUCCESS] Context parity verified. Safe to proceed with deployment.")
        sys.exit(0)

if __name__ == "__main__":
    main()
EOF
