Machine families: general-purpose, compute-optimized, memory-optimized, HPC, accelerator

GCP groups Compute Engine machine types into families optimised for different workload shapes. Choosing the wrong family does not just waste money — it can cause throttling, resource contention, or an inability to meet latency targets. The Brightloaf Order API is a stateless HTTP service with bursty CPU demand; the fulfillment worker is a long-running consumer with moderate, steady CPU and higher JVM heap. These two profiles land in different parts of the family map.

Problem preview: A Brightloaf engineer sizes the fulfillment worker on an N2D compute-optimized machine because it was the cheapest per-vCPU option found in a price list. Under load the worker frequently hits the GC pause ceiling because available memory per vCPU in a compute-optimized type is lower than the application's heap requirement. Business impact: order acknowledgement latency spikes during peak hours, violating the SLO established in the service level objectives exercise.

Custom machine types and extended memory

Standard predefined machine types come in fixed vCPU-to-memory ratios. When a workload sits between two standard sizes — enough CPU headroom in the smaller but not enough memory, or enough memory in the larger but idle CPU — a custom machine type avoids paying for unused resources. Extended memory allows the memory allocation to exceed the maximum for a given vCPU count in the standard ratio, at an additional cost.

Problem preview: A Brightloaf analyst configures a custom machine type with 6 vCPUs and 48 GB of RAM for a batch analytics job that runs nightly. The job finishes in under two hours; the VM is left running. Because the custom type's cost is billed per vCPU and per GB of memory separately, the idle VM costs more per hour than a standard n2-standard-8 would have. Business impact: the monthly sandbox spend exceeds the alert threshold set in Day 18 before the next billing review.

Shared-core vs standard machine types

Shared-core machine types (e2-micro, e2-small, e2-medium, f1-micro, g1-small) run on physical cores shared across multiple VMs. Each gets a guaranteed fraction of a vCPU. They cost significantly less than standard types and are appropriate for development instances, low-traffic services, and workloads where intermittent CPU bursting is acceptable. A standard machine type provides dedicated vCPU capacity; bursting is not the primary mechanism.

Problem preview: The Brightloaf staging Order API is deployed on an e2-micro instance to minimise cost. During a load test that simulates peak traffic, the shared-core fraction is exhausted and requests queue. The staging test then incorrectly informs a go/no-go decision for production, which would run on a dedicated standard type. Business impact: the test result is misleading — production sizing decisions based on a shared-core staging benchmark are not transferable.

Boot disks, images (public, custom, image families), snapshots and machine images

A VM's boot disk is a persistent disk containing the OS; its image source determines the OS, kernel version, and pre-installed software. Public images are maintained by Google or third parties; custom images are built and owned by your project; image families are rolling aliases that always resolve to the latest image in a named set. Snapshots capture a persistent disk's state at a point in time; machine images capture the entire VM configuration (all disks, metadata, network) for full-instance cloning or disaster recovery.

Problem preview: A Brightloaf operator creates a VM from an image family alias (debian-12) assuming the alias is pinned to a specific kernel version. A routine image update rolls the family to a new minor version; the next VM created from the family alias uses the updated image. The new kernel has a different default TCP buffer size that affects the Order API's high-throughput connections. Business impact: a subtle throughput regression appears only after the next deployment, making the root cause difficult to trace.

2 · Technical discussion of each topic

Machine families: general-purpose, compute-optimized, memory-optimized, HPC, accelerator

Family overview

GCP Compute Engine organises machine types into series within families. The family choice is the first decision; the series and size follow from workload measurement. Refer to current GCP documentation for exact series names, vCPU ranges, and regional availability — these change as new hardware generations are introduced.

Family Representative series vCPU:memory ratio Primary workload fit Brightloaf fit
General-purpose E2, N2, N2D, N4, T2D, T2A ~4–8 GB / vCPU (varies by series) Web services, CI/CD, databases, development Order API frontend; fulfillment worker at moderate heap
Compute-optimized C2, C2D, C3, H3 ~4 GB / vCPU (lower memory ratio) CPU-bound: encoding, scientific compute, game servers Not a fit for fulfillment worker (memory-limited)
Memory-optimized M1, M2, M3 ~14–24+ GB / vCPU In-memory databases, SAP HANA, large analytics Overkill for Order API; possible for analytics tier
HPC-optimized H3, A3 (with InfiniBand fabric) Varies; high network bandwidth Tightly-coupled MPI workloads, climate modelling Not a fit; Brightloaf has no HPC requirement
Accelerator-optimized A2, A3, G2 ~7–40+ GB / vCPU; includes GPU ML training, inference, graphics rendering Potential fit for future ML inference; not Day 36

Choosing within a family: series and size

Within the general-purpose family, N2 uses Intel or AMD processors with balanced performance; N2D is AMD EPYC-based and often offers a lower per-vCPU price; E2 uses a shared hardware pool and is the cheapest standard-ratio option but offers lower per-vCPU performance than N2. T2D (Tau T2D) and T2A (Tau Arm) target scale-out workloads like containerised web services. For the Brightloaf Order API, N2 or E2 are the primary candidates; T2D is worth evaluating if the application is pre-tested on x86.

Reading a workload before choosing

From Day 8, the signals that inform machine type selection are:

  • CPU utilisation sustained above ~70% under normal load → move up one size or to a higher-performance series.
  • Memory utilisation near limit with swap activity → choose a higher-memory ratio or a memory-optimized type.
  • Network throughput saturation → consider a type with a higher maximum egress bandwidth (N2 offers up to 32 Gbps with sufficient vCPUs).
  • Disk IOPS saturation → this is a Persistent Disk constraint, not a machine type constraint (covered in Day 37).

Custom machine types and extended memory

When custom sizing applies

Standard machine types increment in fixed vCPU steps. If a workload needs, say, 6 vCPUs and 32 GB of RAM, the nearest standard types are n2-standard-4 (4 vCPU / 16 GB) — too small — or n2-standard-8 (8 vCPU / 32 GB) — correct memory but 25% surplus CPU. A custom machine type with 6 vCPU / 32 GB avoids paying for 2 idle vCPUs.

Custom type naming and constraints

  • Notation: SERIES-custom-vCPUS-MEMORY_MB, e.g. n2-custom-6-32768.
  • vCPU count must be even (except 1); memory must be a multiple of 256 MB.
  • Memory range: at minimum 0.9 GB per vCPU; standard maximum 6.5 GB per vCPU for N2. Exceeding the standard maximum requires extended memory.
  • Extended memory is billed at a higher per-GB rate than standard memory. It is intended for memory-intensive outliers that do not warrant a full memory-optimized type.

Cost model

Custom machine type pricing is per-vCPU per hour + per-GB RAM per hour, billed separately. A custom type with the same vCPU and memory as a predefined type costs slightly more because predefined types receive a small discount for the packaging. Custom types are most economical when they save at least one vCPU or 4+ GB compared to the next standard size up.

Sustained use discounts (SUDs) apply automatically to custom types that run more than 25% of a month in a region. Committed use discounts (CUDs) require a 1- or 3-year commitment and offer deeper savings.

Scenario Standard predefined Custom type Verdict
6 vCPU, 32 GB needed n2-standard-8 (8 vCPU, 32 GB) — 2 idle vCPUs n2-custom-6-32768 (6 vCPU, 32 GB) Custom saves ~25% CPU cost if utilisation confirms 6 vCPU ceiling
4 vCPU, 16 GB needed n2-standard-4 (4 vCPU, 16 GB) — exact match n2-custom-4-16384 — same, slight premium Use predefined; custom adds overhead for no gain
4 vCPU, 48 GB needed Closest: n2-standard-4 (16 GB) — too small; n2-standard-8 (32 GB) — still too small n2-custom-4-49152 with extended memory Extended memory applicable; compare to n2-highmem-4 (32 GB) — may still need custom

Shared-core vs standard machine types

Shared-core characteristics

Shared-core machine types run on physical cores shared by multiple VMs. Each VM receives a guaranteed fraction of a physical core. Available shared-core types include:

  • e2-micro: 2 vCPU (shared), 1 GB RAM. Burstable up to 2 vCPU when capacity is available.
  • e2-small: 2 vCPU (shared), 2 GB RAM.
  • e2-medium: 2 vCPU (shared), 4 GB RAM.
  • f1-micro (legacy): 1 shared vCPU, 0.6 GB RAM. Eligible for the Always Free tier under current limits.
  • g1-small (legacy): 1 shared vCPU, 1.7 GB RAM.

The key distinction: a shared-core VM has a guaranteed minimum CPU allocation (expressed as a fraction of a vCPU) and can burst above that minimum if the physical core has spare capacity. A standard machine type provides dedicated vCPU threads with no sharing — the vCPU count reflects actual available compute, not a fractional guarantee.

When to use shared-core

  • Development, staging environments with intermittent load.
  • Monitoring agents, log forwarders, CI workers that run short jobs and idle most of the time.
  • Applications that can tolerate CPU throttling without user-facing latency impact (background batch).

Critical limitation: benchmark validity

Performance measurements taken on a shared-core VM cannot be used to size a standard-core production deployment. The burst ceiling and scheduling behaviour differ. If a staging environment uses shared-core to save cost, any benchmark results must be labeled with the machine type and marked as "not transferable to production sizing."

Dimension Shared-core (e.g. e2-micro) Standard (e.g. e2-standard-2)
CPU guarantee Fractional share; burst available Full vCPU threads; no sharing
CPU under load May throttle when share exhausted Sustained full utilisation possible
Pricing Significantly lower Higher; more predictable
Benchmark validity Not transferable to standard Transferable within same series
Appropriate use Dev, agents, low-traffic services Production, load testing, SLO-bound services

Boot disks, images (public, custom, image families), snapshots and machine images

Boot disk

A VM's boot disk is a zonal Persistent Disk containing the OS image and the system filesystem. By default it is deleted when the VM is deleted (--no-keep-disks is the gcloud default). To retain the disk for re-attachment or inspection, create the VM with --no-boot-disk-auto-delete. Boot disk size and type (pd-standard, pd-balanced, pd-ssd) affect startup latency, OS throughput, and cost.

Image sources

  • Public images: maintained by Google (Debian, Ubuntu, COS, Windows) or by third-party vendors in the Marketplace. Google updates these for security patches; minor kernel changes may occur.
  • Custom images: built from an existing disk, snapshot, or image. Owned by your project. Used to bake application dependencies, agents, and OS configuration into a golden image. Custom images must be updated and maintained by your team.
  • Image families: a named alias that always resolves to the latest non-deprecated image in the family. For example, debian-12 in project debian-cloud always resolves to the current Debian 12 image. Using a family alias means new VMs pick up OS updates automatically; using a specific image ID pins to a known state.
  • Shared images: custom images published to an image project and shared across projects via IAM. Useful for golden-image pipelines in large organizations.

Snapshots vs machine images

Feature Snapshot Machine image
What it captures A single Persistent Disk at a point in time Full VM: all disks, machine config, metadata, network interfaces, service accounts
Scope One disk; can be any PD, including non-boot One VM instance, all attached resources
Primary use Backup, disk cloning, baseline before risky change VM cloning, disaster recovery, migration to a different zone or region
Restore Create a new disk from snapshot; attach to VM Create a new VM from machine image; all disks and config restored
Cost Per-GB of compressed data stored Per-GB of all disk data stored; higher than a single snapshot
Incremental Yes — only changed blocks after first snapshot Yes — internally uses snapshots

Image family vs pinned image: the tradeoff

Use a family alias (--image-family=debian-12 --image-project=debian-cloud) for environments where automatic OS updates are acceptable and you can tolerate minor changes between VM generations. Pin to a specific image ID (--image=debian-12-bookworm-v20260901) for environments where configuration drift must be controlled, reproducible deploys are required, or OS changes need explicit testing before rollout.

A golden-image pipeline bridges both approaches: periodically build a custom image from the latest family image, run a bake-and-test pipeline, and pin production deployments to the baked custom image ID. This gives patch currency with configuration control.

3 · Real-world problems and solutions

The scenarios below are illustrative examples grounded in Day 36 topics. They are not observed production incidents. All numeric values are design assumptions, not measured results.

Topic 1 field case — Compute-optimized type chosen for a memory-bound fulfillment worker

Situation and business impact

A Brightloaf engineer selects an N2D compute-optimized instance for the fulfillment worker because a marketing table shows it has the lowest per-vCPU price among N-series types. The fulfillment worker is a JVM-based consumer that maintains a large in-memory order cache and performs per-order state validation. The workload's memory requirement is approximately 6 GB of heap for the expected queue depth. The N2D compute-optimized series offers roughly 4 GB of RAM per vCPU; at 2 vCPUs the VM has 8 GB total, which appears sufficient. However, under sustained queue processing, GC pauses lengthen as the heap approaches its configured maximum, because OS overhead and JVM metaspace consume the non-heap remainder. Throughput drops and order acknowledgement latency rises above the SLO threshold.

Constraints

  • Cannot change the JVM heap size beyond 6 GB without re-testing the fulfillment logic under load.
  • Must stay within the sandbox CPU quota; cannot increase vCPU count by more than one.
  • The fix must not require a new VM image (only a machine type change).

Root cause

The selection was driven by a single cost metric (lowest per-vCPU price) without reading the workload's memory signal. The compute-optimized series' lower memory-to-vCPU ratio is correct for CPU-bound workloads but is under-provisioned for memory-bound JVM workloads with a large heap.

Diagnostic sequence

  1. Collect memory utilisation data from Day 8's signals: check resident set size, heap utilisation, and GC pause frequency.
  2. Calculate the minimum RAM required: heap (6 GB) + OS overhead (estimate 1–1.5 GB) + JVM metaspace (estimate 0.5 GB) = approximately 8–8.5 GB effective requirement.
  3. Select a general-purpose type with a higher memory ratio: N2 or N2D highmem series (up to 8 GB/vCPU) would fit 2 vCPU / 16 GB.
  4. Record the rejected compute-optimized option and the reason in the sizing sheet.

Defensible solution

Migrate the fulfillment worker to an N2-highmem-2 or equivalent (2 vCPU / 16 GB). Stop the compute-optimized instance, change the machine type (via gcloud compute instances set-machine-type while stopped), restart, and observe GC pause frequency and throughput under the same queue depth.

Verification

After the change: GC pause frequency should return to background levels; order acknowledgement latency should remain below the SLO threshold. Record the before/after memory headroom (heap used vs total allocated) in the sizing sheet as the post-fix evidence.

Residual risk

The 16 GB highmem option provides significant headroom but increases hourly cost. If peak queue depth is seasonal, a custom type with exactly the required RAM (e.g., 2 vCPU / 10 GB) would balance cost and headroom. This requires a separate sizing iteration.

Topic 2 field case — Custom type left running after nightly batch completes

Situation and business impact

A Brightloaf analyst provisions a custom machine type (6 vCPU / 48 GB RAM) for a nightly analytics batch that processes the previous day's order data. The batch finishes within two hours. The VM is not deleted after the job because the provisioning script lacks a post-job cleanup step. The analyst assumes the VM will be stopped by an instance schedule (from Day 33); however, the schedule was applied to a different instance name and does not cover this VM. The VM runs continuously. Because custom type pricing is per-vCPU and per-GB memory separately, the idle cost is higher than expected.

Constraints

  • The batch must complete within its two-hour window; the VM cannot be downsized mid-job.
  • The budget alert (Day 18) should catch runaway spend, but alert delivery to an unmonitored inbox is a known gap from Day 35's remediation.
  • The fix must not require changing the batch job code — only the infrastructure lifecycle.

Root cause

The provisioning script had no post-job teardown. The instance schedule assumption was not verified against the actual VM name. The combined effect is an orphaned VM with a higher hourly cost than a standard predefined type would have had.

Diagnostic sequence

  1. Inventory running VMs by label: confirm the batch VM is running outside its expected window.
  2. Check the instance schedule: verify which VM names it targets and confirm the batch VM is not included.
  3. Delete the VM immediately and confirm an empty label inventory.
  4. Add a gcloud compute instances delete call to the batch script's exit handler (runs on success or failure).
  5. Apply the instance schedule to the correct VM name or replace the schedule with script-level teardown.

Defensible solution

Update the provisioning script to delete the VM on job completion. As a defence-in-depth, configure a budget alert with an actively monitored recipient (Day 35 remediation) and add a label (owner=batch-analytics, env=lab) so inventory checks catch any future orphans.

Verification

Run the batch script end-to-end. After job completion, confirm the VM is deleted by label inventory. Check the billing report (or budget alert) to confirm no continued charge from that instance after the job window.

Residual risk

Script-level teardown fails if the script is forcibly killed. A second defence is an instance schedule set to stop (not delete) the VM one hour after the expected job end. Stopping is cheaper than running but does not eliminate the disk cost; deletion is cleanest for a truly disposable batch VM.

Topic 3 field case — Shared-core staging benchmark used to size production

Situation and business impact

The Brightloaf staging Order API runs on an e2-micro (shared-core) to minimise lab cost. A load test at 20 requests/second is run against staging; average response time is recorded. The engineer uses this result to justify choosing an e2-standard-2 (standard-core, 2 vCPU / 8 GB) for production, reasoning that if staging handles 20 RPS on a micro, standard will comfortably handle the target 50 RPS. After production launch, the service performs correctly at lower loads but begins to degrade at 35 RPS — well below the projected 50 RPS ceiling.

Root cause

The shared-core micro burst ceiling was not exhausted during the staging test because 20 RPS was below the burst threshold for that particular physical host at test time. The result is not transferable: the e2-micro's guaranteed CPU fraction is far less than a full vCPU, and its burst behaviour depends on physical host utilisation at test time. The staging benchmark result is an artefact of host availability, not a transferable throughput ceiling.

Defensible solution

Run load tests only on standard-core machine types of the same series as the production target. Size staging with a machine type that reflects the production CPU guarantee, not the smallest available type. Annotate all benchmark results with the machine type, series, and "not transferable to shared-core/different series" notes.

Verification

Re-run the load test on an e2-standard-2 staging instance. Record the throughput ceiling and compare to the production target. Record both the machine type and the test date in the sizing sheet. The rejected e2-micro option must appear in the sizing sheet with the reason: "Shared-core; benchmark not transferable to standard sizing."

Topic 4 field case — Image family alias rolls to a new kernel version, causing connection regression

Situation and business impact

The Brightloaf Order API is deployed from a Terraform configuration that uses the debian-12 image family alias and the debian-cloud project. A routine deployment creates a new VM as part of a rolling update. The image family has been updated to a new minor version since the previous deployment; the new VM boots with an updated kernel. The new kernel's default TCP receive buffer size is different from the previous version's default, affecting high-throughput connections from the API to the fulfillment queue. Throughput on those connections is lower than before, but the change is subtle enough that it is not caught by health checks. The regression is noticed during the next load test.

Root cause

The image family alias always resolves to the latest non-deprecated image. Using a family alias in production means kernel and system package versions can change between deployments without an explicit version bump in the Terraform configuration. The team had no mechanism to detect or test image version changes between releases.

Defensible solution

For production VMs: pin to a specific image ID rather than a family alias. Adopt a golden-image pipeline: periodically build a custom image from the latest family image, run automated tests (including connection throughput), and only promote the custom image ID to production after testing passes. Record the current image ID in the Terraform configuration as a versioned value.

Verification

After pinning: a new deployment must use the pinned image ID regardless of which image is currently latest in the family. Confirm the image ID in the running instance's describe output matches the pinned value. The sizing sheet must record the image ID (not family alias) as the customer-managed layer for OS version.

Residual risk

Pinning to a specific image ID means security patches do not roll out automatically. The golden-image pipeline must include a cadence for pulling new family images and testing them. An organisation that pins without a pipeline update process will accumulate unpatched OS versions.
