Part 1 — Topics of the Day

High availability, fault tolerance, and disaster recovery

What it is: High availability keeps a service usable through expected component failures, often by routing requests to a healthy copy. Fault tolerance is the ability to continue a required operation despite a specified fault, with little or no interruption; disaster recovery restores service and data after a larger loss. RTO is the maximum acceptable recovery duration, while RPO is the maximum acceptable age of recovered data.

Why today: Day 12 introduced locations and failure domains. These terms let you state what a second zone, a standby service, or a backup actually protects.

System location: They describe end-to-end behavior across the client route, application workers, database, storage, backups, monitoring, and operational response.

Problem preview

Brightloaf's second Order API worker answers requests after the first fails, but an accidental database deletion appears to both workers. Checkout remains available while order history is missing, delaying fulfillment and customer support.

Stateless and stateful applications

What it is: A stateless application worker does not depend on local memory or local files from a previous request to process the next one. A stateful component owns information that must survive or coordinate across requests, such as accepted orders, inventory changes, or fulfillment records.

Why today: Before planning more replicas or a faster restart, locate the authoritative copy of each business fact. Moving state out of an API process makes worker replacement simpler but does not remove the need to protect the state store.

System location: State can live in worker memory, a local file, a database, a queue, a cache, or an external session store. Its owner and durability must be explicit.

Problem preview

A restarted Order API worker forgets that it already accepted an order event and treats the replay as new. The same purchase can trigger a second fulfillment unless durable state enforces the business invariant.

Part 2 — Technical Discussion

Availability and recovery are different guarantees

Availability asks whether a user can complete a useful request now. Another healthy API worker can improve availability when one process or host stops. It does not prove that the database is correct, a regional outage is survivable, or deleted data can be recovered. End-to-end availability is limited by dependencies on the request path: a healthy frontend cannot complete an order if its only writable database is unavailable.

Fault tolerance needs a named fault and an acceptable outcome. “An Order API worker can stop while a second worker continues accepting orders” is testable. “The system is fault tolerant” hides whether it tolerates a process crash, zone outage, corrupt data, or operator mistake. Redundant components may also share one database or one bad deployment.

Disaster recovery starts with a loss scenario and a recovery plan. A backup is a separately retained recovery point; it must be restorable and its age must fit the business requirement. A live second worker gives a route around worker failure, while a verified backup gives a route back to earlier data after deletion or corruption. Neither substitutes for the other.

Shorter recovery objectives generally require more capacity, preparation, automation, and testing.

Follow the state, not just the process

An Order API request has temporary state, such as parsed JSON and a request ID, and durable business state, such as the accepted order and whether fulfillment has occurred. Temporary state may disappear after the response or process restart. Durable state needs an explicit owner, write rule, read path, and recovery method. “Stateless API” describes the worker; the whole order system still has state.

A worker that stores accepted orders only in a Python set can respond “accepted,” yet the set vanishes when its process exits. Starting a second worker creates another empty set. Workers that read and write one transactional database can be replaced without losing committed rows. The database then becomes a critical dependency requiring access control, backups, consistency rules, and its own failure plan.

Brightloaf's fulfillment invariant is stronger than retaining an order. A replayed event must not create another fulfillment. In the local exercise, a unique order ID in a durable table rejects a second insert. Production must additionally define transaction boundaries among order acceptance, event publication, and fulfillment, and decide how conflicting event payloads are handled.

Part 3 — Real-World Problems and Solutions

Incident exercise · A healthy API pair cannot undo a deleted order

Illustrative scenario—not an observed production incident. Brightloaf operates its online Order API using two redundant virtual machine instances (Worker A and Worker B) in region asia-south1 behind a regional load balancer. Both workers connect to a shared Cloud SQL relational database instance. During a period of elevated afternoon traffic, Worker A suffered a localized guest OS kernel panic and halted. The load balancer detected the failed health check within 10 seconds and seamlessly routed 100% of incoming checkout traffic to Worker B. The operations dashboard remained green, displaying 99.99% frontend availability. However, twelve minutes later, an administrator executing a database cleanup script in the production environment accidentally ran an unqualified DELETE command that purged the active orders table. Although both workers continued answering HTTP health check probes, subsequent shopper queries returned HTTP 404 "Order not found" errors, and the warehouse fulfillment pipeline stalled completely.

Constraints and operational invariants: Order records and delivery coordinates must be restored without corrupting new orders submitted post-incident; customer retries and event replays must preserve Brightloaf's fundamental duplicate fulfillment invariant: a replayed event must never trigger duplicate physical warehouse fulfillment (<= 1 fulfillment per unique order ID). Recovery must adhere to the hypothetical business targets of an RTO of 30 minutes and an RPO of 5 minutes.

Evidence and root cause: Cloud Logging and Cloud Monitoring telemetry showed that frontend route availability remained at 100% and Worker B was fully operational, yet application logs recorded hundreds of database query errors and empty result sets. The root cause was an architectural conflation of high availability and disaster recovery: redundant API workers provide routing fault tolerance against worker failure, but they provide zero protection against corrupted or deleted state in a shared data tier. High availability replicated the destructive delete synchronously, rendering both workers incapable of serving legitimate business data.

Diagnostic sequence:

  1. Query the Cloud SQL instance state and audit logs in Cloud Logging to identify the exact timestamp and identity of the destructive administrative operation.
  2. Isolate the database by immediately revoking write permissions or placing the Order API into read-only maintenance mode to prevent incoming writes from overwriting damaged tables.
  3. Identify the latest available automated backup and verify the availability of transaction logs (write-ahead logs or binlogs) for point-in-time recovery (PITR).
  4. Provision a separate, isolated scratch database instance and execute a point-in-time restore to a timestamp exactly one second prior to the accidental deletion.
  5. Reconcile the recovered order rows against external payment gateway settlement logs and message broker event logs to identify any transactional gap between the backup point and the incident cutoff.

Defensible solution: Execute a point-in-time restore from the Cloud SQL automated backup into a staging database instance. Validate the integrity and row counts of the restored orders table. Replay missed transactions verified by payment gateway transaction tokens, ensuring that all inserts use idempotent primary key constraints. Redirect the Order API connection pool to the restored database and resume normal traffic. Implement architectural guardrails to prevent recurrence: apply IAM least privilege by removing direct DDL/DML delete privileges from administrative personal accounts, enforce Cloud SQL instance deletion protection, and establish mandatory Point-in-Time Recovery testing during quarterly disaster recovery drills.

Verification and residual risk: Query the restored database to confirm that 100% of pre-incident committed orders are present; verify that newly submitted test orders persist correctly; simulate replaying an order event from the incident window and confirm that the fulfillment system rejects duplicate processing with HTTP 200 and new_fulfillment: false. Residual risk: In a high-throughput relational database, point-in-time recovery may miss in-flight transactions committed during the minute immediately preceding the disaster if transaction logs were buffering; reconciling against payment provider webhooks mitigates this RPO gap but requires manual administrative sign-off.

Incident exercise · Process memory causes a duplicate fulfillment attempt

Illustrative scenario—not an observed production incident. Brightloaf deployed a revised microservice worker to handle asynchronous order events published by the checkout frontend. To achieve high throughput, the development team implemented event deduplication using an in-memory Python set: when an event arrived, the worker checked whether the order_id existed in its internal set. If absent, the worker added the ID and immediately dispatched a fulfillment message to the automated packaging line. At 11:30 IST, the worker received order event EV-13-001 for customer purchase BL-13-001. Before the worker could transmit an HTTP 200 acknowledgment back to the upstream message broker, the underlying Compute Engine VM experienced an abrupt preemption restart. The message broker, having timed out waiting for the acknowledgment, re-delivered event EV-13-001 to a newly spawned worker instance. Because the new process initialized with a fresh, empty in-memory set, it treated the replayed event as an original order, dispatching a second physical fulfillment command to the warehouse.

Constraints and operational invariants: Worker instances must remain disposable and stateless to enable autoscaling and automatic repair; network and broker delivery is at-least-once, meaning duplicate event delivery is inevitable; under all retry and replay conditions, Brightloaf must strictly maintain the duplicate fulfillment invariant: each unique order must produce at most one physical warehouse shipment.

Evidence and root cause: Warehouse management logs revealed two distinct packing slips generated for order BL-13-001 within 90 seconds of each other. Worker process logs confirmed that two separate PID instances handled the same event ID. The root cause was locating state ownership inside an ephemeral process memory space instead of a durable transactional store. When the process terminated, its deduplication cache evaporated, turning a routine network retry into an unauthorized duplicate shipment.

Diagnostic sequence:

  1. Inspect warehouse fulfillment logs to correlate order identifiers, packing slip timestamps, and handling worker process IDs.
  2. Review Order API and worker source code to identify where event deduplication state and fulfillment tracking are stored and maintained.
  3. Query Compute Engine lifecycle logs to confirm whether worker preemption, autoscaling, or health-check restarts occurred during the duplicate incident window.
  4. Inspect message broker delivery metrics to verify message retry counts and consumer acknowledgment timeouts.
  5. Analyze the database schema to check whether the fulfillment table enforces uniqueness on the business order identifier.

Defensible solution: Strip all state ownership from worker memory and anchor deduplication within a durable transactional database. Alter the fulfillments table to designate order_id as the primary key. When handling an order event, the worker must execute an atomic insert operation (e.g., INSERT OR IGNORE INTO fulfillments (order_id, event_id) VALUES (?, ?)). The worker inspects the database cursor's affected row count: if rowcount == 1, the insert succeeded and the worker dispatches the fulfillment message; if rowcount == 0, the order was previously processed, and the worker safely acknowledges the event while suppressing any secondary fulfillment dispatch. The business invariant is thereby enforced by the database engine regardless of process restarts or concurrent worker threads.

Verification and residual risk: Execute a simulated duplicate submission test where identical order payloads are submitted concurrently to Worker A and Worker B; verify that exactly one database record is created and exactly one fulfillment event is emitted; confirm that replaying the event returns new_fulfillment: false. Residual risk: While database uniqueness prevents duplicate fulfillment records within a single database, distributed transactions across external payment processors and third-party logistics partners still require end-to-end idempotency keys to ensure partner APIs reject duplicate external calls.

Part 4 — Step-by-Step Lab

Lab 13: Restart, share, and restore Brightloaf order state

Goal and expected result

Show that process-owned state disappears when a process exits, while database-owned state is visible to another worker process. Delete the working record, restore a separate backup, and verify that replaying the event does not create a second fulfillment record.

Mode: local Linux terminal with Python 3 and its standard-library SQLite module. No Docker image, emulator, cloud resource, billing account, or network listener is created. Each command starts a fresh process, making the restart boundary explicit. Named workers model replaceable API processes; this lab does not prove live failover, cloud HA, or production RTO/RPO.

2. Create the complete local state model

Copy the entire block. Volatile mode keeps data for one process only. Durable mode uses a SQLite table whose order_id primary key allows one fulfillment record per order.

cat > day13_lab.py <<'PY'
import argparse
import json
import sqlite3
from pathlib import Path

parser = argparse.ArgumentParser()
parser.add_argument('--mode', choices=('volatile', 'durable'), required=True)
parser.add_argument('--action', choices=('submit', 'status', 'backup', 'erase', 'restore'), required=True)
parser.add_argument('--worker', choices=('a', 'b'), default='a')
parser.add_argument('--database', type=Path, default=Path('orders.db'))
parser.add_argument('--snapshot', type=Path, default=Path('orders.backup.db'))
parser.add_argument('--order-id', default='BL-13-001')
parser.add_argument('--event-id', default='EV-13-001')
args = parser.parse_args()

if args.mode == 'volatile':
    if args.action not in ('submit', 'status'):
        parser.error('volatile mode supports only submit and status')
    orders = set()
    if args.action == 'submit':
        orders.add(args.order_id)
        result = {
            'fulfillments': len(orders),
            'new_fulfillment': True,
            'order_id': args.order_id,
            'worker': args.worker
        }
    else:
        result = {
            'fulfillments': len(orders),
            'orders': sorted(orders),
            'worker': args.worker
        }
else:
    if args.action == 'restore':
        if not args.snapshot.is_file():
            parser.error('backup file does not exist')
        with sqlite3.connect(args.snapshot) as source, sqlite3.connect(args.database) as target:
            source.backup(target)
        result = {'restored': True, 'worker': args.worker}
    elif args.action == 'backup':
        if not args.database.is_file():
            parser.error('database does not exist')
        with sqlite3.connect(args.database) as source, sqlite3.connect(args.snapshot) as target:
            source.backup(target)
        result = {'backup_created': True, 'worker': args.worker}
    else:
        with sqlite3.connect(args.database, timeout=5) as database:
            database.execute(
                'CREATE TABLE IF NOT EXISTS fulfillments '
                '(order_id TEXT PRIMARY KEY, event_id TEXT NOT NULL)'
            )
            if args.action == 'submit':
                cursor = database.execute(
                    'INSERT OR IGNORE INTO fulfillments (order_id, event_id) VALUES (?, ?)',
                    (args.order_id, args.event_id)
                )
                count = database.execute(
                    'SELECT COUNT(*) FROM fulfillments'
                ).fetchone()[0]
                result = {
                    'fulfillments': count,
                    'new_fulfillment': cursor.rowcount == 1,
                    'order_id': args.order_id,
                    'worker': args.worker
                }
            elif args.action == 'erase':
                database.execute(
                    'DELETE FROM fulfillments WHERE order_id = ?',
                    (args.order_id,)
                )
                result = {'erased_order': args.order_id, 'worker': args.worker}
            else:
                orders = [
                    row[0] for row in database.execute(
                        'SELECT order_id FROM fulfillments ORDER BY order_id'
                    )
                ]
                result = {
                    'fulfillments': len(orders),
                    'orders': orders,
                    'worker': args.worker
                }

print(json.dumps(result, sort_keys=True))
PY

Checkpoint A — Find the state owner

3. Submit to process memory, then start a fresh process

python3 day13_lab.py --mode volatile --action submit --worker a
python3 day13_lab.py --mode volatile --action status --worker a

Expected output: the first process sees one fulfillment, but the second starts with an empty set. Its worker name is unchanged; its memory is new.

{"fulfillments": 1, "new_fulfillment": true, "order_id": "BL-13-001", "worker": "a"}
{"fulfillments": 0, "orders": [], "worker": "a"}

If memory were the only deduplication record, a replay after restart could be mistaken for a new order.

4. Put fulfillment identity in a durable store

python3 day13_lab.py --mode durable --action submit --worker a --database "$LAB_DIR/orders.db"
python3 day13_lab.py --mode durable --action status --worker b --database "$LAB_DIR/orders.db"
python3 day13_lab.py --mode durable --action submit --worker b --database "$LAB_DIR/orders.db"

Expected output: worker B is a fresh process, yet sees the row committed by A. Replaying the same order adds no second fulfillment.

{"fulfillments": 1, "new_fulfillment": true, "order_id": "BL-13-001", "worker": "a"}
{"fulfillments": 1, "orders": ["BL-13-001"], "worker": "b"}
{"fulfillments": 1, "new_fulfillment": false, "order_id": "BL-13-001", "worker": "b"}

The order-ID primary key is the local invariant guard. The model does not resolve conflicting payloads or coordinate an external shipping system.

Checkpoint B — Separate availability from recovery

5. Capture a separate recovery point

The timestamp identifies this exercise's backup request; by itself it is not an RPO measurement.

date -u '+Backup requested at %Y-%m-%dT%H:%M:%SZ'
python3 day13_lab.py --mode durable --action backup --worker a --database "$LAB_DIR/orders.db" --snapshot "$LAB_DIR/orders.backup.db"
ls -l "$LAB_DIR/orders.db" "$LAB_DIR/orders.backup.db"

Expected: the JSON line below and two distinct nonempty files. File sizes and timestamps vary.

{"backup_created": true, "worker": "a"}

6. Simulate an erroneous deletion

This deletion affects only the disposable database. Worker B reads the damaged working state; another worker does not replace a recovery copy.

python3 day13_lab.py --mode durable --action erase --worker a --database "$LAB_DIR/orders.db"
python3 day13_lab.py --mode durable --action status --worker b --database "$LAB_DIR/orders.db"

Expected output:

{"erased_order": "BL-13-001", "worker": "a"}
{"fulfillments": 0, "orders": [], "worker": "b"}

7. Restore and verify the invariant

In production, restore into isolation and reconcile newer orders before changing the live store. This disposable example has one known row and no concurrent writers.

python3 day13_lab.py --mode durable --action restore --worker a --database "$LAB_DIR/orders.db" --snapshot "$LAB_DIR/orders.backup.db"
python3 day13_lab.py --mode durable --action status --worker b --database "$LAB_DIR/orders.db"
python3 day13_lab.py --mode durable --action submit --worker b --database "$LAB_DIR/orders.db"
date -u '+Recovery verified at %Y-%m-%dT%H:%M:%SZ'

Expected JSON lines:

{"restored": true, "worker": "a"}
{"fulfillments": 1, "orders": ["BL-13-001"], "worker": "b"}
{"fulfillments": 1, "new_fulfillment": false, "order_id": "BL-13-001", "worker": "b"}

For a real recovery drill, record incident start, first useful response, backup creation time, and latest recovered write. Compare measured values with RTO and RPO. This lab's quick local commands establish no production recovery guarantee.

Verification

Pass when volatile state disappears on a new process, worker B sees durable state, replay leaves one fulfillment row, deletion affects the working database, and restoration recovers the row. Final replay must report "new_fulfillment": false.

Troubleshooting
  • python3: command not found: install Python 3 using your Linux distribution's package manager and repeat preflight.
  • can't open file 'day13_lab.py': check your working directory and return to the temporary directory printed in step 1.
  • backup file does not exist: inspect the backup file and complete step 5 before restore.
  • Durable status is zero before deletion: check that every command uses the same --database "$LAB_DIR/orders.db" path.
  • First durable submit reports "new_fulfillment": false: inspect status; an earlier run may have left the row in the same directory.
