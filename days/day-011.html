1 · Topics of the day

IaaS, PaaS, FaaS, SaaS, and where GCP services fall

Cloud service delivery models represent a spectrum of abstraction and operational delegation between cloud tenants and cloud providers. Infrastructure as a Service (IaaS) provides virtualized compute, block storage, and software-defined networking where the customer manages the operating system, runtime, and applications (such as Google Compute Engine). Platform as a Service (PaaS) and Container as a Service (CaaS) abstract host operating systems, allowing developers to deploy container images or application code while Google manages provisioning, scaling, and runtime security (such as Cloud Run and App Engine). Function as a Service (FaaS) narrows the deployment boundary to ephemeral, event-triggered code snippets (such as Cloud Run functions), while Software as a Service (SaaS) provides turnkey managed business applications (such as Google Workspace and BigQuery managed analytics).

Why today and where it sits: Day 11 bridges local containerization from Days 9 and 10 with cloud resource architectures before exploring cloud regions and cost models on Day 12. Service models sit across the computing stack, determining which layers are operated by customer engineers and which are delegated to Google Cloud managed infrastructure.

Problem preview: A Brightloaf development team deploys a stateless order webhook as a cluster of manually managed Compute Engine virtual machines without automated OS patch pipelines, requiring weekend manual maintenance and failing during an OS package update. Customer order callbacks fail during the maintenance window, causing delayed transaction confirmations and increased operational engineering toil.

Shared responsibility model (what Google secures vs what you secure)

The shared responsibility model establishes the contractual boundary between what Google Cloud secures and what the tenant must secure. Google guarantees security of the cloud—encompassing physical datacenter perimeters, custom server silicon (Titan chips), hypervisor isolation, global fiber backbone encryption, and compliance certifications. The customer retains strict ownership of security in the cloud—including identity and access management (IAM) bindings, firewall rules, data classification, customer-managed encryption keys, network egress controls, and application source code integrity. In modern architecture, Google introduces Shared Fate, partnering with customers through opinionated landing zones, risk frameworks, and security blueprints, yet customer data and access policies always remain 100% customer-owned.

Why today and where it sits: Day 11 establishes non-negotiable governance principles before provisioning live cloud sandboxes on Day 18. Shared responsibility sits at the intersection of infrastructure operations, security architecture, and regulatory compliance, ensuring architects do not assume cloud provider automation replaces customer access governance.

Problem preview: After migrating the Order API from virtual machines to Cloud Run, engineers remove the VM operating system patching backlog but simultaneously close all IAM authorization and data retention review tickets under the assumption that a managed runtime handles all security controls. An unauthenticated service invocation endpoint inadvertently exposes sensitive order payment histories to the public internet, violating privacy compliance and exposing Brightloaf to severe regulatory penalties.

2 · Technical discussion of each topic

IaaS, PaaS, FaaS, SaaS, and where GCP services fall

Architectural evaluation begins by asking: what operational capabilities does the workload strictly require, and how much undifferentiated maintenance should the engineering organization retain? Under Infrastructure as a Service (IaaS), Compute Engine provides virtual machines where the tenant controls the guest operating system kernel version, local disk partitioning, system daemons, network interfaces, and runtime environments. This control is necessary for legacy workloads, custom kernel modules, or specific binary drivers, but demands significant ongoing operational overhead—including OS vulnerability patching, kernel updates, image baking, disk resizing, and high-availability configuration.

Platform as a Service (PaaS) and serverless container runtimes like Cloud Run shift host management entirely to Google. The customer packages their application into an OCI container image and configures desired concurrency, memory limits, and environment variables. Google's control plane automatically provisions underlying worker nodes, routes requests, handles TLS certificates, scales container instances from zero to thousands based on incoming HTTP traffic, and applies host kernel security updates without customer intervention. Function as a Service (FaaS), represented in GCP by Cloud Run functions (formerly Cloud Functions), abstracts the container contract further: developers submit pure code snippets triggered by HTTP requests or Pub/Sub events. Software as a Service (SaaS), exemplified by Google Workspace, eliminates software installation and maintenance entirely, providing turnkey software accessed via APIs or browsers. The architect's responsibility is to select the highest level of abstraction that satisfies application constraints, minimizing toil while maintaining required controls.

Shared responsibility model (what Google secures vs what you secure)

The shared responsibility model is not a marketing concept; it is an audit-enforced boundary defining operational, legal, and security liability. When an enterprise deploys workloads on Google Cloud, Google guarantees the security of the cloud. This includes physical security guards, biometric datacenter access, server hardware supply chain verification, custom Titan security microchips on physical motherboards, hypervisor hardening, automated encryption of data-at-rest with default keys, and default encryption of all inter-datacenter network traffic over Google's private fiber network.

Conversely, the customer is exclusively responsible for security in the cloud. Regardless of whether a customer selects Compute Engine, Cloud Run, or BigQuery, Google does not own or configure customer IAM policies. If a tenant binds allUsers to a Cloud Storage bucket or grants roles/editor to an untrusted identity, Google's infrastructure enforces that policy as declared, exposing data without breach of the provider's boundary. Similarly, customer data classification, network perimeter egress rules, application vulnerability mitigation (such as SQL injection or SSRF), database backup schedules, and domain-specific business invariants (such as preventing duplicate order fulfillment) remain 100% customer obligations. Under Google's Shared Fate model, Google equips customers with Cloud Architecture Framework security blueprints, Security Command Center posture scanners, and policy-as-code guardrails, but the ultimate authority and operational burden of configuration resides with the tenant.

3 · Real-world problem and solution for each topic

Incident exercise · The unpatched webhook cluster

Illustrative scenario—not an observed production incident. Brightloaf's third-party shipping carrier delivers asynchronous package tracking updates via an HTTP webhook callback. To handle these webhooks, an engineering team deployed three Compute Engine virtual machines behind a regional load balancer. The VMs were configured manually without automated OS patch pipelines or managed instance group templates. Over eighteen months, security auditors flagged multiple unpatched Linux kernel vulnerabilities (CVEs) on the guest OS. During a scheduled weekend manual patching operation, an engineer ran a kernel package update on the VMs; the update triggered a dependency conflict with the legacy Ruby runtime, causing the service to fail startup. All shipping carrier webhook delivery attempts failed with HTTP 502 Bad Gateway for 14 hours until the team rolled back the OS packages.

Constraints and evidence: Inbound shipping status updates must not be permanently lost; customer notifications must update within 15 minutes of carrier dispatch; the shipping webhook requires zero custom Linux kernel modules or host-level system agents; and the engineering organization must eliminate recurring guest OS maintenance toil.

Evidence and root cause: Reviewing server logs confirms that the webhook code is a single, stateless 150-line HTTP endpoint receiving JSON payloads and writing them to a Pub/Sub topic. Running the service on IaaS (Compute Engine) required the team to take on full responsibility for guest OS patching, security kernel upgrades, disk maintenance, and VM health checks. The root cause was an architectural service-model mismatch: an IaaS delivery model was chosen for a purely stateless, event-driven web application that naturally belonged on a managed serverless platform (PaaS/CaaS).

Diagnostic sequence:

  1. Inspect the webhook application architecture to verify runtime dependencies, verifying that no custom kernel modules or hardware drivers are required.
  2. Audit VM maintenance logs to determine total engineering hours spent on guest OS package updates, security patching, and server monitoring.
  3. Analyze incoming traffic patterns to observe that request volume fluctuates from zero requests at night to several hundred requests per second during morning dispatch windows.
  4. Evaluate containerization feasibility by packaging the webhook into a minimal container image.
  5. Compare operational responsibilities between Compute Engine (IaaS) and Cloud Run (PaaS).

Defensible solution: Re-platform the shipping webhook service from Compute Engine to Cloud Run (PaaS/CaaS). Package the application into an immutable container image and deploy it with Cloud Run autoscaling (scaling from 0 to 50 container instances). Google assumes full operational ownership of host VM provisioning, operating system security updates, container sandbox patching, and HTTP load balancing. Brightloaf retains ownership only of the application container image, Pub/Sub IAM publisher permissions, and incoming payload validation.

Verification and residual risk: Send synthetic shipping status payloads to the new Cloud Run service; verify that HTTP 200 responses return in under 80 ms; inspect Cloud Monitoring to verify automatic scaling from 0 to 10 instances under load and back to 0 when idle; confirm that carrier delivery retries succeed without duplicate tracking records. Residual risks include cold start latency (typically 500 ms for container spin-up), which is mitigated by configuring a minimum instance count of 1 during business hours.

Incident exercise · The public serverless order leak

Illustrative scenario—not an observed production incident. Brightloaf migrated its internal Order Query API from a private VPC virtual machine into a Cloud Run service to take advantage of serverless scaling. During migration planning, team members celebrated that "Google manages all infrastructure security on Cloud Run." Operating under this flawed assumption, the team closed their quarterly IAM review tickets and removed the private VPC firewall rules. When developers noticed initial 403 Forbidden errors when connecting their frontend dashboard, an engineer added the IAM policy binding allUsers with the role roles/run.invoker to "fix authentication." Two weeks later, an external threat researcher notified Brightloaf that customer order history, postal addresses, and encrypted payment tokens were freely queryable over the public internet by anyone possessing an order UUID.

Constraints and evidence: Public internet access to order records must be terminated immediately; authorized internal microservices (such as Customer Support and Warehouse Dispatch) must maintain uninterrupted access; and the fix must demonstrate compliance with the shared responsibility model without rolling back the serverless deployment.

Evidence and root cause: Audit logs confirm that the Cloud Run service had ingress settings set to all (allowing direct public internet traffic) and an IAM binding granting roles/run.invoker to allUsers. The root cause is a fundamental misunderstanding of the shared responsibility model. While Google provides a secure, hardened container runtime sandbox, Google does not decide who is authorized to invoke customer endpoints. The customer alone owns IAM policies, access control bindings, and network ingress boundaries. Granting public invocation rights was an entirely customer-side authorization misconfiguration.

Diagnostic sequence:

  1. Query the Cloud Run service IAM policy using the Google Cloud CLI or Console to inspect member bindings for roles/run.invoker.
  2. Inspect service ingress networking settings to determine whether the service is exposed to the public internet or restricted to internal traffic.
  3. Analyze Cloud Audit Logs (Data Access logs) to determine whether unauthenticated external IP addresses queried customer order records.
  4. Review application authentication logic to confirm that the container application relied entirely on the platform layer for authentication.
  5. Establish the corrected security perimeter according to the shared responsibility matrix.

Defensible solution: Execute a three-part IAM and network remediation: first, immediately remove the allUsers binding from the Cloud Run service; second, bind roles/run.invoker exclusively to authorized Google Cloud Service Accounts (such as sa-checkout@brightloaf.iam.gserviceaccount.com), requiring all callers to supply valid Google-signed OIDC identity tokens; third, update Cloud Run ingress settings from all to internal-and-cloud-load-balancing, ensuring that all traffic must originate from within the authorized VPC or pass through an authenticated internal Application Load Balancer.

Verification and residual risk: Send an unauthenticated HTTP GET request to the Cloud Run endpoint from an external network; verify that Google's edge gateway immediately rejects the request with HTTP 403 Forbidden; generate a signed Google Cloud OIDC token for the authorized service account and re-send the request, verifying an HTTP 200 response with order details; inspect Cloud Audit Logs to confirm zero unauthenticated requests penetrate the boundary. Residual risks include service account token leakage in client applications, which is mitigated by enforcing short-lived token lifetimes (1 hour maximum) and workload identity federation.

Step 2 — Execute the IAM policy audit simulation

Run a Python script that parses simulated IAM policy declarations for a Cloud Run service and flags shared responsibility violations (such as public allUsers invoker grants):

python3 - <<'PY'
simulated_iam_policy = {
    "bindings": [
        {
            "role": "roles/run.invoker",
            "members": [
                "allUsers"  # Security violation!
            ]
        },
        {
            "role": "roles/run.viewer",
            "members": [
                "group:auditors@brightloaf.com"
            ]
        }
    ]
}

print("=== AUDITING CLOUD RUN IAM POLICY (SHARED RESPONSIBILITY CHECK) ===")
violations = []
for binding in simulated_iam_policy["bindings"]:
    role = binding["role"]
    for member in binding["members"]:
        if member in ["allUsers", "allAuthenticatedUsers"]:
            violations.append(f"CRITICAL: Public access granted to [{role}] via [{member}]")

if violations:
    print("STATUS: VIOLATION DETECTED!")
    for v in violations:
        print(f"  ✗ {v}")
    print("\nRemediating policy: Removing allUsers and restricting to authorized Service Account...")
    # Remediate
    simulated_iam_policy["bindings"][0]["members"] = ["serviceAccount:sa-checkout@brightloaf.iam.gserviceaccount.com"]
    print("STATUS: REMEDIATED -> New member binding: serviceAccount:sa-checkout@brightloaf.iam.gserviceaccount.com")
else:
    print("STATUS: CLEAN -> No public access bindings detected.")
PY

Expected output: The script detects the critical violation, removes allUsers, and replaces it with the authenticated service account binding.
