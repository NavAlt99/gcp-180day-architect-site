1. Shared responsibility for compliance (Google's certifications do not make your workload…

A dangerous and recurring enterprise architectural anti-pattern is assuming that deploying a workload into Google Cloud automatically inherits Google's compliance certifications. While Google Cloud is certified under ISO 27001, SOC 2, PCI-DSS, and FedRAMP, this certification covers only the underlying physical data centers, hardware, and managed hypervisors. The customer remains 100% accountable for application configuration, IAM least privilege, firewall rule authoring, encryption key governance, vulnerability management, and audit logging.

Problem preview: An enterprise fintech startup assumes its app is PCI-compliant because it runs on GCP; the external Qualified Security Assessor (QSA) fails the audit due to unencrypted public storage buckets and broad IAM permissions.

1. Shared responsibility for compliance (Google's certifications do not make your workload…: technical mechanics

1. Shared Responsibility vs. Shared Fate

  • Infrastructure Layer (Google): Physical data center security, environmental controls, hardware lifecycle destruction, hypervisor kernel isolation, and underlying network encryption.
  • Platform & Configuration Layer (Shared): Service agents, managed platform patch cycles (e.g. Cloud Run, GKE), and baseline API security features.
  • Workload & Data Layer (Customer): Identity lifecycle, IAM role bindings, VPC routing, data classification, CMEK rotation, application vulnerability remediation, and audit log monitoring.

2. The Customer Responsibility Matrix (CRM)

  • For frameworks like PCI-DSS and FedRAMP, Google publishes a Customer Responsibility Matrix (CRM) mapping every individual requirement (e.g. PCI Requirement 10: Log and Monitor All Access) to specific customer actions.

2. Standards to know at a conceptual level: technical mechanics

1. Framework Taxonomy & Cross-Mapping

  • Broad Governance & Management: ISO/IEC 27001 (Plan-Do-Check-Act ISMS lifecycle), SOC 2 Type II (attestation evaluating operational effectiveness over a minimum 6-month period across Security, Availability, and Confidentiality).
  • Prescriptive Technical Hardening: CIS Google Cloud Foundations Benchmark (actionable configuration rules for IAM, Logging, Networking, and Storage), NIST SP 800-53 Rev 5 (comprehensive catalog of federal security controls).
  • Domain-Specific Regimes: PCI-DSS v4.0 (Payment cards, CDE scope reduction via tokenization), HIPAA / HITECH (PHI protection via Business Associate Agreements), GDPR (EU data subject rights, right to erasure, data transfer SCCs).

2. CIS Google Cloud Foundations Benchmark Pillars

  • Section 1 (Identity & Access Management): Enforce MFA on all human accounts; disable service account key creation.
  • Section 2 (Logging & Monitoring): Ensure log sinks capture all administrative and IAM policy modifications.
  • Section 3 (Networking): Eliminate default VPC networks; restrict SSH/RDP ingress to IAP range 35.235.240.0/20.
  • Section 4 (Storage): Ensure storage buckets enforce uniform bucket-level access and CMEK encryption.

Architectural evaluation questions

  • What is the operational difference between a SOC 2 Type I report and a SOC 2 Type II report?
  • How does implementing the CIS Google Cloud Foundations Benchmark assist in achieving compliance across ISO 27001 and PCI-DSS?
  • What legal instrument must be executed with Google Cloud before any Protected Health Information (PHI) can be ingested under HIPAA?

Further study: Google Cloud Compliance: Framework mappings and certified offerings catalog.

3. Compliance resource centre and compliance reports manager: technical mechanics

1. Compliance Reports Manager Architecture

  • Self-Service Access: Accessible directly from Google Cloud Console or the public Compliance Resource Center.
  • Non-Disclosure Agreement (NDA) Gating: Public reports (SOC 3, ISO certificates) are downloadable instantly; confidential reports (SOC 1/2 Type II, FedRAMP packages) require electronic agreement to an NDA.
  • Report Types Available:
  • SOC 1 Type II (SSAE 18 / ISAE 3402): Focuses on controls relevant to user organizations' financial reporting.
  • SOC 2 Type II: Comprehensive assessment of Security, Availability, and Confidentiality.
  • PCI-DSS AoC: Formal sign-off by a Qualified Security Assessor for Level 1 Service Provider compliance.
  • ISO Certificates: ISO 27001, ISO 27017 (Cloud Security), ISO 27018 (Cloud Privacy), ISO 27701 (Privacy Info).

2. Operational Evidence Harvesting & Audit Package Preparation

  • Architects combine Google Cloud's external audit reports with the organization's internal Cloud Audit logs and Terraform IaC manifests to produce a complete, unified audit evidence package for regulatory examiners.

Architectural evaluation questions

  • What is the operational difference between public compliance reports (e.g. SOC 3) and confidential reports (e.g. SOC 2 Type II) in Compliance Reports Manager?
  • How does an enterprise architect utilize the Google Cloud PCI Attestation of Compliance (AoC) in their own PCI QSA audit?
  • Why should compliance teams establish an automated annual schedule for harvesting newly published SOC and ISO reports?

1. Shared responsibility for compliance (Google's certifications do not make your workload… · field case

Enterprise scenario: External PCI Qualified Security Assessor (QSA) halts an annual compliance audit, issuing an immediate Failure notice for Requirement 1 (Network Security Controls).

Constraints: Cardholder Data Environment (CDE) must pass annual PCI-DSS Level 1 assessment to maintain credit card processing authorization.

Evidence:

QSA Assessment Deficiency Notice excerpt:

PCI-DSS v4.0 Non-Compliance Finding: Req 1.2.1 / 1.3.1
Finding: Customer CDE VPC network contains default ingress firewall rule "default-allow-ssh" permitting 0.0.0.0/0 on port 22.
Customer Defense: "GCP is PCI-certified; infrastructure firewalls are Google's responsibility."
QSA Finding: REJECTED. Ingress firewall configuration is explicitly designated as Customer Responsibility in the Google Cloud PCI CRM.

Analysis: The cloud engineering team left default VPC networks and open ingress firewall rules active, operating under the mistaken belief that Google managed firewall ingress policies.

Root cause: Engineering team confused cloud provider physical network certification with customer VPC firewall configuration duties.

Diagnostic sequence:

  1. Review the Google Cloud PCI-DSS Customer Responsibility Matrix for Requirement 1.
  2. Audit all VPC networks in the CDE project using <kbd>gcloud compute firewall-rules list</kbd>.
  3. Identify and isolate instances with public external IP addresses.
  4. Inspect Cloud Audit logs for unauthorized SSH access attempts from the internet.

Defensible remediation: Deprovision default VPC networks, delete all `0.0.0.0/0` administrative ingress rules, enforce IAP TCP forwarding, and apply deny-by-default firewall policies.

Verification: Re-scan VPC with automated security posture scanner; confirm 100% compliance with PCI-DSS network segmentation rules.

Residual risk: Third-party vendor SaaS integrations crossing the CDE boundary require continuous reciprocal firewall auditing.

2. Standards to know at a conceptual level · field case

Enterprise scenario: Healthcare application onboarding is halted by chief legal counsel: database contains patient medical records without executed BAA.

Constraints: Workload must comply with HIPAA Privacy and Security Rules; civil monetary penalties apply for uncertified PHI ingestion.

Evidence:

Internal compliance officer audit memorandum:

HIPAA Compliance Defect Report - Project: patient-telemetry-prod
Status: NON-COMPLIANT (CRITICAL RISK)
Finding: Project is processing electronic Protected Health Information (ePHI) across Cloud SQL and Cloud Storage.
Defect 1: Google Cloud Business Associate Agreement (BAA) has not been digitally executed in the Cloud Console.
Defect 2: Cloud Audit Data Access logs for BigQuery and Cloud Storage are disabled, violating 45 CFR § 164.312(b).

Analysis: Developers deployed clinical workloads into a standard GCP project without executing the mandatory BAA or enabling required Data Access audit log categories.

Root cause: The organization ingested ePHI prior to executing the Google Cloud BAA and failed to enable mandatory HIPAA Data Access audit logs.

Diagnostic sequence:

  1. Check Google Cloud Console compliance settings to verify BAA execution state.
  2. Inspect project-level audit logging configuration for `DATA_READ` and `DATA_WRITE` enablement.
  3. Verify that all services storing ePHI are listed on Google Cloud's HIPAA-included services list.
  4. Check encryption at rest configurations on target Cloud SQL and Cloud Storage resources.

Defensible remediation: Execute Google Cloud BAA via the Google Workspace/Cloud Console, enable Data Access audit logging for all HIPAA-included services, and lock log sinks.

Verification: Confirm BAA execution status is Active; verify Cloud Logging captures all patient record queries in tamper-proof sinks.

Residual risk: Non-included Google Cloud services must never be used to process or store ePHI.

3. Compliance resource centre and compliance reports manager · field case

Enterprise scenario: Enterprise SaaS procurement deal stalls because the prospect's security team requires an independent third-party audit report verifying data center physical controls.

Constraints: The prospect will not accept vendor self-attestations; requires an accredited CPA firm's SOC 2 Type II examination report.

Evidence:

Enterprise procurement security questionnaire item 4.12:

Questionnaire Item 4.12: Physical & Environmental Security Controls
Requirement: Provide independent third-party auditor report verifying physical access restrictions, biometric controls, and environmental safeguards for all cloud hosting facilities.
SaaS Vendor Initial Response: "We host on GCP and Google is secure." (REJECTED by customer risk committee).

Analysis: Vendor sales engineers failed to utilize the Compliance Reports Manager to deliver the authoritative Google Cloud SOC 2 Type II report and Customer Responsibility Matrix.

Root cause: The team provided informal vendor assurances rather than downloading authoritative independent auditor attestations from Compliance Reports Manager.

Diagnostic sequence:

  1. Access Google Cloud Compliance Reports Manager via Cloud Console.
  2. Search for the latest SOC 2 Type II Google Cloud Services examination report.
  3. Accept the electronic NDA terms and download the verified PDF report package.
  4. Cross-reference Customer Responsibility Matrix sections addressing customer physical custody boundaries.

Defensible remediation: Retrieve the formal Google Cloud SOC 2 Type II and SOC 3 reports from Compliance Reports Manager and provide them alongside internal security policies.

Verification: Customer risk committee approves vendor security review based on accredited CPA SOC 2 Type II attestation.

Residual risk: Auditors require updated SOC 2 reports annually upon expiration of the current evaluation period.

firewall_rules = [
    {
        "name": "default-allow-ssh",
        "source": "0.0.0.0/0",
        "port": 22,
        "action": "ALLOW",
        "network": "default"
    },
    {
        "name": "default-allow-rdp",
        "source": "0.0.0.0/0",
        "port": 3389,
        "action": "ALLOW",
        "network": "default"
    },
    {
        "name": "allow-iap-admin-ssh",
        "source": "35.235.240.0/20",
        "port": 22,
        "action": "ALLOW",
        "network": "cde-vpc"
    },
    {
        "name": "allow-internal-mesh",
        "source": "10.128.0.0/16",
        "port": 8443,
        "action": "ALLOW",
        "network": "cde-vpc"
    }
]

print("================================================================")
print("PCI-DSS / CIS BENCHMARK FIREWALL COMPLIANCE AUDITOR")
print("================================================================")

def evaluate_rule(rule: dict) -> tuple[bool, str]:
    if rule["source"] == "0.0.0.0/0" and rule["port"] in [22, 3389] and rule["action"] == "ALLOW":
        return False, f"CRITICAL DEFICIENCY: Port {rule['port']} exposed to public internet (0.0.0.0/0)"
    if rule["network"] == "default":
        return False, "HIGH DEFICIENCY: Use of legacy default VPC network in CDE"
    return True, "COMPLIANT (Scoped source and authorized network)"

for r in firewall_rules:
    passed, reason = evaluate_rule(r)
    status = "PASS" if passed else "FAIL"
    print(f"[{status:4s}] Rule: {r['name']:24s} | Network: {r['network']:8s} | Result: {reason}")

print("================================================================")
EOF

class CISBenchmarkAuditor:
    def __init__(self, project_config: dict):
        self.cfg = project_config

    def audit_section_1_iam(self) -> list[dict]:
        findings = []
        # 1.1 Service account keys
        if self.cfg.get("sa_keys_count", 0) > 0:
            findings.append({"id": "CIS-1.1", "status": "FAIL", "msg": "Service accounts have downloadable private keys."})
        else:
            findings.append({"id": "CIS-1.1", "status": "PASS", "msg": "Zero downloadable service account keys present."})
        # 1.2 Separation of duties
        if "roles/owner" in self.cfg.get("service_account_roles", []):
            findings.append({"id": "CIS-1.2", "status": "FAIL", "msg": "Service account possesses project Owner role."})
        else:
            findings.append({"id": "CIS-1.2", "status": "PASS", "msg": "Least-privilege service account roles enforced."})
        return findings

    def audit_section_2_logging(self) -> list[dict]:
        findings = []
        if not self.cfg.get("audit_sink_configured", False):
            findings.append({"id": "CIS-2.1", "status": "FAIL", "msg": "No centralized log sink exported to secure storage."})
        else:
            findings.append({"id": "CIS-2.1", "status": "PASS", "msg": "Centralized audit log export sink active."})
        return findings

mock_gcp_project = {
    "project_id": "brightloaf-enterprise-core",
    "sa_keys_count": 0,
    "service_account_roles": ["roles/storage.objectViewer", "roles/logging.logWriter"],
    "audit_sink_configured": True
}

auditor = CISBenchmarkAuditor(mock_gcp_project)
print("================================================================")
print(f"CIS BENCHMARK SECURITY SCAN: {mock_gcp_project['project_id']}")
print("================================================================")
all_findings = auditor.audit_section_1_iam() + auditor.audit_section_2_logging()
for f in all_findings:
    print(f"[{f['status']:4s}] {f['id']:8s}: {f['msg']}")
print("================================================================")
EOF
