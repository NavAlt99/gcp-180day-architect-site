1 · Topics of the day

Instance templates and Managed Instance Groups (MIGs)

An Instance Template is an immutable Google Cloud resource that defines the blueprint for virtual machines: machine family, boot disk image, attached persistent disks, network interfaces, service account, labels, and startup script metadata. A Managed Instance Group (MIG) uses this template to instantiate and operate a pool of homogeneous, identical instances as a single logical entity. The MIG control plane automates instance creation, health maintenance, recreation of crashed VMs, and integration with Cloud Load Balancing.

Because individual instances in a stateless MIG are ephemeral and treated as disposable cattle rather than pets, all configuration must reside in the template or be pulled dynamically via startup scripts and Secret Manager. Attempting to modify a running VM directly creates configuration drift that disappears the moment the MIG replaces the instance.

Problem preview: An operator applies an emergency software patch directly via SSH to a running VM in a MIG, but does not update the instance template. Under the next autoscaling event or automated health recreation, the patched VM is deleted and replaced by a fresh instance booted from the unpatched template, silently reintroducing the vulnerability and breaking order processing.

Zonal vs regional MIGs

A Zonal MIG allocates all its managed instances into a single zone within a region. A Regional MIG distributes instances across multiple zones (typically three) in a region, providing resilience against single-zone hardware, power, or facility failures. Regional MIGs also offer configurable target distribution shapes, such as EVEN (equal instance count per zone) or ANY / BALANCED (deploying into zones with available hardware capacity).

For stateless microservices such as the Brightloaf Order API, a regional MIG provides high availability without requiring custom cross-zone orchestration. However, spreading instances across zones introduces cross-zone networking considerations and requires ensuring adequate regional vCPU quota and capacity reservations.

Problem preview: The Brightloaf Order API is deployed in a single zonal MIG in us-central1-a to avoid cross-zone networking overhead. A facility impairment in us-central1-a knocks out all API instances simultaneously, causing total downtime for order ingestion and customer checkout abandonment for over forty minutes.

Autoscaling policies (CPU, load balancing utilization, custom metrics, schedules)

Compute Engine Autoscalers dynamically adjust the number of instances in a MIG to match workload demand. Autoscaling signals include average target CPU utilization, Cloud Load Balancing serving capacity (target utilization or request rate per instance), Cloud Monitoring custom metrics (such as a Pub/Sub queue backlog), and recurring time-based schedules.

A critical parameter in every autoscaling policy is the cool-down period (or initialization period). This defines how long the autoscaler ignores performance metrics from a newly created instance while its operating system, JVM runtime, and application caches initialize. If the cool-down period is shorter than the application's actual startup time, premature metrics cause false overload signals, leading to rapid over-scaling, quota exhaustion, and thrashing.

Problem preview: The Order API autoscaler is configured with an aggressive 30-second cool-down period, but the service requires 90 seconds to warm up its JVM and load in-memory pricing rules. During a morning traffic surge, initializing instances peg CPU during warm-up, causing the autoscaler to violently add instances until the regional vCPU quota is exhausted, leading to connection resets and service degradation.

Instance templates and Managed Instance Groups (MIGs)

The immutability principle

Instance templates in Compute Engine are strictly immutable. Once created, an instance template cannot be modified. To update any configuration—whether updating a container tag, changing machine family, modifying a startup script, or attaching a new disk—an engineer must create a new instance template version (or copy from an existing one) and point the MIG to the new template.

This immutability ensures that every instance spawned by the MIG is guaranteed to have identical, reproducible configuration. When an instance crashes, stops responding to health checks, or is terminated by autoscaling, the MIG manager creates a replacement instance directly from the active template.

Zonal vs regional MIGs

Failure boundaries and distribution algorithms

A Zonal MIG exists solely inside one zone (e.g., us-central1-a). If that zone suffers an infrastructure degradation, all instances in the group are vulnerable. In contrast, a Regional MIG operates across multiple zones within the same region (e.g., us-central1-a, us-central1-b, us-central1-c).

Regional MIGs provide two distinct zone distribution shapes:

  • EVEN (Default): The MIG distributes instances equally across all configured zones (e.g., 9 instances across 3 zones = 3 instances per zone). If an instance is deleted or scales down, the MIG maintains balance.
  • ANY / BALANCED: The MIG distributes instances to zones where hardware capacity and quota are available. If one zone experiences a capacity constraint, the MIG allocates instances to the surviving zones.
Dimension Zonal MIG Regional MIG
Failure Boundary Single zone (0% tolerance for zone failure) Region (survives loss of 1 or 2 zones)
Network Cost Zero cross-zone data transfer within group Potential inter-zone ingress/egress charges if communicating across zones
Capacity Resiliency Bound to zonal stockout risks Absorbs zonal capacity shortages by expanding into other zones
Target Workload Batch jobs with local disk latency constraints, test environments Production web APIs, order ingestion, customer-facing services

Autoscaling policies (CPU, load balancing utilization, custom metrics, schedules)

Autoscaling signals and decision mechanics

The Compute Engine Autoscaler evaluates performance telemetry every 10–15 seconds to determine whether the current instance pool satisfies the target utilization. Multiple signals can be combined; the autoscaler chooses the largest recommended instance count among all configured policies:

  • Target CPU utilization: Scales to keep the average vCPU utilization across the fleet at a target percentage (e.g., 60%).
  • Load balancing serving capacity: Integrates directly with Cloud Load Balancing backends to maintain a target number of requests per second (RPS) or target backend utilization per instance.
  • Cloud Monitoring metrics: Uses custom or system metrics, such as Pub/Sub undelivered message count per worker.
  • Schedules: Pre-provisions capacity for predictable, recurring traffic spikes (e.g., 08:00 AM daily peak).

The initialization / cool-down window

When a new VM boots, its initialization script downloads packages, starts runtimes (e.g. JVM), and warms caches. During this phase, CPU usage is typically elevated and the instance is not yet ready to serve production load. The cool-down period instructs the autoscaler to ignore metrics from that VM until the specified time elapses. Setting this value too low leads to false over-scaling cascades; setting it too high makes the fleet sluggish to respond to real surges.

3 · Real-world problems and solutions

The scenarios below represent realistic failure modes encountered in production GCP environments with Managed Instance Groups. Values and traces are synthetic models grounded in architectural principles.

Topic 1 field case — Live manual patching overwritten by MIG instance autohealing

Situation and business impact

During a security vulnerability alert, a systems engineer at Brightloaf logs in via SSH to an active VM (order-api-01) inside the production Managed Instance Group. The engineer manually compiles and updates an OpenSSL shared library and patches the order validation logic directly in /opt/brightloaf/bin/. The API passes immediate health checks, and the vulnerability scanner reports clear for that VM.

Four hours later, during evening checkout traffic, the VM experiences a brief network transient causing two consecutive failed HTTP health probes. The MIG health manager immediately terminates the unhealthy instance and provisions a replacement VM from the active Instance Template. Because the template still points to the old disk image and unpatched startup script, the new instance launches with the unpatched binary. Concurrently, order requests routed to the new VM encounter missing dependencies, generating HTTP 500 errors and corrupting cart states.

Constraints

  • Stateless MIG VMs must be treated as ephemeral; manual configuration state is never persistent.
  • Production deployments must preserve the invariant that replaying an order event never triggers a duplicate fulfillment.
  • All VM updates must be traceable through versioned instance templates.

Root cause

Treating a managed instance as a mutable "pet" rather than disposable infrastructure. When the instance was automatically recreated, all out-of-band manual changes applied to the root filesystem vanished because the instance template was never updated to a new version.

Diagnostic sequence

  1. Inspect Compute Engine system event logs: gcloud compute operations list --filter="targetLink:order-api" reveals an instance recreation event triggered by autohealing.
  2. Describe the newly created instance: gcloud compute instances describe INSTANCE_NAME confirms its source template is still version 1.
  3. Verify that the patch was applied only to the deceased VM's ephemeral root disk and not stored in any golden image, repository, or startup script.

Defensible solution

Establish an immutable release pipeline: bake the patched binary into a new versioned golden image (or container artifact). Create a new instance template (order-api-template-v2). Update the MIG to point to the new template using a rolling-action update (gcloud compute instance-groups managed rolling-action start-update) with controlled max-surge and max-unavailable limits.

Verification

Trigger a simulated instance recreation (gcloud compute instance-groups managed recreate-instances). Verify that the freshly spawned VM automatically boots with the patched library, executes startup verification tests, and responds with HTTP 200 on all order endpoints.

Residual risk

Rolling updates require sufficient project vCPU quota to support max-surge instances. If regional quota is tight, surge provisioning will stall until quota is increased.

Topic 2 field case — Zonal MIG outage during unexpected data center facility impairment

Situation and business impact

To save on perceived inter-zone egress networking costs, the Brightloaf Order API service was deployed in a single Zonal MIG locked to us-central1-a with a target capacity of 8 instances. During a severe local power distribution failure in that facility, Google Cloud declared a zone-wide disruption in us-central1-a.

Because all instances in the Zonal MIG resided in us-central1-a, 100% of the API fleet became unreachable simultaneously. Ingress traffic hitting the global HTTP(S) Load Balancer returned HTTP 502 Bad Gateway errors. Order ingestion completely halted for 45 minutes until cloud operations stabilized the physical facility, causing immediate customer checkout drop-off and support call overload.

Constraints

  • Business SLA mandates 99.95% availability for the Order API ingestion path.
  • The architecture must withstand the complete and sudden loss of any single availability zone.
  • Replaying pending client requests after recovery must not create duplicate order records in Cloud SQL.

Root cause

Single point of failure at the zone level. The team chose a Zonal MIG without evaluating the failure domain against their availability target.

Diagnostic sequence

  1. Examine Cloud Monitoring uptime checks: 100% packet loss to the backend service.
  2. Check Google Cloud Service Health Dashboard: Active incident impacting Compute Engine in us-central1-a.
  3. Inspect MIG status: gcloud compute instance-groups managed list shows zone us-central1-a with all 8 instances in an unreachable state.

Defensible solution

Migrate from a Zonal MIG to a Regional MIG spread across us-central1-a, us-central1-b, and us-central1-c with target distribution shape set to EVEN. When one zone fails, Cloud Load Balancing health checks immediately withdraw the impacted zone's backends, routing 100% of user traffic to healthy instances in zones B and C while the regional autoscaler expands capacity in the surviving zones.

Verification

Conduct a zone-failure simulation in staging: simulate zonal failure by draining and cordoning instances in one zone. Verify that the load balancer seamlessly redistributes HTTP requests to the remaining two zones without dropped connections, maintaining <1% latency degradation.

Residual risk

During a zone outage, surviving zones absorb the entire traffic load. If the regional MIG's max-instances limit or regional quota does not permit sufficient scale-out in the remaining zones, the surviving instances may become CPU-throttled.

Topic 3 field case — Premature autoscaler cool-down period causes JVM warm-up runaway scaling

Situation and business impact

Brightloaf deployed an autoscaling policy targeting 60% average CPU utilization for the Order API service. In an effort to make scaling "lightning fast," the DevOps engineer set the autoscaler's cool-down period to 30 seconds. The underlying service is a Java-based Spring Boot microservice that requires approximately 90 seconds to unpack application jars, perform JVM Just-In-Time (JIT) compilation, warm local caches, and open database connection pools.

During a 09:00 AM breakfast order spike, CPU usage rose to 68%, prompting the autoscaler to launch 2 additional instances. At second 31, the newly created instances were still undergoing heavy JVM startup compilation (reporting 95% CPU) and could not yet accept traffic. The autoscaling engine, seeing average fleet CPU now spike to 78%, concluded that the load had intensified and immediately ordered 4 more instances. This loop repeated every 30 seconds until the group hit its maximum limit and exhausted the project's regional Compute Engine vCPU quota.

Constraints

  • The autoscaler must scale out promptly to absorb legitimate traffic growth.
  • Must not exhaust project regional vCPU quotas on unready, initializing instances.
  • Application initialization characteristics must be measured and directly reflected in infrastructure timing parameters.

Root cause

The cool-down period (30s) was substantially shorter than the application's actual initialization duration (90s). The autoscaler treated initialization CPU burn as serving workload demand, causing cascading over-provisioning and quota depletion.

Diagnostic sequence

  1. Correlate Cloud Monitoring metrics: Plot instance_group/size against instance/cpu/utilization over time. Observe that instance count rises in step-function jumps while CPU stays pinned at 90%+.
  2. Review instance boot logs: Inspect syslog timestamps to measure exact duration between VM boot and the application's "Started Application in X seconds" log line (measured at 88 seconds).
  3. Review autoscaling configuration: Confirm coolDownPeriodSec is set to 30s.

Defensible solution

Calibrate the cool-down period to exceed the measured warm-up time: set coolDownPeriodSec to 120 seconds (90s boot + 30s buffer). Additionally, configure scale-in controls to prevent rapid oscillation (e.g., maximum scale-in of 20% or 2 instances per 5-minute trailing window).

Verification

Subject the staging environment to a synthetic load test step-jump. Verify that the autoscaler adds instances, waits the full 120 seconds for the new instances to report steady serving metrics, and stabilizes fleet CPU at 60% without runaway scaling or quota exhaustion.

Residual risk

A longer cool-down period means the group will not launch subsequent scale-out batches until the cool-down window passes. If incoming traffic spikes faster than one batch can absorb, target CPU utilization may temporarily exceed 60% during the warm-up window.

Exercise 1 — Instance Template authoring and validation

Goal: Author a declarative, reproducible Instance Template specification for the Brightloaf Order API service and verify immutable properties.

Mode: tabletop design / cloud sandbox · Prerequisites: Day 37 exit artifact (storage and metadata decisions).

Preflight

Open day-038-scaling.md. Define the target service parameters: Machine family e2-standard-2, Debian 12 golden image, pd-balanced 20GB boot disk, and service account with roles/monitoring.metricWriter.

  1. Define the template command. Formulate the declarative creation command: 
    gcloud compute instance-templates create order-api-template-v1 \
  --project=PROJECT_ID \
  --machine-type=e2-standard-2 \
  --image-family=debian-12 \
  --image-project=debian-cloud \
  --boot-disk-type=pd-balanced \
  --boot-disk-size=20GB \
  --network=default \
  --tags=order-api,http-server \
  --metadata=startup-script="#!/bin/bash
echo 'Starting Order API' > /var/log/startup.log" \
  --labels=service=order-api,env=production,version=v1
  2. Evaluate template immutability. In your notes, document what occurs if an operator attempts to change the machine type of order-api-template-v1 via CLI. Note: The API rejects edits; an operator must create order-api-template-v2 and update the instance group manager.
  3. Inspect template configuration. If running in a sandbox, describe the template: 
    gcloud compute instance-templates describe order-api-template-v1 \
  --project=PROJECT_ID \
  --format="yaml(name,properties.machineType,properties.disks)"
Expected result

A validated instance template specification recorded in day-038-scaling.md with machine parameters, disk types, and immutability rules clearly stated.

Exercise 2 — Regional vs Zonal MIG capacity and blast radius analysis

Goal: Model capacity distribution and calculate survivable load under single-zone failure for Zonal vs Regional MIGs.

Mode: tabletop / design · Prerequisites: Exercise 1 template definition.

  1. Formulate the Regional MIG specification. Define a 3-zone regional group in us-central1: 
    gcloud compute instance-groups managed create order-api-rmig \
  --project=PROJECT_ID \
  --region=us-central1 \
  --zones=us-central1-a,us-central1-b,us-central1-c \
  --template=order-api-template-v1 \
  --size=6 \
  --instance-redistribution-type=PROACTIVE \
  --target-distribution-shape=EVEN
  2. Model the single-zone failure matrix. Draw a comparison table in day-038-scaling.md:
    • Total Fleet Size: 6 instances.
    • Zonal MIG (all in Zone A): Zone A down → 0 instances remaining (0% serving capacity, 100% outage).
    • Regional MIG (EVEN: 2 in A, 2 in B, 2 in C): Zone A down → 4 instances remaining (66.7% serving capacity, 0% complete outage).
  3. Evaluate failover capacity headroom. Calculate the required minimum fleet size such that losing 1 zone still satisfies 100% of peak traffic without autoscaling delay:

    If peak load requires 6 instances, total provisioned capacity must be 6 / (1 - 1/N) where N=3 zones → 6 / 0.667 = 9 instances (3 per zone). Document this formula.

Expected result

A capacity distribution sheet showing exact instance allocations across three zones, proving that regional distribution prevents total service collapse during single-zone outages.

Exercise 3 — Autoscaling timeline trace under a simulated traffic burst

Goal: Calculate instance scaling decisions and fleet capacity over a 10-minute load timeline under two different cool-down policies.

Mode: tabletop timeline simulation · Prerequisites: Exercises 1 and 2 artifacts.

  1. Define the workload timeline. Assume an Order API workload with initial state:
    • Base capacity: 3 instances (handling 300 RPS, 50% CPU).
    • Autoscaling target: 60% CPU utilization.
    • Instance boot/warm-up time: 90 seconds (utilization = 95% during warm-up).
    • At T = 1:00: Traffic doubles to 600 RPS (fleet CPU jumps to 80%).
  2. Simulate Policy A (Uncalibrated: 30s cool-down).
    • T = 1:00: CPU is 80% > 60%. Autoscaler requests +2 VMs (Total 5).
    • T = 1:30: 30s cool-down expires. New VMs are only at second 30 of warm-up (burning 95% CPU). Average fleet CPU is calculated: (3*80% + 2*95%) / 5 = 86%.
    • T = 1:30: Autoscaler sees 86% CPU and orders +3 VMs (Total 8).
    • T = 2:00: 30s cool-down expires. 5 VMs still warming up. Autoscaler orders +5 VMs (Total 13). Runaway scaling until quota exhaustion.
  3. Simulate Policy B (Calibrated: 120s cool-down + scale-in control).
    • T = 1:00: CPU is 80% > 60%. Autoscaler requests +2 VMs (Total 5).
    • T = 2:30: 120s cool-down period. Telemetry from new VMs is ignored while they complete 90s JVM warm-up.
    • T = 2:30: Cool-down expires. All 5 VMs are healthy and actively sharing load. Average fleet CPU drops to 600 RPS / 5 VMs = 120 RPS/VM = 48% CPU.
    • T = 2:30: Fleet is stable. Zero runaway scaling.
  4. Compile the timeline artifact. Write the complete side-by-side timeline into day-038-scaling.md with explicit assumptions and mathematical checks.
Expected result / acceptance

A completed scaling timeline in day-038-scaling.md illustrating the mathematical difference between premature and calibrated cool-down windows, including capacity ceiling calculations.
