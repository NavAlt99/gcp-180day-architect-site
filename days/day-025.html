Topic 01

Roles: basic (Owner/Editor/Viewer, avoid in production), predefined, custom

What it is: Google Cloud IAM categorizes access into three distinct role tiers: legacy Basic (primitive) roles (roles/owner, roles/editor, roles/viewer) that predate granular IAM; Predefined roles curated and maintained by Google Cloud service teams (e.g., roles/pubsub.publisher, roles/cloudsql.client); and Custom roles authored by platform administrators to bundle exact API permissions at the project or organization level.

Why today: Basic roles violate the principle of least privilege by bundling thousands of destructive permissions across every API surface, creating massive blast radiuses where a single compromised key or operational mistake can destroy an entire environment. Predefined roles offer balanced convenience, while custom roles provide surgical least-privilege boundaries despite their maintenance overhead.

Where it sits: Role definitions specify the collection of fine-grained API permissions (such as storage.buckets.get or spanner.databases.select) that can be granted. They serve as the functional capability payload before identity bindings, resource scopes, and runtime conditions are evaluated.

An engineer granted the legacy roles/editor role on a shared production project accidentally destroyed a primary Cloud SQL database instance while attempting to clean up a staging replica. The resulting database outage halted order ingestion across seven regional fulfillment hubs for forty-two minutes, violating corporate availability SLAs and stalling physical bakery dispatch queues.

Topic 02

IAM policy structure: bindings, members, roles, conditions

What it is: An IAM policy is a declarative JSON/YAML document attached to a Google Cloud resource, folder, or organization. Schema version 3 introduces support for conditional role bindings, where an array of members is bound to a specific role only when an embedded Common Expression Language (CEL) expression evaluates to true based on resource attributes, request time, caller IP, or tag values.

Why today: Static, unconditional IAM bindings leave administrative privileges permanently active, increasing risk exposure during off-hours or outside dedicated change windows. CEL conditions enable temporal windows (e.g., maintenance access expiring after two hours), network perimeter boundaries, and resource attribute filters without managing out-of-band proxy infrastructure.

Where it sits: The IAM policy is the core data contract evaluated by Cloud IAM during every API RPC call. The policy evaluation engine checks the resource's attached policy, decodes the bindings, inspects member identity, and executes CEL logic against the incoming request context.

A malformed Common Expression Language (CEL) condition relying on local wall-clock time rather than UTC caused an automated deployment pipeline to evaluate all IAM role bindings as false during the midnight production release. The false-negative authorization lock blocked mission-critical hotfix rollouts across all microservices for three hours, forcing manual failovers and delaying overnight bakery dispatch schedules.

Topic 03

Policy inheritance and the effective policy

What it is: Google Cloud IAM enforces a strict hierarchical inheritance model across the resource tree: Organization → Folder → Project → Resource. Policy bindings are strictly additive (unioned); permissions granted at a parent node cannot be restricted, revoked, or subtracted at a lower child node by standard IAM policies.

Why today: Engineers frequently inspect only the project-level IAM policy and mistakenly conclude that access is tightly constrained, unaware that broad administrative bindings attached at an ancestral folder grant expansive privileges. Calculating the true effective policy requires traversing the entire ancestral chain to evaluate cumulative bindings and conditions.

Where it sits: Effective policy evaluation occurs in the IAM control plane before authorizing any resource interaction. Tools like IAM Policy Troubleshooter and Cloud Asset Inventory query the ancestral graph to compute whether the union of all ancestral grants satisfies the requested permission.

An inherited roles/pubsub.admin binding attached at a parent root folder inadvertently granted junior developers permission to purge production order topics despite strict project-level restrictions. The resulting unauthenticated topic purge deleted queued bakery orders and corrupted delivery pipeline tracking, directly threatening Brightloaf's duplicate fulfillment invariant.

Topic 01 · Roles: basic (Owner/Editor/Viewer, avoid in production), predefined, custom

Google Cloud Identity and Access Management (IAM) controls access through permissions bundled into roles. Every action in Google Cloud maps to an atomic REST API permission formatted as service.resource.verb (such as compute.instances.start or storage.objects.create). Rather than granting individual permissions directly to principals, IAM requires permissions to be packaged into roles.

The Three Role Tiers

Google Cloud segments roles into three distinct tiers with differing lifecycles, maintenance burdens, and blast radiuses:

  • Basic (Primitive) Roles: The historical roles that originated with Google Cloud Platform: roles/owner, roles/editor, and roles/viewer. These roles apply universally across virtually all Google Cloud services. roles/viewer grants read-only access to almost all metadata and data; roles/editor grants permissions to modify, deploy, create, and delete resources across all services; and roles/owner adds billing administration, project ownership management, and IAM policy modification. Basic roles must be prohibited in production environments because they violate least privilege by design, providing broad horizontal reach across unassociated systems.
  • Predefined Roles: Curated and maintained by Google Cloud service engineering teams. Examples include roles/pubsub.publisher, roles/storage.objectAdmin, and roles/spanner.databaseUser. When Google releases new API methods or features for a service, Google automatically updates the predefined role to include relevant new permissions without customer intervention. Predefined roles represent the recommended default for enterprise architectures.
  • Custom Roles: Customer-authored collections of fine-grained permissions created at the Organization (organizations/{org-id}/roles/{role-id}) or Project (projects/{project-id}/roles/{role-id}) level. Custom roles are necessary when predefined roles are too permissive (for instance, granting unwanted deletion or IAM modification verbs alongside operational read/write access). However, custom roles carry a notable maintenance burden: Google does not automatically update custom roles when new API methods are added, and certain permissions (such as billing or specialized third-party integrations) cannot be included in custom roles.

Topic 02 · IAM policy structure: bindings, members, roles, conditions

An IAM policy attached to a Google Cloud resource defines who has what access. The policy payload is represented as a structured object containing three primary elements:

  1. bindings: A list of associations. Each binding specifies exactly one role and one or more members (principals such as user:, serviceAccount:, or group:).
  2. version: The schema version of the policy document. Policies created without conditional bindings default to version 1. Any policy containing Common Expression Language (CEL) conditions must specify version 3. If a client attempts to write a policy with conditions while specifying version 1, the IAM API rejects the call. Conversely, reading a version 3 policy with an older version 1 client unwinds or obscures conditional expressions.
  3. etag: A base64-encoded concurrency token used for optimistic concurrency control. Updates to IAM policies must include the existing etag to prevent race conditions from overwriting concurrent modifications.

Common Expression Language (CEL) Conditions

IAM Conditions allow role bindings to take effect only when a specified expression evaluates to true. The condition is expressed using Google's Common Expression Language (CEL), a fast, non-Turing-complete, memory-safe expression language. IAM condition expressions evaluate against three attribute namespaces:

  • Request Attributes (request.*): Attributes describing the incoming API call itself. Key attributes include request.time (RFC 3339 timestamp), and request.auth.claims (claims extracted from workforce identity pool tokens or JWTs).
  • Resource Attributes (resource.*): Attributes describing the target resource being accessed. Key attributes include resource.name (the full Google Cloud resource URI), resource.type (e.g., compute.googleapis.com/Instance), and resource.service.
  • Tag Attributes (resource.tags/*): Hierarchical resource tags attached to the resource or inherited from ancestor folders/organization. Tags provide cryptographic tamper-proof boundaries distinct from editable metadata labels.

Topic 03 · Policy inheritance and the effective policy

Google Cloud organizes all resources into a strict hierarchy: Organization → Folders → Projects → Resources. IAM policy evaluation relies on a foundational rule known as additive inheritance. Access granted at any ancestor level in the hierarchy cannot be taken away or overridden by standard IAM policies at a descendant level.

Calculating the Effective Policy

The effective policy is the computational union of all role bindings attached directly to the target resource plus all role bindings attached to every ancestor node in its hierarchical lineage. When a principal requests an action on a resource (for example, reading an object from Cloud Storage):

  1. The IAM evaluation engine inspects the resource's direct IAM policy. If any binding grants the required permission (and passes any CEL condition), access is granted immediately.
  2. If the direct policy does not satisfy the permission, the engine evaluates the containing project's policy.
  3. If unsatisfied, the engine steps up through parent folders sequentially.
  4. Finally, the engine checks the root organization policy.
  5. If no policy at any level grants the permission, the request terminates with 403 PERMISSION_DENIED.

Because standard IAM policies cannot explicitly deny permissions, an overprivileged role grant at the Folder level (e.g., granting roles/editor on a "Production" folder) permanently taints every project and resource beneath that folder, rendering local project-level least privilege impossible.

Important Distinctions in Authorization Controls

Standard IAM policies are strictly additive (allow-only). To enforce explicit negative constraints across the hierarchy, architects must use either IAM Deny Policies (which override all allow policies at lower and equal levels) or Organization Policy Constraints (which govern resource configuration rather than principal identity). Standard IAM allow policies can never revoke an inherited grant.

Incident 25.1

Primitive Role Blast Radius: roles/editor Grants Cloud SQL Destruction

Symptom

At 14:22 UTC, Brightloaf's regional fulfillment microservices began logging database connection timeouts (503 Service Unavailable: connection refused). The primary transactional Cloud SQL PostgreSQL instance (prod-orders-primary) disappeared from the Google Cloud Console. Order ingestion halted across seven regional bakeries, and pending baking batches stalled mid-workflow.

Constraints & Invariant

Duplicate Fulfillment Invariant: Under no circumstances may database recovery or retry replays result in more than one physical fulfillment per unique order ID (≤ 1 physical fulfillment).
Operational Constraint: SREs must restore transactional state to the exact second prior to deletion without dropping idempotent commit logs.

Root Cause Analysis

Three days prior to the incident, an engineer was investigating query latency on a read replica and requested elevated privileges. A junior system administrator granted the basic role roles/editor at the project level brightloaf-prod-orders as an expedient workaround. During a routine script execution intended to delete a decommissioned staging instance, the engineer's environment context was accidentally pointed at the production project. Because roles/editor bundles thousands of permissions across all GCP APIs—including destructive methods like cloudsql.instances.delete—the API executed the deletion immediately without validation.

5-Step Diagnostic Sequence

  1. Audit Log Extraction: Inspect Cloud Audit Logs for cloudsql.instances.delete to determine the initiating principal and exact millisecond of termination.
  2. Point-in-Time Recovery (PITR) Assessment: Query Cloud SQL automated backup logs to locate the most recent transaction log WAL segments and verify automated backup integrity.
  3. Policy Audit: Run an IAM policy inspection on projects/brightloaf-prod-orders to catalog all principals bound to basic roles (roles/owner, roles/editor, roles/viewer).
  4. Transaction Log Verification: Compare uncommitted Pub/Sub order offsets against the point-in-time recovery target to isolate orders that were in-flight during the instance deletion.
  5. Blast Radius Mapping: Execute an IAM permission difference analysis between roles/editor and least-privilege operations required for daily database maintenance.

Defensible Solution & Mitigation

To eliminate basic role blast radius while maintaining operational continuity:

  1. Immediately perform Point-in-Time Recovery (PITR) of prod-orders-primary to 14:22:03Z. Cross-reference completed bakery fulfillment receipts in Spanner to ensure no restored order is double-dispatched.
  2. Enable Instance Deletion Protection on all production Cloud SQL instances to block API deletion calls until the protection flag is deliberately turned off.
  3. Strip roles/editor from all human and automated principals across all production projects.
  4. Deploy a custom organization role: organizations/1029384756/roles/brightloafCloudSqlOperator containing only non-destructive verbs (cloudsql.instances.get, cloudsql.instances.list, cloudsql.instances.restart, cloudsql.instances.export).

Verification & Residual Risk

Verification: Execute an instance deletion API call against a test sandbox instance using brightloafCloudSqlOperator credentials. Confirm the API returns 403 PERMISSION_DENIED with message The client is not authorized to make this request. Missing permission: cloudsql.instances.delete.

Residual Risk: Custom roles must be monitored for API changes. If Cloud SQL introduces new non-destructive management verbs in subsequent API revisions, platform engineers must manually update the custom role YAML definition.

Incident 25.2

CEL Timezone Lockout: Erroneous Condition Blocks Emergency Hotfix Release

Symptom

At 19:05 UTC, the automated continuous deployment pipeline triggering a critical hotfix release for the fulfillment order scheduler failed with 403 PERMISSION_DENIED on clouddeploy.releases.create. On-call SREs attempting to run the rollout manually were similarly blocked. The hotfix was urgent: a race condition in the delivery router was causing duplicate dispatch messages to be emitted to bakery packaging lines.

Constraints & Invariant

Duplicate Fulfillment Invariant: The hotfix contained the idempotency deduplication patch; blocking its deployment allowed duplicate dispatch events to process, directly risking duplicate bread orders (≤ 1 physical fulfillment violated).
Security Constraint: Elevated deployment permissions must remain time-bounded and cannot be made permanently active.

Root Cause Analysis

The release engineer scheduled a temporary emergency change window for Sunday night. When authoring the IAM policy condition for the release pipeline service account, the engineer intended the window to close at 00:00 local time (IST, UTC+05:30). However, instead of specifying timestamp("2026-09-27T23:59:59Z") or applying proper UTC offset conversion, the engineer mistakenly calculated the expiration as 18:30:00Z. When the deployment started at 19:05:00Z, the CEL condition evaluated to false. Because no other unconditional binding granted release creation privileges, the IAM evaluation engine defaulted to a hard deny.

5-Step Diagnostic Sequence

  1. Audit Log Error Inspection: Examine Cloud Deploy API audit logs to pull the exact IAM_PERMISSION_DENIED payload and identify the failing condition title.
  2. Policy Schema Extraction: Retrieve the version 3 IAM policy for projects/brightloaf-prod-fulfillment using Cloud SDK formatted output.
  3. CEL Expression Evaluation: Compare request.time against the condition's RFC 3339 timestamp string to confirm the boolean evaluation outcome.
  4. Queue Drainage Safeguard: Temporarily pause downstream order dispatch workers in Pub/Sub to prevent the unpatched deduplication race condition from emitting duplicate tickets while authorization is resolved.
  5. Concurrency ETag Verification: Validate the current etag of the project's IAM policy prior to applying an updated condition expression.

Defensible Solution & Mitigation

To safely restore deployment access and prevent temporal lockouts:

  1. Immediately patch the IAM policy condition expression with an explicit UTC window including a 4-hour post-maintenance buffer: request.time < timestamp("2026-09-28T04:00:00Z").
  2. Re-trigger the deployment pipeline, successfully deploying the order idempotency deduplication release.
  3. Unpause the Pub/Sub dispatch workers; verify with order event tracking that each unique order ID is processed exactly once.
  4. Standardize all temporal IAM conditions to use an automated Terraform module that strictly formats timestamps in UTC and rejects conditions expiring within 60 minutes of commit.

Verification & Residual Risk

Verification: Run an automated policy simulation passing current system time in UTC and testing boolean return values against boundary conditions. Confirm the pipeline service account authenticates and initiates canary releases without permission warnings.

Residual Risk: Once the temporal condition expires after the buffer window, subsequent release attempts will again fail unless refreshed by a pipeline change management hook.

Incident 25.3

Additive Inheritance Leak: Ancestral Folder Binding Overrides Project Isolation

Symptom

At 11:15 UTC, the primary message bus topic projects/brightloaf-prod-fulfillment/topics/bakery-dispatch was deleted. Over 4,200 pending baking delivery instructions were dropped. Ingestion microservices threw unhandled exceptions, and regional baking hubs were left without dispatched order tickets.

Constraints & Invariant

Duplicate Fulfillment Invariant: Upstream order ingestion systems resubmitted orders from transactional logs. Without the original message ordering and acknowledgment offsets, replayed messages risked creating multiple baking tasks for identical order IDs (≤ 1 physical fulfillment).
Security Constraint: Developers must maintain read and publish access in development projects without ever possessing deletion capability in production.

Root Cause Analysis

The project-level IAM policy for brightloaf-prod-fulfillment was thoroughly reviewed and showed no developer accounts with administrative rights—only roles/pubsub.viewer was present. However, because Google Cloud IAM policy inheritance is strictly additive, inspecting the project policy in isolation gave a false sense of security. At the parent folder level (folders/bakery-operations), an obsolete binding bound group:all-devs@brightloaf.internal to roles/pubsub.admin. When the developer executed a topic-clearing cleanup script locally, the IAM evaluation engine evaluated the effective policy: the ancestral folder grant satisfied pubsub.topics.delete, completely overriding the restrictive project policy.

5-Step Diagnostic Sequence

  1. Hierarchical Policy Crawl: Execute an ancestral policy audit using Cloud Asset Inventory or Policy Troubleshooter tracing all parent folders up to the organization root.
  2. Effective Policy Generation: Compute the union of all role bindings applicable to dev-user@brightloaf.com across every node in the resource hierarchy.
  3. Topic Re-creation & Subscription Recovery: Immediately re-create bakery-dispatch with identical schema definitions and dead-letter queues.
  4. Idempotency Deduplication Audit: Run an offline log reconciliation matching replay candidates against the Spanner physical fulfillment ledger, discarding any message whose order_id already possesses an acknowledged fulfillment record.
  5. Folder Policy Remediation: Remove broad service admin roles from all ancestral folders, re-scoping access strictly to development child projects.

Defensible Solution & Mitigation

To eliminate inheritance leaks and enforce absolute least privilege:

  1. Recreate the topic and attach an IAM Deny Policy or delete the unscrubbed binding at folders/bakery-operations.
  2. Re-architect the folder hierarchy to isolate production projects under a dedicated folders/prod tree with zero human data-plane bindings.
  3. Deploy continuous drift detection using Cloud Asset Inventory feeds to flag any folder-level role binding containing admin or editor roles.
  4. Replay unacknowledged Pub/Sub messages through an idempotent consumer filter that verifies the duplicate fulfillment invariant against Spanner before issuing bakery dispatch commands.

Verification & Residual Risk

Verification: Query the Policy Troubleshooter API simulating dev-user@brightloaf.com requesting pubsub.topics.delete on projects/brightloaf-prod-fulfillment/topics/bakery-dispatch. Verify that the effective authorization decision is ACCESS_DENIED with all ancestor bindings reporting NOT_GRANTED.

Residual Risk: If future folder administrators inadvertently bind groups at the folder level, new inheritance leaks may occur. Automated policy linting must run as a gate in CI/CD before any folder IAM modification is applied.

"""
simulate-iam-conditions.py - IAM Policy v3 & CEL Condition Evaluation Engine
Tests allowed and denied operations against temporal and resource-name conditions.
"""
from datetime import datetime, timezone
import json

# IAM Policy Document Schema Version 3
POLICY_V3 = {
    "version": 3,
    "etag": "BwZ1a2b3c4d=",
    "bindings": [
        {
            "role": "roles/clouddeploy.releaser",
            "members": ["serviceAccount:sa-deploy@brightloaf-prod.iam.gserviceaccount.com"],
            "condition": {
                "title": "emergency_maintenance_window",
                "description": "Permit release creation during emergency window in UTC",
                "expression": "request.time < timestamp('2026-09-28T04:00:00Z')"
            }
        },
        {
            "role": "roles/pubsub.publisher",
            "members": ["serviceAccount:order-ingest@brightloaf-prod.iam.gserviceaccount.com"],
            "condition": {
                "title": "prod_orders_topic_only",
                "description": "Restrict publishing to prod-orders topics only",
                "expression": "resource.name.startsWith('projects/_/topics/prod-orders')"
            }
        }
    ]
}

def evaluate_request(principal, role, req_time_iso, resource_name):
    req_time = datetime.fromisoformat(req_time_iso.replace("Z", "+00:00"))
    
    for binding in POLICY_V3["bindings"]:
        if binding["role"] == role and principal in binding["members"]:
            cond = binding.get("condition")
            if not cond:
                return True, "ALLOWED (Unconditional Binding)"
            
            expr = cond["expression"]
            # Evaluate temporal condition
            if "request.time < timestamp(" in expr:
                cutoff_str = expr.split("'")[1].replace("Z", "+00:00")
                cutoff_time = datetime.fromisoformat(cutoff_str)
                if req_time < cutoff_time:
                    return True, f"ALLOWED (Condition Passed: {cond['title']})"
                else:
                    return False, f"DENIED (Condition Expired: req_time={req_time_iso} >= cutoff={cutoff_str})"
            
            # Evaluate resource name prefix condition
            if "resource.name.startsWith(" in expr:
                prefix = expr.split("'")[1]
                if resource_name.startswith(prefix):
                    return True, f"ALLOWED (Condition Passed: prefix match '{prefix}')"
                else:
                    return False, f"DENIED (Condition Failed: '{resource_name}' does not start with '{prefix}')"
                    
    return False, "DENIED (No matching binding found)"

def resolve_effective_policy(principal, resource_chain):
    effective_bindings = []
    for node in resource_chain:

            if principal in b["members"]:

                })

def evaluate_permission(effective_bindings, target_role, req_context):
    for b in effective_bindings:
        if b["role"] == target_role:
            cond = b.get("condition")
            if not cond:
                return True, f"Allowed unconditionally via inheritance from {b['inherited_from']}"
            expr = cond["expression"]
            if "resource.name.startsWith(" in expr:
                prefix = expr.split("'")[1]
                if req_context.get("resource_name", "").startswith(prefix):
                    return True, f"Allowed under condition '{cond['title']}' inherited from {b['inherited_from']}"
                else:
                    return False, f"Denied: Condition '{cond['title']}' failed prefix check '{prefix}'"
    return False, "Denied: Permission not present in effective policy union"
