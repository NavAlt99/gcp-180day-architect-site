Prerequisite Review & Remediation

Gate 3 covers Days 36–66, a 31-day block that built the entire core operational stack of the Brightloaf order service: identity and IAM principals (Days 36–41 via VM/runtime service accounts), VPC networking and hybrid connectivity (Days 42–57), object and block storage durability (Days 58–60), relational and NoSQL databases (Days 61–63), and messaging with exactly-once semantics (Days 64–66). This checkpoint does not introduce any new service or concept. Instead, it asks you to confirm that evidence from each topic group is reproducible, that critical invariants have been preserved, and that gaps identified during self-assessment are remediated before you move forward into the architecture and design block (Days 68–82).

The self-assessment purpose is to discover, while evidence is still fresh, which areas need a repeat exercise rather than a stronger assertion. A review that finds zero gaps is either perfect work or an incomplete review; both deserve scrutiny before the G3 pass decision is recorded.

A request trace stalls at the IAM middleware layer, returning 403 despite apparent role bindings — the reviewer cannot reproduce which principal was active or which resource binding was in scope at the time of the test. Without a reproducible operational baseline, downstream architecture decisions in Days 68–82 will lack the traceability anchor required by Gate 4, potentially invalidating weeks of design work and forcing a full remediation pass.

Gate 3 Scoring Rubric

Gate 3 is scored across five dimensions: Correctness (does the traced path, recovered state, or idempotency proof match the expected outcome?), Requirement traceability (can each result be linked to a specific day artifact and architectural decision?), Evidence quality (is the evidence reproducible by a second reviewer — commands, logs, diagram edges, timestamps?), Failure/recovery reasoning (is the fault injection point named, the symptom described, and the recovery steps documented?), and Communication (can a peer understand and critique the argument without the author present?).

Each dimension is scored 0–3: 0 absent or incorrect, 1 partial or stated without proof, 2 adequate with explicitly stated limits, 3 clear, reproducible, and defensible. The pass threshold requires at least 2 in every dimension AND 12 or more out of 15 total. A single dimension at 0 or 1 is a gate fail regardless of the sum. Required proof elements are: reproduce the application, trace a request through its full identity-network-storage-messaging path, diagnose and recover a simulated fault, and demonstrate that a duplicate Pub/Sub event does not produce a duplicate fulfillment record.

When a gate day is skipped entirely, the candidate advances without an indexed operational baseline, and Gate 4 reviewers will find that architecture decisions cannot be traced to observed behaviour. A candidate who completes the day but records evidence quality at 0/3 — for instance by providing only a diagram without any command output, log excerpt, or explicit timestamp — will fail the gate on that dimension alone, requiring remediation before the next block begins.

Gate 3 Scoring Rubric — Deep Dive with Worked Example

Dimension 1: Correctness

Correctness asks whether the traced path, recovered state, or idempotency demonstration is factually accurate. A score of 3 means the result is reproducible without unstated assumptions. A score of 2 accepts stated limitations — for example, "this trace was captured in a local emulator, not against production Pub/Sub, so ordering key behaviour may differ." A score of 1 means the mechanism is mostly right but a critical step is wrong or absent — for instance, claiming Cloud SQL HA failover happens automatically but omitting the health-probe mechanism that triggers it. A score of 0 means the answer is factually wrong or entirely missing.

Dimension 2: Requirement Traceability

Each claim in a Gate 3 packet must trace back to a specific prior day artifact. Saying "I covered VPC networking on Day 49" earns a score of 1 at best; citing "Day 49 exit artifact day-049-vpc-design.md, section 'Route table for PSC subnet', decision to use /24 PSC allocation to avoid overlap with hybrid CIDRs" earns a score of 3. The chain is: requirement → day → artifact → decision → observable output.

Dimension 3: Evidence Quality

Evidence must be reproducible by a second reviewer without the author's assistance. A diagram alone is not evidence. A screenshot of a console page is score 1 at best. A command with its exact output, the environment (project ID, region, service account email), and a timestamp is score 2. Adding the cleanup steps and confirming the same output can be reproduced after a fresh session earns score 3.

Dimension 4: Failure/Recovery Reasoning

This dimension is the most frequently failed in Gate 3 reviews. Candidates who trace the happy path successfully but skip the fault injection section receive 0/3 on this dimension alone — which is a gate fail. The minimum for score 2 is: name the fault (e.g., "remove roles/cloudsql.client from the order-service SA"), describe the observed symptom (e.g., "Cloud SQL connection returns PERMISSION_DENIED; Cloud Run 503 after 30 s timeout"), document the diagnosis steps (check Cloud Audit Logs, confirm SA email, re-add binding), and verify recovery with a timestamp.

Dimension 5: Communication

The gate packet must be self-contained. A peer reviewer should be able to read it, understand the architectural claim, test the evidence independently, and rescore without asking the author any questions. Structure, headings, explicit uncertainty statements, and alternative-considered notes all contribute to score 3.

Worked Example: Partial Gate Pass Scenario

Candidate profile

A candidate submits a Gate 3 packet with the following evidence:

  • Traces the order request from client through LB → Cloud Run → Cloud SQL → Pub/Sub with correct service names, VPC routing, and PSC endpoint.
  • Demonstrates idempotency: shows that a duplicate Pub/Sub message with the same order_id does not produce a second fulfillment row.
  • Provides a diagram with correct architecture and labels.
  • Does not attempt the fault injection exercise (IAM binding removal and recovery).
  • Communication is clear and well-structured.

Scoring:

  • Correctness: 3 — traced path and idempotency are correct.
  • Requirement traceability: 2 — links to day artifacts but some decisions lack specific artifact references.
  • Evidence quality: 2 — commands and outputs provided for trace and idempotency; timestamps present.
  • Failure/recovery reasoning: 0 — fault injection section is entirely absent.
  • Communication: 3 — packet is self-contained and clear.

Total: 10/15. Result: GATE FAIL. The sum (10) is below the 12/15 threshold AND the failure/recovery dimension is 0/3 (below the 2/3 per-dimension minimum). Both rules independently fail this candidate.

Remediation: The candidate must complete the fault injection exercise from topic-01-lab step 2, produce a fault timeline with timestamps, and resubmit the failure/recovery section. The other four dimensions do not need to change. After remediation the projected scores are 3+2+2+2+3 = 12, which passes both the sum and per-dimension rules.

3 · Real-world problem and solution for each topic

Topic 1 Field Case — Skipping the Review Cascade

Situation and impact: A candidate completes Days 36–66 without pausing for Gate 3. They proceed directly to Day 68 and begin building architecture decision records (ADRs) for the Brightloaf order service. At Gate 4 (Day 82), the reviewing panel asks: "Which Day 49 artifact proves that the PSC subnet was allocated outside the hybrid CIDR range?" The candidate cannot produce the artifact because it was never committed to the evidence repository — the Day 49 lab ended with a tabletop prediction that was never validated. The ADR for PSC addressing now lacks an operational baseline. All downstream architecture decisions that reference this ADR are suspect, and the candidate is required to return to Day 49, repeat the lab with proper evidence capture, and re-evaluate all ADRs that cite it — a remediation spanning 14 days of design work.

How the failure propagates: Without a reproducible operational baseline, the Gate 4 reviewer identifies a gap in requirement traceability. The G3 decision was never scored, so there is no record of which invariants were verified. Every architecture choice that depended on a verified VPC routing decision now lacks its proof anchor. The candidate cannot pass Gate 4 until the G3 operational baseline is reconstructed.

Remediation: The candidate must (1) complete the Gate 3 self-assessment retrospectively, (2) repeat any exercises that lack committed artifacts, (3) score all five rubric dimensions, (4) produce a signed G3 decision record, and (5) re-examine each ADR written between Days 68 and 82 to confirm or correct its traceability chain. Only then can Gate 4 proceed.

Topic 2 Field Case — High Correctness, Zero Recovery

Situation and impact: A candidate scores 3/3 on Correctness and 3/3 on Communication but records 0/3 on Failure/Recovery Reasoning because they completed the request trace and idempotency demonstration but entirely skipped the fault injection step. Their total is 3+2+2+0+3 = 10/15. Both the per-dimension rule (failure/recovery at 0, which is below 2) and the sum rule (10, which is below 12) independently trigger a gate fail. The candidate is surprised because they felt the trace and idempotency work were thorough.

How partial gate evidence leads to gate fail: The five-dimension rubric is designed so that a strong performance in four dimensions cannot compensate for a complete omission of one. This mirrors real operational practice: a system that is architecturally correct but whose operators have never practiced fault diagnosis is not operationally mature. The gate enforces that the candidate has demonstrated the ability to diagnose a fault, not merely describe the happy path.

Remediation steps: (1) Complete the fault injection exercise: remove a specific IAM binding from the order-service SA and record the symptom from Cloud Logging. (2) Document the diagnosis steps with timestamps. (3) Re-add the binding and record the recovery. (4) Measure the time from fault injection to service restoration and compare with any stated RTO. (5) Resubmit the failure/recovery section. The other four dimensions remain unchanged; only the failure/recovery section is re-evaluated.

Step 1: Request Trace

Trace an order request from the client through IAM authentication → VPC routing → Cloud Run (order-service) → Cloud SQL → Pub/Sub. For each boundary, record: the principal, the resource, the expected outcome, and the log entry or artifact that proves it.

Open Cloud Logging in your sandbox project and filter for the order-service Cloud Run revision. Query the following in the Logs Explorer:

resource.type="cloud_run_revision"
resource.labels.service_name="order-service"
severity>=WARNING

For each hop in the trace, complete a row in this table (copy into your exit artifact):

| Boundary          | Principal / Resource              | Outcome   | Log/Artifact evidence |
|-------------------|-----------------------------------|-----------|-----------------------|
| Client → LB       | Unauthenticated / GLB IP          | TLS term  | LB access log: 200 OK |
| LB → Cloud Run    | LB SA / order-service URL         | Invoke    | Cloud Run request log |
| Cloud Run → SQL   | order-service SA / PSC endpoint   | ALLOW     | Cloud SQL conn log    |
| SQL → Pub/Sub     | order-service SA / orders.v1      | Publish   | Pub/Sub publish ack   |

Step 2: Fault Diagnosis and Recovery

Simulate an IAM permission removal fault. In a real environment, you would run:

# TABLETOP: do not run unless you have a dedicated sandbox project
# Step A — inject fault: remove the Cloud SQL client role from the order-service SA
gcloud projects remove-iam-policy-binding PROJECT_ID \
  --member="serviceAccount:order-service@PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/cloudsql.client"

# Step B — observe symptom in Cloud Logging (Logs Explorer query):
resource.type="cloud_run_revision"
jsonPayload.message=~"PERMISSION_DENIED|connection refused"

# Step C — recover: re-add the binding
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="serviceAccount:order-service@PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/cloudsql.client"

# Step D — verify recovery: confirm next request succeeds
# Record: inject timestamp, first symptom timestamp, recovery timestamp, delta (RTO)

In your exit artifact, record the fault timeline with four timestamps: T_inject, T_symptom, T_recovery_start, T_restored. Calculate the observed RTO = T_restored − T_inject.

Step 3: Duplicate-Event Safety

Demonstrate idempotency via Pub/Sub message ID check. In a real environment, the fulfillment worker checks for a previously processed message_id before committing a fulfillment row. The following tabletop trace shows the expected behaviour:

# Tabletop trace: order_id=ORD-42, message published twice (delivery retry simulation)
#
# Delivery 1:
#   message_id = msg-abc-001
#   order_id   = ORD-42
#   Worker: SELECT 1 FROM processed_messages WHERE message_id = 'msg-abc-001'
#   Result:  0 rows → INSERT INTO fulfillments (order_id) VALUES ('ORD-42')
#            INSERT INTO processed_messages (message_id) VALUES ('msg-abc-001')
#            ACK message
#
# Delivery 2 (retry after timeout):
#   message_id = msg-abc-001  ← same ID (Pub/Sub guarantees same ID on retry)
#   order_id   = ORD-42
#   Worker: SELECT 1 FROM processed_messages WHERE message_id = 'msg-abc-001'
#   Result:  1 row found → SKIP INSERT, ACK message (idempotent)
#
# Expected: fulfillments table contains exactly 1 row for ORD-42
# Invariant: COUNT(fulfillments WHERE order_id='ORD-42') = 1 after 2 deliveries

Record this trace in your exit artifact as the duplicate-event invariant proof. If you have a local Cloud SQL emulator or SQLite, you can run the INSERT / SELECT sequence and paste the actual output.

Step 4: Access Denial Confirmation

Attempt an unauthorized access and confirm Cloud Audit Log captures the denial.

# Tabletop: simulate an unauthenticated caller attempting to invoke the order-service Cloud Run URL
# Expected HTTP response: 403 Forbidden (Cloud Run rejects unauthenticated invocations)
#
# In a real environment:
curl -o /dev/null -s -w "%{http_code}" https://order-service-HASH-uc.a.run.app/orders
# Expected output: 403
#
# Cloud Audit Log query to confirm the denial was captured:
resource.type="cloud_run_revision"
protoPayload.methodName="google.cloud.run.v1.Services.GetIamPolicy"
protoPayload.authorizationInfo.granted=false

Record the HTTP status code and the Audit Log entry in your exit artifact. The Audit Log entry proves that the access attempt was captured — an essential component of the access denial boundary proof.
