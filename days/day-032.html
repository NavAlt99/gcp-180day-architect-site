1 · Topics of the day

Operational evidence, escalation and the maintained learning tracker

Day 32 connects five practices: know the Customer Care service and authorized contacts before an incident; inventory resources with Cloud Asset Inventory; corroborate possible provider incidents with Personalized Service Health (PSH) and the public Cloud Service Health dashboard; map the official Professional Cloud Architect exam guide's six sections; and maintain an 83-topic evidence tracker with current Google Skills resources. This belongs after resource hierarchy and quota work because an operator needs the correct scope, ownership, and evidence before deciding whether a symptom is local, project-specific, or provider-wide.

In the operating system, asset inventory supplies resource context, service-health channels supply provider-event context, support cases carry a bounded evidence package to Customer Care, and the tracker records which course claims have proof. None of these substitutes for application telemetry, the product API's live state, or an internal incident commander.

Problem preview: Brightloaf's Order API is impaired, but the on-call engineer has no current asset list, cannot identify the support entitlement, and treats a quiet public status page as proof that Google Cloud is healthy. The evidence gap delays ownership and escalation, extending customer checkout disruption.

2 · Technical discussion of each topic

From asset scope to provider escalation and course evidence

Scope and ownership. Cloud Asset Inventory (CAI) is a global metadata inventory service that can search, export, monitor, and analyze supported assets at project, folder, or organization scope. It is useful for discovery and audit context, but Google explicitly says it is not designed as a real-time production query path; use the owning service API when current state is safety-critical. The organization chooses support service, contacts, incident roles, evidence retention, and tracker ownership.

Control flow. Begin with user impact and internal telemetry, identify affected projects/resources, then query the owning service and CAI for context. Check PSH first for events relevant to the selected project or organization; use public Cloud Service Health for broad severe incidents or when PSH is unavailable. If evidence and entitlement justify a case, assign priority from actual business impact, attach a sanitized reproducible package, and keep the internal incident running in parallel. A support-case escalation addresses a support-process breakdown; it is not a shortcut that replaces correct case priority.

Tracker design. Give every source topic one stable row with domain, status, last-reviewed date, evidence path, evidence type, confidence, gap, and next action. Keep the current official six-section exam guide as a separate mapping dimension; do not force the roadmap's 83 topics into a false one-to-one exam blueprint. Link current Google Skills activities as learning inputs, then require your own artifact before marking a topic evidenced.

3 · Real-world problem and solution for each topic

Example incident: the empty escalation packet

Supplied facts and impact: Brightloaf operators see failed Order API checkouts in one production project. The public Cloud Service Health page shows no matching broad incident, the team has not checked project-relevant PSH, the asset spreadsheet predates a hierarchy change, and the only named support contact has left the rotation. No failure rate, error text, or provider cause is supplied. Customers cannot reliably place orders, while the incident commander cannot establish affected scope or open a well-supported case.

Constraints and evidence: Do not expose customer data or credentials; do not wait for Customer Care before mitigating; do not call a public-dashboard absence proof of provider health. Available evidence is the affected project ID, an internal UTC symptom window, application telemetry, the old asset sheet, and the current support overview page.

Diagnostic sequence: (1) keep internal incident command active and preserve telemetry; (2) use the project and owning service API to confirm live resources, then use CAI to rebuild scoped metadata context; (3) check project-relevant PSH and record event details or a timestamped no-match result; (4) check the public dashboard as fallback/corroboration; (5) confirm Customer Care service and authorized contacts; (6) choose case priority from current business impact and workaround status; (7) submit a sanitized package; (8) escalate the case only if the support process itself breaks.

Root cause and correction: The operational failure is not a proven Google Cloud outage; it is a broken evidence-and-ownership chain caused by stale inventory, absent contact ownership, and misuse of the public dashboard as a health oracle. Correct it with a scheduled asset snapshot owner, a tested contact sheet, PSH-first runbook, case template, and tracker links to the accepted evidence.

Verification and residual risk: A second operator must reproduce the asset scope, open both health channels, identify the authorized case contact and backup, and review the case package against the template. CAI can lag live changes, PSH may not yet show an emerging event, support response depends on entitlement and case priority, and even a correct provider case does not repair Brightloaf's own application defect.

from pathlib import Path
import csv, json, re

out = Path("day-032-evidence")

assets = [
    {"name":"//compute.googleapis.com/projects/brightloaf-sandbox/zones/us-central1-a/instances/order-api-1","asset_type":"compute.googleapis.com/Instance","project":"brightloaf-sandbox","location":"us-central1-a","owner":"platform","source":"supplied fixture"},

    {"name":"//cloudresourcemanager.googleapis.com/projects/brightloaf-sandbox","asset_type":"cloudresourcemanager.googleapis.com/Project","project":"brightloaf-sandbox","location":"global","owner":"cloud-admin","source":"supplied fixture"},
]
(out / "supplied-assets.json").write_text(json.dumps(assets, indent=2) + "\n")
with (out / "asset-list.csv").open("w", newline="") as f:
    w = csv.DictWriter(f, fieldnames=assets[0].keys())
    w.writeheader(); w.writerows(assets)

roadmap = Path("../gcp-architect-roadmap-100-days.md").read_text()
matches = list(re.finditer(r"^### Topic (\d{3}) references\s*\n\s*\n([^\n]+)", roadmap, re.M))
if len(matches) != 83:
    raise SystemExit(f"expected 83 topic headings, found {len(matches)}")
with (out / "topic-evidence-tracker.csv").open("w", newline="") as f:
    fields = ["topic_id","topic","exam_section","status","evidence_path","evidence_type","last_reviewed","gap","next_action"]
    w = csv.DictWriter(f, fieldnames=fields); w.writeheader()
    for m in matches:
        w.writerow({"topic_id":m.group(1),"topic":m.group(2).strip(),"exam_section":"unmapped","status":"not-started","evidence_path":"","evidence_type":"","last_reviewed":"","gap":"map and collect evidence","next_action":"assign review day"})

    (1,"Designing and planning a cloud solution architecture"),
    (2,"Managing and provisioning a solution infrastructure"),
    (3,"Designing for security and compliance"),
    (4,"Analyzing and optimizing technical and business processes"),
    (5,"Managing implementation"),
    (6,"Ensuring solution and operations reliability"),
]
with (out / "exam-map.csv").open("w", newline="") as f:
    w = csv.writer(f); w.writerow(["section","official_title","checked_date","topic_ids","evidence_gap"])
    for number, title in sections:
        w.writerow([number, title, "2026-09-27", "unmapped", "map roadmap topics without claiming one-to-one coverage"])
