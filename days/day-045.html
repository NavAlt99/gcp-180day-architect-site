Config and secrets

Kubernetes configuration and secret management separates application runtime code from operational parameters and sensitive credentials. While ConfigMaps store non-confidential environment properties and configuration files, Kubernetes Secrets store base64-encoded credentials in the cluster's etcd database. For production Google Cloud environments, the Secret Store CSI Driver integrates GKE with Google Cloud Secret Manager, mounting centrally audited, customer-managed encryption key (CMEK) protected secrets directly into container filesystems as ephemeral volumes.

This capability belongs on Day 45 because Day 44 established persistent storage and VPC networking; today we secure the data that flows into those workloads. Plain Kubernetes Secrets are only obfuscated rather than encrypted by default, vulnerable to overprivileged RBAC access and cluster backup leaks. Integrating Secret Manager ensures enterprise key versioning, automatic credential rotation, and granular Cloud IAM governance.

Problem preview: The order fulfillment service pod fails to start with CreateContainerConfigError and volume mount failures when attempting to read missing local secret keys, while debug logs show unencrypted database passwords exposed across environment variables. Deployment rollouts freeze completely across the regional cluster, and security compliance auditing fails due to plaintext credential exposure in process tables.

Workload Identity Federation for GKE

Workload Identity Federation for GKE establishes a cryptographic bridge between Kubernetes ServiceAccounts (KSAs) and Google Cloud IAM Service Accounts (GSAs). By mapping a KSA within a specific namespace to a GSA, applications running in pods authenticate to Google Cloud APIs without managing, mounting, or rotating long-lived service account private key JSON files.

This topic belongs on Day 45 because Day 26 established IAM tokens and service account fundamentals; today we operationalize least-privilege pod identity. Hardcoded service account keys represent the single most common attack vector in cloud container deployments. Workload Identity replaces static secrets with projected OpenID Connect (OIDC) service account tokens that the GKE metadata server transparently exchanges for short-lived Google OAuth2 tokens.

Problem preview: Newly deployed order analytics pods fail to export telemetry to BigQuery with 403 Forbidden errors because the pod cannot acquire credentials from the GKE metadata server. Analytical data pipelines stall for hours, and developers attempt to bypass the failure by downloading static service account keys, violating enterprise security policy.

Network Policies and Dataplane V2

Kubernetes NetworkPolicies declare granular Layer 3 and Layer 4 packet filtering rules governing pod-to-pod and namespace-to-namespace network ingress and egress. In GKE Dataplane V2, network policy enforcement is powered by Cilium and eBPF programs loaded directly into the Linux kernel traffic control (tc) hooks on host worker nodes, replacing legacy iptables packet filtering.

This topic belongs on Day 45 because Day 44 established cluster service networking; today we apply zero-trust microsegmentation. By default, Kubernetes networking is completely flat, permitting any pod to communicate with any other pod across all namespaces. Dataplane V2 enforces zero-trust boundaries at wire speed with minimal CPU overhead, containing lateral movement if an Internet-facing container is compromised.

Problem preview: After an operator applies a cluster-wide default-deny NetworkPolicy, the checkout service cannot resolve internal DNS names or communicate with the upstream payment processor, dropping all customer transactions. Online storefront purchases halt immediately across all regions, causing revenue loss and generating thousands of connection timeout errors.

Release channels and upgrade strategies (surge upgrades, maintenance windows)

GKE Release Channels (Rapid, Regular, Stable) automate Kubernetes version lifecycle management by balancing feature availability against operational stability. Upgrade strategies govern how worker node pools update their underlying operating system images and Kubernetes binaries, utilizing Surge Upgrades to provision temporary buffer instances or Blue-Green Upgrades to validate workloads on separate node pools within strictly controlled Maintenance Windows and Exclusions.

This topic belongs on Day 45 because mission-critical workloads require deterministic upgrade lifecycles that honor PodDisruptionBudgets (PDBs) and prevent involuntary eviction during peak commercial business hours. Architecturally, release channels decouple cluster maintenance from ad-hoc manual interventions, ensuring continuous security patching without unexpected service interruptions.

Startup vs readiness vs liveness probes

Kubernetes container health checking relies on three distinct probe mechanisms: `startupProbe` detects when slow-initializing applications complete their boot sequence, temporarily suppressing other checks; `readinessProbe` verifies whether a container is ready to accept incoming network traffic, routing traffic only when healthy; and `livenessProbe` detects runtime deadlocks, restarting failed containers via the local kubelet.

This topic belongs on Day 45 because probe misconfigurations are the primary source of cascading restart loops and service flapping in production microservices. Confusing liveness with readiness causes kubelet to violently kill slow-starting JVM or database containers before they can initialize caches or establish connection pools.

Problem preview: A Java-based order processing microservice takes 75 seconds to compile internal caches on startup, but an aggressive liveness probe configured with a 15-second initial delay repeatedly kills the container. The microservice enters a permanent restart loop, preventing deployment rollouts and rendering order processing unavailable to clients.

Troubleshoot CrashLoopBackOff and OOMKilled using kubectl describe, logs, events and…

Kubernetes workload diagnostics requires a structured diagnostic method to isolate why containers fail to execute. `CrashLoopBackOff` indicates that a container repeatedly starts and exits with a non-zero exit code, triggering exponential restart backoff delays from the kubelet. `OOMKilled` (Exit Code 137) indicates that a container exceeded its assigned cgroup memory limit or the host node experienced severe kernel memory exhaustion.

This topic belongs on Day 45 because it synthesizes all runtime primitives into an actionable troubleshooting workflow. Operators must systematically inspect `kubectl describe pod` termination states, review previous container logs (`kubectl logs -p`), evaluate cluster warning events, and analyze resource usage metrics rather than blindly guessing root causes.

Config and secrets

Managing operational state in Kubernetes demands strict separation between application configuration and sensitive cryptographic secrets. ConfigMaps store plaintext key-value pairs or complete configuration files (such as nginx.conf or application YAML files) mounted into pods as volume directories or injected as environment variables. However, Kubernetes Secrets only base64-encode data by default in etcd. While Application-layer Secrets Encryption can protect etcd at rest with Cloud KMS keys, native Secrets lack automated rotation, fine-grained access policies, and enterprise secret versioning.

To establish an enterprise security boundary, Google Kubernetes Engine integrates with Google Cloud Secret Manager via the Secret Store CSI Driver (secrets-store.csi.k8s.io) and the Google Cloud Provider. When a Pod references a SecretProviderClass resource, the Secret Store CSI driver on the worker node communicates with the Secret Manager API using the Pod's Workload Identity. The secret payload is retrieved directly from Secret Manager and mounted as an ephemeral tmpfs volume inside the container filesystem. Sensitive keys never touch the cluster's etcd database, and rotation polling automatically updates mounted files when new secret versions are enabled in Secret Manager.

Architecture Path: Kubernetes Native Secrets vs Secret Manager CSI Integration
Dimension Native Kubernetes Secret Secret Manager CSI Driver Architectural Consequence
Storage Location etcd key-value store (cluster master) Google Cloud Secret Manager (centralized) Eliminates sensitive credential leakage during etcd snapshots.
Encryption at Rest Base64 encoding (requires KMS for AES-CBC) Hardware Security Module (HSM) / Cloud KMS CMEK Guarantees FIPS 140-2 Level 3 envelope encryption.
Access Governance Kubernetes RBAC (coarse namespace scope) Cloud IAM (fine-grained per-secret roles) Enforces dual-plane principle of least privilege.
Lifecycle & Rotation Manual manifest patching or third-party operators Automatic rotation polling & version tracking Facilitates zero-downtime key rotation without pod restart.
Audit Trail Kubernetes API server audit logs Cloud Audit Logs (Data Access & Admin Activity) Provides immutable enterprise compliance and forensic tracing.
Apply it: Injection via Volume vs Environment Variable

Always prefer mounting secrets as volume files rather than injecting them via env or envFrom. Environment variables are captured in crash dumps, child process tables (/proc/$PID/environ), and application diagnostic logs, creating severe security vulnerabilities.

Workload Identity Federation for GKE

Historically, container workloads running inside Kubernetes that required access to Google Cloud services (such as Cloud Storage, BigQuery, or Secret Manager) relied on downloading long-lived service account private keys (JSON format) and mounting them into pods as Kubernetes Secrets. This pattern introduced massive security liabilities: private keys could be leaked through container image layers, committed to source control, or extracted by unauthorized operators, and they lacked automatic expiration or rotation.

Workload Identity Federation for GKE eliminates static private keys by binding Kubernetes ServiceAccounts (KSAs) directly to Google Cloud IAM Service Accounts (GSAs). Under this architecture, the GKE cluster acts as an OpenID Connect (OIDC) identity provider. When Workload Identity is enabled, GKE deploys the GKE Metadata Server as a DaemonSet on every worker node. When a pod makes an HTTP call to the Compute Engine metadata server (http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token), the GKE Metadata Server intercepts the request, reads the pod's projected KSA token, validates its signature against the cluster's OIDC discovery endpoint, and calls Google Cloud IAM Credentials API to generate a short-lived (1-hour) OAuth2 access token for the bound GSA.

Architecture Path: Static Service Account Keys vs Workload Identity Federation
Evaluation Vector Static Service Account JSON Keys Workload Identity Federation Security & Operational Impact
Credential Lifecycle Long-lived (valid up to 10 years unless revoked) Short-lived OAuth2 tokens (maximum 3600 seconds) Limits blast radius of compromised container tokens.
Key Storage Boundary Stored in etcd, container filesystem, or disk Never stored on disk; held purely in ephemeral RAM Prevents credential recovery from stolen node snapshots.
Identity Binding Node-level VM service account or shared Secret Granular Pod-level KSA-to-GSA namespace mapping Prevents sibling pods on same node from sharing IAM roles.
Revocation Speed Manual key deletion via gcloud / console Instantaneous by removing IAM policy binding Enforces immediate access revocation during security incidents.
Apply it: The Three-Way Binding Rule

Workload Identity requires three configuration steps: (1) Annotate the KSA with iam.gke.io/gcp-service-account=GSA_EMAIL; (2) Bind IAM role roles/iam.workloadIdentityUser on the GSA to member serviceAccount:PROJECT_ID.svc.id.goog[NAMESPACE/KSA_NAME]; (3) Specify serviceAccountName: KSA_NAME in the Pod specification.

Network Policies and Dataplane V2

Kubernetes operates on a default open networking model: every pod can route packets to every other pod across all namespaces without restriction. While this simplicity accelerates early development, enterprise cloud architectures mandate microsegmentation to enforce zero-trust security perimeters. The Kubernetes NetworkPolicy API allows platform architects to specify declarative packet filtering rules using label selectors for pods (podSelector), namespaces (namespaceSelector), and CIDR blocks (ipBlock) across both Ingress and Egress directions.

In standard GKE clusters without Dataplane V2, network policies were historically implemented using Calico or kube-iptables, which generated thousands of Linux kernel iptables rules. In large clusters, updating iptables chains introduced high CPU lock contention, slow policy convergence, and packet latency spikes. GKE Dataplane V2 replaces iptables entirely with Cilium and eBPF (extended Berkeley Packet Filter). In Dataplane V2, network policies are compiled into highly optimized eBPF bytecode loaded directly into the kernel's traffic control (tc) hooks on container veth interfaces. Packet filtering decisions occur in nanoseconds via eBPF map lookups (such as cilium_policy_v2), scaling effortlessly to thousands of pods and hundreds of policy rules.

Architecture Path: Default Flat Network vs Dataplane V2 eBPF Zero-Trust Policy
Boundary Component Default Kubernetes Network Dataplane V2 NetworkPolicy Architectural Outcome
Inter-Pod Access Unrestricted (any-to-any across cluster) Default-deny with explicit whitelist rules Restricts lateral movement following container compromise.
Enforcement Engine Linux kernel iptables (linear chain search) eBPF bytecode programs in kernel traffic control O(1) packet lookup overhead; zero iptables lock contention.
DNS Resolution Control Unfiltered UDP/TCP port 53 access Explicit egress rule required to kube-dns / CoreDNS Prevents covert DNS tunneling and data exfiltration.
External Egress Control Unrestricted outbound Internet access via NAT Restricted to approved CIDR blocks and ports Blocks outbound command-and-control (C2) channel callbacks.
Apply it: The DNS Egress Gotcha

When you apply an egress NetworkPolicy that isolates a pod (such as policyTypes: [Egress]), you MUST explicitly include an egress allow rule targeting the kube-system namespace on UDP and TCP port 53. If omitted, the pod will be unable to resolve internal Service names (CoreDNS), causing all microservice calls to fail with DNS timeouts.

Release channels and upgrade strategies (surge upgrades, maintenance windows)

Maintaining high availability across a Kubernetes fleet requires deliberate control over cluster upgrade cadences and worker node evacuation sequences. GKE automates Kubernetes minor and patch upgrades across three distinct Release Channels: Rapid (receives Kubernetes releases immediately for early testing; no SLA), Regular (default production channel; releases soaked for 2–3 months), and Stable (mission-critical enterprise workloads; conservative cadence receiving releases only after extensive global production validation).

When upgrading worker node pools, GKE provides two upgrade strategies: Surge Upgrades and Blue-Green Upgrades. In Surge Upgrades, GKE creates additional node VMs (controlled by maxSurge, e.g. 1 extra node) to maintain cluster compute capacity while cordoning and draining existing nodes (controlled by maxUnavailable, typically 0 for zero-downtime). Blue-Green Upgrades provision an entirely separate node pool of the new version, soak workload traffic on the new pool, and delete the old pool only after operational validation. To ensure upgrades never occur during business-critical operations, architects configure Maintenance Windows (specifying allowed 4–24 hour upgrade blocks) and Maintenance Exclusions (blocking all minor and patch upgrades for up to 30 consecutive days during peak retail events).

Architecture Path: GKE Node Pool Upgrade Strategies
Dimension Surge Upgrade (maxSurge=1, maxUnavailable=0) Blue-Green Upgrade (Batch Soaking) Selection Criteria
Capacity Overhead Low (requires 1–2 temporary surge node VMs) High (requires 100% duplicate node pool quota) Surge is cost-effective; Blue-Green requires high compute quota.
Rollback Speed Slow (must re-drain nodes back to old version) Instantaneous (traffic cut back to Blue pool) Blue-Green is preferred for mission-critical core banking.
Pod Disruption Handling Strictly honors PodDisruptionBudgets (PDBs) Honors PDBs during drain phase Misconfigured PDBs with minAvailable=100% will block upgrades.
Validation Window Continuous rolling drain per node Configurable soak duration (hours to days) Blue-Green allows extended soaking before committing.
Apply it: PodDisruptionBudgets (PDBs)

Always pair surge upgrades with PodDisruptionBudget manifests. A PDB ensures that GKE's node drain controller will never evict pods below your declared threshold (e.g. minAvailable: 2 or maxUnavailable: 1), guaranteeing continuous service availability throughout the upgrade process.

Startup vs readiness vs liveness probes

Container health checking in Kubernetes is divided across three distinct lifecycle phases executed locally by the node's kubelet: startupProbe, readinessProbe, and livenessProbe. Conflating these three probes is one of the most frequent causes of cascading cluster failures.

The startupProbe is designed for slow-starting applications (such as legacy Java enterprise applications, ML model inference servers, or workloads performing database schema migrations). When a startup probe is defined, all liveness and readiness checks are disabled until the startup probe succeeds. This provides a protected startup window (e.g. failureThreshold: 30 with periodSeconds: 5 gives 150 seconds of boot headroom) without loosening ongoing runtime liveness checks. The readinessProbe verifies whether the container is currently capable of serving incoming user requests. If readiness fails (due to overloaded connection pools or backend dependency drops), the pod's endpoint is removed from Service routing and load balancer NEGs; the container is NOT killed. The livenessProbe determines if the application process is deadlocked, hung, or corrupted. If the liveness probe fails, kubelet terminates the container process and restarts it according to its restartPolicy.

Architecture Path: Kubernetes Container Probe Matrix
Probe Type Operational Purpose Action on Consecutive Failure Traffic & Routing Impact
startupProbe Guards container initialization & cache warm-up Kills container and restarts pod Disables liveness & readiness until startup passes.
readinessProbe Validates application capacity to accept requests Keeps container alive; flags pod Unready Removes Pod IP from Service ClusterIP & Load Balancer NEGs.
livenessProbe Detects unrecoverable deadlocks & frozen loops Sends SIGTERM then SIGKILL to restart container Traffic remains routed until readiness or termination takes effect.
Apply it: Never Mirror Liveness to Readiness

Never configure liveness probes to inspect external dependencies (such as downstream databases or payment gateways). If the external database experiences a brief outage, all liveness probes will fail simultaneously, causing kubelet to reboot every pod in the cluster, creating a catastrophic restart storm.

Troubleshoot CrashLoopBackOff and OOMKilled using kubectl describe, logs, events and…

Workload failure diagnosis requires a systematic investigation sequence. When a pod enters a degraded state, platform architects navigate four primary diagnostic artifacts: pod termination state and exit codes via kubectl describe pod, previous process logs via kubectl logs --previous, chronological warning events via kubectl get events, and real-time container resource consumption via kubectl top pod.

The two most pervasive workload failure states are CrashLoopBackOff and OOMKilled. CrashLoopBackOff is not an error itself, but an exponential backoff state imposed by kubelet (10s, 20s, 40s, up to 300s) after a container process exits unexpectedly. Investigating the container's Exit Code reveals the root cause: Exit Code 0 indicates premature process completion; Exit Code 1 indicates application configuration or dependency exceptions; Exit Code 137 indicates the container was forcefully terminated by signal 9 (SIGKILL), typically triggered by the Linux kernel Out-Of-Memory Killer when memory usage breaches resources.limits.memory. Exit Code 143 indicates an orderly SIGTERM shutdown (such as during node drain or scaling down).

Architecture Path: Diagnostic Matrix for Pod Termination Signals
Observed State Exit Code Underlying Mechanism Prescribed Remediation
OOMKilled 137 (128 + 9) cgroup memory limit exceeded; kernel OOM killer invoked Increase resources.limits.memory; tune runtime heap (e.g. MaxRAMPercentage).
Application Crash 1 (or 2..127) Unhandled runtime exception, missing file, or syntax error Inspect kubectl logs -p; verify ConfigMaps, Secrets, and dependencies.
Premature Exit 0 Main container process finished execution (batch script) Verify entrypoint command; ensure server process runs in foreground.
Segmentation Fault 139 (128 + 11) Native memory corruption or invalid memory pointer access Inspect native C/C++ libraries or JVM native memory interface crashes.
Node Eviction N/A Kubelet evicted pod due to node disk pressure or memory pressure Inspect kubectl describe node; configure cluster autoscaling headroom.
Apply it: The `--previous` Flag

When a container crashes and restarts, running kubectl logs pod-name prints logs from the newly started container instance. To see the stack trace or fatal error that caused the previous instance to crash, you MUST run kubectl logs pod-name --previous (or kubectl logs pod-name -c container-name -p).

Config and secrets · field case

Situation and impact: Brightloaf's regional Order Fulfillment microservice failed during a major release rollout. All new replica pods entered a permanent CreateContainerConfigError state. Simultaneously, security monitoring detected that an emergency fallback patch had injected database connection strings containing plaintext passwords directly into container environment variables, exposing production credentials across container inspection logs and triggering an immediate PCI-DSS non-compliance escalation.

Constraints: Eliminate plaintext credentials from etcd and environment variables, automate credential synchronization from Google Cloud Secret Manager, preserve order fulfillment execution, and avoid hard restarts during credential rotation.

Evidence: Running kubectl describe pod order-fulfillment-84f9b revealed: Error: secret "order-db-creds" not found. In the preceding release, database passwords were passed via env.valueFrom.secretKeyRef, but the Secret had been purged during an automated namespace cleanup. An inspection of application container process tables on surviving nodes showed database passwords exposed in plaintext under /proc/$PID/environ.

Root cause: Workloads relied on decoupled, unversioned Kubernetes Secrets stored in etcd and injected via environment variables rather than utilizing centralized Secret Manager CSI volume mounts. When the static Secret was deleted, deployments broke, and plaintext credential injection breached security perimeters.

Diagnostic sequence:

  1. Describe failing pods with kubectl describe pod -l app=order-fulfillment to identify the missing Secret reference in the container specification.
  2. Inspect node events with kubectl get events --field-selector reason=FailedMount to observe volume setup failures.
  3. Audit environment variable exposure by running kubectl exec order-fulfillment-old -- env | grep -i pass to confirm plaintext password presence.
  4. Verify Secret Manager API availability with gcloud secrets list --filter="name~order-db" to locate the authoritative central secret version.

Defensible solution: Deploy the Secret Store CSI Driver and author a SecretProviderClass resource linking the pod to Google Cloud Secret Manager. Update the Deployment manifest to mount the secret as a volume under /etc/secrets rather than injecting environment variables. Configure the CSI driver with enable-secret-rotation: "true" and a 2-minute polling interval, allowing the fulfillment service to read rotated credentials from disk without requiring container restarts.

Verification: Apply the updated Deployment manifest and confirm all pods transition to Running (1/1). Execute kubectl exec -it order-fulfillment-new -- cat /etc/secrets/db-password to confirm file presence while verifying that env contains zero password strings. Audit Cloud Secret Manager access logs in Cloud Logging to confirm that the Secret Store CSI driver successfully accessed the secret using Workload Identity.

Residual risk: If Secret Manager experiences regional API throttling, initial volume mounts may experience transient delays. Applications must cache active credentials in memory and handle read retries gracefully.

Workload Identity Federation for GKE · field case

Situation and impact: Brightloaf's data analytics engineering team deployed an automated batch ingestion service on GKE to export order settlement logs to Google Cloud BigQuery. Immediately upon pod startup, the application threw fatal authentication errors: Google::Cloud::PermissionDeniedError: 403 Forbidden: Caller does not have required permission to use project. In an attempt to restore the batch feed, an engineer downloaded a static service account private key JSON file and committed it to a secret, violating company security policy and triggering a threat detection alert.

Constraints: Eliminate all static service account keys, enforce least-privilege access using Workload Identity Federation, restrict BigQuery dataset write permissions strictly to the analytics pod, and ensure zero credential management overhead for developers.

Evidence: Inspecting the failing pod revealed that it ran under the default Kubernetes ServiceAccount without any annotations. The Google Cloud IAM service account analytics-writer@brightloaf-prod.iam.gserviceaccount.com existed with roles/bigquery.dataEditor, but no IAM binding connected it to the GKE cluster. The GKE cluster had Workload Identity enabled, but the pod had not declared a dedicated KSA and was attempting to query the GKE metadata server without an authorized identity.

Root cause: The application lacked the required three-way Workload Identity binding: a dedicated Kubernetes ServiceAccount was not created, the KSA lacked the iam.gke.io/gcp-service-account annotation, and the Google Service Account had not granted roles/iam.workloadIdentityUser to the pod's namespace identity principal.

Diagnostic sequence:

  1. Check pod service account assignment with kubectl get pod -l app=order-analytics -o jsonpath='{.items[0].spec.serviceAccountName}', observing it used default.
  2. Query GSA IAM policy bindings with gcloud iam service-accounts get-iam-policy analytics-writer@brightloaf-prod.iam.gserviceaccount.com, confirming zero workloadIdentityUser bindings.
  3. Test metadata server token retrieval by running an ephemeral container: kubectl exec -it order-analytics-0 -- curl -H "Metadata-Flavor: Google" http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/email, observing that it returned the node's default compute service account rather than the analytics GSA.

Defensible solution: Implement the complete Workload Identity Federation workflow:

  1. Create a dedicated KSA named analytics-ksa in the analytics namespace.
  2. Annotate the KSA with the target GSA email: iam.gke.io/gcp-service-account=analytics-writer@brightloaf-prod.iam.gserviceaccount.com.
  3. Grant the KSA permission to impersonate the GSA using Cloud IAM: gcloud iam service-accounts add-iam-policy-binding analytics-writer@brightloaf-prod.iam.gserviceaccount.com --role=roles/iam.workloadIdentityUser --member="serviceAccount:brightloaf-prod.svc.id.goog[analytics/analytics-ksa]".
  4. Update the Deployment manifest to specify serviceAccountName: analytics-ksa.

Verification: Re-deploy the analytics pod and execute kubectl exec -it order-analytics-new -- curl -s -H "Metadata-Flavor: Google" http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/email. Verify that the returned email matches analytics-writer@brightloaf-prod.iam.gserviceaccount.com. Confirm that the pod successfully streams order settlement rows into the BigQuery destination table with zero 403 authorization errors.

Residual risk: If an operator deletes the KSA or accidentally changes the namespace name, the IAM principal string in workloadIdentityUser will no longer match, immediately severing token exchange. Keep namespace and KSA definitions in version-controlled GitOps repositories.

Network Policies and Dataplane V2 · field case

Situation and impact: Brightloaf's platform security team deployed a global zero-trust NetworkPolicy in the production namespace to satisfy ISO 27001 microsegmentation mandates. Within four seconds of applying the policy, the entire checkout pipeline crashed. Every microservice attempting to resolve internal cluster services (such as order-db.production.svc.cluster.local) or reach external credit card gateways failed with: dial tcp: lookup order-db... on 10.30.0.10:53: read udp: i/o timeout. Customer checkout transactions dropped to zero across all retail channels.

Constraints: Maintain strict zero-trust microsegmentation, prevent lateral container movement between unrelated namespaces, allow required inter-service communication, and restore cluster DNS and external egress paths.

Evidence: The security team had applied a default-deny-all NetworkPolicy that specified policyTypes: [Ingress, Egress] with empty rules. While this successfully blocked unauthorized lateral traffic, it simultaneously blocked all outbound egress from pods. Specifically, pods were prohibited from sending UDP/TCP packets to the cluster's CoreDNS service IP (10.30.0.10:53 in the kube-system namespace) and could not reach external Google Cloud APIs or payment endpoints.

Root cause: The egress NetworkPolicy failed to include an explicit egress permit rule for Kubernetes DNS resolution (UDP/TCP port 53 targeting kube-system) and lacked an egress rule allowing HTTPS traffic (TCP port 443) to external payment providers.

Diagnostic sequence:

  1. Describe applied network policies with kubectl get networkpolicies -n production, discovering default-deny-all.
  2. Inspect Cilium / Dataplane V2 packet drop logs via kubectl logs -n kube-system -l k8s-app=cilium --tail=50 | grep -i drop, identifying dropped egress packets targeting destination port 53.
  3. Test container socket connectivity from the order pod using kubectl exec -it order-api-0 -- nc -zvw3 10.30.0.10 53, observing connection timeout.

Defensible solution: Replace the crude blanket deny policy with a production-grade zero-trust NetworkPolicy. Specifically, author an egress rule on all application pods that explicitly permits egress to kube-system on port 53 (UDP and TCP) for DNS resolution, allows egress to the database namespace on TCP port 5432, and permits outbound egress to the Internet on TCP port 443 for external payment gateways while maintaining strict ingress isolation.

Verification: Apply the updated NetworkPolicy. Execute kubectl exec -it order-api-0 -- nslookup order-db.production.svc.cluster.local and verify instant resolution in under 2ms. Execute curl -I https://api.stripe.com from the container to confirm external HTTPS egress is functional. Attempt to curl an unrelated admin pod in the accounting namespace and verify that Dataplane V2 drops the unauthorized packet, confirming microsegmentation integrity.

Residual risk: If third-party external services operate on non-standard ports, egress rules must be updated in tandem. Operators should validate network policies in staging environments using Cilium network flow logs before applying them to production.

Release channels and upgrade strategies (surge upgrades, maintenance windows) · field case

Situation and impact: During Brightloaf's peak Black Friday promotional campaign, Google Kubernetes Engine initiated an automatic control plane and node pool patch upgrade. The cluster node pool began cordoning and draining worker nodes. Because the cluster lacked sufficient compute quota to provision temporary surge VMs and several microservices lacked PodDisruptionBudgets, single-replica inventory pods were forcibly evicted. Customers attempting to complete checkouts experienced continuous 503 Service Unavailable errors for 38 minutes.

Startup vs readiness vs liveness probes · field case

Situation and impact: Brightloaf launched a major upgrade to its Java-based Order Calculation engine. Immediately following deployment, all 10 replica pods entered an infinite restart crash loop. The pods failed to reach a ready state, and every 35 seconds, the kubelet killed the containers. CPU utilization across the node pool spiked to 100% as the JVM continually restarted, recompiled classes, and re-initialized connection pools without ever serving a single transaction.

Constraints: Accommodate a 70–80 second container initialization and warm-up window, detect genuine post-initialization deadlocks rapidly within 10 seconds, prevent traffic routing to uninitialized containers, and eliminate restart storms.

Evidence: Inspecting pod events with kubectl describe pod order-calc-78bc revealed: Liveness probe failed: HTTP probe failed with statuscode: 503 followed immediately by Killing container with id containerd://order-calc: Container failed liveness probe, will be restarted. The pod manifest had declared only a liveness probe: initialDelaySeconds: 15, periodSeconds: 10, and failureThreshold: 3. The application required 75 seconds to initialize Hibernate caches and verify database schema migrations. Because 15 + (10 * 2) = 35 seconds, the liveness probe timed out and killed the container at the 35-second mark, long before boot completed.

Root cause: Misconfigured probe lifecycle. The deployment relied solely on an aggressive liveness probe without a startupProbe. The kubelet repeatedly executed liveness checks against an initializing container, mistaking slow boot times for fatal deadlocks.

Diagnostic sequence:

  1. Describe the failing pod with kubectl describe pod -l app=order-calc to identify probe failure reasons and termination timestamps.
  2. Check previous container logs with kubectl logs -l app=order-calc -p, confirming the JVM was actively initializing Spring/Hibernate when it received SIGTERM.
  3. Measure cold start duration locally or in an isolated test container, recording an average boot duration of 72 seconds.

Defensible solution: Decouple the health checks into a three-stage probe architecture:

  1. Add a startupProbe configured with httpGet: /healthz/startup, periodSeconds: 5, and failureThreshold: 20 (providing up to 100 seconds of boot protection).
  2. Configure the readinessProbe with httpGet: /healthz/ready, periodSeconds: 5, and failureThreshold: 2 to gate traffic only when caches are loaded.
  3. Retain an agile livenessProbe configured with httpGet: /healthz/live, periodSeconds: 5, and failureThreshold: 3 that only begins firing after the startup probe succeeds.

Verification: Apply the updated deployment manifest. Observe pod startup via kubectl get pods -w. The pods remain in Running (0/1) during the 72-second initialization window without restarts, successfully transition to Running (1/1), and register with load balancer NEGs. Simulate an intentional deadlock on a running container and confirm that the liveness probe restarts the deadlocked container within 15 seconds.

Residual risk: Setting excessively long startup probe thresholds (e.g. 15 minutes) can delay failure reporting if an image genuinely hangs due to corrupt binaries. Size the startup threshold to 1.3x–1.5x of the measured p99 cold boot time.

Troubleshoot CrashLoopBackOff and OOMKilled using kubectl describe, logs, events and… · field case

Situation and impact: During an unexpected spike in customer cart reservations, Brightloaf's Inventory Reservation microservice crashed across multiple worker nodes, entering a persistent CrashLoopBackOff state. On-call engineers assumed the issue was CPU starvation, edited the deployment to increase CPU limits from 500m to 2000m, and restarted the deployment. The pods crashed again immediately. Inventory reservations remained offline for 52 minutes, resulting in widespread checkout abandonment and database table lock contention.

Constraints: Identify the true termination root cause using standard Kubernetes diagnostic commands, prevent cascading node memory exhaustion, rightsize container resource requests and limits, and restore inventory reservation reliability.

Evidence: Running kubectl describe pod inventory-reservation-69bc immediately highlighted the true failure: under Last State: Terminated, the container reported Exit Code: 137 and Reason: OOMKilled. The pod specification had defined requests.memory: 256Mi and limits.memory: 512Mi. Container process metrics revealed that during peak checkout bursts, in-memory reservation queues ballooned to 580MB, causing the Linux kernel cgroup controller to terminate the container process with SIGKILL (signal 9, exit code 128 + 9 = 137). Increasing CPU limits had zero impact because CPU throttling never causes an Exit Code 137 termination.

Root cause: The container was killed by the kernel cgroup Out-Of-Memory killer because active memory consumption exceeded the rigid 512Mi memory limit. Operators wasted 40 minutes troubleshooting CPU metrics because they did not inspect container termination states and exit codes.

Diagnostic sequence:

  1. Run kubectl describe pod <pod-name> and inspect Containers[].Last State, verifying Exit Code: 137 and Reason: OOMKilled.
  2. Inspect previous container logs via kubectl logs <pod-name> -p, noting that the application log terminated abruptly without an application exception stack trace.
  3. Check cluster events with kubectl get events --field-selector reason=OOMKilled to confirm widespread cgroup limit breaches.
  4. Inspect node memory saturation with kubectl top node and kubectl top pod to observe rapid memory consumption up to the 512Mi boundary.

Defensible solution: Rightsize the container memory profile. Increase requests.memory to 512Mi and limits.memory to 1024Mi, providing sufficient headroom for bursty in-memory reservation queues. For JVM containers, configure -XX:MaxRAMPercentage=75.0 to ensure the runtime leaves 25% of cgroup memory for native thread stacks and metaspace. Implement an in-memory queue bounded buffer that sheds excess requests gracefully rather than allocating unbounded heap memory.

Verification: Apply the updated manifest and execute load tests simulating 2x peak reservation volume. Monitor container memory consumption via kubectl top pod -l app=inventory-reservation, observing that memory peaks safely at 680Mi (well below the 1024Mi limit). Confirm zero Exit Code 137 terminations and 0% CrashLoopBackOff restarts.

Residual risk: Setting memory limits too high (or removing limits entirely) allows memory-leaking containers to consume host memory, potentially causing the node kernel to invoke the host-level OOM killer and terminate critical system daemon pods. Always pair container memory limits with node-level eviction thresholds.

Exercise 6: Diagnosing and Resolving CrashLoopBackOff & OOMKilled Failure Modes

Goal: Deploy synthetic failing workloads representing Exit Code 1 (application failure) and Exit Code 137 (OOMKilled memory limit breach), execute a systematic diagnostic command sequence, and apply precise code and cgroup remediations.

Expected result: Accurate differentiation between application crash loops and kernel memory terminations via container exit codes, followed by successful cgroup rightsizing.

Mode: tabletop / design · Prerequisite: Day 44, Day 8 exit artifacts.

  1. Preflight. Create a dedicated troubleshooting namespace: 
    kubectl create namespace diag-test
  2. Deploy Synthetic OOMKilled Workload (Exit Code 137). Save and apply oom-workload.yaml: 
    cat <<'EOF' > oom-workload.yaml
apiVersion: v1
kind: Pod
metadata:
  name: oom-victim
  namespace: diag-test
spec:
  containers:
  - name: memory-eater
    image: mirror.gcr.io/library/busybox:1.36
    # Allocates 150MB in RAM while limited to 64MB
    command: ["sh", "-c", "head -c 150M /dev/urandom | tr -d '\\0' > /dev/null"]
    resources:
      requests:
        memory: 32Mi
      limits:
        memory: 64Mi
EOF
kubectl apply -f oom-workload.yaml
  3. Execute Diagnostic Inspection for Exit Code 137. Wait for the crash and inspect the pod state: 
    sleep 5
kubectl describe pod oom-victim -n diag-test | grep -E "(State:|Last State:|Exit Code:|Reason:)"
    Observe that the output reports: 
    Last State:     Terminated
  Reason:       OOMKilled
  Exit Code:    137
    This confirms beyond doubt that the container was terminated by the kernel OOM killer due to exceeding its 64Mi limit.
  4. Deploy Synthetic Application Crash Workload (Exit Code 1). Save and apply app-crash.yaml: 
    cat <<'EOF' > app-crash.yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-crash-victim
  namespace: diag-test
spec:
  containers:
  - name: broken-app
    image: mirror.gcr.io/library/busybox:1.36
    # Simulates missing configuration file
    command: ["sh", "-c", "cat /etc/config/missing-file.conf"]
EOF
kubectl apply -f app-crash.yaml
  5. Execute Diagnostic Inspection for Exit Code 1. Inspect the termination state and previous logs: 
    sleep 5
kubectl describe pod app-crash-victim -n diag-test | grep -E "(Exit Code:|Reason:)"
kubectl logs app-crash-victim -n diag-test --previous
    Observe: 
    Exit Code:    1
cat: can't open '/etc/config/missing-file.conf': No such file or directory
    This proves an application configuration error rather than a resource constraint.
  6. Remediate OOMKilled Workload. Apply rightsized memory limits: 
    kubectl delete pod oom-victim -n diag-test

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: oom-resolved
  namespace: diag-test
spec:
  containers:
  - name: memory-eater
    image: mirror.gcr.io/library/busybox:1.36
    command: ["sh", "-c", "head -c 100M /dev/urandom | tr -d '\\0' > /dev/null && sleep 3600"]
    resources:
      requests:
        memory: 128Mi
      limits:
        memory: 256Mi
EOF
  7. Verify Remediated Workload. Inspect pod status: 
    kubectl get pod oom-resolved -n diag-test
    Confirm that the pod status is Running with 0 restarts.
  8. Cleanup. Delete diagnostic namespace: 
    kubectl delete namespace diag-test
  9. Artifact Acceptance. Document the diagnostic comparison table distinguishing Exit Code 137 from Exit Code 1 and save in day-045-workload-failures.md.
Expected result / acceptance

A confirmed forensic diagnosis distinguishing Exit Code 137 (OOMKilled) from Exit Code 1 (application crash), followed by successful memory limit rightsizing.

Troubleshooting

If an OOMKilled container does not report Exit Code 137, inspect node kernel logs with journalctl -k to check if the host Linux kernel OOM killer terminated the container process.
