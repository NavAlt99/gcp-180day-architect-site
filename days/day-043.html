1 · Topics of the day

Node pools, requests/limits, scheduling, taints/tolerations, HPA/VPA and node autoscaling

In Kubernetes, scheduling and elasticity depend directly on container resource governance. Requests represent the guaranteed allocation evaluated by kube-scheduler to place a pod onto a node with sufficient allocatable capacity; limits enforce hard operating ceilings executed by the Linux kernel via cgroups (CPU bandwidth throttling via CFS quota, and out-of-memory termination via the OOM killer).

Autoscaling operates across two synchronized layers: the Horizontal Pod Autoscaler (HPA) scales pod replicas based on measured resource utilization relative to requests, while the Cluster Autoscaler (CA) detects unschedulable Pending pods and provisions new Compute Engine node VMs. When requests and limits are misaligned, pods can be prematurely killed during traffic spikes, or cluster autoscaling can stall because requested capacities exceed physical node sizes.

Problem preview: A developer configures memory limits identical to requests at 512Mi on a JVM-based Order API container without accounting for heap overhead. During a lunch peak, memory spikes trigger kernel OOM kills across active pods; as HPA attempts to scale out to 20 replicas, every new pod is immediately killed during initialization, plunging the service into a catastrophic crash loop.

Kubernetes RBAC versus IAM

Securing a GKE cluster requires navigating two distinct authorization planes: Google Cloud IAM and Kubernetes RBAC. Google Cloud IAM governs access to the GKE control plane API (e.g. creating clusters, resizing node pools, obtaining cluster credentials), whereas Kubernetes RBAC governs granular actions on resources inside the cluster (e.g. reading Secrets, creating Deployments, viewing Pod logs within a specific namespace).

When a developer receives a 403 Forbidden from kubectl, teams frequently misdiagnose the failure as a GCP IAM issue and grant dangerous project-level IAM roles (such as roles/editor or roles/owner) instead of creating a scoped Kubernetes RoleBinding inside the target namespace.

Problem preview: An operator attempts to read a production database Secret via kubectl get secret db-credentials and receives an RBAC authorization denial. In response, a platform administrator grants the operator roles/owner in Google Cloud IAM, inadvertently giving full project administrative control across all cloud resources while still failing to grant internal cluster RBAC permissions.

Workload controller selection and routing abstractions

Kubernetes provides specialized workload controllers tailored to specific execution semantics: Deployments (stateless, interchangeable replicas with rolling updates), StatefulSets (ordered, deterministic network ordinals and dedicated persistent disk bindings), DaemonSets (guaranteeing exactly one pod per eligible node for logging or host agents), and Jobs/CronJobs (finite batch processing run-to-completion).

Networking abstractions similarly decouple endpoints: ClusterIP Services provide internal layer-4 virtual IPs, while the modern Gateway API (replacing legacy Ingress) provides expressive, role-oriented HTTP routing across hostnames and paths. Applying an incorrect controller—such as using a stateless Deployment for a stateful sequencer—violates operational invariants and causes data corruption.

Problem preview: An engineer deploys an in-memory order numbering sequence generator as a stateless Deployment with 3 replicas behind a ClusterIP Service. Inbound order creation calls round-robin across all three pods, producing non-sequential and duplicate order IDs that violate database unique constraints and disrupt warehouse logistics.

2 · Technical discussion of each topic

Node pools, requests/limits, scheduling, taints/tolerations, HPA/VPA and node autoscaling

Requests vs limits: scheduling vs kernel enforcement

Resource allocation in Kubernetes is governed by two independent metrics per container:

  • Requests: Used exclusively by kube-scheduler during the scheduling phase. A node can accept a pod only if:

    node_allocatable - sum(existing_pod_requests) >= new_pod_request

    If no node has sufficient allocatable capacity, the pod remains in a Pending state.
  • Limits: Enforced by the Linux kernel on the worker node.
    • CPU limits: Enforced by the Completely Fair Scheduler (CFS) quota. If a container exceeds its CPU limit, the kernel throttles CPU cycles. The process slows down but is not killed.
    • Memory limits: Enforced by Linux memory cgroups. If a container exceeds its memory limit, the kernel Out-Of-Memory (OOM) killer immediately terminates the process (exit code 137, OOMKilled).

HPA and Cluster Autoscaler interaction loop

The Horizontal Pod Autoscaler and Cluster Autoscaler operate in an orchestrated feedback loop:

  1. HPA queries the Kubernetes Metrics Server every 15 seconds. If average pod CPU utilization exceeds the target percentage (e.g. 60% of CPU request), HPA increases the Deployment's replica count.
  2. The Deployment controller creates new Pods. kube-scheduler attempts to place them onto existing worker nodes.
  3. If existing nodes lack available allocatable capacity to satisfy the new pods' requests, the pods transition to Pending with a FailedScheduling event.
  4. The Cluster Autoscaler observes the Pending pods, identifies which node pool can satisfy their resource requests and node selectors, and triggers an API call to Compute Engine to expand the node pool instance group.
  5. Once new node VMs boot and join the cluster as Ready, the scheduler places the pending pods.

HPA Pod Replicas CPU/Memory utilization vs request, custom metrics Increases/decreases spec.replicas
Cluster Autoscaler Node VMs Pods in Pending state due to capacity Adds/removes Compute Engine VMs from node pool

Kubernetes RBAC versus IAM

Dual-gate authentication and authorization

Every request sent via kubectl traverses two distinct security gates:

  1. Gate 1: Cloud IAM (Google Cloud Plane): Authenticates the user's Google Identity (OAuth2 token) and verifies cluster management permissions (e.g. container.clusters.get). This grants access to download the kubeconfig and reach the cluster endpoint.
  2. Gate 2: Kubernetes RBAC (Cluster Plane): Evaluated inside kube-apiserver. RBAC maps the authenticated email (e.g. alice@brightloaf.com) to cluster-internal Roles or ClusterRoles via RoleBindings. RBAC enforces least privilege on API groups, resources, and verbs (e.g. get, list, create).

3 · Real-world problems and solutions

The scenarios below represent realistic production engineering failure modes involving Kubernetes resource sizing, dual-plane access governance, and controller selection.

Topic 1 field case — Strict memory limits trigger cascading OOMKilled crash loop during HPA scale-out

Situation and business impact

The Brightloaf Order API service is deployed to GKE with Horizontal Pod Autoscaler enabled (target 60% CPU). The container resource configuration specifies requests.memory: 512Mi and limits.memory: 512Mi. The application is a Java Spring Boot microservice that requires 400MB under steady state, but during heap initialization and garbage collection pauses under load, its resident set size (RSS) briefly surges to 580MB.

During an 11:30 AM lunch promotional event, incoming traffic triples. As memory consumption crosses 512MB, the Linux kernel cgroup OOM killer immediately terminates the active pods with exit code 137 (OOMKilled). HPA detects increased CPU and queues, creating 12 additional pod replicas. As each new pod launches and executes JVM warm-up, it hits the 512MB ceiling and is killed within 10 seconds. The entire API fleet enters CrashLoopBackOff, causing total checkout failure for 25 minutes.

Constraints

  • Container memory limits must accommodate temporary JVM garbage collection and classloader spikes.
  • Resource requests must accurately guide the scheduler without stranding unused node memory.
  • Workloads must preserve the invariant that replaying an order event never triggers duplicate fulfillment.

Root cause

Setting a hard memory limit equal to the baseline memory request on a memory-bursty Java workload. Memory limits are enforced with immediate process termination by the Linux kernel; unlike CPU throttling, there is zero grace period for memory overages.

Diagnostic sequence

  1. Inspect pod state: kubectl describe pod POD_NAME reveals Last State: Terminated with Reason: OOMKilled and Exit Code: 137.
  2. Correlate kernel metrics: Cloud Monitoring displays container/memory/used_bytes reaching exactly container/memory/limit_bytes before instant drops to zero.
  3. Inspect HPA events: Confirm HPA scaled replica count up, but all new pods failed to transition to Ready.

Defensible solution

Decouple memory requests from limits: set requests.memory: 512Mi (allowing dense node scheduling) and increase limits.memory: 1024Mi (providing a 100% buffer for JVM warm-up and GC spikes). Tune JVM flags to limit max heap: -XX:MaxRAMPercentage=70.0.

Verification

Execute a synthetic load test step-jump in staging: verify that under load, container memory climbs to 620MB, JVM garbage collection reclaims memory, and pods remain 100% Running with zero OOMKilled terminations.

Residual risk

If memory limits are set too high (or omitted entirely), an actual memory leak inside the container can consume all available node memory, forcing the kernel to terminate critical neighboring pods on the same node.

Topic 2 field case — Kubernetes RBAC secret denial misdiagnosed with dangerous IAM Owner grant

Situation and business impact

During a weekend incident investigation, an application support engineer attempts to inspect database connection parameters by running kubectl get secret db-credentials -n production. The command fails with an error: Error from server (Forbidden): secrets "db-credentials" is forbidden: User "support@brightloaf.com" cannot get resource "secrets" in API group "" in the namespace "production".

The platform administrator misdiagnoses the error as a Google Cloud IAM failure. To expedite troubleshooting, the administrator grants the user roles/owner at the GCP project level. However, rerunning the kubectl command still results in the exact same 403 Forbidden error because in-cluster RBAC is evaluated independently by kube-apiserver. Meanwhile, the support engineer now possesses un-audited project-wide permissions to delete databases, modify VPC firewalls, and alter IAM policies, creating an immediate critical security compliance breach.

Constraints

  • Administrative access must strictly adhere to the principle of least privilege.
  • Must clearly separate Google Cloud infrastructure IAM governance from Kubernetes cluster-internal RBAC.
  • Production database secrets must only be visible to authorized principals within designated namespaces.

Root cause

Conflating Cloud IAM with Kubernetes RBAC. The API server denied the operation because of missing in-cluster RBAC permissions. Granting GCP IAM Owner has zero effect on Kubernetes RBAC rules inside the cluster.

Defensible solution

  1. Immediately revoke the project-level roles/owner IAM grant from the support user.
  2. Ensure the user retains appropriate baseline GCP IAM access (roles/container.viewer) to reach the cluster.
  3. Create a targeted Kubernetes Role in namespace production granting read access to specific secrets, and bind it to the user's email via a RoleBinding.

Verification

Authenticate as the support user: run kubectl auth can-i get secrets -n production. Verify the command outputs yes. Run kubectl auth can-i delete secrets -n production and verify it outputs no. Verify GCP IAM reflects zero elevated project-level permissions.

Residual risk

If GKE legacy Cloud IAM mapping is enabled, certain administrative IAM roles (such as roles/container.admin) automatically grant cluster-admin RBAC rights; organizations should enforce Google Groups for GKE to manage RBAC declaratively.

Topic 3 field case — Stateless Deployment applied to stateful sequencer causes duplicate order IDs

Situation and business impact

To assign guaranteed monotonic sequential transaction IDs to incoming orders, Brightloaf engineers deploy a lightweight sequence generator service (order-sequencer). The engineer packages the application as a standard Kubernetes Deployment with replicas: 3 behind a ClusterIP Service.

Because Deployments treat pods as interchangeable, stateless workers, each of the three pods boots independently with an internal local counter starting at the last database checkpoint. As checkout requests arrive, the ClusterIP service round-robins requests across the three pods. The pods concurrently issue identical order numbers (e.g. Order #10042 is issued by Pod A, Pod B, and Pod C to three different customers). When the orders are committed to Cloud SQL, database unique constraint violations trigger unhandled transaction rollbacks, corrupting order status and causing customer credit cards to be charged without creating confirmed orders.

Constraints

  • Order numbering must be strictly unique and sequential across all order events.
  • Replaying an order event must preserve the invariant that replaying an event never triggers duplicate fulfillment.
  • Workloads requiring stateful identity and dedicated storage must use the appropriate Kubernetes controller.

Root cause

Misapplying a stateless Deployment controller to a stateful sequencing application. Deployments provide no ordered execution, no persistent pod identity, and no exclusive state locking.

Defensible solution

Migrate the sequencer workload from a Deployment to a StatefulSet with replicas: 1 (or an active-passive leader-elected StatefulSet) with a dedicated volumeClaimTemplate. A StatefulSet guarantees a deterministic identity (order-sequencer-0) and ensures that even during pod recreation or node rescheduling, the replacement pod mounts the exact same persistent sequence ledger before accepting traffic.

Verification

Execute a concurrent load test generating 1,000 rapid order number requests: verify that all 1,000 generated order IDs are strictly unique, monotonic, and error-free, with zero database unique constraint collisions.

Residual risk

A single-replica StatefulSet represents a single point of failure during pod restarts; for high-availability sequencing, the application must implement distributed consensus (e.g. Raft or Redis atomic increments).

Exercise 1 — Deliberately creating a Pending pod and diagnosing scheduler events

Goal: Submit a pod manifest with excessive resource requests, observe the scheduler failure, and diagnose using events.

Mode: local cluster (kind/minikube) or GKE sandbox · Prerequisites: Day 42 exit artifact.

Preflight

Open day-043-scheduling.md. Confirm local cluster access (kubectl get nodes). Note the total allocatable CPU of worker nodes.

  1. Apply an oversized pod manifest. Create a pod requesting 64 vCPUs (exceeding node capacity): 
    kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: oversized-test-pod
spec:
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
    resources:
      requests:
        cpu: "64"
EOF
  2. Observe Pending state. Run kubectl get pod oversized-test-pod. Verify the status displays Pending.
  3. Diagnose scheduling failure. Run kubectl describe pod oversized-test-pod. Locate the Events: section:

    Expected output: Warning FailedScheduling default-scheduler 0/3 nodes are available: 3 Insufficient cpu.

    Record this event trace in day-043-scheduling.md.
  4. Remediate the manifest. Edit the request to fit node capacity (e.g. cpu: 100m): 
    kubectl delete pod oversized-test-pod
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: oversized-test-pod
spec:
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.9
    resources:
      requests:
        cpu: "100m"
EOF
    Verify the pod transitions to Running immediately.
Expected result

A captured FailedScheduling event trace and corrected manifest recorded in day-043-scheduling.md.

Exercise 2 — Diagnosing Kubernetes RBAC 403 denial versus IAM authorization

Goal: Differentiate an in-cluster RBAC denial from Google Cloud IAM permissions and configure a scoped RoleBinding.

Mode: tabletop / sandbox · Prerequisites: Exercise 1.

  1. Simulate an RBAC permission check. Test if a developer can read secrets in the production namespace: 
    kubectl auth can-i get secrets --namespace=production --as=developer@brightloaf.com
    Expected output: no.
  2. Author a scoped Kubernetes Role. 
    kubectl apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: secret-reader-role
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: production
  name: secret-reader-binding
subjects:
- kind: User
  name: developer@brightloaf.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: secret-reader-role
  apiGroup: rbac.authorization.k8s.io
EOF
  3. Re-test authorization. 
    kubectl auth can-i get secrets --namespace=production --as=developer@brightloaf.com
    Expected output: yes. Document in day-043-scheduling.md why modifying GCP project IAM would not have satisfied this check.
Expected result

An RBAC authorization verification log proving internal namespace role binding without GCP IAM escalation.

Exercise 3 — Workload controller selection and HPA/Cluster Autoscaler scaling model

Goal: Formulate an HPA and Cluster Autoscaler capacity model for the Brightloaf Order API and document controller mappings.

Mode: architectural analysis · Prerequisites: Exercises 1 and 2.

  1. Map the workload matrix. In day-043-scheduling.md, assign each Brightloaf component to its proper controller:
    • Order API → Deployment (stateless, horizontal scaling).
    • Fulfillment Worker → Deployment or Job (idempotent Pub/Sub consumer).
    • Order Sequencer & Database → StatefulSet (monotonic identity, dedicated storage).
    • Node Log Collector → DaemonSet (host log ingestion).
  2. Model the two-tier autoscaling curve. Calculate:
    • Pod request: cpu: 500m. Node allocatable capacity: cpu: 3800m per e2-standard-4 node (max 7 pods/node).
    • Traffic surge scales pods from 4 to 28 pods.
    • Calculate required nodes: 28 pods / 7 pods/node = 4 nodes. Cluster Autoscaler expands node pool from 1 to 4 nodes.
Expected result / acceptance

A completed day-043-scheduling.md exit artifact containing the Pending pod diagnostic trace, corrected manifest, RBAC authorization verification, and two-tier scaling calculations.

kubectl delete role secret-reader-role -n production --ignore-not-found
kubectl delete rolebinding secret-reader-binding -n production --ignore-not-found
