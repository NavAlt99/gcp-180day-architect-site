2 · Architecture, control flow, boundaries, and limits

End-to-end foundation request trace and system boundaries

Scope, control flow, and ownership. A complete understanding of cloud architecture requires mapping the lifecycle of an application request across all foundational abstraction layers mastered during Block 1:

  1. Client & Name Resolution (Days 3 & 4): The client resolves api.brightloaf.internal using recursive DNS resolution. The authoritative DNS server returns an A record (10.0.2.10). The client establishes a TCP connection on port 443, completes the TLS 1.3 cryptographic handshake, and issues an HTTP POST request carrying an X-Request-ID correlation token.
  2. Subnet & Network Routing (Day 2): The client operating system evaluates its local routing table. Because the destination (10.0.2.10) resides outside its local subnet (10.0.1.0/24), the packet is directed to the default gateway (10.0.1.1). Layer 3 IP forwarding routes the packet across disjoint, non-overlapping subnets to the host network interface without routing loops.
  3. Host & Container Isolation (Days 5, 8, 9, 10): The Linux host receives the packet on eth0. Linux iptables NAT rules forward port 8080 traffic across a virtual bridge to the container network namespace. Linux cgroups enforce memory limits (512 MB), while user namespaces ensure the process executes as a non-root service account (UID 10001).
  4. Twelve-Factor Application Processing (Day 15): The Python application service reads configuration strictly from environment variables (Factor III), parses the incoming JSON payload, validates field types and constraints (returning HTTP 422 on schema violation), and emits unbuffered, structured JSON logs containing timestamp, severity, and request ID to stdout (Factor XI).
  5. Relational Persistence & Invariants (Day 16): The handler opens an atomic transaction (BEGIN TRANSACTION). It inserts the order header and line items into a normalized 3NF relational schema, updates inventory, and inserts a record into order_fulfillments. If any query raises an exception, the handler invokes conn.rollback(), leaving zero orphaned records. An explicit UNIQUE(order_id) constraint on order_fulfillments guarantees that replayed requests can never cause duplicate physical fulfillment (≤ 1 shipment invariant).

Five-dimension rubric, evaluation threshold, and remediation flow

The five evaluation dimensions. The roadmap evaluates architectural readiness using a structured, five-dimension rubric applied across all gates and capstone milestones:

  1. Correctness (Weight: 3 pts): Calculations, network addresses, schema constraints, and shell commands are mathematically and syntactically sound. Zero unhandled exceptions or syntax errors exist in executable artifacts.
  2. Requirement Traceability (Weight: 3 pts): Every architectural decision and configuration parameter links directly to explicit business outcomes, constraints, and curriculum objectives.
  3. Evidence Quality (Weight: 3 pts): All technical assertions are substantiated by timestamped terminal logs, exit codes, and automated assertions. Evidence is reproducible by an independent reviewer without ambient or tribal knowledge.
  4. Failure / Recovery Reasoning (Weight: 3 pts): Architectural designs predict concrete failure modes, implement automated rollback or recovery mechanisms, and strictly defend core business invariants (such as ≤ 1 fulfillment).
  5. Communication (Weight: 3 pts): Explanations are clear, concise, and professional, aligning technical controls with executive business outcomes (Cloud Digital Leader framing) and clearly distinguishing observed facts from tabletop models.

Scoring scale and advancement criteria. Each dimension is scored from 0 to 3: 0 = Absent/Incorrect: Requirement unaddressed or fundamentally flawed; 1 = Partial: Incomplete implementation or unexplained technical gaps; 2 = Adequate with stated limits: Fully functional solution with recognized assumptions and boundaries; 3 = Clear, reproducible, and defensible: Production-grade implementation backed by automated verification and thorough risk analysis.

Advancement rule for Gate 1: To pass Gate 1 and advance to Block 2 (Days 18–35: Cloud environment and identity), a learner must achieve a score of at least 2 in every dimension and an aggregate score of at least 12 out of 15. Any score below 2 requires targeted remediation of that specific topic without adding unneeded cloud services.

3 · Real-world field problems and incident handling

Incident exercise · Overlapping subnets and DNS search loop stall service deployment

Illustrative scenario—not an observed production incident. During an attempted microservice deployment connecting Brightloaf's order intake service to its internal database, container instances running on a Linux Docker bridge experienced complete connection timeouts. Application logs reported repeated psycopg2.OperationalError: could not connect to server: Connection timed out (10000ms) when attempting to resolve and connect to db.internal. When the on-call engineer inspected the container network using the Linux ip-route utility, they discovered that the newly created Docker bridge network had been assigned 10.0.1.0/24, which identically overlapped with the physical host's internal database subnet. Packets destined for the database were routed internally to the local virtual bridge interface (veth) rather than exiting the host gateway. Furthermore, the container's /etc/resolv.conf contained four nested search domains (order.svc.cluster.local, svc.cluster.local, cluster.local, internal), causing DNS queries to loop through multiple recursive NXDOMAIN responses before timing out, bringing the staging deployment to a complete halt.

Constraints: Rely exclusively on synthetic Brightloaf test fixtures, incur zero cloud billing cost, and maintain the duplicate fulfillment invariant.

Root cause analysis: The engineering team lacked rigorous networking foundation verification: (1) overlapping RFC 1918 CIDR allocations (10.0.1.0/24 assigned to both container bridge and database tier) created a routing collision where destination IPs were treated as link-local; and (2) excessive wildcard search domains generated search loops, exceeding client socket timeout thresholds.

5-step diagnostic sequence:

  1. Execute the IP route inspection command and the Docker network inspection command to map all active network interfaces and identify overlapping CIDR ranges across host and container bridges.
  2. Trace packet routing using querying the route lookup for destination 10.0.1.50 to observe that the kernel routes packets to the local virtual interface rather than the physical gateway.
  3. Inspect container DNS configuration (reviewing the resolver configuration in /etc/resolv.conf) and measure DNS resolution latency using time getent hosts db.internal to isolate search domain traversal delays.
  4. Reconfigure the container bridge network to use a disjoint, non-overlapping subnet allocation (e.g. 10.10.1.0/24 for application containers and 10.20.1.0/24 for databases).
  5. Configure an authoritative Fully Qualified Domain Name (FQDN) mapping (db.production.brightloaf.internal) and verify that TCP connection handshakes complete in under 2 ms with zero packet drops.

Defensible solution: Re-architect the network topology into disjoint RFC 1918 subnets and establish explicit FQDN name resolution: First, define an IP address management (IPAM) matrix reserving 10.10.0.0/16 for container application workloads and 10.20.0.0/16 for backend database persistence, eliminating link-local routing collisions. Second, configure container network definitions with explicit non-overlapping subnets (e.g. the container network subnet definition (e.g. --subnet=10.10.1.0/24)). Third, eliminate redundant search domains in container configurations and enforce fully qualified domain names for inter-service communication. Fourth, document these routing and name resolution rules as mandatory preflight checks in the deployment automation pipeline.

Verification and residual risk: Execute synthetic network test scripts asserting that 10.10.1.0/24 and 10.20.1.0/24 communicate across the gateway with zero packet loss; verify that DNS queries resolve in under 2 ms without recursive search domain lookups; confirm that order transactions complete with end-to-end ACID durability and duplicate fulfillment prevention. Residual risk: In multi-VPC cloud environments, future peering connections can introduce route conflicts if CIDR blocks are allocated without centralized IPAM governance; mitigate by maintaining a version-controlled IP registry prior to provisioning cloud networks in Block 2.

Incident exercise · Event replay violates duplicate fulfillment invariant in safety audit

Illustrative scenario—not an observed production incident. During an internal Gate 1 tabletop audit of Brightloaf's order fulfillment service, the architecture review board injected an asynchronous event replay test: an order event (BL-17-901) that had successfully completed processing 15 minutes earlier was re-submitted to the fulfillment queue to simulate an upstream network timeout and Pub/Sub at-least-once message redelivery. The candidate application consumer received the replayed event, parsed the JSON payload, and proceeded to execute its standard fulfillment workflow: it generated a second shipping tracking number (ful-002), dispatched a second notification email to the customer, and decremented physical inventory for a second time. When auditors inspected the warehouse dispatch log, they confirmed that two physical boxes of sourdough had been marked for shipment for a single customer purchase, violating Brightloaf's fundamental duplicate fulfillment invariant (≤ 1 physical fulfillment per unique order ID) and resulting in an immediate Gate 1 audit failure.

Constraints: Rely on synthetic Brightloaf test fixtures, observe zero budget spend, and preserve prior audit evidence.

Root cause analysis: The application engineering team assumed that message brokers guarantee exactly-once delivery and failed to implement idempotency guards within the application or database layer. The fulfillment table lacked a unique constraint on order_id, allowing the consumer to insert multiple fulfillment records for the same order without database kernel rejection.

5-step diagnostic sequence:

  1. Query the relational fulfillment table: SELECT order_id, count(fulfillment_id) FROM order_fulfillments GROUP BY order_id HAVING count(fulfillment_id) > 1; to identify duplicate fulfillments generated by the replay test.
  2. Audit the consumer source code to check for idempotency handling or deduplication caches prior to invoking warehouse fulfillment APIs.
  3. Inspect the database schema DDL using .schema order_fulfillments to verify the absence of uniqueness constraints on the order_id foreign key.
  4. Refactor the relational schema by adding an explicit unique constraint: ALTER TABLE order_fulfillments ADD CONSTRAINT unique_order_fulfillment UNIQUE (order_id);.
  5. Update consumer application code to wrap fulfillment creation in an atomic transaction; catch database unique constraint violations (e.g. IntegrityError); log an idempotent confirmation with new_fulfillment: false; and acknowledge the replayed message without generating duplicate shipments.

Defensible solution: Implement schema-level idempotency enforcement and atomic transaction boundaries: First, add an explicit UNIQUE(order_id) constraint on the order_fulfillments table. This provides immutable, database-level defense-in-depth: even if upstream message brokers redeliver an event multiple times, the database storage engine strictly rejects subsequent insertions. Second, structure the fulfillment handler to query existing fulfillment state inside an atomic transaction: if a record exists for order_id, return HTTP 200 with new_fulfillment: false and exit cleanly. Third, implement structured JSON logging that explicitly flags idempotent message replays ({"severity": "INFO", "order_id": "BL-17-901", "new_fulfillment": false, "message": "Duplicate event re-submission suppressed"}), providing transparent audit evidence for operations teams.

Verification and residual risk: Execute a synthetic automated replay test submitting the identical order fulfillment event three consecutive times; verify that the first execution creates the shipment (new_fulfillment: true) and the subsequent two executions trigger unique constraint suppression, returning new_fulfillment: false without incrementing warehouse counts; confirm that exactly 1 physical fulfillment record exists in the database. Residual risk: High-frequency concurrent replays can trigger transient lock contention on the unique index; mitigate by implementing brief exponential backoff on retry before confirming idempotent completion.

def test_section_5_relational_rollback_and_invariant():
    print("\n--- [Test 5/5] Relational ACID Rollback & Duplicate Fulfillment Invariant ---")
    # Test SQLite schema, transaction rollback, and duplicate fulfillment prevention (Day 16)
    conn = sqlite3.connect(":memory:")
    c = conn.cursor()
    c.execute("PRAGMA foreign_keys = ON;")

    c.execute("""
    CREATE TABLE orders (
        order_id TEXT PRIMARY KEY,
        status TEXT NOT NULL
    );
    """)

    c.execute("""
    CREATE TABLE order_items (
        order_id TEXT NOT NULL,
        line_no INTEGER NOT NULL,
        price REAL NOT NULL CHECK(price > 0),
        PRIMARY KEY (order_id, line_no),
        FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE CASCADE
    );
    """)

    # Relational duplicate fulfillment invariant guard
    c.execute("""
    CREATE TABLE order_fulfillments (
        fulfillment_id TEXT PRIMARY KEY,
        order_id TEXT UNIQUE NOT NULL,
        shipped_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        FOREIGN KEY (order_id) REFERENCES orders(order_id)
    );
    """)
    conn.commit()

    # Part A: Test Atomic Rollback
    try:
        c.execute("BEGIN TRANSACTION;")
        c.execute("INSERT INTO orders VALUES ('BL-FAIL-01', 'CONFIRMED');")
        # Injected constraint violation: negative price violates CHECK constraint
        c.execute("INSERT INTO order_items VALUES ('BL-FAIL-01', 1, -10.0);")
        conn.commit()
    except sqlite3.IntegrityError:
        conn.rollback()

    c.execute("SELECT count(*) FROM orders WHERE order_id = 'BL-FAIL-01';")
    assert c.fetchone()[0] == 0, "Rollback failed! Orphaned order record found."
    print("✓ Rollback verified: Injected exception triggered clean rollback with 0 orphaned records.")

    # Part B: Test Duplicate Fulfillment Invariant Guard
    c.execute("BEGIN TRANSACTION;")
    c.execute("INSERT INTO orders VALUES ('BL-OK-01', 'CONFIRMED');")
    c.execute("INSERT INTO order_items VALUES ('BL-OK-01', 1, 6.50);")
    c.execute("INSERT INTO order_fulfillments (fulfillment_id, order_id) VALUES ('ful-001', 'BL-OK-01');")
    conn.commit()

    # Attempt replayed fulfillment event for same order
    dup_rejected = False
    try:
        c.execute("INSERT INTO order_fulfillments (fulfillment_id, order_id) VALUES ('ful-002', 'BL-OK-01');")
        conn.commit()
    except sqlite3.IntegrityError:
        conn.rollback()
        dup_rejected = True

    assert dup_rejected is True, "CRITICAL ERROR: Duplicate fulfillment was accepted!"
    c.execute("SELECT count(*) FROM order_fulfillments WHERE order_id = 'BL-OK-01';")
    assert c.fetchone()[0] == 1, "Expected exactly 1 fulfillment record."
    print("✓ Invariant verified: Relational UNIQUE constraint rejected duplicate fulfillment replay.")
    conn.close()
    return True
