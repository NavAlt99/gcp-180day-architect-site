1 · Topics of the day

Google's private global network and edge points of presence

A point of presence (PoP) is an edge site where Google connects with peering or transit networks. For an internet-facing service, the chosen Network Service Tier influences where traffic crosses between those external networks and Google's network; this belongs after Day 30's location decision because a region does not, by itself, describe the client delivery path.

In Brightloaf, the path sits between a customer's ISP and the Order API's external frontend; it does not replace DNS, a load balancer, backend placement, or application controls.

Problem preview: Customers far from the workload report a path-dependent experience after Brightloaf assumes every external IP enters Google near the user. The uncertain delivery path delays checkout and makes support unable to defend the network choice.

Network Service Tiers (Premium vs Standard)

Network Service Tiers is a resource-level choice for eligible internet-facing resources: Premium favors Google's backbone and global networking features, while Standard is a cost-oriented regional option with a more limited feature set. It belongs today because the trade-off must be made against the same users, region, frontend type, and traffic assumptions—not as a slogan that one tier is always better.

The control sits on eligible external IP addresses and related forwarding resources; global external IP addresses are Premium, while eligible regional external IPv4 addresses can use either tier.

Problem preview: Brightloaf changes a project default to Standard but leaves an existing global frontend unchanged. The expected saving does not follow from the actual resource configuration, and the unsupported target architecture cannot be approved.

Service availability differs by region (always check)

A named Google Cloud region does not guarantee that every product, feature, machine series, quota, or tier-compatible frontend is available there. This check belongs in the delivery-path decision because a paper design is invalid if one of its regional components cannot be provisioned or paired at the required scope.

The check crosses the product location page, the product-specific availability table, resource scope rules, quota/capacity review, and current pricing; it is an architecture gate, not a one-time memory test.

Problem preview: Brightloaf selects a candidate region before confirming that every required frontend and backend option is offered there. Implementation stops at the first unavailable dependency, delaying the release and forcing an architecture review.

2 · Technical discussion of each topic

Google's private global network and edge points of presence

Separate the internet segment from the Google-network segment. For Premium inbound traffic, Google advertises next hops across its global network to encourage handoff at a PoP close to the user, then carries traffic toward the workload. For Standard inbound traffic, the preferred handoff is at PoPs close to the region of the Standard-tier IP, so more of the path can remain on ISP or transit networks. These are routing behaviors, not promises of a particular PoP, route, or latency.

Google owns the backbone and its advertisements; external networks own their routing decisions; Brightloaf owns DNS, frontend type, IP scope/tier, backend health, and application correctness. A traceroute is supporting evidence only: filtering, asymmetric routes, and hidden hops limit what it proves.

Network Service Tiers (Premium vs Standard)

Hold the workload assumptions constant. Premium supports global external IPs and global external load-balancing modes; Standard uses eligible regional external IPv4 addresses and regional resources. A project default applies only where no resource-level setting overrides it. Changing pools can require a new IP, so DNS migration and rollback belong in the decision.

3 · Real-world problem and solution for each topic

Example incident: the assumed nearest edge

Supplied facts: Brightloaf serves a distant customer cohort through a regional external frontend. The design record says traffic enters Google at the PoP nearest each customer, but it never records the IP's tier or validates the frontend path. Support must diagnose without changing production or claiming a measured slowdown.

Constraints and evidence: Preserve the single frontend, region, DNS name, and backend while comparing paths. Inventory shows only a regional external IP; the tier field and representative client evidence are missing. The business risk is an indefensible checkout path and a potentially inappropriate tier choice.

Diagnosis: (1) resolve the DNS name and identify the serving external IP; (2) map IP → forwarding rule → frontend → backend region; (3) read the configured tier rather than infer it from geography; (4) compare documented inbound routing behavior; (5) design a representative, time-bounded client test and keep its result separate from the architecture model.

Root cause and solution: The failure is the undocumented assumption that every tier hands traffic to Google near the client. Record the actual tier and scope, then select Premium if the requirement is early entry to Google's network; otherwise retain Standard only with an explicit regional-path and cost rationale.

Verification and residual risk: Require an inventory capture, tier-specific path drawing, and test plan with client geography held constant. Actual BGP selection remains dynamic, and a representative test cannot guarantee every user path.

Example incident: a project default mistaken for a migration

Supplied facts: To reduce delivery cost, a Brightloaf operator changes the project default tier to Standard. The Order API still uses an existing global external IP and global frontend. The team has not supplied billing results, errors, or performance measurements.

Constraints and evidence: The public DNS name must remain stable until a reviewed cutover, and global failover is a stated requirement. Resource inventory shows a global IP; documentation says global external IP addresses use Premium and that a resource setting takes precedence over the project default.

Diagnosis: (1) inspect project default; (2) inspect the serving IP, forwarding rule, load-balancer mode, and their scopes; (3) trace configuration precedence; (4) reject Standard if global mode remains required; (5) if requirements become regional, price and design a separate regional Standard frontend plus DNS migration and rollback.

Root cause and solution: The exact failure point is the assumption that a project-default change retrofits an existing global resource. Correct the ADR: retain Premium for the global path, or build an eligible regional Standard path under a separately approved architecture; never present either as a proven saving until billing evidence exists.

Verification and residual risk: Verify the serving IP and rule after any cutover, resolve DNS from representative locations, and compare billed SKUs only after a defined observation window. A new IP can change allowlists and caches; Standard is not a standby classification to apply during an outage.

Example incident: candidate region passes only a map check

Supplied facts: Brightloaf approves a candidate region because it appears on the global locations map. During design review, no one can produce evidence for the exact load-balancer mode, compute shape, or data-service feature in that region. No deployment has been attempted.

Constraints and evidence: Residency keeps the workload inside the approved geography, the public path must match the tier decision, and the release date cannot rely on an unverified feature. The region map proves the region exists, not that every required feature or capacity is available.

Diagnosis: (1) decompose the architecture into provisionable resources; (2) check each product-specific location/feature page; (3) validate global/regional/zonal scope compatibility; (4) review project quota and seek current capacity confirmation where needed; (5) record source URLs and dates; (6) reject or redesign every unchecked row.

Root cause and solution: The failure point is approval at the coarse region-map boundary. Add an availability gate requiring all rows to pass; if a required feature is absent, choose the already-qualified alternate region or replace the feature while rechecking residency, delivery path, and cost.

Verification and residual risk: A reviewer must reproduce every link in the matrix and confirm scopes align. Documentation can change, quota is not capacity, and a passing tabletop gate is still not a successful provisioning test.

4 · Step-by-step labs for each topic

Exercise 1: Trace ownership to the edge

Goal: Draw Premium and Standard inbound paths without confusing documented routing behavior with an observed route.

Expected Result: A two-lane path whose hops name the owning party, evidence, and uncertainty.

Mode: local tabletop; no account, credentials, or cloud resource required.

Preflight: Bring Day 30's location matrix. Create day-031-edge-path.md and label it synthetic Brightloaf tabletop — not measured. Use this supplied fixture: one customer cohort, one candidate region, one Order API backend, Premium lane, Standard lane.

Numbered Exact Execution:

  1. Write the fixed assumptions at the top: identical client cohort, DNS name, region, and backend.
  2. Draw client → ISP/transit → Google PoP → Google network → frontend → Order API twice.
  3. For each hop, record owner | documented behavior | evidence needed.
  4. On Premium, label the intended early handoff near the user; on Standard, label the intended handoff near the workload region. Add actual route may vary to both.
  5. Mark the boundary where a representative client test would begin and list DNS resolution, configured IP/tier, and request telemetry as evidence.
Verification with expected output

Expected: two paths share the same assumptions; every arrow has an owner; neither lane claims a latency number, fixed PoP, or observed result.

Troubleshooting

If the lanes differ in region or backend, normalize them before comparing. If a route statement lacks a source, label it a hypothesis. Do not turn traceroute gaps into failure claims.

Cleanup

No resources or cost. Keep the accepted note; remove only scratch copies.

Artifact Acceptance: The reviewer can point to the internet/Google boundary, the tier-dependent handoff, one limit of the model, and the future verification boundary.

Exercise 2: Hold assumptions constant

Goal: Produce a defensible tier comparison and expose any incompatible requirement.

Expected Result: A decision table with the same workload assumptions in both columns and a provisional tier decision.

Mode: local tabletop; no deployment and no cost.

Preflight: Create day-031-tier-comparison.md. Copy this fixture: global failover required; Cloud CDN required; one public DNS name; regional Order API backends; cost must use a current price source.

Numbered Exact Execution:

  1. Create rows for path, IP scope, frontend scope, backend scope, Cloud CDN, migration, rollback, pricing evidence, and validation.
  2. Fill Premium and Standard using the linked documentation; write not supported rather than inventing a workaround.
  3. Reject Standard for this supplied fixture because global external mode and Cloud CDN are required.
  4. Change only the fixture to single region; no Cloud CDN; regional frontend acceptable, then reassess Standard.
  5. Record the current pricing URL and checked date, but do not copy a price that will become stale.
Verification with expected output

Expected: Premium is selected for the original fixture; Standard becomes a candidate only for the changed regional fixture. The file states that cost and performance remain unmeasured.

Troubleshooting

If both options appear identical, recheck global IP and Cloud CDN support. If a project default is treated as proof of a resource tier, add the resource-level precedence rule and inventory step.

Cleanup

No resources exist to delete. Retain both fixture decisions so the changed constraint is auditable.

Artifact Acceptance: Every decision cites a specific documentation section, contains a rejected alternative, and distinguishes documented behavior from tests and current price verification.

Exercise 3: Build the regional evidence gate

Goal: Turn two candidate regions from Day 30 into a reviewable component-by-component availability matrix.

Expected Result: A dated matrix that says pass, fail, or unknown for each required resource in each region.

Mode: local documentation review; no provisioning, credentials, or cloud cost.

Preflight: Create day-031-region-gate.md. Bring the two real candidate regions and residency requirements from Day 30. Use these required rows: external frontend mode/IP scope, compute shape, data service feature, quota/capacity, residency, and pricing.

Numbered Exact Execution:

  1. Create columns component | exact feature | scope | region A evidence/date | region B evidence/date | status | owner.
  2. Open the product-specific availability section for every row; a general region map may not close a feature row.
  3. Mark quota and capacity separately: documentation can show availability but does not reserve capacity.
  4. Fail any region with an unsupported mandatory feature. Mark missing evidence unknown, never pass.
  5. Add a revalidation date and the person or team that owns each unknown.
  6. Append the tier comparison from Exercise 2 and write the provisional ADR decision.
Verification with expected output

Expected: no blank status cells, every pass has a URL and checked date, and the selected region has no failed mandatory row. Unknowns are explicit blockers or accepted risks.

Troubleshooting

If a product page lists a service but not the needed feature, keep the row unknown and seek product-specific evidence. If scopes conflict, redraw the resource chain before choosing a region.

Cleanup

No cloud resources were created. Keep the matrix with Day 30 evidence and delete only duplicate drafts.

Artifact Acceptance: Combine the two paths, tier comparison, regional matrix, decision, rejected alternative, current pricing/behavior checks, verification plan, and residual risks into day-031-network-tier-adr.md.
