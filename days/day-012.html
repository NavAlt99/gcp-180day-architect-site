Part 1 · Topics of the day

Regions, zones, multi-region and edge locations

What it is. A region is a geographic area in which Google Cloud offers services; a zone is a deployment area inside a region and a separate infrastructure failure domain. “Multi-region” is a location option for certain services, not a promise that every service automatically runs in multiple regions. Edge locations bring selected network delivery functions closer to users; they are not substitutes for an application’s chosen compute and data location.

Why today. Before choosing a VM size or estimating a bill, an architect must decide where requests are served and where data is allowed to reside. System location. This decision spans the client-facing network edge, the Order API’s regional compute, zonal instances and the region of its stateful data.

Problem preview. Brightloaf puts every Order API replica in one zone and checkout becomes unavailable when that zone fails. Lost checkout minutes and a missed delivery cutoff turn a location choice into revenue and fulfillment impact.

Elasticity versus scalability; vertical versus horizontal scaling

What it is. Scalability is the ability to handle more work by adding capacity; elasticity is the ability to add and release that capacity as demand changes. Vertical scaling gives one instance more resources, while horizontal scaling distributes work across more instances.

Why today. A site sized for an average hour can fail during a short sale; a site permanently sized for its largest burst wastes money. System location. A load balancer distributes Order API requests to a pool of application workers, while an autoscaler changes pool size within a configured minimum and maximum.

Problem preview. During a flash sale, Order API latency rises and requests time out although each individual VM is healthy. Abandoned carts and delayed order confirmation create lost sales and customer-support load.

CapEx, OpEx and pay-as-you-go economics

What it is. Capital expenditure (CapEx) buys or builds assets upfront; operating expenditure (OpEx) is a recurring cost of running a service. Cloud pay-as-you-go charging meters specific resources and usage, so the architecture and its traffic pattern affect the bill.

Why today. Location and scaling choices are incomplete until their compute, storage, network and operational costs are compared under the same demand assumptions. System location. Project usage produces billable line items in Cloud Billing; a pricing estimate models those items before deployment.

Problem preview. A cost sheet counts only VM hours while Brightloaf’s cross-region reads and data transfer grow during peak traffic. The monthly bill exceeds the approved margin for the promotion, forcing an unplanned budget review.

Part 2 · Technical discussion

Regions, zones, multi-region and edge locations

Location has several scopes. A Compute Engine VM and its ordinary persistent disk are zonal; a regional managed instance group can spread VMs across zones in one region; a global external Application Load Balancer can accept traffic at Google’s edge and route it to healthy backends. A regional backend does not become multi-region simply because its frontend is global. Stateful dependencies must be checked separately: a multi-zone application still has a single-region outage risk if its only database is regional.

Brightloaf’s application owner chooses the allowed geography, latency target and recovery objective. The platform team owns the project, network, backend placement and routing configuration. Google operates the underlying zones, but Brightloaf owns the architecture that uses them. Control flows from a customer request through the frontend and health-based routing to an Order API worker; that worker reads and writes the order state in its permitted region. Fulfillment may consume the resulting event later, but a replay must resolve to the same order and cannot produce a second shipment.

A region decision must distinguish data residency from low latency. An edge cache may serve static images near a shopper, yet a dynamic checkout request still reaches the regional Order API and its data. Replicating data to a second region may improve disaster recovery but creates legal, consistency and transfer-cost questions. Capacity and service availability also vary by region and zone; check the intended machine family and quotas before committing to a design.

Elasticity versus scalability; vertical versus horizontal scaling

Capacity is bounded by the slowest part of the request path. Adding Order API workers helps only if requests can be distributed and downstream order storage, connection pools and quotas can sustain the extra concurrency. Vertical scaling can be a quick response to CPU or memory pressure, but a larger VM has a finite ceiling and resizing can require replacement or interruption. Horizontal scaling offers smaller failure units and can cross zones, but requires stateless or externally stored session state, health checks, and an explicit strategy for concurrent writes.

In a managed instance group, an instance template describes each VM and the group maintains a desired number of copies. An autoscaling policy evaluates a metric such as CPU utilization and changes the recommended group size within minimum and maximum limits. Initialization periods, metric lag and scale-in controls matter: a newly started worker is not instantly ready, and rapidly deleting workers can terminate in-flight work. The application team owns per-worker load testing and request behavior; the platform team owns the group, health check, autoscaling limits and quota request. The load balancer routes only to healthy workers; the database remains an independent capacity boundary.

For a deliberately simple capacity model, suppose a worker sustains 80 order requests per second at the latency target. At 120 requests per second, two workers suffice only if distribution is even and the storage tier keeps up. At 420 requests per second, six workers provide 480 requests per second of nominal capacity. That is a planning number, not an autoscaler setting proved by production traffic: leave headroom for uneven distribution, warm-up and failures. A single six-times-larger VM is not equivalent to six workers because it still has one zonal failure unit.

CapEx, OpEx and pay-as-you-go economics

Moving from owned servers to cloud does not eliminate planning; it changes when and how costs are incurred. A data-center purchase fixes much of the hardware capacity in advance. Cloud metering can follow actual running time and consumed service units, but idle VMs, retained disks, network transfer and managed-service minimums can still create recurring costs. Teams should compare total cost for the same service level, recovery target and demand curve, including engineering operations, rather than comparing a server purchase price with one cloud VM line item.

The billing account pays for usage; the project groups resources and their charges; labels can help allocate eligible costs, but they are not a substitute for a complete inventory. A cost estimate is a model built from resource shape, location, operating hours, traffic and storage assumptions. Actual prices, discounts, taxes and usage may differ. The finance owner sets the spending envelope, the architecture owner estimates all path components, and the operations owner observes actual usage and acts on variance. Budget alerts are notifications, not hard spending caps.

Elasticity changes the bill because a worker that is removed after a sale no longer consumes the same VM runtime as a permanently running worker. Yet a two-zone minimum for availability must remain in the base case. Location can alter compute prices and network charges; cross-region synchronous dependencies can also add latency. The model below deliberately uses invented unit rates to teach comparison, so the final purchasing decision must be re-priced in the live Google Cloud Pricing Calculator and checked against the applicable contract.

Part 3 · Real-world problems and solutions

Incident exercise · One zonal failure stops checkout

Illustrative scenario—not an observed production incident. Brightloaf deployed its dynamic Order API checkout service to Google Cloud in India. To minimize network latency for local shoppers in Mumbai and Pune, the team selected region asia-south1 and provisioned three compute workers behind an external Application Load Balancer. However, during configuration, the engineers deployed all three worker virtual machines into zone asia-south1-a because it was the default selection in the provisioning console. At 14:15 IST, an unexpected underlying host and power failure in data center building A caused zone asia-south1-a to become temporarily unreachable. Although Google's global edge network and Cloud CDN points of presence remained healthy and responsive, the Application Load Balancer suddenly had zero healthy backend instances to route to. Shoppers across India encountered immediate HTTP 503 Service Unavailable errors during the critical afternoon rush, causing checkout abandonment and missing the regional logistics carrier cutoff.

Constraints and operational invariants: Order data for Indian operations must strictly reside within the approved India geography; edge caching is permitted for static marketing assets and product images, but transactional checkout writes must strictly terminate within the approved region. The checkout workflow must preserve Brightloaf's fundamental duplicate fulfillment invariant: a customer retry or asynchronous event replay must never trigger duplicate physical warehouse fulfillment (<= 1 fulfillment per unique order ID). Furthermore, failover must occur within approved data sovereignty rules without unapproved cross-border replication.

Evidence and root cause: Cloud Monitoring telemetry and load balancer request logs revealed that the global frontend Anycast IP was reachable and TLS handshakes completed in under 12 ms, but 100% of backend requests failed health checks with connection timeouts. The Compute Engine console confirmed that all three running Order API VM instances were placed solely within asia-south1-a. The root cause was architectural failure to establish a multi-zone failure domain: the team conflated a global entry point (the Application Load Balancer) with regional and zonal backend resilience. A single zone is an independent failure domain; by concentrating all replicas in asia-south1-a, the system possessed a single point of failure.

Diagnostic sequence:

  1. Inspect Application Load Balancer backend service health via the Cloud Console or CLI to identify backend target health states across all configured zones.
  2. Check Compute Engine instance placement to verify the zone distribution of all active Order API virtual machines.
  3. Query Google Cloud Service Health to confirm whether active disruptions are confined to a single zone (such as asia-south1-a) versus the entire region.
  4. Review backend health check probe logs in Cloud Logging to confirm whether health check probes failed due to network unreachability or guest OS crashes.
  5. Inspect database connection state and data replication status between the primary database in asia-south1-a and its regional standby.

Defensible solution: Re-architect the compute layer using a Regional Managed Instance Group (Regional MIG) configured with a target distribution across at least two independent zones (asia-south1-a and asia-south1-b). Configure the load balancer backend service with a regional health check that evaluates application readiness. Ensure Cloud SQL is provisioned in High Availability (HA) mode with automatic synchronous failover between Zone A and Zone B. In the event of a zone disruption, the ALB automatically removes unhealthy Zone A instances within 10 seconds and directs 100% of incoming checkout traffic to healthy instances in Zone B. Enforce request deduplication using an Idempotency-Key header persisted in the database with a unique constraint so that customer client retries during failover return the confirmed order status without generating duplicate warehouse shipments.

Verification and residual risk: Simulate a zonal outage by draining traffic or cordoning instances in asia-south1-a; verify that the Application Load Balancer automatically shifts traffic to asia-south1-b within 10 seconds without dropping confirmed orders; submit simulated duplicate order requests and confirm that the database unique constraint rejects duplicate fulfillment events with HTTP 409 or idempotent HTTP 200. Residual risk: A multi-zone deployment survives any single data center or zone failure, but does not survive an entire regional catastrophic failure (such as a fiber cut across Mumbai). Multi-region disaster recovery to asia-south2 (Delhi) would mitigate regional loss, but requires formal executive review of cross-region latency, data transfer egress costs, and asynchronous replication lag.

Incident exercise · Flash-sale load overwhelms a healthy fleet

Illustrative scenario—not an observed production incident. In preparation for a nationwide holiday flash sale, Brightloaf scheduled an email campaign driving shoppers to a limited-time bread and pastry promotion. At 10:00 IST, traffic surged from an average baseline of 120 requests per second to 420 requests per second. Within 90 seconds, shoppers began experiencing extreme checkout lag: p95 response times climbed from 180 ms to over 1,200 ms, exceeding the 800 ms checkout SLO. Soon after, the frontend load balancer began returning HTTP 504 Gateway Timeout errors to 24% of checkout requests. Strangely, the Compute Engine dashboard showed all virtual machines with green checkmarks, and the VM CPU utilization hovered at 78%. Customer support queues rapidly filled with complaints of unconfirmed transactions, abandoned carts, and shoppers unsure whether their payments had succeeded.

Constraints and operational invariants: The fleet must operate with a two-zone minimum availability floor at all times; capacity expansion must respect project compute quotas and database connection limits (maximum 200 backend connections); and scaling operations must drain in-flight orders safely before terminating instances. Retried order submissions caused by frontend timeouts must strictly preserve the duplicate fulfillment invariant: each order key must produce at most one physical fulfillment.

Evidence and root cause: Analysis of the Managed Instance Group autoscaler configuration revealed that the maximum instance count was hardcoded to maxNumReplicas = 3. At a tested sustained throughput of 80 requests per second per worker, three workers provided a hard ceiling of only 240 requests per second—far below the 420 requests per second demand. Additionally, the instance health check targeted a shallow endpoint (/healthz) that merely verified the HTTP listener was running, returning HTTP 200 even when internal request worker threads were completely blocked waiting on saturated database connections. Furthermore, the autoscaler had an initialization period of 300 seconds, meaning even if scaling were permitted, reactive scale-out was too slow to absorb a sudden flash-sale spike.

Diagnostic sequence:

  1. Compare incoming Application Load Balancer request rate (420 req/s) against configured MIG autoscaler target and maximum replica boundaries.
  2. Examine instance-level latency distributions, worker thread saturation, and backlog queue depths across all active Order API virtual machines.
  3. Inspect database connection pool metrics in Cloud Monitoring to determine if worker threads are stalled waiting for available database connections.
  4. Review the health check configuration to verify whether probes assess deep subsystem readiness or merely shallow socket connectivity.
  5. Audit Compute Engine project regional vCPU and IP address quotas to determine if autoscaler expansion is constrained by project limits.

Defensible solution: Implement a three-part scaling and capacity remediation: First, calculate required worker capacity with a 25% safety headroom for 420 req/s (420 × 1.25 / 80 = 6.56, rounding up to 7 workers) and adjust the autoscaler boundaries to minReplicas = 2 (one per zone) and maxReplicas = 8. Second, establish a scheduled scaling policy that pre-warms the instance group to 7 instances 30 minutes prior to scheduled promotional campaigns, eliminating startup latency lag. Third, replace the shallow health probe with a decoupled health model: use a lightweight liveness probe for VM restarts, and an Application Load Balancer readiness probe that evaluates internal worker queue depth and database connection availability. Configure scale-in controls with a 300-second stabilization window and graceful connection draining (drainingTimeoutSec = 60) so that terminating instances finish processing active checkout requests.

Verification and residual risk: Execute a synthetic load test simulating 420 requests per second; verify that the pre-warmed 7-worker fleet maintains p95 latency below 350 ms across both zones with zero HTTP 504 errors; test scale-in behavior after traffic recedes to verify that instances drain in-flight connections without aborting orders; verify that retried orders hit the idempotency cache and never produce duplicate fulfillments. Residual risk: Sizing horizontal workers to absorb peak demand shifts the bottleneck downstream to the relational database. If sale volume exceeds 600 requests per second, the database write capacity will saturate, necessitating read replicas, connection pooling proxies, or asynchronous order queuing.

Incident exercise · The promotion looks profitable until the bill arrives

Illustrative scenario—not an observed production incident. Following the conclusion of Brightloaf's successful 30-day marketing promotion, the finance team conducted a post-campaign profitability review. The marketing director reported 120,000 completed orders and celebrated that the compute fleet matched the planned capacity model. However, when the monthly Google Cloud billing invoice arrived, the total charge for the Order API infrastructure was $542—nearly three times higher than the approved estimate of $180. Because the infrastructure cost per completed order surged from the budgeted $0.0015 to $0.0045, the promotion operated at an operational loss. The chief financial officer immediately initiated an emergency budget freeze and ordered an audit of cloud expenditures.

Constraints and operational invariants: Brightloaf cannot reduce cloud costs by compromising reliability; it must maintain two-zone minimum compute redundancy, high-availability database replication, and regulatory data retention. Cost optimizations must not weaken the duplicate fulfillment invariant or relocate order data outside India. All cost models must use current, published Google Cloud Pricing Calculator rates and contract terms rather than informal estimates.

Evidence and root cause: Detailed inspection of Cloud Billing Cost Table reports broken down by SKU revealed multiple unmodelled expenditure categories. The original estimate naively multiplied the hourly compute price of a single VM by operating hours. It completely omitted: (1) the second always-on VM required for multi-zone high availability; (2) provisioned zonal SSD persistent boot disks that bill 24/7 regardless of whether an autoscaled VM is active or idle; (3) inter-zone and cross-region network egress generated by an unoptimized analytics pipeline querying the primary database from an overseas office; (4) daily snapshot storage and backup retention; and (5) Cloud Logging ingestion volume generated by verbose debug-level logging left enabled in production.

Diagnostic sequence:

  1. Export detailed Cloud Billing data to BigQuery and query charges grouped by service and SKU descriptions to identify top cost drivers.
  2. Compare the invoiced SKUs line-by-line against the original pre-deployment cost model spreadsheet to detect omitted infrastructure components.
  3. Analyze network egress reports to trace the volume, source, and destination of cross-zone and cross-region data transfers.
  4. Audit Compute Engine persistent disk allocations to verify whether disks attached to scaled-down ephemeral VMs were orphaned or retained.
  5. Review Cloud Logging and Cloud Monitoring ingestion rates to evaluate non-compute operational overheads.

Defensible solution: Transition from naive VM-only math to a comprehensive multi-resource Cloud Bill of Materials (BOM) framework. Model all six primary cost drivers: base compute (2 always-on VMs across 2 zones), burst compute (autoscaled instances during peak hours), persistent disk storage, database HA and backup storage, network egress (optimizing cross-zone traffic and eliminating unnecessary cross-region queries), and observability ingestion. Re-estimate costs using the official Google Cloud Pricing Calculator. Implement automated financial guardrails: configure Cloud Billing budget alerts with email and Pub/Sub notifications at 50%, 80%, and 100% of forecast; establish auto-delete policies for ephemeral VM boot disks upon scale-in; tune logging levels from debug to info/warning in production; and co-locate analytics queries within the primary region.

Verification and residual risk: Reconcile the next monthly billing report against the revised BOM model; verify that actual billed charges deviate by less than 5% from the model; verify that budget alerts trigger notifications accurately during synthetic spend testing; confirm that logging adjustments and disk lifecycle automation do not impact diagnostic observability or the order fulfillment invariant. Residual risk: Budget alerts provide notifications but do not automatically terminate cloud resources or cap spend (to prevent accidental production outages). Therefore, operational governance and regular cost reviews by the platform team remain necessary to prevent unexpected resource sprawl.

Lab 2 · Model baseline and sale-burst capacity

Goal and expected result. Compute a reproducible lower bound for horizontal workers and show why a three-worker maximum cannot serve the stated peak. Mode. Local Python 3; the Google Cloud context check remains read-only.

1. Preflight the CLI context and Python runtime

gcloud auth list --filter='status:ACTIVE' --format='table(account,status)'
gcloud config get-value project
python3 --version

Expected output. An active account, the same study project as Lab 1, and a Python 3 version appear. This step makes the project context visible even though the capacity model itself runs locally.

2. Create and run the complete model

Open the same terminal. The code uses 80 sustained requests per second per worker, 120 baseline requests per second and 420 sale requests per second. It applies 25% capacity headroom before rounding up.

cat > day-012-capacity.py <<'PY'
from math import ceil

CAPACITY_PER_WORKER = 80
BASELINE_REQUESTS_PER_SECOND = 120
SALE_REQUESTS_PER_SECOND = 420
HEADROOM_MULTIPLIER = 1.25
MINIMUM_WORKERS = 2
CURRENT_MAXIMUM_WORKERS = 3

for name, demand in (
    ("baseline", BASELINE_REQUESTS_PER_SECOND),
    ("sale", SALE_REQUESTS_PER_SECOND),
):
    bare_minimum = ceil(demand / CAPACITY_PER_WORKER)
    with_headroom = max(MINIMUM_WORKERS, ceil(demand * HEADROOM_MULTIPLIER / CAPACITY_PER_WORKER))
    print(f"{name}: demand={demand} req/s, bare_minimum={bare_minimum}, with_25_percent_headroom={with_headroom}")

maximum_capacity = CURRENT_MAXIMUM_WORKERS * CAPACITY_PER_WORKER
print(f"current_maximum_capacity={maximum_capacity} req/s")
print(f"sale_exceeds_current_maximum={SALE_REQUESTS_PER_SECOND > maximum_capacity}")
PY
python3 day-012-capacity.py

Expected terminal output.

baseline: demand=120 req/s, bare_minimum=2, with_25_percent_headroom=2
sale: demand=420 req/s, bare_minimum=6, with_25_percent_headroom=7
current_maximum_capacity=240 req/s
sale_exceeds_current_maximum=True

Why. Rounding up avoids a fractional worker. Seven is a planning target with simple headroom, not proof that seven workers pass an end-to-end load test or zone-failure test.

Lab 3 · Compare an elastic and fixed-capacity month

Goal and expected result. Calculate the worker-hour difference for the same 420-requests-per-second sale target, then list the charges the model omits. Mode. Local Python 3 and a browser visit to the current Google Cloud Pricing Calculator. The unit rate in this code is invented for arithmetic teaching and must never be quoted as a Google Cloud price.

1. Preflight identity, project and calculator access

gcloud auth list --filter='status:ACTIVE' --format='table(account,status)'
gcloud config get-value project
python3 --version

Expected output. The same active identity and study project remain visible. No sign-in or resource creation is required for the local arithmetic.

2. Run the complete cost comparison

The model assumes a 30-day month, four peak hours per day, two always-on workers and seven total workers during peak. It includes only worker runtime at an invented rate of 0.10 currency units per worker-hour.

cat > day-012-economics.py <<'PY'
DAYS = 30
HOURS_PER_DAY = 24
PEAK_HOURS_PER_DAY = 4
BASE_WORKERS = 2
PEAK_WORKERS = 7
ASSUMED_RATE_PER_WORKER_HOUR = 0.10

monthly_hours = DAYS * HOURS_PER_DAY
peak_hours = DAYS * PEAK_HOURS_PER_DAY
base_hours = BASE_WORKERS * monthly_hours
extra_peak_hours = (PEAK_WORKERS - BASE_WORKERS) * peak_hours
elastic_worker_hours = base_hours + extra_peak_hours
fixed_worker_hours = PEAK_WORKERS * monthly_hours
elastic_model_cost = elastic_worker_hours * ASSUMED_RATE_PER_WORKER_HOUR
fixed_model_cost = fixed_worker_hours * ASSUMED_RATE_PER_WORKER_HOUR

print(f"base_worker_hours={base_hours}")
print(f"extra_peak_worker_hours={extra_peak_hours}")
print(f"elastic_worker_hours={elastic_worker_hours}")
print(f"fixed_worker_hours={fixed_worker_hours}")
