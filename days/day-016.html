1 · Concepts and problem previews

Relational tables, primary/foreign keys, normalization, SELECT/JOIN/GROUP BY and transactions

What it is. Relational data modeling organizes structured business entities into rectangular tables consisting of rows (records) and columns (typed attributes). Primary keys uniquely identify individual entity instances, while foreign keys establish referential integrity constraints across related tables. Database normalization decomposes redundant schemas through First Normal Form (1NF: atomic attributes), Second Normal Form (2NF: elimination of partial key dependencies), and Third Normal Form (3NF: elimination of transitive dependencies). SQL queries retrieve and transform this data using SELECT, multi-table INNER and LEFT JOIN clauses, and GROUP BY aggregations. Transactions group multiple SQL mutations into an atomic unit executed via BEGIN TRANSACTION, COMMIT, and ROLLBACK commands.

Why today. Before architecting enterprise cloud databases on Google Cloud—such as Cloud SQL for PostgreSQL/MySQL or globally distributed Google Cloud Spanner—a cloud architect must understand relational guarantees, foreign key cascades, and transactional boundaries. Applications designed without rigorous relational schema constraints or atomic transactions suffer silent data corruption, orphaned records, and duplicate billing during operational failures.

System location. The relational database management system (RDBMS) represents the foundational system of record in enterprise architectures, executing behind application containers (Cloud Run, GKE) and storing authoritative customer, order, inventory, and financial ledger data.

Problem preview. A mid-flight order checkout throws an unhandled database exception after inserting an order record but before writing the order items and decrementing stock, leaving an orphaned pending charge without fulfillment data. Without an atomic transaction boundary and explicit rollback handler, inconsistent database state leaves customer orders unpaid yet unfulfilled, generating manual support reconciliation costs and damaged customer trust.

Transaction isolation anomalies and Cloud Digital Leader business framing

What it is. Transaction isolation defines the degree to which concurrent database operations are isolated from one another, governed by ACID principles (Atomicity, Consistency, Isolation, Durability) and ANSI SQL isolation tiers: Read Uncommitted, Read Committed, Repeatable Read, and Serializable. Each tier prevents specific concurrency anomalies: Dirty Reads (observing uncommitted changes), Non-Repeatable Reads (row values changing between reads), and Phantom Reads (new rows appearing in range queries). In Google Cloud Digital Leader framing, these technical database controls directly dictate critical business outcomes: revenue capture integrity, inventory reconciliation, customer trust, and operational risk mitigation. Note that database locking mechanisms and deadlock resolution are practiced in depth on Day 61.

Why today. Modern cloud applications execute thousands of concurrent checkout threads across horizontally autoscaled microservices. Choosing an incorrect database isolation level or omitting concurrency guards causes race conditions, phantom inventory allocations, and overselling during promotional flash sales. Architects must balance isolation guarantees against transactional latency and concurrency throughput.

System location. Transaction isolation is enforced directly by the database storage engine via Write-Ahead Logging (WAL), Multi-Version Concurrency Control (MVCC), and row-level lock managers mediating concurrent connection pools.

Problem preview. Two concurrent flash-sale checkout transactions under default Read Committed isolation both read 1 unit of remaining sourdough stock, verify availability, and decrement inventory to negative values. Non-repeatable read concurrency anomalies oversell physical bakery inventory by 18%, forcing Brightloaf to cancel customer orders and issue emergency compensatory refunds during peak holiday trade.

2 · Architecture, control flow, boundaries, and limits

Relational schema architecture, normalization, and transactional control

Scope, control flow, and ownership. A relational database manages structured application state with rigorous schema enforcement. The application client initiates a database session, issues a BEGIN TRANSACTION boundary, executes SQL data definition or manipulation queries, and issues COMMIT to persist mutations or ROLLBACK on exception. The database engine guarantees referential integrity: a foreign key constraint prevents child records (e.g. order items) from referencing nonexistent parent records (e.g. missing orders or unregistered inventory items).

Normalization progression (1NF to 3NF). Designing a relational schema requires decomposing flat, redundant data structures to eliminate update, insertion, and deletion anomalies:

  • First Normal Form (1NF): All attribute values must be atomic (e.g., no comma-separated lists of purchased items in a single cell), each column must have a unique name, and a primary key must uniquely identify each row.
  • Second Normal Form (2NF): Must satisfy 1NF, and all non-key attributes must depend on the entire primary key. In tables with composite keys (such as order_id + line_no), attributes that depend only on part of the key (such as customer_address) must be extracted into a separate table (e.g. customers).
  • Third Normal Form (3NF): Must satisfy 2NF, and no non-key attribute may depend transitively on another non-key attribute. Attributes like item_name and unit_price depend on item_sku, not the order itself, and must reside in an independent inventory table.

Architectural enforcement of invariants. In addition to normalization, Brightloaf's fundamental business rule—the duplicate fulfillment invariant (≤ 1 physical warehouse fulfillment per unique order ID)—is enforced directly at the schema layer. By creating an order_fulfillments table with an explicit UNIQUE (order_id) constraint, the relational database guarantees that replaying an order event, network retry, or Pub/Sub redelivery will trigger an immediate unique constraint violation rather than generating a second shipment.

ACID properties, ANSI isolation tiers, and Cloud Digital Leader business outcomes

ACID transaction guarantees. Relational database engines provide four foundational guarantees known as ACID:

  • Atomicity: All modifications within a transaction block are committed together to the Write-Ahead Log (WAL), or all are rolled back. If a container instance or power fails mid-execution, incomplete transactions leave zero partial traces.
  • Consistency: The database transitions only between valid states. All explicit constraints (NOT NULL, CHECK, UNIQUE, FOREIGN KEY) and application invariants are verified before commit.
  • Isolation: The concurrent execution of multiple transactions results in a system state equivalent to executing them sequentially or under specified isolation barriers.
  • Durability: Once a transaction commits and the WAL flushes to disk (via fsync), the mutations will survive subsequent system crashes, OS panics, or database restarts.

ANSI SQL isolation levels and anomaly prevention. Databases allow configurable isolation levels to balance concurrency performance against data consistency risks:

  • Read Uncommitted: Allows Dirty Reads, Non-Repeatable Reads, and Phantom Reads. Transactions read uncommitted data written by concurrent sessions. Rarely used in production.
  • Read Committed: Eliminates Dirty Reads. Transactions only read committed data. However, if Transaction 1 reads a row, Transaction 2 updates and commits that row, a subsequent read by Transaction 1 will observe the new value (Non-Repeatable Read). Default in Cloud SQL for PostgreSQL.
  • Repeatable Read: Eliminates Dirty Reads and Non-Repeatable Reads via snapshot isolation. Reads within a transaction observe a consistent snapshot frozen at the start of the transaction. In standard SQL, concurrent insertions by other transactions may still appear in range queries (Phantom Reads).
  • Serializable: Eliminates all anomalies (Dirty Reads, Non-Repeatable Reads, Phantom Reads, and Write Skew). Transactions execute as if in strict serial order. In Google Cloud Spanner, TrueTime and distributed lock managers provide external consistency equivalent to strict serializability globally.

Cloud Digital Leader business framing. Technical database decisions are not merely infrastructure details; they directly impact corporate business outcomes: (1) Revenue Assurance: Atomic transactions prevent lost payments and abandoned carts; (2) Operational Efficiency: Relational constraints prevent corrupted order state that requires costly manual support triage; (3) Customer Brand Loyalty: Concurrency controls eliminate inventory overselling, avoiding humiliating out-of-stock cancellation emails; and (4) Regulatory Compliance: Durable audit logging satisfies SOX and financial accounting standards. Note that row locking, deadlock detection, and distributed lock management are explored in depth on Day 61.

3 · Real-world field problems and incident handling

Incident exercise · Partial write failure corrupts customer order state

Illustrative scenario—not an observed production incident. During an early morning deployment of Brightloaf's order checkout service, the operations center received an alert from the billing reconciliation service: 142 customer credit cards had been successfully authorized and captured by Stripe, but the warehouse management system showed zero corresponding order line items. Customers received automated debit notifications from their banks, yet Brightloaf's web interface displayed a generic "500 Internal Server Error" during checkout, and no confirmation emails were generated. When customer service agents investigated the database, they discovered 142 rows in the orders table with status PENDING, but the order_items table contained zero rows for those orders, and warehouse inventory was never decremented. The company was forced to halt the storefront for four hours, initiate manual billing reconciliations, and deploy emergency customer support staff at significant financial expense.

Constraints: Rely entirely on synthetic Brightloaf test fixtures, preserve all evidence logs, incur zero cloud billing cost, and maintain the order invariant: replaying an order event must not create duplicate warehouse fulfillments.

Root cause analysis: The application engineering team had deployed an updated Python checkout handler that executed database mutations using default database autocommit mode. The handler issued an INSERT INTO orders statement, which immediately committed to disk. It then attempted to execute a batch INSERT INTO order_items; however, a newly introduced NOT NULL column constraint on unit_price threw an uncaught database driver exception. Because the statements were not wrapped within an explicit transactional block (BEGIN TRANSACTION ... COMMIT) backed by a catch-all ROLLBACK handler, the initial order insertion remained permanently committed in the database as an orphaned record, leaving customer billing completely desynchronized from fulfillment.

5-step diagnostic sequence:

  1. Query the relational database using an outer join to identify corrupted orders: SELECT o.order_id, o.status, count(i.line_no) as item_count FROM orders o LEFT JOIN order_items i ON o.order_id = i.order_id GROUP BY o.order_id HAVING item_count = 0; to verify the presence of orphaned headers.
  2. Inspect application container logs around the failure timestamp to locate the unhandled SQL exception and trace the connection driver autocommit settings.
  3. Reproduce the failure in an isolated local test harness by injecting a constraint violation on the second SQL statement under autocommit mode, verifying that the order header remains committed.
  4. Refactor the database driver wrapper to enclose the entire multi-table sequence inside an atomic transaction block: BEGIN TRANSACTION; -> insert order -> insert order items -> reserve inventory -> insert fulfillment -> COMMIT;.
  5. Re-run the failure injection test and verify that the exception triggers an immediate ROLLBACK, leaving zero orphaned records in any table and preventing duplicate fulfillment.

Defensible solution: Enforce atomic multi-statement transactional boundaries and relational integrity constraints across all database operations: First, encapsulate every checkout operation within an explicit transaction context using context managers or explicit BEGIN TRANSACTION and COMMIT calls. In Python, wrap the database connection in a try...except block that explicitly invokes conn.rollback() if any statement raises an exception. Second, enforce referential integrity and duplicate fulfillment prevention at the schema level: declare FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE RESTRICT on order_items, and add a UNIQUE(order_id) constraint on order_fulfillments to guarantee that an order ID can never be fulfilled more than once regardless of network retries. Third, configure application health probes to verify database connection pool integrity prior to accepting live customer traffic.

Verification and residual risk: Execute synthetic test orders simulating both valid purchases and injected constraint failures; verify that valid orders commit all rows atomically across orders, order_items, and order_fulfillments; verify that failed orders commit zero rows and return HTTP 500 without leaving orphaned state; verify that replaying a completed order triggers a unique constraint violation on order_fulfillments, upholding the duplicate fulfillment invariant (≤ 1 fulfillment). Residual risk: Long-running atomic transactions can cause lock contention on shared inventory rows during flash sales; mitigate by keeping transactions strictly bounded to necessary database mutations and deferring slow external tasks (email dispatch, PDF rendering) to asynchronous background workers after transaction commit.

Incident exercise · Read committed race condition oversells bakery inventory

Illustrative scenario—not an observed production incident. At 08:00 AM on Cyber Monday, Brightloaf launched a limited holiday promotion offering 50 loaves of rare Artisanal Cranberry Walnut Sourdough at a 40% discount. Within 45 seconds of launch, the storefront received over 1,200 concurrent checkout requests. When the flash sale concluded, the billing system reported 52 confirmed and paid orders, despite the physical bakery having produced exactly 50 loaves. The warehouse management system reported an impossible inventory balance of -2 loaves. Brightloaf was forced to contact two disappointed customers, cancel their holiday orders, issue full refunds alongside $25 compensation vouchers, and endure public criticism on social media, violating executive customer trust objectives.

Constraints: Rely on synthetic Brightloaf test fixtures, observe zero budget spend, and preserve the duplicate fulfillment invariant.

Root cause analysis: The checkout service ran on Google Cloud SQL for PostgreSQL configured with default READ COMMITTED transaction isolation. The inventory allocation logic followed a naive two-step pattern: (1) SELECT stock_qty FROM inventory WHERE item_sku = 'BL-WALNUT', followed by application logic checking if stock_qty >= 1:, and (2) UPDATE inventory SET stock_qty = stock_qty - 1 WHERE item_sku = 'BL-WALNUT'. When two concurrent worker threads executed step 1 simultaneously while 1 loaf remained, both threads read stock_qty = 1. Both threads evaluated the conditional check as true, and both executed the unconditional update. Because Read Committed isolation only locks rows during statement execution, Worker 1 committed stock = 0, and immediately afterward Worker 2 committed stock = -1. This non-repeatable read concurrency anomaly allowed concurrent checkout workers to oversell finite physical inventory.

5-step diagnostic sequence:

  1. Inspect database transaction isolation configuration using SHOW transaction_isolation; to confirm default Read Committed mode.
  2. Correlate application access logs and database query audit logs around timestamp 08:00:01 to identify concurrent SELECT and UPDATE query interleaving.
  3. Construct a local multi-threaded test harness simulating two concurrent checkout sessions competing for a single remaining stock item using naive two-step updates.
  4. Observe the non-repeatable read race condition reproducing negative inventory balance (-1) in the test database.
  5. Refactor the inventory reservation query into an atomic conditional update (UPDATE inventory SET stock_qty = stock_qty - 1 WHERE item_sku = ? AND stock_qty >= 1) and verify that exactly one worker succeeds while the second receives zero affected rows and cleanly aborts.

Defensible solution: Replace naive multi-step reads with atomic conditional SQL updates or row-level pessimistic locks: First, implement conditional atomic updates directly within the SQL engine: UPDATE inventory SET stock_qty = stock_qty - ? WHERE item_sku = ? AND stock_qty >= ?;. Inspect the driver's affected row count (cursor.rowcount); if rowcount == 0, the inventory condition failed, and the application immediately aborts the transaction and returns HTTP 409 Conflict ("Item out of stock") without charging the customer. Second, add an explicit table-level check constraint: ALTER TABLE inventory ADD CONSTRAINT check_stock_non_negative CHECK (stock_qty >= 0);, ensuring the database kernel rejects any statement that would produce negative inventory. Third, link this architectural control to Cloud Digital Leader principles: eliminating inventory overselling directly protects brand reputation, eliminates manual refund processing overhead, and guarantees inventory reconciliation integrity. Note that advanced row-locking (SELECT ... FOR UPDATE) and distributed deadlock troubleshooting are practiced on Day 61.

Verification and residual risk: Execute a concurrent stress test with 20 parallel threads attempting to purchase a single remaining inventory item; verify that exactly 1 thread receives rowcount = 1 and completes checkout, while 19 threads receive rowcount = 0 and return HTTP 409; verify that final inventory stock terminates at exactly 0 and never becomes negative; verify that completed orders uphold the duplicate fulfillment invariant (≤ 1 shipment). Residual risk: Under extreme flash-sale concurrency, hundreds of competing threads targeting the same inventory row can cause database connection pool exhaustion; mitigate by deploying an in-memory Redis reservation layer or queuing orders via Google Cloud Pub/Sub for serialized batch inventory processing.

import sqlite3
import sys

DB_FILE = "brightloaf_test.db"

def init_database(conn):
    cursor = conn.cursor()
    cursor.execute("PRAGMA foreign_keys = ON;")

    cursor.execute("""
    CREATE TABLE IF NOT EXISTS customers (
        customer_id TEXT PRIMARY KEY,
        name TEXT NOT NULL,
        email TEXT UNIQUE NOT NULL,
        shipping_address TEXT NOT NULL
    );
    """)

    cursor.execute("""
    CREATE TABLE IF NOT EXISTS inventory (
        item_sku TEXT PRIMARY KEY,
        item_name TEXT NOT NULL,
        unit_price REAL NOT NULL CHECK(unit_price > 0),
        stock_qty INTEGER NOT NULL CHECK(stock_qty >= 0)
    );
    """)

    cursor.execute("""
    CREATE TABLE IF NOT EXISTS orders (
        order_id TEXT PRIMARY KEY,
        customer_id TEXT NOT NULL,
        status TEXT NOT NULL CHECK(status IN ('PENDING', 'CONFIRMED', 'CANCELLED')),
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE RESTRICT
    );
    """)

    cursor.execute("""
    CREATE TABLE IF NOT EXISTS order_items (
        order_id TEXT NOT NULL,
        line_no INTEGER NOT NULL,
        item_sku TEXT NOT NULL,
        quantity INTEGER NOT NULL CHECK(quantity > 0),
        frozen_unit_price REAL NOT NULL CHECK(frozen_unit_price > 0),
        PRIMARY KEY (order_id, line_no),
        FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE CASCADE,
        FOREIGN KEY (item_sku) REFERENCES inventory(item_sku) ON DELETE RESTRICT
    );
    """)

    cursor.execute("""
    CREATE TABLE IF NOT EXISTS order_fulfillments (
        fulfillment_id TEXT PRIMARY KEY,
        order_id TEXT UNIQUE NOT NULL,
        carrier TEXT NOT NULL,
        shipped_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE RESTRICT
    );
    """)
    conn.commit()
    print("✓ Schema initialized with 5 normalized tables and relational constraints.")

def seed_data(conn):
    cursor = conn.cursor()
    cursor.execute("INSERT OR IGNORE INTO customers VALUES ('cust-001', 'Alice Walker', 'alice@example.com', '123 Sourdough Lane');")
    cursor.execute("INSERT OR IGNORE INTO customers VALUES ('cust-002', 'Bob Smith', 'bob@example.com', '456 Rye Street');")
    cursor.execute("INSERT OR IGNORE INTO inventory VALUES ('SKU-SOURDOUGH', 'San Francisco Sourdough', 6.50, 20);")
    cursor.execute("INSERT OR IGNORE INTO inventory VALUES ('SKU-WALNUT', 'Cranberry Walnut Loaf', 8.00, 10);")
    conn.commit()
    print("✓ Seeded baseline customers and inventory.")

def test_atomic_checkout(conn, order_id, customer_id, items, should_fail=False):
    cursor = conn.cursor()
    try:
        cursor.execute("BEGIN TRANSACTION;")

        cursor.execute("INSERT INTO orders (order_id, customer_id, status) VALUES (?, ?, 'CONFIRMED');",
                       (order_id, customer_id))

        for line_no, (sku, qty) in enumerate(items, start=1):
            if should_fail and line_no == 2:
                print(f"  [!] Injecting deliberate mid-flight failure at line {line_no}...")
                cursor.execute("INSERT INTO order_items (order_id, line_no, item_sku, quantity, frozen_unit_price) VALUES (?, ?, ?, ?, -5.00);",
                               (order_id, line_no, sku, qty))

            cursor.execute("SELECT unit_price, stock_qty FROM inventory WHERE item_sku = ?;", (sku,))
            row = cursor.fetchone()
            if not row or row[1] < qty:
                raise ValueError(f"Insufficient stock for SKU: {sku}")
            price, _ = row

            cursor.execute("INSERT INTO order_items (order_id, line_no, item_sku, quantity, frozen_unit_price) VALUES (?, ?, ?, ?, ?);",
                           (order_id, line_no, sku, qty, price))
            cursor.execute("UPDATE inventory SET stock_qty = stock_qty - ? WHERE item_sku = ?;", (qty, sku))

        fulfillment_id = f"ful-{order_id}"
        cursor.execute("INSERT INTO order_fulfillments (fulfillment_id, order_id, carrier) VALUES (?, ?, 'GroundExpress');",
                       (fulfillment_id, order_id))

        conn.commit()
        print(f"✓ Order {order_id} committed atomically across all 5 tables.")
        return True
    except Exception as exc:
        conn.rollback()
        print(f"✓ Exception caught ({type(exc).__name__}): Transaction ROLLED BACK cleanly.")
        return False

def run_analytical_queries(conn):
    cursor = conn.cursor()
    print("\n--- Analytical Query: Multi-Table JOIN with GROUP BY Aggregation ---")
    query = """
    SELECT 
        c.name AS customer_name,
        o.order_id,
        count(oi.line_no) AS item_count,
        sum(oi.quantity * oi.frozen_unit_price) AS order_total,
        f.fulfillment_id
    FROM customers c
    INNER JOIN orders o ON c.customer_id = o.customer_id
    INNER JOIN order_items oi ON o.order_id = oi.order_id
    LEFT JOIN order_fulfillments f ON o.order_id = f.order_id
    GROUP BY o.order_id;
    """
    cursor.execute(query)
    for row in cursor.fetchall():
        print(f"Customer: {row[0]} | Order: {row[1]} | Items: {row[2]} | Total: ${row[3]:.2f} | Fulfillment: {row[4]}")

def test_duplicate_fulfillment_invariant(conn, order_id):
    cursor = conn.cursor()
    print(f"\n--- Testing Duplicate Fulfillment Invariant for {order_id} ---")
    try:
        cursor.execute("INSERT INTO order_fulfillments (fulfillment_id, order_id, carrier) VALUES ('ful-dup-999', ?, 'DroneShip');", (order_id,))
        conn.commit()
        print("✗ ERROR: Duplicate fulfillment was allowed!")
        sys.exit(1)
    except sqlite3.IntegrityError as err:
        conn.rollback()
        print(f"✓ Invariant preserved: Database UNIQUE constraint rejected duplicate fulfillment: {err}")

if __name__ == "__main__":
    conn = sqlite3.connect(DB_FILE)
    init_database(conn)
    seed_data(conn)

    print("\n=== Test 1: Successful Atomic Order Checkout ===")
    success1 = test_atomic_checkout(conn, "BL-16-001", "cust-001", [("SKU-SOURDOUGH", 2), ("SKU-WALNUT", 1)])
    assert success1 is True

    print("\n=== Test 2: Injected Mid-Flight Failure (Verifying Rollback) ===")
    success2 = test_atomic_checkout(conn, "BL-16-002", "cust-002", [("SKU-SOURDOUGH", 1), ("SKU-WALNUT", 1)], should_fail=True)
    assert success2 is False

    cursor = conn.cursor()
    cursor.execute("SELECT count(*) FROM orders WHERE order_id = 'BL-16-002';")
    assert cursor.fetchone()[0] == 0, "Orphaned order record detected!"
    cursor.execute("SELECT count(*) FROM order_items WHERE order_id = 'BL-16-002';")
    assert cursor.fetchone()[0] == 0, "Orphaned order items detected!"
    print("✓ Clean rollback verified: Zero orphaned records exist for BL-16-002.")

    run_analytical_queries(conn)
    test_duplicate_fulfillment_invariant(conn, "BL-16-001")

    conn.close()
    print("\nAll relational database assertions passed successfully.")

cat > "$LAB16_2_DIR/concurrency_lab.py" <<'PY'
import sqlite3
import sys

DB_FILE = "concurrency_test.db"

def setup_db():
    conn = sqlite3.connect(DB_FILE)
    c = conn.cursor()
    c.execute("DROP TABLE IF EXISTS inventory;")
    c.execute("""
    CREATE TABLE inventory (
        sku TEXT PRIMARY KEY,
        stock_qty INTEGER NOT NULL
    );
    """)
    # Exactly 1 loaf left in stock
    c.execute("INSERT INTO inventory VALUES ('SKU-CRANBERRY', 1);")
    conn.commit()
    conn.close()

def simulate_naive_race_condition():
    setup_db()
    conn1 = sqlite3.connect(DB_FILE)
    conn2 = sqlite3.connect(DB_FILE)

    c1 = conn1.cursor()
    c2 = conn2.cursor()

    # Step 1: Worker 1 and Worker 2 both read stock
    c1.execute("SELECT stock_qty FROM inventory WHERE sku = 'SKU-CRANBERRY';")
    stock_w1 = c1.fetchone()[0]

    c2.execute("SELECT stock_qty FROM inventory WHERE sku = 'SKU-CRANBERRY';")
    stock_w2 = c2.fetchone()[0]

    print(f"  [Naive] Worker 1 observed stock: {stock_w1}")
    print(f"  [Naive] Worker 2 observed stock: {stock_w2}")

    # Step 2: Both workers believe stock is available and write unconditional update
    c1.execute("UPDATE inventory SET stock_qty = ? - 1 WHERE sku = 'SKU-CRANBERRY';", (stock_w1,))
    conn1.commit()

    c2.execute("UPDATE inventory SET stock_qty = ? - 1 WHERE sku = 'SKU-CRANBERRY';", (stock_w2,))
    conn2.commit()

    conn_check = sqlite3.connect(DB_FILE)
    final_stock = conn_check.cursor().execute("SELECT stock_qty FROM inventory;").fetchone()[0]
    conn1.close()
    conn2.close()
    conn_check.close()
    print(f"  [Naive Result] Final inventory stock in database: {final_stock}")
    return final_stock

def simulate_atomic_conditional_update():
    setup_db()
    conn1 = sqlite3.connect(DB_FILE)
    conn2 = sqlite3.connect(DB_FILE)

    c1 = conn1.cursor()
    c2 = conn2.cursor()

    # Worker 1 issues atomic conditional update
    c1.execute("UPDATE inventory SET stock_qty = stock_qty - 1 WHERE sku = 'SKU-CRANBERRY' AND stock_qty >= 1;")
    conn1.commit()
    rows1 = c1.rowcount

    # Worker 2 issues identical atomic conditional update
    c2.execute("UPDATE inventory SET stock_qty = stock_qty - 1 WHERE sku = 'SKU-CRANBERRY' AND stock_qty >= 1;")
    conn2.commit()
    rows2 = c2.rowcount

    conn_check = sqlite3.connect(DB_FILE)
    final_stock = conn_check.cursor().execute("SELECT stock_qty FROM inventory;").fetchone()[0]
    conn1.close()
    conn2.close()
    conn_check.close()

    print(f"  [Corrected] Worker 1 affected rows: {rows1} (Status: {'SUCCESS' if rows1 == 1 else 'FAIL'})")
    print(f"  [Corrected] Worker 2 affected rows: {rows2} (Status: {'SUCCESS' if rows2 == 1 else 'REJECTED - OUT OF STOCK'})")
    print(f"  [Corrected Result] Final inventory stock in database: {final_stock}")
    return rows1, rows2, final_stock

if __name__ == "__main__":
    print("=== 1. Simulating Naive Read Committed Concurrency Race Condition ===")
    naive_result = simulate_naive_race_condition()

    print("\n=== 2. Simulating Corrected Atomic Conditional Update Guard ===")
    r1, r2, final_stock = simulate_atomic_conditional_update()
    assert r1 == 1, "Worker 1 should have succeeded"
    assert r2 == 0, "Worker 2 should have been rejected"
    assert final_stock == 0, "Stock should remain at exactly 0, never negative"
    print("\n✓ Concurrency invariant protected: Negative inventory eliminated.")
PY
