OSI and TCP/IP layer models

The OSI 7-layer reference model and the 4-layer TCP/IP Internet model define modular protocol boundaries, dividing network transmission into physical link framing, network-wide IP packet routing, transport-level host-to-host streams (Layer 4), and application-specific payload semantics (Layer 7). Transport Layer 4 protocols such as TCP and UDP govern port multiplexing, sequence ordering, windowing, and reliability, whereas Application Layer 7 protocols such as HTTP/1.1, HTTP/2, gRPC, and TLS define serialization, request-response semantics, headers, and authorization tokens.

Why today and where it sits: Day 2 establishes fundamental diagnostic boundaries before exploring DNS, TLS handshakes, VPC networks, and Google Cloud Load Balancing. In enterprise cloud systems, this model governs the operational distinction between Layer 4 passthrough load balancers (such as Maglev and Google Cloud Network Load Balancing) and Layer 7 reverse proxies (such as Envoy and Google Cloud Application Load Balancing). Understanding this division prevents conflating network reachability with application readiness.

A cloud load balancer reports green TCP port 443 health checks while backend application runtimes throw unhandled database exceptions and return HTTP 500 error payloads. Rushing to declare an infrastructure routing outage misdirects engineering response while customers experience immediate checkout abandonment and transaction loss.

OSI and TCP/IP layer models

Layer models separate networking responsibilities into bounded modular domains so that failures at one level can be diagnosed and isolated without mistaking them for faults in adjacent systems. The Open Systems Interconnection (OSI) 7-layer reference model defines conceptual boundaries from Physical (Layer 1) to Application (Layer 7). In contrast, the operational TCP/IP model organizes production network stacks into four pragmatic layers: Link (network access and local framing), Internet (IP packet addressing and inter-network routing), Transport (end-to-end host stream and datagram multiplexing), and Application (process communication protocols such as HTTP, TLS, DNS, and gRPC).

Architects must rigorously differentiate between Layer 4 (Transport) and Layer 7 (Application). Layer 4 operates on the 4-tuple consisting of source IP, source port, destination IP, and destination port. Layer 4 protocols such as TCP manage the three-way handshake (SYN, SYN-ACK, ACK), sequence number ordering, sliding-window flow control, congestion avoidance, and connection termination (FIN or RST). Layer 4 has zero awareness of application payload syntax. In contrast, Layer 7 protocols interpret message semantics: HTTP request verbs, Uniform Resource Identifiers (URIs), request and response headers, MIME types, status codes (such as 200 OK or 503 Service Unavailable), and serialized message bodies (JSON or Protocol Buffers).

This distinction governs load balancing in Google Cloud. An External Passthrough Network Load Balancer operates at Layer 4: it inspects packet 5-tuples and directs raw packets to backend virtual machine instances via Maglev consistent hashing without terminating TCP connections, preserving client source IP addresses and delivering line-rate throughput with microsecond latency. Conversely, an External Application Load Balancer operates at Layer 7: it terminates client TCP connections and TLS sessions via Envoy proxies, decrypts payloads, evaluates HTTP path-based and host-based routing rules, injects custom headers, and establishes separate backend TCP/TLS connections to upstream application pools.

Ownership boundaries reflect this separation. Operating system kernels own the TCP/IP stack, managing socket state machines and buffer memory in kernel space. Application runtimes own user-space process memory and request handling. A successful TCP three-way handshake proves physical link connectivity, IP routing, firewall clearance, and the existence of a listening socket; it proves absolutely nothing about whether the application process is healthy, whether database connections are available, or whether the requested business operation can be fulfilled.

IPv4 addressing, private ranges, ARP/NDP and CIDR subnetting

IPv4 addresses are 32-bit binary integers conventionally represented as four dotted-decimal octets ranging from 0.0.0.0 to 255.255.255.255. Classless Inter-Domain Routing (CIDR) replaced legacy classful addressing by defining networks via an arbitrary bit prefix length (/n). The prefix length indicates how many leading bits identify the network routing domain, leaving the remaining (32 - n) bits to identify individual host interfaces.

Subnetting is the mathematical process of borrowing bits from the host portion of an address block to create multiple smaller, logically isolated subnets. When splitting a standard /24 network (which provides 2^(32 - 24) = 256 total IP addresses with subnet mask 255.255.255.0) into four equal subnets, exactly two additional bits are borrowed (2^2 = 4), yielding four /26 subnets (32 - 6 = 26 network bits, mask 255.255.255.192). Each /26 subnet contains 2^(32 - 26) = 64 total IP addresses. The four subnets allocate as follows:

  • Subnet 0 (192.0.2.0/26): Network: 192.0.2.0 | Usable: 192.0.2.1–192.0.2.62 | Broadcast: 192.0.2.63
  • Subnet 1 (192.0.2.64/26): Network: 192.0.2.64 | Usable: 192.0.2.65–192.0.2.126 | Broadcast: 192.0.2.127
  • Subnet 2 (192.0.2.128/26): Network: 192.0.2.128 | Usable: 192.0.2.129–192.0.2.190 | Broadcast: 192.0.2.191
  • Subnet 3 (192.0.2.192/26): Network: 192.0.2.192 | Usable: 192.0.2.193–192.0.2.254 | Broadcast: 192.0.2.255

Architects must account for cloud-specific reservation rules. While standard RFC 1918 networking consumes exactly two addresses per subnet (the first for the network ID and the last for the broadcast address), Google Cloud Virtual Private Cloud (VPC) subnets reserve exactly five IP addresses per subnet: the network address (.0), the default gateway (.1), the Cloud DNS resolver address (.2), an address reserved for Google future use (.3), and the broadcast address (.255 or the final address in the block). In a /26 VPC subnet, 59 IP addresses remain available for Compute Engine instances, GKE nodes, and internal forwarding rules.

RFC 1918 reserves three private address blocks for enterprise intranets: 10.0.0.0/8 (16,777,216 addresses), 172.16.0.0/12 (1,048,576 addresses), and 192.168.0.0/16 (65,536 addresses). In addition, RFC 6598 designates 100.64.0.0/10 as Shared Address Space for Carrier-Grade NAT, which Google Cloud utilizes extensively for Private Service Connect (PSC) and Cloud NAT translations. Private ranges cannot be routed across the public Internet and require Network Address Translation (NAT) or private interconnects.

When an operating system prepares to transmit an IP packet, it consults its Forwarding Information Base (FIB) using the Longest Prefix Match (LPM) rule. If the destination IP falls within the host's locally configured subnet mask, the destination is considered on-link. The host sends an Address Resolution Protocol (ARP, RFC 826) broadcast request querying "who has destination IP, tell source MAC". The target host replies with a unicast ARP reply containing its hardware Layer 2 Ethernet MAC address. In IPv6, Neighbor Discovery Protocol (NDP, RFC 4861) performs this role using ICMPv6 multicast neighbor solicitations. Crucially, if the destination IP is outside the local subnet mask, the host does not ARP for the destination IP; instead, it ARPs exclusively for its configured next-hop default gateway MAC address.

Packet path from NIC to application socket

The packet ingress journey through a Linux host or Compute Engine guest virtual machine represents a tightly orchestrated handoff across physical hardware, device drivers, kernel memory structures, and user-space runtimes. Tracing this path establishes where packets are queued, filtered, translated, and potentially discarded under load.

The nine-stage packet ingress traversal proceeds as follows:

  1. Physical or Virtual NIC Reception: An Ethernet frame arrives at the physical network interface or virtualized virtIO device. The physical layer verifies the frame check sequence (FCS) cyclic redundancy check (CRC). If corrupted, the NIC hardware drops the frame immediately.
  2. Direct Memory Access (DMA) Transfer: The NIC uses DMA bus mastering to copy the raw Ethernet frame directly into host physical RAM mapped to a circular receive descriptor ring buffer (rx_ring) without CPU intervention.
  3. Hardware Interrupt (MSI-X IRQ): Upon depositing the frame in host memory, the NIC asserts a PCIe Message Signaled Interrupt (MSI-X) targeting a specific CPU core.
  4. NAPI SoftIRQ Scheduling: The kernel interrupt service routine (ISR) executes, immediately disables device hardware interrupts for that queue to avoid interrupt storms, and schedules a software interrupt (NET_RX_SOFTIRQ) handled by the kernel thread ksoftirqd. The driver's New API (NAPI) poll routine executes in softIRQ context, draining frames from the DMA ring and allocating a kernel socket buffer (sk_buff) structure for each packet.
  5. Netfilter PREROUTING & Connection Tracking: The kernel passes the sk_buff to the netfilter subsystem at the NF_INET_PRE_ROUTING hook. Kernel connection tracking (conntrack) creates or updates state table entries, and iptables/nftables PREROUTING rules (such as DNAT) are evaluated.
  6. Kernel Routing Decision (FIB Lookup): The kernel routing subsystem executes ip_route_input_noref(). If the destination IP address matches a local interface address, the packet is directed to the local input path (ip_local_deliver). If the packet is destined for another network and IP forwarding is enabled, it is routed to the forward path.
  7. Transport Protocol Demultiplexing: The kernel inspects the IP header protocol field (e.g., protocol 6 for TCP or 17 for UDP) and passes the sk_buff to the transport layer handler (tcp_v4_rcv). The TCP engine parses sequence numbers, verifies checksums, processes acknowledgments, updates the TCP sliding window, and evaluates the TCP connection state machine.
  8. Socket Receive Queue Insertion: The kernel performs a hash table lookup (inet_lookup_skb) using the 4-tuple to locate the matching struct sock. If the socket exists, the sk_buff payload is appended to the socket's receive buffer (sk_receive_queue) up to the limit established by the SO_RCVBUF socket option and sysctl net.ipv4.tcp_rmem.
  9. User-Space Process Syscall & Data Copy: The kernel marks the socket descriptor as readable, waking worker threads blocked in system calls such as epoll_wait(), select(), or blocking read()/recv(). The application executes the read() syscall; the kernel copies the payload bytes from kernel sk_buff memory into the user-space process application buffer and frees the sk_buff memory back to the slab allocator.

Each boundary introduces specific failure signals and trade-offs. If the rate of incoming frames exceeds the capacity of the NIC DMA ring or if SoftIRQ processing is starved by CPU saturation, the driver increments rx_dropped or rx_fifo_errors (observable via ethtool -S or ip -s link). If the application event loop is slow to process connections, the kernel listen backlog overflows, resulting in TCP ListenOverflows and ListenDrops (observable via netstat -s). Tuning sysctl parameters such as net.core.somaxconn and net.core.netdev_max_backlog expands queue limits but consumes unevictable kernel memory.

3 · Real-world problem and solution for each topic

OSI and TCP/IP layer models · field case: L4 TCP handshake success masking L7 application HTTP 503 database pool failure

Symptoms and evidence: During an automated synthetic load test of Brightloaf's checkout service generating 1,200 checkout requests per second, Cloud Monitoring network dashboards showed 100% successful TCP three-way handshakes to port 443 with an average round-trip latency of 1.8 milliseconds. Zero TCP resets (RST) were logged at the Google Cloud External Application Load Balancer. However, client applications recorded an 84% failure rate, receiving HTTP/1.1 503 Service Unavailable responses within 12 milliseconds containing the body {"error": "DATABASE_POOL_TIMEOUT", "service": "order-api"}. The edge proxy health check was configured as a basic TCP SYN check, and reported 100% backend health.

Business and operational constraints: Customer checkout transactions must never result in duplicate orders or multiple credit card charges when retrying failed requests. The platform must maintain high transaction throughput during morning peak order windows while isolating infrastructure transport health from application runtime state.

Causal root-cause reasoning:

Supplied facts: Synthetic load of 1,200 requests/sec; 100% TCP port 443 connection success; 84% HTTP 503 responses returned to clients; edge health check configured as an L4 TCP port check reporting green status; backend application connection pool exhausted at 100/100 active sessions.

Architectural inference: The network transport layer (Layer 4) was functioning flawlessly: packets reached the virtual machines, and the Linux kernel accepted incoming connections into its TCP listening queue. However, the application layer (Layer 7) was critically degraded: worker threads could not obtain a database connection within the 10-millisecond pool acquisition timeout, immediately generating HTTP 503 payloads. Because the load balancer was configured with an L4 TCP check rather than an L7 HTTP check, it continued sending incoming customer requests to saturated backends. Frustrated users clicked checkout multiple times, compounding request load and creating duplicate order risks.

Defensible fix: Reconfigure the load balancer health check from an L4 TCP port test to an L7 HTTP check targeting a dedicated /healthz endpoint that actively queries database connection pool headroom. Configure the reverse proxy with connection limits and circuit breaking to shed excess traffic gracefully before the database pool saturates. To defend the business invariant of exactly one fulfillment per order, implement an idempotent request deduplication middleware in the Order API: every client request must supply a unique idempotency key (such as an order UUID), which the service records in a fast distributed store before initiating transaction processing. Repeated requests with the same key return the original cached response without re-triggering order fulfillment.

Verification plan: Execute decoupled test probes verifying that TCP connect succeeds while HTTP GET /healthz fails when the database pool is exhausted. Simulate duplicate checkout POST requests with the identical idempotency key; verify that the second request returns HTTP 200 with the original order confirmation and that exactly one order fulfillment message is published to the downstream processing queue.

Residual risk: Deep L7 health checks execute database queries and add background load; health check frequency and timeout thresholds must be tuned (e.g. 5-second interval, 2-second timeout) to prevent monitoring traffic from starving production queries during high-load periods.

IPv4 addressing, private ranges, ARP/NDP and CIDR subnetting · field case: Overlapping CIDR /24 and /25 subnets causing asymmetric routing drops

Symptoms and evidence: Brightloaf integrated a newly automated bakery distribution center into its hybrid cloud network. The warehouse robotics system was assigned 192.168.10.0/24, while an existing Enterprise Resource Planning (ERP) inventory synchronization server was placed on 192.168.10.128/25. Outbound inventory updates sent from the ERP host (192.168.10.130) over Cloud Interconnect to the Google Cloud regional database (10.240.0.50) timed out after 60 seconds. Packet captures at the cloud gateway revealed that outbound TCP SYN packets from 192.168.10.130 arrived successfully and the database replied with TCP SYN-ACK packets, but the SYN-ACK packets never reached the ERP host.

Business and operational constraints: Real-time inventory reconciliation must continuously synchronize bread production counts with central order distribution. Re-routing or addressing changes must not disrupt live warehouse robotic conveyor controllers operating on the factory floor.

Causal root-cause reasoning:

Supplied facts: Warehouse robotics assigned 192.168.10.0/24 with Gateway A (192.168.10.1); ERP host assigned 192.168.10.128/25 with Gateway B (192.168.10.129); Cloud Router configured with a single static aggregate return route for 192.168.10.0/24 pointing exclusively to Gateway A.

Architectural inference: The network architecture contained an overlapping CIDR subnet defect. The /25 block (192.168.10.128 to 192.168.10.255) is an exact subset of the /24 block (192.168.10.0 to 192.168.10.255). Outbound packets from the ERP host traveled through Gateway B to Google Cloud. However, the Cloud Router matched the aggregate route 192.168.10.0/24 and forwarded return SYN-ACK packets to Gateway A. Gateway A had no ARP entry or routing table interface for 192.168.10.130, and an intermediate stateful firewall dropped the out-of-sequence SYN-ACK packet because it had never observed the forward SYN on that interface. This asymmetric routing blackhole completely stalled inventory synchronization.

Defensible fix: Disaggregate the monolithic 192.168.10.0/24 address block into two strictly non-overlapping /25 CIDR subnets: assign Subnet 0 (192.168.10.0/25, usable range .1–.126) to Warehouse Robotics via Gateway A, and retain Subnet 1 (192.168.10.128/25, usable range .129–.254) for ERP Systems via Gateway B. Update on-premises core routing tables and Google Cloud Cloud Router BGP advertisements to broadcast both explicit /25 prefixes with their distinct next-hop gateway IPs, ensuring fully symmetric forward and return routing.

Verification plan: Inspect host routing tables using route lookup simulation to verify that destinations in 192.168.10.128/25 resolve explicitly to Gateway B. Execute bidirectional ping and TCP connection handshakes between 192.168.10.130 and 10.240.0.50, verifying that stateful firewalls record matching forward and return session states. Replay order stock decrements to ensure the Brightloaf single-fulfillment invariant holds.

Residual risk: Subnetting down to /25 restricts each broadcast domain to a maximum of 126 usable host addresses. If future warehouse robotics expansion requires more than 126 nodes, the network must be re-architected into a larger RFC 1918 10.0.0.0/8 block with centralized IPAM governance.

Packet path from NIC to application socket · field case: Virtual NIC receive ring buffer overflow and default somaxconn backlog drops

Symptoms and evidence: During a scheduled flash sale event generating 6,000 requests per second to Brightloaf's Order Ingestion API running on a Compute Engine c2-standard-16 Linux VM, clients experienced severe 15-second request timeouts and dropped connections. Cloud Monitoring reported that overall VM CPU utilization was only 22% and memory usage was steady at 35%. However, guest OS network telemetry revealed that interface receive drop counters (rx_dropped) were climbing at 1,400 drops per second, and netstat -s showed 32,000 TCP listen queue drops (ListenDrops) and overflows (ListenOverflows). Single-core CPU metrics showed vCPU 0 pinned at 100% utilization in SoftIRQ mode (si), while the remaining 15 vCPUs remained virtually idle.

Business and operational constraints: Flash sales require processing 10,000 orders per minute without dropped connection requests. Client retry storms caused by timeouts must not result in duplicate order fulfillment or corrupted inventory state.

Causal root-cause reasoning:

Supplied facts: Ingress traffic rate of 6,000 req/sec; overall VM CPU 22%; vCPU 0 pinned at 100% in SoftIRQ context; interface rx_dropped incrementing; 32,000 ListenDrops in netstat; default kernel sysctl net.core.somaxconn=128; single virtIO network queue bound to vCPU 0.

Architectural inference: The bottleneck occurred entirely within the Linux kernel receive pipeline prior to socket delivery. Because the virtual NIC was configured with a single receive queue, all incoming packet hardware interrupts and subsequent NAPI SoftIRQs were directed to vCPU 0. Once vCPU 0 saturated at 100% CPU time in ksoftirqd/0, the NIC DMA receive ring buffer filled completely, causing the driver to discard incoming Ethernet frames before sk_buff allocation (rx_dropped). Furthermore, the default listen backlog limit (somaxconn=128) was vastly inadequate for 6,000 req/sec bursts: when application worker threads were momentarily delayed, the kernel listen backlog filled instantly, dropping TCP connection handshakes before the application could execute accept(). Packets never reached the user-space socket buffer.

Defensible fix: Enable multi-queue virtIO with Receive Side Scaling (RSS) on the Compute Engine VM interface to distribute hardware interrupts and SoftIRQ processing evenly across all 16 vCPUs. Tune kernel socket backlog parameters in /etc/sysctl.d/99-network.conf: expand the socket listen backlog (net.core.somaxconn = 8192), enlarge the driver input queue (net.core.netdev_max_backlog = 16384), increase the TCP half-open SYN backlog (net.ipv4.tcp_max_syn_backlog = 8192), and widen the TCP receive buffer limits (net.ipv4.tcp_rmem = 4096 87380 16777216). Reconfigure the application runtime socket listener with a matching backlog parameter (listen backlog 8192).

Verification plan: Run a local socket load harness dispatching 10,000 concurrent connection requests; inspect netstat -s and assert that ListenDrops remains exactly zero. Monitor CPU utilization across all cores using mpstat to confirm SoftIRQ load is evenly distributed. Test duplicated order payloads to confirm that application-level deduplication keys preserve single-fulfillment integrity.

Residual risk: Increasing socket buffer limits and queue lengths increases kernel memory allocation (kmalloc). Total TCP memory consumption must be constrained via net.ipv4.tcp_mem to prevent extreme traffic surges from exhausting system memory and triggering the Linux Out-Of-Memory (OOM) killer.

import ipaddress

class RoutingTable:
    def __init__(self):
        self.routes = []
    def add_route(self, prefix_str, gateway_str, interface_str):
        self.routes.append((ipaddress.ip_network(prefix_str), gateway_str, interface_str))
        # Sort by prefix length descending (Longest Prefix Match)
        self.routes.sort(key=lambda r: r[0].prefixlen, reverse=True)
    def lookup(self, destination_ip_str):
        dst = ipaddress.ip_address(destination_ip_str)
        for net, gw, iface in self.routes:
            if dst in net:
                return {"destination": str(dst), "matched_prefix": str(net), "next_hop": gw, "interface": iface}
        return None

rt = RoutingTable()
rt.add_route("192.0.2.0/26", "ON_LINK", "eth0")
rt.add_route("192.0.2.64/26", "192.0.2.1", "eth0")
rt.add_route("10.0.0.0/8", "192.0.2.1", "eth0")
rt.add_route("0.0.0.0/0", "192.0.2.1", "eth0")

for dst in ["192.0.2.15", "192.0.2.70", "10.240.0.50", "8.8.8.8"]:
    decision = rt.lookup(dst)
    print(f"[ROUTE LOOKUP] Destination: {dst:<15} -> Prefix: {decision['matched_prefix']:<14} Next-Hop: {decision['next_hop']}")
