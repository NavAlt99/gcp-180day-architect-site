1 · Topics of the day

Business Requirements

Business requirements translate commercial goals into measurable system specifications. The chain runs from a revenue target — "$10 M peak Black Friday revenue at an average basket of $200" — to a user-concurrency figure (50 000 concurrent users), to a sustained request rate (5 000 RPS per service), to an availability SLA (99.95 % monthly, 4.4 hours downtime budget per year). Geography and data-residency obligations are first-class business requirements: EU GDPR data sovereignty, US ITAR export controls, and APAC data-localization laws each constrain multi-region topology choices before a single VM is sized. Brand and customer-experience requirements manifest as latency SLOs (p99 < 300 ms end-to-end), error-rate SLOs (< 0.1 % 5xx per minute window), MTTR targets (≤ 15 minutes for severity-1 incidents), and CDN strategy decisions (Cloud CDN with Cloud Armor for the EU edge, separate for APAC).

A stakeholder presents a revenue goal as a business outcome; the architect's job is to derive measurable system targets from it. Vague requirements like "fast and reliable" are translated to concrete SLOs before any topology decision is made.

Symptom: During a flash sale, the checkout API returns HTTP 503 at 38 000 concurrent users — 24% below the stated 50 000-user capacity goal. Business impact: Each lost transaction costs approximately $200 in abandoned basket value; a 15-minute outage at peak translates to roughly $900 000 in lost revenue, a figure immediately visible in executive dashboards and triggering breach of the SLA bonus clause.

Technical Requirements

Technical requirements are the measurable system properties that must hold for the business requirements to be satisfied. Throughput sizing works from RPS to CPU/memory: at 5 000 RPS and 20 ms average CPU time per request, each 4-vCPU instance handles ~200 RPS; 25 instances are needed at peak, rounded up to 30 with 20% headroom and encoded in a Managed Instance Group autoscaling policy (target CPU 60%, max-replicas 40). Latency decomposition separates p50 / p95 / p99 targets: a p99 < 300 ms budget is split into network (≤ 10 ms intra-region), application (≤ 150 ms), database (≤ 80 ms), and serialization (≤ 60 ms). Tail-latency causes — JVM GC pauses, container cold-start (Cloud Run min-instances = 5), and database lock contention — are named and budgeted. Data volume is sized as: 500 GB/day of order events → Cloud Storage (hot tier) for 30 days, BigQuery partitioned by day for analytics, Bigtable for < 10 ms order-status lookups, and Cloud Spanner for the authoritative order ledger requiring strong consistency.

Integration points must be catalogued alongside latency and throughput: REST/gRPC API contracts, Pub/Sub event streams, BigQuery external tables for near-real-time reporting, Cloud Tasks for deferred jobs, and Eventarc triggers for event-driven workflows.

Symptom: The order-status API p99 latency spikes to 1.2 seconds during nightly batch analytics jobs that query the same Cloud SQL instance serving real-time requests. Business impact: Customer-facing status pages show stale data for up to two minutes, triggering a 12% increase in support ticket volume and breaching the contractual p99 < 500 ms SLO.

Functional vs Non-Functional Requirements (the "-ilities")

Functional requirements specify what the system does: place order, process payment via Stripe, send confirmation email via SendGrid, update inventory in Spanner. Non-functional requirements — the "-ilities" — specify how well it does it. Availability: 99.95% monthly SLO → active-active dual-region topology (us-central1 + us-east1) with Global External Application Load Balancer failover in < 60 s. Scalability: horizontal scale for stateless compute via MIG autoscaling, vertical scale for Hyperdisk IOPS when single-row write throughput is the bottleneck. Durability: RPO ≤ 1 minute → Cloud Spanner multi-region replication (nam6 config), regional Persistent Disk for VM state with Instant Snapshots for sub-minute RPO; RTO ≤ 15 minutes → failover automation tested quarterly. Maintainability: rolling updates with maxSurge=1 / maxUnavailable=0, blue/green deployments via Cloud Deploy, feature flags via LaunchDarkly or Unleash to decouple deploy from release. Security: Workload Identity for SA-to-SA auth, VPC Service Controls around the data perimeter, CMEK on all persistent storage (Cloud KMS), TLS 1.3 in transit, 90-day key rotation. Observability: golden signals (latency, traffic, errors, saturation) measured via Cloud Monitoring, SLI/SLO defined with error-budget burn-rate alerting at 1× and 5× rates.

Symptom: After a rolling update, the payment service reports a 3% error rate for 8 minutes because the new container version expects a database schema column that was not yet deployed by the migration job. Business impact: 8 minutes of 3% payment failures at 1 000 RPS means roughly 1 440 failed transactions, each requiring manual reconciliation and a refund-processing overhead of $15 per incident.

Constraints

Constraints are the boundary conditions that limit architectural choices regardless of what the business ideally wants. Budget: a $500 K/year cloud budget drives committed-use discount (3-year CUD on 20 n2-standard-8 instances = ~37% discount), sustained-use discounts on remaining on-demand VMs, and a budget alert at 80% of monthly allocation. Existing contracts: an Oracle DB on-prem with a 3-year support contract prevents immediate Spanner adoption — a strangler-fig migration with dual writes is required. Skills constraints: the SRE team is proficient in Terraform and Kubernetes Standard but has no GKE Autopilot experience — Autopilot adoption carries a 6-week ramp risk. Legacy systems: the monolith exposes order data via a proprietary binary protocol; an adapter layer (gRPC transcoding) is needed before REST consumers can integrate. Regulatory limits: PCI DSS scope reduction via tokenization (Stripe Radar) keeps cardholder data off GCP infrastructure; HIPAA BAA is not yet executed, blocking PHI storage in Cloud SQL until the agreement is in place. Deadline constraints: the MVP must ship in 90 days, requiring a phased approach — Phase 1 (checkout + payment) in 60 days, Phase 2 (analytics + personalization) in the remaining 30.

Symptom: A team selects GKE Autopilot for the new microservices platform, only to discover that the existing Datadog agent DaemonSet is not supported in Autopilot mode, losing all host-level metrics for the first three weeks post-migration. Business impact: Invisible infrastructure health during the most critical post-migration period means the SRE team cannot meet the 15-minute MTTR SLO, delaying the go-live sign-off and adding two sprint cycles of remediation work.

Geography and Data Residency as Architecture Drivers

Data residency requirements are non-negotiable constraints that determine topology before capacity planning begins. Three regulatory frameworks dominate GCP architecture choices:

  • EU GDPR Article 44-49: Personal data transfer outside the EEA requires adequacy decisions or SCCs. Architecture response: multi-region deployment within europe-west* regions, VPC Service Controls to prevent accidental data exfiltration, and Cloud DLP for real-time PII detection at ingestion.
  • US ITAR (22 CFR 120-130): Technical data for controlled items must remain within US persons' custody. Architecture response: dedicated GCP Assured Workloads project (IL4 or ITAR configuration), FedRAMP High controls, and Workforce Identity Federation to ensure only US-person engineers have access.
  • Japan APPI (Act on Protection of Personal Information): Requires domestic storage unless the recipient country offers equivalent protection. Architecture response: Org Policy constraint limiting resource creation to asia-northeast1, separate billing account for regulatory audit trail isolation.

Brand & Customer Experience as Measurable Requirements

Brand promises translate to SLOs. The SLO must be measurable, time-windowed, and linked to an error budget that governs release velocity. A p99 < 300 ms checkout latency SLO means: measured at the load balancer (not the application), averaged over a 28-day rolling window, with an error budget of 0.05% of requests allowed to exceed the threshold. When the error budget is exhausted, new feature deployments are paused and reliability work is prioritised — this is the error-budget policy.

Technical Requirements — Deep Technical Discussion

Throughput Sizing: RPS → Compute Chain

At 5 000 RPS with an average CPU time of 20 ms per request: each vCPU handles (1000 ms / 20 ms) × 1 vCPU = 50 requests/s. A 4-vCPU instance handles 200 RPS at 100% CPU. At 60% target CPU utilisation (to allow for spikes), effective capacity per instance = 120 RPS. Instances needed = 5 000 / 120 ≈ 42, rounded to 45 with 7% headroom. The MIG autoscaling policy is: target CPU utilisation = 60%, min-replicas = 5, max-replicas = 50, scale-out cooldown 60 s, scale-in cooldown 300 s. Memory: at 200 req/s per instance and 512 KB average request object size, working set = 200 × 512 KB × 2 (double-buffer) = 200 MB active; instance must have ≥ 4 GB RAM with ≥ 50% headroom = 6 GB minimum, select n2-standard-4 (16 GB).

Latency Decomposition: Budget Allocation

A p99 < 300 ms end-to-end budget is allocated across the call chain. Tail-latency causes must be named and mitigated:

  • JVM GC pause: G1GC with -XX:MaxGCPauseMillis=50; tune heap sizing to minimise full GC frequency. Monitor with Cloud Profiler heap allocation view.
  • Container cold start (Cloud Run): Set min-instances = 5 to eliminate cold-start for steady-state traffic; concurrency = 80 to maximise utilisation per instance.
  • Database lock contention (Cloud SQL): Use read replicas for all read queries; route writes to the primary. Enable pg_stat_activity monitoring to detect lock waits > 50 ms.

Integration Points Catalogue

Integration points must be documented with protocol, latency budget, retry policy, and owner. The Brightloaf integration catalogue:

  • REST/gRPC APIs: Order API (REST, JSON, p99 < 200 ms), Fulfillment API (gRPC, proto3, p99 < 100 ms internal). Retry: exponential backoff, 3 attempts, jitter.
  • Pub/Sub event streams: orders.placed, orders.fulfilled, inventory.updated topics. At-least-once delivery; consumer idempotency required (deduplication key = order_id + event_type).
  • BigQuery external tables: Hourly materialised view from Cloud Storage for the analytics team; not for latency-sensitive queries.
  • Cloud Tasks queues: Async email dispatch, invoice PDF generation. Queue: notifications-queue, max concurrency 50, retry limit 5, deadline 600 s.
  • Eventarc triggers: Cloud Storage object created → Cloud Run processor for receipt generation. At-least-once; idempotent handler required.

Durability: RPO/RTO Budget Allocation

RPO (Recovery Point Objective) is the maximum acceptable data loss, expressed in time. RTO (Recovery Time Objective) is the maximum time to restore service. These are business decisions, not technical defaults. The derivation:

  • RPO = 1 minute: Cloud Spanner multi-region (nam6) provides RPO ≈ 0 for the order ledger. Regional Persistent Disk with Instant Snapshots every 60 s provides RPO = 60 s for VM state. Cloud SQL HA replica (zonal) provides RPO ≈ 0 for cross-zone failures.
  • RTO = 15 minutes: Automated failover (Cloud SQL HA promotes replica in <60 s), MIG autohealing (replaces unhealthy instance in <3 min), DNS failover (Cloud DNS TTL = 30 s). Manual steps must not be in the critical path.

Observability: Golden Signals SLI/SLO Design

The four golden signals (Latency, Traffic, Errors, Saturation) are the minimum set of SLIs. Each must have a defined measurement method, a target (SLO), an error budget, and a burn-rate alerting policy:

  • Latency SLI: Proportion of order-place requests completing in <300 ms, measured at the load balancer over a 1-minute window. SLO: 99.5% of requests. Error budget: 0.5% per 28-day window. Burn rate alert: 5× rate for 1 h triggers page; 1× rate for 6 h triggers ticket.
  • Error rate SLI: Proportion of order-place requests returning non-5xx HTTP status. SLO: 99.9%. Alert: 5× burn rate for 5 min triggers page.

Budget: CapEx vs OpEx and Discount Modelling

Cloud computing shifts infrastructure from CapEx (capital expenditure — purchasing servers) to OpEx (operating expenditure — paying per hour). For the Brightloaf workload:

  • On-demand baseline: 30 × n2-standard-8 instances (30 vCPU, 128 GB RAM) at $0.38/h = $273.6/h = $2.4 M/year. Exceeds budget.
  • 3-year CUD: Commit 20 instances at 37% discount = $273.6/h × 66.7% for committed portion. Combined savings: ~$860 K/year. Brings total within budget.
  • SUD (sustained use discount): Automatically applied for instances running >25% of the month. Additional ~12% discount on on-demand instances.
  • Spot VMs for batch: Analytics batch jobs on Spot VMs at 60–91% discount; tolerate eviction with Dataflow autoscaling or Cloud Batch checkpoint/restart.

3 · Real-world problem and solution for each topic

Business Requirements · Field Case Incident

Enterprise scenario: Brightloaf's European e-commerce platform ("Project Rosewood") launches in germany-west1 to serve German and French customers. The architecture was designed to EU GDPR requirements: all PII stored in Cloud Storage buckets in europe-west3 (Frankfurt), BigQuery dataset in EU multi-region. Three weeks post-launch, a Cloud DLP inspection discovers that session analytics events — including hashed email addresses and device fingerprints — are being streamed to a Pub/Sub topic replicated to a Cloud Run service in us-central1 for real-time ML inference. The DLP alert fires on 12 000 events/hour.

Failure symptoms and impact: Cloud DLP policy violation alerts at P1 severity; GDPR Article 44 cross-border transfer without adequacy decision or SCC in place. Business impact: regulatory fine exposure up to €10 M or 2% of global annual turnover under GDPR Article 83; immediate suspension of the EU data processing agreement by the German DPA.

Constraints: The ML inference service cannot be immediately moved to europe-west1 (GPU quota not approved); the business requires real-time personalisation to continue (SLA commitment to marketing team); timeline to fix: 48 hours before DPA notification deadline.

Diagnostic sequence:

  1. Query Cloud Logging for Pub/Sub publish events from the EU analytics topic to identify the subscriber service account and destination.
  2. Inspect the VPC Service Controls access policy: the EU perimeter incorrectly excludes the Pub/Sub subscriber in us-central1 from the deny rule because the ML project was added to the perimeter's allowed-projects list during initial setup.
  3. Verify Cloud DLP inspection results: confirm that device fingerprints are classified as DEVICE_FINGERPRINT_IDENTIFIER (considered personal data under GDPR).
  4. Trace the data flow in Cloud Trace to confirm the analytics events are reaching the US Cloud Run instance.

Root cause: The VPC Service Controls perimeter was configured with the ML project added as an allowed project for early development convenience and was never removed before production launch. The Pub/Sub subscription in us-central1 was not caught in pre-launch data-residency review because the business requirement was documented only as "EU data stays in EU" without an explicit mapping to all integration points including Pub/Sub subscriptions.

Defensible remediation:

  1. Remove the ML project from the EU VPC Service Controls perimeter's allowed-projects list. Deploy VPC-SC dry-run mode first to confirm no other valid integrations are broken.
  2. Create a Pub/Sub topic in europe-west1 specifically for the EU ML inference pipeline. Deploy a scaled-down version of the ML inference Cloud Run service in europe-west1 (use CPU-only inference; request GPU quota expansion in parallel).
  3. Update the business requirements register: add an explicit data-flow diagram requirement that maps every Pub/Sub subscription to its residency classification. Add a pre-launch checklist item: "VPC Service Controls perimeter audit — all subscriber service accounts are EU-resident."
  4. DLP scanning: add a Cloud DLP inspection job on the EU analytics Pub/Sub topic with real-time deidentification as a safeguard.

Verification: Re-run Cloud DLP scan on the Pub/Sub topic — zero violations. Cloud Monitoring shows EU analytics events routing only to europe-west1 Cloud Run. VPC Service Controls audit log shows no denied requests from valid EU services.

Residual risk: CPU-only ML inference in europe-west1 has higher latency and lower throughput than GPU inference; personalisation quality degrades slightly until GPU quota is approved (~4 weeks). VPC-SC dry-run removal may reveal other integrations that were relying on the allowed-projects exception.

Technical Requirements · Field Case Incident

Enterprise scenario: Brightloaf's order-status API serves 2 000 RPS in steady state with a p99 latency SLO of 500 ms. The technical requirements document specifies that analytics queries run against a separate BigQuery dataset. During a quarterly business review, the data team discovers that BigQuery cost is $40 K/month (above the $25 K budget) and decides to route all analytics queries to a Cloud SQL read replica to "save money." Three weeks later, the order-status API p99 latency spikes to 1.8 s during business hours (09:00–17:00) while analytics queries run against the Cloud SQL replica.

Failure symptoms and impact: Cloud Monitoring latency SLO shows the order-status API breaching the 500 ms p99 threshold for 6 hours/day. Customer support ticket volume increases 18%. SLO error budget is consumed at 3× burn rate. Business impact: SLA breach clause activates at the end of the month, triggering a 15% service credit (approximately $45 K). The "cost saving" costs more than the original BigQuery bill.

Constraints: Analytics team cannot immediately return to BigQuery (budget approval process takes 2 weeks); the Cloud SQL replica must remain available for analytics during the fix window; the order-status API cannot tolerate degraded performance.

Diagnostic sequence:

  1. Check Cloud SQL Insights for the read replica: pg_stat_activity shows 40+ active analytics sessions with full-table sequential scans averaging 45 s each.
  2. Cloud Monitoring: correlate the order-status API p99 latency spike exactly with analytics query activity timestamps — match is within 2-minute windows.
  3. Check Cloud SQL CPU and I/O metrics: replica CPU at 95%; read I/O at 98% of provisioned IOPS (3 000 IOPS on db-n1-standard-4). The analytics queries saturate the I/O, causing the order-status point reads to queue.
  4. Verify that order-status reads are hitting the replica (correct behaviour) but the replica is I/O-saturated by analytics workload.

Root cause: The technical requirements document specified that analytics must use BigQuery but did not include an acceptance criterion (e.g., "Cloud SQL replica I/O utilisation must remain below 60% during analytics windows"). Without a measurable limit, the routing decision appeared acceptable to the data team. The requirement was stated without a unit and without a measurement method.

Defensible remediation:

  1. Immediately: throttle analytics query concurrency on the Cloud SQL replica to 5 sessions maximum using PgBouncer connection pooling with a pool_size=5 limit for the analytics user role. This limits I/O pressure to ~30% immediately.
  2. Short term: use BigQuery Omni or Cloud SQL federated query with row-level sampling (TABLESAMPLE SYSTEM (10 PERCENT)) for exploratory analytics — reduces I/O by 90%.
  3. Long term: reinstate BigQuery as the analytics tier. Justify cost: $40K/month BigQuery vs. $45K/month SLA credit (plus reputational cost). Update the technical requirements register: add "Cloud SQL read replica CPU ≤ 60% and IOPS ≤ 60% at all times; analytics queries routed exclusively to BigQuery."

Verification: Cloud SQL Insights shows replica CPU back to 35% during analytics windows. Order-status API p99 returns to 210 ms. SLO error budget burn rate drops to 0.3×.

Residual risk: PgBouncer connection pool is a new component requiring monitoring and capacity planning. BigQuery reinstatement budget approval may take 2 weeks — interim I/O throttling is a stopgap.

Functional vs Non-Functional Requirements · Field Case Incident

Enterprise scenario: Brightloaf's payment service undergoes a rolling update to add support for a new discount code schema. The new version (v2.4) expects a discount_code_id column in the orders table in Cloud SQL. The migration was scheduled to run as a Kubernetes Job before the rolling update, but the job's completion is not checked by the deployment pipeline before pods are replaced. The migration job takes 7 minutes (ALTER TABLE on a 2 TB table with ALGORITHM=INPLACE); the rolling update starts after 30 seconds (the default health check pass window). New pods start receiving traffic before the migration completes.

Failure symptoms and impact: For 6.5 minutes, 100% of checkout requests that include a discount code return HTTP 500 (column not found). Non-discount orders succeed. Error budget consumed: 6.5 min × 1 000 RPS × 3% (discount-code orders) = 11 700 failed transactions. Business impact: 11 700 failed checkouts at $200 average basket = $2.34 M in abandoned carts. Customer trust impact triggers social media escalation.

Constraints: The maintainability requirement (zero-downtime deploys) is in the requirements register, but the migration dependency was not captured as an explicit pre-condition. The pipeline uses Cloud Build with a Deploy step that was not configured to gate on the migration Job's success.

Diagnostic sequence:

  1. Cloud Logging: search for column "discount_code_id" of relation "orders" does not exist — first occurrence at 14:32:30, 6.5 minutes after the rolling update began.
  2. GKE Event logs: Kubernetes Job schema-migration-v2.4 shows status.completionTime at 14:39:00; rolling update began at 14:32:00.
  3. Cloud Build history: the Deploy step executed 30 seconds after the migration Job was submitted, without waiting for status.succeeded.
  4. Rollback: initiated at 14:39:30 (when the on-call engineer saw the alert); new pods replaced with v2.3 pods. Service restored at 14:47:00 (8 minutes post-detection, within the 15-minute MTTR budget by 7 minutes).

Root cause: The maintainability requirement — "deploy with zero downtime" — was captured without the implied pre-condition: "all schema migrations required by the new version must complete successfully before any new-version pod receives traffic." This gap between the functional requirement (process payment) and the non-functional requirement (zero-downtime deploy) was not surfaced until the migration dependency created an incompatibility window.

Defensible remediation:

  1. Update the Cloud Build pipeline: add a pipeline gate step that waits for the schema migration Job to complete successfully before rolling out the new pod version. A reference Cloud Build step sequence: 
    steps:
- name: 'gcr.io/cloud-builders/kubectl'
  args: ['wait', '--for=condition=complete', 'job/schema-migration-v2.4', '--timeout=900s']
  env: ['CLOUDSDK_COMPUTE_ZONE=us-central1-a', 'CLOUDSDK_CONTAINER_CLUSTER=prod-cluster']
- name: 'gcr.io/cloud-builders/gke-deploy'
  args: ['run', '--filename=k8s/payment-v2.4.yaml', '--location=us-central1', '--cluster=prod-cluster']
    This ensures no new-version pod receives traffic until Job.status.succeeded = 1, or the build fails after a 15-minute timeout.
  2. Adopt expand/contract migration pattern: first deploy a schema version that adds the nullable discount_code_id column (backward compatible with v2.3); then deploy v2.4 which writes to the column; then, after v2.3 is fully drained, make the column NOT NULL in a third migration step.
  3. Update requirements register: add under Maintainability: "All schema migrations that are prerequisites for a new version must be verified complete (Kubernetes Job status.succeeded=1) before any new-version pod is added to the LB backend pool."

Verification: Run the pipeline in staging with a simulated slow migration (sleep 300 in migration job). Confirm that the Deploy step blocks until the Job completes. Then introduce an intentional migration failure — confirm the pipeline fails and no new-version pods receive traffic.

Residual risk: Expand/contract pattern increases the total number of deployment steps from 1 to 3 per schema change; this increases release cycle time by ~20 minutes per schema-changing deploy. Teams may be tempted to skip the pattern for "small" schema changes — requires enforcement via pipeline policy.

Constraints · Field Case Incident

Enterprise scenario: Brightloaf's infrastructure team migrates the order processing microservices to GKE Autopilot to reduce operational overhead (a skills constraint mitigation strategy: the team cannot manage node pools). The migration is completed in 4 days and passes smoke tests. Two weeks later, the SRE on-call notices that the Datadog APM agent is not reporting any host-level infrastructure metrics (CPU, memory, network) for the GKE nodes, only application-level metrics from the SDK. The Datadog agent was deployed as a DaemonSet — which is not supported in GKE Autopilot (Autopilot does not allow privileged DaemonSets or host-network containers).

Failure symptoms and impact: Infrastructure metrics (node CPU, memory pressure, disk I/O saturation) are invisible for 3 weeks post-migration. During that window, a memory leak in the inventory service causes node memory pressure to grow silently. When the node hits OOMKilled threshold, it evicts 8 pods simultaneously, causing a 45-second service disruption. The disruption triggers the 99.95% monthly SLO breach (4.4-hour annual budget consumed by this single incident). Business impact: SLA credit clause activates; post-incident review discovers 3 weeks of blind spots in infrastructure observability.

Constraints: The skills constraint mitigation strategy ("use Autopilot to reduce ops burden") was implemented without fully auditing existing observability tooling against Autopilot compatibility. The constraint register did not include "Datadog DaemonSet observability" as a dependency to verify before migration.

Diagnostic sequence:

  1. After the OOMKilled event: check Datadog dashboards — no host-level memory metrics for GKE nodes for the past 3 weeks. Application metrics are present.
  2. Check GKE Autopilot documentation: privileged DaemonSets and host-network containers are not supported. The Datadog node agent requires hostPID: true and hostNetwork: true — both blocked by Autopilot.
  3. Review the pre-migration constraint register: Datadog DaemonSet compatibility was not listed as a constraint to verify before selecting Autopilot.
  4. Cloud Monitoring: node memory utilisation metrics are available via GKE native monitoring (Prometheus metrics from the kubelet) — these were enabled but not routed to Datadog, creating a dual-source gap.

Root cause: The constraint register documented the skills constraint ("team lacks Autopilot experience") and the mitigation (use Autopilot + Google PSO training), but did not enumerate downstream dependencies of the existing tooling stack. The constraint audit did not ask: "What does our existing monitoring agent require from the node that Autopilot does not provide?"

Defensible remediation:

  1. Immediate: switch GKE node monitoring from Datadog DaemonSet to the Google-managed Prometheus collector + Datadog Metrics Agent sidecar pattern (runs in the application pod, not as a privileged DaemonSet). This recovers node-level metrics via cAdvisor without requiring host privileges.
  2. Short term: enable GKE Managed Prometheus with PodMonitoring resources to collect kubelet node metrics; configure Datadog Agent to scrape from the GMP endpoint.
  3. Long term: update the constraint register template to include a mandatory "Tooling Compatibility Audit" section: for each migration decision, list all existing tooling (CI/CD, monitoring agents, security scanners) and verify compatibility with the target platform before migration begins.

Verification: Datadog dashboard shows node-level CPU and memory metrics for all GKE Autopilot nodes. Cloud Monitoring confirms GKE Managed Prometheus is collecting kubelet metrics at 60-second intervals. Re-run the memory-leak scenario in a staging cluster — verify that OOMKilled alert fires in Datadog within 2 minutes of memory pressure exceeding 80%.

Residual risk: Sidecar pattern increases per-pod resource overhead (~50 MB RAM per pod for the Datadog agent). For a cluster with 200 pods, this adds ~10 GB of RAM overhead — a cost and capacity consideration that must be added to the budget constraint. GKE Managed Prometheus data is stored in Google Managed Service for Prometheus (GMSF), not Datadog — engineers must query two sources until a unified dashboard is built.
