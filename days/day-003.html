1 · Topics of the day

Day 3 separates three boundaries that are often conflated: a name resolving to an address, a packet being reachable to that address, and a transport connection becoming established. Build from the Day 2 next-hop artifact and preserve uncertainty where a local resolver, network policy, or remote host is not under your control.

Exit evidence: Produce one annotated DNS/transport diagram that distinguishes IPv4 and IPv6 name resolution, IP reachability, and a TCP established connection; attach answers for record type, resolver role, endpoint, port, and handshake state.

1. IPv6 addressing and scope

IPv6 represents a 128-bit address, normally written as hexadecimal groups, with a prefix length that identifies the network portion. Scope matters: link-local addresses require an interface context, while a global-looking address still needs a usable route and a listening service before it can support an application exchange.

Problem preview: A client has an AAAA answer but attempts a link-local destination without an interface scope. The user experiences an apparent name-resolution success followed by no usable connection.

Technical discussion → Real-world problem → Step-by-step lab →

2. DNS records, TTL and resolver roles

DNS maps names to typed resource records. A recursive resolver serves a client from cache when permitted or follows delegations to authoritative servers; an authoritative server publishes zone data. A TTL constrains caching of an answer but is not a promise about propagation, reachability, or application availability.

Problem preview: A cache returns an older address until its recorded TTL expires after a planned change. Users may be sent to the previous destination even though the zone data was changed.

Technical discussion → Real-world problem → Step-by-step lab →

3. TCP and UDP, ports, connection states and buffers

A socket endpoint pairs an IP address with a port. TCP creates ordered, reliable byte-stream state through a handshake and teardown states such as ESTABLISHED and TIME_WAIT; UDP sends independent datagrams without creating a TCP-style connection. Socket buffers absorb bounded send/receive work but do not remove application, network, or peer limits.

Problem preview: A service name resolves and packets reach the host, but no process is listening on the requested TCP port. The user sees a failed connection even though DNS and IP reachability may be separately healthy.

2 · Technical discussion of each topic

The path is intentionally layered: addressing supplies a scoped destination, DNS supplies data from an authority through a resolver cache, and transport supplies a socket-to-socket exchange. A successful result at one layer is evidence only for that layer.

1. IPv6 addressing and scope: technical mechanics

Address, prefix, and scope

An IPv6 address is not a route. A host selects a source and next hop according to local interface, addressing, and routing information; Neighbor Discovery replaces IPv4 ARP functions on IPv6 links. Link-local addresses are valid only on their link, so a socket destination may need a zone/interface identifier in local tooling.

  • Control boundary: interface configuration, prefix and route selection are local network controls.
  • Data path: a DNS AAAA answer supplies an address record; packets still require a source address, route, next-hop resolution, and a receiver.
  • Failure signal: an AAAA response or a formatted address alone cannot establish which path failed.
  • Trade-off: dual stack improves compatibility but creates independent IPv4 and IPv6 paths that must be tested and evidenced separately.

Evidence limit: supplied resolver text can show a record; a local IPv6 route-table observation can show a route on that host; neither proves behavior from another network.

Architectural evaluation questions

  • Which scope and interface make this IPv6 destination meaningful?
  • What evidence separates an AAAA answer from route reachability?
  • When is an IPv4 fallback a compatibility choice rather than proof that IPv6 is broken?

Further study: RFC 4291 §2: IPv6 addressing architecture (accessed 2026-09-30).

2. DNS records, TTL and resolver roles: technical mechanics

Records and roles

A and AAAA records map names to IPv4 and IPv6 addresses. CNAME aliases one name to another; MX, TXT, NS, SOA, and PTR serve mail, text policy, delegation, zone, and reverse-lookup roles. The stub resolver usually asks a recursive resolver; recursive and authoritative are different responsibilities even when an implementation can host both.

  • Control boundary: zone owner publishes the authoritative data; cache operator controls local resolver behavior; client controls what it queries and records.
  • Data path: query → recursive cache or delegation → authoritative answer → TTL-bearing response → client decision.
  • Failure signal: NXDOMAIN, SERVFAIL, timeout, or a stale cache answer are different observations requiring different evidence.
  • Trade-off: shorter TTL may reduce cache persistence but increases query dependency; it does not make every resolver refresh simultaneously.

Evidence limit: dig output identifies a responding server and flags in one observation. It does not alone prove which upstream servers were contacted or when every cache will expire.

Architectural evaluation questions

  • Which role owns the RRset and which role may serve a cached answer?
  • What does the displayed TTL prove and not prove?
  • How would you avoid calling a DNS result a reachability test?

Further study: RFC 1034 §4.3.1: name-server and resolver behavior (accessed 2026-09-30).

3. TCP and UDP, ports, connection states and buffers: technical mechanics

Socket and transport boundary

A TCP connection is identified by local and remote address/port pairs. The three-way handshake synchronizes state: client SYN, server SYN-ACK, client ACK; only then is the connection established. TIME_WAIT is a TCP state used during connection termination and is not an application error by itself. UDP has ports and checksum/datagram semantics but no built-in connection establishment, ordering, or retransmission equivalent to TCP's stream behavior.

  • Control boundary: the operating system owns socket state and buffer limits; the application owns port binding, protocol expectations, and backpressure behavior.
  • Data path: DNS answer → route → destination address → transport port → process socket → application protocol.
  • Failure signal: refused, timeout, reset, and an application response are distinct signals; they must not be collapsed into a generic “network down.”
  • Trade-off: TCP adds ordered delivery and congestion/retransmission behavior; UDP leaves reliability and ordering decisions to the application.

Evidence limit: a local ss listing can show local socket state. It cannot prove a remote process's state or an application's semantic success.

Architectural evaluation questions

  • Which five-tuple fields identify the observed TCP flow?
  • What fact distinguishes connection establishment from an application response?
  • When is UDP appropriate only if the application can tolerate or implement loss/order handling?

Further study: RFC 9293: Transmission Control Protocol (accessed 2026-09-30).

3 · Real-world problem and solution for each topic

These are synthetic Brightloaf tabletop cases. The quoted command outputs are illustrative local evidence formats, not records of a real production event; each diagnosis preserves the distinction between an observed symptom and an architectural inference.

1. IPv6 addressing and scope · field case

Enterprise scenario: Synthetic tabletop: Brightloaf's test client receives an AAAA record for a service and an operator copies a link-local address into a runbook without its interface context.

Failure symptoms and impact: Supplied symptom: the lookup is recorded as successful while the follow-on connection cannot identify a usable destination. Business impact is a delayed test, not a claimed production outage.

Constraints: Do not modify network configuration or claim a remote service failure; use the supplied output and local route table only.

Evidence:

$ dig AAAA api.example.test
;; ANSWER SECTION:
api.example.test. 300 IN AAAA 2001:db8:1::20

$ ip -6 route
fe80::/64 dev eth0 proto kernel metric 256

This is illustrative local evidence.

Root cause: Architectural inference: the runbook confused a DNS record with a scoped, routed socket destination. The supplied documentation prefix is also reserved for examples and must not be treated as a live target.

Diagnostic sequence:

  1. Label the AAAA answer as name-resolution evidence only.
  2. Record the destination scope and the local interface/route separately.
  3. Check whether the test target and socket endpoint are supplied or locally observable.
  4. Stop at an unknown route or listener rather than assigning an application cause.

Defensible remediation:

  1. Store address, prefix, scope, and interface as separate runbook fields.
  2. Require a two-path worksheet: AAAA resolution plus a bounded local route observation.

Verification: A reviewer can point to distinct fields for DNS answer, chosen interface, route evidence, and TCP state; no field claims that another field proves it.

Residual risk: Local routes and remote policy can change after the worksheet is made; repeat observations when the environment changes.

2. DNS records, TTL and resolver roles · field case

Enterprise scenario: Synthetic tabletop: a Brightloaf migration worksheet changes the intended A and AAAA targets, but the test team treats a cached recursive response as proof that the authoritative zone is wrong.

Failure symptoms and impact: Supplied symptom: different test locations show different answers. Operational impact is delayed cutover review; no customer impact or propagation time is asserted.

Constraints: Use only supplied transcripts and labels; do not edit a public or private DNS zone.

Evidence:

$ dig www.example.test A
;; flags: qr rd ra; QUERY: 1, ANSWER: 1
;; ANSWER SECTION:
www.example.test. 120 IN A 192.0.2.44
;; SERVER: 192.0.2.53#53

Illustrative output: ra indicates recursion available from the responding server.

Root cause: Architectural inference: the worksheet lacks resolver-role and TTL fields, so a cache observation is being compared directly with an unobserved authoritative response.

Diagnostic sequence:

  1. Classify the supplied server as recursive response evidence, not authoritative proof.
  2. List query name, type, answer, TTL, flags, and responding server.
  3. Obtain supplied authoritative evidence only if the exercise provides it; otherwise record unknown.
  4. Compare observations without inventing a propagation interval.

Defensible remediation:

  1. Add cache-versus-authority columns to the change worksheet.
  2. Require the cutover decision to cite RR type, answer, TTL, responder, and observation time.

Verification: The revised worksheet can explain why two answers may differ without declaring either a network failure.

Residual risk: Caching behavior and delegation configuration remain environment-dependent and must be observed again during a real, authorized change.

3. TCP and UDP, ports, connection states and buffers · field case

Enterprise scenario: Synthetic tabletop: a Brightloaf integration test uses the right hostname but labels every failure “DNS” without recording the destination port or TCP state.

Failure symptoms and impact: Supplied symptom: the test report cannot tell a refused port from a timeout or an application-level rejection. The business effect is slower triage, not a claimed outage.

Constraints: No listener is created and no port scan is performed; use supplied socket-state examples and a bounded local observation.

Evidence:

State      Recv-Q Send-Q Local Address:Port Peer Address:Port
ESTAB      0      0      192.0.2.10:51524  192.0.2.44:443
TIME-WAIT  0      0      192.0.2.10:51525  192.0.2.44:443

Illustrative state output; documentation addresses are not live targets.

Root cause: Architectural inference: the test evidence skipped the socket endpoint and state transition, collapsing name resolution, IP delivery, transport establishment, and application behavior into one unsupported cause.

Diagnostic sequence:

  1. Record local and remote address/port separately.
  2. Place SYN, SYN-ACK, and ACK before ESTABLISHED in the diagram.
  3. Classify a supplied result as refused, timeout, reset, established, or application response only when the evidence states it.
  4. Treat buffer pressure as a bounded queue/backpressure question, not proof that packets were lost.

Defensible remediation:

  1. Use a four-layer triage form: DNS, route, transport state, application protocol.
  2. Require a destination port and a state/result field before assigning an owner.

Verification: A reviewer can locate the endpoint pair, handshake, state, and evidence boundary without calling a TCP state an application result.

Residual risk: NAT, firewall, load balancer, and remote application behavior can still obscure a path; the form records that uncertainty.

4 · Step-by-step labs for each topic

The exercises use supplied or local resolver output only. Do not alter DNS zones, firewall rules, routes, or remote services. Save the diagram and answers as an evidence artifact.

Exercise 1: Build an IPv6 scope worksheet

Goal: Separate IPv6 notation, scope, resolver answer, and route evidence.

Expected result: One annotated IPv6 branch with an explicit unknown/stop condition where evidence is absent.

Mode: local/tabletop; no cloud resources or credentials required · Prerequisite: Day 2 network-path artifact, a terminal with dig and curl, and a text editor

Preflight: Use only approved public documentation/test names; record local command output as an observation, not as a universal result.

Exact execution

  1. Stage 1 — Preflight: write 2001:db8:1::20/64 and fe80::1 in the worksheet; mark the documentation prefix and link-local scope.
  2. Stage 2 — Prepare inputs: copy the supplied AAAA response and local IPv6 route-table output into two labeled columns.
  3. Stage 3 — Author analysis: draw client → AAAA answer → selected interface → route → server socket, leaving a blank only for unobserved evidence.
  4. Stage 4 — Execute bounded observation: run ip -6 addr and ip -6 route; record only the local interface and route lines relevant to the worksheet.
  5. Stage 5 — Inspect result: identify one prefix length, one interface, and whether the supplied address is link-local or documentation/global-formatted.
  6. Stage 6 — Rehearse edge case: replace the destination with fe80::1 and state why an interface/zone is required before a local test is meaningful.
  7. Stage 7 — Diagnose and decide: label the earliest missing proof as DNS, route, neighbor, listener, or unknown; write one next safe observation.
  8. Stage 8 — Close out: remove copied transient output that contains unrelated local addresses and save the redacted worksheet.
Expected result / acceptance

Compare the recorded diagram and command transcript with the stated invariant; environment-dependent resolver output is illustrative.

Artifact acceptance: Artifact contains address/prefix, scope, resolver evidence, route evidence, one stated limitation, and a next-hop/stop decision. (File: day-003-dns-transport-evidence.md).

Troubleshooting

If the IPv6 route command is unavailable, use supplied output and explicitly mark the local observation unperformed; do not substitute IPv4 output.

Goal: Draw the TCP handshake, contrast UDP, and identify the boundary between transport and application evidence.

Mode: local/tabletop; no cloud resources or credentials required · Prerequisite: Day 2 network-path artifact, a terminal with dig and curl, and a text editor

Preflight: Use only approved public documentation/test names; record local command output as an observation, not as a universal result.

Exact execution

  1. Stage 1 — Preflight: write the endpoint template local-IP:local-port → remote-IP:remote-port and state that port identifies the transport endpoint, not the application outcome.
  2. Stage 2 — Prepare inputs: use supplied IPv4 192.0.2.44, IPv6 2001:db8:1::20, remote port 443, and local port 51524 as documentation-only values.

  7. Stage 7 — Diagnose and decide: classify each supplied result as DNS answer, route evidence, TCP state, application response, or unknown; choose one next bounded observation.
  8. Stage 8 — Close out: remove any unrelated local endpoints from the artifact and save the final diagram with its evidence-limit note.
