IPv6 addressing and scope

IPv6 identifies interfaces using 128-bit addresses. Prefixes describe address ranges; loopback, link-local and global-scope unicast addresses have different reachability rules. An AAAA DNS answer names an IPv6 destination but does not establish a route or socket connection.

Why today and where it sits: Day 3 extends Day 2's IPv4 path to dual-stack clients before the learner studies transport and DNS in detail. Address selection sits between name resolution and a network-layer attempt toward Brightloaf's Order API.

Problem preview: Brightloaf publishes an AAAA record, but IPv6 clients time out before TCP connects. Checkout requests from those clients cannot reach the Order API, delaying order placement.

DNS records, TTL and resolver roles

DNS returns typed records: A and AAAA carry addresses, CNAME names an alias, MX identifies mail exchangers, TXT carries text, NS identifies delegated name servers, SOA records zone authority, and PTR supports reverse lookup. A record's TTL controls how long a resolver may cache that answer.

Why today and where it sits: The Day 3 exit diagram starts with name resolution and must separate it from packet reachability and connection state. Clients ask a recursive resolver, which may use cached data or obtain an answer from the authoritative zone for the name.

Problem preview: An authoritative A record changes while a customer resolver still returns its cached old address. Some shoppers reach the retired Order API endpoint, disrupting checkout during the change window.

TCP and UDP, ports, connection states and buffers

TCP provides an ordered byte stream after connection establishment; UDP sends datagrams without TCP's handshake or delivery guarantees. A socket endpoint combines an address, transport protocol and port, while socket buffers hold bytes waiting to be sent or read.

Why today and where it sits: After an A or AAAA answer, the learner must label client and server endpoints and distinguish an attempted TCP handshake from an established connection. This boundary sits below TLS and the Order API's HTTP processing.

Problem preview: A client sends a SYN to the Order API but observes no SYN-ACK. The order request never reaches an established transport connection, so checkout times out before an HTTP response.

2 · Technical discussion of each topic

IPv6 addressing and scope

Address and prefix. IPv6 addresses have 128 bits, normally written as eight hexadecimal groups separated by colons. Leading zeros in a group may be omitted, and one consecutive run of all-zero groups may be compressed with ::. For example, 2001:0db8:0000:0000:0000:0000:0000:0010 becomes 2001:db8::10. The double colon can appear only once in one address because a second omission would make the number of zero groups ambiguous. A /64 prefix says that the first 64 bits identify the network portion for that address and prefix; it is not a port number. 2001:db8::/32 is reserved for documentation, so examples using it are not internet destinations. RFC 4291, address text and RFC 5952, canonical text describe these rules.

Scope matters. ::1 is the loopback address, used to reach the same host. Link-local addresses in fe80::/10 are for a single link; a link-local destination may need an interface identifier because the same text can exist on more than one link. Global-scope unicast addresses can be routed beyond the local link when the network permits it. The address type tells you where a packet could be used, but it does not establish that a route, firewall rule or listener exists. RFC 4291, unicast addresses provides the address classes.

From name to connection. An A DNS record supplies an IPv4 address; an AAAA record supplies an IPv6 address. A client may have both answers and choose an address family for a connection attempt. After it chooses IPv6, it needs a usable source address, route and next-hop reachability. IPv6 Neighbor Discovery uses ICMPv6 messages to discover routers and on-link neighbors; it is not the same exchange as IPv4 ARP. The destination must then have a listening socket for the chosen address family and port. RFC 4861, Neighbor Discovery overview explains the local-link mechanisms.

Diagnostic boundary: An AAAA answer proves that a name resolved to an IPv6 address. It does not prove that packets reach that address or that TCP established. If the A path works and the AAAA path fails, keep those facts separate and check the IPv6 route, filtering and listener before blaming DNS.

DNS records, TTL and resolver roles

An application commonly asks a local resolver for a name. A recursive resolver can answer from cache or query the DNS hierarchy until it reaches an authoritative server for the relevant zone. The authoritative server holds the zone's records; the recursive resolver serves clients and caches responses. A cached answer can remain visible after an authoritative change until its TTL expires, so “the record was updated” and “every client now sees it” are different claims. Negative answers may also be cached under separate rules.

Record types answer different questions. An A or AAAA answer provides an address to try, but does not establish a route, transport connection or healthy application. A CNAME points to another name that must be resolved; MX is about mail delivery rather than web requests. NS and SOA describe delegation and zone authority. PTR is commonly used for reverse lookup; it does not prove ownership or authentication of the forward name. In cloud incidents, checking the requested type, response, TTL, resolver and authoritative zone avoids treating every reachability problem as “DNS is down.”

TCP and UDP, ports, connection states and buffers

TCP's ordinary active open uses a three-message handshake: SYN, SYN-ACK, ACK. The peers exchange initial sequence numbers and reach ESTABLISHED before the application treats the connection as ready. A TCP connection is identified by protocol plus source and destination addresses and ports. The server can listen on one port while many clients connect using distinct source endpoints. After closing, TIME-WAIT is a normal state that helps handle delayed segments from the old connection; it is not automatically a leak or an outage.

TCP preserves ordered bytes for an application but does not preserve application message boundaries. A single send can be read in pieces, and multiple sends can be combined in one read. Socket buffers absorb short differences between producer and consumer rates; full buffers can cause backpressure or blocking, not magic unlimited capacity. UDP keeps datagram boundaries but does not itself guarantee delivery, ordering or duplicate suppression. An application choosing UDP must provide any needed reliability at another layer. A DNS answer that names an IP is separate from the transport handshake, and an established connection is separate from a successful HTTP response.

3 · Real-world problem and solution for each topic

Case 1 · An AAAA answer with no IPv6 route

Illustrative symptom and impact: Brightloaf's Order API publishes both A and AAAA records. A group of IPv6-preferring checkout clients obtains 2001:db8:abcd:1200::25 in the supplied fixture but sees a connection timeout, while IPv4 requests succeed; orders from those clients are delayed.

Constraints, evidence and root cause: The documentation address is an example, not a live endpoint. The affected client has a valid AAAA answer but no route to the selected IPv6 destination. The answer proves name resolution, while the missing route prevents a useful SYN from reaching the intended path. A different client could have a route and fail later, so diagnosis must use that client's route and transport observations.

Response and verification: Record the queried name, returned AAAA, selected source address and route; compare with the working A path. Correct the IPv6 route and next-hop configuration, or withdraw the unusable AAAA record through a controlled DNS change while keeping the working A endpoint healthy. Recheck DNS, route, handshake and an Order API response independently. Any retried order or event must retain its idempotency key, and Fulfillment must reject a replay against durable state before issuing a second shipment. Residual risk remains until both client address families and the return path are exercised.

Case 2 · Old A answers after a DNS cutover

Illustrative symptom and impact: At 09:02 Brightloaf changes the authoritative A record for orders.example.test from 192.0.2.10 to 192.0.2.20. At 09:03 an affected resolver still returns the old address with 180 seconds of remaining TTL, so some shoppers reach the retiring Order API endpoint.

Constraints, evidence and root cause: The times and addresses are supplied fixture observations. The old recursive answer is within its cache lifetime; the authoritative update does not invalidate it. A customer may also query AAAA, so collect the requested type, resolver address, answer and remaining TTL before attributing the behavior to this cache. Do not assume every resolver expires at the same wall-clock time.

Response and verification: Keep the old endpoint healthy through the planned TTL window, compare affected recursive and authoritative answers, and monitor A and AAAA paths separately. For a future migration, lower TTL well before cutover and wait for prior high-TTL answers to age out. Verify that new queries receive the intended records and that each resulting address reaches the Order API. Retire the old endpoint only after observed clients have moved; maintain a rollback path. A correct DNS answer still does not prove a TCP connection or successful order processing.

Case 3 · A SYN without an established connection

Illustrative symptom and impact: A Brightloaf checkout client receives the intended address but times out before an HTTP response. In the supplied trace its SYN leaves source port 53001 for destination port 443, with no SYN-ACK observed; new orders cannot be submitted on that path.

Constraints, evidence and root cause: A process-running indicator and a valid DNS answer are insufficient. The first unproven boundary is the return of SYN-ACK; a missing route, filtering rule, unavailable listener or missing return path could explain it. The fixture intentionally does not identify which of these caused the absence, so no single firewall or application fix is justified yet.

Response and verification: Record the exact source and destination addresses, protocol and ports. Compare client route, outbound and inbound policy, server listener and server return route; obtain packet observations on both sides where permitted. Repair the first demonstrated failure and repeat the handshake check before testing TLS or HTTP. Verify an application response and one durable order record. Treat TIME-WAIT from earlier connections as normal lifecycle evidence, not proof that this request connected. A retry must keep the order key stable so Fulfillment can suppress duplicate business action.

Exercise 1 · Classify IPv6 addresses and select a path

Goal: Read and classify IPv6 addresses, then trace a supplied dual-stack lookup. Mode: local Linux terminal with Python 3 plus a Markdown diagram. The example addresses are documentation fixtures; do not try to contact them. Bring Day 2's IPv4 next-hop worksheet.

Step 1 — Confirm Python

Open a Linux terminal and run:

python3 --version

Expected: a Python 3 version. Open the Day 1 evidence repository and create a note named day-003-ipv6.md with your editor. Record the version you observed.

Step 2 — Parse addresses and a prefix

Copy and run this offline Python script:

python3 - <<'PY'
from ipaddress import IPv6Address, IPv6Network

address = IPv6Address('2001:0db8:0000:0000:0000:0000:0000:0010')
network = IPv6Network('2001:db8:abcd:1200::/64')
print('compressed:', address.compressed)
print('network:', network.network_address, 'prefix:', network.prefixlen)
print('loopback:', IPv6Address('::1').is_loopback)
print('link-local:', IPv6Address('fe80::1').is_link_local)
PY

Expected output:

compressed: 2001:db8::10
network: 2001:db8:abcd:1200:: prefix: 64
loopback: True
link-local: True

The script shows zero compression, a /64 network prefix and two special address scopes. If parsing fails, check the number of colons and the placement of ::. Save the actual output in the note; do not replace it with the expected text.

Step 3 — Trace supplied resolver answers

Use these fixture records, not a live DNS query:

orders.example.test A    192.0.2.25
orders.example.test AAAA 2001:db8:abcd:1200::25

Draw two paths. The IPv4 path ends at address 192.0.2.25, TCP port 443. The IPv6 path ends at address 2001:db8:abcd:1200::25, TCP port 443. Mark the A and AAAA lookups as name resolution only. Both addresses are from documentation ranges (RFC 5737, RFC 3849).

Step 4 — Inject and diagnose one failure

Add these observations to the diagram:

IPv4: A answer returned; route present; TCP handshake established.
IPv6: AAAA answer returned; client has no route to the IPv6 destination.

Predict the result: the IPv6 name lookup succeeds, but its TCP handshake cannot start successfully. Note the next evidence you would seek: the selected IPv6 source address and route. A working IPv4 response does not repair the IPv6 path.

Step 5 — Verify and keep the artifact

Under the diagram, answer separately what the DNS reply proves, what a completed TCP handshake proves, and what an HTTP response would prove. The note passes when it contains the four actual Python results, both socket endpoints and the first failing IPv6 boundary. Link it into Day 3's combined DNS/transport artifact.

No cloud or network resource was created. Keep the note and script output; there is nothing to delete.
