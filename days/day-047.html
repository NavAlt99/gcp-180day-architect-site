Part 1 · Topics of the day

Cloud Run: services vs jobs, revisions, traffic splitting, concurrency, scaling and VPC networking

Cloud Run is Google Cloud's fully managed, serverless compute platform built on Knative standards and isolated by the gVisor secure user-space kernel sandbox. Unlike traditional container orchestration where infrastructure teams manage Kubernetes control planes and node pools, Cloud Run abstracts host infrastructure entirely, provisioning and scaling stateless HTTP-based microservices (Cloud Run services) or run-to-completion batch tasks (Cloud Run jobs) on demand. Deployments generate immutable, dated revisions that support zero-downtime blue-green rollouts and weighted traffic splitting down to 1% granularity, while scaling parameters (concurrency from 1 to 1000 requests per instance, min/max instance boundaries, and CPU allocation throttled to request lifecycles versus always allocated) dictate cold-start responsiveness, thread safety, and runtime cost. Modern enterprise deployments integrate directly with VPC subnets via Direct VPC Egress—eliminating Serverless VPC Access connector bandwidth bottlenecks—and secure ingress endpoints using IAM invoker roles (roles/run.invoker), OIDC identity token authentication, and custom domain TLS certificates.

This capability belongs on Day 47 because Days 42–46 covered Kubernetes management and service mesh operations; architects must now contrast Kubernetes operational complexity against serverless compute runtimes for stateless APIs, asynchronous webhooks, and background batch jobs. In enterprise architectures, Cloud Run acts as the primary compute runtime for event ingestion webhooks, customer-facing web applications, and scheduled operational maintenance tasks.

When an unverified deployment misconfigures concurrency to default single-threaded limits while running CPU-throttled async tasks, instances saturate instantly during flash traffic bursts and queue inbound checkout calls. Upstream API gateways experience 504 Gateway Timeouts, abandoning shopping carts and triggering customer support escalations.

Cloud Run functions (Cloud Functions): event-driven triggers, gen1 vs gen2, cold starts and timeouts

Cloud Run functions (formerly Cloud Functions) provide an event-driven serverless computing model designed to execute lightweight code snippets in response to cloud infrastructure events. While Gen 1 operated on legacy container wrappers with 9-minute execution timeouts, single-request concurrency, and rigid App Engine networking, Gen 2 standardizes fully on Cloud Run infrastructure, unlocking up to 60-minute execution windows, multi-concurrency (up to 1,000 parallel requests per container), Direct VPC egress, and native Eventarc integration based on the CloudEvents standard. Events emitted by Cloud Storage (object creation, archival, deletion), Pub/Sub message topics, Cloud Audit Logs, and Firestore document updates are converted into standardized CloudEvent envelopes and delivered reliably to function endpoints, where configurable minimum instances and Startup CPU boost flags mitigate cold-start initialization latency.

This topic belongs on Day 47 because modern cloud systems rely on decoupled, event-driven architectures to react asynchronously to state changes without maintaining continuously running VMs or GKE pods. In production landing zones, Cloud Run functions form the reactive connective tissue executing image watermarking, audit log streaming, automated security posture remediation, and asynchronous order fulfillment workflows.

When a storage trigger function lacks idempotency checks and cold-start mitigations, bursty file uploads cause Pub/Sub redelivery loops that process duplicate invoice records while exceeding the function timeout limit. Customer billing records are billed multiple times, while database connection pools become exhausted and crash dependent inventory services.

Part 2 · Technical discussion of each topic

Cloud Run Runtime Mechanics, Scaling Formulations, and Network Egress Topologies

Cloud Run executes container images conforming to the Open Container Initiative (OCI) specification, running within a multi-tenant sandboxed virtualization layer powered by Google's gVisor kernel interceptor. Unlike standard Linux namespaces where containers share the host kernel directly, gVisor provides strong multi-tenant hardware and kernel boundary isolation without the heavy boot overhead of traditional VMs.

1. Services vs. Jobs Architecture:

  • Cloud Run Services: Designed for long-lived, request-driven HTTP/1, HTTP/2, gRPC, and WebSocket workloads. Services listen on the port specified by the $PORT environment variable (default 8080) and automatically autoscale from zero instances up to the configured --max-instances ceiling based on incoming request concurrency. Services handle graceful lifecycle shutdowns: when an instance is marked for scaling down, Cloud Run sends a SIGTERM signal, providing a 10-second grace period for the container to drain active connections and flush logs before a final SIGKILL.
  • Cloud Run Jobs: Designed for batch processing tasks that run to completion and do not listen for incoming network requests. A job consists of one or more tasks executed in parallel (e.g. database schema migrations, daily financial reconciliation, ML batch inference). Jobs support task arrays (indexed 0 to N-1), configurable task retries (--max-retries), parallel execution ceilings (--parallelism), and extended task execution timeouts up to 24 hours (86,400 seconds). Jobs are triggered on-demand via Cloud Scheduler, Workflows, Cloud Tasks, or direct API/CLI execution.

2. Autoscaling Mechanics and Concurrency Sizing:

Cloud Run autoscaling is governed by the --concurrency setting (default 80, configurable from 1 to 1000 requests per instance). Unlike Kubernetes Horizontal Pod Autoscaling (HPA) which evaluates CPU or memory thresholds over 15–60 second metrics collection windows, Cloud Run scales instantly on active in-flight request metrics evaluated at the Google Front End (GFE) proxy level:

$$\text{Target Instances} = \left\lceil \frac{\text{Active In-flight Requests}}{\text{Concurrency Target} \times \text{Utilization Factor}} \right\rceil$$

If an application runtime is single-threaded (e.g., standard Python WSGI without gevent/gunicorn greenlets, or Node.js executing CPU-intensive synchronous operations), setting --concurrency=80 leads to severe head-of-line blocking and request timeouts. For single-threaded runtimes, concurrency should be dialed down to 1–10; for asynchronous, non-blocking runtimes (Go, Netty, Node async I/O, ASGI), concurrency of 80–250 yields optimal throughput and cost efficiency.

3. CPU Allocation Policies:

  • CPU allocated only during request processing (CPU idle throttling, default): CPU is throttled down to nearly zero when no requests are being processed. This allows containers to scale to zero cost between requests. However, any background asynchronous thread spawned after returning the HTTP response will be starved of CPU cycles and freeze until the next request arrives.
  • CPU always allocated (--no-cpu-throttling): CPU remains active even when the container is not serving an active HTTP request. Essential for applications that execute background workers, maintain continuous WebSocket connections, poll Pub/Sub topics internally, or run Prometheus metric pull endpoints.

5. Ingress Controls, Authentication, and Custom Domains:

  • Ingress Controls: Cloud Run supports three ingress levels: all (publicly accessible from the internet), internal (accessible only from within the same VPC network, VPC Service Controls perimeters, or via Private Service Connect), and internal-and-cloud-load-balancing (accessible only through an External or Internal Application Load Balancer, blocking direct access to the default *.a.run.app URL).
  • Authentication & Invoker Permissions: By default, private Cloud Run services enforce IAM authentication. Callers must possess the roles/run.invoker IAM role and present an OpenID Connect (OIDC) identity token in the Authorization: Bearer $(gcloud auth print-identity-token) HTTP header. The Google Front End validates that the token was signed by Google and that the token's aud (audience) claim matches the Cloud Run service URL before forwarding the request to the container.
  • Custom Domains: Custom domains can be mapped directly to Cloud Run services using Google-managed Let's Encrypt certificates, or exposed through an HTTPS External Application Load Balancer with Serverless Network Endpoint Groups (Serverless NEGs) to enable Cloud Armor WAF security rules and Cloud CDN caching.

Cloud Run Functions: Eventarc Triggers, Generation Comparison, and Cold-Start Mitigation

Cloud Run functions represent the convergence of Google Cloud Functions into a unified serverless container paradigm. Under the Gen 2 architecture, every deployed function is compiled into an OCI container via Cloud Native Buildpacks and deployed as an idiomatic Cloud Run service managed by the Eventarc event router.

1. Architectural Transition: Gen 1 vs. Gen 2:

In Gen 1, functions executed in rigid, proprietary language sandboxes running on legacy App Engine infrastructure. Concurrency was strictly limited to 1 request per instance, execution timeout was capped at 9 minutes, and egress was constrained to Serverless VPC Access connector VM pools. In Gen 2, functions run directly on the standard Cloud Run compute engine inside gVisor sandboxes. This unlocks up to 60 minutes execution timeout, multi-concurrency (up to 1,000 parallel requests/events per container), Direct VPC egress, traffic splitting across revisions, and instance sizing up to 8 vCPUs and 32 GiB RAM.

2. Eventarc Event Routing & CloudEvents Specification:

Eventarc serves as the central event router for Google Cloud serverless architectures, standardizing asynchronous events from over 90 Google Cloud services into the industry-standard CloudEvents v1.0 specification. Whether an event originates from Cloud Storage object creation, Cloud Pub/Sub message publication, or Cloud Audit Logs capturing an administrative API call, Eventarc wraps the event payload into a uniform JSON structure:

{
  "specversion": "1.0",
  "id": "78129038-a12b-45cf-810a-e248b9912091",
  "source": "//storage.googleapis.com/projects/_/buckets/brightloaf-invoices",
  "type": "google.cloud.storage.object.v1.finalized",
  "datacontenttype": "application/json",
  "time": "2026-09-27T10:14:22.450Z",
  "data": {
    "bucket": "brightloaf-invoices",
    "name": "invoices/2026/09/INV-99120.pdf",
    "size": "245192",
    "metageneration": "1"
  }
}

Eventarc delivers the event via an HTTP POST request to the Cloud Run function endpoint, authenticated using a Google-managed service account OIDC identity token with the roles/run.invoker IAM role.

3. Cold Starts and Mitigation Strategies:

When a serverless function scales from zero instances, the initial request experiences a cold start consisting of container scheduling, image layer pulling, language runtime initialization (e.g. JVM class loading or Python module importing), and application bootstrap (e.g. establishing database connection pools). Google Cloud provides two primary architectural controls to eliminate or drastically reduce cold starts:

  • Minimum Instances (--min-instances): Keeps one or more container instances permanently warm and ready to serve requests immediately. While min-instances incurs continuous compute charges (or idle throttled CPU charges), it guarantees 0ms cold-start latency for baseline production traffic.
  • Startup CPU Boost (--cpu-boost): Temporarily allocates additional vCPU power (typically doubling the configured vCPU allocation) exclusively during the container startup phase. Once the container passes its initial health check and begins serving traffic, CPU allocation returns to its configured baseline, reducing cold start duration by 50% to 70% at zero additional cost.

4. Distributed Idempotency and At-Least-Once Delivery Guarantees:

Asynchronous event buses such as Cloud Pub/Sub and Eventarc guarantee at-least-once delivery. In cases of transient network partitions, downstream database timeouts, or container crashes, the messaging subsystem redelivers the event. To prevent duplicate business state modifications (such as charging a customer credit card twice or double-deducting inventory):

  1. The function extracts the unique event.id attribute from the CloudEvent envelope.
  2. The function executes an atomic check-and-set operation in a low-latency shared datastore (such as Memorystore Redis via Direct VPC Egress): SET order_event:{event.id} "PROCESSING" NX EX 3600.
  3. If the key already exists (return code null / false), the function detects a duplicate redelivery, logs the collision, and immediately returns HTTP 200 to acknowledge the message and terminate further retries.
  4. If the key is newly created, the function proceeds with business logic execution. Upon successful completion, it updates the key status to COMPLETED. In case of unexpected runtime failure, it deletes the key to allow legitimate retries, or relies on an Eventarc Dead-Letter Topic (DLT) after 5 consecutive failures.

Part 3 · Real-world problem and solution for each topic

Cloud Run Concurrency Saturation and Async Thread Starvation · field case

Situation and impact: Brightloaf launched a promotional campaign offering free artisan pastries, driving 8,500 checkout webhook requests per minute to the Cloud Run order-checkout-api service. Within 3 minutes, customers experienced spinning checkout screens and HTTP 504 Gateway Timeout errors, resulting in over 4,200 dropped transactions and an estimated $64,000 in lost revenue.

Constraints: Must not exceed a maximum cloud budget ceiling of $300/month for the service; must integrate securely with private Cloud SQL via VPC; and must complete order tokenization within a strict 3-second SLA.

Diagnosis and solution: Cloud Monitoring metrics revealed that the service was deployed with default concurrency (80) and default CPU allocation (throttled when not actively processing an HTTP request). However, the application code was written in Python Flask using standard synchronous workers, which can only process one request at a time per OS process thread. When 80 concurrent requests arrived at a single container, 79 requests queued waiting for the single worker thread to release, quickly hitting the 60-second request timeout. Furthermore, the code attempted to dispatch asynchronous telemetry events in background daemon threads after returning the HTTP 200 response; because the CPU was instantly throttled down to 0% upon response completion, the background threads froze indefinitely. The resolution required setting --concurrency=10, configuring --no-cpu-throttling (CPU always allocated), and establishing --min-instances=3 with Direct VPC egress.

Alternative and residual risk: Setting --no-cpu-throttling prevents scaling down compute cores to zero billing cost during complete idle periods. Platform teams should use scheduled Cloud Scheduler jobs to lower min-instances to 0 outside business hours to conserve budget.

Cloud Run Function Duplicate Invoice Generation and Redelivery Loop · field case

Situation and impact: Brightloaf runs a Cloud Run function triggered by Cloud Storage object finalization events to process digital customer invoice PDFs and dispatch automated payment receipts. During an overnight batch export of 12,000 PDF invoices, a transient database connection timeout caused the function container to crash after 55 seconds. Pub/Sub's at-least-once delivery mechanism immediately redelivered the event messages, but because the function lacked deduplication logic, it regenerated duplicate invoices and charged customers credit cards twice, prompting over 800 bank dispute claims and $140,000 in disputed funds.

Constraints: Must preserve guaranteed event delivery; cannot lose invoice events if a database node fails; and must execute within existing serverless function infrastructure without deploying full VM clusters.

Diagnosis and solution: Examination of Cloud Logging showed identical event.id identifiers logged multiple times across redelivered execution attempts. Because the function was operating without an atomic deduplication store, each redelivery executed the full invoice dispatch flow from the beginning. The resolution required upgrading the function to Gen 2 on Cloud Run, binding an Eventarc trigger with an explicit dead-letter topic (DLT) after 5 failed delivery attempts, and introducing an atomic idempotency check in Memorystore Redis using the CloudEvent ID before initiating external billing transactions.

Alternative and residual risk: Relying on Redis for idempotency introduces a dependency on Redis availability. If Redis experiences a node failover, the function should fail closed and allow Pub/Sub to retry rather than executing without idempotency guarantees.

Exercise 2: Event-Driven Cloud Run Function with Idempotency Guard and Exit Artifact Assembly

Mode: Python code authoring & evidence generation · Prerequisite: Exercise 1.

  1. Author Idempotent Cloud Run Function Code. Create main.py illustrating the atomic Redis deduplication guard: 
    cat <<'EOF' > main.py
import functions_framework
import json
import os
import redis
from cloudevents.http import CloudEvent

# Connect to private Memorystore Redis via Direct VPC Egress
r = redis.Redis(host=os.getenv('REDIS_HOST', '10.128.0.100'), port=6379, db=0)

@functions_framework.cloud_event
def process_invoice(cloud_event: CloudEvent):
    event_id = cloud_event["id"]
    data = cloud_event.data
    
    # Atomic Check-And-Set Idempotency Key (1 hour expiry)
    dedup_key = f"processed_event:{event_id}"
    is_new = r.set(dedup_key, "IN_PROGRESS", nx=True, ex=3600)
    
    if not is_new:
        print(f"DUPLICATE DETECTED: Event {event_id} already processed. Acknowledging to avoid redelivery.")
        return ("Duplicate event skipped", 200)
    
    try:
        # Process order invoice
        order_id = data.get("order_id", "UNKNOWN")
        print(f"PROCESSING: Generating invoice for order {order_id} (Event: {event_id})")
        
        # Mark as completed
        r.set(dedup_key, "COMPLETED", ex=86400)
        return ("Invoice processed successfully", 200)
    except Exception as e:
        # Delete key on failure to allow clean retry
        r.delete(dedup_key)
        print(f"ERROR: Failed processing event {event_id}: {str(e)}")
        raise e
EOF
