Load balancer taxonomy: global vs regional, external vs internal, proxy vs passthrough, L4 vs L7

Google Cloud delivers a comprehensive spectrum of software-defined load balancing options categorized across four fundamental architectural axes: Scope (Global Anycast vs Regional), Ingress point (External public IPv4/IPv6 vs Internal RFC 1918), Processing layer (Layer 4 transport vs Layer 7 application awareness), and Architecture (Proxy connection termination vs Maglev Direct Server Return passthrough). Selecting the correct architectural permutation governs client latency, TLS offloading, high-availability multi-region failover, compliance boundaries, and backend protocol preservation.

When an engineer provisions an Application Load Balancer to terminate high-frequency UDP telemetry from warehouse automated guided vehicles, every datagram is silently discarded because Layer 7 proxies only accept HTTP/gRPC traffic. The autonomous vehicle fleet enters emergency safety stops across the sorting depot, halting pallet distribution for eight hours and stranding $1.2 million in scheduled freight shipments.

Regional external and internal Application Load Balancers

When legal compliance and data residency regulations mandate that TLS termination and packet inspection must never cross a sovereign geographic border, Regional external Application Load Balancers deploy managed Envoy proxies strictly within that region. For microservice-to-microservice east-west traffic inside a VPC or across cross-project Shared VPCs, Internal Application Load Balancers deliver Layer 7 URL routing, canary traffic splitting, and zero-trust Private Service Connect endpoints, powered by a dedicated regional proxy-only subnet.

External and internal proxy Network Load Balancers (TCP/SSL proxy)

Load balancer taxonomy: global vs regional, external vs internal, proxy vs passthrough, L4 vs L7

Architecting production load balancing in Google Cloud requires evaluating four independent, orthogonal architectural axes:

The Four Architectural Axes

  1. Scope (Global vs Regional):
    • Global Load Balancers: Utilize a single Anycast IPv4 and IPv6 virtual IP (VIP) advertised globally via Border Gateway Protocol (BGP) from all Google edge points of presence (PoPs). Client TCP/TLS connections terminate at the closest edge PoP to minimize latency. Traffic traverses Google's private global fiber network to backends in any region. When backends in the local region reach capacity or fail health checks, Google Front Ends (GFEs) automatically spill traffic over to healthy backends in secondary regions with zero DNS change.
    • Regional Load Balancers: The VIP is bound to a single Google Cloud region. Traffic enters Google's network in that region and is distributed only to backends residing within that same region. Regional load balancers are required for strict data sovereignty compliance (such as GDPR Article 44–50, German BaFin, or Swiss FINMA banking regulations) where TLS keys, plaintext application payloads, and inspection logs must remain physically within a sovereign jurisdiction.
  2. Ingress Point (External vs Internal):
    • External Load Balancers: Publicly reachable across the internet via globally or regionally routable public IP addresses. Protected against layer 3/4 volumetric floods by Google's global DDoS infrastructure and optionally shielded by Google Cloud Armor WAF at Layer 7.
    • Internal Load Balancers: Accessible only from within your private Virtual Private Cloud (VPC) networks, peered VPCs, or connected on-premises hybrid networks (via Cloud Interconnect or HA VPN) through private RFC 1918/RFC 6598 IP addresses.
  3. Processing Layer (Layer 4 vs Layer 7):
    • Layer 4 Transport: Routes traffic based solely on IP 5-tuples (Source IP, Source Port, Destination IP, Destination Port, Protocol: TCP/UDP/ESP/ICMP/GRE). Fast, lightweight, and protocol-agnostic.
    • Layer 7 Application: Terminates HTTP/1.1, HTTP/2, HTTP/3 (QUIC), and gRPC sessions. Inspects host headers, URL request paths, HTTP methods, cookies, and custom headers to execute intelligent content-based routing, URL rewriting, redirects, and header manipulation.
  4. Architecture (Proxy vs Passthrough):
    • Proxy Architecture (Envoy / GFE): The load balancer terminates the client connection (Socket 1: Client to Proxy) and establishes a separate, independent connection to the backend (Socket 2: Proxy to Backend). Enables TLS termination, HTTP header inspection, compression, and request routing, but masks the client's source IP address from backend network sockets.
    • Passthrough Architecture (Maglev): The load balancer does not terminate the connection. Google's distributed software router (Maglev) forwards raw IP packets directly to backend VM interfaces. Backends terminate the TCP or UDP socket directly and respond directly to the client via Direct Server Return (DSR), bypassing the load balancer on the return path.

Direct Server Return (DSR) vs. Dual-Connection Socket Model

Understanding the low-level socket and packet lifecycle differences between passthrough and proxy load balancers is vital for capacity planning and troubleshooting:

  • Passthrough Maglev Flow (Direct Server Return):
    1. The client initiates a TCP handshake (SYN) to the load balancer VIP.
    2. Maglev receives the packet, computes a consistent hash on the 5-tuple, and encapsulates the packet in a Geneve/GRE tunnel inside the Andromeda virtual network fabric.
    3. The packet arrives at the backend VM's eth0 interface without modifying the destination IP (which remains the VIP). A local route or kernel loopback alias directs the packet to the local application socket.
    4. The backend application accepts the connection. When sending the SYN-ACK response, the VM kernel crafts the packet with Source IP = VIP and Destination IP = Client IP.
    5. The return packet exits the VM directly through the VPC's default internet gateway (or Cloud NAT) and travels over the public internet back to the client. The return path completely bypasses Maglev! This asymmetric routing delivers massive egress throughput at line rate with near-zero latency overhead.
  • Proxy Dual-Socket Flow (GFE / Envoy):
    1. The client sends a SYN to the load balancer VIP. The GFE or regional Envoy terminates the TCP connection and completes the TLS handshake.
    2. The proxy buffers and parses the HTTP request headers or TCP stream.
    3. The proxy selects a backend instance based on the URL map, capacity limits, and health checks.
    4. The proxy initiates a second TCP handshake to the backend VM's internal IP address, drawing a source IP from Google Front End IP pools (for global ALB) or the dedicated Proxy-Only Subnet (for regional ALB).
    5. The backend sees the proxy's IP as the remote socket address. The original client IP is transmitted via the X-Forwarded-For HTTP header or the binary PROXY protocol v2 header.
    6. Response packets must travel back to the proxy, which forwards them over the client socket. The load balancer must handle both ingress and egress bandwidth.

The Regional Proxy-Only Subnet Mandate

Regional external ALBs, Regional internal ALBs, and Regional internal proxy NLBs are powered by managed Envoy proxy fleets running within the region. These Envoy instances require a dedicated Proxy-Only Subnet within the VPC:

gcloud compute networks subnets create proxy-only-us-east4   --purpose=REGIONAL_MANAGED_PROXY   --role=ACTIVE   --region=us-east4   --network=prod-shared-vpc   --range=10.10.99.0/24
  • Subnet Sizing: Google Cloud mandates a minimum subnet prefix of /26 (64 addresses, 60 usable) and strongly recommends /24 (256 addresses, 252 usable) or /23 for production environments. Each active Envoy proxy instance consumes internal IP addresses from this pool. As traffic scales up, Google Cloud automatically provisions additional Envoy instances. If the proxy subnet runs out of IP addresses, autoscaling fails, new connections are dropped, and existing connections suffer socket exhaustion.
  • Subnet Immutability: Once created, a proxy-only subnet cannot be expanded or edited in-place. If an undersized proxy subnet exhausts its IPs, an architect must create a second proxy-only subnet in the same region with --role=ACTIVE. Google Cloud will automatically demote the existing subnet to --role=BACKUP and gracefully migrate Envoy instances without dropping connections.
  • Subnet Scope and Isolation: Exactly one active proxy-only subnet can exist per VPC network per region. This subnet cannot be used for standard Compute Engine VMs, GKE Pods, Cloud SQL instances, or PSC endpoints.
  • Firewall Ingress Mandate: Workload subnets hosting backend instances or GKE pods must have an ingress firewall rule explicitly permitting traffic from the proxy-only subnet CIDR range on the application listening port.

Global external Application Load Balancer (HTTP/S): URL maps, backend services, backend buckets, host and path rules

The Global external Application Load Balancer provides Layer 7 reverse proxying and content-based routing at planetary scale.

End-to-End Packet and Control Flow

  1. Client Ingress to Anycast VIP: The client issues an HTTPS request. BGP Anycast routes the TCP handshake to the nearest Google edge PoP among hundreds distributed worldwide.
  2. Global Forwarding Rule: Matches incoming packets on the VIP and specified port (TCP 80 or 443) and directs them to a Target HTTP(S) Proxy.
  3. Target HTTPS Proxy:
    • Terminates the TLS connection using one or more Google-managed or self-managed SSL certificates (bound via Certificate Manager or SSL Certificate resources).
    • Enforces an SSL Policy defining minimum TLS version (TLS 1.0, 1.1, 1.2, or 1.3) and cryptographic cipher profile (COMPATIBLE, MODERN, RESTRICTED, or CUSTOM).
    • Negotiates HTTP/2 or HTTP/3 (QUIC) over UDP port 443.
    • Forwards the decrypted HTTP request object to a URL Map.
  4. URL Map Routing Engine: Evaluates host headers and URL paths, matching request criteria to route traffic to specific Backend Services or Backend Buckets.
  5. Backend Service: Manages session affinity, connection draining, outlier detection, and traffic balancing algorithms across backend instance groups or NEGs.

URL Map Anatomy and Advanced Traffic Management

URL Maps are declarative routing engines capable of sophisticated traffic manipulation:

  • Host Rules: Inspect the HTTP Host request header (e.g. api.brightloaf.com vs cdn.brightloaf.com). Host rules map specific domains or wildcards (*.brightloaf.com) to a Path Matcher.
  • Path Matchers and Path Rules: Match the request URI path against literal patterns or wildcard suffixes:
    • Exact match: /api/v1/checkout/express
    • Prefix match: /api/v1/orders/*
    • Catch-all default service: Handles any request that fails to match explicit path rules.
  • Path Rule Precedence: URL Maps evaluate rules in a deterministic order: exact matches take precedence over prefix matches, and longer prefix matches take precedence over shorter prefix matches. However, unanchored patterns (e.g., /api* vs /api/*) can lead to accidental shadowing of subpaths.
  • URL Rewriting and Redirects: Automatically rewrite path prefixes (pathPrefixRewrite: "/v2/orders") or issue HTTP 301/302 redirects (e.g., redirecting all HTTP port 80 traffic to HTTPS port 443 with httpsRedirect: true).
  • Header-Based and Cookie-Based Routing: Route requests to specialized backends based on custom headers (e.g. X-Client-Tier: Enterprise) or session cookies.
  • Weighted Traffic Splitting (Canary Deployments): Allocate percentage weights across multiple backend services (e.g., 95% to orders-v1-stable and 5% to orders-v2-canary) with optional header-based session pinning.

Backend Services: Instance Groups vs. Network Endpoint Groups (NEGs)

Backend services dispatch traffic to heterogeneous endpoint collections:

  • Managed Instance Groups (MIGs): Pools of Compute Engine VMs. Traffic balances to VM eth0 interfaces. Requires containerized applications to rely on host port mapping or VM-level orchestration.
  • Zonal Network Endpoint Groups (Zonal NEGs): Contain IP:Port pairs for individual GKE Pods. Enables container-native load balancing:
    • GFE/Envoy routes packets directly to Pod IPs, bypassing kube-proxy and iptables NAT on the GKE worker node.
    • Eliminates double-hopping (where a node receives a packet and routes it across the node network to a pod on a different node).
    • Significantly reduces network latency, preserves pod-level health signals, and ensures optimal load distribution.
  • Serverless NEGs: Point to serverless Google Cloud runtimes (Cloud Run services, Cloud Functions, App Engine). Enables placing Cloud Armor WAF and custom domain SSL certificates in front of Cloud Run.
  • Hybrid NEGs: Target on-premises or third-party cloud IP addresses reachable over Cloud Interconnect or HA VPN, allowing the global ALB to act as an external reverse proxy for legacy data centers.
  • Private Service Connect (PSC) NEGs: Target producer services published in other VPC networks or by third-party SaaS vendors without requiring VPC peering.

Balancing Modes and Capacity Scaling

Google Cloud ALBs use sophisticated capacity-based balancing algorithms:

  • RATE Balancing Mode: Defines the maximum requests per second (RPS) an instance or endpoint can handle (maxRatePerInstance or maxRatePerEndpoint). Ideal for I/O-bound microservices.
  • UTILIZATION Balancing Mode: Defines a target average backend CPU utilization (e.g. maxUtilization = 0.80). Ideal for CPU-intensive computing workloads.
  • Capacity Scaler: An adjustable multiplier (0.0 to 1.0) applied to an entire backend group. Setting the capacity scaler to 0.0 gracefully drains traffic from an instance group without deleting it or marking it unhealthy.

Backend Buckets and Cloud CDN Integration

When static assets (images, CSS, JavaScript, compiled media) are stored in Google Cloud Storage, a Backend Bucket routes requests directly from the URL map to the GCS bucket. Enabling Cloud CDN on the backend bucket caches static assets at all edge PoPs worldwide, reducing latency to single-digit milliseconds and dramatically lowering Cloud Storage egress charges.

Regional external and internal Application Load Balancers

When enterprise regulations demand strict regional isolation or internal VPC microsegmentation, regional Application Load Balancers deploy Envoy proxies directly into the designated region.

Regional External Application Load Balancer Architecture

Regional external ALBs are purpose-built for workloads subject to stringent regulatory mandates:

  • Data Sovereignty and Jurisdictional Compliance: Many financial, healthcare, and governmental bodies (e.g. European Banking Authority, GDPR, German C5) require that cryptographic keys, TLS decryption, Layer 7 packet inspection, and web application firewall evaluation occur strictly within a designated geographic jurisdiction. Because Global ALBs terminate TLS at the nearest global GFE PoP (which might be outside the sovereign jurisdiction), Regional External ALBs ensure that TLS termination and proxying occur strictly inside the selected Google Cloud region.
  • Regional DDoS Fault Domain Isolation: By binding the load balancer to a single region, regional operational incidents or network anomalies cannot cascade across global infrastructure.

Regional Internal Application Load Balancer (Internal ALB) Architecture

Internal ALBs serve as private, secure ingress points for internal enterprise applications:

  • Private East-West Microservices Ingress: Modern microservice architectures require Layer 7 features—such as content-based path routing, gRPC load balancing, and header-based canary deployments—without exposing endpoints to the public internet. Internal ALBs provide these capabilities using private RFC 1918 IP addresses.
  • Shared VPC Integration: In enterprise hub-and-spoke topologies, the Internal ALB forwarding rule and proxy-only subnet can reside in the Shared VPC Host Project, while backend services point to Zonal NEGs or MIGs running in various Service Projects.
  • Private Service Connect (PSC) Consumer Integration: Workloads in consumer VPCs or remote on-premises networks can access an Internal ALB through a PSC endpoint (forwarding rule with private IP). This enables multi-tenant service consumption without the IP address overlapping conflicts or transitive routing limitations of VPC Network Peering.

Proxy-Only Subnet Lifecycle and Capacity Management

Because regional Envoy proxies execute inside the VPC data plane, managing the proxy-only subnet is a critical operational task:

  • Address Consumption Dynamics: Each Envoy proxy instance consumes one internal IP address from the proxy-only subnet for its management interface and additional IPs for backend connections. The number of Envoy instances autoscales based on active connections, new connection rate, and bandwidth.
  • Capacity Planning Formula: Plan for at least 1 Envoy instance per 1,000 active connections or 100 new connections per second. For high-volume production microservices, a /24 subnet (252 usable IPs) provides ample headroom for thousands of concurrent proxy instances and seamless rolling upgrades.
  • Monitoring Proxy Subnet IP Exhaustion: Monitor the Cloud Monitoring metric loadbalancing.googleapis.com/subnet/proxy/allocated_ip_addresses. Alerting should trigger when allocation exceeds 70% of available subnet IPs.

External and internal proxy Network Load Balancers (TCP/SSL proxy)

When applications use non-HTTP protocols that still require reverse proxy benefits (such as global Anycast IP access, centralized SSL certificate management, and health checks), Proxy Network Load Balancers provide the optimal architectural solution.

Architectural Scope and Enterprise Workloads

Proxy Network Load Balancers bridge the gap between Layer 7 HTTP proxies and raw Layer 4 passthrough routers:

  • Target Workloads: MQTT IoT brokers (port 8883), PostgreSQL and MySQL database proxies (e.g. PgBouncer on port 5432, ProxySQL on port 3306), Redis cache clusters (port 6379), multiplayer gaming session daemons, financial FIX protocol streams, and proprietary binary RPC services.
  • Centralized TLS/SSL Offload: SSL Proxy NLBs terminate client SSL/TLS handshakes at Google edge GFEs, decrypt the payload, and forward plaintext TCP (or re-encrypted TLS) to backend VMs. This offloads cryptographic CPU overhead from application servers and centralizes SSL certificate renewal via Certificate Manager.
  • Global vs Regional Proxy NLB:
    • Global External Proxy NLB: Anycast VIP advertised globally; terminates TCP/SSL at the edge GFE PoP and uses Google's backbone to reach backends in multiple regions.
    • Regional External / Internal Proxy NLB: Regional VIP terminated by managed Envoy proxy instances inside the VPC; requires a dedicated REGIONAL_MANAGED_PROXY proxy-only subnet.

Preserving Client Identity with PROXY Protocol (v1 vs v2)

Because a proxy load balancer terminates the client TCP connection and opens a separate TCP connection to the backend, the backend operating system kernel records the proxy's IP address (a GFE IP or a proxy-only subnet IP) as the remote socket address. This breaks IP-based geolocation, security audit logging, and fraud detection algorithms.

To preserve original client IP metadata across the proxy boundary, Proxy NLBs support the PROXY protocol:

  • PROXY Protocol v1 (Human-Readable ASCII): Prepends an ASCII string to the start of the TCP connection immediately after the handshake completes: 
    PROXY TCP4 198.51.100.22 34.120.55.10 54321 8883\r\n
    Easy to read and debug, but incurs higher string-parsing overhead on backend socket listeners.
  • PROXY Protocol v2 (Compact Binary): Prepends a standardized 16-byte binary structure containing a magic signature (\x0D\x0A\x0D\x0A\x00\x0D\x0A\x51\x55\x49\x54\x0A), protocol version, address family (IPv4 vs IPv6), source IP, destination IP, source port, and destination port, followed by optional Type-Length-Value (TLV) extension fields. High performance and negligible bandwidth overhead.
  • Backend Software Configuration Mandate: The backend software (e.g., NGINX stream module, HAProxy, Envoy, Netty, or custom daemon) MUST be explicitly configured to decode the PROXY protocol header before reading application data: 
    # Backend Service configuration in Google Cloud
gcloud compute backend-services update db-proxy-backend   --global   --proxy-header=PROXY_V2

    Critical Operational Warning: If PROXY protocol is enabled on the Google Cloud backend service but the backend software is not configured to decode it, the backend application will interpret the PROXY binary header as corrupted application payload, dropping connections immediately!

Selecting Incompatible Load Balancer for Raw Non-HTTP Workload · field case

Situation and impact: Brightloaf's warehouse operations team deployed an automated guided vehicle (AGV) tracking fleet in us-central1. The AGV robots communicate using a custom high-frequency UDP telemetry stream on port 9000. An infrastructure engineer provisioned an External Application Load Balancer (ALB) to terminate the traffic. When the AGV robots initiated broadcasts, zero telemetry packets reached backend servers. The AGVs entered safety lockouts, shutting down the automated pallet loading dock for 8 hours and delaying $1.2 million in scheduled freight shipments.

Constraints: AGV hardware firmware strictly supports UDP broadcasts; cannot modify vehicle firmware to use HTTP/REST or WebSockets; must provide high availability across multiple backend VM instances; client source IP must be preserved natively for robot spatial tracking.

Diagnostic sequence: 1. Inspect Load Balancer Configuration: Executed CLI inspection on the active forwarding rule: 

gcloud compute forwarding-rules describe agv-telemetry-fwd-rule   --region=us-central1   --format="yaml(IPProtocol,loadBalancingScheme,target)"
Observed IPProtocol: TCP and target: .../targetHttpProxies/.... 2. Packet Capture on Backend VM: Captured network interfaces on the telemetry server pool: 
sudo tcpdump -nn -i eth0 udp port 9000
Result: Exactly zero UDP packets arrived at the backend VM network interface. 3. Edge Metric Inspection: Queried Cloud Monitoring metrics for the external ALB. Observed that GFE edge proxies logged zero successful HTTP requests and generated elevated TCP connection reset errors for incoming non-HTTP handshakes.

Root cause: The incident was caused by selecting an Application Load Balancer (ALB) for a UDP workload. Application Load Balancers operate strictly at Layer 7 and only accept HTTP, HTTPS, HTTP/2, and gRPC traffic. Furthermore, Proxy Network Load Balancers only support TCP. The correct architectural selection was a Regional External Passthrough Network Load Balancer. Passthrough NLB operates directly on Google's Maglev distributed forwarding layer, supporting raw UDP and TCP traffic with native client IP preservation and Direct Server Return (DSR).

Defensible remediation: 1. Deleted the incompatible ALB forwarding rule and target proxy. 2. Created a regional health check supporting the telemetry application. 3. Created a regional backend service with protocol UDP and balancing scheme EXTERNAL. 4. Created a Regional External Passthrough NLB forwarding rule listening on UDP port 9000: 

gcloud compute forwarding-rules create agv-telemetry-nlb-rule   --region=us-central1   --load-balancing-scheme=EXTERNAL   --backend-service=agv-udp-backend-svc   --ip-protocol=UDP   --ports=9000
Once applied, all AGVs re-established communication instantly and warehouse operations resumed.

Alternative and residual risk: Passthrough NLB does not terminate TLS or decrypt traffic. If TLS is required for UDP (DTLS), encryption must terminate directly on backend VM software. Backend firewalls must explicitly permit UDP port 9000 from client ranges.

URL Map Path Rule Ordering Causing Critical Blackhole · field case

Situation and impact: Brightloaf pushed an update to their Global external ALB to route new mobile checkout endpoints (/api/v1/checkout/express). Immediately after deploying the updated URL map, all mobile checkout requests returned HTTP 404 Not Found. Over 14,000 customers abandoned their shopping carts during the flash promo, resulting in a loss of $310,000 in revenue.

Constraints: Must maintain a single Anycast frontend IP for both legacy API and express checkout; cannot redeploy application containers or change client API paths.

Diagnostic sequence: 1. Query Cloud Logging for HTTP 404 Errors: 

gcloud logging read 'resource.type="http_load_balancer" AND httpRequest.status=404'   --limit=10   --format="json(httpRequest.requestUrl,jsonPayload.statusDetails,jsonPayload.backendTargetProject)"
Result: Logs showed requests to /api/v1/checkout/express routed to legacy-api-backend-svc instead of checkout-backend-svc, with status details response_code_matched_backend. 2. Inspect URL Map Configuration YAML: 
gcloud compute url-maps export web-global-url-map
Observed the pathMatcher structure: 
pathRules:
- paths:
  - "/api*"
  service: projects/prod-net/global/backendServices/legacy-api-backend-svc
- paths:
  - "/api/v1/checkout/*"
  service: projects/prod-net/global/backendServices/checkout-backend-svc

Root cause: In the URL Map, an engineer added the unanchored path pattern /api* (without a trailing slash) above the checkout rule. In URL map path matching, /api* matches any path beginning with the characters /api, including /api/v1/checkout/express. Because this rule appeared first and captured the request prefix, the express checkout traffic was intercepted and forwarded to the legacy backend, which returned HTTP 404.

Defensible remediation: 1. Restructured the URL Map pathMatcher:

  • Defined explicit, unambiguous path rules (/api/v1/checkout/* and /api/v1/checkout/express).
  • Anchored legacy API routes with explicit trailing delimiters (/api/v1/legacy/*).
  • Set the default service of the pathMatcher to api-default-backend.
2. Validated the URL Map configuration using the CLI validation command before production deployment: 
gcloud compute url-maps validate   --url-map=web-global-url-map   --load-balancing-scheme=EXTERNAL_MANAGED
3. Applied the corrected URL map. Mobile checkout transactions completed successfully with HTTP 200 OK.

Alternative and residual risk: Always include automated unit tests in CI/CD pipelines that run URL Map validation against synthetic URL paths before applying changes to production load balancers:

gcloud compute url-maps validate --url-map=web-global-url-map

Internal ALB Dropping Microservice Traffic Due to Exhausted Proxy Subnet · field case

Situation and impact: Brightloaf implemented an Internal Application Load Balancer (ILB) in us-east4 to manage east-west traffic between the frontend gateway and backend inventory pods. During a morning traffic surge, the internal load balancer began dropping 60% of requests with HTTP 503 Service Unavailable. The inventory microservice dashboards showed 0% CPU utilization and all pods were healthy, yet client calls failed with connection timeouts.

Constraints: Must preserve internal Layer 7 routing and path-based canary deployments; cannot expose microservices to external networks.

Diagnostic sequence: 1. Verify Backend Pod Health: Checked GKE inventory pods in us-east4. CPU utilization was at 3%, memory normal, and health checks were passing 100%. 2. Inspect Cloud Logging for ALB Status Details: 

gcloud logging read 'resource.type="http_load_balancer" AND httpRequest.status=503'   --limit=10   --format="yaml(jsonPayload.statusDetails,jsonPayload.responseCodeDetail)"
Result: Status showed failed_to_pick_backend with response code detail envoy_proxy_resource_exhaustion. 3. Inspect Proxy-Only Subnet IP Utilization: 
gcloud compute networks subnets describe proxy-only-east4   --region=us-east4   --format="yaml(ipCidrRange,purpose,role)"
Observed that the proxy-only subnet was provisioned with CIDR 10.10.99.0/28 (only 16 total IP addresses, with only 12 usable host IPs). All 12 IP addresses were fully consumed by active Envoy proxy instances. When connection spikes arrived, Envoy could not autoscale additional proxy replicas, causing incoming client connections to be refused.

Root cause: Undersized /28 proxy-only subnet ran out of IP addresses during the traffic spike. Because Envoy instances could not be provisioned, existing proxies suffered socket starvation and returned HTTP 503 errors.

Defensible remediation: 1. Created a new proxy-only subnet in us-east4 with a /24 CIDR block (256 IP addresses) with active role: 

gcloud compute networks subnets create proxy-only-east4-v2   --purpose=REGIONAL_MANAGED_PROXY   --role=ACTIVE   --region=us-east4   --network=prod-shared-vpc   --range=10.10.100.0/24
The previous subnet automatically transitioned to BACKUP role. 2. Updated the backend firewall rule to permit ingress from the new proxy subnet: 
gcloud compute firewall-rules update allow-internal-alb-east4   --source-ranges=10.10.100.0/24
3. Envoy automatically scaled to 32 instances. Dropped connections ceased immediately and HTTP 503 errors fell to 0.00%.

Alternative and residual risk: Ensure firewall rules on backend VMs allow ingress explicitly from the new /24 proxy-only subnet range, otherwise all connections from newly spawned Envoy proxies will be blocked.

Client IP Masking in TCP Proxy Breaking Fraud Detection · field case

Situation and impact: Brightloaf's security risk engine flags fraudulent account takeovers by analyzing the true geographical origin IP of incoming password reset requests. After migrating their authentication proxy to an External TCP Proxy Load Balancer, the fraud engine logged 100% of incoming connections originating from a single internal Google IP (130.211.0.4). Because all global traffic appeared to originate from one address, rate-limiting algorithms engaged globally, locking 85,000 legitimate users out of their accounts.

Constraints: Workload uses a custom binary TCP authentication handshake; cannot switch to HTTP; fraud engine requires the true public IPv4/IPv6 client IP.

Diagnostic sequence: 1. Inspect Backend Connection Logs: Analyzed incoming socket connections on the auth servers: 

sudo ss -tnp state established '( dport = :9000 )'
Observed that every active connection had a remote peer address within 130.211.0.0/22 or 35.191.0.0/16 (Google Front End edge proxy pools). 2. Inspect Backend Service Configuration: 
gcloud compute backend-services describe auth-tcp-backend   --global   --format="yaml(proxyHeader)"
Observed proxyHeader: NONE. 3. Verify Packet Flow: Confirmed that TCP Proxy terminates the client socket at the edge GFE and establishes a fresh TCP socket to the backend without prepending client metadata.

Root cause: TCP Proxy Load Balancers terminate the client TCP session at Google's edge GFEs. The GFE then establishes a second, independent TCP connection to the backend instances. Consequently, the backend socket sees the GFE's internal proxy IP as the remote address. To restore true client IP visibility without altering the transport layer, PROXY protocol v2 header injection must be enabled on the backend service and parsed by the backend socket application.

Defensible remediation: 1. Updated the backend service configuration to enable PROXY Protocol v2: 

gcloud compute backend-services update auth-tcp-backend   --global   --proxy-header=PROXY_V2
2. Updated the backend authentication server software configuration to enable PROXY protocol v2 decoding on its listening socket: 
# Example NGINX stream block configuration:
# server {
#     listen 9000 proxy_protocol;
#     proxy_pass backend_auth_cluster;
# }
3. Flushed the fraud detection rate limit cache. Authenticated client requests resumed, and fraud logs correctly attributed logins to users' true geographic origin IPs.

Alternative and residual risk: If backend software does not support PROXY protocol v2, enabling it on the backend service will corrupt incoming TCP payloads, causing applications to drop connections immediately. Health check probes will also fail if sent to a PROXY protocol port unless configured with PROXY headers.

Exercise 1: Evaluate and Select Load Balancers Using Architectural Constraints

Goal: Formulate an architectural decision record (ADR) mapping workload constraints to Google Cloud load balancer types across the 4 core axes.

Mode: production practice · Prerequisite: Day 52 exit artifacts.

  1. Review the 4-Axis Decision Framework: 
    # Architectural selection rubric:
# Axis 1 - Scope: Global Anycast (low latency, cross-region failover) vs Regional (data sovereignty)
# Axis 2 - Ingress: External (Public IP, Cloud Armor) vs Internal (RFC 1918, VPC microservices)
# Axis 3 - Layer: Layer 7 (HTTP/S, URL Maps, gRPC) vs Layer 4 (TCP, UDP, ICMP, GRE)
# Axis 4 - Architecture: Proxy (TLS offload, PROXY protocol) vs Passthrough (Maglev, DSR, line-rate)
  2. Formulate Workload Requirements for Brightloaf: Document constraints for:
    • Public Order Web & API: HTTPS, global client base, multi-region failover, URL path routing, Cloud Armor WAF.
    • Warehouse AGV Telemetry: High-throughput UDP port 9000, regional data residency, zero protocol conversion latency.
    • Internal Inventory Microservice: East-west internal RFC 1918 traffic, canary deployments, Private Service Connect.
    • Legacy Database Connection Pool: Non-HTTP TCP port 5432, TLS termination, client IP preservation.
    • Static Media Assets: Global CDN edge caching, Cloud Storage origin, signed URLs.
  3. Calculate Proxy-Only Subnet IP Capacity:

    For each region deploying regional Envoy load balancers, calculate the required proxy subnet prefix based on expected peak concurrency (e.g. 5,000 concurrent RPS requiring at least 16–32 Envoy instances, demanding a minimum /26 or recommended /24 subnet).

  4. Draft the Decision Matrix: Complete the selection ADR comparing Global External ALB with Regional Passthrough NLB and documenting rejected alternatives.
Expected result / acceptance

A completed load balancer selection matrix with clear architectural justification, rejected alternatives, proxy subnet sizing calculations, and operational trade-offs.

Troubleshooting

Ensure you never select an ALB for UDP or non-HTTP protocols, and never select a Passthrough NLB if Cloud Armor Layer 7 WAF inspection or URL path routing is required.

Cleanup and cost

No chargeable cloud resources created for this design evaluation exercise.

Exercise 2: Build and Test a Global External Application Load Balancer

Goal: Deploy a Global external ALB with an HTTP health check, backend service, Zonal NEG, backend bucket, and URL map path routing.

  2. Create Global Backend Service: 
    gcloud compute backend-services create web-backend-svc   --protocol=HTTP   --port-name=http   --health-checks=basic-http-check   --global   --load-balancing-scheme=EXTERNAL_MANAGED   --enable-logging   --logging-sample-rate=1.0
  3. Create Cloud Storage Backend Bucket for Static Assets:

Exercise 4: Configure TCP Proxy Load Balancer with PROXY Protocol v2
