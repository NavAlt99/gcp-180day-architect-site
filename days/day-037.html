1 · Topics of the day

Persistent Disk types (standard, balanced, SSD, extreme), Hyperdisk, Local SSD (ephemeral)

Storage performance shapes application behaviour at least as much as CPU or network. GCP offers a spectrum of block-storage options distinguished by durability, IOPS ceiling, throughput, and cost. At one end, Local SSD delivers the highest IOPS but loses all data when the VM is stopped or migrated. At the other, Persistent Disk Extreme and Hyperdisk Extreme offer very high provisioned IOPS with full zonal durability. Knowing which type fits a given access pattern prevents both under-provisioned storage (throttling) and over-provisioned storage (wasted spend).

For Brightloaf, the Order API's boot disk needs only moderate sequential read performance; the fulfillment worker's write-ahead log needs consistent low-latency writes; the analytics batch needs high sequential throughput. These three workloads land on different disk types.

Problem preview: The Brightloaf fulfillment worker is deployed on a standard pd-standard boot disk. Under sustained write load the disk IOPS ceiling is reached and writes queue, causing the write-ahead log to stall. Acknowledgement latency rises. Business impact: orders are queued rather than confirmed, potentially triggering customer-facing timeouts and retry storms from the Order API.

Zonal vs regional persistent disks

A zonal Persistent Disk is replicated within a single zone's storage infrastructure. A regional Persistent Disk replicates synchronously across two zones in the same region, enabling a failover scenario where a standby VM in the secondary zone can attach the disk without waiting for data replay. The trade-off: regional PDs have higher cost per GB and may have lower maximum IOPS than the equivalent zonal type. They are appropriate when the application requires sub-minute failover RPO and cannot tolerate restoring from snapshot.

Problem preview: A Brightloaf database VM uses a zonal PD in us-central1-a. The zone experiences a brief outage. Recovery requires restoring from the most recent snapshot, which is two hours old. Two hours of order data may be replayed from the fulfillment queue, but the reconciliation process takes the team several hours to verify. Business impact: extended downtime and operator effort that a regional PD with a pre-configured failover VM would have reduced to a zone-failover attach operation.

Startup scripts and metadata server

The Compute Engine metadata server (metadata.google.internal, IP 169.254.169.254) is a link-local HTTP endpoint accessible only from inside the VM. It provides instance identity, project information, custom metadata key-value pairs, and — crucially — a short-lived access token for the instance's attached service account. A startup script is executed by the guest OS on first boot (and on each subsequent boot if configured). It can read metadata values to configure the application without baking secrets or environment-specific values into the image.

Problem preview: A Brightloaf engineer adds a startup script that retrieves a database password from a custom metadata key and writes it to a local config file. An infrastructure auditor later discovers the password was visible in plaintext in the GCP Console's instance metadata tab, accessible to anyone with Compute Viewer rights on the project. Business impact: a sensitive credential is exposed through the metadata API to a wider audience than intended, violating the least-privilege requirement established in Day 25.

2 · Technical discussion of each topic

Persistent Disk types (standard, balanced, SSD, extreme), Hyperdisk, Local SSD (ephemeral)

The durability–performance spectrum

GCP block storage falls into two broad categories: network-attached Persistent Disk (durable, survives VM stop/delete if configured) and Local SSD (physically attached NVMe, ephemeral). Within Persistent Disk, four standard types plus the Hyperdisk family cover the range from lowest-cost to highest-IOPS provisioned storage.

Type Underlying media Max IOPS (read/write) Max throughput Durability Typical use
pd-standard HDD Low (~3,000 read / 3,000 write per disk, varies with size) Moderate sequential Zonal; replicated within zone Boot disks for low-traffic VMs, infrequent-access data
pd-balanced SSD Higher; balanced between cost and performance Good sequential + random Zonal General-purpose VMs, databases with moderate IOPS needs
pd-ssd SSD Higher than balanced; suitable for most production databases High sequential + random Zonal Production databases, high-throughput workloads
pd-extreme SSD Provisioned IOPS up to 120,000 (read and write) High Zonal; available on select machine types Latency-sensitive databases, SAP HANA, very high IOPS
Hyperdisk Balanced SSD (disaggregated) Provisioned; adjustable without re-creating disk Provisioned throughput Zonal or regional Workloads needing on-demand IOPS/throughput adjustment
Hyperdisk Extreme SSD (disaggregated) Up to 350,000 IOPS provisioned Very high Zonal; select machine types only Highest-performance databases, analytics
Hyperdisk Throughput HDD (disaggregated) Lower IOPS; high sequential throughput Provisioned; up to 2,400 MB/s Zonal Big-data streaming, Kafka, log aggregation
Local SSD NVMe, physically attached Very high; typically 680,000+ IOPS per disk Very high Ephemeral — lost on VM stop, live migrate, or preemption Caches, temp files, scratch space, high-performance computing scratch

IOPS and throughput limits: disk vs VM

IOPS and throughput are bounded by both the disk type's per-disk limits and the machine type's per-VM storage performance limit. A large pd-ssd may support higher IOPS than a small e2 VM can actually drive. Always check both limits when sizing. For Persistent Disk, IOPS generally scales with disk size up to the type's maximum.

Hyperdisk vs Persistent Disk: the key difference

Classic Persistent Disk IOPS and throughput are coupled to disk size — you provision more capacity to get more performance. Hyperdisk decouples storage capacity from performance: you independently specify the IOPS and throughput you need. You can also resize IOPS and throughput without recreating the disk (subject to limits). This is valuable when a workload's performance requirements are known in advance and differ from what disk-size-coupled scaling would deliver.

Local SSD: the ephemeral guarantee

Local SSD is physically attached to the host machine. Data on Local SSD is lost when the VM is:

  • Stopped (not just restarted).
  • Live-migrated to a different host (Google maintenance).
  • Preempted (if a Spot VM).
  • Terminated due to a host error.
Local SSD data survives a guest OS reboot (while the VM keeps running on the same host). Using Local SSD for anything other than a cache or scratch space requires a checkpoint/reload mechanism on every start or migration.

Zonal vs regional persistent disks

Replication model

A zonal Persistent Disk stores its data across multiple physical storage nodes within a single zone's infrastructure. This provides durability against individual storage-node failure but does not protect against a full zone outage. Zonal PDs are by far the most common choice.

A regional Persistent Disk (regional PD) synchronously replicates data across two zones in the same region. Each write is confirmed only after both zones acknowledge it. If one zone becomes unavailable, a standby VM in the secondary zone can attach the disk and continue operations with near-zero data loss (RPO ≈ 0 for confirmed writes). The failover is not automatic — the operator or an orchestration system must force-attach the disk to the standby VM.

Comparison

Dimension Zonal PD Regional PD
Replication Within one zone Across two zones in one region
Zone-outage RPO Restore from snapshot (RPO = age of last snapshot) Near zero (confirmed writes replicated synchronously)
Zone-outage RTO Time to restore snapshot + verify data Time to force-attach to standby VM (minutes with runbook)
Cost Standard rate Higher (approx. 2× storage cost for the replicated data)
IOPS / throughput limit Full type limit May be lower for some types; verify in documentation
Attachment One VM at a time (read-write); multiple VMs (read-only) One VM at a time per zone; force-attach during failover
Typical use Most workloads; pair with snapshots for backup Stateful services with zone-failover SLA; database primaries

Force-attach and the failover procedure

To use a regional PD for failover: (1) pre-provision a standby VM in the secondary zone; (2) when the primary zone fails, force-detach the disk from the (unreachable) primary VM using the GCP API; (3) attach it to the standby VM. The --disk-scope=regional flag and the force-attach capability are required. This procedure must be documented and tested before a real failure.

Startup scripts and metadata server

The metadata server

Every Compute Engine VM can reach the metadata server at http://metadata.google.internal/computeMetadata/v1/ (or http://169.254.169.254/computeMetadata/v1/). Requests must include the header Metadata-Flavor: Google; requests without this header are rejected to prevent SSRF-induced metadata leakage from applications that blindly proxy URLs.

Key metadata paths

Path Returns Security note
instance/name VM instance name Safe; no secrets
instance/zone Zone identifier (full resource path) Safe
instance/service-accounts/default/token Short-lived OAuth 2.0 access token for the attached service account Treat as a secret; do not log or expose
instance/service-accounts/default/scopes OAuth scopes granted to the service account at VM creation Safe; describes capabilities only
project/project-id GCP project ID Safe
instance/attributes/KEY Custom key-value set at VM creation or via the API Not secret: visible to any principal with Compute Viewer on the project; do not store secrets here
project/attributes/KEY Project-level custom key-value Same as instance attributes — visible to project viewers; not a secrets store

Startup scripts

A startup script is set via the startup-script metadata key (for inline scripts) or startup-script-url (for a GCS URL). The guest OS agent runs it as root on first boot and on each subsequent boot unless the metadata is removed. Common uses:

  • Install packages from a private repository whose URL is stored in metadata.
  • Pull the latest application version from Cloud Storage.
  • Read the instance's zone and set a local environment variable for configuration.
  • Register the instance with a service registry.

Secrets in startup scripts: the anti-pattern

A startup script should never read a secret from instance or project attributes. Those attributes are visible to any principal with roles/compute.viewer. Instead, the startup script should use the service account token from the metadata server to authenticate to Secret Manager and retrieve the secret at runtime. This keeps the secret out of instance metadata entirely. 

# Correct: retrieve secret via metadata token → Secret Manager
TOKEN=$(curl -s -H "Metadata-Flavor: Google" \
  http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['access_token'])")

SECRET=$(curl -s -H "Authorization: Bearer $TOKEN" \
  "https://secretmanager.googleapis.com/v1/projects/PROJECT_ID/secrets/db-password/versions/latest:access" \
  | python3 -c "import sys,json,base64; print(base64.b64decode(json.load(sys.stdin)['payload']['data']).decode())")

The above is a tabletop illustration. In practice, use the Secret Manager client library or gcloud secrets versions access within the startup script. The service account must have roles/secretmanager.secretAccessor for the specific secret.

3 · Real-world problems and solutions

The scenarios below are illustrative examples grounded in Day 37 topics. They are not observed production incidents. Values and conditions are design assumptions, not measured results.

Topic 1 field case — pd-standard boot disk throttles fulfillment worker WAL writes

Situation and business impact

The Brightloaf fulfillment worker is deployed on a VM whose boot disk is pd-standard (HDD-backed). The worker's write-ahead log (WAL) is written to this boot disk. Under normal queue depth the boot disk IOPS budget is sufficient, but during a promotional event the queue depth spikes and WAL write frequency increases proportionally. The pd-standard disk's IOPS ceiling is reached; writes queue inside the kernel's I/O scheduler. The fulfillment worker's WAL flush latency rises, causing the consumer to stall. Unacknowledged Pub/Sub messages accumulate, triggering backoff in the Order API. Customer-facing order confirmation latency rises above the SLO threshold.

Constraints

  • The boot disk cannot be swapped while the VM is running; a stop-resize-start or a disk snapshot-and-replace operation is required.
  • WAL data must not be lost during the transition; a snapshot must be taken before any disk change.
  • The fix must not require application code changes — only infrastructure changes.

Root cause

The boot disk type was chosen for cost (pd-standard is the cheapest) without analysing the WAL write IOPS pattern. The WAL is a write-intensive, latency-sensitive workload that belongs on a pd-ssd or pd-balanced disk at minimum, not an HDD-backed standard disk.

Diagnostic sequence

  1. Observe disk write IOPS and write throughput via Cloud Monitoring (compute.googleapis.com/instance/disk/write_ops_count) during the incident window.
  2. Compare observed IOPS against the pd-standard ceiling for the disk size in use.
  3. Confirm that WAL writes are the dominant I/O pattern (sequential, small, frequent).
  4. Decide whether to move the WAL to a separate pd-ssd data disk, or to reprovision the boot disk as pd-ssd.

Defensible solution

Stop the fulfillment worker VM. Snapshot the pd-standard boot disk. Create a new pd-ssd boot disk from the snapshot. Attach the pd-ssd disk to the VM as the boot disk. Restart the VM and verify the WAL write latency returns to baseline.

Verification

After the change: observe disk write IOPS and write latency under a simulated load that matches the promotional-event queue depth. Confirm that IOPS remain below the pd-ssd ceiling and that WAL flush latency is within the fulfillment worker's acceptable window. Record the before/after comparison in the block-storage comparison table (exit artifact).

Residual risk

Moving the WAL off the boot disk entirely (to a dedicated secondary pd-ssd) is more operationally complex but avoids contention between OS I/O and WAL I/O on the same disk. If future queue depth growth is expected, plan for a Hyperdisk Balanced with provisioned IOPS that can be adjusted without recreating the disk.

Topic 2 field case — Zonal PD zone outage causes hours of recovery instead of minutes

Situation and business impact

The Brightloaf order database VM runs on a zonal Persistent Disk in us-central1-a. The team takes daily snapshots at 02:00 UTC. At 11:30 UTC the zone experiences a partial infrastructure outage that makes the VM and its disk unreachable. The recovery procedure requires restoring the snapshot from 02:00 UTC (9.5 hours of data loss), replaying the fulfillment queue to reconcile missing writes, and verifying data consistency — a process that takes the on-call team several hours. During this window no new orders can be written to the database. Business impact: order acceptance is suspended for several hours; customers receive errors; the on-call team performs unplanned weekend work.

Constraints

  • The zone outage prevents attaching the original disk to any VM in the same zone.
  • A regional PD would have required a pre-provisioned standby VM in the secondary zone.
  • The failover procedure must have been documented and tested before the outage — a procedure written during an outage is unreliable.

Root cause

The recovery plan relied on daily snapshots but did not include a zone-failover option. A regional PD with a standby VM would have enabled a force-attach failover with near-zero data loss. The decision to use a zonal PD was not re-evaluated against the recovery time objective (RTO) and recovery point objective (RPO) when the SLO was tightened.

Defensible solution

Migrate the database disk to a regional PD. Pre-provision a standby VM in us-central1-b. Write and test the force-attach failover runbook. Increase snapshot frequency to reduce the RPO for scenarios where force-attach is not applicable (e.g., regional-level failure, which a regional PD cannot protect against).

Verification

Conduct a planned failover drill: stop the primary VM, force-attach the regional PD to the standby VM, start the standby, and verify the database is accessible with all confirmed writes present. Record the RTO (time from primary stop to standby ready) and RPO (zero, as confirmed writes were replicated). The drill result goes into the block-storage comparison table as the post-fix evidence.

Residual risk

A regional PD protects only against a single-zone outage within one region. A regional outage requires a cross-region backup strategy (e.g., scheduled cross-region snapshot copies). The higher cost of regional PD (approximately 2× zonal) must be justified by the RTO/RPO requirement.

Topic 3 field case — Database password stored in instance attribute; visible to Compute Viewers

Situation and business impact

A Brightloaf engineer writes a startup script for the fulfillment worker that retrieves a database password from the instance attribute db-password and writes it to /etc/fulfillment/db.conf. The attribute is set at VM creation time using --metadata=db-password=SECRET_VALUE. An infrastructure auditor with roles/compute.viewer on the project discovers the password by browsing the instance's Custom Metadata section in the GCP Console. The auditor cannot connect to the database (correct — they lack the firewall access), but the password itself is now visible to any principal with Compute Viewer rights on the project. Business impact: the credential must be rotated, a rotation procedure must be tested under production traffic, and the team must audit all other VMs for the same pattern.

Root cause

Instance and project metadata attributes are not a secrets store. They are accessible to any principal with Compute Viewer rights via the API and console. The engineer treated metadata as a convenient configuration channel without considering its visibility. Secrets belong in Secret Manager, not in metadata.

Defensible solution

  1. Rotate the database password immediately.
  2. Remove the db-password attribute from the instance.
  3. Create a Secret Manager secret for the database password and set it to the new value.
  4. Grant the fulfillment worker's service account roles/secretmanager.secretAccessor on that specific secret.
  5. Update the startup script to retrieve the secret via the metadata server token and the Secret Manager API (as shown in the Part 2 code example).
  6. Audit all other VMs for sensitive values in custom metadata.

Verification

After remediation: confirm the db-password attribute is absent from the instance describe output. Confirm the startup script retrieves the secret from Secret Manager and the fulfillment worker connects to the database. Confirm that a Compute Viewer cannot see the password — they should see only the Secret Manager secret resource name, not the secret value.

Residual risk

If the startup script logs the secret value (e.g., via an inadvertent set -x in bash), the secret will appear in Cloud Logging and be visible to log readers. Always ensure startup scripts do not echo or log secret values. Use set +x around secret retrieval sections.

Exercise 2 — Persistence evidence: write a file, restart VM, confirm file survives

Goal: Demonstrate data persistence across a VM restart (persistent disk survives; Local SSD does not). Produce persistence evidence for the exit artifact.

Mode: cloud sandbox (preferred) or supplied trace · Prerequisites: Day 36 VM lifecycle skills; active identity confirmed (Day 35 G2 artifact).

Preflight

Confirm active project and account. Confirm Compute Engine API enabled. If cloud access is unavailable, describe the expected result as a tabletop prediction and label it accordingly.

  1. Create a test VM. 
    gcloud compute instances create bf-persist-test \
  --project=PROJECT_ID \
  --zone=us-central1-a \
  --machine-type=e2-micro \
  --image-family=debian-12 \
  --image-project=debian-cloud \
  --boot-disk-type=pd-balanced \
  --no-address \
  --labels=env=lab,owner=day37
  2. Write a file to the persistent boot disk. SSH into the VM and create a marker file: 
    gcloud compute ssh bf-persist-test \
  --project=PROJECT_ID \
  --zone=us-central1-a \
  --command="echo 'day37-persist-test' | sudo tee /var/bf-persist-marker.txt"
  3. Restart the VM. 
    gcloud compute instances stop bf-persist-test \
  --project=PROJECT_ID --zone=us-central1-a
gcloud compute instances start bf-persist-test \
  --project=PROJECT_ID --zone=us-central1-a
  4. Verify the file survived. 
    gcloud compute ssh bf-persist-test \
  --project=PROJECT_ID \
  --zone=us-central1-a \
  --command="cat /var/bf-persist-marker.txt"
    Expected output: day37-persist-marker. Record this output as the persistence evidence.
  5. Note the ephemeral contrast. Write in day-037-persistence.md: "If this file were written to a Local SSD, it would not survive step 3 (VM stop). The persistent boot disk retains the file because it is a network-attached durable disk."
  6. Zonal vs regional note. In the same file, add: "This boot disk is zonal (pd-balanced in us-central1-a). If the zone became unavailable, the disk would be unreachable until the zone recovered. A regional PD in us-central1-a/b would enable a force-attach failover to a standby VM in us-central1-b."
  7. Delete the VM and confirm cleanup. 
    gcloud compute instances delete bf-persist-test \
  --project=PROJECT_ID --zone=us-central1-a --quiet

gcloud compute instances list \
  --project=PROJECT_ID \
  --filter="labels.env=lab AND labels.owner=day37"
    Confirm zero rows.
Expected result / acceptance

The exit artifact contains: (1) the marker file content seen after VM restart ("day37-persist-test"), (2) the emphatic note that Local SSD would not have survived the stop, (3) the zonal vs regional observation, (4) a deletion confirmation with empty label inventory.

Troubleshooting

If SSH fails: confirm the VM is RUNNING with gcloud compute instances describe bf-persist-test; check that no firewall rule blocks SSH (IAP tunnel may be needed with --tunnel-through-iap). If the file is missing after restart: confirm the tee command was run as sudo and the path is on the persistent boot disk (not a tmpfs mount).

Cleanup and cost

Delete the VM after step 7. An e2-micro stopped VM incurs no CPU charge but the boot disk continues to accrue storage cost if not deleted. Confirm deletion with an empty label inventory. Check whether the boot disk was auto-deleted (default when --no-boot-disk-auto-delete was not passed).

Exercise 3 — Metadata server flow: read instance name and zone; identify safe vs unsafe attributes

Goal: Read metadata values from the metadata server via the correct header, identify which paths are safe and which must not contain secrets, and add the metadata flow to the persistence evidence file.

Mode: cloud sandbox (preferred) or supplied trace · Prerequisites: Exercise 2 VM or any running VM.

  1. Read instance name from the metadata server. From inside the VM (via SSH): 
    curl -s -H "Metadata-Flavor: Google" \
  http://metadata.google.internal/computeMetadata/v1/instance/name
    Expected: the instance name (e.g., bf-persist-test). This is a safe path with no secrets.
  2. Read the zone. 
    curl -s -H "Metadata-Flavor: Google" \
  http://metadata.google.internal/computeMetadata/v1/instance/zone
    Expected: a full zone resource path. Extract the zone name (last segment). Record both in the persistence file.
  3. Attempt to read the service account token. 
    curl -s -H "Metadata-Flavor: Google" \
  "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"
    Record the response structure (token_type, access_token, expires_in). Do not log or save the actual token value. Note: "This token is a short-lived credential. It must be treated as a secret and never logged."
  4. Test the header requirement. 
    curl -s http://metadata.google.internal/computeMetadata/v1/instance/name
    Expected: an error (request without the required header is rejected). Record the response and note why the header is required (SSRF defence).
  5. Document the safe vs unsafe attribute policy. In day-037-persistence.md, add a table: Metadata path | Contains secrets? | Visibility | Safe to store in attributes?
    • instance/name — No — VM-level — Yes (no secrets)
    • instance/zone — No — VM-level — Yes
    • instance/service-accounts/default/token — Yes (treat as secret) — VM-only (link-local) — Never log or expose
    • instance/attributes/KEY — Depends on value — Project Compute Viewer can read — Never store secrets here
Expected result / acceptance

The persistence file contains: metadata server read results for name and zone (labeled observed or tabletop), the token structure with the value redacted, the header-rejection response, and the safe/unsafe attribute policy table. The exit artifact satisfies "inspect a redacted metadata flow."

Troubleshooting

If the metadata server is unreachable: confirm you are running the command from inside the VM (not from the Cloud Shell external to the VM). The metadata server IP 169.254.169.254 is link-local and not routable from outside. If the VM has no default service account, the token path returns a 404; use gcloud compute instances describe to check the serviceAccounts field.

Cleanup

No additional cloud resources are created in this exercise. Ensure the VM from Exercise 2 is deleted before filing the exit artifact.
