Day 1 — Local workspace and learning baseline

Outcome: Create a local evidence repository, record one command and its exit status, set a realistic study pace, and assign ownership for future lab spending and cleanup.

Entry prerequisites: None. Begin with a local Linux shell, editor, Git, and Python 3. A Google Cloud account is not needed until Day 18.

Exit artifact

A versioned README with available study hours, environment, baseline skills, budget and cleanup owner. Keep the command observation and synthetic fixture in the same repository.

This page uses local exercises and illustrative Brightloaf cases. A local result does not prove cloud configuration or production behavior.

1 · Topics of the day

Local workspace and evidence repository

What it is: A local directory in which a shell runs commands, an editor changes files, and Git records selected snapshots. A command's exit status is evidence about that command's completion, while its output gives the observation needed to interpret the result.

Why today and system location: Day 1 establishes the workstation-side evidence boundary before any cloud resource exists. Later labs can refer to committed commands and observations instead of reconstructed memories.

Problem preview: An operator records that a setup command ran but omits its exit status and output. The next engineer cannot reproduce the baseline, delaying diagnosis of a Brightloaf release issue.

Study sessions and learning baseline

What it is: A plan that distinguishes 180 study units from calendar days and records available hours and current skills. A skill marked demonstrated needs a specific observation or artifact, not a feeling of familiarity.

Why today and system location: The plan lives in the learner's versioned README and informs when to repeat a lab or advance. It sets a realistic pace for the foundations block without assuming a fixed start date.

Problem preview: A learner schedules 180 consecutive days despite having only a few study hours each week. Prerequisite gaps accumulate, and later Brightloaf design decisions are made without a defensible baseline.

Synthetic data, budget and cleanup ownership

What it is: A rule to use invented retailer records in exercises, choose a future lab spend target, and name the person responsible for finding and deleting created resources. An alerts-only Cloud Billing budget sends notifications but does not automatically stop usage.

Why today and system location: These decisions belong in the local README before cloud setup on Day 18. Synthetic fixtures stay outside the production customer-data boundary; later sandbox resources will need an owner and a cleanup record.

Problem preview: A sandbox exercise uses a real order export and assumes a budget alert will stop charges. Customer information crosses into an unmanaged environment while retained resources continue to accrue cost.

2 · Technical discussion

Local workspace and evidence repository

The shell resolves a command, starts a process or executes a builtin, connects its input and output streams, and reports an exit status. In Bash, zero means that the command considers itself successful; a nonzero status requires investigation. Capture $? immediately: any later command replaces it. A successful process can still print incomplete or wrong data, so preserve a relevant output sample as well.

The local filesystem owner controls the working directory and permissions. Git tracks only files that are staged and committed; it does not automatically record terminal output, secret redaction, or whether a claimed observation was truthful. A commit is a reproducible snapshot of selected files, not proof that a cloud service is healthy. Never commit credentials or real customer data.

Worked example to read before the lab

This command prints a fixed marker. If it completes normally, capture its status before running another command; the observation is limited to this local process.

status=$?
printf 'exit_code: %s\n' "$status"

Expected lines: day-1-baseline and exit_code: 0. A different status means stop and inspect the Python error.

Study sessions and learning baseline

The roadmap's day number labels a unit of work, not an elapsed calendar day. Divide the roadmap's estimated total hours by hours actually available each week to obtain a planning range; add time for missed sessions and remediation. The result is an estimate, not a completion guarantee. Recalculate after a few sessions using observed effort instead of treating the initial estimate as a deadline.

Use three evidence states: new (not yet studied), familiar (can explain it), and demonstrated (can reproduce a relevant result and explain a failure). Day 1 can demonstrate local shell and Git basics after the lab. It cannot demonstrate GCP networking, IAM, or production readiness merely because those topics appear later in the roadmap.

Synthetic data, budget and cleanup ownership

A synthetic order has invented identifiers, items, amounts, and contact data. Its structure can exercise parsing without exposing a real customer. An order_id and stable replay key can describe a future deduplication contract, but a JSON fixture alone does not implement or prove exactly-once fulfillment. That behavior requires a durable business-side decision when the Fulfillment consumer is built.

A future sandbox budget needs an amount, scope, notification recipients, and an owner. An alerts-only Cloud Billing budget reports spending against thresholds; it does not automatically cap charges. Spend cap budgets are a separate, limited service feature and cannot be assumed to cover persistent resources. The Day 1 local lab creates no chargeable cloud resources, so cleanup is limited to retaining the evidence repository and confirming that no cloud project was touched.

3 · Real-world problems and solutions

Case 1 · A release note without a result

Illustrative symptom and impact: Brightloaf's release checklist says “configuration check ran,” but the operator saved neither the command's exit status nor its output. When the Order API fails to start after deployment, responders cannot tell whether the check succeeded, failed, or ran from an old workspace; recovery is delayed while they repeat the step.

Constraints and root cause: The team has only a local text note and a Git commit made after the incident. A commit proves what files were recorded, but the shell status was overwritten by a later command and the original output was never saved. No evidence supports a claim that the check passed.

Defensible response: Stop asserting success. Re-run the read-only check from a known working directory with the exact versioned input; immediately capture its status and the relevant output with a timestamp. Compare the resulting file with the committed revision, have a second operator review the evidence, and only then decide whether to roll back or continue. Add a release gate that requires command, status, output summary and commit ID. A successful rerun supports the current environment only; it does not retroactively prove the missing historical result.

Case 2 · Calendar dates mistaken for readiness

Illustrative symptom and impact: A Brightloaf team marks a prerequisite complete because its calendar says Day 17, although no one can show the local command and network worksheets. The later Order API migration review cannot establish who can diagnose a failed route, so the cutover date slips.

Constraints and root cause: Engineers have different weekly availability and no recorded baseline. The schedule counted elapsed days rather than completed study units, and “familiar” was treated as equivalent to demonstrated skill.

Defensible response: Record each person's available weekly hours and the artifact that supports each skill claim. Re-estimate the calendar range from actual capacity, reserve sessions for remediation, and review completed artifacts before moving to a dependency that uses them. A learner who cannot reproduce a result marks the skill familiar or new and repeats the relevant exercise. The review ends with an explicit advance-or-repeat decision and a revised date communicated to stakeholders.

Case 3 · An unsafe sandbox assumption

Illustrative symptom and impact: A Brightloaf analyst proposes copying a real order export into a training project and assumes a small alerts-only budget will stop charges. The plan risks disclosing customer records and leaves the cost of any retained resource without an accountable owner.

Constraints and root cause: The exercise needs only field shapes and sample values; no production data or cloud resource is required. The plan confuses a billing notification with spend enforcement and has no cleanup inventory or named operator.

Defensible response: Reject the production export and build a small invented JSON fixture. Review it for real identifiers, addresses, tokens and secrets before committing it. Write the future sandbox budget target, alert recipients, cleanup owner and resource-inventory procedure into the README. Before a later cloud lab, confirm the actual project, billing scope, permissions, resource dependencies and deletion commands. After that lab, delete dependents before dependencies and verify the project inventory. Keep the fulfillment contract explicit: a stable event key is part of the fixture, but a future consumer must store a durable deduplication decision before replay can be considered safe.

4 · Step-by-step labs

Exercise 1 · Create a local evidence repository

Goal and expected result: Create an empty local Git repository, run one harmless command, record its exact result and commit the observation. Mode: local Linux shell; no Google Cloud account, emulator or Docker needed.

Preflight: Read the worked example in Part 2. Confirm that Bash, Git and Python 3 are available. The exercise intentionally refuses to overwrite an existing ~/gcp-architect-learning directory.

command -v bash
command -v git
command -v python3
git --version
python3 --version

Expected: three executable paths, a Git version and a Python 3 version. If a command is missing, use your operating system's documented installation method before continuing.

1. Initialize, observe and commit

bash -e <<'SH'
repo="$HOME/gcp-architect-learning"
if [ -e "$repo" ]; then
  printf 'Directory already exists: %s\nChoose a fresh workspace before running this exercise.\n' "$repo" >&2
  exit 2
fi
mkdir "$repo"
cd "$repo"
git init
python3 -c 'print("day-1-baseline")'
status=$?
printf 'command: python3 baseline print\nexit_code: %s\n' "$status" > command-observation.txt
printf '# Day 1 learning evidence\n\nEnvironment: %s\n' "$(uname -s)" > README.md
git add README.md command-observation.txt
git -c user.name='Learner' -c user.email='learner@example.invalid' commit -m 'Record Day 1 local baseline'
printf 'status after commit: '
if [ -z "$(git status --porcelain)" ]; then printf 'clean\n'; else printf 'dirty\n'; exit 1; fi
cat command-observation.txt
git log -1 --format='%s'
SH

Verification: Output includes day-1-baseline, status after commit: clean, exit_code: 0, and the commit subject Record Day 1 local baseline. Git's branch name and commit hash vary. Inspect the README in the directory; it records the actual OS family.

Troubleshooting: If the directory exists, inspect it before choosing another location; do not run commands that overwrite its files. If Git reports an identity error, use the exact per-commit identity options in the block. A nonzero Python result stops the block before commit.

Cleanup: Retain this local repository as Day 1 evidence. No cloud resource was created or needs deletion. Artifact acceptance: the committed README and observation file exist, the recorded status is zero, and Git status is clean.

Exercise 2 · Record an honest study baseline

Goal and expected result: Add your available weekly hours, an estimated calendar range and evidence-based skill ratings to the README. Mode: local calculation; no GCP configuration. Preflight: complete Exercise 1 and confirm the repository exists.

test -d "$HOME/gcp-architect-learning/.git"
git -C "$HOME/gcp-architect-learning" log -1 --format='%s'

Expected commit subject: Record Day 1 local baseline. Set WEEKLY_HOURS below to your actual available hours before executing the next block; the shown value of 8 is a runnable example.

1. Calculate and commit the plan

WEEKLY_HOURS=8
python3 - "$HOME/gcp-architect-learning" "$WEEKLY_HOURS" <<'PY'
from pathlib import Path
import sys

repo = Path(sys.argv[1])
hours = float(sys.argv[2])
if hours <= 0:
    raise SystemExit('Weekly hours must be greater than zero')
plan = (
    '\n## Study capacity and initial skills\n'
    f'- Available study hours per week: {hours:g}\n'
    f'- Estimated calendar range: {485.5 / hours:.1f} to {665.0 / hours:.1f} weeks, before missed sessions or remediation.\n'
    '- Study days are units of work, not consecutive calendar dates.\n'
    '- Local shell: demonstrated by command-observation.txt.\n'
    '- Git commit: demonstrated by the Day 1 local commit.\n'
    '- Google Cloud IAM and networking: new or unassessed; no cloud lab has run.\n'
    '- Review this estimate after several actual study sessions.\n'
)
with (repo / 'README.md').open('a', encoding='utf-8') as stream:
    stream.write(plan)
print(f'weekly_hours={hours:g}; estimated_weeks={485.5 / hours:.1f}–{665.0 / hours:.1f}')
PY
git -C "$HOME/gcp-architect-learning" add README.md
git -C "$HOME/gcp-architect-learning" -c user.name='Learner' -c user.email='learner@example.invalid' commit -m 'Record Day 1 study capacity'
git -C "$HOME/gcp-architect-learning" status --short

Verification: At 8 hours per week, the printed range is 60.7–83.1 weeks. Your range changes with your input. An empty final short-status output means the README edit was committed.

Troubleshooting: A zero or nonnumeric hours value stops the calculation. If the first preflight fails, finish Exercise 1 before editing the README. Mark a skill demonstrated only when you can name its artifact.

Cleanup: Retain the README and commit; no remote resource exists. Artifact acceptance: weekly hours, estimated range, skill ratings and evidence references appear in the committed README.

Exercise 3 · Set the synthetic-data and cleanup charter

Goal and expected result: Save a valid invented order fixture and a future sandbox budget and cleanup rule without creating cloud resources. Mode: local JSON and Git. Preflight: verify the repository and Python's standard JSON module; no gcloud setup is appropriate on Day 1.

test -d "$HOME/gcp-architect-learning/.git"
python3 -c 'import json; print("json available")'

Expected: json available. Set LAB_BUDGET_USD and CLEANUP_OWNER below to the future sandbox amount and actual responsible person before running; the shown values are runnable examples.

1. Write and validate the fixture

repo="$HOME/gcp-architect-learning"
mkdir -p "$repo/fixtures"
cat > "$repo/fixtures/synthetic-order.json" <<'JSON'
{
  "order_id": "BL-TRAINING-001",
  "event_id": "BL-TRAINING-001-created-v1",
  "customer_id": "SYNTHETIC-CUSTOMER-001",
  "item_sku": "BREAD-001",
  "quantity": 2,
  "currency": "USD"
}
JSON
python3 -m json.tool "$repo/fixtures/synthetic-order.json" > /dev/null
printf 'fixture_valid=true\n'

Expected output: fixture_valid=true. These are invented identifiers. The stable event_id states a future replay key; this JSON check does not implement Fulfillment deduplication.

2. Record ownership and commit

LAB_BUDGET_USD=50
CLEANUP_OWNER='Learner'
repo="$HOME/gcp-architect-learning"
printf '\n## Future sandbox charter\n- Monthly planning target (USD): %s\n- Cleanup owner: %s\n- Day 1 cloud spend: 0; no cloud account or resource used.\n- Use synthetic data only; never commit credentials or production customer exports.\n- An alerts-only billing budget notifies; it does not stop usage.\n- Before each later cloud lab, record project, resource names, region, dependencies and expected cost.\n- After each lab, delete dependents before dependencies and verify the remaining inventory.\n- Fulfillment replay rule: a future consumer must durably reject a second fulfillment for the same business event.\n' "$LAB_BUDGET_USD" "$CLEANUP_OWNER" >> "$repo/README.md"
git -C "$repo" add README.md fixtures/synthetic-order.json
git -C "$repo" -c user.name='Learner' -c user.email='learner@example.invalid' commit -m 'Record Day 1 sandbox charter'
git -C "$repo" status --short
git -C "$repo" log -1 --format='%s'

Verification: final short status is empty, the commit subject is Record Day 1 sandbox charter, and the README contains your chosen amount and owner. Review the JSON manually for any real person or account data before sharing the repository.

Troubleshooting: If JSON validation fails, correct its syntax before committing. If Git reports no changes, inspect the path and confirm you are using the Day 1 repository. If a real identifier entered the fixture, replace it with invented data before staging.

Cleanup: Keep the repository and fixture as evidence. No cloud resource exists, so there are no deletion commands to run. Artifact acceptance: the versioned README includes hours, environment, skills, budget and cleanup owner; the synthetic JSON parses; all three lab commits exist; Git status is clean.

Daily evidence
