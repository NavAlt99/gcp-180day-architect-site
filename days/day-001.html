Day 1 — Local workspace and learning baseline

Outcome: Create a disposable local evidence repository, capture process exit codes and standard streams, calculate realistic curriculum pacing against available study hours, and establish a sandbox governance charter with synthetic data boundaries and cleanup accountability.

Entry prerequisites: None. Begin with an operational POSIX shell (Bash), an editor, Git, and Python 3. A Google Cloud account and cloud billing credentials are not required until Day 18.

Exit artifact

A versioned README with available study hours, environment profile, evidence-based baseline skills, sandbox budget target, and cleanup owner, accompanied by committed terminal observation files and synthetic order fixtures.

This page uses local exercises and illustrative Brightloaf scenarios. A local terminal observation demonstrates workstation-level mechanics but does not prove remote cloud configuration or production infrastructure health.

1. Local workspace and evidence repository

A local workspace is the shell, editor, files, and tools used to perform study tasks. An evidence repository keeps commands, results, dates, and explanations together so a later reviewer can retrace a conclusion. This belongs on Day 1 because every later exercise needs a known place to work and save evidence.

Problem preview: A learner records only a screenshot and omits the command and exit status. A reviewer cannot reproduce the result or tell whether the command succeeded.

2. Study sessions and learning baseline

A study baseline records available time, current skills, and a feasible learning plan. A session is a bounded period with a goal and a saved result; calendar progress alone does not demonstrate competence. This belongs today because later topics depend on prerequisites and evidence from earlier days.

Problem preview: A learner schedules more hours than are available and marks topics complete by date. Later exercises expose gaps that the calendar never measured.

Synthetic data is invented test information that resembles the structure of real data without copying real customer records. 1. Local workspace and evidence repository: technical mechanics

Subtopics in this discussion: shell and editor; working directory and repository; command output and exit status; versioned evidence.

Shell and editor

What it is in general: A shell reads commands and starts programs; an editor creates and changes files. Their outputs and errors make local work inspectable.

Relevance to a cloud architect: Architects need to inspect configuration, run safe checks, and record the exact inputs behind a design decision. A shell is an interface, not proof that a remote system changed.

Relevance to GCP: Later curriculum uses the gcloud CLI to interact with Google Cloud. Day 1 only records whether the command is available; cloud authentication and account setup are scheduled for Day 18.

Working directory and repository

What it is in general: A working directory is the current location for files. A version control repository records snapshots and history so changes can be reviewed or recovered.

Relevance to a cloud architect: Versioned notes make architecture assumptions and operational procedures reviewable and help teams identify which version informed a decision.

Relevance to GCP: A repository can later hold reviewed deployment configuration and runbooks for Google Cloud. Day 1 uses a local Git repository only; no remote or cloud integration is required.

Command output and exit status

What it is in general: A process emits output streams and returns a status to indicate success or failure according to that program's convention. A later command can replace the shell's most recent status, so capture it promptly.

Relevance to a cloud architect: Automation should preserve failures and evidence so a failed validation cannot be mistaken for a successful deployment gate.

Relevance to GCP: Later gcloud commands can be scripted and their status recorded, but a zero exit code alone does not establish that an application meets its requirements. This local exercise demonstrates status capture only.

Versioned evidence

What it is in general: Evidence is an artifact that supports a claim, such as a command, timestamp, exit code, and observed output. Git records changes to files over time.

Relevance to a cloud architect: Reviewers need to distinguish a supplied fact, a local observation, a design inference, and an unresolved question.

Relevance to GCP: A future cloud architecture decision record can link to Google Cloud documentation and deployment outputs stored in an approved repository. This local README is not an audit log for a cloud project.

Evidence limit: Local observations establish only what occurred in this local environment.

Further study: Pro Git: About Version Control (section 1.1).

2. Study sessions and learning baseline: technical mechanics

Subtopics in this discussion: available study capacity; session design and pacing; baseline skills and evidence; review and adjustment.

Available study capacity

What it is in general: Capacity is the time realistically available after fixed obligations and rest. A plan allocates that finite resource among study, practice, and review.

Relevance to a cloud architect: Architecture work has competing delivery and operational commitments. Estimates should reflect capacity and dependencies, not wishful schedules.

Relevance to GCP: The 180-day GCP curriculum sequences foundations before cloud account setup and later services. Use the published day prerequisites to decide pacing; there is no GCP service that substitutes for learner capacity planning.

Session design and pacing

What it is in general: A session has a question, a focused activity, and a saved outcome. A review interval revisits evidence and adjusts the next session.

Relevance to a cloud architect: Time-boxed investigation reduces unstructured exploration and leaves a decision trail for peers.

Relevance to GCP: A session might later read official GCP documentation or run a bounded lab, but Day 1 remains local. Do not assume every session needs cloud access.

Baseline skills and evidence

What it is in general: A baseline describes current knowledge using evidence such as an explanation or completed task, with unknowns recorded explicitly.

Relevance to a cloud architect: Teams need to know which assumptions require validation and which skills need support before assigning operational responsibility.

Relevance to GCP: Record familiarity with Linux, networking, identity, or Google Cloud as self-assessed unless supported by a specific artifact. This is not a certification result or proof of GCP proficiency.

Review and adjustment

What it is in general: A review compares planned effort and saved outputs with actual experience, then updates the next plan.

Relevance to a cloud architect: Replanning when prerequisites or constraints change is part of sound delivery estimation.

Relevance to GCP: If a GCP lab requires an unfamiliar prerequisite, return to the curriculum reference and adjust the schedule before running it.

Evidence limit: A plan and self-rating do not prove learning outcomes; later artifacts provide stronger evidence.

Further study: Pro Git: About Version Control (reviewable learning notes).

3. Synthetic data, budget and cleanup ownership: technical mechanics

Subtopics in this discussion: synthetic data and data boundaries; budget versus spend control; resource inventory and cleanup ownership; evidence limits.

Synthetic data and data boundaries

What it is in general: Synthetic data is deliberately constructed test input. A data boundary states what information may be used and where it may be stored.

Relevance to a cloud architect: Architects should minimize exposure, classify data, and ensure test environments do not inherit unnecessary production data or secrets.

Relevance to GCP: Later GCP exercises can use invented records in approved project resources. Day 1 requires no cloud account and uses only clearly labeled example values.

Budget versus spend control

What it is in general: A budget is a planned amount used to compare spending and trigger alerts or workflows. A budget amount by itself may not stop consumption.

Relevance to a cloud architect: Cost ownership requires a response path, resource inventory, and an operator authorized to act; an alert alone is not an enforced limit.

Relevance to GCP: Google Cloud Billing alerts-only budgets notify about actual or forecast costs and do not automatically cap usage. Google documentation describes automated responses and a separate spend cap option subject to service support and its current status. Day 1 only studies and records the distinction; it creates no billing configuration.

Resource inventory and cleanup ownership

What it is in general: An inventory names resources and dependencies; cleanup assigns a person to verify deletion after use. Deletion order follows dependencies.

Relevance to a cloud architect: Clear ownership reduces abandoned resources, unexpected cost, and uncertainty about retained data.

Relevance to GCP: A future lab should record project and resource identifiers and verify inventory after cleanup. There is no project or resource to clean up on Day 1.

Evidence limits

What it is in general: A tabletop plan predicts what a control might do; an observation records what a real environment did. They are different evidence classes.

Relevance to a cloud architect: Cost and security decisions should state whether a claim comes from documentation, an observation, a prediction, or an open question.

Relevance to GCP: Use current Cloud Billing documentation for product behavior. A local worksheet cannot prove future charges, budget delivery timing, or automatic cleanup.

Evidence limit: This exercise creates no cloud resource, budget, charge, or production evidence.

Further study: Google Cloud Billing: create budgets and alerts (alerts-only behavior).

3 · Real-world problems and solutions

The cases below are explicitly illustrative tabletop exercises. They show how weak records, unrealistic schedules, or ambiguous ownership can undermine later architecture work; none describes an observed production incident.

1. Local workspace and evidence repository · field case

Enterprise scenario: Illustrative tabletop: a learner shares a screenshot of a command but no command text, date, or exit status.

Failure symptoms and impact: A reviewer cannot reproduce the result; the learning artifact may be incorrectly treated as verified.

Constraints: Use only local synthetic text and preserve the scheduled Day 1 scope.

Evidence:

Supplied facts: This is a hypothetical exercise prompt.

Local observation: None supplied; the learner inspects the artifact they create.

Architectural inference: Without command and status context, the screenshot cannot establish successful execution.

Root cause: The evidence artifact omits provenance: command, environment, time, and exit status.

Diagnostic sequence:

  1. List the claim and the artifact that is supposed to support it.
  2. Check whether command, environment, date, output, and status are recorded.
  3. Mark any missing field as unknown rather than infer it.

Defensible remediation: Record the exact harmless command, date, environment, output, and captured exit status in a versioned README.

Verification: Run the harmless command and confirm its output and status appear in the saved note; inspect the Git diff.

Residual risk: A reproducible local command does not prove later cloud behavior or architectural correctness.

2. Study sessions and learning baseline · field case

Enterprise scenario: Illustrative tabletop: a weekly plan schedules twelve study hours although the learner has six available.

Failure symptoms and impact: Practice and review are repeatedly skipped, leaving later architecture choices unsupported.

Constraints: Use learner-supplied availability; no exam scores or completion outcomes are assumed.

Evidence:

Supplied facts: The hypothetical states six available hours and a twelve-hour plan.

Local observation: Learner records actual availability and completed sessions.

Architectural inference: A plan that exceeds stated capacity must omit, defer, or compress work.

Root cause: The schedule was created without reconciling planned hours with available capacity.

Diagnostic sequence:

  1. Write available hours for each day of the week.
  2. Sum planned hours and compare with availability.
  3. Mark the session or review that would be dropped first.

Defensible remediation: Replan inside the stated capacity and preserve a review slot; defer excess work rather than claim completion.

Verification: Recalculate the weekly total and compare it to the learner's stated availability.

Residual risk: Capacity varies; the worksheet does not measure understanding or future interruptions.

3. Synthetic data, budget and cleanup ownership · field case

Enterprise scenario: Illustrative tabletop: a team assigns a monthly sandbox budget but names no cleanup owner and assumes the alert deletes resources.

Failure symptoms and impact: The assumed response may not occur; a resource could remain active and consume funds.

Constraints: Day 1 is a local planning exercise. No actual budget, billing account, resource, price, or cost is assumed.

Evidence:

Supplied facts: The case prompt supplies the mistaken assumption; it is hypothetical.

Documentation: Google Cloud states alerts-only budgets do not automatically cap usage or spending.

Local observation: No billing configuration or resource is created.

Open question: Any future automation needs an owner, permissions, tested trigger, and defined failure response.

Root cause: The design confuses notification with enforcement and leaves cleanup responsibility unassigned.

Diagnostic sequence:

  1. Separate planned spend, alert, automated response, and cleanup action.
  2. Name the owner and the inventory evidence required after cleanup.
  3. Check the current official billing documentation before a future cloud exercise.

Defensible remediation: Record a conservative planning assumption, an alert recipient, the person responsible for cleanup, and an inventory verification step; treat alerts as notifications unless a separate supported control is configured and tested.

Verification: Review the written plan for an owner, resource inventory fields, cleanup order, and explicit alert limitation.

Residual risk: A tabletop worksheet cannot establish actual service support, delivered alerts, or spending outcomes.

4 · Step-by-step labs

Complete each exercise locally with synthetic text only. Do not create a cloud project or resource on Day 1.

Exercise 1: Create a local evidence repository

Goal: Create a small versioned README and record one harmless command with its exit status.

Expected result: A local Git commit contains README.md with environment and a reproducible command observation.

Mode: Local Linux shell and Git; no cloud access or external network · Prerequisite: A Linux shell, text editor, and Git installed

Preflight: Record the results of pwd, git --version, and bash --version; choose a disposable directory under /tmp and confirm the name is unused.

Exact execution

  1. Stage 1 — Preflight. Run pwd; git --version; bash --version and record the working directory and tool versions in a scratch note. Stop if Git is unavailable; do not install unfamiliar tools during this exercise.
  2. Stage 2 — Prepare workspace. Run bash mkdir -p /tmp/day1-workspace-lab && cd /tmp/day1-workspace-lab && git init and confirm bash git status --short is empty.
  3. Stage 3 — Author README. Create README.md with headings Environment, Command observation, and Evidence limit. Record the OS/shell/editor you actually have; do not guess unavailable details.
  4. Stage 4 — Execute harmless command. Run bash printf 'day1-check\n'; status=$?; printf 'exit_status=%s\n' "$status" and paste the observed output in README.md.
  5. Stage 5 — Inspect result. Run bash cat README.md; git diff --check; git status --short and verify the output and status are present and the diff has no whitespace errors.
  6. Stage 6 — Rehearse missing evidence. In a separate note, remove the recorded exit status and write why the output alone is insufficient; restore the status field in README.md and confirm the distinction.
  7. Stage 7 — Record and verify decision. Run bash git add README.md && git -c user.name='Day 1 Learner' -c user.email='learner@example.invalid' commit -m 'Record local learning baseline' then bash git log -1 --oneline; record the commit ID in your exit note.
  8. Stage 8 — Close out. Run bash git status --short and record whether it is clean. Keep the disposable repository as the exit artifact; if removing it later, inspect its path first and remove only this exact exercise directory.
Expected result / acceptance

Local command output, captured zero status, README content, and Git commit are visible and internally consistent.

Artifact acceptance: README.md records actual environment details and a harmless command with its output and exit status; one Git commit exists. File: /tmp/day1-workspace-lab/README.md. (File: day-001-topic-01.md).

Troubleshooting

If Git initialization fails, verify directory permissions and that the location is writable. If commit identity is missing, use the per-command identity supplied in Stage 7; do not change global Git configuration.

Cleanup and cost

No cloud resources or credentials are used. Retain the repository as evidence or remove only /tmp/day1-workspace-lab after confirming the path.

Exercise 2: Build a weekly capacity and skills baseline

Goal: Calculate available study time and record a truthful baseline with evidence and unknowns.

Expected result: A README contains a feasible weekly plan, short skills inventory, and one next review date.

Mode: Local worksheet and Markdown; no cloud services · Prerequisite: A calendar or a blank weekly table

Preflight: Choose the next seven days and use only obligations and study windows you can currently identify.

Exact execution

  1. Stage 1 — Preflight. Write seven dates in day1-plan.md; mark fixed obligations and rest periods before allocating study time.
  2. Stage 2 — Prepare inputs. For each day record available study minutes from your actual calendar. Enter zero when unavailable; do not infer future free time.
  3. Stage 3 — Author the plan. Allocate up to 120 minutes/day among study, practice, and review. Sum the allocations and compare them with daily availability.
  4. Stage 4 — Execute a planning check. Use this supplied example as a check: 6 available hours and a 12-hour plan. Record over by 6 hours and reduce or defer sessions until planned time fits capacity.
  5. Stage 5 — Inspect baseline. Make a table with skill, self-rating (new, some practice, comfortable), evidence, and uncertainty. Mark every rating without an artifact as self-assessed.
  6. Stage 6 — Rehearse a changed constraint. Remove one planned 60-minute session. Identify the deferred activity and update the remaining plan without changing the stated availability.
  7. Stage 7 — Record decision. Write one next-session goal, one prerequisite question, and a review date. Link each skill claim to an artifact or label it self-assessed.
  8. Stage 8 — Close out. Read day1-plan.md, recalculate totals, and save it in the Day 1 evidence repository. Note that actual learning has not yet been measured.
Expected result / acceptance

Daily planned minutes do not exceed recorded availability; self-assessments and evidence-backed claims are clearly distinguished.

Artifact acceptance: A dated weekly plan, total capacity, baseline skills table, uncertainty, and next review date are saved. File: day1-plan.md. (File: day-001-topic-02.md).

Troubleshooting

If capacity is uncertain, mark it unknown and plan only around confirmed hours. Avoid converting a self-rating into a demonstrated skill claim.

Cleanup and cost

No cloud resources created. Keep the Markdown worksheet with the local evidence repository.

Exercise 3: Write a synthetic data and sandbox governance charter

Goal: Create synthetic input, a budget assumption, and a cleanup checklist without provisioning cloud resources.

Expected result: A local README identifies synthetic data, budget assumptions, an owner, and post-exercise cleanup evidence.

Mode: Offline local text and shell; zero cloud API calls · Prerequisite: Text editor and a local directory

Preflight: Confirm you are working in a disposable local directory. Do not run gcloud, create a project, or enter payment information.

Exact execution

  1. Stage 1 — Preflight. Record the current directory and write mode: offline tabletop at the top of day1-governance.md. Confirm the note contains no real names, credentials, or customer data.

  2. Stage 2 — Prepare synthetic input. Create sample.json with exactly this fictional JSON, then label all fields synthetic in the README.

    {
  "order_id": "TEST-001",
  "amount": 12.50,
  "customer": "SYNTHETIC"
}
  3. Stage 3 — Author governance plan. Record a planned monthly budget amount as a learner-selected assumption, currency, review date, alert recipient, and cleanup owner. Do not describe it as an actual Google Cloud budget.
  4. Stage 4 — Execute a tabletop review. Add a resource inventory table with columns resource, dependency, owner, cleanup action, and verification. Add one fictional VM and one fictional disk, with disk dependent on VM use.
  5. Stage 5 — Inspect safety and sequence. Check that all data values are synthetic and order the cleanup: stop/delete VM, inspect disk, delete disposable disk, verify inventory. Mark the table as a proposed sequence, not an observed cloud result.
  6. Stage 6 — Rehearse budget alert failure. Assume a notification arrives after the planned threshold. Record that the alert alone does not prove spending stopped; name the human response and the documentation check required before automation.
  7. Stage 7 — Record findings. Add source links to Google Cloud budget behavior and write separate labels for documentation fact, tabletop prediction, local observation, and open question.
  8. Stage 8 — Close out. Run bash git diff --check if the note is in Git, verify no cloud project or resource was created, and save the charter with the Day 1 README.
Expected result / acceptance

The JSON values are fictional, the planned amount is labeled an assumption, and the alert limitation and cleanup owner are explicit.

Artifact acceptance: A committed or saved synthetic fixture and charter with owner, planned amount/currency, review date, inventory, dependency order, source, and evidence labels. No cloud project or chargeable resource exists from this exercise. (File: day-001-topic-03.md).

Troubleshooting

If any fixture value came from a real system, replace it with invented data before saving. If budget currency or amount is not known, mark it as an open planning decision rather than fabricate a quote.

Cleanup and cost

No cloud resource is provisioned. Retain the synthetic note and JSON; delete only disposable local copies after checking their paths.

Daily evidence

Save one version-controlled README that records available study hours, local environment, baseline skills, planned study budget, and named cleanup owner. Add supporting command output or planning notes if useful. The evidence is a local learning baseline; it does not demonstrate cloud deployment, production readiness, actual cloud cost, or measured learning outcomes.

Exit artifact: A versioned README recording study hours, environment, baseline skills, a planned study budget, and a cleanup owner.
