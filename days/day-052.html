Cloud DNS (public and private zones, forwarding, peering zones, DNSSEC, response policies)

Google Cloud DNS is a 100% SLA, software-defined, globally distributed Domain Name System managed across Google's worldwide Anycast infrastructure. In enterprise deployments, Cloud DNS handles complex split-horizon, hybrid, and zero-trust naming requirements.

Cloud DNS Zone Types & Architectures

  • Public Zones: Authoritative name servers globally exposed to the public internet. Google Anycast IP addresses route queries to the geographically closest Google Point of Presence (PoP), mitigating DDoS amplification and delivering low lookup latency.
  • Private Zones: Authoritative for internal domains (e.g. gcp.brightloaf.internal) visible only to designated authorized VPC networks. Queries originate from the Compute Engine metadata resolver (169.254.169.254) inside Google's Andromeda SDN and never traverse the public internet.
  • Forwarding Zones (Outbound): Directs lookups for designated target domains (e.g. corp.brightloaf.internal or onprem.corp) to upstream DNS servers located on-premises or in partner clouds across Cloud VPN or Cloud Interconnect. Outbound queries egress from Google's fixed resolver address space: 35.199.192.0/16.
  • Peering Zones: Enables a consumer VPC to delegate lookup requests for a specific domain namespace to a producer DNS Hub VPC without establishing VPC Network Peering or requiring IP reachability between the two VPCs. This decouples DNS namespace management from network topology.

Inbound and Outbound Hybrid Resolution Mechanics

Production hybrid cloud architectures require seamless bi-directional name resolution between Google Cloud VPCs and on-premises Active Directory or BIND infrastructure:

  • Inbound Server Policy: When enabled on a VPC network, Cloud DNS allocates internal IP addresses from the primary IP address range of each subnet in that VPC. On-premises DNS resolvers are configured with conditional forwarding rules targeting these subnet IP addresses across Cloud Interconnect. Inbound queries hitting these addresses are intercepted by Andromeda and answered directly by Cloud DNS private zones.
  • Outbound Forwarding Path & The 35.199.192.0/16 Rule: When a GCP VM queries an on-premises record, Andromeda forwards the request to Cloud DNS. Cloud DNS proxies the UDP/TCP port 53 query across Cloud Interconnect or Cloud VPN to on-premises resolvers. Critical operational requirement: These queries always originate from 35.199.192.0/16. If Cloud Router does not advertise 35.199.192.0/16 via BGP, or if on-premises perimeter firewalls drop packets from this range, hybrid resolution silently fails with 100% packet loss.

DNSSEC and DNS Response Policy Zones (RPZ)

  • DNSSEC (DNS Security Extensions): Provides cryptographic authentication of DNS data to prevent DNS spoofing and cache poisoning. Cloud DNS supports DNSSEC for both public and private zones, managing Key Signing Keys (KSK) and Zone Signing Keys (ZSK), generating RRSIG records, and providing Delegation Signer (DS) records for registrar publication.
  • DNS Response Policies: Implements a software-defined DNS firewall directly in the VPC metadata lookup path. Response policies evaluate incoming queries before consulting authoritative zones. Rules can return a static IP (split-horizon override), pass through, or return NXDOMAIN to immediately sinkhole compromised command-and-control (C2) domains across all VMs in the authorized VPC.

Network Connectivity Center (NCC as enterprise transit hub connecting VPC spokes, hybrid links, and SD-WAN router appliances)

Traditional multi-VPC cloud architectures face significant scalability hurdles: VPC Network Peering enforces a strict non-transitive routing rule and has a quota limit of 25 peerings per VPC, creating an exponential N*(N-1)/2 configuration bottleneck. Network Connectivity Center (NCC) solves this by positioning Google's global fiber backbone as a centralized, high-speed software-defined transit hub.

Core Architecture: Hubs and Spokes

NCC operates on a clean, scalable hub-and-spoke abstraction:

  • NCC Hub: A global Google Cloud management resource that defines the administrative boundary for dynamic transit routing. A hub coordinates route exchange and maintains the global routing table.
  • VPC Spokes: VPC networks attached to the NCC hub. When VPC spoke transit is enabled, subnets from one VPC spoke are dynamically advertised to all other attached VPC spokes, creating a scalable hub-and-spoke topology without point-to-point peering.
  • Hybrid Spokes: Cloud Interconnect VLAN attachments, HA VPN tunnels, and Cloud Routers attached as spokes. Routes learned dynamically via BGP from on-premises routers are propagated through the hub to other hybrid locations or VPC spokes.
  • Router Appliance Spokes: Third-party virtual network appliances (such as Cisco SD-WAN, Fortinet FortiGate, or Palo Alto VM-Series) running on Compute Engine instances. Cloud Router establishes internal BGP peering sessions with the router appliance instances, allowing seamless route exchange between SD-WAN fabric and Google Cloud.

Transitivity Model: Site-to-Cloud vs Site-to-Site Data Transfer

NCC provides two distinct data transfer modes:

  1. Site-to-Cloud: Enables hybrid on-premises locations and remote branch offices to communicate directly with workloads running across any attached GCP VPC spoke. Routes flow seamlessly between BGP hybrid spokes and VPC subnet routes.
  2. Site-to-Site Data Transfer: Transforms Google Cloud's private global fiber network into an enterprise WAN backbone. Traffic between two remote branch offices or data centers transits through Google's physical network, providing lower latency, higher availability, and predictable packet delivery compared to public internet VPNs.

BGP Route Propagation, Subnet Constraints, and ASN Governance

  • Subnet Non-Overlap Mandate: All VPC spokes attached to an NCC Hub must have completely non-overlapping IPv4 and IPv6 CIDR blocks. If an overlapping subnet is detected, NCC suspends route propagation for the conflicting prefix across all spokes.
  • BGP Autonomous System Numbers (ASN): Cloud Routers and Router Appliances must use private 2-byte or 4-byte ASNs (RFC 6996, range 64512–65534). Organizations must carefully plan ASN assignments so that on-premises BGP peers, Cloud Routers, and SD-WAN appliances do not collide, which would trigger BGP AS-path loop detection and drop valid routes.
  • Data Transfer Billing: Inter-region traffic transiting an NCC hub incurs standard inter-region egress charges. Inter-spoke traffic within the same region utilizes Google's high-speed local backbone with zero inter-spoke transit surcharges.

VPC Flow Logs, Firewall Rules Logging, Packet Mirroring

Enterprise network forensics, regulatory compliance, and performance diagnostics require a layered telemetry architecture operating at the virtual interface layer without degrading production workload performance.

VPC Flow Logs

VPC Flow Logs record network telemetry directly from the Google Andromeda SDN hypervisor for all virtual network interfaces (vNICs) on Compute Engine instances and GKE nodes:

  • Captured Attributes: Source and destination IP addresses, source and destination ports, IP protocol, packet counts, byte counts, flow start and end timestamps, TCP flags, and round-trip time (RTT) latency metrics.
  • Sampling and Aggregation: Sampling rates range from 0.01 (1%) to 1.0 (100% of packets). Aggregation intervals can be tuned to 5 seconds, 30 seconds, 1 minute, 5 minutes, or 15 minutes to balance Cloud Logging ingestion costs against diagnostic granularity.
  • Metadata Enrichment: Flow logs can be enriched with GKE pod names, pod namespaces, service names, cluster names, Compute Engine VM names, network tags, and geographic location tags (continent, country, region).
  • BigQuery Export & Cost Control: Exporting flow logs to BigQuery enables petabyte-scale SQL queries to identify top bandwidth consumers, analyze egress traffic trends, and audit unauthorized outbound socket attempts. High-volume, predictable flows (such as internal health checks) can be excluded using Cloud Logging sink exclusion filters.

Firewall Rules Logging

Firewall Rules Logging records an immutable audit entry every time a VPC firewall rule or hierarchical firewall policy evaluates a packet:

  • Disposition Logging: Records whether the packet was ALLOWED or DENIED.
  • Rule Attribution: Captures the exact matched rule name, priority, direction (ingress or egress), VPC network, and target tags.
  • Diagnostic Differentiator: Firewall logs conclusively distinguish between a network security drop (where a firewall rule drops the packet and logs a DENIED entry) and an application service crash or routing failure (where no firewall rule intervened).

Packet Mirroring

While Flow Logs provide L4 metadata, Packet Mirroring clones actual raw packet payloads (Layer 3 through Layer 7). Andromeda mirrors packets asynchronously directly at the virtual switch layer:

  • Zero VM Impact: Cloning occurs in the physical host kernel; guest OS CPU cycles, memory, and vNIC bandwidth are completely untouched. Workload network throughput and latency experience zero degradation.
  • Collector Architecture: Mirrored packets are encapsulated and forwarded to an Internal TCP/UDP Load Balancer (ILB) frontend. The ILB distributes traffic across a pool of collector VMs running open-source or commercial intrusion detection/prevention systems (IDS/IPS) such as Suricata, Zeek, Snort, or Wireshark.
  • Granular Filtering: Mirroring policies can filter traffic based on IPv4/IPv6 CIDR ranges, IP protocols (TCP, UDP, ICMP), and traffic direction (ingress, egress, or both), avoiding unnecessary collector load.

Network Intelligence Center (Connectivity Tests, Network Topology, Performance Dashboard)

Network Intelligence Center (NIC) provides comprehensive visibility, proactive mathematical verification, and automated fault localization across Google Cloud and hybrid networks.

Connectivity Tests: Static Modeling & Dynamic Live Probing

Connectivity Tests evaluates end-to-end packet reachability between any two network endpoints (GCE VM, GKE node, Cloud SQL, on-prem IP, or internet address):

  • Static Configuration Analysis: Builds a formal mathematical graph model of your entire network control plane. It evaluates hierarchical firewall policies, VPC firewall rules, VPC routing tables, VPC Network Peering, Shared VPC bindings, Cloud NAT translation rules, Cloud Load Balancer forwarding rules, and NCC transit hubs. It traces the exact hop-by-hop path and deterministically identifies the dropping component (e.g. DROPPED_BY_FIREWALL_RULE: default-deny-ingress or DROPPED_NO_ROUTE: 0.0.0.0/0).
  • Dynamic Live Data-Plane Probing: Complements static analysis by injecting active synthetic probe packets into Google's physical data plane. Probing verifies that the physical path is operational, discovers unadvertised BGP routes, and measures real-time packet loss and round-trip latency.
  • Deterministic Outcomes: Every test outputs an unambiguous status: REACHABLE, DROPPED, UNDETERMINED (when hitting external networks without probing), or AMBIGUOUS (when multiple non-deterministic equal-cost paths exist).

Network Topology: Dynamic Communication Graph

Network Topology visualizes the operational communication graph across projects, regions, zones, subnets, and hybrid connections:

  • Traffic Volume Overlay: Maps real-time throughput (bytes/second) across all network edges, instantly exposing unintentional cross-region data transfers and anomalous egress spikes.
  • Packet Loss & Latency Heatmaps: Color-codes paths exceeding latency thresholds or dropping packets, enabling operators to pinpoint degraded subnets before application SLOs are violated.

Performance Dashboard: Global Infrastructure Baselines

Performance Dashboard displays packet loss and latency metrics measured across Google Cloud's worldwide physical backbone:

  • Regional & Zonal Matrices: Provides continuous, authoritative latency and loss benchmarks between all Google Cloud regions and zones worldwide.
  • Incident Isolation: Enables engineering teams to differentiate between an internal application bottleneck (such as database connection starvation or garbage collection pauses) and an underlying cloud network impairment, eliminating hours of unproductive finger-pointing.
Apply it

Input: An internal payment VM cannot connect to an on-premises database across Cloud VPN. Is it blocked by a firewall, missing a BGP route, or failing on-premises? Expected: Run a Connectivity Test from the VM internal IP to the database IP on port 5432. The test output pinpoints the exact hop and rule causing the drop.

Hybrid DNS Forwarding Query Drop and Firewall Asymmetry · field case

Enterprise Scenario & Business Impact

Brightloaf's automated inventory replenishment microservice deployed on Compute Engine instances in us-east4 attempted to connect to an on-premises Oracle database cluster by fully qualified domain name (db.corp.brightloaf.internal). The DNS queries repeatedly timed out with ;; connection timed out; no servers could be reached. The replenishment daemon crashed, failing to process inventory restock orders for 45 supermarket distribution centers before morning retail shifts. The incident halted $1.4 million in scheduled warehouse dispatches.

Operational Constraints

  • Workloads must resolve on-premises resources using enterprise FQDNs; hardcoding IP addresses in microservice manifests is strictly prohibited by security policy.
  • Internal Active Directory DNS servers cannot be exposed to the public internet.
  • DNS query resolution latency across the hybrid connection must remain under 30ms to maintain API transaction SLOs.

Diagnostic Sequence

  1. Logged into the application VM and verified local name resolution: querying api.google.internal succeeded via 169.254.169.254, but querying db.corp.brightloaf.internal timed out after 5000ms.
  2. Audited the Cloud DNS forwarding zone configuration: the zone corp.brightloaf.internal was configured with target resolver IP 172.16.1.10 over Cloud Interconnect.
  3. Executed a packet capture (tcpdump) on the on-premises DNS server at 172.16.1.10 during test lookups. Zero incoming UDP port 53 packets arrived at the server.
  4. Inspected the on-premises perimeter firewall logs: discovered massive drops of incoming UDP/TCP port 53 packets originating from the IP range 35.199.192.0/16. The firewall dropped the traffic because 35.199.192.0/16 was recognized as an external Google public CIDR and was absent from the internal network access control list (ACL).
  5. Inspected the Cloud Router BGP advertised routes: the router advertised local VPC subnets (10.10.0.0/16), but was not configured with a custom route advertisement for 35.199.192.0/16, causing return packets on-premises to fail routing.

Root Cause Analysis

Cloud DNS outbound forwarding queries do not originate from the querying VM's internal private IP. Instead, Google Cloud proxies all outbound forwarding queries from the fixed, reserved Google IP block 35.199.192.0/16. Because on-premises perimeter firewalls treated 35.199.192.0/16 as an unpermitted external IP block, all ingress DNS requests were dropped. Furthermore, the on-premises core routers lacked a route back to 35.199.192.0/16 across Cloud Interconnect because Cloud Router omitted the custom BGP prefix advertisement.

Defensible Remediation

  1. Configured custom route advertisements on the Cloud Router BGP session to advertise 35.199.192.0/16 across Cloud Interconnect to the on-premises BGP peers.
  2. Updated the on-premises perimeter firewall security policies to whitelist ingress UDP and TCP traffic on port 53 from source prefix 35.199.192.0/16 to the corporate DNS resolvers.
  3. Configured an Inbound Server Policy on the VPC to ensure bi-directional symmetry for on-premises clients querying GCP services.

Verification & Acceptance

Re-ran DNS lookups from the Compute Engine instances. Resolving db.corp.brightloaf.internal returned 172.16.5.25 in 7.2ms. The inventory replenishment microservice restarted successfully and cleared the dispatch backlog within 20 minutes.

Residual Risk & Preventative Guardrails

If hybrid link bandwidth saturates, UDP DNS lookups can experience packet drops or jitter. Guardrail: Deploy caching DNS forwarders in each regional VPC and enforce automated CI/CD pipeline checks that validate Cloud Router custom route advertisements for 35.199.192.0/16 before provisioning forwarding zones.

Multi-Spoke Transit Isolation and SD-WAN Routing Partition · field case

Enterprise Scenario & Business Impact

Brightloaf acquired a regional logistics enterprise operating workloads across three standalone GCP VPCs and two remote distribution depots connected via Cisco SD-WAN. Engineers attempted to route traffic between the logistics depot (192.168.10.0/24) and central financial reporting in finance-vpc (10.1.0.0/16) by peering both networks to an intermediate transit VPC. Traffic failed completely: ping tests produced Destination Host Unreachable and BGP sessions flapped continuously. The logistics depot was unable to transmit freight bills of lading, stalling 120 delivery trucks at distribution gates.

Operational Constraints

  • Must not construct a fragile full mesh of 15 point-to-point IPsec VPN tunnels across disparate environments.
  • Must support dynamic, automatic failover across redundant SD-WAN connections without manual route table edits.
  • Must maintain centralized security policy governance and transit auditability from a central NetOps project.

Diagnostic Sequence

  1. Initiated ping and traceroute tests from the finance VM (10.1.1.20) to the SD-WAN depot host (192.168.10.15): packets were immediately dropped at the local VPC gateway.
  2. Audited the VPC routing tables: finance-vpc was peered with transit-vpc, and transit-vpc was connected to the SD-WAN gateway. However, routes for 192.168.10.0/24 were completely missing from the finance-vpc route table.
  3. Checked peering configuration flags: both --import-custom-routes and --export-custom-routes were enabled on the peering between finance-vpc and transit-vpc. Despite this, traffic could not traverse the intermediate transit VPC.
  4. Confirmed hypervisor behavior: Google Cloud Andromeda SDN strictly enforces the non-transitive peering rule. An intermediate peered VPC cannot act as a transit router to forward packets between two other networks.

Root Cause Analysis

Google Cloud VPC Network Peering is non-transitive by design. Peering allows communication strictly between the two directly connected VPC networks; it cannot transit traffic to a third network or on-premises SD-WAN link. The team attempted to use a peered VPC as a transit router without deploying an active transit routing plane.

Defensible Remediation

  1. Deployed a global Network Connectivity Center (NCC) Hub in the central network host project: enterprise-transit-hub.
  2. Attached the three standalone VPCs as VPC Spokes with VPC transit routing enabled.
  3. Attached the Cisco SD-WAN virtual instances on Compute Engine as Router Appliance Spokes.
  4. Established internal BGP peering sessions between Google Cloud Router and the SD-WAN router appliances.
  5. The NCC Hub automatically exchanged dynamic BGP routes and propagated spoke subnets across all attached networks, establishing a fully transitive software-defined transit hub over Google's global backbone.

Verification & Acceptance

Verified that the NCC Hub reported all spokes in status ACTIVE. Executed bidirectional ping tests between depot workstations and finance hosts: latency stabilized at 11ms with 0% packet loss. Freight bills of lading transmitted immediately, releasing the delivery trucks.

Residual Risk & Preventative Guardrails

NCC requires strict subnet non-overlap across all linked VPC spokes. Guardrail: Enforce organizational IP Address Management (IPAM) policies to guarantee CIDR exclusivity before attaching new VPC spokes, and assign distinct private ASNs (64512–65534) to avoid BGP loop detection drops.

Undetected Data Exfiltration Due to Disabled Telemetry · field case

Enterprise Scenario & Business Impact

An external threat intelligence advisory alerted Brightloaf that an attacker had compromised a Compute Engine instance in their analytics environment and established persistent outbound communication with a known command-and-control (C2) server in Eastern Europe. The attacker exfiltrated 45 GB of unencrypted customer analytics telemetry over 14 days. When the security incident response team opened Cloud Logging to determine the breach timeline and blast radius, zero network connection records existed because VPC Flow Logs and Firewall Rules Logging were disabled on the analytics subnet. Without forensic evidence, regulators mandated public breach notification and levied a $350,000 preliminary non-compliance penalty.

Operational Constraints

  • Must establish continuous, immutable network telemetry across all production subnets without generating unsustainable Cloud Logging ingestion costs.
  • Must introduce real-time intrusion detection and payload inspection without inserting inline chokepoints or adding latency to production batch pipelines.
  • Must satisfy SOC 2 Type II and ISO 27001 audit logging mandates for all cloud network egress.

Diagnostic Sequence

  1. Queried Cloud Logging using resource.type="gce_subnetwork" AND logName:"logs/compute.googleapis.com%2Fvpc_flows": returned 0 results.
  2. Inspected subnet configuration: the subnet analytics-prod-us-east4 had enableFlowLogs: false.
  3. Checked VPC firewall rules: all rules had enableLogging: false.
  4. Captured a live disk snapshot of the compromised instance: forensic analysis revealed an unauthorized cron job running an encrypted python exfiltration script uploading data via HTTPS on port 8443.

Root Cause Analysis

The analytics subnet was provisioned with zero network telemetry to avoid perceived Cloud Logging costs. Without VPC Flow Logs, the organization was blind to network layer connections. Without Firewall Rules Logging, security teams could not audit whether egress traffic conformed to policy. Without Packet Mirroring, the contents and TLS SNI of outbound connections could not be inspected by intrusion detection systems.

Defensible Remediation

  1. Enabled Firewall Rules Logging across all hierarchical and VPC firewall rules with metadata enabled.
  2. Enabled VPC Flow Logs across all subnets with a 5-minute aggregation interval, 0.5 (50%) sampling rate, and metadata inclusion (including GKE pod annotations and instance names).
  3. Configured Cloud Logging exclusion filters to exclude high-volume internal health-check traffic (35.191.0.0/16 and 130.211.0.0/22) from log storage, reducing logging billable volume by 72%.
  4. Deployed a Packet Mirroring Policy on sensitive database and analytics subnets. Configured an Internal TCP/UDP Load Balancer distributing mirrored traffic across an auto-scaled pool of Suricata IDS collector VMs that automatically feed threat alerts into Security Command Center.

Verification & Acceptance

Simulated an anomalous outbound socket connection to a test external endpoint. Within 45 seconds, the connection appeared in BigQuery via VPC Flow Log export with complete 5-tuple and RTT metrics. Simultaneously, Suricata detected the outbound TLS handshake and generated a high-severity alert in Security Command Center.

Residual Risk & Preventative Guardrails

Enabling 100% flow log sampling during unexpected network floods can generate high logging bills. Guardrail: Configure Cloud Monitoring budget alerts on log ingestion volume and enforce Organization Policy constraints that mandate flow logs on all newly provisioned subnets.

Silent Route Blackhole Diagnosed via Network Intelligence Center · field case

Enterprise Scenario & Business Impact

After migrating a payment tokenization service from Compute Engine in us-central1 to a GKE cluster in us-east4, customer credit card processing began failing intermittently with 504 Gateway Timeout. Network engineers on-premises insisted Google Cloud firewalls were dropping the traffic. GCP administrators insisted that their VPC egress firewall rules were completely open on TCP port 8443. The two engineering teams remained in an adversarial deadlock for 16 hours while 28% of customer checkouts failed, causing $420,000 in abandoned transactions.

Operational Constraints

  • Cannot run invasive packet sniffers or interrupt live production payment traffic during trading hours.
  • Must produce deterministic, mathematically verifiable proof of the exact packet drop point to resolve the cross-team deadlock.
  • Resolution must maintain high-availability automated routing failover across the hybrid connection.

Diagnostic Sequence

  1. Both teams reviewed firewall rules: GCP firewall rule allow-egress-vault permitted TCP 8443; on-prem ASA firewall allowed TCP 8443 from GCP subnets. Neither log showed denied packets.
  2. Executed a standard traceroute from the GKE node to 172.16.5.25: output stalled at hop 1 with asterisk timeouts (* * *), providing zero diagnostic insight.
  3. Created a Connectivity Test in Network Intelligence Center: configured source endpoint as GKE node IP 10.10.1.15, destination endpoint as on-prem token vault 172.16.5.25, protocol TCP, destination port 8443.
  4. The static configuration analysis executed in 3.4 seconds and returned RESULT: DROPPED. The trace breakdown revealed that while firewall rules were evaluated as MATCHED_PERMIT, the routing evaluation failed: a legacy custom static route for destination 172.16.0.0/16 with priority 100 directed traffic to a decommissioned VPN gateway instance that had been shut down three months prior.

Root Cause Analysis

Google Cloud routes traffic using strict route priority (lower number = higher priority). The dynamic BGP routes learned from Cloud Router across Cloud Interconnect had a priority of 1000. However, an orphaned custom static route with priority 100 directed all traffic for 172.16.0.0/16 to the stopped legacy VPN gateway, silently blackholing packets before they could reach Cloud Interconnect.

Defensible Remediation

  1. Deleted the stale custom static route (route-to-legacy-vpn-gateway) from the VPC network routing table.
  2. With the static override removed, Andromeda immediately promoted the Cloud Router dynamic BGP route (priority 1000) as the active best-path route for 172.16.0.0/16.
  3. Re-ran the Network Intelligence Center Connectivity Test to verify the end-to-end path.

Verification & Acceptance

The Connectivity Test immediately returned RESULT: REACHABLE, displaying a complete end-to-end trace through VPC routes, Cloud Router, and Cloud Interconnect handoff. Live payment tokenization requests completed in 4.1ms with a 100% success rate, clearing all checkout errors.

Residual Risk & Preventative Guardrails

Static routes can silently override dynamic BGP routing and break failover semantics. Guardrail: Establish an automated CI/CD policy that bans static RFC 1918 routes in VPCs where Cloud Router BGP is enabled, and schedule automated nightly Connectivity Tests in Network Intelligence Center to alert on route anomalies.

Exercise 1: Configure Cloud DNS Inbound Policy, Authoritative Zone, and Response Policy

Goal: Provision an inbound DNS server policy for hybrid on-premises access, configure an authoritative private zone, and apply a DNS Response Policy (RPZ) to sinkhole a simulated malware domain.

Mode: production practice · Prerequisite: Day 51 exit artifacts.

  1. Create a Cloud DNS Inbound Server Policy: Enable Google's internal metadata resolver to listen for incoming hybrid queries from on-premises networks: 
    gcloud dns policies create hybrid-dns-inbound-policy   --networks=prod-shared-vpc   --enable-inbound-forwarding   --description="Enable inbound DNS forwarding for on-premises hybrid resolvers"
  2. Retrieve Subnet Inbound DNS IP Endpoints: Identify the IP addresses provisioned in each subnet for on-premises resolvers to target: 
    gcloud compute networks subnets describe prod-app-us-east4   --region=us-east4   --format="value(gatewayAddress)"
    Google Cloud provisions the inbound DNS forwarder at the subnet primary gateway address offset (+1 or +2).
  3. Create an Authoritative Private DNS Managed Zone: 
    gcloud dns managed-zones create gcp-internal-zone   --dns-name="gcp.brightloaf.internal."   --description="Private production zone for internal microservices"   --visibility=private   --networks=prod-shared-vpc

gcloud dns record-sets create "api.gcp.brightloaf.internal."   --zone=gcp-internal-zone   --type=A   --ttl=300   --rrdatas=10.10.1.50
  4. Configure a DNS Response Policy (RPZ) Sinkhole: Create a DNS firewall rule to override and sinkhole a malicious C2 domain: 
    gcloud dns response-policies create malware-sinkhole-policy   --networks=prod-shared-vpc   --description="Sinkhole malicious command-and-control domains"

gcloud dns response-policy-rules create block-malware-rule   --response-policy=malware-sinkhole-policy   --dns-name="malicious-c2.attacker.com."   --behavior=override   --local-data=name="malicious-c2.attacker.com.",type=A,ttl=300,rrdatas=127.0.0.1
  5. Verify Local and Sinkhole Resolution: 
    dig +short api.gcp.brightloaf.internal @169.254.169.254
dig +short malicious-c2.attacker.com @169.254.169.254
    Verify that the internal service resolves to 10.10.1.50, while the malicious domain returns 127.0.0.1.
Expected result / acceptance

Cloud DNS successfully answers internal lookups for api.gcp.brightloaf.internal with 10.10.1.50 and immediately sinkholes malicious-c2.attacker.com to loopback 127.0.0.1.

Troubleshooting

If private records return NXDOMAIN, verify that the querying VM belongs to an authorized VPC network and that trailing periods (.) were included in both zone and record names.

Cleanup and cost

Delete response policy rules, response policy, record sets, managed zone, and DNS policy to prevent ongoing hourly zone charges.

Exercise 2: Create a Network Connectivity Center (NCC) Hub and Attach Spoke Networks

  3. Attach Spoke VPC 2 (Analytics) to the NCC Hub:

gcloud network-connectivity hubs describe enterprise-transit-hub

Exercise 3: Configure VPC Flow Logs, Firewall Rules Logging, and Packet Mirroring

Goal: Enable VPC Flow Logs with custom sampling and aggregation intervals, enable firewall rules logging, and extract 5-tuple forensic metrics from Cloud Logging.

Mode: production practice · Prerequisite: Day 51 exit artifacts.

  1. Enable VPC Flow Logs on Subnet: Configure 5-minute aggregation interval, 50% sampling, and full metadata enrichment: 
    gcloud compute networks subnets update prod-app-us-east4   --region=us-east4   --enable-flow-logs   --logging-aggregation-interval=interval-5-min   --logging-flow-sampling=0.5   --logging-metadata=include-all
  2. Enable Firewall Rules Logging on Deny Ingress Rule: 
    gcloud compute firewall-rules update default-deny-ingress   --enable-logging   --logging-metadata=include-all
  3. Generate Network Traffic and Filter Flow Logs in CLI: 
    gcloud logging read   'resource.type="gce_subnetwork" AND logName:"logs/compute.googleapis.com%2Fvpc_flows"'   --limit=5   --format="table(jsonPayload.src_ip,jsonPayload.dest_ip,jsonPayload.dest_port,jsonPayload.bytes_sent,jsonPayload.rtt_msec)"
  4. Inspect Denied Packets in Firewall Audit Logs: 
    gcloud logging read   'resource.type="gce_firewall_rule" AND jsonPayload.disposition="DENIED"'   --limit=5   --format="table(timestamp,jsonPayload.rule_details.reference,jsonPayload.connection.src_ip,jsonPayload.connection.dest_port)"
Expected result / acceptance

VPC Flow Logs output 5-tuple records with packet, byte, and RTT latency metrics. Firewall rules logging reports exact matched rule names with disposition DENIED.

Troubleshooting

If no logs appear immediately, remember that flow logs are buffered according to the aggregation interval (up to 5 minutes). Generate sustained test traffic.

Cleanup and cost

Disable flow logs or reduce sampling rate to 0.1 after completing diagnostics to minimize Cloud Logging storage costs.

Exercise 4: Run a Network Intelligence Center Connectivity Test

Goal: Formally model and test an end-to-end packet path between two instances, diagnosing simulated firewall and routing blocks.

Mode: production practice · Prerequisite: Day 51 exit artifacts.

  1. Create and Execute a Connectivity Test: Model a TCP connection between an application VM and an internal database instance on port 5432: 
    gcloud network-management connectivity-tests create app-to-db-test   --source-instance=projects/prod-payments-01/zones/us-east4-a/instances/payment-worker-01   --destination-instance=projects/prod-data-01/zones/us-east4-b/instances/db-primary-01   --protocol=TCP   --destination-port=5432
  2. Inspect the Reachability Analysis Trace: 
    gcloud network-management connectivity-tests describe app-to-db-test   --format="yaml(reachabilityDetails.result,reachabilityDetails.traces)"
  3. Simulate Failure and Re-verify: Add a firewall rule blocking port 5432, then re-run the test: 
    gcloud compute firewall-rules create block-db-test   --network=prod-shared-vpc   --action=DENY   --rules=tcp:5432   --direction=EGRESS   --priority=500

gcloud network-management connectivity-tests rerun app-to-db-test

gcloud network-management connectivity-tests describe app-to-db-test   --format="get(reachabilityDetails.result)"
    Observe that the result changes from REACHABLE to DROPPED, identifying the exact blocking firewall rule.
Expected result / acceptance

Connectivity Test outputs step-by-step trace evaluation across routes, firewalls, and hypervisor NAT with unambiguous REACHABLE or DROPPED determination.

Troubleshooting

If the test reports UNDETERMINED, verify whether the destination address exists outside Google Cloud (e.g. across hybrid VPN where dynamic live probing is required).

Cleanup and cost

Delete the temporary deny firewall rule and the connectivity test after completing the verification.
