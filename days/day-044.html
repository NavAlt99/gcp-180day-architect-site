Container-native load balancing (NEGs)

Network Endpoint Groups (NEGs) in Google Kubernetes Engine integrate Google Cloud Load Balancing directly with Kubernetes Pod data planes. Rather than routing client traffic through Compute Engine instance groups to an arbitrary worker node's NodePort—where host-level kube-proxy packet filters must translate and forward requests across the cluster network—NEGs register individual Pod IP addresses and container target ports as direct load balancer backends.

This capability belongs on Day 44 because Day 43 established workload controllers and pod lifecycle primitives; today we integrate those workloads into Google Cloud VPC networking. In the end-to-end architecture, NEGs sit at the edge boundary connecting external or internal Google Cloud Application Load Balancers (ALBs) to VPC-native pod interfaces, orchestrated automatically by GKE's background NEG controller without multi-hop latency or client IP address erasure.

Problem preview: During high-traffic flash sales, backend order pods on dense worker nodes suffer CPU starvation and 502 Bad Gateway errors while pods on adjacent nodes sit idle, and upstream security logs show all requests originating from internal node IP addresses rather than external customer clients. Customers experience abandoned shopping carts and checkout failures, while security compliance auditing fails due to client IP masquerading across intermediate nodes.

VPC-native clusters, alias IPs, private clusters, authorized networks

VPC-native GKE clusters use Google Cloud VPC Alias IP ranges to allocate IP addresses to Pods directly from secondary subnet ranges, making every pod a first-class participant in the VPC network without relying on static Google Cloud route table entries. Private clusters isolate worker nodes by stripping external public IP addresses and segregating the Kubernetes API server control plane inside a Google-managed tenant VPC connected across a private VPC Network Peering boundary, protected by Master Authorized Networks.

This topic belongs on Day 44 because it completes the foundational networking established on Day 5 and the cluster provisioning models introduced on Day 42. Architecturally, this topic governs the subnet allocation, routing boundaries, and admission webhook network paths linking customer VPC resources with the Google-managed control plane, enabling secure communication with internal databases and corporate networks.

The core order processing engine halts completely, preventing customer order writes, and emergency autoscaling fails during peak demand due to unrecoverable IP address exhaustion.

Storage

Kubernetes storage in GKE decouples persistent data lifecycle from transient container lifecycles through three distinct abstractions: PersistentVolume (PV) representing physical block or file storage provisioned in Google Cloud; PersistentVolumeClaim (PVC) representing a declarative storage request by a workload; and StorageClass defining the dynamic provisioner, volume type, reclaim policy, volume expansion capabilities, and binding modes.

This topic belongs on Day 44 because Day 37 introduced Compute Engine persistent disks and Day 43 introduced StatefulSets; today we bridge these primitives into production state management. In the platform hierarchy, storage sits between the GKE CSI driver (such as pd.csi.storage.gke.io), the Linux kernel block layer on Compute Engine worker nodes, and regional Google Cloud storage APIs.

Problem preview: After a worker node in zone us-central1-a fails, the order sequence generator pod remains indefinitely stuck in Pending state with volume node affinity conflict, unable to attach its persistent volume to an available node in zone us-central1-b. Transaction sequencing and batch order processing are paralyzed for over two hours, breaching the 15-minute Recovery Time Objective (RTO) and halting regional distribution.

Container-native load balancing (NEGs)

Traditional Kubernetes ingress routing on Google Cloud historically relied on NodePort services. When an external HTTP(S) load balancer received traffic, it dispatched requests to a random node VM on an assigned high-range TCP port (such as 31200). On that node VM, Linux kernel iptables or IPVS packet filters evaluated the KUBE-NODEPORTS chain and performed Destination NAT (DNAT). If the selected target pod was scheduled on a different worker node, the receiving node performed Source NAT (SNAT or MASQUERADE) and routed the packet across the VPC network to the second node. This legacy pattern introduced two severe architectural penalties: a redundant inter-node network hop increasing tail latency, and complete erasure of the original client IP address unless externalTrafficPolicy: Local was configured (which itself created severe load imbalances when pods were unevenly distributed across nodes).

Container-native load balancing eliminates the NodePort middleman. When a Kubernetes Service is annotated with cloud.google.com/neg: '{"ingress": true}', the GKE NEG controller automatically creates a Google Cloud Network Endpoint Group of type GCE_VM_IP_PORT. As pods are scheduled, become ready, or terminate, the NEG controller directly registers and deregisters the individual Pod IP addresses and container target ports with the Google Cloud Backend Service. Google Cloud Load Balancers (both global external Application Load Balancers and regional internal Application Load Balancers) program their Envoy proxy data planes to route HTTP/HTTPS requests straight to the Pod's veth network interface in a single hop.

Furthermore, container-native load balancing revolutionizes health checking and datapath performance. In NodePort configurations, Google Cloud health checks probe the worker node's kube-proxy listener, which reports healthy even if the application container on that node has crashed or entered an unresponsive deadlock. With NEGs, Google Cloud health checks target individual pods at their configured readiness endpoints (such as /healthz). When combined with GKE Dataplane V2 (powered by Cilium and eBPF), intra-cluster and ingress packets bypass iptables connection tracking tables entirely, minimizing CPU packet-processing overhead and maximizing throughput.

Architecture Path: NodePort vs Container-Native (NEG) Ingress
Dimension Legacy NodePort Routing Container-Native NEG Routing Architectural Consequence
Backend Endpoint Type GCE_VM_IP (Instance Group / Node VM) GCE_VM_IP_PORT (Direct Pod IP & Target Port) Direct addressing eliminates intermediate VM port mapping.
Network Hops 2 hops (Client → LB → Node 1 → Node 2 Pod) 1 hop (Client → LB → Target Pod) Removes inter-node forwarding and reduces p99 latency by 15–40ms.
Client Source IP Overwritten by SNAT (MASQUERADE) Fully preserved in L7 headers & L4 proxy sockets Maintains audit fidelity, geo-location, and fraud detection.
Load Balancing Distribution Per-node equal weighting (causes pod imbalance) Per-pod equal weighting across all nodes High-density nodes receive traffic proportional to active pods.
Health Check Scope Node-level kube-proxy listener Direct Pod readiness probe endpoint Unhealthy pods are drained instantly without affecting sibling pods.
Apply it: Standalone vs Ingress-Managed NEGs

GKE supports two operational modes: Ingress-managed NEGs (where creating a GKE Ingress automatically provisions Google Cloud forwarding rules, URL maps, and NEGs) and Standalone NEGs (where a Service creates a NEG via cloud.google.com/neg: '{"exposed_ports": {"80":{}}}' that can be bound to custom Terraform-managed Backend Services or Cross-Region Application Load Balancers).

VPC-native clusters, alias IPs, private clusters, authorized networks

Modern GKE clusters are built as VPC-native clusters by default. In legacy routes-based clusters, pod IP ranges were isolated inside each node, and the cluster manager injected static Google Cloud routes (up to 1 route per node) into the VPC route table. Because Google Cloud VPC networks enforce strict route table quotas (historically 200–300 custom routes), routes-based clusters could not scale to enterprise dimensions and could not route pod traffic directly across Cloud VPN or VPC Network Peering without complex NAT gateways.

VPC-native clusters solve this limitation using VPC Alias IP ranges. When provisioning a VPC-native cluster, you define a primary subnet IP range for Node VMs (such as 10.10.0.0/24) and two secondary IP ranges: one for Pods (such as 10.20.0.0/16) and one for Services / ClusterIPs (such as 10.30.0.0/20). When Compute Engine creates a node VM, GKE assigns an alias IP CIDR block from the secondary Pod range directly to the VM's network interface (NIC). By default, GKE allocates a /24 CIDR (256 addresses) per node to support up to 110 pods. In high-density or IP-constrained architectures, setting --max-pods-per-node=32 configures GKE to assign a /26 CIDR (64 addresses) per node, preserving 75% of your secondary subnet address space.

Private GKE clusters elevate security by decoupling the cluster from the public Internet. Worker nodes are assigned only internal RFC 1918 IP addresses. The Kubernetes API server runs in a Google-managed tenant VPC. A VPC Network Peering connection connects the customer VPC to the master VPC using a reserved /28 master CIDR (such as 172.16.0.0/28). Communication between the control plane and worker nodes utilizes the Konnectivity service (port 8132/443). To secure administrative access, architects can deploy Master Authorized Networks, which restrict API server access to designated CIDR ranges (such as corporate bastions or VPN exit gateways) and reject all other connection attempts.

Architecture Path: VPC-Native Network Subnetting & Control Plane Isolation
Boundary Component CIDR Allocation Network Scope Control & Routing Behavior
Primary Subnet Range 10.10.0.0/24 (256 IPs) Compute Engine Worker Node VMs Allocates node eth0 interfaces; routes VPC traffic and internal SSH/bastion access.
Secondary Range: Pods 10.20.0.0/16 (65,536 IPs) VPC Alias IPs assigned to Pods Directly routable across VPC, peered networks, Cloud Interconnect, and NEGs without NAT.
Secondary Range: Services 10.30.0.0/20 (4,096 IPs) ClusterIP Virtual Addresses Cluster-internal routing only; resolved via CoreDNS and routed via Dataplane V2 eBPF.

Crucial Boundary: Webhook Firewall Rules

Because the Google-managed GKE control plane initiates connections to admission webhooks running inside worker node pods (such as cert-manager, OPA Gatekeeper, or custom mutating webhooks on ports 8443 or 9443), customer VPC firewall rules MUST explicitly permit ingress from the master /28 CIDR to worker node tags. Default VPC firewall rules block these requests, causing deployments to hang.

Storage

Stateful workloads deployed in GKE require persistent, durable block or file storage that survives container restarts, pod evictions, and node upgrades. The Kubernetes Container Storage Interface (CSI) separates storage operations into control plane provisioning and node-level attachment. In GKE, the Compute Engine Persistent Disk CSI driver (pd.csi.storage.gke.io) runs as a control plane deployment managing Google Cloud API calls and a DaemonSet on every worker node managing operating system mounts.

When an application requires persistent storage, it declares a PersistentVolumeClaim referencing a StorageClass. The StorageClass defines key operational behaviors: provisioner (such as pd.csi.storage.gke.io), type (such as pd-balanced, pd-ssd, or hyperdisk-balanced), reclaimPolicy (Delete for ephemeral sandboxes or Retain for enterprise audit ledgers), and allowVolumeExpansion: true (enabling live volume resizing without downtime). When volume expansion is triggered by updating the PVC size, the CSI driver calls the Compute Engine API to resize the disk and instructs the node kernel to resize the filesystem (ext4 or xfs) online.

The most critical architectural parameter for high-availability clusters is volumeBindingMode. By default, legacy storage classes used volumeBindingMode: Immediate, which commands the CSI driver to provision a Compute Engine persistent disk the instant a PVC is created. Because Compute Engine persistent disks are zonal resources, the driver picks an arbitrary zone (such as us-central1-a). If the cluster scheduler subsequently places the consuming Pod on a node in us-central1-b due to resource availability or anti-affinity rules, the attachment fails permanently with a volume node affinity conflict. Configuring volumeBindingMode: WaitForFirstConsumer delays disk creation until the scheduler has bound the Pod to a specific node, ensuring the persistent disk is provisioned in the exact zone where the workload executes.

Architecture Path: GKE CSI Storage Dynamic Provisioning Lifecycle
Lifecycle Phase Executing Component Control Action Verification Artifact
1. Claim Creation Stateful Workload / Developer Applies PersistentVolumeClaim specifying StorageClass and capacity. PVC status reports Pending awaiting consumer.
2. Topology Scheduling kube-scheduler Evaluates node CPU/memory and selects worker node in zone us-central1-b. Pod status transitions to node assignment.
3. Dynamic Provisioning CSI External Provisioner Calls GCP Compute API: gcloud compute disks create --zone=us-central1-b. PV created with node affinity to zone b; PVC enters Bound.
4. Node Attachment CSI External Attacher Calls GCP Compute API: instances.attachDisk targeting selected node VM. Block device appears under /dev/disk/by-id/google-* on host node.
5. Mount & Handover CSI Node Driver & Kubelet Formats device (mkfs.ext4) if new; bind-mounts into pod container directory. Container filesystem mounts volume at designated target path.
Apply it: Zonal PD vs Regional PD

Standard zonal persistent disks can only be mounted by nodes in a single zone. For mission-critical stateful workloads that must withstand zone outages without manual volume snapshots, GKE supports Regional Persistent Disks (replicated synchronously across two zones) configured by adding replication-type: regional-pd and listing both zones in allowedTopologies.

3 · Real-world problem and solution for each topic

Container-native load balancing (NEGs) · field case

Situation and impact: Brightloaf launched an online flash sale for artisan holiday pastries, funneling over 14,000 HTTP requests per second into the primary order-ingress microservice behind a Google Cloud External Application Load Balancer. Within six minutes of launch, 8.4% of checkout requests began failing with 502 Bad Gateway errors. Concurrently, security compliance monitors generated high-severity alerts: incoming audit logs recorded 100% of client traffic originating from internal node IP 10.10.0.14 instead of public customer IPs, violating PCI-DSS data tracing rules and triggering payment processor fraud blocks that halted checkout.

Constraints: Preserve customer order integrity (zero duplicate orders created on replay), maintain zero-downtime rolling updates, operate within current cluster compute quotas, and guarantee end-to-end client IP preservation for financial compliance.

Evidence: Inspecting the GKE Service manifest revealed type: NodePort with no NEG annotations. The load balancer backend service targeted an unmanaged instance group pointing to VM port 31200. Linux kernel metrics on worker node gke-prod-pool-1-a4f2 (IP 10.10.0.14) demonstrated massive conntrack table pressure and 98% CPU core utilization driven by iptables packet evaluation. A packet capture on backend pod veth interfaces confirmed that all incoming packets underwent SNAT with the source IP replaced by the intermediate node's IP. During rolling pod deployments, the load balancer continued spraying traffic to nodes where old pods had already terminated, triggering TCP connection resets.

Root cause: The Ingress utilized legacy NodePort routing rather than Container-Native Load Balancing. Traffic arrived at arbitrary node VMs and was forwarded across the internal cluster network using iptables SNAT (MASQUERADE). This double-hop architecture concentrated packet forwarding through a single node, saturated kernel conntrack tables, caused 502 connection drops, and wiped out original client IP addresses.

Diagnostic sequence:

  1. Run gcloud compute backend-services describe order-backend-svc --global to confirm the backend type was INSTANCE_GROUP rather than NETWORK_ENDPOINT_GROUP.
  2. Execute kubectl get svc order-ingress-svc -o jsonpath='{.metadata.annotations}' to verify the absence of cloud.google.com/neg annotations.
  3. Check node connection tracking with sudo conntrack -C on worker node 10.10.0.14, discovering conntrack utilization exceeding 94% of kernel maximums.
  4. Inspect application container access logs, observing that the X-Forwarded-For header contained internal RFC 1918 node IPs rather than public client source IPs.

Defensible solution: Convert the Service to use Container-Native Load Balancing. Add the annotation cloud.google.com/neg: '{"ingress": true}' to the Service manifest. Update the GKE Ingress to point to this annotated service, triggering GKE's NEG controller to create a GCE_VM_IP_PORT NEG and attach it to the Backend Service. Configure container-level readiness probes on the Pod specification targeting /healthz. Set the Backend Service draining-timeout to 60 seconds to match the Pod's terminationGracePeriodSeconds, ensuring active in-flight checkout transactions finish cleanly before pods terminate.

Verification: Query gcloud compute network-endpoint-groups list to verify the creation of the GKE-managed NEG. Inspect backend endpoints with gcloud compute network-endpoint-groups list-network-endpoints to confirm individual Pod IPs and ports are registered. Issue test requests through the external load balancer IP and verify via application logs that the true public client IP is captured in both the socket source and the X-Forwarded-For header. Re-run load tests at 15,000 requests/sec and confirm 0% 502 errors and even CPU distribution across all worker nodes.

Residual risk: Pod churn during aggressive Horizontal Pod Autoscaling (HPA) scale-down events requires 15–30 seconds for the Google Cloud control plane to deregister network endpoints. Workload pods must handle SIGTERM signals gracefully and honor termination grace periods to prevent dropped connections during rapid scaling down.

VPC-native clusters, alias IPs, private clusters, authorized networks · field case

Situation and impact: Brightloaf initiated a critical security migration, transitioning its production GKE clusters from public-node topologies to hardened Private GKE Clusters with Master Authorized Networks. Immediately following the cutover, an emergency order validation hotfix deployment failed completely. Every execution of kubectl apply failed with: Internal error occurred: failed calling webhook "validate.order.brightloaf.internal": Post "https://order-validator.default.svc:8443": context deadline exceeded. Simultaneously, newly created pods entered an unrecoverable ImagePullBackOff crash loop when attempting to pull third-party schema validators from external container registries. With deployment pipelines locked, zero new releases could reach production.

Constraints: Maintain strict private cluster security posture (zero public IP addresses on worker nodes), retain strict control plane access controls, and restore automated CI/CD pipeline deployments without bypassing admission validation webhooks.

Evidence: The GKE cluster was confirmed as private: node VMs possessed only internal IP addresses (10.10.0.0/24), and the control plane master CIDR was provisioned as 172.16.0.0/28. The mutating/validating webhook pod was running healthy and listening on TCP port 8443 on worker node 10.10.0.12. Testing local container connectivity within the cluster succeeded, but requests from the API server failed. VPC firewall rules revealed that the default network firewall configuration only allowed intra-cluster node traffic (10.10.0.0/24), with no rule permitting traffic from the master CIDR 172.16.0.0/28 across the VPC peering boundary. Additionally, the region us-central1 lacked a Cloud NAT gateway, meaning private nodes had no egress route to the public Internet.

Root cause: Two critical network boundaries were broken: (1) Missing ingress firewall rule permitting traffic from the Google-managed master CIDR (172.16.0.0/28) to worker node target port 8443, causing the API server's admission review calls to be silently dropped by VPC firewall filters; (2) Absence of a regional Cloud NAT gateway on the private subnet, causing all outbound Internet requests (for container image pulls and external public APIs) to be blackholed.

Diagnostic sequence:

  1. Inspect API server failure events with kubectl get events --sort-by='.metadata.creationTimestamp', identifying repeated context deadline exceeded errors targeting port 8443.
  2. Query VPC firewall rules with gcloud compute firewall-rules list --filter="network:prod-vpc", verifying that no rule permitted source range 172.16.0.0/28 on port 8443.
  3. Check node Internet connectivity by running an ephemeral diagnostic container and issuing curl -I https://gcr.io, observing 100% packet loss and connection timeouts.
  4. Verify Cloud NAT configuration with gcloud compute routers nats list --router=prod-router --region=us-central1, confirming zero NAT gateways were configured.

Defensible solution: First, create a dedicated VPC firewall rule allowing ingress from the GKE master CIDR 172.16.0.0/28 to target node tags on TCP port 8443. Second, deploy a regional Cloud Router and Cloud NAT gateway in us-central1 configured for the cluster's primary and secondary subnet ranges, enabling private nodes and pods to securely access external container registries and APIs without assigning public IP addresses. Third, configure Master Authorized Networks with corporate VPN CIDRs to secure administrative access to the private cluster endpoint.

Verification: Re-run kubectl apply -f order-validation-hotfix.yaml and observe that the validating webhook intercepts and accepts the resource in under 5 milliseconds. Inspect pod startup events to verify that container images are pulled successfully through Cloud NAT with zero ImagePullBackOff errors. Inspect Cloud NAT translation metrics in Cloud Monitoring (compute.googleapis.com/nat/allocated_addresses) to confirm active outbound sessions.

Residual risk: If custom admission webhooks fail internally or crash, the API server will reject all matching workload deployments unless the webhook configuration sets failurePolicy: Ignore. In production, mission-critical webhooks must run multiple replicas spread across zones with horizontal pod autoscaling.

Storage · field case

Situation and impact: Brightloaf's transactional Order Sequencer—a stateful service responsible for generating globally monotonic order IDs and maintaining the uncommitted order ledger—was hosted in a multi-zone GKE cluster across us-central1-a, us-central1-b, and us-central1-c. During scheduled Compute Engine host maintenance, worker node gke-node-a-01 in zone us-central1-a was cordoned and drained. The sequencer pod terminated cleanly, but when the Kubernetes scheduler attempted to place the pod on an available node in zone us-central1-b, the pod entered a persistent Pending state. Scheduling events reported: FailedScheduling: 0/3 nodes available: 1 node had untolerated taint, 2 nodes had volume node affinity conflict. Order generation was blocked across all retail branches for 48 minutes, breaching the 15-minute RTO.

Constraints: Preserve transaction ledger data without loss or corruption, enforce exactly-one active writer on the block volume (ReadWriteOnce), and guarantee rapid automated failover across availability zones without requiring manual disk recreation.

Evidence: The Order Sequencer PVC requested a 200Gi volume backed by StorageClass standard-rwo. Inspecting the StorageClass definition via kubectl get sc standard-rwo -o yaml revealed volumeBindingMode: Immediate. The underlying PersistentVolume was a zonal Compute Engine persistent disk created in us-central1-a. When node gke-node-a-01 was drained, zone us-central1-a had zero remaining worker nodes with sufficient memory headroom, forcing the scheduler to pick a node in zone us-central1-b. However, Compute Engine persistent disks are zonal constructs physically confined to the hardware fabric of a single data center; a zonal disk provisioned in zone a cannot be attached to a virtual machine running in zone b.

Root cause: The StorageClass was configured with volumeBindingMode: Immediate without multi-zone topology awareness. The persistent disk was provisioned in zone us-central1-a the moment the PVC was created, long before pod scheduling occurred. When the host node failed and capacity shifted to another zone, the zonal disk could not cross zone boundaries, deadlocking the scheduler.

Diagnostic sequence:

  1. Describe the pending pod with kubectl describe pod order-sequencer-0, confirming the volume node affinity conflict error.
  2. Inspect the persistent volume with kubectl get pv pvc-48df... -o yaml, observing the topology constraint: topology.gke.io/zone: us-central1-a.
  3. Check zone node availability with kubectl get nodes -L topology.gke.io/zone, verifying that all nodes in zone us-central1-a were either cordoned or memory-saturated.
  4. Inspect the StorageClass with kubectl describe sc standard-rwo, discovering VolumeBindingMode: Immediate and missing topology constraints.

Defensible solution: Create an updated, topology-aware StorageClass named regional-order-sc configured with provisioner: pd.csi.storage.gke.io, volumeBindingMode: WaitForFirstConsumer, and allowVolumeExpansion: true. For workloads requiring high availability across zone maintenance windows without manual data restoration, configure parameters.type: pd-balanced with replication-type: regional-pd and specify allowedTopologies encompassing both us-central1-a and us-central1-b. Update the StatefulSet volumeClaimTemplates to reference this new StorageClass, ensuring that the CSI driver only creates the volume after the scheduler selects a viable node, or provisions a synchronously replicated Regional Persistent Disk that attaches seamlessly in either zone.

Verification: Deploy the updated StatefulSet and observe that the PVC remains in Pending state until the pod is scheduled. Trigger a node drain with kubectl drain gke-node-a-01 --ignore-daemonsets --delete-emptydir-data. Verify that the pod is rescheduled to a node in zone us-central1-b, the Regional PD successfully attaches to the new node within 14 seconds, the filesystem mounts cleanly, and order sequencing resumes without ledger corruption.

Residual risk: Regional Persistent Disks incur approximately 2x the raw disk cost of zonal disks and introduce slight write latency overhead due to synchronous cross-zone replication. Workload throughput must be monitored to ensure synchronous writes meet application latency budgets.

Exercise 1: Tracing Pod-to-Service Traffic, Dataplane V2 eBPF, & Container-Native Ingress (NEGs)

  5. Trace Documented CNI vs Dataplane V2 Packet Path. Execute a diagnostic trace comparing intra-cluster service resolution: 
    python3 - <<'EOF'
# Documented CNI Comparison:
# Path A: Standard kube-proxy iptables:
# Packet: Pod A (10.20.1.5) -> kernel netfilter PREROUTING -> KUBE-SERVICES chain ->
# KUBE-SVC-XXX -> KUBE-SEP-XXX (DNAT to Pod B: 10.20.2.8:8080) -> eth0 -> inter-node SNAT -> Pod B.
# Overhead: O(N) linear rule evaluation across thousands of iptables chains.

# Path B: GKE Dataplane V2 (Cilium eBPF):
# Application Syscall: Pod A connect(10.30.0.10:80) [ClusterIP]
# eBPF Hook: sock_ops program intercepts sys_connect before packet creation
# Map Lookup: BPF hash map cilium_lb4_services_v2 translates (10.30.0.10:80 -> 10.20.2.8:8080)
# Result: Socket destination mutated in memory to Pod B IP directly.
# Overhead: O(1) constant-time hash lookup; 0 iptables rules traversed.
print("=== TRACE COMPARISON DOCUMENTED ===")
print("Standard CNI (kube-proxy): Linear iptables traversal + intermediate node SNAT")
print("Dataplane V2 (eBPF): Socket-level translation at connect() syscall + direct VPC routing")
EOF
  6. Verify Ingress Packet Path and Client Source IP. Obtain the external ingress IP, issue a test request, and inspect logs:

curl -s -D - "http://${INGRESS_IP}/" -o /dev/null

    Confirm that the cluster is VPC-native; standard routes-based clusters cannot bind Pod IPs directly to NEGs.

gcloud compute backend-services list --filter="name~order-ingress" --format="value(name)"

Exercise 2: VPC-Native IP Planning, Private Cluster Boundaries, & Master Authorized Networks

Goal: Calculate secondary subnet allocations for a VPC-native cluster, verify control plane isolation in a private GKE cluster, configure master-to-webhook firewall rules, and restrict administrative access with Master Authorized Networks.

Expected result: Documented subnet allocation plan supporting high-density nodes, successful admission webhook execution across the master peering boundary, and verified rejection of unauthorized administrative CIDRs.

Mode: tabletop / design · Prerequisite: Day 43, Day 5 exit artifacts.

  1. Preflight. Verify Google Cloud VPC network configuration: 
    export VPC_NAME="brightloaf-vpc"
export SUBNET_NAME="gke-subnet"
export REGION="us-central1"
gcloud compute networks subnets describe ${SUBNET_NAME} --region=${REGION} --format="yaml(ipCidrRange,secondaryIpRanges)"
  2. Execute Subnet Calculation. Model primary and secondary IP ranges for a 200-node cluster: 
    python3 - <<'EOF'
# Node VMs: /24 (256 addresses) -> supports up to 250 nodes
# Pod Secondary Range: default 110 pods allocates /24 per node (requires /16 for 256 nodes)
# Optimized: max-pods-per-node=32 allocates /26 per node (64 IPs per node)
nodes = 200
ips_per_node_default = 256  # /24
ips_per_node_optimized = 64 # /26
print(f"Default Pod CIDR required: {nodes * ips_per_node_default} IPs (Minimum /16 required)")
print(f"Optimized Pod CIDR required: {nodes * ips_per_node_optimized} IPs (Minimum /18 required)")
print(f"IP space conserved: {((nodes*ips_per_node_default) - (nodes*ips_per_node_optimized))} addresses saved")
EOF
  3. Define VPC Firewall Rule for Admission Webhooks. Author a firewall rule allowing the Google-managed master CIDR (172.16.0.0/28) to reach worker node admission webhooks on port 8443: 
    gcloud compute firewall-rules create allow-gke-master-to-webhook \
    --network=${VPC_NAME} \
    --action=ALLOW \
    --direction=INGRESS \
    --source-ranges=172.16.0.0/28 \
    --target-tags=gke-brightloaf-node \
    --rules=tcp:8443,tcp:9443,tcp:10250 \
    --description="Allow GKE master control plane to reach node admission webhooks and kubelet"
  4. Configure Master Authorized Networks. Restrict access to the private cluster's API server endpoint: 
    gcloud container clusters update ${CLUSTER_NAME} \
    --region=${REGION} \
    --enable-master-authorized-networks \
    --master-authorized-networks="198.51.100.0/24,203.0.113.50/32"
  5. Deploy Regional Cloud NAT for Private Node Egress. Configure outbound NAT translation so private nodes without external IPs can pull container images: 
    gcloud compute routers create gke-nat-router \
    --network=${VPC_NAME} \
    --region=${REGION}

gcloud compute routers nats create gke-nat-gateway \
    --router=gke-nat-router \
    --region=${REGION} \
    --auto-allocate-nat-external-ips \
    --nat-all-subnet-ip-ranges \
    --enable-logging
  6. Verification. Verify firewall and NAT deployment: 
    gcloud compute firewall-rules describe allow-gke-master-to-webhook
gcloud compute routers nats describe gke-nat-gateway --router=gke-nat-router --region=${REGION}
kubectl get validatingwebhookconfigurations -o wide
    Confirm that the control plane invokes webhook admission reviews without context deadline timeouts.
  7. Troubleshooting. If admission webhooks fail with timeout: 
    gcloud compute firewall-rules list --filter="network:${VPC_NAME} AND direction=INGRESS"
gcloud logging read 'resource.type="gce_subnetwork" AND logName:"logs/compute.googleapis.com%2Ffirewall"' --limit=10
    Ensure that worker nodes actually possess the network tag gke-brightloaf-node matching the firewall rule target.
  8. Cleanup. Delete created firewall rule and Cloud NAT gateway: 
    gcloud compute routers nats delete gke-nat-gateway --router=gke-nat-router --region=${REGION} --quiet
gcloud compute routers delete gke-nat-router --region=${REGION} --quiet
gcloud compute firewall-rules delete allow-gke-master-to-webhook --quiet
  9. Artifact Acceptance. Save the IP allocation calculation and firewall rule definition in day-044-networking-storage.md.
Expected result / acceptance

A mathematically validated subnet allocation model, operational Cloud NAT gateway, and active VPC firewall rule protecting master-to-node admission webhook reviews.

Troubleshooting

Do not overlap master /28 CIDR blocks with any customer VPC subnet ranges, on-premises networks connected via VPN, or secondary pod/service ranges; master peering will fail if address collision occurs.

Cleanup and cost

Deleting Cloud NAT and Cloud Router terminates the hourly NAT gateway uptime charge while keeping the underlying VPC subnet configuration intact.

Exercise 3: CSI StorageClass Dynamic Provisioning, Volume Expansion, & Topology Binding

Goal: Deploy a topology-aware StorageClass using WaitForFirstConsumer, dynamically provision a Compute Engine persistent disk via a StatefulSet, perform live online volume expansion, and verify failover across zones.

Expected result: PersistentVolume is provisioned dynamically in the exact zone selected by the Kubernetes scheduler; updating the PVC size resizes the underlying GCE persistent disk and node filesystem without downtime or volume affinity conflicts.

Mode: tabletop / design · Prerequisite: Day 43, Day 37 exit artifacts.

  1. Preflight. Verify GKE CSI driver installation and cluster zones: 
    kubectl get csidrivers
kubectl get nodes -L topology.gke.io/zone
    Confirm that pd.csi.storage.gke.io is active in the cluster.
  2. Author the Topology-Aware StorageClass. Save this definition as storageclass-topology.yaml: 
    cat <<'EOF' > storageclass-topology.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: topology-balanced-sc
provisioner: pd.csi.storage.gke.io
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
reclaimPolicy: Delete
parameters:
  type: pd-balanced
allowedTopologies:
- matchLabelExpressions:
  - key: topology.gke.io/zone
    values:
    - us-central1-a
    - us-central1-b
EOF
  3. Apply StorageClass and Author StatefulSet. Deploy the StorageClass and create a stateful workload referencing it: 
    kubectl apply -f storageclass-topology.yaml

cat <<'EOF' > stateful-order-sequencer.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: order-sequencer
  namespace: default
spec:
  serviceName: "order-sequencer-headless"
  replicas: 1
  selector:
    matchLabels:
      app: order-sequencer
  template:
    metadata:
      labels:
        app: order-sequencer
    spec:
      containers:
      - name: ledger
        image: mirror.gcr.io/library/busybox:1.36
        command: ["sh", "-c", "while true; do date >> /data/ledger.log; sleep 1; done"]
        volumeMounts:
        - name: ledger-data
          mountPath: /data
  volumeClaimTemplates:
  - metadata:
      name: ledger-data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: topology-balanced-sc
      resources:
        requests:
          storage: 10Gi
EOF
kubectl apply -f stateful-order-sequencer.yaml
  4. Verify Topology Binding and Dynamic Provisioning Trace. Observe how the PVC remains in Pending until the Pod is assigned a node, then transitions to Bound in the matching zone: 
    kubectl get pvc
kubectl get pods -l app=order-sequencer -o wide
POD_ZONE=$(kubectl get pods order-sequencer-0 -o jsonpath='{.spec.nodeName}' | xargs -I {} kubectl get node {} -o jsonpath='{.metadata.labels.topology\.gke\.io/zone}')
PV_ZONE=$(kubectl get pv $(kubectl get pvc ledger-data-order-sequencer-0 -o jsonpath='{.spec.volumeName}') -o jsonpath='{.metadata.labels.topology\.gke\.io/zone}')
echo "Pod Zone: ${POD_ZONE} | PV Zone: ${PV_ZONE}"
    Confirm that POD_ZONE exactly equals PV_ZONE.
  5. Execute Online Volume Expansion. Expand the PVC from 10Gi to 20Gi without restarting the pod: 
    kubectl patch pvc ledger-data-order-sequencer-0 -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
sleep 15
kubectl get pvc ledger-data-order-sequencer-0
kubectl exec order-sequencer-0 -- df -h /data
    Confirm that the mounted filesystem reflects the expanded 20Gi capacity.
  6. Troubleshooting. If the PVC remains stuck in Pending indefinitely: 
    kubectl describe pvc ledger-data-order-sequencer-0
kubectl describe pod order-sequencer-0
    Verify that the pod scheduler can find a node with available CPU and memory in the zones listed under allowedTopologies.
  7. Cleanup. Delete StatefulSet, PVCs, and StorageClass: 
    kubectl delete -f stateful-order-sequencer.yaml
kubectl delete pvc ledger-data-order-sequencer-0
kubectl delete -f storageclass-topology.yaml
  8. Artifact Acceptance. Assemble the exit evidence: save the complete packet path and CSI storage topology diagram with managed-service boundaries into day-044-networking-storage.md.
Expected result / acceptance

A verified PersistentVolume dynamic binding matching the pod's scheduled zone, followed by an online non-disruptive filesystem expansion from 10Gi to 20Gi.

Troubleshooting

Persistent disk volume expansion is irreversible; you cannot shrink a PVC or PV once expanded. If online resize does not reflect inside the pod, check if the underlying filesystem (ext4 vs xfs) requires pod remounting.

Cleanup and cost

Deleting the PVC triggers the StorageClass reclaimPolicy (Delete), which automatically calls the Compute Engine API to destroy the persistent disk, preventing persistent storage charges.
