Part 1 · Topics of the day

Git fundamentals (branch, merge, PR)

What it is. Git is a distributed version control system that records changes to a directory of files as an immutable, cryptographically hashed directed acyclic graph (DAG) of commit objects. A branch is a movable pointer to a specific commit, allowing isolated parallel exploration; merging integrates divergent commit histories through fast-forward or three-way merge operations; a pull request (PR) or merge request provides an asynchronous peer review, automated validation gate, and audit checkpoint before integrating code into the primary production trunk.

Why today. In modern cloud architecture, infrastructure (Terraform), cluster state (Kubernetes manifests), and microservice configurations are declared as code. Establishing rigorous Git hygiene, branch isolation, and review controls is the prerequisite for reliable GitOps and CI/CD delivery pipelines.

System location. Git repositories sit at the developer workstation and remote code forges (such as Cloud Source Repositories, GitHub, or GitLab), serving as the single source of truth triggering Cloud Build pipelines and deployment controllers.

Problem preview. A developer directly pushes an unreviewed schema change to the main branch, triggering an automated pipeline that deploys a broken order validation model to production. Checkout immediately halts with HTTP 400 validation failures, creating cart abandonment and blocking critical order fulfillment.

REST APIs and JSON

What it is. Representational State Transfer (REST) is an architectural style for networked systems characterized by stateless client-server interactions, resource-oriented URIs, standard HTTP request verbs (GET, POST, PUT, DELETE, PATCH), and standardized HTTP response status codes. JavaScript Object Notation (JSON) is the universal, language-agnostic text serialization format for transmitting structured key-value maps, arrays, strings, numbers, and boolean primitives over HTTP.

Why today. Google Cloud management APIs, Kubernetes control planes, and cloud-native microservices communicate primarily via RESTful HTTP/JSON interfaces. Cloud architects must understand payload contracts, status code semantics, and defensive parsing boundaries to build resilient service integrations.

System location. RESTful HTTP/JSON interfaces operate across ingress load balancers, API gateways, Cloud Run microservice endpoints, and third-party payment and carrier webhook integrations.

Problem preview. An upstream payment gateway webhook transmits an unexpected JSON error schema with missing order identifiers during a checkout retry, causing the Order API to crash with an unhandled parser exception. Shoppers are billed without receiving confirmation, flooding customer support with payment disputes and delaying warehouse dispatch.

Part 2 · Technical discussion

Git fundamentals (branch, merge, PR)

Git treats project history as a snapshot stream rather than file-by-file delta diffs. Every commit is identified by a unique cryptographic hash (SHA-1 or SHA-256) calculated over its directory tree, author identity, parent commit hashes, and commit message. Because commit identifiers are cryptographically linked to their entire ancestry, history cannot be altered without changing all subsequent hashes, providing an immutable audit trail for cloud infrastructure declarations.

Branching creates a named reference pointing to a commit. In trunk-based development, engineers maintain a protected primary branch (typically main) representing production-ready code. Developers branch from main to create short-lived feature branches (such as feature/order-tax). Merging reconciles divergent histories: a fast-forward merge simply advances the branch pointer when no divergent commits exist on main, whereas a non-fast-forward merge creates a dedicated merge commit joining two divergent lines of history. In cloud deployment pipelines, squash merging is frequently favored because it condenses a multi-commit feature branch into a single atomic, bisectable commit on the trunk.

The Pull Request (PR) workflow introduces governance and automated validation before integration. Protected branch policies require pull requests to pass automated continuous integration (CI) gates—such as static code analysis, linter checks, and unit tests—and require sign-off from authorized peer reviewers before code can enter main. In GitOps architectures, committing or merging to main serves as the automated trigger for deployment engines (such as Cloud Build or Config Sync), ensuring that running cloud environments strictly reflect audited, version-controlled repository state.

REST APIs and JSON

RESTful architectures model services as hierarchically named resources exposed over standard HTTP. A resource identifier is represented as a URI path (such as /v1/orders for a collection, or /v1/orders/BL-14-1001 for an individual instance). Clients interact with resources using standardized HTTP verbs. Method semantics dictate safety and idempotency: GET and HEAD are safe and idempotent (they perform reads without modifying server state); PUT and DELETE are idempotent but modify state (repeating the exact request yields the identical resulting state); while POST is neither safe nor inherently idempotent (invoking it repeatedly creates multiple distinct resources unless explicit application deduplication is implemented).

JSON represents structured data using lightweight human-readable syntax composed of two structural forms: associative key-value objects enclosed in curly braces {}, and ordered sequences of values enclosed in square brackets []. Keys must be double-quoted strings. Values may be strings, numbers, booleans (true, false), null, or nested objects and arrays. RESTful APIs negotiate payload serialization using the Content-Type: application/json request and response header. Servers must validate JSON syntax defensively: malformed JSON (such as unquoted keys or trailing commas) must be rejected with HTTP 400 Bad Request before attempting to parse business fields.

HTTP status codes provide standardized signaling across failure domains. Success responses occupy the 2xx class (200 OK for query results, 201 Created for newly persisted entities). Client errors occupy the 4xx class (400 Bad Request for malformed payloads, 404 Not Found for absent resources, 409 Conflict for duplicate unique keys, and 422 Unprocessable Entity for syntactically valid JSON that violates domain validation rules). Server errors occupy the 5xx class (500 Internal Server Error for unhandled crashes, 502 Bad Gateway when an upstream proxy returns an invalid response, and 504 Gateway Timeout when a backend dependency fails to respond in time). To guarantee the business invariant that an order is fulfilled at most once ($\le 1$ physical fulfillment), APIs implementing POST /v1/orders must require an Idempotency-Key header, ensuring client retries across transient network drops return the original confirmed response without duplicate order creation.

Part 3 · Real-world problems and solutions

Incident exercise · Unreviewed commit to main breaks checkout schema

Illustrative scenario—not an observed production incident. In an urgent effort to support an upcoming regional marketing campaign, a developer modified Brightloaf's Order API JSON payload model. The developer renamed the core field order_id to id and added a mandatory postal_code_ext string field to the JSON schema. Believing the change was minor and under pressure to meet a deadline, the developer bypassed local feature branching and executed a direct a direct push to origin main to the team's central repository. The repository had no branch protection rules enabled on main. Cloud Build immediately detected the new commit on the trunk branch, triggered an automated container build, and deployed the new container revision to the production Cloud Run Order API service. Within 30 seconds, 100% of production checkout transactions initiated by mobile app shoppers began failing with HTTP 400 Bad Request errors. Because the mobile client continued transmitting the established payload containing order_id, the newly deployed service rejected the requests for missing the required id field. Customer shopping carts were abandoned en masse, and order intake completely halted during the evening peak.

Constraints and operational invariants: Checkout operations must be restored immediately; production deployment pipelines must guarantee that breaking API schema changes cannot be merged without verification; and all recovery actions must strictly preserve Brightloaf's fundamental duplicate fulfillment invariant: a retried order submission or replayed event must never cause duplicate physical warehouse fulfillment (<= 1 fulfillment per unique order ID).

Evidence and root cause: Review of repository Git history using the commit log on main identified an unreviewed commit (commit 4f9b81a) authored directly on main without a pull request reference. Cloud Run service revision logs confirmed that the deployment coincided with the commit timestamp, and container logs recorded thousands of schema validation errors: Missing required field: id. The root cause was operational failure to enforce branch protection and automated pull request verification: allowing direct write access to main bypassed peer code reviews and automated backward-compatibility tests, permitting a breaking API contract regression to reach production unchallenged.

Diagnostic sequence:

  1. Inspect Cloud Run traffic metrics and error logs to identify the exact timestamp and revision identifier associated with the surge in HTTP 400 responses.
  2. Query the repository Git log on main to isolate recent commits deployed around the incident onset.
  3. Execute the commit diff between HEAD~1 and HEAD to examine the specific code modifications introduced in the culprit commit.
  4. Review repository branch configuration settings to verify whether branch protection rules and required status checks are active on main.
  5. Inspect the Order API schema definition and test fixtures to verify whether backward-compatibility aliases exist for legacy client payloads.

Defensible solution: Execute a two-phase remediation: First, immediate operational recovery: in Cloud Run, execute an instant traffic rollback to the previous healthy container revision, restoring checkout intake in under 30 seconds. In Git, create a clean rollback commit using the revert command targeting commit 4f9b81a and push it to main to align repository state with running production. Second, architectural prevention: enable GitHub/GitLab Branch Protection on main, requiring that: (a) all code changes originate from feature branches; (b) pull requests require at least two approving reviews from designated Principal Architects; and (c) Cloud Build automated CI checks—including unit tests, linter checks, and an automated JSON schema compatibility test suite—must pass before merging. Ensure all future schema updates provide backward-compatible field aliases (e.g. accepting both order_id and id) until client version deprecation cycles complete.

Verification and residual risk: Submit synthetic checkout requests using both legacy and updated JSON schemas; verify that both return HTTP 201 Created; attempt a direct a direct push to main from a developer workstation and verify that the remote Git server rejects the push with an error enforcing branch protection; verify that retried orders hit the database primary key and never generate duplicate warehouse fulfillment. Residual risk: While branch protection guards against unauthorized trunk pushes, emergency "hotfixes" during live production outages can tempt engineers to request temporary bypasses; emergency break-glass procedures must require post-incident auditing and mandatory peer reconciliation within 24 hours.

Incident exercise · Unhandled JSON error schema causes duplicate billing

Illustrative scenario—not an observed production incident. Brightloaf's Order API integrates with an external third-party payment gateway to authorize customer credit card charges during checkout. Under standard operating conditions, the gateway returns a 200 OK JSON payload containing {"status": "APPROVED", "transaction_id": "TX-9901"} or a 400 Bad Request JSON payload containing {"status": "DECLINED", "error_code": 104}. However, during a high-concurrency flash sale, the payment gateway's front-facing reverse proxy became saturated. When the Order API dispatched an authorization request, the gateway's proxy timed out and returned an HTTP 502 Bad Gateway response with an HTML body (<html><head><title>502 Bad Gateway</title>...) and a Content-Type: text/html header. The Order API's payment integration client, having assumed all responses would be JSON, immediately executed json.loads(response.text) without checking status codes or content types. The Python runtime raised an unhandled json.decoder.JSONDecodeError exception, terminating the request thread and causing the Order API to emit an HTTP 500 Internal Server Error to the shopper's browser. Believing the order had failed, the shopper clicked the checkout button a second time. Because the Order API did not supply a client-generated Idempotency-Key header to the gateway, and because the first payment attempt had actually succeeded in the gateway's backend before the proxy timeout, the gateway processed the second request as a completely new charge. The customer's credit card was billed twice for a single order of bread, while the Order API only recorded one confirmation in its database.

Constraints and operational invariants: Third-party network responses cannot be assumed to be healthy or valid JSON; network timeouts and upstream 5xx errors are routine operational occurrences; under all conditions of network retry, proxy timeout, or gateway malfunction, Brightloaf must strictly preserve the duplicate fulfillment invariant: a customer purchase must never result in duplicate physical shipments or unauthorized duplicate financial billing (<= 1 fulfillment per unique order ID).

Evidence and root cause: Application error logs in Cloud Logging revealed unhandled JSONDecodeError: Expecting value: line 1 column 1 (char 0) exceptions coinciding with outgoing payment calls. Payment gateway settlement statements showed duplicate transaction authorizations for the same order UUID within 45 seconds. The root cause was two-fold: (1) fragile, unvalidated JSON deserialization that blindly attempted to parse non-JSON responses without inspecting HTTP status codes or the Content-Type response header; and (2) absence of header-based idempotency keys on payment authorization calls, converting routine network timeouts and user retries into duplicate financial transactions.

Diagnostic sequence:

  1. Query Cloud Logging for severity >= ERROR entries containing JSONDecodeError across all Order API microservice instances.
  2. Inspect HTTP response headers returned by the upstream payment gateway during the error period, specifically examining Content-Type and status codes.
  3. Correlate application exception timestamps with payment gateway merchant transaction logs to identify unacknowledged yet captured payments.
  4. Audit the payment client source code to verify whether HTTP response status codes are checked prior to payload deserialization.
  5. Inspect payment API request payloads to determine whether unique idempotency tokens (such as Idempotency-Key) are transmitted with outgoing payment authorizations.

Defensible solution: Implement a robust, defensive REST client protocol: First, update the payment integration client to inspect the HTTP response status code and verify that the Content-Type header contains application/json before attempting deserialization; wrap all parsing logic in defensive exception handling that captures json.JSONDecodeError and converts upstream 502/504 errors into a standardized, retryable internal error object. Second, implement strict idempotency handling: generate a unique client idempotency token (e.g. Idempotency-Key: BL-14-ORD-<uuid>) derived from the order session and transmit it as an HTTP header on every payment authorization call, ensuring the gateway's deduplication engine treats retried calls as idempotent queries. Third, reconcile unacknowledged payments via an asynchronous worker that polls the gateway transaction status before allowing secondary checkout attempts.

Verification and residual risk: Execute synthetic API integration tests supplying: (a) a valid 200 JSON payload, (b) an upstream HTML 502 error page, and (c) a malformed JSON payload; verify that the client parses valid responses cleanly and handles HTML/malformed payloads gracefully without crashing; verify that submitting identical requests with the same Idempotency-Key returns the original authorization without generating a second charge; verify that duplicate fulfillment events are suppressed. Residual risk: Upstream third-party payment gateways maintain their own internal idempotency cache TTL (typically 24 hours); if a client retry occurs after the gateway cache expires, the gateway may fail to detect the duplicate, requiring secondary reconciliation via daily bank settlement batches.

Lab 14.2 · REST API contracts, JSON parsing, and defensive error handling

Goal and expected result. Implement a robust Python REST client function that validates response headers, parses valid JSON payloads, catches malformed syntax, and handles upstream non-JSON 502 responses gracefully. Verify that duplicate submissions preserve the $\le 1$ fulfillment invariant.

Mode. Local terminal with Python 3 standard library (json module).

1. Author the defensive REST API parsing engine

cat > "$LAB_DIR/day14_api.py" <<'PY'
import json
import sys

def parse_api_response(raw_payload, content_type="application/json"):
    """
    Defensively parses API responses, checking Content-Type header
    before attempting JSON deserialization.
    """
    if "application/json" not in content_type:
        return {
            "status": "ERROR",
            "http_code": 502,
            "error_type": "InvalidContentType",
            "message": f"Expected application/json but received: {content_type}",
            "snippet": raw_payload[:60]
        }
    try:
        data = json.loads(raw_payload)
        return {
            "status": "SUCCESS",
            "http_code": 200,
            "data": data
        }
    except json.JSONDecodeError as err:
        return {
            "status": "ERROR",
            "http_code": 400,
            "error_type": "MalformedJSON",
            "message": f"Syntax error at line {err.lineno}, col {err.colno}: {err.msg}"
        }

# Simulated test fixtures
TEST_1_VALID = '{"order_id": "BL-14-1001", "status": "CONFIRMED", "total": 16.20}'
TEST_2_MALFORMED = '{"order_id": "BL-14-1001", status: UNQUOTED_VAL}'
TEST_3_GATEWAY_HTML = '<html><head><title>502 Bad Gateway</title></head><body>Gateway Timeout</body></html>'

print("=== Running REST API Defensive Parser Tests ===")
r1 = parse_api_response(TEST_1_VALID, "application/json")
print(f"Test 1 (Valid 200):     Status={r1['status']}, Code={r1['http_code']}, OrderID={r1['data']['order_id']}")

r2 = parse_api_response(TEST_2_MALFORMED, "application/json")
print(f"Test 2 (Malformed 400): Status={r2['status']}, Code={r2['http_code']}, Error={r2['error_type']}")

r3 = parse_api_response(TEST_3_GATEWAY_HTML, "text/html")
print(f"Test 3 (Non-JSON 502):  Status={r3['status']}, Code={r3['http_code']}, Error={r3['error_type']}")

# Verify Invariant: Idempotent duplicate check
order_cache = set()
def process_order(order_id, idempotency_key):
    if idempotency_key in order_cache:
        return {"order_id": order_id, "new_fulfillment": False, "status": "ALREADY_PROCESSED"}
    order_cache.add(idempotency_key)
    return {"order_id": order_id, "new_fulfillment": True, "status": "FULFILLMENT_DISPATCHED"}

p1 = process_order("BL-14-1001", "key-7b8f")
p2 = process_order("BL-14-1001", "key-7b8f") # Duplicate retry
print(f"\n=== Idempotency Invariant Check ===")
print(f"First Submission:  new_fulfillment={p1['new_fulfillment']} ({p1['status']})")
print(f"Second Submission: new_fulfillment={p2['new_fulfillment']} ({p2['status']})")
assert p1["new_fulfillment"] is True
assert p2["new_fulfillment"] is False
print("Fulfillment invariant strictly verified: <= 1 fulfillment per order key.")
