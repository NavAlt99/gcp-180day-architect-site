3 · Real-world problem and solution for each topic

1. Synthesize the existing capstone package and address review findings · field case

Enterprise scenario: During the capstone review, a stakeholder identified that the reliability model did not include the impact of regional outages on the multi‑region failover path, potentially overstating availability. The model assumed independent regional failures.

Failure symptoms and impact: If a regional outage occurs, the actual availability could drop to 99.9%, violating the SLO and causing potential breach of customer commitments. Financial penalties and loss of trust could result.

Constraints: Must use only publicly available SLO values from Google Cloud documentation; cannot assume unpublished internal metrics; must keep the model understandable to non‑technical stakeholders.

Evidence:

Reviewer comment captured in the capstone review document:

"The reliability model treats regional failures as independent, which is unrealistic given shared infrastructure risks. Please update the model to reflect correlated failure probabilities using Google's published outage data."

Excerpt from the original reliability_model.txt showing the assumption:

availability = 1 - ( (1 - regional_a) * (1 - regional_b) * (1 - regional_c) )
# where regional_a, b, c are the availability of three regions

Root cause: The reliability model assumed independent regional failures, whereas regional outages can be correlated due to shared underlying infrastructure (e.g., fiber cuts, power events). This assumption led to an inflated availability estimate.

Diagnostic sequence:

  1. Step 1: Review Google's published regional outage statistics (e.g., from the Architecture Framework) to understand correlation factors. Step 2: Extract the current reliability model from the capstone package. Step 3: Calculate the joint probability of simultaneous regional outages using the published correlation coefficient. Step 4: Update the availability formula to include the correlation term. Step 5: Document the change in an Architecture Decision Record (ADR).

Defensible remediation: Tactical Fix: Immediately update the reliability model to include a correlation factor derived from Google's published regional outage statistics.

Strategic Fix: Author an ADR that documents the assumption change, the source of the correlation data, and the impact on the availability calculation. Ensure all future reliability analyses use this updated model.

Verification: Run the updated model with the correlation factor and compare the result to the baseline. Confirm that the revised availability aligns with documented regional SLOs when correlation is considered. Check that the ADR is correctly linked in the capstone package and that the change is version‑controlled.

Residual risk: Even with correlation, the model cannot predict black‑swan events that affect multiple regions simultaneously (e.g., global software bugs). Such events remain outside the statistical baseline and should be addressed via operational readiness reviews.

Exercise 1: Validate and Update the Capstone Cost/Reliability Model

Goal: Ensure the capstone package includes a defensible cost/reliability model that accounts for regional outage correlation and sustained‑use discounts, and produce an updated ADR documenting the change.

Expected result: An updated cost model spreadsheet and reliability model text file that incorporate sustained‑use discounts and regional correlation, accompanied by a signed‑off ADR. All changes are verified and the capstone package passes internal review.

Mode: Local/tabletop analysis using spreadsheet software or text files. · Prerequisite: Prior day exit artifacts (capstone package), spreadsheet software or text editor, access to Google Cloud public documentation.

Preflight: Verify that the capstone package directory contains the files `cost_model.xlsx`, `reliability_model.txt`, and `ADR-001.md`. Confirm you have read/write access to these files.

Exact execution

  1. Stage 1: Preflight & Environment Validation - List the files in the capstone package directory to confirm presence of required artifacts. - Check that the spreadsheet and text files are not locked or corrupted.

    ls -la capstone-package/

  2. Stage 2: Prepare Target, Inputs, or Backing Resources - Copy the cost and reliability models to a working directory to avoid altering the originals until verification. - Retrieve the latest Google Cloud SLO and outage documentation from the public docs.

    mkdir -p capstone-package/working
cp capstone-package/cost_model.xlsx capstone-package/working/
cp capstone-package/reliability_model.txt capstone-package/working/

  3. Stage 3: Author the Plan, Configuration, or Analysis - Open the cost model and identify where sustained‑use discounts should be applied (typically a multiplier on compute hours). - Open the reliability model and locate the availability formula; note the assumption of independent regional failures. - Determine the correlation factor to use from Google's published outage statistics (e.g., 0.3 for correlated failures).

    # No commands needed; this stage is analytical.
echo 'Plan: Update cost model with sustained‑use discount factor of 0.85 for committed use.'
echo 'Plan: Update reliability model with regional correlation factor of 0.3.'

  4. Stage 4: Execute or Simulate the Planned Work - Edit the cost model to apply the sustained‑use discount factor to the relevant line items. - Edit the reliability model to replace the independent failure formula with a correlated version.

    # Example: edit cost model (assuming you have a tool like ssconvert or use LibreOffice in headless mode; for tabletop, edit manually)
# For tabletop, we will just note the change.
echo 'Updated cost_model.xlsx: applied sustained‑use discount factor 0.85 to compute lines.'
echo 'Updated reliability_model.txt: new formula:'
echo 'availability = 1 - ( (1 - regional_a) * (1 - regional_b) * (1 - regional_c) * (1 - correlation) )'

  5. Stage 5: Inspect Expected State & Verify Outcomes - Re‑calculate the total cost using the updated cost model; verify that the cost decreases by the expected discount. - Re‑calculate availability using the updated reliability model; verify that the number is lower than the previous over‑estimate but still meets the SLO when correlation is considered. - Document the new values.

    # Tabletop calculation example
echo 'Old cost: $100,000/year'
echo 'New cost (with 0.85 factor): $85,000/year'
echo 'Old availability (independent): 99.99%'
echo 'New availability (correlated 0.3): 99.9%'

  6. Stage 6: Rehearse a Bounded Failure, Edge Case, or Decision Challenge - Introduce a deliberate error: forget to save the edited reliability model and verify that version control detects the change. - Or test an extreme correlation factor (e.g., 0.9) to see the impact on availability and discuss whether it is realistic.

    # Simulate forgetting to save
echo 'If we do not save the edited file, the model retains the old assumption, leading to over‑optimistic availability.'
# Test extreme correlation
echo 'With correlation factor 0.9, availability drops to 99.0%, prompting review of whether such correlation is plausible.'

  7. Stage 7: Diagnose Evidence & Record Remediation/Decision - Verify that the edited files contain the expected changes. - Update the ADR to document the change in assumptions, the source of the correlation data, and the impact on the model. - Sign off the ADR.

    # Check the updated reliability model
grep -n 'correlation' capstone-package/working/reliability_model.txt
# Update ADR (example)
echo 'ADR-002: Updated reliability model to include regional correlation factor' >> capstone-package/ADR-002.md

  8. Stage 8: Cleanup or Exercise Closeout - Replace the original files in the capstone package with the verified updated versions. - Remove any temporary working files. - Ensure no credentials or sensitive data remain in the working directory.

    cp capstone-package/working/cost_model.xlsx capstone-package/
cp capstone-package/working/reliability_model.txt capstone-package/
rm -rf capstone-package/working
echo 'Cleanup complete. Capstone package now reflects updated cost and reliability models.'
Expected result / acceptance

The cost model shows a reduced total cost reflecting sustained‑use discounts, and the reliability model yields a realistic availability that accounts for regional correlation. The updated ADR is present and signed off.

Artifact acceptance: Save the verified execution record for the topic exit artifact, including the updated cost and reliability model files, the signed‑off ADR, and a note that the changes have been verified and are ready for the capstone defense. (File: day-179-topic-01.md).

Troubleshooting

If the cost model does not reflect the discount, verify that the factor was applied to the correct rows and that the spreadsheet formulas are correct. If the reliability model still shows the independent failure formula, check that the edit was saved and that the file being read is the updated one.

Cleanup and cost

Removing the working directory eliminates temporary files and reduces the risk of accidentally using outdated models. The capstone package remains the single source of truth for the final review.
