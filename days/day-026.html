Part 1 · Topics of the day

Architecting modern Google Cloud workload authentication: eliminating service account keys through attached identities and impersonation, mastering Application Default Credentials (ADC) lookup order, and distinguishing OAuth2 access tokens from OIDC ID tokens.

Topic 01

Service accounts, least privilege, attached identity, impersonation and key avoidance

What it is: Service accounts are specialized non-human Google Cloud identities used by applications, microservices, and automation pipelines to authenticate against Google Cloud APIs. Traditional architectures relied on downloadable JSON private keys, but modern cloud security mandates key avoidance. Workloads run under attached identities (via Compute Engine, GKE Workload Identity, or Cloud Run runtime service accounts), while human operators and CI/CD pipelines generate ephemeral access tokens through service account impersonation using the roles/iam.serviceAccountTokenCreator role.

Why today: Downloadable service account JSON keys represent the single most common attack vector in cloud environments. They never expire automatically, cannot be centrally rotated without coordinated application restarts, and frequently leak into version control systems, developer laptops, and CI/CD build artifacts. Attached identities and impersonation replace static secrets with short-lived, centrally audited OAuth2 tokens minted on demand.

Where it sits: Service accounts function both as an identity (a principal granted permissions on Google Cloud resources) and as a resource itself (an object upon which other principals are granted permissions, such as the permission to impersonate or attach the account). Understanding this dual nature is vital for enforcing least privilege.

A leaked service account private key stored in an engineer's public repository was weaponized by an unauthorized actor to issue administrative Cloud Spanner mutations. The fraudulent database writes injected fake order cancellations into the production queue, halting seven bakery dispatch lines and threatening Brightloaf's duplicate fulfillment invariant.

Topic 02

ADC resolution at introductory depth, metadata service, access versus ID tokens, audience and expiry

What it is: Application Default Credentials (ADC) is Google Cloud's standardized credential discovery protocol implemented across all Google Cloud client libraries. ADC resolves credentials transparently by traversing a deterministic search chain: first checking the GOOGLE_APPLICATION_CREDENTIALS environment variable, then inspecting user credentials generated by the local Cloud SDK, and finally querying the local Compute Engine metadata server (http://metadata.google.internal/computeMetadata/v1/). Furthermore, workloads utilize two structurally distinct token types: OAuth2 Access Tokens for authorizing requests to Google APIs, and OpenID Connect (OIDC) ID Tokens (JWTs with explicit aud audience claims) for authenticating to private Cloud Run, Cloud Functions, and API gateways.

Why today: Developers frequently confuse access tokens and ID tokens, attempting to call private serverless endpoints with raw Google API access tokens, or conversely passing ID tokens to Cloud Storage or Spanner. This misunderstanding leads to intermittent authentication failures, insecure audience validation, and broken deployment pipelines.

Where it sits: The metadata service and ADC protocol operate at the machine-runtime boundary. They abstract credential management away from application logic, providing automatic, in-memory token caching and refresh before expiration without storing secrets on disk.

An order ingestion service mistakenly passed an OAuth2 access token instead of a signed OIDC ID token with a matching audience to a private Cloud Run fulfillment endpoint. The resulting HTTP 401 Unauthorized rejection dropped 3,400 incoming store orders during peak breakfast hours, delaying regional truck departures and incurring heavy retail SLA penalties.

Topic 01 · Service accounts, least privilege, attached identity, impersonation and key avoidance

A service account is a specialized identity managed by Google Cloud IAM designed for automated workloads, microservices, and continuous integration pipelines rather than human end-users. In Google Cloud, service accounts occupy a unique architectural posture: they are both an identity (which can be granted IAM roles on resources such as Pub/Sub topics or Spanner databases) and a resource (which has its own IAM policy controlling which principals can act as or impersonate that service account).

The Vulnerability of Static Service Account Keys

Historically, workloads running outside Google Cloud or automated developer tooling authenticated by generating downloadable JSON private key pairs (containing an RSA private key). This pattern represents an extreme security liability:

  • Indefinite Lifespan: Static keys never expire by default. A key generated today remains valid for up to 10 years unless explicitly revoked in the Google Cloud Console or API.
  • Zero Attribution: If an attacker obtains a downloaded private key, every API call issued with that key appears in Cloud Audit Logs as originating from the service account itself, completely obscuring the true physical identity or IP of the threat actor.
  • Secret Sprawl: Keys inevitably end up stored in developer home directories, CI/CD configuration variables, Docker images, and public or private Git repositories.

Because of these risks, modern enterprise security enforces Key Avoidance. Organizations apply the organization policy constraint constraints/iam.disableServiceAccountKeyCreation across all production folders to strictly block the creation of new static keys.

Attached Workload Identity and Service Account Impersonation

Modern Google Cloud architectures eliminate static keys using two primary paradigms:

  1. Attached Workload Identity: When workloads execute on native Google Cloud compute platforms (Compute Engine VMs, Google Kubernetes Engine pods, Cloud Run containers, or Cloud Functions), the platform attaches the service account identity directly to the execution runtime. The workload requests short-lived (1-hour) OAuth2 access tokens directly from the local Compute Engine metadata server without any credentials stored on disk.
  2. Service Account Impersonation: Human developers, operational engineers, or external CI/CD runners authenticate using their own primary identity (e.g., corporate Google Workspace identity or federated workforce identity) and dynamically assume the identity of a target service account. The initiating principal must possess the roles/iam.serviceAccountTokenCreator role on the target service account resource. When requested, Google Cloud's IAM Credentials API verifies caller permissions and mints an ephemeral access token valid for a maximum of 60 minutes. Crucially, Cloud Audit Logs records both the impersonated service account and the human principal who requested the impersonation token (dual-principal audit logging).

Topic 02 · ADC resolution at introductory depth, metadata service, access versus ID tokens, audience and expiry

Google Cloud client libraries implement a standardized, automated credential discovery workflow known as Application Default Credentials (ADC). Rather than hardcoding credentials or loading files directly, client libraries instantiate authentication providers that search a predefined sequence of locations to discover credentials.

ADC Resolution Precedence Order

  1. Environment Variable GOOGLE_APPLICATION_CREDENTIALS: If set, the client library reads the file pointed to by this variable. The file may contain a service account key, an external workforce identity configuration, or user credentials.
  2. User ADC (Local Development): If the environment variable is unset, the library searches for the well-known user credentials file generated by the Google Cloud CLI:
    Linux/macOS: ~/.config/gcloud/application_default_credentials.json
    Windows: %APPDATA%\gcloud\application_default_credentials.json
    Note: Running the standard CLI login flow authenticates the Google Cloud CLI itself, but client libraries specifically require the auth application-default login command to populate this local JSON file.
  3. Attached Compute Metadata Server: If no local files exist, the library queries the Compute Engine metadata server via the link-local IP http://169.254.169.254/computeMetadata/v1/ (or hostname http://metadata.google.internal/computeMetadata/v1/) supplying the mandatory HTTP header Metadata-Flavor: Google. The metadata server dynamically returns an OAuth2 token minted for the VM's or container's attached service account.
  4. Terminal Error: If all three discovery steps fail, the library raises DefaultCredentialsError: Could not automatically determine credentials.

OAuth2 Access Tokens vs. OpenID Connect (OIDC) ID Tokens

Understanding the fundamental distinction between Access Tokens and ID Tokens is essential for securing multi-tier cloud architectures:

  • OAuth2 Access Tokens (Authorization): Used exclusively to authorize calls to Google Cloud APIs (such as Cloud Storage, Pub/Sub, BigQuery, or Spanner). Access tokens are typically opaque bearer tokens (starting with ya29.) that represent authorization grants scoped to API URL sets (e.g., https://www.googleapis.com/auth/cloud-platform). The receiving Google API gateway parses and checks the token against IAM policies. Access tokens do not contain an audience claim targeting third-party or custom application endpoints.
  • OpenID Connect ID Tokens (Authentication & Identity): Used to authenticate a caller's identity to custom services, private Cloud Run microservices, Cloud Functions, and API Gateways. An ID token is a cryptographically signed JSON Web Token (JWT) conforming to the OIDC standard. It contains standard claims: iss (issuer: https://accounts.google.com), sub (subject: unique principal ID), email (service account email), exp (expiration timestamp), and most crucially, aud (audience). The destination service validates that the token was signed by Google's public certificates and verifies that the aud claim strictly matches its own URL (e.g., https://order-dispatch-xyz.run.app).

Incident 26.1

Exfiltrated Static Key Breach: Rogue Spanner Mutations Threaten Duplicate Baking

Symptom

At 03:14 UTC, Brightloaf's security monitoring alerted on anomalous write activity on the primary Cloud Spanner instance orders-spanner in project brightloaf-prod-orders. Over 1,200 active bakery orders had their status updated to CANCELLED, while 450 new synthetic order records were inserted. Concurrently, regional bakery dispatch lines experienced processing anomalies, receiving conflicting order IDs.

Constraints & Invariant

Duplicate Fulfillment Invariant: The physical baking line must never execute duplicate batches for the same customer order (≤ 1 physical fulfillment per unique order ID).
Operational Constraint: SREs must immediately revoke attacker access without interrupting valid in-flight transactions from legitimate microservices.

Root Cause Analysis

A contractor attempting to debug an order routing script generated a service account JSON private key on their local laptop. The contractor accidentally committed the key file (sa-fulfillment-worker-key.json) into a public repository. Within 28 minutes, an automated scanner scraped the private key and began issuing unauthorized mutations against Cloud Spanner. Because the service account held broad write permissions on the database and static keys do not record caller IP or identity, the attacker was able to anonymously alter transactional order states.

5-Step Diagnostic Sequence

  1. Key Identification: Search Cloud Audit Logs for the anomalous serviceAccountKeyName to identify the compromised key ID (8f4c9a12b0e7).
  2. Immediate Key Revocation: Delete the compromised key via IAM to instantly invalidate all subsequent API calls from the attacker.
  3. Database Mutation Scoping: Query Cloud Spanner commit timestamps to isolate all transactions executed using the compromised key between 03:14 UTC and 03:42 UTC.
  4. Fulfillment Re-verification: Cross-reference the affected 1,200 order IDs against regional bakery fulfillment dispatch systems to freeze any conflicting orders before bread dough entered production ovens.
  5. Key Estate Audit: Run an inventory across all Google Cloud projects to locate any remaining active service account keys.

Defensible Solution & Mitigation

To permanently eliminate static key exfiltration risks:

  1. Enforce the organization policy constraint constraints/iam.disableServiceAccountKeyCreation across the entire organization hierarchy.
  2. Migrate all automated workloads to Attached Workload Identity (GKE Workload Identity and Cloud Run runtime service accounts).
  3. Mandate that human engineers and CI/CD runners access production resources strictly via Service Account Impersonation using roles/iam.serviceAccountTokenCreator, ensuring complete dual-principal audit trails.
  4. Roll back the fraudulent Spanner mutations using Spanner point-in-time recovery (PITR) to restore order state prior to 03:14 UTC. Re-validate that no cancelled order was re-dispatched to physical bakery lines.

Verification & Residual Risk

Verification: Attempt to create a service account key using the iam service-accounts keys create CLI method against any project. Confirm the operation is blocked with Request is prohibited by organization policy: constraints/iam.disableServiceAccountKeyCreation.

Residual Risk: Third-party SaaS tools that do not support Workload Identity Federation may require temporary organizational policy exceptions. Such exceptions must require VP approval and 30-day automated key expiration.

Incident 26.2

Access Token vs ID Token Mismatch: Cloud Run Ingress 401 Outage

Symptom

At 06:00 UTC, store edge gateways across forty retail locations began logging HTTP 401 Unauthorized errors when transmitting morning batch bread orders to the central ingestion endpoint (https://order-ingest-prod-xyz.run.app). Over 3,400 orders accumulated in edge gateway retry buffers, and bakery management dashboards showed zero inbound orders for the upcoming morning baking shift.

Constraints & Invariant

Duplicate Fulfillment Invariant: When store gateways flush their backlogged queues, accumulated retries must not result in duplicate baking orders (≤ 1 physical fulfillment per unique order ID).
Security Constraint: The Cloud Run ingestion microservice must remain private and authenticated (allUsers invoker access strictly prohibited).

Incident Evidence

date: Sun, 27 Sep 2026 06:01:14 GMT
server: Google Frontend
www-authenticate: Bearer error="invalid_token" error_description="The token is not an ID token"
content-length: 331

<html><head><title>401 Unauthorized</title></head>
<body><h1>401 Unauthorized</h1>
The request was not authenticated. Expected OpenID Connect ID token with audience matching service URI.
</body></html>

Root Cause Analysis

During a weekend software upgrade of the store edge gateways, developers updated the authentication module to use Google Cloud client libraries. However, the client code invoked google.auth.default() to acquire an OAuth2 Access Token (the standard bearer token used for Google Cloud APIs such as Cloud Storage and Pub/Sub). Because the target service was a private Cloud Run endpoint guarded by Google Cloud's serverless ingress proxy, the proxy required an OpenID Connect (OIDC) ID Token containing an aud (audience) claim matching the service URL. Passing an access token caused the ingress proxy to immediately reject the request with HTTP 401 before it ever reached the application container.

5-Step Diagnostic Sequence

  1. Header Inspection: Inspect the WWW-Authenticate response header from the Cloud Run endpoint to observe error_description="The token is not an ID token".
  2. Token Type Analysis: Decode the bearer token transmitted by the client gateway. Confirm that the token is an opaque OAuth2 access token (starting with ya29.) rather than a three-part JWT (Header.Payload.Signature).
  3. Audience Validation Check: Verify that the Cloud Run service IAM policy grants roles/run.invoker to the store gateway service account.
  4. Backlog Queue Throttling: Place edge gateway outbound dispatch queues into a controlled drain state to prevent a burst of duplicate order submissions upon authentication restoration.
  5. Client Library Reconfiguration: Update edge client code to use google.auth.transport.requests with google.oauth2.id_token.fetch_id_token specifying the explicit target service audience.

Defensible Solution & Mitigation

To restore order ingestion and prevent future token confusion:

  1. Deploy a hotfix to edge store gateways: configure the client to request an OIDC ID token targeting audience="https://order-ingest-prod-xyz.run.app".
  2. Verify that the gateway service account retains roles/run.invoker on the Cloud Run service.
  3. Slowly drain the backlogged order queues through an idempotent ingestion gateway that inspects the order_id against the Spanner deduplication index, dropping replayed events.
  4. Add automated CI/CD integration tests asserting that all client SDK calls targeting internal microservices utilize ID tokens, while calls targeting GCP resource APIs use access tokens.

Verification & Residual Risk

Verification: Execute an authorized curl probe passing the newly generated OIDC ID token to the Cloud Run endpoint. Confirm the response status is HTTP/2 200 OK and inspect Cloud Run request logs to verify identity extraction.

Residual Risk: If the Cloud Run service URL changes (e.g., migrating to a custom domain), client configurations must update their requested audience parameter; otherwise, audience mismatch errors will recur.

#!/usr/bin/env python3
"""
impersonate-sa.py - Service Account Impersonation Simulator
Demonstrates ephemeral token minting and dual-principal audit logging.
"""
from datetime import datetime, timezone, timedelta
import secrets
import json

class IAMCredentialsService:
    def __init__(self):
        # Service Account IAM Policies (Who can impersonate)
        self.sa_policies = {
            "sa-fulfillment-worker@brightloaf-prod-orders.iam.gserviceaccount.com": {
                "token_creators": [
                    "user:sre-lead@brightloaf.com",
                    "serviceAccount:ci-runner@brightloaf-ops.iam.gserviceaccount.com"
                ]
            }
        }

    def generate_access_token(self, caller_principal, target_sa, scopes, lifetime_seconds=3600):
        policy = self.sa_policies.get(target_sa)
        if not policy:
            raise PermissionError(f"Target service account {target_sa} does not exist.")
        
        if caller_principal not in policy["token_creators"]:
            raise PermissionError(
                f"Principal {caller_principal} lacks roles/iam.serviceAccountTokenCreator on {target_sa}"
            )

        lifetime = min(lifetime_seconds, 3600)
        now = datetime.now(timezone.utc)
        expire_time = now + timedelta(seconds=lifetime)
        
        # Ephemeral OAuth2 Bearer Token
        token = "ya29.c." + secrets.token_urlsafe(48)
        
        # Dual-Principal Audit Log Entry
        audit_log = {
            "protoPayload": {
                "@type": "type.googleapis.com/google.cloud.audit.AuditLog",
                "authenticationInfo": {
                    "principalEmail": caller_principal,
                    "serviceAccountDelegationInfo": [
                        { "firstPartyPrincipal": { "principalEmail": target_sa } }
                    ]
                },
                "serviceName": "iamcredentials.googleapis.com",
                "methodName": "google.iam.credentials.v1.IAMCredentials.GenerateAccessToken",
                "resourceName": f"projects/-/serviceAccounts/{target_sa}",
                "status": { "code": 0 }
            },
            "timestamp": now.isoformat()
        }

        return {
            "accessToken": token,
            "expireTime": expire_time.isoformat(),
            "auditLog": audit_log
        }

def main():
    iam = IAMCredentialsService()
    target_sa = "sa-fulfillment-worker@brightloaf-prod-orders.iam.gserviceaccount.com"
    caller = "user:sre-lead@brightloaf.com"
    scopes = ["https://www.googleapis.com/auth/cloud-platform"]

    print(f"=== Service Account Impersonation Request ===")
    print(f"Caller Principal : {caller}")
    print(f"Target SA        : {target_sa}")
    print(f"Requested Scopes : {scopes}\n")

    result = iam.generate_access_token(caller, target_sa, scopes, 3600)
    print(f"[IMPERSONATION SUCCESSFUL]")
    print(f"Ephemeral Access Token : {result['accessToken'][:22]}...")
    print(f"Token Expiration UTC   : {result['expireTime']}")
    print(f"\n[DUAL-PRINCIPAL CLOUD AUDIT LOG]:")
    print(json.dumps(result['auditLog'], indent=2))

    # Test Unauthorized Caller
    print("\n=== Testing Unauthorized Caller Impersonation ===")
    bad_caller = "user:contractor@brightloaf.com"
    try:
        iam.generate_access_token(bad_caller, target_sa, scopes)
    except PermissionError as e:
        print(f"[EXPECTED REJECTION]: {e}")

if __name__ == "__main__":
    main()

## 2. Separation of Authentication vs. Authorization
