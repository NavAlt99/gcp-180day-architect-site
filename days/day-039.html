1 · Topics of the day

Autohealing with health checks

Autohealing is an automated control loop in Managed Instance Groups that detects and replaces failing, frozen, or corrupted virtual machines. While Cloud Load Balancing health checks dictate whether an instance should receive ingress network packets, an autohealing health check dictates whether the underlying VM should live or be destroyed and recreated from scratch.

A foundational element of autohealing is the initial delay (grace period). The autohealing controller ignores failed probes until this duration expires, providing the guest operating system, container runtime, and application caches adequate time to boot and pass readiness probes before facing recreation.

Problem preview: A DevOps engineer attaches an autohealing health check with an aggressive 15-second initial delay to the Order API MIG, but the Java application requires 50 seconds to warm up its database connection pools. Every newly provisioned VM is marked unhealthy and killed before it can ever finish booting, plunging the entire service into a perpetual recreation death spiral with zero live instances.

Rolling updates: max surge, max unavailable, canary rollouts

Compute Engine enables zero-downtime application deployments across a MIG through declarative rolling update policies. By specifying maxSurge (the number of additional instances created above the target size) and maxUnavailable (the number of instances allowed to be offline or draining during the update), teams can balance deployment speed against capacity guarantees.

Canary deployments allow validating a new instance template version against a small percentage of production traffic before committing the entire fleet. When misconfigured, aggressive unavailability limits can strip serving headroom during peak hours, degrading latency and triggering cascading backend timeouts.

Problem preview: An operator initiates a rolling update for the Order API with maxUnavailable: 50% and maxSurge: 0 during peak checkout hours on a group sized at 4 instances. Half of the serving capacity is immediately terminated, overloading the surviving two instances to 100% CPU and causing gateway timeout spikes (HTTP 504) for online shoppers.

Stateful MIGs

While standard MIGs are strictly stateless and treat instances as identical, disposable cattle, Stateful MIGs preserve individual instance identities and state across automated restarts, autohealing, and rolling updates. This includes preserving specific persistent disk attachments, static internal/external IP addresses, and custom metadata keys tied to deterministic instance names (e.g., kafka-node-0).

Stateful MIGs bridge the gap between automated fleet management and stateful architectures such as databases, distributed streaming brokers, and local transactional ledgers. A stateful policy defines which disks are preserved when an instance is recreated, ensuring customer transactional data is not destroyed during operating system patching.

Problem preview: An engineer mounts an auxiliary persistent disk for the local order audit ledger onto a MIG instance but fails to configure a stateful policy for that disk. During an automated OS security update, the MIG recreates the VM, detaches and silently deletes the unmanaged auxiliary disk, resulting in permanent loss of local audit records.

Unmanaged instance groups

An Unmanaged Instance Group is a heterogeneous collection of virtual machines grouped together solely to serve as backend targets for Cloud Load Balancing. Unlike MIGs, unmanaged groups provide no instance templates, no automated health recreation, no rolling update coordination, and no autoscaling capabilities.

Unmanaged groups are strictly reserved for legacy monoliths, specialized appliance pairs, or third-party clustered applications with bespoke failover controllers. Relying on an unmanaged group for high-traffic microservices shifts all operational toil and failure recovery back onto manual human intervention.

Problem preview: A team deploys three legacy order gateways in an unmanaged instance group behind an internal load balancer; when one VM crashes due to an out-of-memory kernel panic over the weekend, no autohealing controller exists to restart or replace it. The remaining two VMs absorb traffic until Monday morning when a traffic surge crashes the second instance, leaving only one degraded node to handle the entire enterprise load.

2 · Technical discussion of each topic

Autohealing with health checks

Load balancing vs autohealing health checks

In Google Cloud Compute Engine, health checks serve two distinct architectural roles that must not be conflated:

  • Load Balancing Health Check: Probes the service endpoint (e.g. /healthz) to determine traffic eligibility. If probes fail, the load balancer marks the backend as UNHEALTHY and stops routing new connections to it. The VM remains alive and running to allow debugging or recovery.
  • Autohealing Health Check: Configured directly on the Managed Instance Group. If probes consistently fail beyond the unhealthy threshold, the MIG controller issues an API command to forcefully stop, destroy, and recreate the VM from the template.

The initial delay requirement

When an instance boots, it must execute OS initialization, initialize background daemons, launch the application runtime, warm local caches, and establish database connection pools. The autohealing policy parameter initialDelaySec tells the MIG manager how long to withhold judgment. Probes are ignored until initialDelaySec has elapsed.

Parameter Recommended Setting Impact of Misconfiguration
Check Interval 5–10 seconds Too frequent: unnecessary CPU/network overhead; Too infrequent: slow detection
Healthy Threshold 2 consecutive successes Ensures service is truly operational before admitting traffic
Unhealthy Threshold 3 consecutive failures Prevents recreation on momentary network blips
Initial Delay Measured Boot Time + 30–60s margin Too short: permanent recreation death spiral; Too long: broken instances linger

Rolling updates: max surge, max unavailable, canary rollouts

Update parameters and capacity guarantees

When rolling out a new Instance Template, the MIG manager executes an automated rolling update. Two mathematical levers govern the rollout curve:

  • maxSurge: The number (or percentage) of extra instances created above the target capacity. Specifying maxSurge: 2 (or 25%) allows the MIG to provision 2 new version instances and verify health before terminating old ones.
  • maxUnavailable: The number (or percentage) of instances that can be offline simultaneously during the update. Specifying maxUnavailable: 0 guarantees that serving capacity never drops below 100% of the target size.

Canary rollout deployment shape

A canary deployment distributes traffic across two instance templates simultaneously within the same MIG. By specifying a targetSize fraction for Template B (e.g., 10%), the MIG updates only 1 or 2 instances to the canary template while keeping 90% on the stable version. After verifying application metrics and error budgets in Cloud Monitoring, the operator increases the target size to 100% to complete the rollout.

Strategy maxSurge maxUnavailable Capacity Floor Quota Impact
High Availability (Recommended) 25% (or 1+) 0 100% Requires temporary surplus regional vCPU quota
Quota Constrained 0 1 N - 1 Fits within exact quota; reduces total serving headroom
Aggressive / Unsafe 0 50% 50% High risk of overload and cascading gateway 504 errors

Stateful MIGs

Preserving disks, IPs, and metadata across recreations

In a standard stateless MIG, instance recreation discards all local root and attached persistent disks, recreating fresh empty disks from the template image. In a Stateful MIG, you define a per-instance configuration or group-level stateful policy:

  • Stateful Persistent Disks: Disks marked as stateful are detached when an instance is stopped or recreated, preserved without data loss, and reattached to the replacement VM upon reboot.
  • Stateful IP Addresses: Specific static internal or external IP addresses remain bound to deterministic VM names (e.g. backend-01 always retains 10.0.1.5).
  • Stateful Metadata: Custom metadata keys (e.g. cluster node role, shard ID) persist across instance updates.

Unmanaged instance groups

Architectural boundaries and operational comparison

An Unmanaged Instance Group is simply a logical container for existing Compute Engine VMs. The group does not manage lifecycle, does not monitor health, and cannot scale.

Capability Managed Instance Group (MIG) Unmanaged Instance Group
Instance Homogeneity Identical (derived from single template) Heterogeneous (different sizes, OS, configs)
Autohealing Automated restart & recreation on failure None (manual intervention required)
Autoscaling Dynamic expansion/contraction via metrics None (static instance list)
Rolling Updates Canary, maxSurge, maxUnavailable automated Manual per-VM reconfiguration
Load Balancer Integration Native backend service target Native backend service target

3 · Real-world problems and solutions

The scenarios below represent realistic production engineering incidents involving GCP Managed Instance Group lifecycle management. Values, traces, and metrics are architectural models.

Topic 1 field case — Premature initial delay triggers autohealing death spiral

Situation and business impact

A Brightloaf operations team enables an autohealing health check on the production Order API Managed Instance Group. They reuse the HTTP health check from the External HTTP(S) Load Balancer (interval 5s, unhealthy threshold 2) and set the autohealing initialDelaySec to 15 seconds. The Order API is a containerized Java service that takes 45 seconds to boot, establish connection pools to Cloud SQL, and register its endpoints.

Immediately after applying the policy, the autohealing controller checks instances at second 16. Because the applications are still initializing, the probes return connection refused. By second 26, the unhealthy threshold of 2 failures is reached. The MIG controller marks all instances unhealthy, issues a terminate command, and provisions new VMs. The new VMs also take 45 seconds to boot and are similarly terminated at second 26. The entire 8-node fleet enters an unbroken cycle of recreation, producing 100% downtime for order processing.

Constraints

  • Autohealing must accurately detect true frozen or deadlocked application runtimes.
  • Must not prematurely execute VM termination during normal initialization.
  • Preserve the invariant that replaying an order event never triggers a duplicate fulfillment.

Root cause

The autohealing initial delay (15s) was significantly shorter than the application's actual cold-boot readiness time (45s). The controller mistook normal initialization for application failure.

Diagnostic sequence

  1. Inspect MIG operation history: gcloud compute instance-groups managed list-errors --region=us-central1 displays non-stop Instance autohealing triggered events.
  2. Check instance uptime: Instances show uptimes of less than 40 seconds before being shut down.
  3. Measure cold-boot duration: Start a standalone test instance from the template and time the duration until /healthz returns HTTP 200 (measured at 44.8 seconds).

Defensible solution

Update the autohealing policy to provide adequate headroom: set initialDelaySec to 90 seconds (45s boot + 45s safety buffer). Increase the unhealthy threshold to 3 consecutive failures.

Verification

Apply the updated autohealing policy (gcloud compute instance-groups managed set-autohealing order-api-rmig --initial-delay=90s). Observe instance stabilization: all 8 instances boot, survive past second 50, transition to HEALTHY, and remain running continuously with zero unexpected recreations.

Residual risk

If a genuine deadlock occurs during application boot (e.g., database connection pool exhaustion), autohealing will wait the full 90 seconds before taking corrective action.

Topic 2 field case — Aggressive maxUnavailable policy strips capacity during midday deployment

Situation and business impact

During a 1:00 PM peak ordering window, a software update is dispatched to the 6-instance Order API Managed Instance Group. The rolling update policy specifies maxUnavailable: 3 (50% of the fleet) and maxSurge: 0 to prevent exceeding regional project vCPU quota.

The MIG manager immediately stops and drains 3 instances simultaneously. Peak order traffic (normally distributed across 6 instances) slams into the 3 surviving instances. Their vCPU utilization hits 100%, request queues back up, and the frontend load balancer begins returning HTTP 504 Gateway Timeout errors to hundreds of online customers. Cart conversion drops by 35% before the new instances pass health checks 5 minutes later.

Constraints

  • Deployments must guarantee 100% serving capacity (zero capacity reduction) at all times.
  • Must prevent regional vCPU quota exhaustion during surge provisioning.
  • Rollback must be possible within 60 seconds if the new version exhibits unexpected errors.

Root cause

Setting maxUnavailable to 50% on a production group operating near baseline capacity. Halving active capacity during peak traffic guarantees severe CPU overload on surviving nodes.

Defensible solution

Enforce a zero-downtime rolling update policy: set maxUnavailable: 0 and maxSurge: 2 (or 25%). The MIG provisions surplus instances from the new template first, waits for them to become healthy, and only then drains and deletes the old instances.

Verification

Simulate a rolling update in staging under 100% simulated load: verify that the total healthy instance count never drops below 6, and HTTP latency remains flat throughout the rollout.

Residual risk

maxSurge: 2 requires temporary extra vCPU quota. If regional quota is at 100%, the surge instances will fail to schedule.

Topic 3 field case — Auxiliary audit disk deleted during stateless rolling update

Situation and business impact

To satisfy financial audit compliance, each fulfillment worker instance writes raw order event payloads to an attached 100GB secondary Persistent Disk (audit-log-disk). The team operates the fulfillment workers inside a Managed Instance Group. When creating the group, the team assumed that attached disks would naturally persist across updates.

During a security update to the instance template (updating the base OS patch), the MIG initiates an automated rolling replacement. The MIG controller deletes the old instance, terminates its attached secondary persistent disk (because it was declared as an ephemeral disk in the template rather than a stateful disk), and provisions a new blank disk. The local un-replicated audit event logs for the past 14 days are completely erased, violating financial data retention regulations.

Constraints

  • Local compliance logs must survive automated instance updates and autohealing recreations.
  • The architecture must maintain automated rolling update capabilities for security patching.
  • Audit event persistence must not require building custom manual VM management scripts.

Root cause

The secondary disk was managed as a standard stateless disk inside the template instead of being registered under the MIG's Stateful Policy. In a stateless MIG, instance recreation destroys all attached disks not explicitly protected by a stateful preservation policy.

Defensible solution

Configure the Managed Instance Group with a Stateful Policy for the audit disk: designate device name audit-log-disk under --stateful-disk with auto-delete=never. When the MIG replaces a VM, it cleanly detaches the disk, recreates the VM with the new template OS, and reattaches the exact same disk without data loss.

Verification

Write a test marker file to the stateful disk (/mnt/audit/test-marker.txt). Trigger a rolling instance replacement (gcloud compute instance-groups managed rolling-action restart). Confirm upon reboot that the replacement VM mounts the exact same disk volume and the marker file is intact.

Residual risk

Stateful MIGs cannot be automatically downsized by autoscalers without explicit per-instance un-managing commands, as the autoscaler cannot know which stateful disk is safe to discard.

Topic 4 field case — Silent weekend VM crash in unmanaged instance group

Situation and business impact

A legacy partner order translation component was deployed into an Unmanaged Instance Group consisting of three custom-configured virtual machines (gateway-1, gateway-2, gateway-3) behind an Internal TCP/UDP Load Balancer. At 02:14 AM on Sunday, gateway-2 suffered a guest kernel panic triggered by an out-of-memory memory leak.

Because unmanaged instance groups lack autohealing and automated lifecycle management, Google Cloud took no action. The dead VM remained completely offline for over 30 hours. On Monday morning at 08:30 AM, business traffic doubled. The two surviving instances rapidly saturated their CPU, and gateway-1 crashed under memory pressure at 08:45 AM, leaving only one degraded node to process all enterprise partner orders, resulting in severe order backlogs and missed delivery SLAs.

Constraints

  • Enterprise partner order processing must auto-recover from VM crashes without human paging.
  • Eliminate single points of failure in gateway routing fleets.
  • Preserve the invariant that replaying an order event never triggers a duplicate fulfillment.

Root cause

Using an Unmanaged Instance Group for a production service. Unmanaged groups provide zero automated recreation, leaving dead instances offline indefinitely until an operator manually intervenes.

Defensible solution

Migrate the gateway fleet from an Unmanaged Instance Group to a Managed Instance Group (MIG) backed by an Instance Template and an autohealing health check. If an instance experiences a kernel crash, the MIG autohealing controller detects probe failure and automatically recreates a healthy instance within 2 minutes.

Verification

Simulate a kernel crash on a gateway VM (sudo echo c > /proc/sysrq-trigger). Verify that within 120 seconds, the MIG controller registers the failure, provisions a clean replacement instance, and restores the group to its full 3-node capacity automatically.

Residual risk

Moving to a MIG requires encapsulating all gateway configuration into the instance template and automated startup scripts; any remaining pet-like manual configuration will be lost during recreation.

Exercise 1 — Autohealing health check configuration and initial delay calibration

Goal: Formulate an autohealing health check policy with verified application readiness delays and validate recreation behavior.

Mode: tabletop design / sandbox · Prerequisites: Day 38 Instance Template definition.

Preflight

Open day-039-recovery.md. Document baseline application characteristics: Cold boot time = 45 seconds; Target port = 8080; Path = /healthz.

  1. Define the autohealing health check. Author the command specification: 
    gcloud compute health-checks create http order-api-autoheal-check \
  --project=PROJECT_ID \
  --port=8080 \
  --request-path=/healthz \
  --check-interval=10s \
  --timeout=5s \
  --unhealthy-threshold=3 \
  --healthy-threshold=2
  2. Calibrate the initial delay. Calculate the required grace period:

    initialDelaySec = measured_boot_time (45s) + safety_buffer (45s) = 90s.

    Document why setting this value to 15s creates a recreation death spiral.
  3. Apply to the Managed Instance Group. 
    gcloud compute instance-groups managed set-autohealing order-api-rmig \
  --project=PROJECT_ID \
  --region=us-central1 \
  --http-health-check=order-api-autoheal-check \
  --initial-delay=90s
Expected result

A calibrated autohealing specification recorded in day-039-recovery.md proving that initial delay encloses application startup time.

Exercise 2 — Rolling update execution with maxSurge and zero unavailability

Goal: Design and model a zero-downtime rolling update deployment curve with canary validation.

Mode: tabletop / design · Prerequisites: Exercise 1 autohealing configuration.

  1. Formulate the zero-downtime update policy. Define the update command for a 6-node fleet: 
    gcloud compute instance-groups managed rolling-action start-update order-api-rmig \
  --project=PROJECT_ID \
  --region=us-central1 \
  --version=template=order-api-template-v2 \
  --max-surge=2 \
  --max-unavailable=0 \
  --min-ready=60s
  2. Calculate the capacity timeline. In day-039-recovery.md, map the instance states during rollout:
    • T = 0: 6 instances on v1 (100% capacity).
    • T = 1m: 2 surge instances provisioned on v2 (8 total instances, 133% capacity).
    • T = 2m: Surge instances pass health check (60s min-ready). MIG drains and deletes 2 v1 instances (6 instances, 100% capacity).
    • T = 3m: Process repeats until all 6 instances run v2. Active capacity never drops below 6.
  3. Evaluate canary alternative. Model a 15% canary split using two template versions simultaneously in the same MIG.
Expected result

A deployment timeline table in day-039-recovery.md demonstrating 100% serving capacity preservation throughout the update cycle.

Exercise 3 — Stateful MIG policy authoring for persistent data volumes

Goal: Author a stateful disk policy to preserve compliance audit volumes across automated VM recreations.

Mode: tabletop / design · Prerequisites: Day 37 block storage concepts.

  1. Define the stateful policy. Author the command attaching device audit-log-disk as stateful: 
    gcloud compute instance-groups managed update order-api-rmig \
  --project=PROJECT_ID \
  --region=us-central1 \
  --stateful-disk=device-name=audit-log-disk,auto-delete=never
  2. Document the disk lifecycle. Detail in day-039-recovery.md what happens during an autohealing recreation:

    OS root disk is wiped and rebuilt from template; audit-log-disk is detached, held in us-central1-a, and reattached to the newly created VM with filesystem data fully preserved.
