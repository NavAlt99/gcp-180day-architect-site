Workforce directory architecture: Cloud Identity, Google Workspace, and consumer accounts

A fundamental tenet of Google Cloud security architecture is the complete decoupling of identity authentication from resource authorization. Google Cloud does not maintain an internal user directory; instead, it relies entirely on external identity repositories to authenticate human principals before evaluating IAM permissions.

Identity Directory Options Compared

Enterprise architects encounter three primary identity repository models within Google Cloud environments:

  1. Cloud Identity (Free & Premium): Google's standalone Identity-as-a-Service (IDaaS) platform anchored to an enterprise-verified primary domain (such as brightloaf.com). It provides centralized user provisioning, password policies, SAML 2.0 / OIDC federation with external corporate IdPs (such as Okta, Ping Identity, or Microsoft Entra ID), 2-Step Verification enforcement, and automated de-provisioning. The Premium edition adds context-aware access, mobile device management (MDM), and automated user lifecycle rules.
  2. Google Workspace: Integrates the complete suite of productivity applications (Gmail, Google Drive, Docs, Meet) on top of the exact same underlying Cloud Identity directory and Google Admin Console. An enterprise utilizing Google Workspace already possesses an authoritative Cloud Identity directory for Google Cloud authentication.
  3. Consumer Google Accounts: Personal accounts ending in @gmail.com or unmanaged email addresses created directly on Google. These accounts belong entirely to the individual; enterprise administrators cannot reset passwords, enforce security keys, audit logins, or revoke access upon employee termination.

Enterprise Directory Federation & Domain Restricted Sharing

To establish a secure enterprise workforce baseline, architects implement two critical integration controls:

  • Automated Directory Synchronization: Enterprises synchronize users and groups from Active Directory using Google Cloud Directory Sync (GCDS) or from cloud identity providers (Okta / Entra) using SCIM (System for Cross-domain Identity Management) connectors. When an employee is deactivated in the corporate HRIS, their Google Cloud access is revoked immediately.
  • Domain Restricted Sharing Organization Policy: To prevent shadow IT and data exfiltration, administrators enforce the constraint constraints/iam.allowedPolicyMemberDomains at the Organization root. This constraint strictly limits IAM role assignments to verified Cloud Identity customer directory IDs, programmatically blocking the addition of personal @gmail.com accounts or external partner domains.

Principal taxonomy: Evaluating the six IAM principal types and public exposure risks

In Google Cloud IAM, an authorization policy binds one or more Roles to specific Principals on a resource. Understanding the precise syntax, evaluation behavior, and security blast radius of each principal type is essential for preventing unintended data disclosures.

The Six Principal Types

  1. user:{email}: Represents an individual human account (e.g. user:alice@brightloaf.com). Evaluated by matching the authenticated email in the caller's OAuth2 bearer token.
  2. group:{email}: Represents a Google Group (e.g. group:bakery-ops@brightloaf.com). When evaluated, the IAM engine queries Cloud Identity to determine if the calling user belongs to the group.
  3. serviceAccount:{email}: Represents a Google Cloud service account (e.g. serviceAccount:order-api@bl-prod.iam.gserviceaccount.com), used by applications, CI/CD runners, and VM instances.
  4. domain:{domain.com}: Represents all users within an entire verified Cloud Identity domain (e.g. domain:brightloaf.com). Automatically matches any user account created under that domain.
  5. allAuthenticatedUsers: A global Google-managed identifier matching any human or workload authenticated with any Google account anywhere in the world. This includes personal consumer @gmail.com accounts, external contractors, and competitors.
  6. allUsers: A global identifier matching anyone on the public internet, completely unauthenticated. Used exclusively for public internet assets (such as public web static assets on Cloud Storage or unauthenticated Cloud Run endpoints).

The Catastrophic Fallacy of allAuthenticatedUsers

A frequent and disastrous security vulnerability arises from conflating domain:company.com with allAuthenticatedUsers. Administrators erroneously assume that allAuthenticatedUsers restricts access to "users who have authenticated into our corporate single sign-on." In reality, Google Cloud interprets this identifier as anyone who has authenticated with Google. Binding allAuthenticatedUsers to an internal bucket or database grants download permissions to all 3 billion Google account holders globally.

Why groups (not individual users) should receive roles: Limits, privilege creep, and decoupling

Enterprise IAM architecture establishes a strict governance rule: IAM roles must be assigned to Google Groups, never to individual user accounts. While Google Cloud permits binding roles directly to user:alice@brightloaf.com, doing so introduces severe operational failure modes, privilege accumulation vulnerabilities, and hard platform limit violations.

Hard Platform Limits: Policy Size and Member Thresholds

Google Cloud enforces strict platform quotas on IAM policy payloads:

  • Maximum Policy Size: An individual IAM policy on an Organization, Folder, Project, or Resource cannot exceed 250 KB in total serialized JSON size.
  • Maximum Member Limit: A single IAM policy cannot contain more than 1,500 total member entries across all role bindings.

In an enterprise with 200 developers working across 50 microservices, binding individuals directly to roles results in thousands of discrete member entries, rapidly exhausting policy limits. Once the 250 KB limit is reached, all subsequent IAM modifications fail with an API error, blocking emergency hotfixes and deployment pipelines. Binding roles to Google Groups reduces hundreds of individual entries down to a single compact entry (e.g. group:bakery-devs@brightloaf.com), shrinking policy size by over 95%.

Eliminating Privilege Accumulation and Orphan Permissions

When roles are bound directly to individuals, organizational role changes result in severe security drift:

  • Privilege Creep: When an engineer transfers from the Logistics team to the Analytics team, new permissions are granted on analytics projects, but administrators rarely audit or remove existing permissions across dozens of logistics projects. Over years, senior staff accumulate dangerous superuser privileges across the entire cloud estate.
  • Orphan Permissions: When an employee or contractor departs the enterprise, failing to clean up direct bindings leaves residual references across hundreds of project policies. If the user account is ever reprovisioned or compromised, inherited project bindings remain active.
  • Architectural Decoupling: With group-based authorization, identity management is completely decoupled from cloud infrastructure. Adding or removing an employee from a group in Okta or Cloud Identity instantly grants or revokes access across all cloud projects globally, requiring zero Terraform runs or Google Cloud IAM updates.
