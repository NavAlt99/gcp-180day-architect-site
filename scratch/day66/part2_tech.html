Reproduce, diagnose and restore the integrated application

1. The Imperative of Reproducibility: Declarative IaC & Network Topology

In enterprise cloud engineering, an infrastructure configuration that cannot be recreated deterministically from source code is an unquantified liability. While single-service tutorials encourage ad-hoc console provisioning, production architectures must adhere to the Declarative Reproduction Discipline: every managed resource, network route, security perimeter, and IAM binding must be expressed in auditable Infrastructure as Code (Terraform / OpenTofu) or fully scripted gcloud workflows. Rebuilding the integrated retail order baseline for Brightloaf requires instantiating five tightly coupled layers in strict dependency order:

  1. VPC Networking & Private IP Foundations: A regional custom-mode VPC network (brightloaf-vpc) hosting a dedicated /24 subnet (10.128.10.0/24) reserved exclusively for Cloud Run Direct VPC Egress. Unlike legacy Serverless VPC Access connectors—which required dedicated /28 subnets and provisioned underlying Compute Engine connector instances that introduced throughput ceilings, scaling lag, and cold-start latency—Direct VPC Egress binds container instances directly to elastic network interfaces (subinterfaces) inside the VPC, drawing up to 251 available private IP addresses with wire-speed throughput and zero intermediate VM hops.
  2. Private Service Connect (PSC) Datastore Endpoints: A Regional High Availability Cloud SQL for PostgreSQL 16 instance configured across primary zone us-central1-a and standby replica zone us-central1-f. The instance is published via Private Service Connect to a private endpoint forwarding rule inside brightloaf-vpc at IP 10.128.0.50/32 on TCP port 5432. PSC completely supersedes legacy VPC Peering for managed databases by eliminating RFC 1918 IP address overlap collisions, preserving customer VPC route autonomy, and preventing transitive routing vulnerabilities.
  3. Container Runtime Tier (Cloud Run): The containerized order-service API runtime deployed with Direct VPC Egress enabled (--network=brightloaf-vpc --subnet=order-egress-subnet --vpc-egress=private-ranges-only). Running on Google's hardened gVisor microVM sandbox, the service operates under a dedicated least-privilege service account (sa-order-service@...) possessing only roles/cloudsql.client and roles/pubsub.publisher.
  4. Asynchronous Event Fabric with Dead-Letter Topic: A Cloud Pub/Sub topic (orders.v1) enforcing message ordering via ordering_key = order_id. The downstream fulfillment worker ingests messages via a pull subscription (orders.v1.fulfillment-sub) configured with a strict dead-letter policy: deadLetterTopic = projects/brightloaf-prod/topics/orders.v1.dlq with maxDeliveryAttempts = 5.
  5. Edge Security & Global Ingress: A Global external Application Load Balancer terminating client HTTPS via Google-managed TLS 1.3 certificates, protected by Cloud Armor rate-limiting (2,000 QPS per source IP) and pre-configured OWASP Top 10 rulesets, dispatching traffic to the Cloud Run service via a Serverless Network Endpoint Group (NEG).

2. Controlled Failure Injection: Probes, Circuit Breakers & Quarantine

Resilience cannot be asserted; it must be verified under synthetic stress. The architecture incorporates three controlled failure injection probe points designed to test system boundaries under realistic failure conditions:

Failure Injection 1: Datastore Network Partition & Pool Exhaustion

Relational databases represent the most fragile stateful component in cloud microservices. When a database failover occurs, or when a network route to the PSC endpoint is severed, client applications that lack decoupled health checking rapidly enter a catastrophic failure loop. If the application exposes a monolithic health probe (/healthz) that checks database connectivity and fails when the database is unreachable, Cloud Run interprets the failure as a container crash and continuously kills and restarts instances. This triggers a cold-start reboot storm: hundreds of restarting containers simultaneously flood the recovering database with fresh TCP handshakes, SSL negotiations, and pool warm-up queries, causing immediate secondary connection pool collapse.

To eliminate this failure mode, the baseline architecture enforces Decoupled Dual-Probe Architecture:

  • Liveness Probe (/healthz): Validates only that the HTTP process is running, event loops are unblocked, and local memory thresholds are healthy. Returns HTTP 200 OK regardless of downstream database availability, preventing Cloud Run from initiating destructive container restarts during transient infrastructure outages.
  • Readiness Probe (/readyz): Actively executes a fast connection validation against the database pool (SELECT 1 with a strict 1,000ms timeout). If the PSC endpoint is unreachable or the pool is saturated, /readyz immediately returns HTTP 503 Service Unavailable. The upstream Global ALB detects the readiness probe failure and instantly purges the container instance from the healthy backend pool, preventing user checkout requests from being routed to a crippled backend.
  • Client-Side Circuit Breaker: The application runtime wraps database operations in a circuit breaker pattern (e.g., PyBreaker). Upon detecting 3 consecutive socket timeouts to 10.128.0.50:5432, the circuit transitions from CLOSED to OPEN. In the open state, incoming checkout requests fail immediately with HTTP 503 and a Retry-After: 30 header in under 3 milliseconds, rather than blocking container threads for the full 60-second GFE gateway timeout.
Failure Injection 2: Poison Pill Payload & Head-of-Line Blocking Prevention

In distributed event-driven systems utilizing ordering keys, a poison pill is a malformed, corrupted, or schema-violating message that cannot be processed by the consumer logic. In Cloud Pub/Sub, when message ordering is enabled (enable_message_ordering = true), the broker guarantees that messages published with the same ordering_key are delivered to subscribers in the exact order received. However, this architectural guarantee introduces a severe vulnerability: Head-of-Line (HoL) Blocking. If consumer logic throws an unhandled exception (e.g., JSON syntax error, missing mandatory attribute, or database constraint violation) and NACKs the message, Pub/Sub redelivers the identical failed message on the next pull. Because the broker cannot violate FIFO ordering, all subsequent valid messages queued behind that ordering key remain permanently stuck in the subscription backlog.

The baseline mitigates this vulnerability by configuring a Dead-Letter Topic (DLT) with Retry Bound:

  • The subscription specifies maxDeliveryAttempts = 5 pointing to orders.v1.dlq.
  • When the fulfillment consumer encounters a corrupted payload, it logs the exception with full W3C trace correlation and NACKs the message. Pub/Sub increments the delivery counter.
  • Upon the 5th consecutive delivery failure, Pub/Sub's broker service agent automatically forwards the poison message to the dead-letter topic and automatically acknowledges the message on the primary subscription.
  • The ordering key partition is instantly unblocked, allowing subsequent valid customer orders to resume processing within seconds. A Cloud Monitoring alert triggers immediately on pubsub.googleapis.com/subscription/dead_letter_message_count > 0, paging on-call engineers to inspect the quarantined payload in the dead-letter queue without customer-facing downtime.
Failure Injection 3: Identity Token Breach & Perimeter Rejection

Security defense-in-depth requires verifying that unauthorized callers are rejected at the edge before consuming backend compute or memory resources. Cloud Run provides built-in IAM authentication enforced directly at the Google Front End (GFE) proxy layer:

  • Unauthenticated Requests (Missing / Expired Bearer Token): The client dispatches a request without an Authorization: Bearer <id_token> header. The GFE terminates the request at the edge, returning HTTP 401 Unauthorized with zero container invocation, preserving backend compute capacity.
  • Unauthorized Principals (Invalid IAM Invoker Role): A caller presents a valid Google-signed OIDC token issued to a service account or user that has not been granted roles/run.invoker on the Cloud Run service. The Cloud Run IAM authorizer evaluates the policy and returns HTTP 403 Forbidden.
  • Audit Evidence: Every rejected request generates an immutable audit record in Cloud Logging with protoPayload.status.code = 7 (PERMISSION_DENIED), enabling automated Security Command Center alerts and rate-based IP banning via Cloud Armor.

5. Rigorous Inventory & Teardown Dependency Ordering (LIFO)

Cloud resource destruction is governed by strict mathematical directed acyclic graph (DAG) dependencies. Deleting infrastructure out of order results in dependency deadlocks (e.g. attempting to delete a VPC subnet while a Cloud Run Direct VPC Egress subinterface holds an active IP allocation) or leaves orphaned resources that quietly accumulate thousands of dollars in unbudgeted billing leaks. To ensure safe, deterministic teardown, architects must enforce a strict Last-In, First-Out (LIFO) Reverse-Dependency Deletion Order across five operational phases:

Teardown Phase Resource Type & Scope Target GCP Resources Reverse Dependency Constraint Orphan Risk & Billing Leak Prevention
Phase 1: Ingress Edge & Forwarding Global Networking & Security Global forwarding rules, target HTTPS proxies, URL maps, SSL certificates, Cloud Armor policies, Serverless NEGs. Must be deleted before compute backends; otherwise ingress proxies attempt to route traffic to non-existent runtimes. Orphaned external forwarding rules and unattached static IP addresses incur hourly reservation fees if unreleased.
Phase 2: Compute Runtimes & IAM Serverless Workloads Cloud Run services (order-service, fulfillment-service), IAM policy bindings, Secret Manager IAM bindings. Must be destroyed before subnets; deleting Cloud Run releases dynamic Direct VPC Egress IP allocations in the VPC subnet. Active Cloud Run min-instances continue billing for idle provisioned vCPU/memory if left running in background.
Phase 3: Messaging & Event Bus Asynchronous Messaging Pub/Sub pull subscriptions, Dead-Letter Topics (orders.v1.dlq), primary topic (orders.v1), Pub/Sub IAM roles. Subscriptions must be detached before topics can be deleted; drain or purge dead-letter messages prior to deletion. Subscriptions retain unacknowledged messages for 7 days, incurring message storage charges and persistent backlog metrics.
Phase 4: Data Layer & Private Access Managed Datastores Private Service Connect forwarding rules (10.128.0.50), Cloud SQL HA instances (primary + standby), automated backup policies. PSC forwarding rule must be deleted before releasing VPC subnet IP; Cloud SQL termination protection must be explicitly disabled. Cloud SQL Regional HA instances represent the single highest hourly billing cost; orphaned instances leak $300–$1,200/month.
Phase 5: Network Foundations & IPs Core VPC Infrastructure Dedicated Direct VPC Egress subnet (10.128.10.0/24), VPC firewall rules, Cloud NAT gateways, static external IPv4 addresses. Subnets cannot be deleted until all NIC subinterfaces, PSC rules, and router attachments are completely released. Reserved external static IP addresses not bound to an active forwarding rule or VM incur idle reservation fees ($0.010/hr).
Apply it: Diagnostic Triage Sequence

Scenario: Client checkouts are failing with HTTP 504 Gateway Timeout. SREs observe that Cloud Run container instances are alive and CPU utilization is under 15%.

Step-by-step Triage:

  1. Inspect Cloud Trace: Query traces with http.status_code=504. Confirm the bottleneck span: if the root span stalls for 60,000ms inside database connection acquisition, the failure is in the datastore layer.
  2. Evaluate Decoupled Probes: Check /healthz versus /readyz. If /healthz returns 200 but /readyz returns 503, the container runtime is healthy but connection pooling to PSC 10.128.0.50:5432 is severed.
  3. Audit PSC Endpoint Status: Inspect forwarding rule operational status and target service attachment connectivity using the Compute API or gcloud compute forwarding-rules describe psc-cloudsql-endpoint --region=us-central1.
  4. Containment: Trip the application circuit breaker to OPEN, forcing instant HTTP 503 with Retry-After headers. This sheds load, preserves user sockets, and enables Cloud SQL HA failover to complete cleanly.
