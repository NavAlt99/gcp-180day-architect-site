3 · Real-world problems and production mitigations

Cloud Pub/Sub Ordering Key Poison Pill Stalling Regional Stream and EOD Transport Misconception · field case

Situation and impact: Brightloaf's regional fulfillment pipeline deployed an update to store point-of-sale (POS) systems across the Midwest region. The pipeline utilized Cloud Pub/Sub with message ordering enabled, using ordering_key = store_id to ensure that inventory deductions, register receipts, and customer order updates were processed in strict sequential order. Immediately following the deployment, POS terminal POS-042 at store store-chi-042 emitted an invalid order event containing an unescaped control character in the customer notes field. The downstream fulfillment microservice failed to deserialize the JSON payload, raised an unhandled exception, and returned a negative acknowledgment (nack) to Pub/Sub. Because ordering keys guarantee sequential delivery, Pub/Sub paused the entire partition for store-chi-042 and repeatedly redelivered the malformed poison pill. Over the next 52 minutes, 14,000 valid customer orders across Chicago retail bakeries accumulated in the unacknowledged queue backlog, bringing regional dispatch to a complete standstill. Concurrently, an upstream network blip caused the payment gateway to retry unacknowledged publish RPCs. Because engineering operated under the assumption that Pub/Sub's Exactly-Once Delivery (EOD) prevented duplicate processing end-to-end, the consumer processed each retried message as an independent transaction, generating 820 duplicate credit card charges totaling $61,500.

Diagnostic sequence:

  1. Backlog and Age Telemetry: Cloud Monitoring metrics for the subscription fulfillment-worker-sub showed subscription/oldest_unacked_message_age spiking to 3,120 seconds, while subscription/backlog_bytes grew exponentially. However, overall CPU utilization on consumer pods remained below 5%, indicating that worker threads were idle rather than compute-bound.
  2. Partition Identification: Querying subscriber log streams in Cloud Logging revealed continuous, repeating stack traces: json.decoder.JSONDecodeError: Invalid control character at: line 1 column 142. Filtering logs by ordering_key identified that 100% of repeated deserialization failures were concentrated on a single key: store-chi-042.
  3. Ordering Stoppage Verification: Inspecting Pub/Sub subscription metrics confirmed that valid messages published after the initial failure were buffered in the topic but withheld from delivery, adhering strictly to Pub/Sub's ordering guarantee.
  4. Producer Retry Audit: Financial ledger reconciliation flagged 820 transactions with distinct Pub/Sub message_id values but identical POS terminal transaction IDs (pos_tx_id) and identical credit card authorization tokens. Tracing payment gateway egress logs confirmed that network socket timeouts during peak load triggered publisher-side retries, emitting duplicate messages with unique message IDs.

Root cause: Two interrelated architectural failures caused the incident: (1) The subscription lacked a Dead Letter Topic and exponential backoff retry policy, allowing a single deserialization error to halt an entire ordering partition indefinitely via head-of-line blocking; (2) The engineering team conflated transport-level Exactly-Once Delivery (which only prevents broker-to-client redeliveries during an active lease) with end-to-end business idempotency, failing to implement consumer-side deduplication against producer publish retries.

Defensible remediation:

  1. Configure Dead Letter Topic & Delivery Threshold: Attach a Dead Letter Topic (orders.v1.deadletter) to the subscription with maxDeliveryAttempts: 5. Grant the Cloud Pub/Sub service account (service-{PROJECT_NUMBER}@gcp-sa-pubsub.iam.gserviceaccount.com) the roles/pubsub.publisher role on the dead-letter topic and roles/pubsub.subscriber on the primary subscription.
  2. Implement Exponential Retry Backoff: Configure the subscription retry policy with a minimum backoff of 10 seconds and a maximum backoff of 600 seconds, preventing tight deserialization retry loops.
  3. Emergency Cursor Reset via Seek: During the incident, operators captured a subscription snapshot, executed the seek operation to bypass the poison pill, and pushed the offending message into a manual quarantine queue for offline reprocessing: 
    gcloud pubsub subscriptions seek fulfillment-worker-sub --time="2026-09-28T04:15:00Z"
  4. Implement Consumer-Side Token Deduplication: Add an application-level deduplication filter in the consumer microservice backed by a Cloud SQL unique token store (keyed on pos_tx_id), discarding duplicate messages resulting from publisher retries.

Verification: The remediation was validated in the staging environment by injecting 5 synthetic malformed JSON payloads interleaved among 50,000 valid messages under ordering key store-chi-042. Cloud Monitoring confirmed that each poison pill was retried exactly 5 times, after which Pub/Sub automatically forwarded the message to orders.v1.deadletter and acknowledged it on the primary subscription. The remaining 49,995 valid messages processed with zero disruption, maintaining an end-to-end p99 delivery latency of 85ms. Synthetic publisher retries injecting duplicate pos_tx_id tokens were intercepted by the consumer deduplication table with 100% accuracy, verifying zero duplicate financial transactions.

Residual Risk: Messages diverted to the Dead Letter Topic require operational monitoring and an automated replay mechanism once software fixes are deployed. Alert policies must be established on subscription/dead_letter_message_count > 0 to notify on-call engineers of quarantined payloads.

Transactional Outbox Dual-Write Failure and Premature Crash-After-Ack Data Loss · field case

Situation and impact: Brightloaf's Order Service initially utilized direct procedural dual-writing: incoming checkout requests wrote an order row into a Cloud SQL PostgreSQL database and immediately called pubsub_client.publish() to notify regional warehouse fulfillment services. During a high-velocity Black Friday promotion, Cloud SQL connection pool saturation caused database write latencies to increase to 1,800ms. In several dozen concurrent checkout threads, the database write succeeded and committed, but the subsequent HTTP/2 gRPC call to Pub/Sub timed out after 3 retries due to client-side network socket exhaustion. As a result, 340 customer orders were committed and billed in Cloud SQL, but no fulfillment event was ever emitted to Pub/Sub; the orders sat invisible and unfulfilled in the database while customers complained of missing deliveries. In an emergency reaction, an engineering team deployed a hotfix to the fulfillment consumer service that moved the message.ack() call to the very beginning of the message handler to "prevent Pub/Sub ack deadline timeouts." Two hours later, a Google Kubernetes Engine (GKE) node pool upgrade triggered spot VM preemptions across the cluster. Worker pods acknowledged 185 incoming order messages from Pub/Sub, but their underlying nodes were terminated by GKE before the worker processes could commit the order records to Cloud SQL. Pub/Sub dropped the messages permanently, erasing 185 paid customer orders from the platform without trace.

Diagnostic sequence:

  1. Audit Log Discrepancy: Automated end-of-day reconciliation between Stripe payment capture webhooks and Cloud SQL orders rows revealed 340 orders marked 'PAID' in Stripe and present in Cloud SQL, but completely missing from warehouse dispatch logs and Pub/Sub audit logs.
  2. Network Socket Inspection: Cloud Logging for the Order Service showed client-side gRPC exceptions: grpc._channel._InactiveRpcError: StatusCode.DEADLINE_EXCEEDED occurring immediately after db.commit() calls, proving that events were dropped post-commit due to network timeouts.
  3. Ack-Without-Commit Investigation: Analysis of GKE pod termination logs during the node pool upgrade revealed that 4 fulfillment worker pods received SIGTERM signals while processing batches. Pub/Sub subscription metrics recorded 185 message acknowledgments, but a SQL query for the corresponding order IDs in Cloud SQL returned 0 rows. Tracing the hotfixed code confirmed that message.ack() was executed prior to the database transaction, causing catastrophic message loss upon container termination.

Root cause: The initial outage was caused by the dual-write trap, where independent non-atomic operations across Cloud SQL and Pub/Sub inevitably drop events during network timeouts. The secondary, catastrophic data loss was caused by violating the fundamental crash/ack boundary invariant: acknowledging a message before durable database persistence guarantees irreversible message loss whenever worker compute instances terminate prematurely.

Defensible remediation:

  1. Implement the Transactional Outbox Pattern: Re-architect the Order Service to write business records to orders and event envelopes to an outbox_events table within a single ACID transaction in Cloud SQL. Completely eliminate direct Pub/Sub publish calls from the order ingestion path.
  2. Deploy Resilient Outbox Relay Worker: Deploy a dedicated daemon worker that polls outbox_events using SELECT ... FOR UPDATE SKIP LOCKED LIMIT 100, publishes events to Cloud Pub/Sub with ordering keys, and updates outbox row status to 'PUBLISHED' only after receiving the Pub/Sub publish acknowledgment. (For high-throughput clusters, migrate the relay to serverless Datastream CDC).
  3. Enforce the Crash-Before-Ack Boundary: Revert the consumer hotfix and enforce the strict invariant: consumers must execute the database transaction inserting into processed_events and mutating business state FIRST; message.ack() is executed ONLY after the database transaction successfully commits.
  4. Enable Automatic Ack Deadline Extension: Configure the consumer's subscriber_client flow control settings to automatically extend acknowledgment deadlines while worker database transactions are in flight, eliminating artificial timeout pressure.

Verification: The remediation was validated under a chaotic load test injecting 2,500 checkout transactions per second while systematically evicting 20% of GKE worker pods via targeted pod deletion commands and severing Cloud SQL network connections for 15-second intervals. End-to-end reconciliation verified that 100% of the 50,000 generated orders were captured in Cloud SQL, 100% were published via the Transactional Outbox Relay, and 100% were fulfilled by the consumer. Replayed messages resulting from killed worker pods were safely intercepted by the processed_events table, yielding exactly 0 duplicate fulfillments and 0 lost orders.

Residual Risk: The polling outbox table can accumulate millions of historical published records, degrading query performance. An automated partitioning policy or scheduled archival job must run daily to purge rows with status = 'PUBLISHED' AND created_at < NOW() - INTERVAL '7 days'.
