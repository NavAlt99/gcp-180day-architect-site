Incident 26.1

Exfiltrated Static Key Breach: Rogue Spanner Mutations Threaten Duplicate Baking

Symptom

At 03:14 UTC, Brightloaf's security monitoring alerted on anomalous write activity on the primary Cloud Spanner instance orders-spanner in project brightloaf-prod-orders. Over 1,200 active bakery orders had their status updated to CANCELLED, while 450 new synthetic order records were inserted. Concurrently, regional bakery dispatch lines experienced processing anomalies, receiving conflicting order IDs.

Constraints & Invariant

Duplicate Fulfillment Invariant: The physical baking line must never execute duplicate batches for the same customer order (≤ 1 physical fulfillment per unique order ID).
Operational Constraint: SREs must immediately revoke attacker access without interrupting valid in-flight transactions from legitimate microservices.

Incident Evidence

      "serviceAccountKeyName": "//iam.googleapis.com/projects/brightloaf-prod-orders/serviceAccounts/sa-fulfillment-worker@.../keys/8f4c9a12b0e7"

Root Cause Analysis

A contractor attempting to debug an order routing script generated a service account JSON private key on their local laptop. The contractor accidentally committed the key file (sa-fulfillment-worker-key.json) into a public repository. Within 28 minutes, an automated scanner scraped the private key and began issuing unauthorized mutations against Cloud Spanner. Because the service account held broad write permissions on the database and static keys do not record caller IP or identity, the attacker was able to anonymously alter transactional order states.

5-Step Diagnostic Sequence

  1. Key Identification: Search Cloud Audit Logs for the anomalous serviceAccountKeyName to identify the compromised key ID (8f4c9a12b0e7).
  2. Immediate Key Revocation: Delete the compromised key via IAM to instantly invalidate all subsequent API calls from the attacker.
  3. Database Mutation Scoping: Query Cloud Spanner commit timestamps to isolate all transactions executed using the compromised key between 03:14 UTC and 03:42 UTC.
  4. Fulfillment Re-verification: Cross-reference the affected 1,200 order IDs against regional bakery fulfillment dispatch systems to freeze any conflicting orders before bread dough entered production ovens.
  5. Key Estate Audit: Run an inventory across all Google Cloud projects to locate any remaining active service account keys.

Defensible Solution & Mitigation

To permanently eliminate static key exfiltration risks:

  1. Enforce the organization policy constraint constraints/iam.disableServiceAccountKeyCreation across the entire organization hierarchy.
  2. Migrate all automated workloads to Attached Workload Identity (GKE Workload Identity and Cloud Run runtime service accounts).
  3. Mandate that human engineers and CI/CD runners access production resources strictly via Service Account Impersonation using roles/iam.serviceAccountTokenCreator, ensuring complete dual-principal audit trails.
  4. Roll back the fraudulent Spanner mutations using Spanner point-in-time recovery (PITR) to restore order state prior to 03:14 UTC. Re-validate that no cancelled order was re-dispatched to physical bakery lines.

Verification & Residual Risk

Verification: Attempt to create a service account key using the iam service-accounts keys create CLI method against any project. Confirm the operation is blocked with Request is prohibited by organization policy: constraints/iam.disableServiceAccountKeyCreation.

Residual Risk: Third-party SaaS tools that do not support Workload Identity Federation may require temporary organizational policy exceptions. Such exceptions must require VP approval and 30-day automated key expiration.

Incident 26.2

Access Token vs ID Token Mismatch: Cloud Run Ingress 401 Outage

Symptom

At 06:00 UTC, store edge gateways across forty retail locations began logging HTTP 401 Unauthorized errors when transmitting morning batch bread orders to the central ingestion endpoint (https://order-ingest-prod-xyz.run.app). Over 3,400 orders accumulated in edge gateway retry buffers, and bakery management dashboards showed zero inbound orders for the upcoming morning baking shift.

Constraints & Invariant

Duplicate Fulfillment Invariant: When store gateways flush their backlogged queues, accumulated retries must not result in duplicate baking orders (≤ 1 physical fulfillment per unique order ID).
Security Constraint: The Cloud Run ingestion microservice must remain private and authenticated (allUsers invoker access strictly prohibited).

Incident Evidence

HTTP/2 401 Unauthorized
content-type: text/html; charset=UTF-8
date: Sun, 27 Sep 2026 06:01:14 GMT
server: Google Frontend
www-authenticate: Bearer error="invalid_token" error_description="The token is not an ID token"
content-length: 331

<html><head><title>401 Unauthorized</title></head>
<body><h1>401 Unauthorized</h1>
The request was not authenticated. Expected OpenID Connect ID token with audience matching service URI.
</body></html>

Root Cause Analysis

During a weekend software upgrade of the store edge gateways, developers updated the authentication module to use Google Cloud client libraries. However, the client code invoked google.auth.default() to acquire an OAuth2 Access Token (the standard bearer token used for Google Cloud APIs such as Cloud Storage and Pub/Sub). Because the target service was a private Cloud Run endpoint guarded by Google Cloud's serverless ingress proxy, the proxy required an OpenID Connect (OIDC) ID Token containing an aud (audience) claim matching the service URL. Passing an access token caused the ingress proxy to immediately reject the request with HTTP 401 before it ever reached the application container.

5-Step Diagnostic Sequence

  1. Header Inspection: Inspect the WWW-Authenticate response header from the Cloud Run endpoint to observe error_description="The token is not an ID token".
  2. Token Type Analysis: Decode the bearer token transmitted by the client gateway. Confirm that the token is an opaque OAuth2 access token (starting with ya29.) rather than a three-part JWT (Header.Payload.Signature).
  3. Audience Validation Check: Verify that the Cloud Run service IAM policy grants roles/run.invoker to the store gateway service account.
  4. Backlog Queue Throttling: Place edge gateway outbound dispatch queues into a controlled drain state to prevent a burst of duplicate order submissions upon authentication restoration.
  5. Client Library Reconfiguration: Update edge client code to use google.auth.transport.requests with google.oauth2.id_token.fetch_id_token specifying the explicit target service audience.

Defensible Solution & Mitigation

To restore order ingestion and prevent future token confusion:

  1. Deploy a hotfix to edge store gateways: configure the client to request an OIDC ID token targeting audience="https://order-ingest-prod-xyz.run.app".
  2. Verify that the gateway service account retains roles/run.invoker on the Cloud Run service.
  3. Slowly drain the backlogged order queues through an idempotent ingestion gateway that inspects the order_id against the Spanner deduplication index, dropping replayed events.
  4. Add automated CI/CD integration tests asserting that all client SDK calls targeting internal microservices utilize ID tokens, while calls targeting GCP resource APIs use access tokens.

Verification & Residual Risk

Verification: Execute an authorized curl probe passing the newly generated OIDC ID token to the Cloud Run endpoint. Confirm the response status is HTTP/2 200 OK and inspect Cloud Run request logs to verify identity extraction.

Residual Risk: If the Cloud Run service URL changes (e.g., migrating to a custom domain), client configurations must update their requested audience parameter; otherwise, audience mismatch errors will recur.
