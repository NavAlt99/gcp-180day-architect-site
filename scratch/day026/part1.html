Part 1 · Topics of the day

Architecting modern Google Cloud workload authentication: eliminating service account keys through attached identities and impersonation, mastering Application Default Credentials (ADC) lookup order, and distinguishing OAuth2 access tokens from OIDC ID tokens.

Topic 01

Service accounts, least privilege, attached identity, impersonation and key avoidance

What it is: Service accounts are specialized non-human Google Cloud identities used by applications, microservices, and automation pipelines to authenticate against Google Cloud APIs. Traditional architectures relied on downloadable JSON private keys, but modern cloud security mandates key avoidance. Workloads run under attached identities (via Compute Engine, GKE Workload Identity, or Cloud Run runtime service accounts), while human operators and CI/CD pipelines generate ephemeral access tokens through service account impersonation using the roles/iam.serviceAccountTokenCreator role.

Why today: Downloadable service account JSON keys represent the single most common attack vector in cloud environments. They never expire automatically, cannot be centrally rotated without coordinated application restarts, and frequently leak into version control systems, developer laptops, and CI/CD build artifacts. Attached identities and impersonation replace static secrets with short-lived, centrally audited OAuth2 tokens minted on demand.

Where it sits: Service accounts function both as an identity (a principal granted permissions on Google Cloud resources) and as a resource itself (an object upon which other principals are granted permissions, such as the permission to impersonate or attach the account). Understanding this dual nature is vital for enforcing least privilege.

A leaked service account private key stored in an engineer's public repository was weaponized by an unauthorized actor to issue administrative Cloud Spanner mutations. The fraudulent database writes injected fake order cancellations into the production queue, halting seven bakery dispatch lines and threatening Brightloaf's duplicate fulfillment invariant.

Topic 02

ADC resolution at introductory depth, metadata service, access versus ID tokens, audience and expiry

What it is: Application Default Credentials (ADC) is Google Cloud's standardized credential discovery protocol implemented across all Google Cloud client libraries. ADC resolves credentials transparently by traversing a deterministic search chain: first checking the GOOGLE_APPLICATION_CREDENTIALS environment variable, then inspecting user credentials generated by the local Cloud SDK, and finally querying the local Compute Engine metadata server (http://metadata.google.internal/computeMetadata/v1/). Furthermore, workloads utilize two structurally distinct token types: OAuth2 Access Tokens for authorizing requests to Google APIs, and OpenID Connect (OIDC) ID Tokens (JWTs with explicit aud audience claims) for authenticating to private Cloud Run, Cloud Functions, and API gateways.

Why today: Developers frequently confuse access tokens and ID tokens, attempting to call private serverless endpoints with raw Google API access tokens, or conversely passing ID tokens to Cloud Storage or Spanner. This misunderstanding leads to intermittent authentication failures, insecure audience validation, and broken deployment pipelines.

Where it sits: The metadata service and ADC protocol operate at the machine-runtime boundary. They abstract credential management away from application logic, providing automatic, in-memory token caching and refresh before expiration without storing secrets on disk.

An order ingestion service mistakenly passed an OAuth2 access token instead of a signed OIDC ID token with a matching audience to a private Cloud Run fulfillment endpoint. The resulting HTTP 401 Unauthorized rejection dropped 3,400 incoming store orders during peak breakfast hours, delaying regional truck departures and incurring heavy retail SLA penalties.
