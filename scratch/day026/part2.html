Part 2 · Technical discussion

In-depth technical architecture of Google Cloud service account lifecycles, Application Default Credentials (ADC) resolution mechanics, and the cryptographic distinction between authorization access tokens and identity ID tokens.

Topic 01 · Service accounts, least privilege, attached identity, impersonation and key avoidance

A service account is a specialized identity managed by Google Cloud IAM designed for automated workloads, microservices, and continuous integration pipelines rather than human end-users. In Google Cloud, service accounts occupy a unique architectural posture: they are both an identity (which can be granted IAM roles on resources such as Pub/Sub topics or Spanner databases) and a resource (which has its own IAM policy controlling which principals can act as or impersonate that service account).

The Vulnerability of Static Service Account Keys

Historically, workloads running outside Google Cloud or automated developer tooling authenticated by generating downloadable JSON private key pairs (containing an RSA private key). This pattern represents an extreme security liability:

  • Indefinite Lifespan: Static keys never expire by default. A key generated today remains valid for up to 10 years unless explicitly revoked in the Google Cloud Console or API.
  • Zero Attribution: If an attacker obtains a downloaded private key, every API call issued with that key appears in Cloud Audit Logs as originating from the service account itself, completely obscuring the true physical identity or IP of the threat actor.
  • Secret Sprawl: Keys inevitably end up stored in developer home directories, CI/CD configuration variables, Docker images, and public or private Git repositories.

Because of these risks, modern enterprise security enforces Key Avoidance. Organizations apply the organization policy constraint constraints/iam.disableServiceAccountKeyCreation across all production folders to strictly block the creation of new static keys.

Attached Workload Identity and Service Account Impersonation

Modern Google Cloud architectures eliminate static keys using two primary paradigms:

  1. Attached Workload Identity: When workloads execute on native Google Cloud compute platforms (Compute Engine VMs, Google Kubernetes Engine pods, Cloud Run containers, or Cloud Functions), the platform attaches the service account identity directly to the execution runtime. The workload requests short-lived (1-hour) OAuth2 access tokens directly from the local Compute Engine metadata server without any credentials stored on disk.
  2. Service Account Impersonation: Human developers, operational engineers, or external CI/CD runners authenticate using their own primary identity (e.g., corporate Google Workspace identity or federated workforce identity) and dynamically assume the identity of a target service account. The initiating principal must possess the roles/iam.serviceAccountTokenCreator role on the target service account resource. When requested, Google Cloud's IAM Credentials API verifies caller permissions and mints an ephemeral access token valid for a maximum of 60 minutes. Crucially, Cloud Audit Logs records both the impersonated service account and the human principal who requested the impersonation token (dual-principal audit logging).

Topic 02 · ADC resolution at introductory depth, metadata service, access versus ID tokens, audience and expiry

Google Cloud client libraries implement a standardized, automated credential discovery workflow known as Application Default Credentials (ADC). Rather than hardcoding credentials or loading files directly, client libraries instantiate authentication providers that search a predefined sequence of locations to discover credentials.

ADC Resolution Precedence Order

  1. Environment Variable GOOGLE_APPLICATION_CREDENTIALS: If set, the client library reads the file pointed to by this variable. The file may contain a service account key, an external workforce identity configuration, or user credentials.
  2. User ADC (Local Development): If the environment variable is unset, the library searches for the well-known user credentials file generated by the Google Cloud CLI:
    Linux/macOS: ~/.config/gcloud/application_default_credentials.json
    Windows: %APPDATA%\gcloud\application_default_credentials.json
    Note: Running the standard CLI login flow authenticates the Google Cloud CLI itself, but client libraries specifically require the auth application-default login command to populate this local JSON file.
  3. Attached Compute Metadata Server: If no local files exist, the library queries the Compute Engine metadata server via the link-local IP http://169.254.169.254/computeMetadata/v1/ (or hostname http://metadata.google.internal/computeMetadata/v1/) supplying the mandatory HTTP header Metadata-Flavor: Google. The metadata server dynamically returns an OAuth2 token minted for the VM's or container's attached service account.
  4. Terminal Error: If all three discovery steps fail, the library raises DefaultCredentialsError: Could not automatically determine credentials.

OAuth2 Access Tokens vs. OpenID Connect (OIDC) ID Tokens

Understanding the fundamental distinction between Access Tokens and ID Tokens is essential for securing multi-tier cloud architectures:

  • OAuth2 Access Tokens (Authorization): Used exclusively to authorize calls to Google Cloud APIs (such as Cloud Storage, Pub/Sub, BigQuery, or Spanner). Access tokens are typically opaque bearer tokens (starting with ya29.) that represent authorization grants scoped to API URL sets (e.g., https://www.googleapis.com/auth/cloud-platform). The receiving Google API gateway parses and checks the token against IAM policies. Access tokens do not contain an audience claim targeting third-party or custom application endpoints.
  • OpenID Connect ID Tokens (Authentication & Identity): Used to authenticate a caller's identity to custom services, private Cloud Run microservices, Cloud Functions, and API Gateways. An ID token is a cryptographically signed JSON Web Token (JWT) conforming to the OIDC standard. It contains standard claims: iss (issuer: https://accounts.google.com), sub (subject: unique principal ID), email (service account email), exp (expiration timestamp), and most crucially, aud (audience). The destination service validates that the token was signed by Google's public certificates and verifies that the aud claim strictly matches its own URL (e.g., https://order-dispatch-xyz.run.app).
