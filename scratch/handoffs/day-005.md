- topic-01: Relevance to GCP: Google Cloud VPN encrypts all traffic using IPsec ESP with pre-shared keys or certificates. Cloud VPN supports both HA VPN and Classic VPN, enforcing tunnel-mode encapsulation. Each Cloud VPN tunnel can process up to 250,000 packets per second or up to 3 Gbps egress/ingress depending on packet size. Primary documentation: Google Cloud HA VPN overview (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#ha-vpn, https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#ipsec_and_ike_support
- topic-01: Relevance to GCP: Cloud VPN strongly recommends IKEv2 for faster rekeying, improved reliability, and support for dynamic route renegotiation. Google Cloud HA VPN enforces IKEv2 exclusively, requiring BGP peering across Cloud Router, whereas legacy Classic VPN supported IKEv1 with static routing. Primary documentation: Google Cloud IKE and Dead Peer Detection (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#ike-and-dpd, https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#ha-vpn
- topic-01: Relevance to GCP: Google Cloud provides native managed Site-to-Site VPN through Cloud VPN (HA VPN with two gateway interfaces providing 99.99% service availability). Google Cloud does not provide a multi-tenant managed Client VPN service; instead, architects implement Google Cloud Identity-Aware Proxy (IAP) for zero-trust application access, or host self-managed virtual appliances (e.g. OpenVPN Access Server) on Compute Engine when legacy client VPN tunnels are mandated. Primary documentation: Google Cloud VPN topologies and HA architecture (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#ha-vpn, https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/topologies#ha-configurations
- topic-01: Relevance to GCP: Google Cloud HA VPN requires Cloud Router and BGP dynamic routing. When a new subnet is created in the VPC, Cloud Router automatically advertises the new CIDR to the on-premises peer over BGP without requiring manual static route updates or tunnel recreation. Static route-based and policy-based VPNs are restricted to legacy Classic VPN. Primary documentation: Cloud VPN HA requirements and Cloud Router integration (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#ha-vpn, https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#ha-vpn-stack-types
- topic-01: Relevance to GCP: Google Cloud VPC virtual networks support MTU values of 1460 or 1500 (and jumbo frames up to 8896). Cloud VPN gateways default to an MTU of 1460 bytes to accommodate IPsec ESP overhead without fragmentation. GCP automatically enforces MSS clamping on Cloud VPN interfaces to prevent MTU black holes. Primary documentation: Google Cloud VPN specifications and MTU (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#specifications, https://docs.cloud.google.com/network-connectivity/docs/vpn/concepts/overview#network-bandwidth
- topic-02: Relevance to GCP: Google Cloud provides distinct load balancer categories: Network Load Balancers (regional L4 passthrough balancers built on Maglev) versus Application Load Balancers (global and regional L7 proxies based on Envoy). Application Load Balancers evaluate URL maps to route traffic across distinct backend services. Primary documentation: Google Cloud load balancer types overview (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview#load-balancer-types, https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview#application-lb, https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview#network-lb
- topic-02: Relevance to GCP: Google Cloud health check probes originate from distributed Google IP ranges: 35.191.0.0/16 and 130.211.0.0/22 for global and regional proxies, and 35.191.0.0/16 for internal load balancers. VPC firewalls must explicitly allow ingress from these probe ranges on the health check port; failure to permit probe ingress causes the load balancer to mark all backends unhealthy immediately. Primary documentation: Google Cloud health check concepts and health state transitions (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/load-balancing/docs/health-check-concepts#health_state, https://docs.cloud.google.com/load-balancing/docs/health-check-concepts#criteria-protocol-http
- topic-02: Relevance to GCP: Cloud Load Balancing supports multiple session affinity modes configured on backend services: NONE (round-robin/least request), CLIENT_IP , GENERATED_COOKIE , and HEADER_FIELD . When a backend instance fails its health check, GCP automatically re-hashes client sessions to remaining healthy instances regardless of affinity settings. Primary documentation: Google Cloud load balancer backend service configuration (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview#load-balancer-types, https://docs.cloud.google.com/load-balancing/docs/load-balancing-overview#summary-gclb
- topic-02: Relevance to GCP: Google Cloud's External and Internal Network Load Balancers use Maglev distributed software routing to achieve line-rate passthrough performance: the client IP is preserved directly in the IP packet header received by the VM NIC, and egress traffic routes directly through the VPC virtual network gateway rather than hairpinning through a proxy instance. Google Application Load Balancers use Envoy proxies located at Google Point of Presence (PoP) edge infrastructure. Primary documentation: Underlying technologies of Google Cloud load balancers (accessed 2026-10-04) . - topic-02: Relevance to GCP: Cloud Load Balancing backend services provide configurable connection draining timeouts (defaulting to 300 seconds, configurable from 0 to 3600 seconds). Global Application Load Balancers use balancing modes based on Rate (RPS per instance) or Utilization (target CPU), dynamically routing traffic across global instance groups and overflowing to alternative regions when local instance capacity is exhausted. Primary documentation: Key features of Cloud Load Balancing (accessed 2026-10-04) . - topic-03: Relevance to GCP: Google Cloud VPC firewall rules are strictly stateful and enforced distributed across virtual machine hypervisors via Google's Andromeda virtual switch layer. Return traffic is automatically allowed, regardless of any configured ingress or egress deny rules. Andromeda maintains conntrack tables per VM instance, meaning firewalls scale horizontally with compute capacity and avoid centralized network appliance bottlenecks. Primary documentation: Google Cloud VPC firewall rule components (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/firewall/docs/firewalls#firewall_rule_components, https://docs.cloud.google.com/firewall/docs/firewalls#priority_order_for_firewall_rules
- topic-03: Relevance to GCP: Google Cloud VPC firewall rules accept priority values between 0 and 65535 (default priority is 1000). If two rules have identical priority and matching criteria, a DENY rule always takes precedence over an ALLOW rule. Furthermore, Hierarchical Firewall Policies enforced at the Organization or Folder level take precedence over all VPC-level firewall rules. Primary documentation: Google Cloud priority order for firewall rules (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/firewall/docs/firewalls#priority_order_for_firewall_rules, https://docs.cloud.google.com/firewall/docs/firewalls#firewall_rule_components
- topic-03: Relevance to GCP: Every Google Cloud VPC network has two unremovable, uneditable implied baseline firewall rules at priority 65535: an implied allow egress rule (permits all outbound traffic from all instances) and an implied deny ingress rule (blocks all inbound traffic to all instances). Default VPCs also include pre-populated priority 65534 rules (e.g. default-allow-internal, default-allow-ssh, default-allow-rdp), which enterprise architects routinely delete or override with custom zero-trust policies. Primary documentation: Google Cloud implied firewall rules (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/firewall/docs/firewalls#firewall_rule_components, https://docs.cloud.google.com/firewall/docs/firewalls#priority_order_for_firewall_rules
- topic-03: Relevance to GCP: Google Cloud VPC firewall rules support three target filtering mechanisms: All instances in network , Target network tags , and Target service accounts . Source filtering similarly supports IP CIDR blocks, source tags, and source service accounts. Rules targeting service accounts are strictly validated and cannot be combined with network tags. Primary documentation: Google Cloud target parameters and service accounts (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/firewall/docs/firewalls#firewall_rule_components, https://docs.cloud.google.com/firewall/docs/firewalls#priority_order_for_firewall_rules
- topic-03: Relevance to GCP: In Google Cloud, firewall rules operate at the VM hypervisor boundary. A common architecture flaw occurs when a public load balancer is placed in front of backend VMs, but the backend VMs retain public IP addresses and a broad priority 100 ingress firewall rule permits traffic from 0.0.0.0/0 . Attackers discover the backend VM public IPs and connect directly to port 443, completely bypassing the load balancer, Cloud Armor WAF policies, and rate limits. Primary documentation: Google Cloud firewall architecture and defense boundaries (accessed 2026-10-04) . Cited supporting sections in subtopic (support unreviewed): https://docs.cloud.google.com/firewall/docs/firewalls#firewall_rule_components, https://docs.cloud.google.com/firewall/docs/firewalls#priority_order_for_firewall_rules
