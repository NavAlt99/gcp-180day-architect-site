- topic-01: Relevance to GCP: In Google Cloud, High Availability is native to regional multi-zone compute and storage services. Regional Managed Instance Groups (Regional MIGs) automatically balance virtual machines across three zones within a region (e.g., us-central1-a , b , and c ); if an entire zone experiences a power disruption, the regional MIG health checker detects the failure and provisions replacement instances in the remaining healthy zones. Similarly, Cloud SQL HA maintains a primary database in one zone and a synchronous standby replica in an alternate zone using regional persistent disk replication, executing automatic failover in approximately 60 seconds if the primary becomes unresponsive. Cited supporting sections in subtopic: https://docs.cloud.google.com/architecture/disaster-recovery#how_rto_limits_product_choices
- topic-01: Relevance to GCP: In Google Cloud, fault tolerance at the data layer is embodied by Cloud Spanner . Spanner utilizes Google's proprietary TrueTime API (synchronized atomic clocks and GPS receivers) combined with Paxos consensus distributed across multiple data centers and regions. Writes are committed synchronously across a quorum of replicas; if a storage node or entire availability zone crashes mid-transaction, surviving quorum nodes finalize the commit seamlessly with zero failover pause and five-nines (99.999%) SLA availability. At the network tier, Google's global software-defined Andromeda mesh provides fault-tolerant packet delivery by dynamically rerouting traffic around physical fiber cuts in sub-milliseconds without dropping established TCP flows. Cited supporting sections in subtopic: https://docs.cloud.google.com/architecture/disaster-recovery#how_rto_limits_product_choices
- topic-01: Relevance to GCP: Google Cloud facilitates multi-region DR across managed services. For cold/warm DR, architects configure automated cross-region replication: Cloud Storage dual-region buckets ( nam4 or eur4 ) with Turbo Replication guarantee 100% object replication between distant regions within 15 minutes. For database tiers, Cloud SQL Cross-Region Read Replicas maintain asynchronous copies in a distant region, which can be promoted to a standalone read-write primary via gcloud sql instances promote-replica during regional evacuations. Compute infrastructure is codified using declarative Terraform scripts, enabling rapid reconstitution in alternate regions without manual human configuration errors. Cited supporting sections in subtopic: https://docs.cloud.google.com/architecture/disaster-recovery#how_rto_limits_product_choices
- topic-01: Relevance to GCP: Google Cloud publishes product-specific RTO and RPO capability mappings in the official Architecture Center. For example, Cloud Spanner provides RPO = 0 and RTO = 0 natively. Cloud SQL HA provides RPO = 0 and RTO < 60 seconds for single-zone failures, but cross-region read replica failover provides RPO of seconds (due to asynchronous replication lag) and RTO of 5 to 15 minutes for promotion. Persistent Disk Asynchronous Replication (PD Async Rep) replicates block storage between regions with an RPO target under 1 minute without requiring application-level database replication engines. Cited supporting sections in subtopic: https://docs.cloud.google.com/architecture/disaster-recovery#how_rto_limits_product_choices
- topic-01: Relevance to GCP: Google Cloud enforces this critical separation across its storage and database portfolios. In Cloud SQL , architects combine High Availability (for automatic zonal hardware failover) with automated daily backups and continuous Write-Ahead Log ( WAL ) archiving. This enables Point-in-Time Recovery ( PITR ) via gcloud sql instances restore-backup , allowing restoration to any specific minute within the preceding 7 days. In Cloud Storage , architects protect against accidental bucket deletion by enabling Object Versioning and configuring Bucket Lock with WORM (Write Once, Read Many) retention policies that legally prevent objects from being deleted even by root administrative credentials until the retention period expires. Cited supporting sections in subtopic: https://docs.cloud.google.com/architecture/disaster-recovery#how_rto_limits_product_choices
- topic-02: Relevance to GCP: In Google Cloud, stateless architecture is the native execution model for Cloud Run and standard Stateless Managed Instance Groups (MIGs) . Cloud Run scales container instances from zero to hundreds of concurrent workers in sub-seconds in response to incoming HTTP traffic. Because containers maintain zero local disk state, Google Cloud routes incoming traffic to whichever container instance has available concurrency headroom across the entire region. Cited supporting sections in subtopic: https://docs.cloud.google.com/compute/docs/instance-groups#support_for_stateful_workloads
- topic-02: Relevance to GCP: Google Cloud provides managed stateful storage services that encapsulate this distributed complexity, such as Cloud SQL , AlloyDB , Cloud Spanner , and Cloud Bigtable . When architects must run self-managed stateful software (such as custom Cassandra or Kafka clusters) directly on Compute Engine, they utilize Stateful Managed Instance Groups with stateful disk configurations to guarantee that attached Persistent Disks and IP addresses persist across VM repair and update cycles. Cited supporting sections in subtopic: https://docs.cloud.google.com/compute/docs/instance-groups#support_for_stateful_workloads
- topic-02: Relevance to GCP: In GCP architectures, architects isolate the presentation and business logic layers into stateless Regional MIGs or Cloud Run services. All transient user sessions are externalized to Memorystore for Redis , and all durable business transactions are committed to Cloud SQL or Cloud Spanner . This decoupling ensures that the compute tier can autoscale from 2 to 200 instances without touching database schemas or risking session loss. Cited supporting sections in subtopic: https://docs.cloud.google.com/compute/docs/instance-groups#support_for_stateful_workloads
- topic-02: Relevance to GCP: Google Cloud provides Memorystore for Redis as a fully managed, in-memory caching service with High Availability support. In an HA Memorystore configuration, Google Cloud automatically provisions a primary node and a replica node across two separate zones, replicating data via asynchronous replication and executing automatic failover within 30 seconds if the primary node degrades. Cited supporting sections in subtopic: https://docs.cloud.google.com/compute/docs/instance-groups#support_for_stateful_workloads
- topic-02: Relevance to GCP: Architects configure Stateful MIGs via gcloud compute instance-groups managed set-stateful-policy , defining specific device names (such as --stateful-disk=device-name=data-disk,auto-delete=never ) and static IP reservation. This capability allows organizations to modernize legacy stateful workloads with automated health-check auto-healing while guaranteeing zero data loss on attached persistent block storage. Cited supporting sections in subtopic: https://docs.cloud.google.com/compute/docs/instance-groups#support_for_stateful_workloads
