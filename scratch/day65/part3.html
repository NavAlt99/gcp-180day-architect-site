Cloud SQL Private Service Connect Connection Pool Exhaustion and Conflated Liveness Probe Outage · field case

Situation and impact: Brightloaf launched a nationwide marketing campaign promoting artisanal holiday gift baskets, driving a sudden 12-fold surge in checkout traffic to 5,000 QPS on the order-service API. The service was hosted on Cloud Run in us-central1, configured with Direct VPC Egress to an internal subnet, connecting to a Regional HA Cloud SQL PostgreSQL 16 database over Private Service Connect (PSC IP 10.128.0.50:5432). As traffic surged, Cloud Run autoscaled from 5 to 60 container instances within 90 seconds. Immediately, the checkout API degraded: response latency spiked from 45ms to over 15 seconds, and the Global external ALB began returning HTTP 503 Service Unavailable to 62% of incoming shoppers. Within 18 minutes, 18,500 customer orders failed mid-checkout, stranding $129,500 in revenue, causing severe reputational damage, and triggering hundreds of merchant payment dispute alerts.

Diagnostic sequence:

  1. Edge Telemetry & HTTP Status Codes: Cloud Monitoring metrics for the external ALB (loadbalancing.googleapis.com/https/request_count) showed response_code_class = 500 surging to 3,100 QPS. The backend service status showed that 48 out of 60 Cloud Run container instances were marked unhealthy or unavailable by GFE health checkers.
  2. Direct VPC Egress Network Exhaustion: Inspecting Cloud Run system logs in Cloud Logging revealed critical networking failures during container scale-up: Direct VPC Egress: IP address exhaustion in subnet projects/brightloaf-prod/regions/us-central1/subnetworks/cloud-run-egress (CIDR 10.128.10.0/28). The subnet had been provisioned with a /28 CIDR mask, providing only 11 usable IP addresses after accounting for GCP reserved gateway IPs. As Cloud Run attempted to provision beyond 11 instances, containers failed to bind network interfaces and entered crash loops.
  3. Database Backend Connection Saturation: Querying Cloud SQL PostgreSQL metrics revealed cloudsql.googleapis.com/database/postgresql/num_backends pinned at exactly 250 (100% of configured max_connections). Application container logs were flooded with fatal PostgreSQL connection pool errors: psycopg2.OperationalError: FATAL: remaining connection slots are reserved for non-replication superuser connections. Each container had initialized an unmanaged pool of 20 connections, attempting to open 60 × 20 = 1,200 concurrent TCP connections to the single primary database instance over PSC.
  4. Readiness Probe Absence & Traffic Admission: Inspecting the Cloud Run service YAML revealed that engineering had configured a single liveness probe on /healthz (which merely verified that the Python process was running) but completely omitted a readiness probe (/readyz). Consequently, the ALB GFE routed incoming user checkout requests to newly spawned container instances within 300ms of boot—long before the containers had established their database connection pools or completed PSC handshakes. Incoming requests immediately encountered connection acquisition timeouts, generating cascading 503 errors.

Root cause: A compound architectural breakdown across networking, datastore sizing, and lifecycle health checks: (1) Direct VPC Egress was constrained to a minuscule /28 subnet, starving autoscaled serverless instances of IP allocations; (2) Connection pool sizing per container instance was uncoordinated with the PostgreSQL database capacity, exceeding max_connections by 480%; and (3) The omission of a dedicated /readyz readiness probe caused the ALB to route production traffic to uninitialized containers during cold starts.

Defensible remediation:

  1. Expand Direct VPC Egress Subnet: Provision a dedicated /24 subnet (providing 251 usable IP addresses) specifically for Cloud Run Direct VPC Egress, eliminating IP starvation up to maximum horizontal scale: 
    gcloud compute networks subnets create cloud-run-egress-v2 \
    --network=brightloaf-vpc \
    --region=us-central1 \
    --range=10.128.10.0/24
    Update the Cloud Run service to attach to the expanded subnet with private ranges routing: 
    gcloud run services update order-service \
    --region=us-central1 \
    --network=brightloaf-vpc \
    --subnet=cloud-run-egress-v2 \
    --vpc-egress=private-ranges-only
  2. Right-Size Connection Pools and Deploy PgBouncer: Reconfigure the application connection pool to cap maximum active connections at 4 per container instance, and cap Cloud Run autoscaling at max-instances = 50, guaranteeing that total database connections never exceed 200 (well within PostgreSQL's 250 ceiling). Deploy a regional PgBouncer proxy on the PSC network path configured in transaction pooling mode for future scale.
  3. Decouple Liveness from Readiness: Implement a distinct /readyz endpoint in order-service that validates database connection pool acquisition before returning HTTP 200. Configure Cloud Run readiness and liveness probes: 
    gcloud run services update order-service \
    --region=us-central1 \
    --liveness-probe-path=/healthz \
    --liveness-probe-initial-delay=5s \
    --liveness-probe-period=10s \
    --readiness-probe-path=/readyz \
    --readiness-probe-initial-delay=2s \
    --readiness-probe-period=3s \
    --readiness-probe-failure-threshold=2

Verification: The remediation was validated using an automated synthetic load test in staging, ramping traffic from 100 QPS to 5,500 QPS over 60 seconds. Cloud Monitoring confirmed that Cloud Run scaled smoothly to 50 instances across the /24 subnet with zero IP allocation errors. Cloud SQL active connection metrics peaked at 198 (below the 250 ceiling). Container readiness checks held ALB traffic admission for an average of 2.1 seconds during container cold starts, resulting in zero connection reset errors and a 100% success rate across 150,000 synthetic transactions.

Residual Risk: Sustained traffic surges exceeding 5,000 QPS may cause Cloud Run instances to reach their maximum pool capacity (50 instances × 4 connections = 200 connections), queuing requests at the container level. To scale beyond this limit, an architectural migration to transaction-pooled PgBouncer or AlloyDB for PostgreSQL will be required.

Dropped W3C Trace Context across Pub/Sub, Inventory Oversell Race Condition, and Unverified OIDC Dispatch · field case

Situation and impact: Brightloaf launched a flash promotion offering a limited batch of 500 artisan sourdough loaves at a promotional price. Ingress traffic peaked at 1,800 QPS. Within minutes, multiple cascading data and security anomalies emerged: (1) Over 150 loaves were oversold beyond physical bakery stock, resulting in inventory_count = -150 and forcing the customer care team to issue $34,000 in refunds and apology gift cards; (2) An unauthorized internal data ingestion cron job inadvertently called the asynchronous fulfillment service directly, triggering duplicate shipments on 400 orders; and (3) When site reliability engineers attempted to investigate the failure in Cloud Trace, the trace graphs abruptly terminated at the Cloud Run API boundary, completely omitting the asynchronous fulfillment worker processing hops and blinding on-call engineers for 45 minutes.

Diagnostic sequence:

  1. Trace Discontinuity Audit: SREs queried Cloud Trace using incoming traceparent IDs collected from customer support refund tickets. In Cloud Trace, spans showed the ALB edge request (3ms) and Cloud Run order-service execution (42ms), followed by a Pub/Sub publish call. However, zero asynchronous spans existed for the fulfillment-service. Inspecting publisher code revealed that while the API captured the incoming traceparent header, it published the event payload to Cloud Pub/Sub topic orders.v1 as raw bytes without populating message attributes. Consequently, the fulfillment worker had no parent trace context and generated isolated, unlinked trace IDs.
  2. Inventory Race Condition Analysis: Database inspection revealed that inventory.stock for artisan sourdough reached -150. Reviewing the application checkout logic revealed that inventory checking was executed as an optimistic application-level assertion: 
    # VULNERABLE CODE: TOCTOU Race Condition
stock = db.query("SELECT stock FROM inventory WHERE item_id = :id")
if stock >= quantity:
    db.execute("UPDATE inventory SET stock = stock - :qty WHERE item_id = :id")
    Under 1,800 QPS concurrent load, 35 threads simultaneously read stock = 1 before any single thread could commit the decrement. Furthermore, the inventory table lacked a database-level CHECK (stock >= 0) constraint, allowing concurrent updates to drive stock deeply negative.
  3. Unauthorized Dispatch & Deduplication Failure: Reviewing Cloud Logging for fulfillment-service revealed two independent log streams processing identical order_id values 14 seconds apart. The second stream was initiated by an internal analytics test runner calling the fulfillment HTTP webhook directly. The fulfillment service had been deployed with --allow-unauthenticated enabled and lacked OIDC signature verification middleware. Furthermore, the worker inserted fulfillment dispatch records without checking a deduplication table, executing physical packing orders twice.

Root cause: Three critical architectural violations: (1) Failure to inject W3C traceparent and X-Request-Id headers into Cloud Pub/Sub message attributes stripped distributed trace context across the asynchronous boundary; (2) Reliance on optimistic application-layer inventory checks without database row locking (FOR UPDATE) or database-level CHECK constraints violated the Inventory Integrity invariant; and (3) Ingress security perimeter omission allowed unauthenticated internal HTTP calls to bypass IAM, while missing consumer deduplication violated the Exactly-One Fulfillment invariant.

Defensible remediation:

  1. Enforce Hard Database Inventory Constraints & Pessimistic Locking: Add a hard check constraint in PostgreSQL preventing stock from ever dropping below zero: 
    ALTER TABLE inventory ADD CONSTRAINT chk_inventory_non_negative CHECK (stock >= 0);
    Update the checkout transaction to acquire a pessimistic row-level lock prior to decrementing stock: 
    BEGIN;
SELECT stock FROM inventory WHERE item_id = :id FOR UPDATE;
UPDATE inventory SET stock = stock - :qty WHERE item_id = :id;
INSERT INTO orders (order_id, customer_id, total, status) VALUES (...);
INSERT INTO outbox_events (event_id, aggregate_id, payload, traceparent) VALUES (...);
COMMIT;
  2. Propagate W3C Trace Context across Pub/Sub: Update the outbox relay publisher to inject traceparent and x-request-id into Pub/Sub message attributes. Update the fulfillment worker to extract attributes and resume the parent span: 
    # Publisher context injection
message = pubsub_v1.PubsubMessage(
    data=json.dumps(event_payload).encode("utf-8"),
    ordering_key=order_id,
    attributes={
        "traceparent": current_traceparent,
        "x-request-id": current_request_id
    }
)
  3. Enforce OIDC Verification & Consumer Deduplication Table: Re-deploy fulfillment-service with authentication enforced (--no-allow-unauthenticated) and verify Google-signed OIDC ID tokens. In the consumer, enforce the Crash-Before-Ack discipline using a dedicated processed_events deduplication table: 
    INSERT INTO processed_events (event_id, order_id)
VALUES (:evt_id, :ord_id)
ON CONFLICT (order_id) DO NOTHING;
    If zero rows are inserted, acknowledge the message immediately and bypass physical fulfillment.

Verification: The fix was tested in the staging environment by running a high-concurrency race simulation script executing 100 concurrent checkout threads against a stock balance of exactly 10 loaves. The database successfully committed 10 purchases and immediately threw CheckViolation errors on the remaining 90 concurrent attempts, keeping final stock at exactly 0. Concurrently, synthetic unauthenticated HTTP POST requests to fulfillment-service were instantly rejected with HTTP 401 Unauthorized. The test published 50 identical Pub/Sub event IDs; the consumer processed the first message and discarded the remaining 49 as duplicates, proving exactly-one fulfillment.

Residual Risk: Pessimistic row locking (SELECT ... FOR UPDATE) on high-demand inventory records serializes database writes on that specific row, potentially increasing transaction latency during extreme hot-spot flash sales. When scaling beyond 10,000 QPS on a single SKU, inventory partitioning or reserved allocation buckets will be necessary.
