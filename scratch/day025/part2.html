Topic 01 · Roles: basic (Owner/Editor/Viewer, avoid in production), predefined, custom

Google Cloud Identity and Access Management (IAM) controls access through permissions bundled into roles. Every action in Google Cloud maps to an atomic REST API permission formatted as service.resource.verb (such as compute.instances.start or storage.objects.create). Rather than granting individual permissions directly to principals, IAM requires permissions to be packaged into roles.

The Three Role Tiers

Google Cloud segments roles into three distinct tiers with differing lifecycles, maintenance burdens, and blast radiuses:

  • Basic (Primitive) Roles: The historical roles that originated with Google Cloud Platform: roles/owner, roles/editor, and roles/viewer. These roles apply universally across virtually all Google Cloud services. roles/viewer grants read-only access to almost all metadata and data; roles/editor grants permissions to modify, deploy, create, and delete resources across all services; and roles/owner adds billing administration, project ownership management, and IAM policy modification. Basic roles must be prohibited in production environments because they violate least privilege by design, providing broad horizontal reach across unassociated systems.
  • Predefined Roles: Curated and maintained by Google Cloud service engineering teams. Examples include roles/pubsub.publisher, roles/storage.objectAdmin, and roles/spanner.databaseUser. When Google releases new API methods or features for a service, Google automatically updates the predefined role to include relevant new permissions without customer intervention. Predefined roles represent the recommended default for enterprise architectures.
  • Custom Roles: Customer-authored collections of fine-grained permissions created at the Organization (organizations/{org-id}/roles/{role-id}) or Project (projects/{project-id}/roles/{role-id}) level. Custom roles are necessary when predefined roles are too permissive (for instance, granting unwanted deletion or IAM modification verbs alongside operational read/write access). However, custom roles carry a notable maintenance burden: Google does not automatically update custom roles when new API methods are added, and certain permissions (such as billing or specialized third-party integrations) cannot be included in custom roles.

Topic 02 · IAM policy structure: bindings, members, roles, conditions

An IAM policy attached to a Google Cloud resource defines who has what access. The policy payload is represented as a structured object containing three primary elements:

  1. bindings: A list of associations. Each binding specifies exactly one role and one or more members (principals such as user:, serviceAccount:, or group:).
  2. version: The schema version of the policy document. Policies created without conditional bindings default to version 1. Any policy containing Common Expression Language (CEL) conditions must specify version 3. If a client attempts to write a policy with conditions while specifying version 1, the IAM API rejects the call. Conversely, reading a version 3 policy with an older version 1 client unwinds or obscures conditional expressions.
  3. etag: A base64-encoded concurrency token used for optimistic concurrency control. Updates to IAM policies must include the existing etag to prevent race conditions from overwriting concurrent modifications.

Common Expression Language (CEL) Conditions

IAM Conditions allow role bindings to take effect only when a specified expression evaluates to true. The condition is expressed using Google's Common Expression Language (CEL), a fast, non-Turing-complete, memory-safe expression language. IAM condition expressions evaluate against three attribute namespaces:

  • Request Attributes (request.*): Attributes describing the incoming API call itself. Key attributes include request.time (RFC 3339 timestamp), and request.auth.claims (claims extracted from workforce identity pool tokens or JWTs).
  • Resource Attributes (resource.*): Attributes describing the target resource being accessed. Key attributes include resource.name (the full Google Cloud resource URI), resource.type (e.g., compute.googleapis.com/Instance), and resource.service.
  • Tag Attributes (resource.tags/*): Hierarchical resource tags attached to the resource or inherited from ancestor folders/organization. Tags provide cryptographic tamper-proof boundaries distinct from editable metadata labels.

Topic 03 · Policy inheritance and the effective policy

Google Cloud organizes all resources into a strict hierarchy: Organization → Folders → Projects → Resources. IAM policy evaluation relies on a foundational rule known as additive inheritance. Access granted at any ancestor level in the hierarchy cannot be taken away or overridden by standard IAM policies at a descendant level.

Calculating the Effective Policy

The effective policy is the computational union of all role bindings attached directly to the target resource plus all role bindings attached to every ancestor node in its hierarchical lineage. When a principal requests an action on a resource (for example, reading an object from Cloud Storage):

  1. The IAM evaluation engine inspects the resource's direct IAM policy. If any binding grants the required permission (and passes any CEL condition), access is granted immediately.
  2. If the direct policy does not satisfy the permission, the engine evaluates the containing project's policy.
  3. If unsatisfied, the engine steps up through parent folders sequentially.
  4. Finally, the engine checks the root organization policy.
  5. If no policy at any level grants the permission, the request terminates with 403 PERMISSION_DENIED.

Because standard IAM policies cannot explicitly deny permissions, an overprivileged role grant at the Folder level (e.g., granting roles/editor on a "Production" folder) permanently taints every project and resource beneath that folder, rendering local project-level least privilege impossible.

Important Distinctions in Authorization Controls

Standard IAM policies are strictly additive (allow-only). To enforce explicit negative constraints across the hierarchy, architects must use either IAM Deny Policies (which override all allow policies at lower and equal levels) or Organization Policy Constraints (which govern resource configuration rather than principal identity). Standard IAM allow policies can never revoke an inherited grant.
