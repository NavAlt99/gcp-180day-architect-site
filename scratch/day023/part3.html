Brightloaf Incident 23.1 · Automated workspace pruning deletes shared production artifact registry

Context & Architecture: The following operational crisis represents a synthetic engineering postmortem from Brightloaf's centralized platform engineering team. Brightloaf hosts its shared container base images, Helm charts, and microservice deployment packages inside Google Cloud project bl-shared-artifacts-prod. All regional bakery Kubernetes (GKE) clusters and CI/CD deployment pipelines authenticate against Artifact Registry repositories within this central project to pull running container software.

Failure Symptom

At 07:12 UTC, during morning peak traffic across 450 franchise stores, GKE worker nodes executing an automated autoscaling event failed to pull updated microservice images. Pod statuses collapsed into ImagePullBackOff cascades across all regional clusters. Terminal application logs on the API gateways emitted severe container runtime errors:

Failed to pull image "us-docker.pkg.dev/bl-shared-artifacts-prod/bakery-pos/order-api:v2.4":
rpc error: code = Unknown desc = failed to pull and unpack image:
failed to resolve reference: unexpected status from GET request:
https://us-docker.pkg.dev/v2/bl-shared-artifacts-prod/bakery-pos/order-api/manifests/v2.4:
403 Forbidden: Project bl-shared-artifacts-prod is pending deletion.

Within minutes, autoscaling was paralyzed, and regional bakery cash registers were unable to communicate with backend order ingestion services.

Operational & Business Constraints

  • Zero Transaction Drop & Invariant Preservation: Franchise retail transactions must not be lost; point-of-sale cash registers buffer orders locally for up to four hours. Crucially, replaying an order or re-ingesting events from terminal queues must never cause a second physical fulfillment (≤ 1 physical fulfillment per unique order ID). Double-baking dough batches creates costly waste and franchisee billing disputes.
  • Recovery Time Objective (RTO): The central container registry must be restored in under 30 minutes to prevent total store checkout paralysis.
  • Service Continuity: Existing running container pods must continue processing in-flight transactions without disruption while image pull capability is repaired.

Discovered Evidence

Platform security audit investigation established the following facts:

  1. Cloud Audit Log Entry: Central activity logs recorded a project shutdown API call: 
    {
  "protoPayload": {
    "@type": "type.googleapis.com/google.cloud.audit.AuditLog",
    "serviceName": "cloudresourcemanager.googleapis.com",
    "methodName": "google.cloud.resourcemanager.v3.Projects.DeleteProject",
    "resourceName": "projects/bl-shared-artifacts-prod",
    "authenticationInfo": {
      "principalEmail": "ci-cleaner-sa@brightloaf-ops.iam.gserviceaccount.com"
    }
  },
  "timestamp": "2026-09-27T07:11:45.302Z"
}
  2. Automation Script Regex Flaw: An automated scheduled Cloud Function configured to prune expired ephemeral test projects executed a regex match: re.match(r"bl-.*-artifacts-.*", proj_id), which inadvertently matched the production project bl-shared-artifacts-prod instead of ephemeral staging environments.
  3. Absence of Project Lien: Querying the project for protective liens revealed zero configured liens: 
    gcloud resource-manager liens list --project=bl-shared-artifacts-prod
Listed 0 items.
    Because no lien existed, the Cloud Resource Manager API accepted the deletion request immediately without requiring human confirmation.

Root Cause Analysis

The outage was caused by the combination of an overly permissive automated cleanup script and the complete absence of a protective Project Lien (resourcemanager.lien). The automated cleanup service account possessed roles/resourcemanager.projectDeleter. When a flawed regex matched the shared production project ID, the deletion call proceeded without resistance, transitioning the project into DELETE_REQUESTED. This state immediately decoupled Cloud Billing and shut down Artifact Registry API endpoints, preventing all GKE clusters from pulling images during morning autoscaling.

5-Step Diagnostic Sequence

  1. Inspect Registry HTTP Error: Review GKE kubelet events and image pull errors; observe the HTTP 403 response indicating Project is pending deletion.
  2. Query Resource Manager Project State: Run the project description command to confirm the lifecycle state is DELETE_REQUESTED.
  3. Identify Caller in Audit Logs: Search Cloud Audit Logs for DeleteProject calls to discover the executing principal identity and source script.
  4. Audit Project Liens: Run the liens list command to verify why the deletion call was not blocked at the control plane gateway.
  5. Verify Edge POS Buffer & Invariant: Inspect store telemetry to ensure store cash registers are safely buffering orders in encrypted local queues with unique idempotency UUIDs.

Defensible Solution & Remediation

  1. Execute Immediate Project Undelete: Recover the project within its 30-day soft recovery window using the Resource Manager API: 
    gcloud projects undelete bl-shared-artifacts-prod
  2. Re-attach Cloud Billing Account: Soft-deletion severs billing associations; immediately re-link the corporate billing account to restore API quota and services: 
    gcloud billing projects link bl-shared-artifacts-prod   --billing-account=01A2B3-4C5D6E-7F8A9B
  3. Apply Immutable Project Lien: Create a persistent Project Lien to programmatically prevent any future deletion: 
    gcloud resource-manager liens create   --project=bl-shared-artifacts-prod   --restrictions=resourcemanager.projects.delete   --reason="Production shared artifact registry; deletion strictly forbidden"
  4. Least-Privilege Cleanup Automation: Strip roles/resourcemanager.projectDeleter from the cleanup service account; restrict its scope exclusively to an ephemeral sandbox folder.
  5. Drain POS Queue & Guarantee Invariant: With Artifact Registry restored, GKE nodes scale cleanly. Cash register POS queues drain their buffered transactions into the order ingestion topic. The backend deduplication ledger verifies order UUID hashes, guaranteeing that replaying events causes zero duplicate bakery fulfillments (≤ 1 physical fulfillment per unique order ID).

Verification and Residual Risk

Verification: GKE image pull tests for order-api:v2.4 succeeded with HTTP 200 within 4 minutes of re-linking billing. Subsequent execution of the project deletion command failed with HTTP 400 FAILED_PRECONDITION: A lien is preventing this project from being deleted. Store telemetry verified all 450 bakeries completed morning checkout draining with zero dropped or duplicate orders.

Residual Risk: Soft-deleted projects release static external IP reservations immediately upon entering DELETE_REQUESTED. For workloads relying on external static IPs rather than DNS hostnames, IP recovery is not guaranteed if another customer claims the released IP.

Brightloaf Incident 23.2 · Team-first hierarchy collision leaks staging load into production cluster

Context & Architecture: The following operational crisis represents a synthetic systems engineering postmortem from Brightloaf's Mobile Ordering engineering division. Brightloaf organized its resource hierarchy using a Team-First structure, grouping projects under department folders (e.g. folders/619283019284 labeled /Mobile-App-Division). Both the production mobile backend (bl-mobile-prod) and the staging environment (bl-mobile-staging) were nested together inside this shared departmental folder.

Failure Symptom

At 11:30 UTC, during the lunchtime ordering surge, the production PostgreSQL database supporting mobile customer checkouts suffered massive connection exhaustion. Transaction response latencies spiked from 25 milliseconds to over 45 seconds, triggering an automated database crash restart. Cloud Monitoring alerts reported critical database saturation:

PostgreSQL Alert [FATAL]: Remaining connection slots are reserved for non-replication superuser connections.
Active Connections: 2,048 / 2,048 (100% Exhaustion)
Client IP Range: 10.200.40.0/24 (Staging Performance Benchmark Cluster)

Thousands of retail customers using the mobile app were greeted with spinning payment screens and failed order submissions, resulting in approximately 4,000 in abandoned bakery shopping carts.

Operational & Business Constraints

  • Fulfillment Invariant Protection: In accordance with Brightloaf's fundamental rule, replaying failed transactions or handling client retries must never cause duplicate physical bakery fulfillments (≤ 1 physical fulfillment per unique order ID). Partially committed database sessions must be cleanly rolled back.
  • Immediate Isolation: Non-production test traffic must be cut off from production databases instantly without requiring a full production application restart.
  • Continuous Compliance: Strict separation of duties between non-production developers and production data stores must be enforced to maintain SOC 2 compliance.

Discovered Evidence

Investigation across IAM policies, folder bindings, and database connection logs revealed:

  1. Inherited Folder-Level IAM Grant: The mobile engineering Google Group group:mobile-developers@brightloaf.com was granted roles/editor at the parent folder /Mobile-App-Division. Because permissions are additive, this grant gave all developers full read, write, and network administration privileges across both staging and production projects.
  2. Misconfigured Test Runner: A performance engineer ran a distributed locust benchmark intended to stress-test a new mobile menu caching layer. An environment variable file in the test runner contained DATABASE_HOST=10.128.4.15 (the private IP of the production database instance in bl-mobile-prod) rather than the staging database IP.
  3. Shared VPC Peering Route: A legacy VPC Network Peering connection between the staging VPC and production VPC lacked firewall ingress rules blocking port 5432, allowing the benchmark runner to open 2,000 parallel database connections.

Root Cause Analysis

The root cause was architectural failure in folder hierarchy design. Adopting a flat Team-First folder structure placed production and non-production projects in the same administrative container. A broad roles/editor binding assigned at the team folder inherited directly into production. Coupled with an unsegmented network peering route, there was no administrative or network boundary preventing a staging test script from saturating the production database cluster.

5-Step Diagnostic Sequence

  1. Query Active Database Connections: Execute pg_stat_activity on the PostgreSQL primary to identify client IP addresses, connection counts, and active query strings.
  2. Trace Source IP to Project: Correlate the source IP subnet 10.200.40.0/24 with VPC route tables to identify that connections originated from the staging benchmark GKE cluster.
  3. Inspect Folder Hierarchy & IAM Inheritance: Trace the parent folder structure to reveal that bl-mobile-prod and bl-mobile-staging shared the /Mobile-App-Division folder where developers held inherited roles/editor.
  4. Audit Network Firewall Rules: Inspect VPC ingress rules on the production database subnet, discovering that port 5432 was open to the peered staging subnet.
  5. Verify Deduplication Ledger & Rollbacks: Query the orders database transaction table to verify that incomplete benchmark transactions were rolled back and that customer order IDs maintained exact deduplication hashes.

Defensible Solution & Remediation

  1. Immediate Network Ingress Cut: Deploy an emergency high-priority VPC firewall rule blocking all ingress from non-production subnets to port 5432: 
    gcloud compute firewall-rules create drop-staging-to-prod-db   --network=bl-production-vpc   --priority=100   --action=DENY   --rules=tcp:5432   --source-ranges=10.200.0.0/16
  2. Reorganize Hierarchy into Environment-First Topologies: Decommission the /Mobile-App-Division folder and migrate projects into top-level environment folders: /Production/Mobile and /Non-Production/Mobile.
  3. Restrict IAM Scoping: Assign developer write and testing roles strictly at the /Non-Production folder branch. In /Production, developers hold strictly read-only logging roles (roles/logging.viewer), with production deployments restricted to CI/CD service accounts.
  4. Rotate Production Database Credentials: Immediately cycle all database passwords and IAM database authentication tokens to terminate any lingering developer session configurations.
  5. Validate Order Fulfillment Invariant: Verify that aborted customer payment sessions did not dispatch printing instructions to local bakery ovens. Customers whose sessions timed out were prompted to re-submit; the application idempotency layer matched resubmitted UUID tokens, guaranteeing ≤ 1 physical fulfillment per unique order ID.

Verification and Residual Risk

Verification: Testing connections from the staging benchmark cluster to 10.128.4.15:5432 confirmed immediate TCP RST / drop by the firewall. Production database active connections returned to normal baseline (42 connections), and latency dropped to 18 ms. Audit logs confirmed developers no longer hold write access in /Production.

Residual Risk: Reorganizing enterprise folder hierarchies requires migrating active projects between folders, which temporarily locks project moves during active Shared VPC or IAM propagation.

Brightloaf Incident 23.3 · Unconstrained offshore compute deployment triggers data residency breach

Context & Architecture: The following operational crisis represents a synthetic cloud compliance postmortem from Brightloaf's enterprise data architecture team. Brightloaf operates under strict regulatory mandates and consumer protection standards requiring all customer personal data, transaction histories, and franchise banking records to reside and process exclusively within continental United States borders.

Failure Symptom

At 16:45 UTC, Brightloaf's automated Security Command Center (SCC) dashboard triggered a critical compliance finding:

SECURITY FINDING [CRITICAL]: Data Residency and Public Exposure Violation!
Resource: //compute.googleapis.com/projects/bl-analytics-prod/zones/europe-west3-b/instances/ml-perf-node-01
Issue 1: Physical provisioning in unapproved offshore region (europe-west3).
Issue 2: Instance possesses external public IP address (35.198.112.45).
Data Access: Active read queries executed against Cloud Storage bucket containing US retail sales logs.

An unauthorized virtual machine had been provisioned in an overseas European data center with a public internet IP address, actively pulling confidential franchise order transaction archives.

Operational & Business Constraints

  • Mandatory Data Sovereignty: Customer PII, bakery payment records, and POS transaction files must never leave approved domestic storage and compute zones. Cross-border transfer triggers severe regulatory fines and mandatory customer notifications.
  • Order Invariant Preservation: Active production order streams and ETL pipelines must continue normal operations without data corruption or duplicate physical bread production (≤ 1 physical fulfillment per unique order ID).
  • Immutable Control Plane Enforcement: Security policies must prevent recurrence programmatically rather than relying on developer vigilance or manual reviews.

Discovered Evidence

Cloud Audit Logs and Terraform state inspection revealed:

  1. Contractor Terraform Execution: A contract machine learning engineer working on bread waste forecasting was granted roles/compute.admin in bl-analytics-prod to evaluate model training speeds. Faced with GPU spot capacity limits in US regions, the contractor modified their local Terraform script to deploy a high-memory VM in europe-west3-b (Frankfurt) with an ephemeral public IP for direct SSH access.
  2. IAM Authorization Succeeded: Because the contractor possessed roles/compute.admin, IAM evaluated the API call as fully authorized.
  3. Absence of Organization Policy Guardrails: The Organization node lacked active Organization Policy constraints for constraints/gcp.resourceLocations and constraints/compute.vmExternalIpAccess, allowing the offshore deployment to proceed without warning.

Root Cause Analysis

The breach occurred because the cloud platform relied exclusively on IAM permissions without enforcing Organization Policy Service guardrails. IAM only verifies identity permissions (who can call the API). Without Organization Policy constraints governing resource configurations (what configurations can exist), an identity with legitimate compute administrative privileges was able to violate sovereign data boundaries and expose an unshielded public IP address to the internet.

5-Step Diagnostic Sequence

  1. Review Security Command Center Finding: Inspect finding details to identify instance name, zone (europe-west3-b), external IP (35.198.112.45), and creation timestamp.
  2. Query Activity Audit Logs: Search Cloud Audit Logs for compute.instances.insert to determine caller identity, authentication method, and provisioning client parameters.
  3. Audit Current Organization Policies: Run the organization policy list command at the organization root to confirm whether location or external IP constraints were configured or inherited.
  4. Inspect Ingress / Egress Flow Logs: Analyze VPC Flow Logs for IP 35.198.112.45 to verify whether external actors connected to the instance or if customer data was exfiltrated to external IPs.
  5. Audit Order Event Queues & Invariant: Verify that domestic order ingestion pipelines remained unaffected and that all processed transactions maintained unique idempotency tokens.

Defensible Solution & Remediation

  1. Immediate Instance Termination: Destroy the non-compliant offshore compute instance immediately using the Compute Engine API: 
    gcloud compute instances delete ml-perf-node-01   --zone=europe-west3-b   --project=bl-analytics-prod   --quiet
  2. Enforce Resource Location Org Policy: Apply a centralized Organization Policy List Constraint at the Organization root restricting all resource creation strictly to US locations: 
    gcloud resource-manager org-policies set-policy policy-resource-locations.yaml   --organization=714029482103

    Where policy-resource-locations.yaml specifies allowed_values: ["in:us-locations"] under constraint constraints/gcp.resourceLocations.

  3. Enforce External IP Restriction Org Policy: Apply a Boolean Constraint at the Organization root denying external IP addresses across all Compute Engine VMs: 
    gcloud resource-manager org-policies enable-enforce   compute.vmExternalIpAccess   --organization=714029482103
  4. Deploy Cloud NAT & IAP for Secure Access: Provision Cloud NAT in authorized US regions for required outbound package updates and enforce Identity-Aware Proxy (IAP) TCP forwarding for secure administrative SSH access without public IPs.
  5. Verify Order Invariant Across Domestic Pipelines: Re-run audit verification on domestic order streams, confirming zero transaction leakage and guaranteeing that all processed orders adhere to ≤ 1 physical fulfillment per unique order ID.

Verification and Residual Risk

Verification: Re-running Terraform to deploy an instance in europe-west3 failed instantly at the control plane gateway: HTTP 400 FAILED_PRECONDITION: Organization Policy constraint constraints/gcp.resourceLocations violated. Attempting to allocate an external IP in us-central1 similarly failed with constraints/compute.vmExternalIpAccess violated. Flow log analysis confirmed zero customer records escaped domestic boundaries before instance shutdown.

Residual Risk: Organization policies apply strictly to new resource creation and mutations; existing non-compliant resources instantiated prior to policy enforcement are not automatically shut down and must be identified via Security Command Center audits.
