Project lifecycle mechanics, shutdown states, and lien-based deletion protection

In Google Cloud, a Project is the fundamental boundary for infrastructure ownership, IAM identity evaluation, API enablement, and cost tracking. Understanding the deterministic state transitions of a project lifecycle is critical for architecting resilient production systems and automated decommissioning pipelines.

Lifecycle States: Active, Pending Deletion, and Purged

A project progresses through three distinct states in the Cloud Resource Manager API:

  1. ACTIVE: The project is fully functional. Resources can be created, APIs are operational, service agents authenticate, and Cloud Billing processes charges for provisioned infrastructure.
  2. DELETE_REQUESTED (The 30-Day Soft Recovery Window): When a deletion request is initiated (via the Resource Manager API projects.delete), the project immediately transitions into a soft-deleted state:
    • All running Compute Engine instances, GKE nodes, and Cloud SQL instances are stopped immediately.
    • Static external IP addresses and internal subnet reservations are released back to the global pool.
    • Cloud Billing associations are severed immediately; no further compute charges accrue.
    • Underlying persistent disks, Cloud Storage buckets, and configuration metadata are retained in a frozen state for exactly 30 days.
    • During this 30-day window, a principal granted the roles/resourcemanager.projectDeleter role can call projects.undelete to reverse the shutdown and restore access.
  3. DELETED (Permanent Hard Purge): Exactly 30 days after the deletion request, Google Cloud initiates automated cryptographic erasure across all underlying storage systems. The project metadata is deleted from the global directory, and the globally unique Project ID is permanently retired. Google Cloud never recycles or reissues a project ID.

Protecting Critical Workloads via Project Liens

To prevent catastrophic outages caused by automated script errors or administrative misclicks, Google Cloud provides Project Liens (resourcemanager.lien). A lien places a declarative lock on a project container, blocking deletion at the admission boundary:

  • Mechanism: A lien declares a restriction (specifically resourcemanager.projects.delete), an origin string (such as terraform-production-lock), and a human-readable reason.
  • Enforcement: When a lien exists on a project, any attempt to delete the project—even by a Project Owner or Organization Administrator—is rejected with an HTTP 400 Bad Request / FAILED_PRECONDITION error: "A lien is preventing this project from being deleted."
  • Lifecycle: Deletion can only proceed after an authorized principal with roles/resourcemanager.lienModifier explicitly deletes the lien resource. All enterprise landing zones should mandate that Terraform automatically creates liens on production and shared-services projects during provisioning.

Hierarchy design patterns: Environment-First vs. Team-First vs. Hybrid topologies

Enterprise landing zone architecture requires structuring Folders beneath the Organization root to enforce operational boundaries. Choosing between Environment-First, Team-First, and Hybrid topologies defines how IAM policies inherit, how Organization Policy guardrails apply, and how cross-environment risks are contained.

Topological Patterns Compared

  • Environment-First Topology: Top-level folders represent environment lifecycle stages (/Production, /Non-Production, /Sandbox). Under each environment folder, child folders represent business units or product teams.
    • Advantages: Superior security isolation. Broad developer write grants can be assigned safely at /Non-Production without risking permission leakage into /Production. Organization Policy guardrails (such as blocking external IPs or enforcing CMEK encryption) can be applied strictly across the entire production estate.
    • Trade-offs: Cross-environment team visibility requires engineers to navigate separate folder trees.
  • Team-First (Department-First) Topology: Top-level folders represent departments or business units (/Retail-Bakery, /Logistics, /Analytics), with environment folders (/Prod, /Staging, /Dev) nested underneath each team.
    • Advantages: Aligns with corporate organizational charts; team leads enjoy localized governance over their entire technology stack.
    • Trade-offs: Severe risk of permission contamination. Administrators frequently assign broad team roles at the top-level department folder, unintentionally granting developers production write access. Applying uniform organization policies requires duplicating policies across dozens of separate environment folders.
  • Hybrid / Matrix Topology: Combines top-level functional infrastructure containers (such as /Shared-Core-Services and /Security-Audit) alongside Environment-First business folders, providing dedicated landing zones for centralized networking (Shared VPC host projects) and security logging sinks.

Organization Policy Service: Centralized guardrails overriding IAM

The Organization Policy Service provides centralized, programmatic governance that configures constraints across the Google Cloud resource hierarchy. While IAM controls identities and dictates which principals can call specific APIs, Organization Policies control resources and define what configurations are legally allowed to exist.

The Architectural Distinction: IAM vs. Organization Policy

A fundamental principle of enterprise cloud architecture is that Organization Policies act as an absolute veto power that overrides IAM privileges. Even if a principal is granted roles/owner on a project or roles/resourcemanager.organizationAdmin at the organization root, an API request that violates an active Organization Policy constraint will be rejected at the control plane gateway before the resource is allocated.

Constraint Types: Boolean vs. List Constraints

Organization policy constraints fall into two distinct functional categories:

  1. Boolean Constraints: Enforce or relax a specific binary rule across target resources. Key production examples include:
    • constraints/compute.vmExternalIpAccess: When enforced, completely blocks the assignment of external public IP addresses to Compute Engine virtual machines.
    • constraints/iam.disableServiceAccountKeyCreation: When enforced, blocks developers and automation scripts from generating downloadable user-managed service account private keys (JSON keys), forcing adoption of Workload Identity Federation.
    • constraints/compute.disableSerialPortAccess: Disables interactive serial console access to VMs, closing out-of-band backdoors.
  2. List Constraints: Restrict resource attributes to an explicit allowlist or denylist of string values. Key production examples include:
    • constraints/gcp.resourceLocations: Enforces physical data residency by restricting resource provisioning strictly to authorized geographic locations (e.g. allowed_values: ["in:us-locations"]).
    • constraints/compute.trustedImageProjects: Restricts which project sources can supply VM operating system boot images (e.g. allowing only projects/debian-cloud and corporate golden image projects).
    • constraints/iam.allowedPolicyMemberDomains: Restricts IAM member bindings strictly to authorized Google Workspace / Cloud Identity customer directory domains, blocking personal @gmail.com additions.
